# 0033 출처별 실제 수신 경로를 확인해요

- 상태: 완료 (erulabo의 카드 이후 실제 수신은 0032에서 사람이 확인해요. 아래 "검증하지 못한 것")
- 출처: [출처별 다운로드](../specs/subtitles.md#출처별-다운로드), [자막 후보 조회](../specs/subtitles.md#자막-후보-조회), [공개 자막 경로 조사](../brainstorm/web-gui-subtitles.md#공개-자막-경로-조사)
- 막는 티켓: 없음

## 작업

제품을 만들기 전에 확인할 일이에요. 결과 목표 3의 알려진 불확실성 가운데 출처별 실제 수신 경로의 재현성을 다뤄요.
2026-09-26의 표본은 출처마다 하나였고, Naver는 관리형 Chromium에서 다운로드를 확인하지 못했으며, 서버 브라우저로 받은 것은 erulabo뿐이에요.
`.scratch/`의 임시 실행물(0032의 배치나 기존 `.scratch/server-auth-browser`)에서 확인하고 제품 코드는 바꾸지 않아요.

- Anissia `/anime/caption/recent`에서 여섯 경로(erulabo, Blogger·Drive 개별 자막, Blogger·Drive 회차 ZIP, Tistory 일반 첨부, Tistory WinPNG, Naver 블로그 첨부)마다 새 표본을 둘 이상 골라요.
- 경로마다 Anissia 게시물 주소에서 서버의 파일 바이트까지 단계를 기록해요. 게시물에서 받을 파일을 찾는 단서, 원하는 회차를 고르는 단서, 브라우저가 필요한지 HTTP로 충분한지, 서명 URL의 유효 시간과 다시 얻는 방법, CAPTCHA·로그인 여부, 만료·오류 HTML을 자막과 가르는 신호를 봐요.
- 서버 브라우저의 다운로드가 서버 폴더에 실제로 떨어지는지 경로마다 확인해요(Naver는 꼭 다시 확인해요).
- Anissia 자막 정보의 회차 표시 `0`이 무엇을 뜻하는지(등록할 때의 기본값이 남은 것인지), 게시물 하나가 여러 회차를 담는 일이 얼마나 흔한지, 같은 제작자의 줄이 바뀔 때 게시물 주소가 바뀌는지(회차마다 새 게시물인지, 한 게시물을 고치는지) 표본으로 확인해요. Anissia 쪽 갱신 방식(줄 덮어쓰기, 자막 종료 시 줄 삭제, 제작자가 입력하는 `updDt`)은 2026-10-02에 소스로 확인했어요.
- 제작자가 Anissia 줄을 그대로 두고 게시물의 파일만 바꾸는 수정을 감지할 수 있도록, 경로마다 게시물의 파일 정보(이름·크기·날짜·해시 등)를 인증 없이 다시 읽을 수 있는지와 그 비용을 기록해요. 감지 주기를 둘지는 이 결과로 따로 정해요(사용자 결정, 2026-10-02).
- 결과로 공통 수신 결과와 실패 분류의 초안(받음, 인증 필요, 만료, 파일 아님, 출처 구조 바뀜, 네트워크 실패 등)과 출처별 작업 단계 목록을 만들어 [작업과 인증 명세의 남은 구체화](../specs/jobs.md#남은-구체화)를 갱신하고, 관찰 기록은 [공개 자막 경로 조사](../brainstorm/web-gui-subtitles.md#공개-자막-경로-조사)에 더해요.

## 완료 기준

| 확인 | 기대 결과 |
| --- | --- |
| 여섯 경로 | 경로마다 표본 둘 이상의 단계 기록과, 서버에 떨어진 파일의 크기·형식 확인이나 실패의 근거가 있어요. 한 경로의 성공을 다른 경로에 쓰지 않아요. |
| 브라우저와 HTTP | 경로마다 어느 쪽으로 받았는지와, 다른 쪽을 확인하지 않았다면 그 사실이 있어요. |
| 회차 표시 `0`·여러 회차 게시물·게시물 주소의 변화 | 관찰한 사례와 해석이 있고, 확정하지 못한 것은 미상으로 남아 있어요. |
| 게시물 파일 정보의 재확인 | 경로마다 인증 없이 읽을 수 있는 파일 정보와 읽지 못하는 까닭이 있어요. |
| 명세 갱신 | 공통 결과·실패 분류 초안과 출처별 단계 목록이 작업과 인증 명세에 있고, 서명 URL·쿠키·토큰·자막 본문은 저장소에 남기지 않았어요. |

## 결과

2026-10-02에 `.scratch/source-paths/`(추적하지 않는 임시 실행물)의 HTTP 클라이언트와 CDP로 제어한 헤드리스 Chromium 153으로 확인했고 제품 코드는 바꾸지 않았어요. 관찰의 자세한 내용은 [공개 자막 경로 조사의 2026-10-02 재확인](../brainstorm/web-gui-subtitles.md#2026-10-02-경로별-재확인)에, 공통 수신 결과·실패 분류·출처별 단계 초안은 [작업과 인증 명세의 남은 구체화](../specs/jobs.md#공통-수신-결과와-실패-분류-초안)에 있어요.

### 확인한 것

| 경로 | 표본 | 받은 방법 | 결과 |
| --- | --- | --- | --- |
| erulabo | 게시물 2 | HTTP로 게시물, 브라우저로 카드 직전까지 | 카드 위치·회차 단서까지만 확인했고 카드는 누르지 않았어요. |
| Blogger·Drive 개별 | 게시물 3 | HTTP 3, 브라우저 1 | ASS 3개를 받았고 브라우저 파일이 HTTP와 바이트가 같았어요. 인증 없음. |
| Blogger·Drive 회차 ZIP | 게시물 3 | HTTP 3, 브라우저 1 | ZIP 3개가 CRC를 통과했어요(한 ZIP은 CP949 멤버 이름). 인증 없음. |
| Tistory 일반 첨부 | 게시물 2(+2는 읽기만) | HTTP 2, 브라우저 1 | ZIP 2개와 안의 SRT를 확인했어요. 서명 URL은 이달 말까지예요. |
| Tistory WinPNG | 게시물 3 | 브라우저(뷰어 스크립트) 3 | JMK→SMI·ASS 또는 SMI 파일들을 복원했고 브라우저 다운로드가 폴더에 떨어졌어요. |
| Naver 블로그 첨부 | 게시물 3(+2는 읽기만) | HTTP 3, 브라우저 2 | SMI·ZIP·ASS를 받았어요. 브라우저 다운로드가 폴더에 떨어졌어요(아래). |

- Naver의 브라우저 다운로드는 저장 버튼을 한 번 누르면 선택 칸만 열리고 `내 컴퓨터 저장`을 한 번 더 눌러야 시작돼요. 2026-09-26에 받아지지 않았던 것은 이 첫 클릭 때문으로 보이고, 이번에는 두 번째 클릭으로 파일이 폴더에 떨어졌어요. 새 창이 시작한 다운로드의 `Browser.download*` 이벤트는 페이지 연결로 오지 않아 폴더를 봐야 해요.
- 브라우저가 꼭 필요한 경로는 erulabo(Turnstile)와 Tistory WinPNG(뷰어 스크립트)뿐이에요. 나머지 넷은 HTTP로 충분했고, 그중 Drive·Tistory·Naver는 브라우저도 확인했어요.
- 회차 표시 `0`: 작품별 자막 55줄 가운데 24줄이 `0`이고 22줄은 주소가 비어 있었으며, 주소가 있는 `0`은 극장판·유튜브 영상·블로그 첫 화면 주소였어요. 등록 기본값인지 제작자의 선택인지는 미상이에요.
- 여러 회차를 담은 게시물은 열어 본 20개 가운데 7개이고 제작자의 습관에 몰려 있어요. 주소는 C소라·에텔레로사·이마이가 한 게시물을 고쳐 가며 그대로 두고, erulabo·스모모·수퍼소닉EX 등은 회차마다 새 게시물로 보여요. 한 시점의 Anissia 줄만 보여서 추정이에요.
- 게시물의 파일 정보는 인증 없이 다시 읽을 수 있어요(erulabo는 게시물 수준까지만). Anissia 줄이 그대로인 수정은 실제로 있었어요. 게시물 수정 시각이 `updDt`보다 58시간 넘게 늦은 게시물이 열한 곳 가운데 넷이고, Drive 파일 여섯 가운데 둘이 `updDt`보다 13시간·20시간 뒤에 바뀌었어요.
- Anissia API의 `updDt`는 `2026-10-02T11:17:00`처럼 `T`로 이은 값으로 왔어요.

### 검증하지 못한 것

- erulabo의 카드 이후(Turnstile 통과 뒤의 `download_url`·파일·헤더·서명 URL 유효 시간)는 사람이 인증해야 해서 받지 않았고, 0032에서 확인해요. CAPTCHA는 어떤 방식으로도 건드리지 않았어요.
- WinPNG를 서버 브라우저 없이 복원하는 길과, 뷰어 스크립트 버전이 바뀔 때 같은 PNG의 SMI·ASS 바이트가 달라지는지(하느 762의 12화는 2026-09-26의 32,355바이트가 지금 33,627바이트인데, 게시물 수정과 스크립트 변경을 가르지 못했어요), 키가 필요한 PNG.
- Drive의 할당량·바이러스 검사 화면과 폴더 링크, Tistory 서명 URL의 월 말 뒤 실제 거절, Naver 토큰의 최대 유효 시간(21분 넘게 쓸 수 있었던 것까지만 봤어요), 429.
- 서버 컨테이너 안의 브라우저 수신, 휴대폰·VPN 경로. 브라우저 확인은 개발 PC의 헤드리스 Chromium이에요.
- 게시물 수정 시각의 변화가 언제나 파일 변경인지.

### 남은 일

- 0038은 [실패 분류 초안](../specs/jobs.md#공통-수신-결과와-실패-분류-초안)으로 공통 수신 결과를 정해요.
- 0042(Blogger·Drive)와 0044(Naver)는 HTTP로 충분해서 0039(브라우저 컨테이너)를 기다릴 이유가 줄었어요. 0043(WinPNG)은 사람의 조작 없이 뷰어를 돌릴 브라우저가 필요해요. 막는 티켓을 바꿀지는 사용자가 정해요.
- Anissia 줄이 그대로인 게시물 수정을 감지할지와 주기는 사용자가 이 결과로 정해요. 값을 싸게 다시 읽는 길은 Drive `HEAD`, Tistory `Range` 요청, Naver 게시물 읽기예요.
- 작업과 자막 명세에 아직 옛 서술이 남은 곳은 [자막 명세의 남은 구체화](../specs/subtitles.md#남은-구체화)("출처별 변경 확인… 아직 검증하지 않았어요"), [출처별 다운로드](../specs/subtitles.md#출처별-다운로드)의 WinPNG 행("이미지에서 실제 자막 바이트를 복원", JMK 변환 포함), [자막 후보 조회](../specs/subtitles.md#자막-후보-조회)의 `updDt` 형식("`YYYY-MM-DD HH:mm:ss`")이에요. 요구사항을 바꾸는 일이라 이 티켓에서 고치지 않았어요.
