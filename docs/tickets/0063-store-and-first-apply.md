# 0063 받은 자막 파일 하나를 보관하고 영상 옆에 처음 적용해요

- 상태: 완료
- 출처: [보관본과 적용본](../specs/subtitles.md#보관본과-적용본), [파일의 회차](../specs/subtitles.md#파일의-회차), [체크포인트와 중단 복구](../specs/jobs.md#체크포인트와-중단-복구), [작업 상세](../specs/jobs.md#작업-상세), [작업 결과](../specs/jobs.md#작업-결과)
- 막는 티켓: 없음

## 작업

목표 4의 첫 조각이에요. 후보 작업이 받은 자막 파일 하나가 보관과 첫 적용까지 처음부터 끝까지 가요.
보관의 DB 구조와 파일 효과의 기록을 여기서 정하고, 뒤 티켓은 이 위에 경우를 더해요(사용자 결정, 2026-10-04). 분석부터 만들면 그 결과를 쓰는 쪽이 없어 보관 구조를 짐작으로 정하게 돼서예요.

- 대상은 후보 작업(사용자가 고른 후보, 구독 제작자 자동 수신)에서 받은 자막 파일(ASS·SRT·SMI)이 하나뿐인 회차예요.
  압축 파일, 자막이 여럿인 회차, 폰트가 함께 온 회차는 [0064](0064-multi-file-packages.md)·[0065](0065-archive-extraction.md)를 기다리고, 그 까닭을 작업 상세에 적어요.
- 회차는 후보의 회차 표시를 그 출처의 회차 대응으로 옮긴 시즌 회차예요.
  파일 이름의 번호가 후보의 회차 표시나 옮긴 시즌 회차와 같거나 이름에 번호가 없으면 그 회차의 파일이고, 어느 쪽과도 다르면 보류해 `회차 확인 필요`로 물어요.
- 보관은 `.trss/subtitles/<제작자>/<원래 이름>`이고, 같은 이름·다른 내용은 번호를 붙여요.
  제작자 폴더 이름의 안전한 표기와 번호 붙이기(확장자 앞의 위치, 대소문자만 다른 이름)를 정해, 명세의 [남은 구체화](../specs/subtitles.md#남은-구체화)에서 [보관본과 적용본](../specs/subtitles.md#보관본과-적용본)으로 옮겨 적어요.
  DB는 [보관 관계 필드](../specs/settings.md#보관-관계-필드)의 묶음·보관본·자산과 같은 관계를 담아요. 보관을 확인하면 수신 영역의 원 수신물을 지워요.
- 첫 적용은 영상이 준비돼 있고 같은 줄기의 자막이 없을 때 해요. 보관본을 `.trss/` 안의 임시 파일로 복사·검증하고, 덮어쓰지 않는 이름 바꾸기로 영상 옆에 공개해요.
  같은 회차에 자막이 이미 있거나 공개할 이름이 차 있으면 적용하지 않고 기존 파일을 그대로 둬요(교체 승인은 [0068](0068-replacement-approval.md)). 영상이 없으면 보관까지만 하고 까닭을 적어요(영상 대기는 [0067](0067-awaiting-video.md)).
- 파일 효과마다 의도 → 증거 → 완료를 기록하고, 재시작한 worker는 [중단 위치 표](../specs/jobs.md#체크포인트와-중단-복구)대로 디스크와 대조해요.
- 목표 3에서 받기까지만 하고 끝난 작업은 worker가 다시 집어 이어가요(사용자 결정, 2026-10-04). 다시 받지 않아요.
- 화면은 작업 단계의 `보관`·`적용`, 작업 상세 경로 구역의 영상·적용본·보관본, 회차 줄의 `자막 ✓`, 라이브러리의 자막 범위예요.

## 결과

### 만든 것 (2026-10-05)

- **DB**(마이그레이션 49 `store_apply.sql`): 묶음(`subtitle_packages`)·자산(`subtitle_assets`)·묶음 항목(`subtitle_package_entries`)·보관본(`subtitle_stored`)·보관본의 자산(`subtitle_stored_assets`)·적용본(`subtitle_applied`)과 작업의 배치 계획(`subtitle_job_plan`)·파일 효과(`subtitle_file_effects`)를 만들어요. 작업의 `wait`·`stage`와 단계 표의 값에 `placement`·`approval`·`video`·`store`·`apply`를 더했어요. 마지막에 목표 3에서 받기까지만 하고 `done`·`partial`로 끝난 후보 작업(올리기·직접 찾기 제외)을 `pending`으로 되돌리고 `finished_at`을 비워요.
- **배치**(`crates/trss-jobs/src/place/`): 받기가 끝난 같은 실행에서 이어가요. 게시물마다 받은 파일을 분석해 계획 줄을 적고(`episode.rs`가 회차를 정해요), 줄마다 보관 효과와 적용 효과를 하나씩 실행해요(`files.rs`가 임시 파일 복사·검증·덮어쓰지 않는 이름 바꾸기를, `records.rs`가 기록을 맡아요). 모듈 문서에 순서와 재시작 표가 있어요.
  - 파일 하나뿐인 게시물만 배치해요. 파일이 여럿이거나 압축 파일인 게시물은 작업을 `자막 대기`로 두고 까닭을 적어요(0064·0065). worker가 시작할 때 다시 집어요.
  - 출처의 회차 대응 줄이 없으면 같은 번호를 그 회차로 보고 `assignment = explicit`으로 적어요. 이 판단은 [파일의 회차](../specs/subtitles.md#파일의-회차)에 적었고, 사용자 결정을 기다려요(0059와 함께 묻기로 했어요).
  - 작품 폴더가 없으면 아무것도 쓰지 않고 `영상 대기`로 기다리며, worker가 시작할 때 다시 집어요.
- **실행기**(`runner.rs`): 받기 단계를 먼저 끝내 기록하고(`received`), 배치를 돌린 뒤 계획의 상태로 작업 상태를 정해요(`settle`). 보류한 줄이 있으면 `보류`, 회차를 물으면 `회차 확인 필요`, 분석을 기다리면 `자막 대기`예요.
- **웹 API**: 작업 상세의 단계에 `보관`·`적용`이 들어가고, `placements`가 줄마다 이름·회차·결과·영상·적용본·보관본을 줘요. 보관을 확인해 수신 영역에서 지운 파일은 수신 경로를 보여주지 않아요. 할 일 목록에 `placement_check`(`회차 확인 필요`) 카드가 생겼어요(`todo_api.rs`).
- **웹 화면**: 작업 상세의 회차별 결과에 받은 파일마다 배치 결과(`적용함`, 까닭을 붙인 `보관만 함`, `회차 확인 필요`, `보류`, `보관·적용 실패`)를, 경로 구역에 줄마다 영상·적용본·보관본을 나눠 보여줘요. 할 일 화면에 `회차 확인 필요` 카드(받은 파일 수, 첫 질문, `확인` 버튼)가 있어요. 상태 배지에 `회차 확인 필요`·`교체 승인`·`영상 대기`·`보관하는 중`·`적용하는 중`을 더했어요.
- **명세**: [보관본과 적용본](../specs/subtitles.md#보관본과-적용본)에 제작자 폴더 이름의 안전한 표기와 번호 붙이기를 옮겨 적었어요. [체크포인트와 중단 복구](../specs/jobs.md#체크포인트와-중단-복구)에 보관·적용의 순서와 재시작 표를 적었어요.

독립 검토(2026-10-05, 복잡한 불변식 검토)에서 나온 결함을 고쳤어요. 각 시험은 고친 코드를 되돌리면 실패하는 것을 확인했어요.

- 사람이 지운 적용본 자리에 다시 적용하면 적용본 기록의 유일 색인에 걸려 작업이 다섯 번 실패한 뒤 보류되고, 공개한 파일은 기록 없이 남았어요. 이제 앞 기록을 지워진 것으로 적고 새 기록을 더해요.
- 멈춘 작업의 끝나지 않은 효과가 가려는 이름을 다른 작업이 고르면 효과 색인에 걸리거나(같은 대소문자), 대소문자만 다른 두 파일이 생겨 자산 색인에 걸렸어요. 이제 진행 중인 효과의 목적지를 차 있는 이름으로 보고, 효과 색인도 대소문자를 가리지 않아요. 다른 작업의 적용 효과가 가려는 회차는 기존 자막이 있는 것처럼 보관만 해요(`a_name_another_jobs_store_is_about_to_take_is_taken_whatever_its_case`, `an_episode_another_jobs_apply_is_about_to_take_keeps_it`).
- 보관만 하는 형식(SSA 같은)의 줄에 결과가 없어 화면에 `보관 대기`로 남았어요. 이제 `보관만 함`이에요(`a_row_only_stored_is_settled_by_its_store`).
- 작품 폴더가 없으면 작업을 영영 보류했어요. 이제 `영상 대기`로 기다리고 worker가 시작할 때 다시 집어요.
- 한 실행 안에서 다른 줄의 받기가 앞 수신의 바이트를 읽으려다, 보관하며 지운 파일이라 앞 수신을 보류할 수 있었어요. 두 게시물이 같이 쓰는 파일은 줄이 둘 생겼어요. 이제 지운 수신은 다시 읽지 않고 같이 쓰며, 같은 수신은 한 번만 계획해요(`a_file_two_posts_share_is_planned_once_and_shared_again_once_stored`).
- 그 밖에 이름을 다시 고를 때 정하지 못하면 효과를 보류하고, 이름을 다시 고른 자리에 같은 바이트의 보관본이 있으면 그것을 쓰며, 적용을 물리는 기록을 한 트랜잭션으로 묶고, 형식을 다시 확인하지 못한 옛 수신은 `자막 대기`가 아니라 보류하고, 새로 만든 폴더를 담은 폴더도 동기화하고, 같이 쓰는 수신도 지운 것으로 적어 수신 경로를 숨겨요.

### 한계

- 실제 서버 디스크(xfs, bind mount)와 NFS에서 덮어쓰지 않는 이름 바꾸기·동기화·객체 식별이 되는지는 확인하지 않았어요(0060의 탐침). 이름 바꾸기가 `RENAME_NOREPLACE`를 받지 않는 파일시스템이면 모든 공개가 실패해요.
- 전원이 꺼지는 경우의 내구성은 시험하지 않았어요. 재시작 시험은 기록과 디스크를 그 상태로 만들어 확인한 것이에요.
- Infuse에서 적용본과 `.trss/`가 어떻게 보이는지는 0061에서 확인해요.
- 마이그레이션이 되돌린 작업은 만든 순서로 돌아요. 같은 회차의 옛 수정본 작업이 먼저 적용되고, 새 수정본은 보관만 하고 끝나요. 새 수정본으로 바꾸는 것은 교체 승인(0068)의 일이에요.
- 출처의 회차 대응 줄이 없을 때 같은 번호로 적용하는 판단은 사용자 결정을 기다려요. 결정이 다르면 고쳐야 해요.
- 위 표의 개발 환경 관찰(2026-10-04)은 검토 전의 코드예요. 검토 뒤 고친 코드로 다시 지은 이미지(2026-10-05)에서는 worker가 시작하며 `자막 대기` 작업 13개를 다시 집어 같은 까닭으로 기다리게 했고 보류한 효과는 없었어요. 같은 이미지에서 새 가짜 후보 하나(FX Senshi Kurumi-chan 2화, 영상 있음, 자막 없음)를 골라 받자, 받기·보관·적용 단계를 거쳐 `완료`가 됐어요. 보관본과 적용본은 바이트가 같고 inode가 달랐고, 수신 경로는 보이지 않았고, 라이브러리가 적용본을 2화의 자막으로 기록했어요.
