# 0013 라이브러리 화면에서 작품을 둘러보고 찾아요

- 상태: 진행 중
- 출처: [라이브러리 화면](../specs/library.md#라이브러리-화면), [웹 앱 공통 명세](../specs/web-app.md)
- 막는 티켓: [0012](0012-watch-folders-discovery.md)

## 작업

[0012](0012-watch-folders-discovery.md)가 기록한 작품을 라이브러리 화면에 한 목록으로 보여주고, 보기·정렬·필터·검색으로 둘러보고 작품 상세로 들어가요.
지금 비어 있는 라이브러리 화면을 대신해요.

- 보기는 표지 격자와 목록이고, 표지는 [0015](0015-work-artwork.md) 전까지 작품명 첫 글자 같은 빈 표지 자리예요. 이미지가 없어도 작품명과 상태로 찾고 열 수 있어야 하는 요구와 같은 모양이에요.
- 상태 두 줄은 최신 로컬 시즌 기준의 영상 보유 범위와 자막 보유 범위(`자막 1–10화`, 빈 회차는 구간을 나눔, 시즌마다 구분)이며, 자막은 0012가 영상 옆에서 찾은 파일로 세요. 회차를 확인하지 못한 자막 파일이 있으면 `자막 확인 필요`예요.
- 정렬 다섯 가지와 필터 여섯 가지는 명세대로 두고, 기본은 `최근 자막 추가순`이에요. 날짜가 미상인 작품은 알려진 날짜 뒤에 두고 같은 값은 제목순이에요.
- 방영 정보(방영연도·방영 중)와 원제·영문명은 시즌마다 AniList 항목을 연결하는 티켓(0015 다음, [README](README.md#2-작품-발견과-방영작-구독))이 붙을 때까지 없어요. 그동안 `방영연도순`은 모두 미상이라 제목순과 같고, `방영 중` 필터는 방영 정보를 아직 모르는 까닭을 빈 상태 문장으로 알려요. 검색은 작품명(폴더 이름)으로 해요.
- 할 일 배지는 할 일이 생기는 결과 목표 3부터 붙어요.
- 보기·정렬은 브라우저에 기억하고, 상세에 다녀오거나 뒤로 가기를 해도 검색·필터·스크롤 위치가 남아요.
- 목록은 서버 페이지네이션이에요(사용자 결정, 2026-10-01): 정렬·필터·검색을 서버가 하고, 마지막으로 받은 항목 다음부터 받는 커서로 끝에 닿으면 다음 페이지를 이어 불러와요. 검색은 입력이 멈춘 뒤 보내요. 처음 구현은 520개를 한 번에 받아 그렸고, 이것으로 바꿨어요.

## 완료 기준

| 입력·상태 | 기대 결과 |
| --- | --- |
| 표지 격자에서 목록으로 바꾼 뒤 새로고침·같은 브라우저의 새 페이지 | 목록 보기로 열려요. 정렬도 같아요. |
| 목록 보기의 한 줄 | 48px 표지 자리, 제목, 영상·자막 상태가 한 줄이에요. 항목 전체가 눌리고 올려 두면 배경이 밝아져요. |
| 영상 1–12화, 자막 1–3·5–12화인 시즌 | `자막 1–3·5–12화`처럼 구간을 나눠 보여줘요. |
| 두 시즌이 있는 작품 | 상태는 최신 시즌(번호가 가장 큰 시즌) 기준이에요. |
| 회차를 확인하지 못한 자막 파일이 있는 작품 | 확인된 범위와 별개로 `자막 확인 필요`가 보이고 `확인 필요` 필터에 걸려요. |
| 추가 시각이 서로 다른 작품·영상·자막과 미상이 섞인 자료 | 다섯 정렬마다 기대 순서대로이고, 미상은 뒤에서 제목순이에요. 정렬을 바꿔도 작업이 생기지 않아요. |
| 검색어 입력 후 작품 상세에 들어갔다가 뒤로 가기 | 검색어·필터·스크롤 위치가 그대로예요. |
| 약 520개 작품의 자료(격자·목록 각각) | 정렬·검색·스크롤이 눈에 띄게 멈추지 않고, 상세에 다녀와도 위치를 잃지 않아요. |
| 520개 작품을 목록으로 열고 끝까지 스크롤 | 처음에는 한 페이지만 받고, 끝에 닿을 때마다 다음 페이지를 받아 중복·누락 없이 520개가 이어져요. 페이지를 받는 사이 작품이 더해져도 이미 본 항목이 다시 나오지 않아요. |
| 세 페이지째까지 내려 상세에 갔다가 뒤로 가기 | 받은 페이지와 스크롤 위치가 그대로예요. |
| 검색어를 빠르게 입력 | 입력이 멈춘 뒤 한 번만 요청하고, 늦게 온 이전 검색 결과가 새 결과를 덮지 않아요. |
| 휴대폰 너비 | 가로 스크롤 없이 격자·목록이 보여요. |

## 결과

### 구현한 것

- 읽기 API `GET /api/library/works?sort=&filter=&q=&after=&limit=`(`src/web/library_api.rs`, 정렬·필터·검색·커서는 `src/store/library/page.rs`, 작품별 요약은 `src/store/library/overview.rs`)는 한 페이지를 `{ items, next, total, library_count }`로 답해요. `items`의 작품은 ID, 작품명(폴더 이름), `missing`, 감시 폴더, 최신 시즌 번호, 최신 시즌의 영상·자막 회차 범위, `subtitle_coverage`(`all`·`some`·`none`), `subtitle_check_needed`, 작품 추가 시각, 모든 시즌에서 가장 최근에 알려진 영상·자막 추가 시각(모르면 `null`)이에요. `total`은 필터·검색에 맞는 작품 수(`작품 N편`), `library_count`는 라이브러리 전체 작품 수(빈 라이브러리와 조건에 맞는 작품이 없는 경우를 가려요)예요.
  - `sort`는 `title`·`year`·`added`·`video`·`subtitle`(기본 `subtitle`), `filter`는 `all`·`airing`·`complete`·`partial`·`none`·`check`(기본 `all`), `limit`은 1–200(기본 60)이에요. 모르는 정렬·필터, 범위를 벗어난 `limit`, 알아볼 수 없는 커서, 다른 정렬로 만든 커서는 400과 한국어 한 문장이에요.
  - 정렬은 키 `(정렬의 시각 최신순·미상은 알려진 시각 뒤, 제목, 작품 ID)`예요. 제목은 NFC로 맞추고 대소문자를 가린 뒤 코드 포인트 순으로 견줘서(숫자 → 라틴 → 한글) 브라우저의 `Intl.Collator`와 구두점·악센트 순서가 다를 수 있어요. `title`과 `year`는 시각이 없어서 제목순이에요(방영연도를 아는 작품이 아직 없어요).
  - 커서는 마지막으로 보낸 항목의 키를 16진수로 쓴 불투명한 값이에요(정렬 이름 포함). 다음 페이지는 그 키 뒤의 작품이라, 페이지를 받는 사이 작품이 더해지거나 빠져도 이미 본 항목이 다시 나오지 않아요. 키가 앞선 자리에 새로 생긴 작품은 이미 지나온 자리라 보이지 않고, 뒤에 생긴 작품은 나와요. 페이지 사이에 한 작품의 정렬 시각이 바뀌면(새 파일) 그 작품만 중복되거나 빠질 수 있고, 화면은 ID로 중복을 걸러요.
  - 계산은 요청마다 전체 작품의 요약(작품·파일·미확인 파일 세 쿼리)을 구해 메모리에서 필터·정렬하고 한 페이지를 잘라요. 520개에서 충분히 빨라서 SQL 키셋은 쓰지 않았어요. 회차 구간·`자막 다 갖춤`/`일부`/`없음`·`확인 필요`·`방영 중`(아직 아무것도 맞지 않음)의 정의는 처음 구현과 같아요.
  - 검색은 작품명(폴더 이름)에 질의가 들어 있는지를 NFC로 맞춘 소문자로 견줘요(앞뒤 공백은 뗌). 이를 위해 `unicode-normalization`을 의존성에 더했어요.
  - 폴더가 없는 작품(`missing`)은 이름과 기록된 추가 시각을 남기되 영상·자막 보유를 세지 않고 `subtitle_coverage`·`subtitle_check_needed`는 비워요(0012 결과가 읽는 쪽에 남긴 일이에요). 회차는 적힌 그대로 두고 숫자로만 견주며(`013`과 `13`은 한 회차, 정수 `u128` 비교), 연속한 번호는 한 구간이고 빈 번호에서 나눠요. 정수가 아닌 회차(`17.5`)는 따로 한 구간으로 숫자 구간 뒤에 놓아요. `subtitle_check_needed`는 회차를 확인하지 못한 파일 중 자막 확장자인 것이 있을 때이고 `.part`와 영상은 해당하지 않아요.
- 화면(`web/src/screens/LibraryScreen.tsx`, `web/src/screens/library/`): 표지 격자(작품명 첫 글자를 제목에서 정한 색조의 블록에 얹은 표지 자리, 제목, 영상·자막 두 줄)와 목록(48px 표지 자리, 제목, 영상·자막이 한 줄), 항목 전체가 작품 상세 링크, 올려 두면 배경이 밝아지고 밑줄은 없어요. 정렬 다섯 가지, 필터 여섯 가지, 작품명 검색, `작품 N편`(서버의 `total`), 빈 상태 문장(`방영 중`, 조건에 맞는 작품 없음과 `검색과 필터 지우기`, 빈 라이브러리)은 처음 구현과 같아요. 영상 줄은 `영상 1–12화`·`영상 없음`·`폴더 없음`, 자막 줄은 `자막 1–3·5–12화`·`자막 없음`·`자막 확인 불가`(폴더가 없는 작품)이고 `자막 확인 필요` 배지가 따로 붙어요. 정수 회차의 앞 `0`은 떼어 보여줘요. 표지(`Cover`)는 이미지 주소를 받으면 `loading="lazy"`로 읽도록 준비해 뒀어요(0015 전까지 주소를 주는 곳은 없어요).
  - 목록 읽기(`library/pages.ts`의 `useWorkPages`): 첫 페이지를 읽고, 목록 끝의 높이 1px 띠가 뷰포트 아래 600px 안에 들어오면(`IntersectionObserver`) 마지막 `next`로 다음 페이지를 이어 붙여요. `더 보기` 버튼은 없고, 이어 붙이는 자리는 목록 아래라서 스크롤 위치가 움직이지 않아요. 이어 읽기가 300ms 넘게 걸리면 한 줄로 알리고, 실패하면 한 줄과 `다시 시도`를 두며 저절로 다시 보내지는 않아요.
  - 검색은 입력이 250ms 멈춘 뒤에 한 번 보내요. 정렬·필터·검색이 바뀌면 첫 페이지부터 읽고 페이지 맨 위로 가요. 새 결과가 오기까지는 앞의 목록을 흐리게 보여줘요. 다른 질의로 바뀌면 이전 요청을 취소하고, 늦게 온 답은 그 사이 같은 질의의 페이지가 바뀌었는지 보고 버려요.
  - 받은 페이지는 질의를 키로 `lib/cached.ts`에 두고(`library:list:<정렬>:<필터>:<검색>`, 마지막 질의의 것만 남겨요), 상세에 다녀오거나 뒤로·앞으로 가기를 하면 다시 읽지 않고 받은 페이지를 첫 렌더에 그대로 그려서 `useScrollOnNavigate`가 같은 높이에서 위치를 되돌려요. 메뉴로 라이브러리를 열면 남은 것을 보여주며 첫 페이지를 다시 읽어 바꿔요. 보기·정렬은 `localStorage`(`trss-library-v1`, 모든 접근을 `try/catch`로 감쌈)에, 검색·필터는 페이지가 사는 동안 메모리에 둬요.
  - 감시 폴더를 추가·해제·다시 확인하거나 수집·보관 폴더를 바꾸면 `forgetLibrary()`가 목록 페이지(`library:list:`)와 작품 상세(`library:work:`) 캐시를 모두 버려요. 0014에서 발견한 틈(`FoldersPanel`이 작품 상세 캐시를 버리지 않던 것)을 이 함수로 고쳤어요.
  - 작품 상세 경로 `/library/<작품 ID>`와 상세 화면은 0014가 채웠어요.

### 검증한 것

- `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`(588개)가 통과했고, 웹은 `npm run typecheck`와 `npm run build`가 통과했어요.
- Rust 시험(`page.rs`, `library_api/tests.rs`, `tests/library_watch.rs`): 정렬 다섯 가지 모두에서 같은 시각·미상·같은 제목이 섞인 자료를 페이지 크기 1·2·5·7·22·23·24로 끝까지 이어 받았을 때 한 번에 받은 순서와 같고 중복·누락이 없어요. 시각 정렬은 최신순·미상 뒤·제목 다음 ID예요. 페이지 사이에 앞뒤로 작품이 더해지거나 커서가 가리키던 작품이 빠져도 이미 본 항목이 나오지 않아요(단위·API). 필터 여섯 가지의 정의와 `total`·`library_count`, 검색(대소문자, NFC로 친 질의가 NFD 이름에 맞음, 대괄호), 커서 왕복과 알아볼 수 없는 값, 잘못된 `sort`·`filter`·`limit`·`after`와 다른 정렬의 커서가 400과 한국어 문장인지, 빈 라이브러리를 시험해요. 130개 작품을 `limit=50`으로 다섯 정렬 모두 3페이지에 걸쳐 중복·누락 없이 받아요.
- 정렬 기대 순서를 서버 코드와 따로 구했어요: 스크래치 DB(520개 작품·11 384개 파일, 영상·자막 시각이 알려진 것·같은 값·미상이 섞이고 폴더 없음 2개)를 SQLite로 직접 읽어 정렬 키를 파이썬으로 계산한 520개 순서와, API를 페이지 크기 60과 7로 끝까지 따라가 얻은 순서가 다섯 정렬 모두 같아요. 필터별 개수는 전체 520, 다 갖춤 212, 일부 180, 없음 126, 확인 필요 54, 방영 중 0이고 처음 구현이 기록한 값과 같아요.
- 시간: 페이지 하나(60개)를 답하는 데 디버그 빌드 약 30 ms, 릴리스 빌드 5–9 ms(`curl`, 520개 작품, 로컬 `trss-web`)예요. 520개 전체를 한 번에 받던 처음 구현은 디버그 44 ms, 릴리스 11 ms였어요.
- 브라우저(헤드리스 Chromium을 DevTools 프로토콜로 구동, 로컬 `trss-web`, 위 스크래치 DB, 2026-10-01. 이 환경의 Browser 패널은 가려져 있어 `IntersectionObserver`·`requestAnimationFrame`이 돌지 않아서 쓰지 않았어요):
  - 520개를 격자·목록으로 열고 끝까지 스크롤: 처음 요청은 첫 페이지 하나이고, 끝에 닿을 때마다 `after=` 요청이 하나씩 가서 요청이 모두 9개(1+8, 60개씩)이며 항목 링크 520개가 모두 서로 달라요(중복 0, 누락 0). 페이지가 붙는 동안 스크롤 위치가 움직이지 않았어요.
  - 페이지를 받는 사이 작품 추가: 목록을 제목순으로 한 페이지 받은 뒤 DB에 이미 지나온 자리 앞의 작품(`0 inserted first`)과 맨 뒤의 작품(`~ inserted last`)을 넣고 끝까지 스크롤했더니 521개가 모두 서로 다르고, 앞의 것은 나오지 않고 뒤의 것은 마지막에 나와요(`작품 N편`은 서버의 새 합계인 522라 보이는 수와 하나 달라요).
  - 세 페이지 이상(4페이지, 240개)까지 내려 6 000px에서 상세를 열고 브라우저 뒤로 가기: 항목 240개, 높이 23 867px, 위치 6 000px가 그대로이고 요청이 없어요. 상세의 `라이브러리로` 링크도 같아요. 검색어(`이야기`)와 필터(`자막 일부`)를 건 채 2 500px에서 상세에 갔다가 뒤로 가도 검색어·필터·위치가 그대로이고 요청이 없어요. 다른 메뉴에서 라이브러리 메뉴로 들어가면 첫 페이지 하나만 다시 읽고 맨 위에서 시작해요.
  - 검색: 60 ms 간격으로 `series 01`을 치면 멈춘 뒤 요청이 하나(`q=series+01`)이고 7편이 나와요. 응답을 1.5초 늦춘 `zz` 요청 뒤에 `series 02`를 치면 `series 02`의 7편이 남고 늦은 답이 덮지 않아요. 대문자 질의, NFC로 친 질의 대 NFD 폴더 이름, 대괄호로 시작하는 이름이 찾아져요.
  - 정렬·필터를 바꾸면 첫 페이지 하나부터 읽어요(`자막 일부` 60개 → 끝까지 180개, 끝까지 내린 채 정렬을 바꾸면 맨 위에서 첫 페이지부터). `방영 중`은 한 문장의 빈 상태예요. 이어 읽기를 실패시키면 `다음 작품을 불러오지 못했어요.`와 `다시 시도`가 뜨고 저절로 반복하지 않으며, 다시 시도하면 이어져요.
  - 처음 구현과 같은 행: 격자→목록 전환 뒤 새로고침하면 목록 보기와 같은 정렬이에요. 목록의 한 줄은 48px 표지, 제목, 영상·자막이고 항목 전체가 링크이며 올려 두면 배경이 `#f1f4f8`에서 `#fbfcfd`로 밝아져요(`hover: hover`를 켠 상태, 밑줄 없음). `Gap Test`는 `영상 1–12화`·`자막 1–3·5–12화`, `Two Seasons`는 `영상 1–4화`·`자막 1–2화`, `Zero Pad`는 `영상 13–15·17.5화`·`자막 13–15화`, `Unconfirmed Sub`는 `자막 1–4화`와 `자막 확인 필요`, `Only Unconfirmed`는 `자막 없음`과 `자막 확인 필요`이고 둘 다 `확인 필요` 필터에 걸려요. 정렬을 바꾸는 동안 DB의 `commands`는 0행이에요. 390px·320px에서 격자·목록 모두 520개를 끝까지 이어 붙인 뒤 `scrollWidth == innerWidth`예요.
  - 520개가 이어 붙은 목록(격자·목록 각각)을 3초에 걸쳐 끝까지 스크롤하고, 첫 페이지에서 프레임마다 40px씩 내리며 페이지가 붙는 동안도 8초 스크롤해 프레임 간격을 쟀어요: 중앙값·95번째 16.7 ms, 최대 16.8 ms, 33 ms를 넘는 프레임 0개, 긴 작업(`longtask`) 0개예요. 첫 렌더는 한 페이지(60개)의 DOM이에요.

### 검증하지 못한 것

- 520개에서의 스크롤·그리기가 눈에 띄게 멈추지 않는지는 사람이 본 확인이 아니에요. 위 프레임 간격은 GPU 없는 헤드리스 Chromium(소프트웨어 그리기, 데스크톱 폭)에서 잰 것이고, 실제 기기 특히 휴대폰의 스크롤 감은 알 수 없어요. 이 행은 실제 기기에서 스크롤해 보고 닫아요.
- 가려진 Browser 패널에서는 `IntersectionObserver`가 돌지 않아서 패널 쪽 확인은 하지 못했고, 위 확인은 모두 헤드리스 Chromium에서 했어요. 다른 엔진(Firefox·Safari)은 보지 않았어요.
- 실제 휴대폰·터치·가상 키보드, 키보드 조작과 초점 표시, 라이트·다크 모드마다의 글자 대비 측정은 하지 않았어요.
- 자동 화면 시험은 없어요(이 저장소에 웹 시험 도구가 없어요). 화면 동작은 위 브라우저 확인으로만 봤고 커서·정렬·필터·검색은 Rust 시험과 파이썬 계산으로 따로 닫았어요.
- 감시 폴더를 해제·다시 확인한 뒤 작품 상세 캐시가 버려지는 것은 코드로만 바꿨고 브라우저에서 해 보지 않았어요(`forgetLibrary`는 두 접두사를 지우는 한 줄이에요).
- 영상·자막 추가 시각은 시험 자료의 DB 값을 직접 바꿔 섞었어요(worker의 감시 폴더 확인이 만든 시각은 `tests/library_watch.rs`로 확인했어요). 실제 NAS 폴더나 운영 DB로는 보지 않았어요.
