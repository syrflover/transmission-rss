# 0059 압축 해제 도구와 한도를 정해요

- 상태: 완료
- 출처: [압축 해제의 격리와 한도](../specs/subtitles.md#압축-해제의-격리와-한도)(사용자 결정, 2026-10-04), 올리기가 넘긴 ZIP이 아닌 압축 파일([0047](../archive/tickets/3-subtitle-candidates-and-receiving/0047-subtitle-upload.md))
- 막는 티켓: 없음

## 작업

확인할 일이에요. [0065](0065-archive-extraction.md)가 압축 해제를 만들기 전에, 형식마다 쓸 도구와 한도의 수치를 정해요.

- 풀어야 하는 형식은 ZIP, RAR(4·5), 7z, gzip, bzip2, xz, tar와 나뉜 조각(`.part1.rar`·`.r00`·`.z01`·`.7z.001`·`.zip.001`)이에요.
  형식마다 순수 Rust 크레이트, C 라이브러리(libarchive 같은 것), 외부 도구(bsdtar·unrar·7z) 가운데 쓸 수 있는 것을 견줘요.
  견줄 것은 지원 범위(RAR5, 나뉜 조각, 암호의 감지), 이용 허락, musl 정적 빌드와 alpine 이미지에 들어가는지, 이미지 크기예요. RAR은 이용 허락이 따로 있어서 특히 봐요.
- 개발 환경 수신 영역에 있는 여덟 경로의 실제 묶음에서 멤버 수, 풀린 크기, 폴더 깊이, 경로 길이, 압축률, 가장 큰 폰트를 재요.
- 폭탄 표본(압축률이 아주 높은 것, 멤버가 아주 많은 것, 중첩된 것, 사전이 큰 xz·7z, 경로 이탈·링크 멤버)을 만들어, 고른 도구의 최대 메모리와 시간을 재요.
- 측정값과 올리기의 한도(파일 하나 200MiB, 묶음 1GiB, 파일 500개, ZIP 읽기 2GiB)에서 출발해 한도의 수치를 정하고, 명세의 그 절에 적어요.
- 도구 사이에 사용자 결정이 필요한 비용 차이(이용 허락, 이미지에 외부 실행 파일 추가)가 있으면 추천과 함께 묻고, 답을 받은 뒤 정해요.

## 결과

조사는 2026-10-04에 했어요. 실행은 `docker run -m 128m --memory-swap 128m --cpus 0.25`에서 1000:1000으로 했고, 출력은 overlay 디스크에 썼어요. 측정한 곳은 데스크톱(커널 7.2.8, cgroup v2)이라 J4105 서버보다 빨라요. 사용자 결정은 2026-10-05에 받았어요.

### 고른 도구

모든 형식을 순수 Rust 크레이트로 풀어요(xz만 C의 liblzma). 외부 실행 파일은 이미지에 넣지 않아요.

| 형식 | 도구 | 이용 허락 | 빌드·이미지 |
| --- | --- | --- | --- |
| ZIP, `.zip.001` | `zip` 크레이트(이미 써요)와 조각을 이어 읽는 reader | MIT | 늘지 않아요 |
| 7z, `.7z.001` | `sevenz-rust2` 0.23과 이어 읽는 reader. 풀기 전에 coder ID와 사전 속성을 읽어요 | Apache-2.0 | 순수 Rust |
| tar, gzip, bzip2, xz | `tar`, `flate2`, `bzip2`(순수 Rust), `liblzma`(`memlimit`) | MIT·Apache-2.0, xz-utils(0BSD·public domain) | liblzma가 musl 정적 빌드로 빌드됐어요 |
| RAR 4·5, `.partN.rar`, `.rar`+`.r00` | `rars` 0.10.0 | Apache-2.0 | 순수 Rust. 목록에서 64MiB를 넘는 멤버가 있는 RAR은 풀지 않아요(사용자 결정) |
| `.z01`로 나뉜 ZIP | 풀지 않아요(사용자 결정). `풀지 못함`과 까닭을 남기고 원본은 수신 영역에 둬요 | | |

- 크레이트들은 암호를 알아봐요. `zip`은 AES와 ZipCrypto를, `sevenz-rust2`는 AES coder와 헤더 암호화를, `rars`는 암호가 필요하다는 것을 알려줘요. 경로 이탈과 링크는 `rars`가 스스로 거절하고, 나머지는 멤버의 이름과 종류를 보고 호출하는 쪽이 거절해요.
- 외부 도구만 쓰는 길(`7zz`+`bsdtar`, 이미지 +10.57MiB)은 고르지 않았어요.
  - 둘 다 압축률이 높아도 멈추지 않아요.
  - `7zz`는 `..`와 `/` 경로를 말없이 고쳐 쓰고 링크를 만들어요. 암호가 걸린 파일은 0바이트 파일로 남겨요. Alpine의 `7zz`는 RAR을 풀지 못해요.
  - `bsdtar`는 링크와 FIFO를 그대로 만들어요. 나뉜 RAR에서 조각에 걸친 멤버를 빠뜨리고도 성공으로 끝나요. 암호가 걸린 ZIP에서는 암호를 계속 물어요.
- RAR의 다른 후보도 고르지 않았어요.
  - unRAR을 옮긴 크레이트(`unrar-rs`, `weaver-unrar`, `unrar`)는 unRAR 이용 허락을 따라요. 빌드해 보지 않았어요.
  - RARLAB `unrar`는 Alpine에 없어요.
  - libarchive C API는 시험하지 않았어요.
- `rars`는 저자가 unar·libarchive·UNRARLIB를 참고해 AI로 쓴 지 다섯 달 된 크레이트예요. 기본 설정은 106MB 멤버를 통째로 메모리에 올려 128M 컨테이너에서 OOM으로 죽었어요. 그래서 사용자가 64MiB 멤버 상한을 골랐어요.

### 실제 묶음 (2026-10-04)

개발 환경 수신 영역의 폴더 28개를 쟀어요. ZIP 13개는 내용이 다른 4종이고 모두 폴더 없이 평평해요(깊이 1).

| --- | --- | --- | --- | --- | --- | --- |
| `삼전닉스 레버리지 01.zip`(5) | 9,393 B | 1 | 35,186 B | 62 B | 3.9 | `.smi` 35,186 B |
| `네죽사 1~8화 자막.zip`(2) | 106,408 B | 8 | 402,994 B | 73 B | 3.9 | `.ass` 55,926 B |

| `Yani Neko - 12.zip`(2) | 11,724 B | 1 | 31,792 B | 18 B | 2.8 | `.srt` 31,792 B |

- 최대치는 멤버 8개, 풀린 크기 402,994 B, 깊이 1, 멤버 경로 94 B, 압축률 3.9예요.
- 압축 파일이 아닌 폴더까지 보면, 가장 큰 폰트는 `a옛날목욕탕L.ttf`(2,166,920 B)이고 가장 긴 파일 이름은 115 B예요.
- `pack.rar`(폴더 `42b61ce5`)는 RAR5 머리와 글자 몇 개뿐인 19바이트 파일이라 실제 RAR이 아니에요.
- 실제 RAR·7z 묶음은 수신 영역에 없었어요. 실제 묶음은 아주 작아서, 한도의 위쪽 값은 올리기의 한도와 폭탄 측정에서 정했어요.

### 폭탄 표본 (2026-10-04)

`probe`는 고른 크레이트로 만든 측정용 프로그램이에요. 최대 메모리에는 페이지 캐시가 들어 있어서, 큰 파일을 쓰는 실행은 이 커널에서 128M로 보여요(`oom_kill` 0).

### 한도

수치는 [압축 해제의 격리와 한도](../specs/subtitles.md#압축-해제의-격리와-한도)에 적었어요. 사용자가 정한 것 말고는 이 측정에서 제가 정했어요.

- 풀린 크기 합계는 512MiB이고 시간은 120초예요. 1GiB로 하면 이 속도로 300초 남짓이 필요해요.
- bzip2는 순수 Rust로 둬요. C보다 2.5배 느리지만 시간 한도가 worker를 지켜요.
- RAR의 사전 상한도 xz·7z와 같은 64MiB로 둬요. `rars`의 사전 한도 64MiB가 128MiB 사전 표본을 바로 거절했어요.
- 자식 프로세스를 worker 실행 파일로 다시 띄울지, 작은 실행 파일을 따로 둘지는 측정하지 않아서 0065에서 정해요.

### 사용자 결정 (2026-10-05)

- RAR은 `rars`로 풀고, 목록에서 64MiB를 넘는 멤버가 있으면 풀지 않아요.
- `.z01`로 나뉜 ZIP은 지원하지 않아요.
- xz·7z의 사전 상한은 64MiB예요. 풀 때 70MB 남짓을 써서, worker 메모리 한도를 256M로 올리자는 사용자 제안을 0065에서 반영하고 실제 서버의 `oom_kill`로 확인해요.
- 이 결정과 함께, 대응 행이 없는 출처의 후보는 후보의 회차 번호를 그대로 시즌 회차로 써요([파일의 회차](../specs/subtitles.md#파일의-회차)).

### 확인하지 못한 것

- WinRAR로 만든 RAR 4·5와 나뉜 RAR로는 풀어 보지 않았어요. RAR 표본은 모두 `rars`의 writer나 직접 쓴 작은 RAR5 writer로 만들었어요. `rars`가 만든 RAR4 두 개는 libarchive도 풀지 못했는데, writer와 reader 가운데 어느 쪽 문제인지 몰라요.
- CP949 멤버 이름(ZIP·RAR4·7z), `.tar.001`·`.gz.001`, PPMd 7z, BCJ2, 4GiB 넘는 ZIP64, deflate64는 시험하지 않았어요.
- Landlock·seccomp는 살피지 않았어요. `RLIMIT_NOFILE` 64는 재지 않았어요.
- 서버 커널의 페이지 캐시 동작과 J4105의 속도는 0065에서 재요.
- 수신 영역에는 ZIP 4종만 있어서, 여덟 경로마다 실제 묶음을 재지는 못했어요.
