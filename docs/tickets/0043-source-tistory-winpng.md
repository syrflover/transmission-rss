# 0043 Tistory WinPNG 이미지에서 뷰어로 자막을 꺼내요

- 상태: 완료
- 출처: [출처별 다운로드](../specs/subtitles.md#출처별-다운로드)(Tistory WinPNG), [Tistory WinPNG 조사](../brainstorm/web-gui-subtitles.md#tistory-winpng)
- 막는 티켓: [0038](0038-receive-result-tistory.md), [0039](0039-browser-container-lifecycle.md)

## 작업

서버 브라우저가 게시물의 WinPNG 뷰어로 이미지 안의 파일을 꺼내 수신 영역에 둬요. 사람의 조작은 없어요(2026-10-02 결정). 이미지 형식을 trss가 직접 해석하지 않는 까닭은 [출처별 다운로드](../specs/subtitles.md#출처별-다운로드)에 있어요.
0033에서 이미지 안에는 SMI가 그대로 든 경우(762)와 JMK(Jamaker 프로젝트)가 든 경우(763·761)가 있었어요. 자막 파일은 그대로 받고, JMK는 뷰어가 변환한 SMI·ASS를 둘 다 받아 한 묶음으로 두며 JMK는 보관하지 않아요(사용자 결정). 뷰어가 만든 파일은 blob 링크의 브라우저 다운로드로 떨어지므로 다운로드 폴더를 보고 판단해요.
PNG 다운로드나 뷰어 표시만으로 성공으로 보지 않아요. 파일 키가 필요한 이미지는 지원 여부를 구분해 실패로 알려요.

## 완료 기준

| 입력·상태 | 기대 결과 |
| --- | --- |
| 여러 회차·하위 폴더가 든 WinPNG 이미지(시험 표본) | 복원한 파일들이 원래 이름·폴더 구조와 함께 수신 영역에 있고, 각 파일이 자막 바이트(예: `<SAMI>` 시작)예요. |
| JMK가 든 이미지(시험 표본) | 파일마다 SMI·ASS 둘이 한 묶음으로 수신 영역에 있고 JMK는 없어요. |
| 일반 이미지(WinPNG 아님) | 자막 없음으로 분류된 실패예요. |
| 파일 키가 필요한 이미지 | 추가 입력 필요로 구분돼요. |
| 실제 게시물 하나 | 실제 서버에서 복원한 파일의 수·크기·형식을 확인한 결과가 있어요. |

## 결과

### 만든 것 (2026-10-03)

- **뷰어로 꺼내기**: 본문에 `*.kakaocdn.net`의 `.png` 이미지만 있는 Tistory 게시물은 서버 브라우저가 게시물을 열고, 스킨의 WinPNG 뷰어에 이미지를 하나씩 열게 해서 뷰어가 만든 파일 링크를 차례로 내려받아요. 형식은 trss가 해석하지 않고 뷰어 코드도 담지 않아요. 지연 로딩 이미지도 주소를 찾아요.
- **받은 것의 판정**: 뷰어가 만든 파일의 바이트로만 판정하고, 뷰어가 준 이름과 폴더 구조를 지켜 수신 영역에 둬요. JMK는 뷰어가 만든 SMI·ASS만 받아요. 다운로드는 누른 링크의 이름과 맞을 때만 그 파일로 받아요. 폴더는 깊이 8, 600바이트까지이고 넘으면 그 파일만 `파일 아님`이에요. 같은 이름의 파일과 폴더는 번호로 나눠요.
- **실패 분류(마이그레이션 44)**: 회차 단위 분류에 `자막 없음`(뷰어가 읽을 수 있는 이미지가 없음)과 `추가 입력 필요`(뷰어가 키 입력창을 띄움; 한 이미지라도 그러면 그 게시물 전체)를 더했어요. 브라우저가 출처가 본 이미지를 하나도 찾지 못하면 `출처 구조 바뀜`, 읽히는 이미지 없이 일부를 못 읽었으면 `네트워크 실패`(다시 시도)예요. Drive 폴더 링크가 함께 있으면 그림뿐이어도 `자막 대기`로 남아요. `subtitle_job_files.folder`도 이 마이그레이션이에요.
- **작업과 브라우저 실행**: 수신기(`WinpngReader`)가 작업마다 풀에서 실행을 받아 읽는 동안 붙들고, 작업이 끝나면 놓아요. 인증을 기다리는 작업은 실행을 놓지 않아요(0040·0041이 쓸 자리). 서버 브라우저가 없는 worker는 지금처럼 `자막 대기`예요. 임시 폴더 `.tmp/winpng-<작업>`은 다음 실행과 기존 정리(sweep)가 지워요.
- 실패 이유는 고정된 문장이고, 페이지가 던진 글이나 주소는 남기지 않아요. 14일 재확인(0050)은 여전히 WinPNG를 읽지 않아요.
- 규칙 전체는 [공통 수신 결과와 실패 분류](../specs/jobs.md#공통-수신-결과와-실패-분류)와 [출처별 다운로드](../specs/subtitles.md#출처별-다운로드)에 있어요.

### 검증한 것

| 완료 기준 | 근거 |
| --- | --- |
| 여러 회차·하위 폴더 | `crates/trss-jobs/tests/winpng.rs`(이름·폴더 유지, 겹치는 이름, 재시작 복구). 실제 서버 브라우저(2026-10-03): 하느 761에서 48개(ASS 24·SMI 24, 1,381,372바이트, `예고` 하위 폴더에 12쌍), 87.6초 |
| JMK | 가짜 페이지 시험. 실제: 하느 763에서 SMI 325,531·ASS 170,859바이트, JMK 없음 |
| 일반 이미지 | 가짜 페이지 시험, 실제 뷰어에 만든 일반 그림을 준 무시된 시험(`자막 없음`) |
| 키가 필요한 이미지 | 가짜 페이지 시험과 `only_a_prompt_asks_for_a_key`, 실제 뷰어에 읽기 실패를 강제해 키 입력창이 뜬 경우(`추가 입력 필요`). 실제로 키가 필요한 이미지는 보지 못했어요. |
| 실제 게시물 | 761·762·763을 무시된 시험 `winpng_sample`(`--features test-hooks`)로 두 번(리뷰 수정 전후) 받았어요. 762는 SMI 12개 766,818바이트, 모두 `<SAMI>`로 시작해요. |

개발 환경(서버 데이터 복사본, 2026-10-03, 리뷰 수정 전 코드)에서 처음부터 끝까지 확인했어요. 복사본 작품 하나의 시즌을 하느 763의 Anissia 작품에 연결하고, 작품 상세에서 후보를 골라 받았어요. 작업이 `done (1/1)`이 됐고, SMI·ASS 두 파일만 받았으며 worker 로그에 다운로드 주소가 없었어요. 리뷰 수정 뒤에는 개발 환경에서 다시 받지 않았고, 수정된 수신기는 위 실제 게시물 시험으로 확인했어요.

같은 게시물을 다시 꺼낸 바이트는 앞선 관찰과 달랐어요. 763은 파일마다 4바이트 컸고, 762의 12화는 32,201바이트로 앞선 두 값(32,355·33,627)과 달랐어요. 뷰어가 만든 바이트를 같은 파일의 판정 근거로 쓰기 전에 확인해야 한다는 [미상](../specs/jobs.md)은 그대로예요.

최종 코드(2026-10-03)에서 `cargo fmt --check`, `cargo clippy --workspace --all-targets -D warnings`(경고 0), `cargo test --workspace`(2,067개 통과, 실패 0, 무시 4), 웹 `tsc`와 단위 시험(27개 통과)이 통과했고, `dev/compose.sh up`으로 개발 환경을 다시 만들었어요(마이그레이션 44).

### 독립 리뷰

마이그레이션, 경로, 신뢰 경계, 실행 수명, 분류를 두고 리뷰를 받았어요. 막는 결함은 없었고 아래를 고쳤어요.

| 지적 | 처리 |
| --- | --- |
| 끝난 실행에서 다운로드 비우기가 끝없이 돎 | 준비된 결과가 성공일 때만 이어 가고 오류면 끝내요 |
| 지연 로딩 이미지를 못 찾으면 영구 `자막 없음` | 주소를 더 찾고, 못 찾으면 `출처 구조 바뀜` |
| Drive 폴더와 일반 그림이 있는 게시물이 영구 실패 | `자막 대기`로 남겨요 |
| 다른 호스트의 그림 하나가 게시물 전체를 `네트워크 실패`로 | kakaocdn 이미지만 보고, 못 읽은 이미지는 건너뛰어요 |
| 늦게 온 다운로드가 다음 링크의 파일이 됨 | 이름이 맞는 다운로드만 받아요 |
| 알림창도 키 필요로 봄 | 입력창만 봐요 |
| 폴더 깊이·길이와 파일·폴더 이름 충돌 | 상한과 번호 붙이기 |
| 임시 폴더가 남음 | 정리(sweep)가 지워요 |
| 페이지의 오류 글이 이유에 보임 | 고정 문장 |
| 페이지가 뜨자마자 띄운 알림창 | 이동 전에 알림창 처리를 켜요 |
| 시험용 스크립트 주입이 제품 코드에 | `test-hooks` 기능 뒤로 |

### 한계

- 실제로 키가 필요한 이미지와 지연 로딩 스킨은 보지 못했어요(흉내만 냈어요).
- 뷰어가 이어지는 다운로드를 조용히 버려서 다시 누르기 때문에, 48개짜리 게시물은 약 87초 걸려요. 시간 한도(이미지 90초, 다운로드 20초 × 4번)는 시작값이에요.
- 뷰어의 전역 함수와 패널 구조에 기대요. 스킨이 바뀌면 `출처 구조 바뀜`이나 `네트워크 실패`로 드러나요.
- 키가 필요한 이미지에 키를 넣는 길은 없어요.
