# 0125 작품 폴더를 옮기느라 받지 못한 체크 항목을 옮긴 뒤 받아요

- 상태: 완료 (2026-10-08)
- 출처: [0123](0123-collect-moves-archived-work-folder.md)의 실제 서버 관찰(2026-10-08), [방영작 구독](../specs/collection.md#방영작-구독), 사용자 결정(2026-10-08)
- 막는 티켓: 없음. 0092 전에 고치고, 이것만으로 배포하지는 않아요(0124와 같이, 사용자 결정 2026-10-08).

## 작업

0123부터 구독의 작품 폴더가 보관 폴더에 있으면 규칙을 `멈춤`으로 만들고, worker의 `start` 명령이 폴더를 수집 폴더로 옮긴 뒤 규칙을 켜요.
구독 확인 단계는 만들어진 규칙이 `멈춤`으로 돌아오면 체크한 지난 항목을 받지 않아요. 사용자가 옮긴 뒤 규칙 화면에서 다시 골라야 해요.
2026-10-08 실제 서버에서 `정반대의 너와 나` 2기를 구독할 때 체크한 두 항목이 이렇게 받지 않은 채 남았어요. 사용자는 체크한 항목을 옮긴 뒤 저절로 받기를 바라요(사용자 결정, 2026-10-08).

- 구독 요청에 체크한 지난 항목을 받을 순서대로 함께 보내요. 서버가 그 규칙이 작품 폴더를 기다려야 한다고 정하면, 그 항목들을 `start` 명령에 담아 둬요. 기다리지 않으면 지금처럼 화면이 받기 명령을 보내요.
- worker는 폴더를 옮기고 규칙을 켠 뒤, 담아 둔 항목마다 `다시 받기`(`receive_once`) 명령을 순서대로 접수해요. 받는 길은 지금의 `다시 받기`와 같아서, 규칙이 고르는지와 회차 변환의 첫 결정도 같은 코드가 해요.
- 옮기지 못하면 규칙은 지금처럼 `멈춤`이고 담아 둔 항목은 받지 않아요. 규칙 상세의 폴더 이동 문장에 까닭이 나오고, 항목은 규칙 화면의 지난 회차에 남아요.
- 구독 확인 단계는 옮기는 중이면 옮긴 뒤 체크한 항목을 받는다고 알려요. 규칙 상세의 폴더 이동 문장은 체크한 항목을 받기 시작했다고 알려요.

## 완료 기준

| 상태 | 기대 결과 |
| --- | --- |
| 보관 폴더에 있는 작품을 구독하며 지난 항목 둘을 체크 | 폴더를 옮기고 규칙을 켠 뒤 두 항목을 체크한 순서대로 받아요. 확인 단계와 규칙 상세가 그렇게 알려요. |
| 옮기지 못함 | 규칙은 `멈춤`이고 두 항목은 받지 않으며, 규칙 상세에 까닭이 나와요. |
| worker가 규칙을 켠 뒤 받기 명령을 다 접수하기 전에 멈춤 | 다음 worker가 `start`를 이어 하고, 받기 명령은 항목마다 한 번만 생겨요. |
| 작품 폴더가 보관 폴더에 없음 | 지금처럼 확인 단계가 체크한 항목을 바로 받아요. |

- 시험은 이동과 명령을 맡은 trss-collect에, 요청의 모양은 trss-web에 둬요([테스트 나눔 ADR](../adr/0015-test-a-rule-once-in-its-crate.md)).
- 실제 서버 확인은 다음 배포 뒤 보관 폴더에 있는 작품의 속편을 구독할 때 해요.

## 결과

2026-10-08에 구현했어요.

- 구독 요청(`POST /api/subscriptions`)이 체크한 항목을 `receive`(기록 항목 ID, 받을 순서)로 함께 보내요. 서버는 규칙이 작품 폴더를 기다릴 때만 이 값을 써요. 채널의 기록에 없는 항목이나 같은 항목이 두 번 들어 있으면 400으로 거절하고 아무것도 만들지 않아요. 기다리지 않으면 무시하고, 화면이 지금처럼 받기 명령을 보내 진행을 보여줘요.
- `rule_archive` 명령 값에 `receive`를 더했어요. 비어 있으면 저장하는 글에서 빠져서 다른 명령과 예전 명령의 모양은 그대로예요. `start`는 규칙을 켠 뒤 항목마다 `receive_once`를 순서대로 접수해요. 명령 ID는 `<start의 ID>-receive-<항목 ID>`라서, 중간에 끊긴 `start`를 다시 돌려도 항목마다 한 번만 생겨요. 그 항목에 다른 받기 명령이 열려 있으면 그쪽에 맡겨요.
- 접수한 받기 명령은 worker가 `start`가 끝난 뒤의 다음 살펴보기에서 가져가요. 받는 길은 `다시 받기`와 같아서, 규칙이 그 항목을 고르는지와 회차 변환의 첫 결정도 같은 코드가 해요.
- `start`의 결과 문장 끝에 "구독할 때 체크한 지난 항목 N개를 이어서 받아요."가 붙어, 규칙 상세의 폴더 이동 문장에 나와요. 구독 확인 단계는 옮기는 중이면 체크한 항목을 옮긴 뒤 받는다고 알려요.
- [보관과 복원의 폴더 이동](../specs/collection.md#보관과-복원의-폴더-이동)의 구독 화면 항목을 이 동작으로 바꿨어요.

### 완료 기준과 시험

| 완료 기준 | 시험 |
| --- | --- |
| 옮긴 뒤 체크한 순서대로 받음 | `trss-collect`의 `a_start_receives_the_ticked_items_in_order_once_the_rule_is_on_and_once_each`: 규칙이 켜지고, worker가 `start` 다음에 두 받기 명령을 체크한 순서로 가져가며, 결과 문장이 그렇게 알려요. 요청의 모양은 `trss-web`의 `a_subscription_that_waits_for_its_work_folder_carries_the_ticked_items_in_its_start` |
| 옮기지 못함 | `a_start_that_does_not_turn_the_rule_on_receives_none_of_the_ticked_items`: 규칙은 `멈춤`이고 받기 명령이 없어요. |
| 받기 명령을 다 접수하기 전에 멈춤 | 첫 시험이 같은 `start`를 두 번 돌려도 받기 명령이 항목마다 하나예요. |
| 작품 폴더가 보관 폴더에 없음 | `trss-web` 시험의 마지막 부분: 규칙이 켜진 채 만들어지고 서버는 받기 명령을 만들지 않아요. |

- 명령 값의 모양은 `a_start_carries_the_ticked_items_and_other_commands_are_as_before`가 봐요.
- 2026-10-08 `cargo test -p trss-collect -p trss-web -p trss-worker -j 4`가 모두 통과했어요(실패 0). `npm run typecheck`도 통과했어요.

### 검증하지 못한 것

- 실제 worker가 폴더를 옮긴 뒤 받기 명령까지 이어 돌려 토렌트를 수집 폴더에 넣는 흐름은 시험하지 않았어요. trss-collect 시험은 보관 폴더가 없는 경우로 규칙을 켜는 단계까지만 봐요. 명령 실행기가 명령이 끝날 때마다 새로 접수된 명령을 가져가는 것은 기존 동작이에요.
- 구독 확인 단계의 문장은 타입 검사만 했고 브라우저에서 보지 않았어요.
- 제목을 기다리던 구독에 제목을 정하며 체크한 항목(`NameTitle`)은 바꾸지 않았어요. 그때는 구독할 때의 `start`가 이미 폴더를 옮겨 두었어요.
