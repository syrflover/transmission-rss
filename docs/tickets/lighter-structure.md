# 구조 가볍게 하기 명세

## 목표와 범위

2026-10-21에 사용자는 trss가 너무 무거워졌다고 했고, 특히 worker 방식을 짚었어요. 그날 조사에서 찾은 근거는 다음과 같아요.

- 파일이나 Transmission을 건드리는 사용자 동작은 모두 web이 명령으로 적고 worker가 집어 실행해요. 이 인계와 관련된 코드가 `trss-core`에 3,873줄, `trss-worker`에 10,503줄(테스트 7,059줄 포함)이에요([한 프로세스 ADR](../adr/0019-one-process-for-web-and-worker.md)).
- 자막 작업은 단계와 효과마다 기록을 남겨, 다시 시작할 때 디스크와 대조해 이어 해요. 효과의 기록만 담는 테이블은 `jobs/store_apply.sql`의 `subtitle_file_effects` 하나이고, 받기 기록(`subtitle_job_files`)과 재배치 제거(`subtitle_relocations`), 교체 계획에는 효과의 상태와 열이 섞여 있어요. 서버에서 이 재개가 일어난 것을 본 기록은 없어요([끊긴 작업 ADR](../adr/0020-interrupted-jobs-wait-for-a-restart.md)).
- 화면의 TypeScript 타입은 Rust 응답과 손으로 맞춰요. `trss-web`에는 `Serialize`를 붙인 구조체·열거형이 206개, 테스트 밖의 `json!` 호출이 75곳 있어요.
- 화면은 서버 상태를 18곳에서 주기적으로 다시 읽어요. 간격은 0.7초에서 60초예요.
- 2026-10-21 `5cdae9e`에서 `cargo test --workspace --no-run -j 4`가 94초 걸렸고, 그중 `trss-worker` 단위의 빌드가 64.1초였어요. 이 빌드는 외부 크레이트도 다시 빌드해서 `trss-core`만 고친 빌드가 아니었어요. `trss-core`를 고친 뒤의 빌드는 [기준값](#기준값)에서 다시 측정했어요.
- 같은 날 같은 코드에서 `cargo test --workspace -j 4`를 빌드 뒤 다시 실행하니, 테스트 바이너리 31개의 시간 합이 43.2초였고 테스트는 3,086개였어요. 기본 실행에서 테스트가 하나도 돌지 않는 `remote_screen_docker`가 빌드에 15.6초를 써요.
- 테스트 코드는 Rust 코드의 약 55%예요. 테스트가 139k줄, 제품 코드가 114k줄이에요. 파일 이름과 `mod tests`로 나눈 어림값이에요.

이 변경으로 코드를 읽고 고치는 비용, 기능 하나를 더하는 단계, 테스트에 드는 계산 자원, 서버 운영을 줄여요. 수집과 자막 기능은 모두 두고, 기능 안의 규칙도 바꾸지 않아요(사용자 결정, 2026-10-21). 끝나면 다음이 사실이에요.

- web과 worker는 `trss`라는 프로세스 하나이고, 컨테이너도 하나예요.
- 명령은 지금처럼 기록으로 남고, 적은 즉시 같은 프로세스에서 실행돼요.
- 화면은 SSE 연결 하나로 무엇이 바뀌었는지 듣고, 바뀐 것만 다시 읽어요.
- 실행 도중 끊긴 자막 작업은 `중단됨`으로 멈추고, 사람이 다시 시작해요.
- 화면의 API 타입은 Rust 타입에서 생성돼요.
- 합친 크레이트의 테스트는 한 곳에 모이고, 테스트 바이너리가 테스트마다 들이는 준비 비용이 줄어요.
- 바뀐 구조에서 테스트와 빌드 시간을 다시 측정해, 기능 크레이트를 묶을지 사용자가 정할 수 있어요.

다음은 범위 밖이에요.

- 기능과 그 규칙의 변경. 바뀌는 것은 아래 요구에 적은 화면 문구, `중단됨` 상태와 다시 시작, 화면이 바뀐 것을 아는 방식뿐이에요.
- 서버 브라우저 컨테이너와, 받은 압축 파일을 푸는 `trss-extract` 프로세스.
- 기능 크레이트 묶기. 이 변경은 묶을지 정할 측정값까지만 만들어요.
- 이 변경이 닿지 않는 크레이트의 테스트 양 줄이기. 그 테스트는 나중에 그곳을 고치는 변경이 정리해요(사용자 결정, 2026-10-21).
- 0.7.0 피드백의 남은 티켓 0140·0143, [리팩터링 뒤의 명세 차이 수정](README.md#리팩터링-뒤의-명세-차이-수정)의 티켓, 목표 6. 이 변경을 먼저 하고, 그 티켓들은 새 구조에서 해요(사용자 결정, 2026-10-21).
- 문서 작성 절차.

## 요구사항과 완료 기준

### 동작 보존

- [ ] 기능의 판정·저장 규칙과 화면에 보이는 내용은 그대로예요. 달라지는 것은 이 명세가 적은 것뿐이에요.
- [ ] 기능 규칙을 확인하는 테스트는 모두 통과해요. 지우는 테스트는 없어지는 인계만 확인하던 것과, 기능 크레이트가 이미 확인하는 규칙을 API나 프로세스를 거쳐 다시 확인하던 것뿐이에요. 티켓 결과에 지운 테스트와 그 까닭을 짝지어 적어요.
- [ ] API의 경로와 JSON 모양은 그대로예요. 더하는 것은 이벤트 경로와 자막 작업을 다시 시작하는 경로이고, 그 밖에 더하거나 빼는 필드는 이 명세에 적은 것뿐이에요.
- [ ] 명세의 검증 표가 이름으로 가리키는 테스트를 옮기거나 지운 티켓은, 같은 커밋에서 그 행을 고쳐요.

### 한 프로세스와 이름

- [ ] `trss-web`과 `trss-worker` 크레이트는 `trss` 크레이트 하나가 되고, 바이너리도 `trss` 하나예요. 기능 크레이트는 그대로예요.
- [ ] 앱 이미지에는 `trss`, `trss-extract`, `trss-probe` 바이너리와 정적 화면이 들어가고, 이미지는 `trss`로 시작해요.
- [ ] Compose의 `trss-web`·`trss-worker` 서비스는 `trss` 서비스 하나가 돼요. 이 서비스는 1000:1000으로 돌고, 미디어를 쓰기로 마운트하고, `trss_net`(`gw_priority`)과 `browser_net`에 붙어요. 지금 web이 하는 서브넷 확인을 그대로 하고, `stop_grace_period`는 15초예요. 환경 변수는 두 서비스가 받던 것을 합친 것이에요.
- [ ] 메모리 한도는 지금 두 컨테이너 한도의 합인 384M(worker 256M, web 128M)로 시작하고, 서버에서 측정한 값을 [0058](0058-server-oom-and-resource-limits.md)에 적어요.
- [ ] `trss` 프로세스 하나가 화면과 API, 5분 수집 주기, 감시 폴더 읽기(알림과 자동 감시), 명령, 자막 작업, 서버 브라우저의 수명, 보관 파일 정리를 돌려요.
- [ ] 같은 앱 데이터 폴더로 두 번째 `trss`를 시작하면, 그 프로세스는 이미 도는 프로세스가 있다고 로그에 남기고 멈춰요. 이 잠금 하나가 worker 잠금, 대기열마다의 잠금 파일, 브라우저 잠금, 수집 주기의 두 번째 실행 막기를 대신해요.
- [ ] 시작할 때 쓸 수 있는지 확인하는 목록에서 깨우기 소켓이 빠지고, 나머지 확인은 그대로예요.
- [ ] API 처리기는 미디어 파일을 직접 바꾸지 않아요. 파일을 바꾸는 일은 명령, 자막 작업, 보관 파일 정리의 실행 경로에서만 하고, 그 경로가 쓰기 직전에 계획·승인·현재 파일을 확인하는 지금 규칙은 그대로예요.
- [ ] 화면과 서버가 보내는 문구에 `worker`가 나오지 않아요. 행위자가 필요한 곳은 `trss`로 쓰고, 그렇지 않은 곳은 행위자를 빼요. 2026-10-21에 찾은 곳은 화면 9곳, 서버 4곳이에요.

### 명령

- [ ] API는 명령을 `commands` 테이블에 적은 뒤 같은 프로세스에서 곧바로 실행을 시작하고, 끝나기를 기다리지 않고 적은 명령으로 응답해요. 실행은 진행 중인 수집 주기나 관계없는 명령을 기다리지 않고, 대상이 겹치는 구간만 차례를 기다려요. 차례 규칙은 [웹 명령과 상태 갱신](../specs/web-app.md#웹-명령과-상태-갱신)의 지금 규칙 그대로예요.
- [ ] 같은 ID와 같은 내용으로 다시 보낸 명령은 적은 명령을 돌려주고, 같은 ID에 다른 내용이면 409로 거절해요. 같은 종류와 대상으로 열린 명령은 하나뿐이에요.
- [ ] 명령 안에서 다시 시도하는 경우(Transmission이 새 폴더를 늦게 보고할 때, 토렌트 추가에 응답이 없을 때, DB 오류)의 대기와 횟수는 지금과 같아요. 실행을 시작할 때마다 시도 횟수가 하나 늘고, 다섯 번째 시작에서 이유와 함께 끝나요. 다음 확인을 기다리던 것만 실행 안에서 기다리는 것으로 바뀌어요.
- [ ] 동시에 실행하는 명령은 지금처럼 8개까지예요.
- [ ] 프로세스가 다시 시작하면 끝나지 않은 명령을 다시 실행하고, 이것도 시도 한 번으로 세요. 업그레이드 직전에 끝나지 않은 명령도 새 버전이 처음 시작할 때 같은 길로 실행돼요(사용자 결정, 2026-10-21).
- [ ] 깨우기 소켓, 3초 주기 조회, worker 잠금 아래의 claim, `worker_heartbeat` 테이블은 없어져요. 테이블과 소켓 파일은 마이그레이션과 시작 처리가 지워요.
- [ ] 명령의 지난 결과를 읽는 곳은 그대로 `commands` 테이블을 읽어요. 규칙의 마지막 폴더 이동과 폴더 편집 막기, 회차 되돌리기, Anissia 새로고침의 결과, 수집 주기가 세는 응답 없던 토렌트 추가예요.
- [ ] `모두 보관`·`N개 보관`은 고른 규칙을 명령 하나로 받아 서버가 그 순서대로 보관하고, 잘 끝나지 않은 규칙에서 멈춰요. 탭을 숨기거나 화면을 닫아도 남은 규칙을 이어서 보관해요(사용자 결정, 2026-10-21).
- [ ] 보관 파일 정리는 요청하면 곧바로 실행해요. 프로세스가 다시 시작하면 `asked`인 정리를 다시 실행하고, 파일마다 길이와 SHA-256을 확인하는 지금 규칙은 그대로예요.

### 수집이 멈췄는지의 판정

- [ ] 상태판의 멈춤 판정은 수집 주기만 봐요. 진행 중인 주기가 `max(30분, 주기 간격의 10배)`를 넘게 돌거나, 끝난 주기의 다음 확인 시각이 한 주기 넘게 지났는데 다음 주기가 시작하지 않았으면 멈춘 것이에요. 감시 폴더 읽기와 명령은 주기와 따로 돌므로 판정에 들어가지 않아요.
- [ ] 멈췄을 때 편성 옆 열의 `다음` 자리와 수집 상태판의 RSS 칸은 `RSS 확인이 멈췄어요. 컨테이너 로그를 확인해 주세요.`를 강조 색으로 보여요. 휴대폰 요약의 `RSS 멈춤`은 그대로예요.

### 화면 알림

- [ ] 서버는 SSE 경로 하나로 무엇이 바뀌었는지 보내요. 이벤트는 바뀐 것의 종류와 ID만 담고, 화면은 이벤트를 받으면 지금의 조회 경로로 다시 읽어요.
- [ ] 아래 18곳은 주기 조회를 하지 않고, 표의 바뀜을 알리는 이벤트를 받을 때 다시 읽어요(사용자 결정, 2026-10-21). 지난 회차 검색의 진행은 명령이 아니라 API가 직접 돌리는 검색이에요.

- [ ] 2026-10-21에 찾은 18곳 말고도 서버 상태를 주기적으로 읽는 곳이 있으면, 그곳도 같은 방식으로 바꿔요. 입력이 멈추기를 기다리는 미리보기와 `몇 분 전` 같은 화면 안의 시계는 서버 상태 조회가 아니어서 그대로예요.
- [ ] 서버가 읽는 순간의 시각으로 정하는 상태는, 그 상태가 바뀌는 기한이 지나면 서버가 이벤트를 보내요. 그래서 아무 일도 일어나지 않아서 생기는 상태도 화면에 닿아요. 2026-10-21에 찾은 것은 상태판의 `stalled`예요.
- [ ] 브라우저 탭 하나는 연결을 하나만 열어요. 탭이 숨겨지면 연결을 닫고, 다시 보이면 연결한 뒤 보이는 것을 한 번 다시 읽어요.
- [ ] 연결이 끊겼다 다시 이어지거나, 서버가 이벤트를 다 보내지 못했다고 알리면, 화면은 보이는 것을 모두 다시 읽어요. 그래서 놓친 이벤트가 화면을 옛 상태로 남기지 않아요.
- [ ] 이벤트 경로는 다른 API와 같은 접근 경계 안에 있어요. 원격 인증 화면의 WebSocket은 그대로예요.
- [ ] 개발 환경의 Vite 프록시를 거쳐도 이벤트가 쌓이지 않고 바로 화면에 닿아요.

### 끊긴 자막 작업

- [ ] 받기·보관·적용·교체·재배치 단계를 실행하던 중에 프로세스가 멈춘 작업은, 다시 시작한 뒤 `중단됨`이 돼요. 이 작업은 할 일로 올리지 않고, 할 일 화면의 `자막 작업` 맨 위에 실패한 작업과 함께 보여요(사용자 결정, 2026-10-21).
- [ ] 인증·배치 확인·교체 승인·영상 대기·자막 대기처럼 사람을 기다리던 작업은 다시 시작한 뒤에도 그대로 기다려요.
- [ ] `중단됨`은 `held`와 다른 상태예요. 작업의 진행 중·보류를 읽는 곳(할 일 개수, 작업 목록과 상세, 라이브러리 배지, 작품 상세의 적용 상태, 영상 대기 판정)은 이 상태를 끝나지 않은 실패로 다뤄요.
- [ ] `중단됨`인 작업의 목록 행과 작업 상세에 `다시 시작` 버튼이 있고, 누르면 끊긴 단계부터 다시 해요. 수신 영역에 이미 받아 둔 묶음은 다시 받지 않아요.
- [ ] 파일을 쓰는 단계는 새 파일을 끝까지 쓴 뒤 이름을 바꿔 제자리에 둬요. 끊겨도 원래 파일이나 새 파일 중 하나는 제자리에 있어요.
- [ ] 교체는 새 파일과 지금 파일을 `RENAME_EXCHANGE`로 한 번에 맞바꾸고, 밀려난 파일이 승인한 원래 파일과 다르면 다시 맞바꿔요. 그래서 경로가 비는 순간이 없어요. 서버의 미디어 파일시스템이 이를 지원하는 것은 [0151](0151-probe-rename-exchange.md)이 서버에서 확인했어요.
- [ ] 재배치의 제거나 교체가 끊겨 옆으로 옮긴 파일이 남으면, trss는 그 파일을 자동으로 지우지 않아요.
- [ ] 끊겨서 남은 임시 파일은 trss가 지워요. 앱 데이터 폴더의 `receive/.partial/`과 `subtitle-files/.tmp/`는 시작할 때 비우고, 작품 폴더의 `.trss/staging/`은 한 실행이 그 폴더에 처음 쓰기 전에 비워요. 옮긴 파일은 `.trss/aside/`에 두어 이 정리에 걸리지 않아요.
- [ ] 자동 재개를 위한 효과별 기록 테이블과 기록·디스크 대조 코드는 없어져요. 마이그레이션이 테이블을 지우고, 업그레이드 때 실행 도중이던 작업은 `중단됨`이 돼요.

### 화면 타입 생성

- [ ] API가 화면에 보내는 응답과 화면에서 받는 요청 본문은 모두 Rust 구조체나 열거형이고, 화면의 TypeScript 타입은 그 타입에서 생성돼요. `json!`으로 만들던 응답과 오류 본문, 이벤트도 구조체가 돼요.
- [ ] 정해진 문자열만 오는 필드는 TypeScript에서도 문자열 리터럴 유니언이고, `string`으로 넓히지 않아요.
- [ ] 정수 필드는 TypeScript에서 `number`예요.
- [ ] 생성한 파일은 저장소에 커밋하고, 생성 결과가 커밋한 파일과 다르면 Rust 테스트가 실패해요. 화면을 빌드하는 Docker 단계에는 Rust가 없어서예요.
- [ ] 손으로 쓴 같은 뜻의 타입은 지우고, 화면은 생성한 타입을 써요. 생성한 이름끼리 겹치지 않아요. `npm run typecheck`가 통과해요.

### 테스트 정리

- [ ] `trss` 크레이트의 테스트는 단위 테스트 바이너리 하나와 `tests/it` 바이너리 하나에 있어요. 자기 바이너리를 갖는 것은 프로세스를 따로 써야 하는 테스트뿐이에요. 메모리 최고치를 측정하는 테스트처럼 프로세스 전체의 값을 보는 테스트가 여기에 들어가요.
- [ ] `trss` 크레이트의 테스트는 [테스트 나눔 ADR](../adr/0015-test-a-rule-once-in-its-crate.md)을 따라요. API 테스트는 요청과 응답의 모양만 확인하고, 프로세스 테스트는 다시 시작, 단일 실행 잠금, 동시 실행, 이벤트처럼 프로세스에서 생기는 일만 확인해요. 기능 규칙을 API나 프로세스를 거쳐 다시 확인하던 테스트는, 기능 크레이트가 그 규칙을 확인하고 있으면 지우고, 아니면 기능 크레이트로 옮겨요.
- [ ] `remote_screen_docker`는 기본 `cargo test --workspace`에서 빌드되지 않아요. 따로 켜면 지금처럼 돌아요.
- [ ] 테스트 바이너리가 테스트 하나를 준비하는 데 드는 비용을 측정해요. 실행 시간이 가장 큰 바이너리들과 빌드 시간이 가장 큰 테스트 단위들이 대상이에요. 찾은 원인마다 고치거나, 고치지 않은 까닭을 결과에 적어요. 고친 것은 고치기 전과 뒤의 값을 함께 적어요. 2026-10-21에 실행에서 가장 큰 것은 `trss-web` 단위 테스트(7.0초, 468개)와 `trss-worker`의 `it`(6.6초, 91개)였고, 빌드에서 가장 큰 것은 `trss-jobs`의 `it`(37.8초), `trss-web` 단위 테스트(33.8초), `trss-collect` 단위 테스트(30.5초)였어요.
- [ ] 메모리 최고치를 측정하는 테스트 3개는 기본 실행에 그대로 둬요(사용자 결정, 2026-10-21). 2026-10-21에 셋을 합쳐 6.3초가 걸렸어요. 합친 프로세스가 메모리 한도 안에서 도는지를 바꿀 때마다 바로 알려고 두는 거예요.

## 순서

1. 첫 티켓을 시작하는 커밋에서 기준값을 측정해요.
2. web과 worker를 `trss` 하나로 합쳐요. 크레이트, 이미지, Compose, 단일 실행 잠금, 인계 코드 없애기, 명령 바로 실행, 다시 시작 때 명령 다시 실행, 멈춤 판정, 문구, `trss` 크레이트의 테스트 정리가 여기에 들어가요.
3. 끊긴 자막 작업을 `중단됨`으로 바꿔요.
4. 화면 알림을 SSE로 바꿔요.
5. 화면 타입을 생성해요.
6. 테스트의 고정 비용을 측정하고 줄여요.
7. 다시 측정하고, 기능 크레이트 결정을 받아요.
8. 서버에 올려 확인해요.

2–5는 합친 `trss` 크레이트를 고치므로 2가 먼저예요. 4는 같은 프로세스 안에서 바뀜을 알아야 하므로 2 뒤예요. 5를 4 뒤에 하면 이벤트 타입도 함께 생성돼요. 3과 5는 2의 크레이트 합치기 뒤에, 4는 2의 명령 바로 실행 뒤에 시작할 수 있고, 5의 마지막 티켓은 4 뒤에 해요. 티켓과 막는 관계는 [티켓 목록의 구조 가볍게 하기](README.md#구조-가볍게-하기)에 있어요. 4 가운데 [0155](0155-events-for-jobs-todos-candidates.md)와 [0156](0156-events-for-covers-schedule-status.md)은 3 뒤에 쓰는 쓰기 길 모으기 명세의 티켓 뒤에 해요([결정](#결정)). 6은 테스트의 모양이 2–5로 정해진 뒤에 해야 같은 것을 두 번 고치지 않아요. 7과 8은 코드 변경이 끝난 뒤예요.

## 티켓에서 받을 사용자 결정

- 서버의 미디어 파일시스템이 `RENAME_EXCHANGE`를 지원하지 않을 때의 교체 방법은, [0151](0151-probe-rename-exchange.md)이 지원하는 것을 확인해서 정하지 않아도 돼요(2026-10-21).
- 측정 결과를 보고, 기능 크레이트를 묶을지 정해야 해요.
- 이 변경을 서버에 올리는 때를 승인해야 해요. 서버에서 `trss-probe`를 돌리는 것은 2026-10-21에 사용자가 직접 했어요([0151](0151-probe-rename-exchange.md)).
- 이 릴리스에 함께 들어가는 0137–0139·0141·0142를 [0143](0143-deploy-feedback-fixes.md)의 서버 확인대로 이 배포에서 함께 볼지 정해야 해요.

## 결정

사용자의 결정이에요. 모두 2026-10-21에 정했어요.

- 수집과 자막 기능을 모두 두고, 기능 안의 규칙도 그대로 둬요.
- 줄일 것은 코드를 읽고 고치는 비용, 기능 하나를 더하는 단계, 테스트에 드는 계산 자원, 서버 운영이에요.
- web과 worker를 한 프로세스로 합쳐요([한 프로세스 ADR](../adr/0019-one-process-for-web-and-worker.md)).
- 합친 크레이트·바이너리·컨테이너의 이름은 `trss`예요.
- 합친 프로세스가 미디어를 쓰기로 마운트하는 것을 받아들여요. 접근 경계인 LAN·VPN과 origin 검사는 그대로예요.
- 명령은 `commands` 테이블에 기록으로 남기고, 적은 즉시 실행해요.
- 다시 시작하면 끝나지 않은 명령을 다시 실행해요.
- 화면은 SSE로 바뀐 것을 알고, 서버 상태를 주기적으로 읽던 18곳을 모두 바꿔요.
- 실행 도중 끊긴 자막 작업은 `중단됨`으로 멈추고, 실패한 작업처럼 `자막 작업` 맨 위에 보여요([끊긴 작업 ADR](../adr/0020-interrupted-jobs-wait-for-a-restart.md)).
- 화면의 TypeScript 타입은 Rust 타입에서 생성해요.
- 기능 크레이트를 묶을지는 합친 뒤 다시 측정하고 정해요.
- 테스트 정리는 이 변경이 닿는 테스트와 테스트 바이너리의 고정 비용까지만 해요. 다른 크레이트의 테스트 양은 줄이지 않아요.
- 메모리 최고치를 측정하는 테스트는 기본 실행에 둬요.
- 이 변경을 0140·0143, 리팩터링 뒤의 명세 차이 수정 티켓, 목표 6보다 먼저 해요.
- 이 변경을 마치면 따로 서버에 올려 확인해요.
- 바뀜 이벤트는 trss-core의 채널로 알려요. 상태를 쓰는 코드가 커밋한 뒤 바뀐 것의 종류와 ID를 알리고, 메모리에만 있는 상태(지난 회차 검색의 진행)도 같은 채널로 알려요. DB가 스스로 알리면 행만 알고 화면의 대상은 모르고, `trss` 크레이트에서만 알리면 기능 크레이트 안에서 도는 실행의 바뀜이 늦어서예요.
- 상태를 바꾸는 길을 대상별로 하나로 모으고 알림은 그 길에서만 하는 일은, [0153](0153-no-effect-records.md) 뒤에 명세와 티켓을 따로 써서 해요. [0155](0155-events-for-jobs-todos-candidates.md)와 [0156](0156-events-for-covers-schedule-status.md)은 그 길 위에서 해요. 2026-10-21에 자막 작업 상태를 쓰는 SQL 문이 파일 17개에 79개로 흩어져 있어 알림을 빠뜨리기 쉬운데, 0153이 그 코드를 크게 바꾸므로 그 뒤에 모아요.
- `모두 보관`·`N개 보관`은 명령 하나로 받아 서버가 규칙 순서대로 보관해요. 화면이 규칙을 하나씩 보내고 끝나기를 기다리면, 숨겨진 탭이 이벤트 연결을 닫는 동안 남은 규칙을 보내지 못하고 멈춰서예요. 0154의 검토에서 나온 것이고, [0163](0163-batch-archive-on-server.md)이 해요.
- 자막 작업이 보관본이나 들인 사본을 공개한 뒤 기록하기 전에 끊기면, 다시 할 때 앱이 고를 이름에 기록 없는 파일이 있고 길이와 SHA-256이 같으면 그 파일을 기록해요. 그대로 두고 다음 번호로 새로 쓰면, 화면과 보관 파일 정리에 나오지 않는 파일이 남고 보관본 이름에 `(2)`가 붙어서예요. [0153](0153-no-effect-records.md)이 해요.

이 명세를 쓰며 정한 것이에요. 사용자가 바꿀 수 있어요.

- 이벤트는 바뀐 것의 종류와 ID만 담고, 화면은 지금의 조회 경로로 다시 읽어요. 데이터의 출처가 조회 경로 하나로 남고, 이벤트용으로 같은 데이터의 타입을 따로 두지 않아도 돼서예요.
- 멈춤처럼 시간이 지나서 생기는 상태는, 서버가 그 기한에 이벤트를 보내요. 화면이 기한을 계산해 다시 읽게 하면 판정 규칙이 화면과 서버 두 곳에 생겨서예요.
- 숨겨진 탭은 연결을 닫아요. HTTP/1.1에서 브라우저는 서버 하나에 연결을 6개쯤만 열어서, 숨은 탭이 연결을 쥐고 있으면 다른 탭의 API 요청이 막힐 수 있어서예요.
- API 처리기는 미디어 파일을 직접 바꾸지 않아요. 쓰기 직전의 확인을 한 경로에 두는 지금 규칙을 지키고, 미디어를 쓰기로 마운트하는 위험을 그 경로로 좁히려는 거예요.
- 명령 안의 다시 시도 횟수와 대기는 지금과 같아요. 기능 안의 규칙을 그대로 두기로 한 결정을 따른 거예요.
- 교체는 `RENAME_EXCHANGE`로 해요. 효과별 기록 없이도 경로가 비는 순간을 없애려는 거예요.
- 끊겨서 옆으로 옮긴 채 남은 파일은 자동으로 지우지 않아요. 사용자 자막의 하나뿐인 사본일 수 있어서예요.
- 새 임시 파일은 `.trss/staging/`과 `receive/.partial/`에, 옮긴 파일은 `.trss/aside/`에 두고, 예전 `.trss/tmp/`와 `receive/.tmp/`는 비우지 않아요. 예전 두 폴더에는 옮긴 원래 자막과 보호 복사본, 다시 시작한 뒤에도 남아야 하는 사이트 확인 다운로드가 있어서예요. 0153을 시작하며 정했어요.
- 다른 작업의 끝나지 않은 효과를 피하던 판정은 없애요. 실행은 한 번에 한 작업뿐이고 기록 없이 다시 하는 단계에는 반쯤 공개된 상태가 남지 않아서예요. 다른 작업의 끊긴 적용이 회차를 가리던 드문 경우에 `보관만` 하던 것이 일반 비교와 교체 계획이 되고, 재배치 제거의 `지우는 중` 상태는 화면에 나오지 않아요. 0153을 시작하며 정했어요.
- 0153이 단계를 기록 없이 다시 하게 바꾸며 드문 경우의 동작이 달라졌어요. 사본이 없어지고 보관본이 그 회차로 돌아온 재배치 제거가 `done`으로 끝나 재배치를 새로 맞추는 것, 예전 릴리스가 지우다 남긴 사본을 나중의 재배치가 다시 계획하는 것, 끊긴 적용을 다시 하면 `ADOPTED` 문장이 남는 것, 교체에 `RENAME_EXCHANGE`가 꼭 있어야 하는 것, 다시 맞바꾼 교체가 들인 보관본을 하나 더 남기는 것이에요. 까닭은 [0153 결과의 바뀐 동작](0153-no-effect-records.md#바뀐-동작)에 있어요. 0153을 마치며 정했어요.
- 보관 파일 정리도 명령처럼 바로 실행하고, 다시 시작하면 다시 실행해요. 지금도 파일마다 확인하며 지워서 다시 실행해도 되기 때문이에요.
- 메모리 한도는 두 컨테이너 한도의 합으로 시작해요. 합쳤을 때의 사용량을 서버에서 측정하기 전이라, 지금 여유를 그대로 두려는 거예요.
- 멈춤 문구는 `RSS 확인이 멈췄어요. 컨테이너 로그를 확인해 주세요.`로 바꿔요. 화면이 보인다면 프로세스는 살아 있으므로, worker가 도는지 확인하라는 지금 문구는 맞지 않아요.
- 타입 생성 도구는 serde 속성을 읽는 ts-rs로 하고, 정수는 `number`로 생성해요. 지금 화면이 정수를 `number`로 받고 있어서예요.

## 가정

- 수신 영역에 이미 받아 둔 묶음은 작업의 `받음` 상태로 알 수 있어서, 다시 시작할 때 다시 받지 않아도 돼요. 2026-10-22에 [0153](0153-no-effect-records.md)이 `받음`을 받기를 마친 수신(`done`)으로 읽게 했고, 기록 없이 다시 시작한 작업이 그 묶음을 다시 받지 않는 것을 테스트로 확인했어요.
- 설정의 버전 충돌 처리와 교체 승인을 다시 검증하는 규칙은 그대로예요.
- 서버 브라우저 컨테이너와 `trss-extract`는 바꾸지 않아도 합친 프로세스와 함께 돌아요.
- 서버의 미디어 파일시스템이 `RENAME_EXCHANGE`를 지원해요. 2026-10-21에 [0151](0151-probe-rename-exchange.md)이 서버(j4105)의 미디어 마운트인 xfs의 작품 폴더에서 확인했어요.
- API의 정수 값은 모두 2^53보다 작아요. 확인하지 않았어요.
