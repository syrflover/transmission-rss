# 0117 되풀이해 쓰는 SQL 문을 캐시해요

- 상태: 완료 (2026-10-08)
- 출처: [SQL 문 캐시](refactoring.md#sql-문-캐시), [0116](../archive/tickets/5-deployed-verification/0116-allocator-measurement.md)의 측정
- 막는 티켓: [0092](0092-refactor-baseline.md)(기준값)

## 작업

2026-10-07 [0116](../archive/tickets/5-deployed-verification/0116-allocator-measurement.md)의 측정에서, 운영 한도로 띄운 trss-web의 user CPU 표본 중 8–10%가 SQL을 해석하는 함수(`sqlite3RunParser`, `yy_reduce`, `sqlite3GetToken`, `keywordCode`)였어요.
같은 날 `tests/` 폴더와 `_tests.rs` 파일을 빼고 `prepare`를 부르는 곳이 175곳이었고, `prepare_cached`를 쓰는 곳은 없었어요.
프로세스마다 SQLite 연결이 하나이고 `Mutex` 뒤에 있으므로(trss-core의 `db.rs`), 그 연결의 문 캐시가 모든 요청에 쓰여요.

- 되풀이해 쓰는 SQL 문을 `prepare_cached`로 받아요. 한 번만 쓰는 문(마이그레이션, 가져오기 같은)은 그대로 둬요.
- rusqlite의 문 캐시는 기본 크기가 작으므로, 쓰는 문의 수에 맞춰 연결을 열 때 크기를 정해요.
- 동작을 바꾸지 않는 정리라서, 기존 테스트를 고치지 않고 통과시켜 확인해요.

## 완료 기준

## 결과

### 바꾼 것

- 테스트 밖의 코드에서 되풀이해 쓰는 SQL 문 715곳을 연결의 문 캐시로 받아요. `prepare`는 `prepare_cached`로, 같은 경로의 `execute`와 `query_row`는 `prepare_cached(…)?.execute(…)`와 `.query_row(…)`로 바꿨어요. 크레이트별로 trss-jobs 354곳, trss-collect 179곳, trss-library 151곳, trss-core 23곳, trss-anilist와 trss-anissia 4곳씩이에요. trss-web, trss-worker, trss-browser에는 테스트 밖의 SQL이 없어요.
- 그대로 둔 것이에요.
  - 한 번만 쓰는 문이에요. trss-core `db.rs`의 마이그레이션과 pragma, `settings/migrate.rs`, 채널 가져오기(`channels/import.rs`), 프로세스가 시작할 때 한 번 도는 `ScreenStore::unbind_all`과 `StatusStore::record_cycle_interval`, `execute_batch`예요.
  - `IN (?, ?, …)`의 개수처럼 모양이 값에 따라 달라지는 문 11곳이에요. 수집 이력 목록(`history_page`)이 여기에 들어요. 웹 요청마다 도는 경로이지만, 선택 필터 네 개의 조합만큼 모양이 생겨서 캐시하지 않았어요.
  - `format!`으로 만들어도 고정된 열 목록, `under_way()`의 상태 목록, 상수 조각만 넣는 문은 모양이 정해져 있어서 캐시해요.
- 연결을 여는 `Db::open_blocking`에서 캐시 크기를 1024로 정해요(`STATEMENT_CACHE_CAPACITY`). 바꾼 곳의 SQL 글자를 정리해 세면 서로 다른 문이 약 680개이고, web과 worker는 각각 그 일부만 써요.
- trss-core에 `a_cached_statement_is_prepared_again_after_the_schema_changed`를 더했어요. 캐시에 든 `SELECT *`가 열을 더한 뒤와, 표를 지우고 다른 열로 다시 만든 뒤에 새 열과 행을 읽는지 확인해요.

### 검증한 것

2026-10-08, 개발 PC(Ryzen 5 5600X, RAM 32 GB)에서 측정했어요. 원자료는 이 PC의 `dev/local/measure/0117/`에 있어요.

테스트예요.

- 기존 테스트는 고치지 않았어요. `cargo test --locked --workspace -j 4`에서 2,819개가 통과했고, 실패는 0개, 무시는 14개였어요. 앞(0092의 기준값)은 2,818·0·14이고, 하나 많은 통과는 위에서 더한 테스트예요.
- 0092와 같은 명령과 빌드 상태로 두 번 측정했어요. 테스트 바이너리 31개의 합은 앞 56.6초와 56.3초, 뒤 56.1초와 54.9초예요. 줄어든 폭이 같은 상태로 두 번 잰 차이와 비슷해서, 테스트 시간에는 뚜렷한 효과가 없다고 봐요.

web 부하예요. 0116과 같은 `dev/measure/run.sh`로, `df890d3`에서 빌드한 앞 이미지와 이 변경을 더한 뒤 이미지를 세 번씩 섞어 측정했어요. 데이터는 0116 때 뜬 개발 환경의 사본이고, 한도는 운영 compose 그대로예요. 표는 평균이고 괄호는 최소–최대예요.

- web 부하의 CPU 시간이 36% 줄었어요. user 시간은 1.74초 줄어서, 파서 함수 네 개의 표본(앞의 8.5%, 약 0.35초)보다 훨씬 많이 줄었어요. 0116에서 적었듯 이 네 함수는 SQL 해석의 하한이고, 문을 만드는 데 드는 나머지(코드 생성, 할당)도 함께 빠진 것으로 봐요.
- 요청 3,390개가 앞뒤 모두 성공했고, 응답의 바이트 수가 앞뒤로 같았어요(317,529,360바이트).
- 최대 메모리는 늘지 않았어요. 앞의 web 최대 메모리는 10.70–20.15 MiB로 흔들렸어요.
- 측정을 시작할 때 load average는 2.8–4.5였어요. 무거운 빌드나 테스트는 함께 돌지 않았어요.

### 알아 둘 것과 남은 일

- 캐시에서 꺼낸 문은 처음 한 단계를 돌기 전까지 스키마가 바뀌기 전의 열 이름과 개수를 알려줘요. SQLite가 돌 때 다시 준비하므로 읽는 행은 맞아요. 지금 제품 코드는 문을 돌리기 전에 `column_count()`나 `column_names()`를 읽지 않아요. 더한 테스트도 행을 읽은 뒤에 열을 확인해요.
- 캐시 크기는 문이 늘어도 자동으로 따라가지 않아요. 서로 다른 문의 수가 1024에 가까워지면 상수를 올려야 해요. 실행 중에 실제로 캐시에 든 문의 수는 세지 않았어요.
- 측정은 이 PC의 개발 환경에서만 했어요. 실제 서버(J4105)에서 측정한 값은 없어요.
