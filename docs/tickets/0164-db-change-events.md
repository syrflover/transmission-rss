# 0164 DB 연결이 바뀐 표의 종류와 행의 ID를 커밋 뒤에 알려요

- 상태: 대기
- 출처: [구조 가볍게 하기 명세의 화면 알림](lighter-structure.md#화면-알림), [명세의 결정](lighter-structure.md#결정)
- 막는 티켓: [0154](0154-change-events-and-command-reads.md)(바뀜 채널과 SSE 경로). 0154를 마쳐서 바로 시작할 수 있어요.

## 작업

[0155](0155-events-for-jobs-todos-candidates.md)와 [0156](0156-events-for-covers-schedule-status.md)이 화면 11곳을 이벤트로 옮기려면, 그 화면들이 읽는 DB 상태가 바뀔 때마다 이벤트가 가야 해요. 2026-10-22에 조사해 보니 테스트 밖의 쓰기 SQL 문이 390곳에 흩어져 있었어요. 할 일은 저장된 행 없이 읽을 때 셈하고, 작품을 넣으면 DB trigger가 표지와 시즌 정보의 첫 작업 행을 만들어요. 그래서 쓰는 코드마다 알리게 하지 않고, DB 연결이 커밋 뒤에 바뀐 표의 종류와 행의 ID를 알리게 해요(사용자 결정, 2026-10-22).

- trss-core가 모든 표의 종류와, 바뀐 행이 가리키는 대상의 열(작업, 작품, Anissia 작품 같은 것)을 적은 목록을 가져요. 대상 열이 없는 표는 종류만 알리고, 화면이 읽지 않는 표는 알리지 않는 표로 적어요.
- 채널을 받은 DB 연결은 목록의 표마다 넣기·고치기·지우기 뒤에 도는 임시 trigger를 걸어요. trigger는 종류와 대상 ID를 연결의 임시 표에 적고, `Db::run`이 끝날 때 열린 트랜잭션이 없으면 적힌 것을 읽어 비우고 알려요. 임시 표는 메모리에 둬요.
- 임시 trigger로 하는 까닭은 2026-10-22에 sqlite3로 확인했어요. `WITHOUT ROWID` 표, 스키마 trigger가 만든 행, cascade로 지워진 행, `WHERE` 없는 `DELETE`까지 적히고, 되돌린 트랜잭션과 아무 행도 바꾸지 않은 쓰기는 적히지 않았어요. SQLite의 update hook은 `WITHOUT ROWID` 표(75개 중 44개)와 `WHERE` 없는 `DELETE`를 알리지 않고, preupdate hook은 rusqlite 빌드에 bindgen과 libclang이 필요해요.
- 종류는 화면이 읽는 표의 묶음으로 정해요. 원격 화면처럼 자주 바뀌는 표는 따로 두어, 그 표를 읽는 화면만 다시 읽게 해요.
- 이벤트의 `id`는 대상 열이 없으면 `null`이에요. 화면은 자기 대상의 ID이거나 `null`인 이벤트를 받으면 다시 읽어요.
- 명령 표는 [0154](0154-change-events-and-command-reads.md)의 `CommandStore`가 이미 한 길에서 ID와 함께 알리므로, 이 장치에서는 알리지 않는 표로 적어요. 메모리에만 있는 지난 회차 검색의 진행도 지금처럼 그 코드가 알려요.
- `trss`의 web과 worker 연결은 모두 채널을 받아요. 테스트에서는 이벤트를 확인하는 것만 채널을 붙여서, 다른 테스트는 임시 trigger를 만드는 비용을 들이지 않아요.

## 완료 기준

- [ ] 마이그레이션을 마친 스키마의 모든 표가 목록에 종류와 대상 열로, 또는 알리지 않는 표로 있어요. 목록에 없는 표나 표에 없는 열이 있으면 테스트가 실패해요.
- [ ] 채널을 받은 연결이 커밋한 쓰기마다 바뀐 표의 종류와 대상 ID를 한 번씩 알리는 것을 테스트가 확인해요. 테스트하는 경우는 rowid 표와 `WITHOUT ROWID` 표의 넣기·고치기·지우기, 스키마 trigger가 만든 행, cascade로 지워진 행, `WHERE` 없는 `DELETE`, 대상 열이 바뀐 고치기(옛 ID와 새 ID 둘 다)예요.
- [ ] 되돌린 트랜잭션, 아무 행도 바꾸지 않은 쓰기, 읽기만 한 `Db::run`은 알리지 않아요. 테스트가 확인해요.
- [ ] 알림은 커밋한 뒤에 가요. 이벤트를 받고 다른 연결로 읽으면 바뀐 값이 보이는 것을 테스트가 확인해요.
- [ ] `trss` 프로세스에서 worker 쪽 쓰기의 이벤트가 `GET /api/events`로 화면에 닿는 것을 프로세스 테스트가 확인해요.
- [ ] 명령과 지난 회차 검색의 이벤트는 그대로예요. 0154의 테스트가 고치지 않고 통과해요.
- [ ] 화면의 이벤트 타입이 `id`가 `null`인 이벤트를 받아들이고, 화면 테스트와 `npm run typecheck`가 통과해요.
- [ ] 행 하나를 쓸 때 더 드는 시간과, 개발 환경에서 수집 주기 하나와 자막 작업 하나가 보내는 이벤트 수를 측정해 결과에 적어요. 이벤트가 몰려 화면이 쉬지 않고 다시 읽을 만큼이면, 서버가 짧은 간격으로 모아 보내게 하고 그 간격을 결과에 적어요.
- [ ] 같은 커밋에서 [웹 앱 공통 명세](../specs/web-app.md)의 작업 상태 갱신 문단과 검증 표에, 이벤트를 누가 언제 보내는지와 표와 종류의 목록이 어디 있는지 적어요.
- [ ] [명세의 동작 보존 조건](lighter-structure.md#동작-보존)을 지켜요.
