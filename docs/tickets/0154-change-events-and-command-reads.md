# 0154 바뀜을 알리는 SSE 경로를 만들고 명령과 지난 회차 검색의 주기 조회를 바꿔요

- 상태: 완료
- 출처: [구조 가볍게 하기 명세의 화면 알림](lighter-structure.md#화면-알림)
- 막는 티켓: [0147](0147-commands-start-at-once.md)(명령 바로 실행)

## 작업

화면은 서버 상태를 18곳에서 주기적으로 다시 읽어요. 이 티켓은 무엇이 바뀌었는지 알리는 SSE 경로 하나와 화면 쪽의 연결을 만들고, 그 위로 명세 표의 처음 7곳을 옮겨요. 명령의 상태를 읽던 6곳과 지난 회차 검색의 진행이에요. 나머지 11곳은 [0155](0155-events-for-jobs-todos-candidates.md)와 [0156](0156-events-for-covers-schedule-status.md)이 같은 길로 옮겨요.

명령의 상태는 [0147](0147-commands-start-at-once.md)이 만든 실행 경로에서 바뀌므로 그 뒤에 해요. 지난 회차 검색은 명령이 아니라 API가 직접 돌리는 검색이에요.

명세를 쓰며 정한 것은 다음과 같아요.

- 이벤트는 바뀐 것의 종류와 ID만 담고, 화면은 지금의 조회 경로로 다시 읽어요. 데이터의 출처가 조회 경로 하나로 남고, 이벤트용으로 같은 데이터의 타입을 따로 두지 않아도 돼서예요.
- 숨겨진 탭은 연결을 닫아요. HTTP/1.1에서 브라우저는 서버 하나에 연결을 6개쯤만 열어서, 숨은 탭이 연결을 쥐고 있으면 다른 탭의 API 요청이 막힐 수 있어서예요.

바뀜을 내보내는 방법은 사용자가 정했어요(2026-10-21, [명세의 결정](lighter-structure.md#결정)). trss-core의 채널로, 상태를 쓰는 코드가 커밋한 뒤 바뀐 것의 종류와 ID를 알리고, 지난 회차 검색의 진행처럼 메모리에만 있는 상태도 같은 채널로 알려요. 이 티켓이 다루는 명령과 지난 회차 검색은 상태를 바꾸는 길이 이미 하나씩이라 그 길에서 알려요. 0155와 0156은 같은 채널을 쓰되, 0153 뒤에 쓰는 쓰기 길 모으기 명세가 모은 길에서 알려요.

## 결과

2026-10-21에 바뀜을 알리는 SSE 경로 `GET /api/events`와 trss-core의 바뀜 채널을 만들고, 명세 표의 처음 7곳을 주기 조회에서 이벤트로 옮겼어요. 일괄 보관은 탭이 숨겨진 동안 멈추게 됐는데, 그것을 고치는 [0163](0163-batch-archive-on-server.md)이 끝날 때까지 동작 보존 상자는 비워 둬요. 까닭은 [일괄 보관](#일괄-보관)에 있어요.

### 채널과 알리는 곳

- `trss_core::changes`의 `Changes`는 tokio broadcast 채널을 감싸요. `announce(kind, id)`로 알리고, 듣는 쪽이 없어도 실패하지 않아요. 바뀜의 종류(`ChangeKind`)는 지금 `command`와 `past_search`이고, 0155와 0156이 늘려요.
- 채널은 0147의 `Wakes`처럼 명시적으로 건네요. `main.rs`가 프로세스에 하나 만들어 웹의 `AppState::with_changes`와 worker의 `Worker::with_changes`에 주고, 둘이 각자의 `CommandStore`와 `PastSearch`에 넘겨요. `CommandStore::new`는 그대로라서, 채널을 받지 않은 테스트의 저장소는 아무에게도 알리지 않아요. DB 핸들에 채널을 넣거나 프로세스 전역으로 두는 길은 고르지 않았어요.
- `CommandStore`는 커밋한 뒤에 알려요. 새로 접수했을 때, 집어 실행을 시작했을 때, 시작 횟수를 넘겨 집는 길에서 실패로 끝냈을 때, 끝냈을 때예요. 거절했거나 이미 있던 접수, 끝낸 것이 없는 끝내기, 화면이 보지 않는 `note_*`는 알리지 않아요.
- 회차 되돌리기는 명령 상태가 바뀌지 않아도 파일을 기록할 때마다 진행이 보여서, `announce_progress`로 그때도 알려요.
- `PastSearch`는 검색이 시작할 때, 진행(`sent`/`needed`)이 바뀔 때, 끝나거나 실패할 때 레지스트리 잠금 안에서 알려요. 같은 규칙의 새 검색, 개수와 시간을 넘긴 정리, 취소로 지워진 검색도 알려요. 리뷰에서 나온 것으로, 다른 탭이 따라가던 검색이 지워져도 그 탭이 다시 읽어 예전처럼 `검색이 사라졌어요`를 보여요.

### 이벤트 경로

경로는 구독한 뒤에 `ready`를 먼저 보내고, 바뀜마다 `change`(`{"kind":…,"id":…}`)를, 채널을 따라가지 못해 건너뛰면 `lagged`를 보내요. 15초 동안 보낼 것이 없으면 `alive`를 보내요. 모든 이벤트에 JSON `data`가 있어요. 프로세스를 끌 때는 `AppState::shutdown`으로 스트림을 닫아서, 열린 연결이 graceful shutdown을 붙잡지 않아요. 압축하는 layer는 없고, reverse proxy를 위해 `X-Accel-Buffering: no`를 보내요. 다른 경로와 같은 `Host` 검사를 거쳐요.

`alive`는 리뷰에서 나온 것이에요. 처음에는 keep-alive를 SSE 주석으로 보냈는데, `EventSource`는 주석을 페이지에 전하지 않아요. 그래서 노트북이 잠든 사이 서버가 다시 시작하는 식으로 연결이 소리 없이 죽으면, 화면이 그것을 모른 채 옛 상태로 남을 수 있었어요. 이제 화면은 45초 동안 아무 이벤트도 못 들으면 연결을 새로 열고, `ready`로 모두 다시 읽어요.

### 화면

- `web/src/lib/events.ts`가 탭의 `EventSource` 하나를 맡아요. 페이지가 보이고 듣는 화면이 있을 때만 열고, `ready`·`lagged`와 읽지 못한 `change`에는 모두에게 다시 읽게 하고, 맞는 `change`는 그 화면에만 알려요. 브라우저가 포기한 연결은 5초 뒤에 다시 열어요. 한 화면의 처리기가 예외를 던져도 다른 화면은 알림을 받아요.
- `watchCommands.ts`의 `CommandWatch`는 명령을 읽기 전에 듣기 시작하고, 한 명령의 읽기는 한 번에 하나만 하며, 읽는 중에 온 바뀜은 끝난 뒤 한 번 더 읽어요. 읽지 못하면 그 화면이 예전에 쓰던 간격 뒤에 다시 읽어요(일괄 보관 1초, 지난 회차 검색 2.1초, 나머지 2초). 그래서 실패를 견디는 시간은 예전과 같아요.
- 명령과 지난 회차 검색을 읽는 요청은 15초가 지나면 실패로 쳐요(`timedRead`). 대답이 오지 않는 읽기 하나가 뒤의 읽기를 모두 막지 않게 하려는 것으로, 리뷰에서 나온 것이에요.

7곳은 이렇게 바뀌었어요.

| 곳 | 파일 | 지금 |
| --- | --- | --- |
| 구독 추가와 지난 회차 검색의 받기 행 | `collect/subs/add/useReceive.ts` | 기다리는 명령 ID를 `CommandWatch`로 따라가요 |

### 일괄 보관

`모두 보관`·`N개 보관`은 화면이 규칙마다 명령을 보내고 끝나기를 기다려 다음 규칙을 보내요. 탭을 숨기면 이벤트 연결이 닫혀 화면이 명령이 끝난 것을 모르므로, 지금 규칙 하나는 서버가 끝까지 옮기지만 남은 규칙은 다시 보일 때까지 보내지 않아요. 예전에는 1초 주기 조회가 숨겨진 탭에서도 느리게 돌아 이어 갔어요. 리뷰에서 나온 것이고, 사용자가 일괄 보관을 서버가 순서대로 처리하게 하기로 했어요(2026-10-21, [명세의 결정](lighter-structure.md#결정)). [0163](0163-batch-archive-on-server.md)이 해요.

### 개발 환경에서 확인

2026-10-21에 이 PC의 개발 환경(서버 DB 사본, 이 변경으로 빌드한 이미지)을 Vite 개발 서버로 열고 built-in browser로 봤어요.

- 감시 폴더의 `다시 확인`을 누르자, 명령의 접수·시작·끝남 `change` 셋이 POST 응답과 같은 43 ms에 Vite 프록시를 거쳐 왔어요. 화면은 44 ms에 명령을 한 번 읽고 52 ms에 폴더 목록을 다시 읽은 뒤 `다시 확인했어요.`를 보였고, 14초 동안 명령을 다시 읽지 않았어요.
- 리뷰를 고친 이미지에서 다시 누르자 이번에는 끝남이 첫 읽기 뒤에 와서, 화면이 명령을 두 번 읽고 끝났어요. 마지막 이벤트 15초 뒤에 `alive`가 프록시를 거쳐 왔어요.
- 화면의 `sharedEvents`에 구독자 둘을 붙이자 연결이 하나 열렸어요. `visibilitychange`로 숨김을 흉내 내자 닫혔고, 다시 보이게 하자 열려 4 ms 뒤 `ready`로 둘 다 다시 읽었어요. 마지막 구독자가 빠지자 닫혔어요. built-in browser는 뒤에 있는 탭도 `visible`로 남겨서 숨김은 흉내 냈어요.

확인하지 않은 것은 다음과 같아요.

- 브라우저가 실제로 탭을 숨길 때와, 브라우저가 포기한 연결을 5초 뒤에 다시 여는 것
- 소리 없이 죽은 연결을 45초 뒤에 새로 여는 것: 가짜 스트림과 멈춘 시계로만 확인했어요.
- 7곳의 React 훅: 자동 테스트가 없고, 개발 환경에서는 감시 폴더의 `다시 확인`만 눌러 봤어요.
- 서버(j4105)와 reverse proxy를 거친 전달

### 검토

구현은 `stora:task` 에이전트가 했고, 독립 검토(`stora:complex-reviewer`)가 이벤트를 놓쳐 화면이 옛 상태로 남는 순서를 찾았어요. 막는 문제는 없었고, 지적 일곱 가지 가운데 여섯은 위에 적은 대로 고쳤어요. 지워진 검색의 알림, `alive`와 45초 감시, 회차 되돌리기의 진행 읽기, 읽기 시간 제한, 처리기 예외, 명세 문구예요. 남은 하나는 [일괄 보관](#일괄-보관)이에요.
