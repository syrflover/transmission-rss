# 0154 바뀜을 알리는 SSE 경로를 만들고 명령과 지난 회차 검색의 주기 조회를 바꿔요

- 상태: 대기
- 출처: [구조 가볍게 하기 명세의 화면 알림](lighter-structure.md#화면-알림)
- 막는 티켓: [0147](0147-commands-start-at-once.md)(명령 바로 실행)

## 작업

화면은 서버 상태를 18곳에서 주기적으로 다시 읽어요. 이 티켓은 무엇이 바뀌었는지 알리는 SSE 경로 하나와 화면 쪽의 연결을 만들고, 그 위로 명세 표의 처음 7곳을 옮겨요. 명령의 상태를 읽던 6곳과 지난 회차 검색의 진행이에요. 나머지 11곳은 [0155](0155-events-for-jobs-todos-candidates.md)와 [0156](0156-events-for-covers-schedule-status.md)이 같은 길로 옮겨요.

명령의 상태는 [0147](0147-commands-start-at-once.md)이 만든 실행 경로에서 바뀌므로 그 뒤에 해요. 지난 회차 검색은 명령이 아니라 API가 직접 돌리는 검색이에요.

명세를 쓰며 정한 것은 다음과 같아요.

- 이벤트는 바뀐 것의 종류와 ID만 담고, 화면은 지금의 조회 경로로 다시 읽어요. 데이터의 출처가 조회 경로 하나로 남고, 이벤트용으로 같은 데이터의 타입을 따로 두지 않아도 돼서예요.
- 숨겨진 탭은 연결을 닫아요. HTTP/1.1에서 브라우저는 서버 하나에 연결을 6개쯤만 열어서, 숨은 탭이 연결을 쥐고 있으면 다른 탭의 API 요청이 막힐 수 있어서예요.

이 티켓에서 정하는 것은 기능 크레이트 안에서 생기는 바뀜을 이벤트로 내보내는 방법이에요. 0155와 0156이 같은 방법을 써요.

## 완료 기준

- [ ] 서버는 SSE 경로 하나로 무엇이 바뀌었는지 보내요. 이벤트는 바뀐 것의 종류와 ID만 담아요. API 테스트가 경로, 응답 형식, 이벤트 모양을 확인해요.
- [ ] 다음 7곳은 주기 조회를 하지 않고, 이벤트를 받을 때 지금의 조회 경로로 다시 읽어요.
  - 구독 추가와 지난 회차 검색의 받기 행: 그 한 번 받기·지난 회차 받기 명령의 상태
  - 수집 기록의 다시 받기: 그 한 번 받기 명령의 상태
  - 규칙의 폴더 이동: 그 규칙 보관 명령의 상태
  - 일괄 보관: 그 규칙 보관 명령들의 상태
  - 감시 폴더 다시 읽기: 그 감시 폴더 다시 읽기 명령의 상태
  - 회차 되돌리기: 그 회차 되돌리기 명령의 상태
  - 지난 회차 검색의 진행: 그 검색의 단계
- [ ] 명령이 접수·실행·끝남·실패로 바뀔 때와 지난 회차 검색의 단계가 바뀔 때 서버가 이벤트를 보내는 것을 `trss` 크레이트의 프로세스 테스트가 확인해요.
- [ ] 브라우저 탭 하나는 연결을 하나만 열어요. 탭이 숨겨지면 연결을 닫고, 다시 보이면 연결한 뒤 보이는 것을 한 번 다시 읽어요.
- [ ] 연결이 끊겼다 다시 이어지거나, 서버가 이벤트를 다 보내지 못했다고 알리면, 화면은 보이는 것을 모두 다시 읽어요. 서버가 이벤트를 다 보내지 못한 경우를 테스트가 만들어 확인해요.
- [ ] 이벤트 경로는 다른 API와 같은 접근 경계 안에 있어요. 경계 밖의 요청을 거절하는 것을 API 테스트가 확인해요. 원격 인증 화면의 WebSocket은 그대로예요.
- [ ] 개발 환경의 Vite 프록시를 거쳐도 이벤트가 쌓이지 않고 바로 화면에 닿아요. 개발 환경에서 명령 하나를 실행해 확인하고 결과에 적어요.
- [ ] 연결과 다시 읽기를 맡는 화면 코드는 테스트가 있고, 화면 테스트와 `npm run typecheck`가 통과해요.
