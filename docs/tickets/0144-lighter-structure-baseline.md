# 0144 구조를 바꾸기 전의 테스트·빌드 시간과 인계 코드 줄 수를 측정해요

- 상태: 완료 (2026-10-21, 아래 "결과")
- 출처: [구조 가볍게 하기 명세의 다시 측정과 기능 크레이트 결정](lighter-structure.md#다시-측정과-기능-크레이트-결정)
- 막는 티켓: 없음

## 작업

이 변경이 테스트에 드는 계산 자원과 인계 코드를 얼마나 줄였는지 견주려면, 바꾸기 전의 값을 마지막에 다시 측정할 때와 같은 방법으로 남겨야 해요. 이 티켓이 명세의 첫 티켓이므로, 이 티켓을 시작하는 커밋이 기준이에요. 코드를 바꾸는 티켓은 모두 이 티켓 뒤에 시작하고, [0161](0161-remeasure-and-crate-decision.md)이 같은 방법으로 다시 측정해요.

명세의 목표와 범위에 있는 값은 2026-10-21 `5cdae9e`에서 측정했어요. 그 뒤로는 문서 커밋만 있었지만, 줄 수를 센 명령은 스크립트로 남지 않았고 크레이트별 빌드 시간은 표로 남지 않았어요. 그래서 이 티켓의 커밋에서 다시 측정하고, 다시 쓸 수 있는 스크립트로 남겨요.

측정하는 값은 다음과 같아요.

- `cargo test --workspace -j 4`를 빌드한 뒤 두 번 다시 실행했을 때, 테스트 바이너리마다의 시간과 그 합, 통과·건너뛴 테스트 수. `dev/measure/test-times.py`로 로그에서 읽어요.
- `trss-core`의 파일 하나를 건드린 뒤 `cargo test --workspace --no-run -j 4 --timings`의 wall time과, 빌드 단위마다의 시간.
- 인계 코드의 줄 수. 2026-10-21에 센 방법은 `.rs` 파일의 모든 줄을 세는 것이었고, 대상은 `trss-core`의 `commands/`, `queue.rs`, `wake.rs`, `heartbeat.rs`, `lock.rs`, `folder_locks.rs`와 `trss-worker` 크레이트 전체였어요. 이번에는 `trss-web` 크레이트도 세고, 크레이트는 `src`와 `tests`를 나눠 세요. 합친 뒤에는 두 크레이트 대신 `trss` 크레이트를 세어 견줘요.

## 완료 기준

- [x] 측정한 커밋과 날짜, 빌드 상태(빌드 뒤 다시 실행, `-j 4`, glibc), 값이 이 티켓의 결과와 [명세의 결과](lighter-structure.md#결과)에 있어요.
- [x] 측정하는 동안 다른 빌드나 테스트가 기계를 함께 쓰지 않았는지 확인해 결과에 적어요.
- [x] 인계 코드의 줄 수를 세는 스크립트가 `dev/measure/`에 있고, 합친 뒤의 `trss` 크레이트도 같은 스크립트로 셀 수 있어요.
- [x] 원본 로그와 `--timings` 결과는 `dev/local/measure/0144/`에 있어요.

## 결과

2026-10-21에 `d8432c8a`를 개발 PC(Ryzen 5 5600X, 12 스레드, RAM 32 GB, glibc, rustc 1.99.1)에서 측정했어요. 명령은 모두 `-j 4`이고, 테스트 시간은 빌드 뒤 다시 실행한 값이에요. 바이너리마다와 크레이트마다의 값, 측정 방법은 [명세의 기준값](lighter-structure.md#기준값)에 있어요. 원본 로그와 `--timings` 결과는 이 PC의 `dev/local/measure/0144/`에 있어요.

| 값 | 측정값 |
| --- | ---: |
| 테스트 바이너리 31개의 `finished in` 합, 두 번 | 43.0초, 43.0초 |
| 통과·실패·무시 | 3,086·0·14 |
| `trss-core`를 고친 뒤의 빌드, 증분 캐시를 다시 쓴 warm | 13.7초 |
| `trss-core`를 고친 뒤의 빌드, 증분 컴파일을 끈 cold | 81.2초 |
| 인계 코드, `trss-core`의 여섯 곳 | 3,873줄 |
| 인계 코드, `trss-web` 크레이트 | 47,827줄 |
| 인계 코드, `trss-worker` 크레이트 | 10,503줄 |

작업에는 `trss-core`의 파일을 건드린 뒤 빌드한다고 적었지만, 건드리기만 하면 빌드가 2.3초였어요. rustc가 `~/.cargo/config.toml`의 `rustc-wrapper`인 kache를 거치는데, kache는 내용이 같은 파일의 컴파일 결과를 캐시에서 돌려줘요. 그래서 `crates/trss-core/src/lib.rs`에 값이 매번 다른 공개 상수를 더해 내용을 바꿨어요.

내용을 바꾼 빌드는 처음에 99.2초, 바로 다음에 11.9초가 걸렸어요. 증분 캐시를 얼마나 다시 쓰는지에 따라 시간이 크게 달라져서, warm과 cold를 따로 측정하는 `dev/measure/core-edit-build.sh`를 만들었어요. [0161](0161-remeasure-and-crate-decision.md)은 warm은 warm끼리, cold는 cold끼리 견줘요. 스크립트는 측정한 뒤 `lib.rs`를 원래대로 돌려놓고 한 번 더 빌드해요. 마지막에 만든 `trss-core`의 rmeta에 더한 상수가 없는 것을 확인했어요.

명세의 목표와 범위에 있던 `5cdae9e`의 94초 빌드는 `trss-core`만 고친 빌드가 아니었어요. 단위 67개를 빌드했는데, 외부 크레이트의 단위 18개와 `trss-core`에 기대지 않는 단위 6개가 들어 있었어요. 그래서 그 값을 견주는 데 쓰지 않고, 명세와 [티켓 목록](README.md#구조-가볍게-하기)의 그 문장을 이 결과에 맞게 고쳤어요.

측정마다 시작하기 전에 `pgrep`으로 다른 cargo나 rustc 프로세스가 없는 것을 확인했어요. rust-analyzer의 flycheck가 결과를 마지막으로 쓴 시각은 측정을 시작하기 전인 04:18이에요.

인계 코드의 줄 수는 `dev/measure/handoff-lines.sh`로 셌어요. `5cdae9e`에서 센 3,873줄과 `trss-worker`의 10,503줄(테스트 7,059줄)이 그대로 나왔어요. 스크립트는 `trss` 크레이트가 있으면 같은 방법으로 세요. 크레이트를 합친 모양의 임시 커밋에서 세어 확인하고, 그 커밋은 지웠어요.

musl 대상과, 빈 `target/`에서 처음부터 하는 빌드는 측정하지 않았어요. 명세가 견주는 값이 아니어서예요.
