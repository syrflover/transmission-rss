# 0005 기존 YAML을 채널 단위로 가져와요

- 상태: 완료
- 출처: [가져오기](../specs/settings.md#가져오기), [기존 YAML](../specs/settings.md#기존-yaml), [설정 화면](../specs/settings.md#설정-화면)
- 막는 티켓: [0002](0002-app-state-db.md), [0003](0003-web-shell.md)

## 작업

설정 화면의 `데이터` 묶음에 가져오기를 두고, transmission-rss의 기존 YAML을 `파일 선택` → `검토` → `결과` 단계로 앱 DB에 가져와요.
기존 채널 설정을 앱으로 옮기는 첫 경로라, 0009의 배포 전환이 이 티켓에 기대요.

- 설정 화면은 [목록·상세형](../specs/settings.md#설정-화면)의 틀을 세우고, 이 티켓에서는 `데이터`의 가져오기만 채워요.
  다른 항목은 해당 결과 목표에서 채워요.
- 채널 순서와 채널 안 규칙 순서를 파일 그대로 보존하고, `excludes`·`match`·`regex`·`case_insensitive`·`directory`·`episode`의 의미와 생략된 기본값을 지금처럼 읽어요.
- 이미 있는 채널은 `교체`·`추가`·`건너뛰기`를 채널마다 고르며, 처음에는 아무것도 고르지 않은 상태이고 모두 고르기 전에는 `가져오기`가 비활성이에요.
  `교체`를 고르면 없어질 규칙 이름을 검토 단계에 보여줘요.
- 지금 채널이 하나도 없으면 묻지 않고 모두 추가해요.
- 가져온 채널의 URL 쿼리 값은 모두 비밀로 표시해요.
- 규칙 주석에서 만드는 구독 제안은 결과 목표 2(방영작 구독)에서 이 검토 단계에 더해요.
  이 티켓의 검토 단계는 규칙 목록과 평가 순서까지 보여줘요.
- 가져오기는 다운로드·파일 변경을 실행하지 않아요.
- 0002의 `replace_channel`은 채널의 규칙 목록을 통째로 바꾸며 규칙 ID를 모두 새로 발급해요.
  `교체`에서 파일과 겹치는 규칙의 ID를 유지할지(이후 구독·수집 이력이 규칙 ID를 가리킴) 이 티켓에서 정하고 테스트로 고정해요.

## 완료 기준

| 입력·상태 | 기대 결과 |
| --- | --- |
| 채널이 없는 앱에 기존 YAML(채널 2, 규칙 N) | 선택을 묻지 않고 모두 추가돼요. 순서와 모든 규칙 값이 파일과 같고, 쿼리 값은 모두 비밀이에요. |
| 지금 채널 A에 규칙 5개, 파일의 A에 규칙 3개(겹치는 것 2개)를 `교체` | 검토에 없어질 규칙 3개의 이름이 보이고, 결과에 없앤 규칙 3개가 따로 적혀요. A의 규칙이 파일과 같아져요. |
| 같은 파일로 `추가` | 새 ID의 채널·규칙이 더해지고 기존 A는 그대로예요. |
| 이미 있는 채널 두 개 중 하나만 고름 | `가져오기`가 비활성이고, 남은 채널 수를 문장으로 알려요. |
| YAML이 아닌 파일이나 필수 필드가 빠진 파일 | 파일 선택 단계에서 까닭을 실패로 보여주고 아무것도 바꾸지 않아요. |
| `episode: -24`, `regex: true`인 규칙 | 값이 보존돼 0001의 판정과 0004의 이름 변경에 그대로 쓰여요. |
| 가져오기 적용 도중 DB 오류를 일으킴 | 일부 채널만 바뀌지 않고 적용 전 상태가 남아요. |

- 결과 단계가 가져오기로 다운로드·적용·파일 정리를 하지 않는다고 문장으로 알려요.

## 결과

설정 화면의 목록·상세 틀과 `데이터 > 가져오기`(기존 YAML)를 만들었어요. 다른 설정 항목은 왜 비었는지 알리는 빈 화면이에요.
가져오기는 채널과 규칙만 DB에 쓰고, 다운로드·자막 적용·파일 정리는 하지 않아요. 결과 단계가 이를 문장으로 알려요.

### 구현한 것

- 파일을 읽는 `crates/trss-import/src/legacy.rs`는 옛 실행 파일과 같은 `ChannelConfig` 역직렬화를 그대로 써서 생략된 기본값(`episode`는 1)을 예전처럼 읽어요.
  YAML이 아니거나 필수 필드(`url`·`directory`·`rules`, 규칙의 `match`·`directory`)가 없거나 값 형식이 틀리면 어디가 왜 틀렸는지 한국어 문장으로 알리고, 그 문장에는 파일 내용(토큰)을 되풀이하지 않아요.
  `http`·`https`가 아닌 주소, 빈 채널 `directory`, 절대 경로 규칙 `directory`도 이 단계에서 거부해요.
- 적용은 `ChannelStore::import_channels`(`crates/trss-collect/src/store/channels/import.rs`)가 한 트랜잭션으로 해요. 채널 여러 개를 추가·교체하다 하나라도 실패하면 적용 전 상태가 그대로 남아요.
- API는 두 단계이고 서버가 미리보기를 들고 있지 않아요.
  - `POST /api/import/legacy/preview` `{ content }`는 파일을 읽고 지금 채널과 견줘 검토 자료를 돌려줘요. 아무것도 바꾸지 않아요.
  - `POST /api/import/legacy/apply` `{ content, choices: [{ index, existing_id, existing_version, decision }] }`는 파일을 다시 읽고 지금 상태로 다시 견줘 적용해요.
  - 파일 원문은 브라우저에서 서버로만 가요. 응답의 주소는 모두 쿼리 값(과 사용자 정보)을 가린 형태이고, 화면이 돌려받은 가려진 값으로는 적용할 수 없어요.
  - 선택이 지금 충돌하는 채널과 정확히 맞지 않으면(빠짐·넘침·다른 채널·교체 때 버전 불일치) `409 conflict`로 아무것도 적용하지 않고, 화면은 `다시 검토`를 보여줘요. 채널이 이미 있는데 선택이 없는 요청도 같은 처리예요.
- 화면은 `파일 선택` → `검토` → `결과`이고, 이미 있는 채널의 `교체`·`추가`·`건너뛰기`는 처음에 아무것도 고르지 않은 상태예요.
  모두 고르기 전에는 `가져오기`가 비활성이고 남은 채널 수를 문장으로 알려요. `교체`를 고르면 없어질 규칙 이름을 바로 보여줘요.

### 정한 것

- **이미 있는 채널**: 스킴·호스트·포트·경로와 쿼리 이름의 집합이 같으면 같은 채널이에요. 쿼리 값은 비밀이라 비교하지 않아서, 토큰을 바꿔도 같은 채널로 봐요.
  여럿이 해당하면 주소 전체가 같은 채널을 먼저 짝지어요. 지금 채널 하나는 파일의 채널 하나에만 짝지어지고(파일 순서대로), 남는 파일 채널은 새 채널로 보고 묻지 않고 추가해요. 그래서 한 채널을 두 번 교체하는 일이 없어요.
- **`교체`의 규칙 ID**: 같은 채널 안에서 일치 문구·`regex`·`case_insensitive`가 모두 같으면 지금 규칙의 ID를 유지해요(`store::channels::import::match_rules`).
  유지한 규칙은 저장 폴더·회차 변환·상태를 파일 값으로 바꾸고 버전을 올려요. 나머지 지금 규칙은 삭제하고, 파일에만 있는 규칙은 새 ID를 받아요.
  같은 키가 여럿이면 순서대로 하나씩 짝지어요. 일치 문구가 없는 규칙(제목 대기)은 비교할 정체가 없어서 짝지어지지 않아요.
  이후 구독·수집 이력이 가리키는 ID가 살아남도록 `replace_channel`(모든 ID 재발급)을 쓰지 않았어요.
- **`match: ""`**: 파일 선택 단계에서 몇 번째 채널의 몇 번째 규칙인지와 까닭을 알리고 거부해요(사용자 결정).
  예전 실행 파일에서는 빈 문구가 모든 제목에 맞지만, 앱에는 모든 항목에 맞는 규칙이 없고 빈 문구는 `제목 대기`라서, 어느 쪽으로 읽어도 파일의 뜻이 바뀌기 때문이에요.
  처음 구현은 제목 대기로 가져왔고, 통합 뒤 거부로 바꿨어요.
- **`교체`가 남기는 것**: 파일이 표현하지 못하는 채널의 `past_search`는 지금 값을 유지해요. 검토에서 없어진다고 알린 적 없는 값을 조용히 지우지 않기 위해서예요.
  채널 순서는 교체하면 그 자리를 지키고, 추가된 채널은 기존 채널 뒤에 파일 순서대로 붙어요.
- 컴파일되지 않는 정규식은 [0001](0001-rule-evaluation.md)처럼 규칙을 그대로 가져오되, 검토에 `정규식을 읽을 수 없음`과 어떤 제목에도 맞지 않는다는 문장을 보여줘요.

브라우저 검사는 다음을 관찰했어요: 목록·상세(PC는 나란히, 휴대폰은 목록과 항목이 따로), 각 단계(파일 선택·거부 사유·검토·결과)의 가로 넘침 없음, YAML이 아닌 파일과 필수 필드 없는 파일의 사유 표시와 DB 무변경, 채널이 없을 때 선택 없이 추가, 두 채널 중 하나만 골랐을 때 `가져오기` 비활성과 남은 채널 수 문장(2개→1개), `교체` 선택 때 없어질 규칙 이름 표시, 결과의 `없앤 규칙` 별도 목록, `건너뛰기`만 고르면 DB가 그대로임.
적용 뒤 DB를 직접 읽어 값을 확인했어요: `episode -24`·`regex`·`case_insensitive` 보존, `match ''`가 `NULL`, 겹치는 규칙 두 개의 ID 유지, `추가`가 새 ID의 복사본을 만듦, 모든 쿼리 이름이 `secret_query`에 있음.

### 확인하지 못한 것

- 실제 사용자 채널 YAML은 쓰지 않았어요. 표본은 가짜 토큰을 쓴 같은 구조의 파일이에요.
- 실제 휴대폰의 터치·가상 키보드·안전 영역, Chromium 밖의 브라우저, 스크린 리더는 확인하지 않았어요.
- 텍스트 대비는 토큰 값으로 고른 색을 눈으로 본 정도이고, 실제 렌더링 배경 위 값을 재지 않았어요.
- 웹과 worker가 서로 다른 프로세스로 동시에 쓰는 경우는 확인하지 않았어요. 미리보기와 적용 사이에 채널이 바뀌면 버전과 충돌 검사가 막지만, 그 사이에 같은 주소의 새 채널이 생기는 경우는 막지 못해요(추가한 채널이 겹칠 뿐 데이터는 잃지 않아요).
- 앱 YAML 가져오기와 규칙 주석의 구독 제안은 이 티켓 범위 밖이라 없어요. 파일 선택 단계가 앱 YAML은 아직 열리지 않았다고 알려요.

### 남은 것

- `crates/trss-collect/src/store/channels/mod.rs`에 `pub mod import;`와 `#[cfg(test)] mod import_tests;` 두 줄을 더했어요. 같은 파일을 고치는 [0007](0007-channels-tab-secrets.md)과 합칠 때 이 줄 근처에서 충돌할 수 있어요.
- `import.rs`는 `repo.rs`의 비공개 SQL 도우미를 쓸 수 없어서 채널·규칙 INSERT 문을 따로 갖고 있어요. 뒤에 `repo.rs`를 다듬을 때 합치면 좋아요.
- 사용자 정보(`https://user:pass@host/...`)가 든 주소는 이 티켓의 표시 함수(`display_url`)만 가려요. 0002의 `mask_url`과 `Channel::masked_url`은 쿼리 값만 가려서, 뒤 티켓의 채널 화면이 그 값을 쓰면 사용자 정보가 보일 수 있어요.
- 요청 본문은 axum 기본 한도(2MB)이고 화면도 같은 한도로 먼저 알려요.
- 가져오기로 채널이 생겨도 worker 전환([0004](0004-worker-collection-history.md), [0009](0009-deploy-web-worker.md)) 전에는 수집이 이 채널을 쓰지 않아요.
