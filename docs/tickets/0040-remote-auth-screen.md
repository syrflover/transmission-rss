# 0040 작업 상세에서 원격 화면으로 인증해요

- 상태: 완료 (2026-10-04, 사용자가 실제 휴대폰의 원격 화면에서 실제 erulabo 확인을 풀고 서버 브라우저가 받았어요. 아래 "결과")
- 출처: [작업 화면 안의 인증과 브라우저 수명](../specs/jobs.md#작업-화면-안의-인증과-브라우저-수명), [작업 상세](../specs/jobs.md#작업-상세), [접근 경계와 기기](../specs/web-app.md#접근-경계와-기기)
- 막는 티켓: [0039](0039-browser-container-lifecycle.md), [0053](0053-browser-egress-and-web-origin.md)

## 작업

작업 상세의 인증 상태에 서버 브라우저의 원격 화면·마우스·키보드 입력을 붙여요. 방식은 0032에서 정한 CDP 화면 전송과 입력 전달이고, 웹이 중계해요.

- 웹이 서버 브라우저에 닿는 길(사용자 결정, 2026-10-03): trss-web도 `browser_net`에 넣고, 웹은 `browser_net` 쪽(브라우저 컨테이너)에서 들어온 연결을 모두 거절해요. 브라우저가 여는 외부 페이지가 로그인 없는 웹 API에 닿지 못하게 하려는 것이고, 이 거절은 시험으로 지켜요. 브라우저가 호스트 LAN 주소로 게시된 웹 포트에 오는 연결은 받는 쪽에서 `trss_net` 게이트웨이 주소로 보여 이 거절로 가려낼 수 없어서(2026-10-03 관찰), 그 경로는 0053이 브라우저의 송신 제한과 웹의 Host·Origin 검사로 막아요. worker가 중계하는 길은 worker에 HTTP 서버와 두 번의 프레임 중계가 생겨서 고르지 않았어요.
- 화면·입력 연결은 웹을 거치며, 원격 화면 페이지와 같은 접근 보호를 받아요. 외부 페이지에서 보낸 연결이나 다른 작업·끝난 실행으로의 연결은 거부해요.
- 화면을 연 기기가 보고하는 크기·기기 픽셀 비율·터치 여부를 기기 지표 흉내로 원격 페이지에 맞추고(렌더링은 1배), 기기를 바꿔 열면 마지막으로 연 기기를 따라 다시 맞춰요. 맞추는 동안과 이전 크기의 프레임을 보고 만든 입력은 버려요. 휴대폰에서는 단계를 한 줄로 접어 사람 확인 상자가 첫 화면에 보이게 해요.
- 원격 화면 옆에 원격 페이지 `새로고침`을 둬요.
- 연결이 끊기면 같은 작업의 유효한 실행에 다시 붙고, 유휴 종료된 실행을 재연결 시도만으로 다시 띄우지 않아요. 사용자가 작업을 다시 열면 페이지와 인증 화면을 다시 준비해요.
- 할 일의 `인증 필요` 카드와 작품 상세의 인증 카드가 이 화면으로 이어져요.

## 완료 기준

| 입력·상태 | 기대 결과 |
| --- | --- |
| 가짜 CAPTCHA 페이지의 인증 필요 작업을 PC에서 엶 | 원격 화면에서 클릭·입력이 서버 브라우저에 전달되고, 통과하면 작업이 `받기`로 넘어가요. |
| 실제 휴대폰에서 같은 작업을 엶 | 한 줄로 접힌 단계 아래 원격 화면의 사람 확인 상자가 첫 화면 안에 보여요. |
| 유휴 종료된 인증 필요 작업을 엶 | 단계는 `인증`에 머물고 브라우저와 인증 화면이 다시 준비돼요. 받은 파일과 기록은 그대로예요. |
| 화면을 열어 둔 채 입력 없이 유휴 시간이 지남 | 브라우저가 닫히고, 화면은 다시 열면 준비된다고 알려요. 연결 재시도가 브라우저를 계속 띄우지 않아요. |
| 다른 출처(Origin)의 페이지에서 원격 입력 연결 시도, 끝난 실행의 연결로 입력 | 모두 거부돼요. |
| 웹만 재시작 | 같은 작업의 유효한 원격 화면에 다시 연결되고 브라우저가 새로 뜨지 않아요. |
| 실제 erulabo 게시물, 768MiB 한도의 제품 이미지(`Dockerfile.browser`) | 사람이 이 원격 화면으로 직접 인증을 통과하고 서버 브라우저가 파일을 받아요. 메모리 한도 초과 종료가 없어요. 0032의 장치와 다른 제품 이미지에서도 인증이 되는지 보는 확인이에요(0039에서 옮김, 사용자 결정 2026-10-03). |

## 결과

### 만든 것 (2026-10-03)

- **웹과 worker의 연결**: 마이그레이션 45(`subtitle_job_screens`)가 작업마다 묶인 실행, 웹의 준비 요청, 마지막 원격 입력 시각을 담아요. 토큰·쿠키·주소는 담지 않아요. worker만 실행을 시작·종료하고, 웹은 실행기의 토큰 보호 CDP 중계로 묶인 실행에만 닿아요([ADR 0013](../adr/0013-web-on-browser-network.md)).
- **준비와 유휴**: 작업 상세를 열 때 한 번 보내는 `POST`만 준비를 요청하고, 상태 조회와 재연결은 브라우저를 띄우지도 사용으로 치지도 않아요. 원격 입력만 사용으로 쳐요(10초에 한 번까지 기록).
- **원격 화면 연결**: 작업과 묶인 실행·페이지에 걸린 WebSocket 하나로 화면 프레임과 입력을 주고받아요. 끝난 실행이나 다른 페이지로 바뀐 연결은 끝나요. 크기를 바꿀 때마다 세대를 올리고, 옛 세대 프레임에서 만든 입력과 바꾸는 동안의 입력은 버려요. 바꾸기 직전에 눌린 버튼과 손가락은 원격에서 떼요. 마지막으로 연 기기의 크기를 따르고, 한 묶음에 화면은 4개까지이며 넘으면 가장 오래된 화면이 닫혀요. 응답 없는 연결은 핑으로 걸러요.
- **웹의 browser_net 거절**: 웹은 `browser_net`에서 온 연결을 HTTP를 읽기 전에 끊어요. 게시 포트의 연결이 `browser_net`으로 들어오는 배치(`gw_priority` 없음)면 시작하지 않아요.
- **가짜 사람 확인과 출처의 자리**: 개발용 가짜 출처의 `/check/<이름>` 게시물은 네트워크 없이 브라우저 안에서 답하고, 사람의 클릭만 SRT를 받게 해요. 실제 출처(0041)가 끼울 자리는 `AuthPage`예요.
- **웹 화면**: 작업 상세의 `인증` 구역에 원격 화면, `새로고침`, 휴대폰의 `키보드`, 닫혔을 때의 `다시 열기`를 뒀어요. 휴대폰에서는 단계를 한 줄로 접고 머리를 줄여요.
- 프로토콜과 규칙 전체는 [작업 화면 안의 인증과 브라우저 수명](../specs/jobs.md#작업-화면-안의-인증과-브라우저-수명)에 있어요.

### 검증한 것

개발 환경(서버 데이터 복사본, `dev/compose.sh`, 2026-10-03)에서 앱 안 브라우저로 확인했어요.

| 완료 기준 | 결과 |
| --- | --- |
| 가짜 CAPTCHA 작업을 PC에서 엶 | 됐어요. 작품 상세에서 가짜 확인 후보(16화)를 골라 받자 작업이 `인증 필요`가 됐어요. 작업 상세의 원격 화면에서 상자를 누르자 `받기`를 거쳐 `받음`이 되고 `dev-check16.srt`(870바이트, SRT)를 받았어요. |
| 실제 휴대폰에서 엶 | 됐어요(2026-10-04 12:11 KST, 개발 환경, `34f6642`에서 지은 이미지). 사용자가 실제 휴대폰으로 실제 erulabo [859](https://erulabo.com/859)(1화) 후보의 인증 작업 화면을 열자, 사람 확인 상자가 스크롤 없이 첫 화면 안에 보였어요(사용자 확인). 사용자가 그 화면을 터치해 Turnstile을 풀었고, 서버 브라우저가 `drive.usercontent.google.com`에서 ZIP(13,673바이트)을 받아 작업이 끝났어요. 앞서 2026-10-03에는 앱 안 브라우저의 390×844 흉내에서 단계가 한 줄로 접히고 상자가 첫 화면 안(y≈620)에 보였어요. 같은 날 직접 찾기 작업으로 휴대폰에서 연 erulabo 게시물은 상자를 보려면 스크롤해야 했어요. 직접 찾기는 서버가 페이지를 건드리지 않는 경로라서, 이 기준의 대상이 아니에요. |
| 유휴 종료된 작업을 엶 | 됐어요. 닫힌 뒤 페이지를 다시 열자 worker가 확인 화면을 다시 준비했고, 상자를 눌러 받았어요. 다시 연 뒤 첫 프레임까지 8초 넘게 걸렸어요. |
| 화면을 연 채 입력 없이 유휴 시간이 지남 | 됐어요. 300초 뒤 실행이 닫히고 화면은 "서버 브라우저가 쉬는 동안 닫혔어요. 작업 화면을 다시 열면 다시 준비해요"와 `다시 열기`를 보였어요. 그 뒤 30초 넘게 새 실행이 뜨지 않았어요. |
| 다른 Origin의 연결, 끝난 실행의 연결 | 단위 시험(다른 Origin·Host, 묶이지 않은 실행, 바뀐 페이지)과 개발 환경 확인: 다른 Origin의 WebSocket은 `403`이었어요. `browser_net`에 붙인 컨테이너에서 웹의 `browser_net` 주소로 연결하면 바로 끊겼어요. |
| 웹만 재시작 | 됐어요. 확인 화면을 연 채 `trss-web`만 재시작하자 묶인 실행이 그대로였고 새 브라우저가 뜨지 않았어요. 화면이 다시 붙어 상자를 누르자 받았어요. |
| 실제 erulabo, 제품 이미지 | 됐어요(2026-10-03 23:50 KST, 개발 환경, `Dockerfile.browser`로 지은 `trss-browser:local`, 768MiB 한도). 사용자가 PC 웹 화면의 원격 화면에서 [859](https://erulabo.com/859)(1화)의 Turnstile을 직접 풀었고, 서버 브라우저가 ZIP을 받아 작업이 끝났어요([0041 결과](0041-source-erulabo.md#결과)). 컨테이너의 메모리 최대치는 약 591MiB였고 `oom_kill`은 0, 재시작은 0이었어요. |

실제 브라우저 이미지 시험 두 개(`remote_screen_docker`, `auth_sample`, 0053을 합친 이미지)가 통과했어요. 앞의 시험은 휴대폰 크기 프레임을 받고, 옛 세대의 탭은 버려지며, 원격 화면을 거친 탭으로 작업이 `인증` → `받기` → 완료가 되는지 봐요. 뒤의 시험은 스크립트 클릭으로는 받지 않고 사람의 클릭만 받는지 봐요.

위 개발 환경 확인은 리뷰의 마지막 수정(핑, 화면 자리, 입력 잠금) 전 코드에서 했어요. 최종 코드로 다시 만든 개발 환경에서는 PC의 가짜 확인 한 번만 다시 확인했고(받음), 핑이 오가는 동안 화면이 유지되는지는 단위 시험으로만 확인했어요. 최종 코드(2026-10-03)에서 `cargo fmt --check`, `cargo clippy --workspace --all-targets -D warnings`(경고 0), `cargo test --workspace`(2,136개 통과, 실패 0, 무시 4), 웹 `tsc`와 단위 시험(70개 통과)이 통과했어요.

### 독립 리뷰

신뢰 경계(실행·페이지 묶음, Origin, `browser_net` 거절), 수명(준비·유휴·도착·재시작), 저장 데이터, 자원 한도를 두고 리뷰를 받았어요. 고친 뒤 다시 확인한 결과 '맞음'이었어요.

| 지적 | 처리 |
| --- | --- |
| DNS 재바인딩이면 Origin==Host 검사가 통과하고, 준비 `POST`에는 Origin 검사가 없음 | 0053의 웹 전체 Host·Origin 검사 아래로 옮기고 화면 자체의 검사는 뺐어요 |
| `gw_priority`가 없으면 모든 사용자를 조용히 거절 | 시작하지 않아요 |
| 같은 실행의 두 번째 확인을 실행이 바뀐 것으로 봄 | 묶음을 (실행, 페이지, 묶은 시각)으로 보고, 화면이 새 묶음에 다시 붙어요 |
| 준비 응답과 유휴 종료의 경합 | 유휴 종료와 같은 잠금 안에서 사용으로 쳐요 |
| 늦게 온 파일을 지움 | 회차가 아직 기다리면 남겨요 |
| 확인용 임시 폴더가 남음 | 회차가 끝나면 지우고, 정리(sweep)가 오래된 것을 지워요 |
| 멈춘 클라이언트, 화면 수 상한 없음 | 보내기 시간 한도와 4개 상한(넘으면 가장 오래된 화면을 닫음), 핑 |
| 거절 로그 폭주 | 1분에 한 줄 |
| 크기를 바꾼 뒤 옛 프레임이 새 세대로 찍힘, 눌린 버튼이 남음 | 순서 장벽으로 옛 프레임을 버리고, 눌린 입력을 원격에서 떼요 |
| worker 종료 때 잘못된 안내 | 다음 시작이 재시작 안내를 남겨요 |

### 한계

- 실제 휴대폰에서는 터치로 상자를 풀어 받는 것까지 확인했어요(2026-10-04). 가상 키보드와 한글 입력은 실제 휴대폰에서 확인하지 않았어요.
- HTTPS 앞단 프록시 뒤의 WSS는 확인하지 않았어요.
- Docker Engine 28·Compose 2.33보다 오래된 환경은 `gw_priority`를 몰라 웹이 시작하지 않아요. Engine 29.8.2에서만 확인했어요.
- 프레임은 JPEG 이미지로 그리며 부드러움은 재지 않았어요. 다시 연 뒤 첫 프레임이 늦게 오는 원인은 확인하지 않았어요.
