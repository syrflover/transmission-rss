# 실행 계획과 티켓

웹 재설계 명세([웹 앱 공통 명세](../specs/web-app.md)와 주제별 명세)를 구현하는 순서와, 지금 실행할 티켓을 담아요.
전체 범위는 [구현 순서](../specs/web-app.md#구현-순서)의 다섯 결과 목표로 나누고, 실행 가능한 티켓은 지금 시작할 결과 목표만 자세히 적어요.
뒤 목표는 앞 목표에서 정한 DB 구조와 웹 명령 계약에 따라 모양이 달라지므로, 그 앞 목표가 끝나 갈 때 티켓으로 나눠요.
티켓이 없는 목표도 범위에서 빠진 것이 아니며, 티켓을 닫았다고 결과 목표나 명세의 완료 조건이 확인된 것은 아니에요.

## 티켓 문서의 관례

- 티켓 하나가 파일 하나이고, 이름은 `0001-짧은-영문-이름.md`처럼 번호와 이름이에요.
- 맨 위에 `상태`(`대기`·`진행 중`·`완료`·`보류`), 출처 명세, 막는 티켓을 적어요.
  막는 티켓이 없으면 바로 시작할 수 있어요.
- 본문은 `작업`과 `완료 기준`이에요.
  완료한 티켓에는 `결과` 절을 더해 검증한 것·검증하지 못한 것·남은 일을 적고, 그 뒤에 내용을 나중 작업으로 고쳐 쓰지 않아요.
- 구현 중에 명세와 어긋나는 것을 발견하면 티켓이 아니라 명세의 요구를 기준으로 삼고, 사용자 결정이 필요한 차이는 티켓에 적어 결정을 받아요.
- 한 결과 목표의 마지막 티켓이 끝나면 그 목표의 완료 조건과 관련 명세를 티켓 결과와 맞춰 보고, 충족한 것과 남은 것을 이 문서의 목표 절에 적어요.
  그 변경에서 목표의 티켓을 `docs/archive/tickets/<목표 번호>-<짧은-영문-이름>/`(예: `1-app-owned-collection`)으로 함께 옮기고, 목표 절에는 요약·완료 기록과 보관 위치 링크만 남겨요.
  같은 목표의 티켓끼리는 파일 이름으로 가리키므로 그대로 두고, 명세·ADR·다른 목표의 티켓에서 들어오는 링크와 보관한 티켓에서 나가는 링크는 같은 변경에서 고쳐요.
  보관한 티켓은 qmd의 `archive` 컬렉션에 들어가 기본 검색에서 빠지고, 컬렉션을 지정하면 찾을 수 있어요.

### 1. 앱 소유 설정과 수집 기반

외부 YAML과 5분 cron으로 한 번씩 돌던 수집을, 앱 DB의 채널·규칙으로 상시 실행하는 worker와 웹 화면으로 옮겨요.

### 3. 자막 후보와 수신

자막 후보를 찾고, 구독 제작자는 자동으로, 그 밖에는 사용자가 골라 받으며, 인증은 trss 안에서 끝내요.
이 목표의 수신은 받은 묶음을 앱 데이터 폴더의 수신 영역에 두는 데까지이며, 분석·보관·적용은 결과 목표 4예요. 출처별 다운로드의 "적용까지 이어지는지"의 확인은 목표 4에서 끝나요.

- [자막 후보 조회](../specs/subtitles.md#자막-후보-조회), [구독 제작자 자동 수신](../specs/subtitles.md#구독-제작자-자동-수신)과 구독 제작자 출처의 [회차 대응 자동 결정](../specs/library.md#자막의-회차-대응)
- 시즌의 [Anissia 연결](../specs/library.md#작품-연결과-제외), 작품 상세의 [자막 후보 구역](../specs/library.md#자막-후보-구역)과 [제작자 지정](../specs/library.md#머리와-시즌)
- [출처별 다운로드](../specs/subtitles.md#출처별-다운로드) 여섯 경로(공통 결과·실패 표현을 정한 뒤 병행 가능), [직접 찾기와 자막 올리기](../specs/subtitles.md#직접-찾기와-자막-올리기)
- [서버 브라우저 인증과 수명](../specs/jobs.md#작업-화면-안의-인증과-브라우저-수명), [할 일](../specs/jobs.md#할-일)과 [할 일 화면](../specs/jobs.md#할-일-화면), [작업 상세](../specs/jobs.md#작업-상세)
- [공통 정책](../specs/settings.md#공통-정책)(브라우저 유휴 시간·동시 작업 수, 자막 형식 우선순위)과 설정 화면
- 기반: [기능별 크레이트 workspace](../adr/0011-feature-crate-workspace.md), [웹 명령의 즉시 실행](../specs/web-app.md#웹-명령과-상태-갱신)

완료는 다음을 모두 관찰한 때예요: Anissia 최근 자막 목록의 변화가 30분마다 후보로 쌓이고 연결한 시즌의 후보를 작품 상세에서 골라 받을 수 있으며, 구독 제작자의 새 회차와 수정본이 선택 없이 받아지고, 여섯 경로가 각각 실제 서버의 수신 영역까지 파일을 받으며, erulabo는 실제 웹 화면에서 사람이 CAPTCHA만 풀어 받고, 직접 찾기와 올리기로 지난 회차를 들일 수 있어요.

2026-10-02의 결정이에요(사용자 결정).

- Anissia 자막 정보는 제작자마다 마지막 게시물 한 줄뿐이라, 후보는 trss가 30분마다 최근 자막 목록을 읽어 모든 작품의 변화를 쌓아 만들고, 연결 전의 지난 회차는 직접 찾기와 올리기로 받아요([ADR 0012](../adr/0012-past-subtitles-find-and-upload.md)).
- 구독 제작자의 수정본도 자동으로 받고 교체는 승인을 기다려요([ADR 0009](../adr/0009-follow-subtitle-creator.md)). Anissia 줄이 그대로인 게시물의 파일 변경 감지는 0033의 확인 뒤 정해요.
- 후보는 작품 상세에서 고르고, 구독하지 않은 작품의 Anissia 연결은 전체 목록 검색이 기본이에요(편성표에서도 골라요).
- 올리기는 자막·폰트만 받고 나머지는 빼고 알려요. 제작자 모르는 자막에는 Anissia 제작자를 붙일 수 있어요.
- 웹 명령은 접수 즉시 실행해요. 수집 주기의 잠금 밖에서 도는 실행 기반은 자막 작업에도 필요해요.
- 목표 3의 기능 작업 전에 저장소를 기능별 크레이트의 workspace로 나눠요([ADR 0011](../adr/0011-feature-crate-workspace.md)).

순서는 크레이트 이동(0029–0030)과 명령 실행 기반(0031)이 먼저이고, 그동안 확인할 일 0032·0033을 따로 진행해요.
그 뒤 연결·후보(0034–0035, 0037)와 작업 기반(0036)이 나란히 가고, 0033의 실패 분류로 공통 수신 결과(0038)를 정한 다음 출처별 경로(0041–0044)를 병행해요.
서버 브라우저는 0032 → 0039 → 0040 순서이며, erulabo(0041)와 직접 찾기(0046)가 그 위에 있어요.
일반 출처의 회차 대응 확인(`회차 확인 필요`)은 목표 4의 묶음 분석과 함께 해요.

알려진 불확실성을 먼저 확인할 일로 뺐어요: 서버 Chromium의 원격 화면 방식과 기기 폭에 맞추는 창 크기(0032), 출처별 실제 수신 경로의 재현성과 Anissia 회차 표시 `0`의 뜻(0033)이에요.

### 4. 보관·적용과 교체 승인

받은 묶음을 분석해 `.trss/`에 보관하고, 영상 옆에 적용하며, 기존 자막의 교체는 비교와 승인을 거쳐요.

- [묶음 분석](../specs/subtitles.md#자막-묶음-분석과-안전한-배치-판단), [보관본과 적용본](../specs/subtitles.md#보관본과-적용본), [폰트](../specs/subtitles.md#폰트), [영상 대기](../specs/subtitles.md#영상-대기)
- [교체 비교와 승인](../specs/subtitles.md#교체-비교와-승인), [체크포인트와 중단 복구](../specs/jobs.md#체크포인트와-중단-복구)
- 작품 상세의 자막 쪽과 [보관 파일의 정리](../specs/library.md#보관-파일의-정리), 설정의 파일 용량

알려진 불확실성: 압축 해제·자원 한도의 수치, 실제 파일시스템의 공개·동기화 동작이에요.
