# 실행 계획과 티켓

웹 재설계 명세([웹 앱 공통 명세](../specs/web-app.md)와 주제별 명세)를 구현하는 순서와, 지금 실행할 티켓을 담아요.
전체 범위는 [구현 순서](../specs/web-app.md#구현-순서)의 다섯 결과 목표로 나누고, 실행 가능한 티켓은 지금 시작할 결과 목표만 자세히 적어요.
뒤 목표는 앞 목표에서 정한 DB 구조와 웹 명령 계약에 따라 모양이 달라지므로, 그 앞 목표가 끝나 갈 때 티켓으로 나눠요.
티켓이 없는 목표도 범위에서 빠진 것이 아니며, 티켓을 닫았다고 결과 목표나 명세의 완료 조건이 확인된 것은 아니에요.

## 티켓 문서의 관례

- 티켓 하나가 파일 하나이고, 이름은 `0001-짧은-영문-이름.md`처럼 번호와 이름이에요.
- 맨 위에 `상태`(`대기`·`진행 중`·`완료`·`보류`), 출처 명세, 막는 티켓을 적어요.
  막는 티켓이 없으면 바로 시작할 수 있어요.
- 본문은 `작업`과 `완료 기준`이에요.
  완료한 티켓에는 `결과` 절을 더해 검증한 것·검증하지 못한 것·남은 일을 적고, 그 뒤에 내용을 나중 작업으로 고쳐 쓰지 않아요.
- 구현 중에 명세와 어긋나는 것을 발견하면 티켓이 아니라 명세의 요구를 기준으로 삼고, 사용자 결정이 필요한 차이는 티켓에 적어 결정을 받아요.
- 한 결과 목표의 마지막 티켓이 끝나면 그 목표의 완료 조건과 관련 명세를 티켓 결과와 맞춰 보고, 충족한 것과 남은 것을 이 문서의 목표 절에 적어요.
  그 변경에서 목표의 티켓을 `docs/archive/tickets/<목표 번호>-<짧은-영문-이름>/`(예: `1-app-owned-collection`)으로 함께 옮기고, 목표 절에는 요약·완료 기록과 보관 위치 링크만 남겨요.
  같은 목표의 티켓끼리는 파일 이름으로 가리키므로 그대로 두고, 명세·ADR·다른 목표의 티켓에서 들어오는 링크와 보관한 티켓에서 나가는 링크는 같은 변경에서 고쳐요.
  보관한 티켓은 qmd의 `archive` 컬렉션에 들어가 기본 검색에서 빠지고, 컬렉션을 지정하면 찾을 수 있어요.

## 결과 목표

### 1. 앱 소유 설정과 수집 기반

외부 YAML과 5분 cron으로 한 번씩 돌던 수집을, 앱 DB의 채널·규칙으로 상시 실행하는 worker와 웹 화면으로 옮겨요.
미리보기와 실제 처리가 같은 규칙 판정을 쓰고, 모든 RSS 항목이 수집 이력에 남아 이후의 한 번 받기·구독·지난 회차 검색의 바탕이 돼요.

2026-10-04에 닫았어요. 범위와 티켓 0001–0009는 [보관한 목표 1](../archive/tickets/1-app-owned-collection/README.md)에 있어요.

완료는 다음을 모두 관찰한 때예요: 기존 YAML을 가져온 앱이 cron 없이 같은 항목을 같은 폴더로 받고, 웹에서 고친 규칙이 다음 처리에 쓰이며, 미리보기와 실제 처리의 결과가 같고, 수집 이력에서 한 번 받기를 할 수 있어요.

- 관찰한 것이에요([0009](../archive/tickets/1-app-owned-collection/0009-deploy-web-worker.md)).
  - 실제 서버(j4105, 2026-10-01): 기존 YAML에서 채널 2개와 규칙 26개를 가져왔어요. worker의 첫 주기는 cron이 넣은 토렌트를 같은 폴더에서 모두 알아봤어요. 전환 전에 저장한 토렌트 목록과 견줘 빠진 토렌트, 새 토렌트, 폴더가 바뀐 토렌트가 없었어요. 수집 이력의 한 번 받기 두 건이 `received`로 끝났어요. 웹만 재시작하는 동안 worker는 계속 돌았어요.
  - 서버의 cron 항목은 2026-10-01에 지웠고, 옛 실행 파일과 그 코드는 2026-10-02에 걷어냈어요. 0.5.0으로 컨테이너를 다시 만든 뒤 첫 주기는 새 항목 0개였어요. DB의 이력이 남은 거예요.
  - 사용자 확인(2026-10-04): 휴대폰 LTE에서 공인 IP로 웹과 Transmission에 닿지 않아요. 휴대폰에서 0003·0006을 했고, `.torrent` 추가 응답 시간도 봤다고 알렸어요. 관찰한 값은 받지 않았어요.
- 시험으로 확인한 것: 웹에서 고친 규칙이 다음 처리에 쓰이는 것과, 미리보기의 예측이 다음 주기의 처리와 같은 것이에요. 0006의 통합 시험 `what_the_preview_predicts_for_an_edit_is_what_the_next_cycle_does_after_it_is_saved`와 `after_a_reorder_through_the_api_the_next_cycle_picks_the_first_match_in_the_new_order`예요. 실제 서버에서 규칙을 고친 뒤 다음 주기를 따로 관찰한 기록은 없어요.
- 남은 것이에요. 티켓마다의 다른 한계는 보관한 각 티켓의 `남은 일`에 있어요.
  - 원격 인증 화면(목표 3)의 보호를 실제 배포 경로에서 확인하는 일은 결과 목표 5로 넘겼어요. 서버는 0.5.0이라 원격 화면이 아직 없어요.
  - Transmission OOM 관찰과 자원 한도는 [0058](0058-server-oom-and-resource-limits.md)에서 이어가요.
  - 0004가 적은 음수 회차 변환의 이름 반복 변경(가짜 서버에서 본 `S04E38` → `S04E14`)은 실제 Transmission에서 따로 관찰하지 않았어요.

### 2. 작품 발견과 방영작 구독

세 종류 영상 입력에서 작품·시즌·회차를 발견하고, 방영작을 구독해 수집을 시작하며, 영상 쪽의 확장 수집을 연결해요.

2026-10-04에 닫았어요. 범위, 결정, 진행 순서와 티켓 0010–0028은 [보관한 목표 2](../archive/tickets/2-work-discovery-and-subscriptions/README.md)에 있어요.

이 목표에는 따로 적은 완료 관찰이 없었어요. 그래서 티켓마다의 완료 기준과 [구현 순서](../specs/web-app.md#구현-순서)의 2단계에 맞춰 봤어요. 0010–0028은 모두 `완료`예요. 실제 외부 서비스로 해 볼 확인이 남은 티켓도 있지만, 사용자가 0013·0014의 휴대폰 확인 뒤 이 목표를 닫기로 했어요(2026-10-04).

- 관찰한 것이에요.
  - 실제 서버(j4105, 0.5.0, 2026-10-02): 첫 주기에서 수집 폴더가 감시 폴더로 등록되고, 첫 스캔이 작품 29개를 읽었어요([0009](../archive/tickets/1-app-owned-collection/0009-deploy-web-worker.md)). 운영 데이터로 라이브러리와 작품 상세가 그려졌어요(0013·0014). Transmission이 받은 회차가 inotify 알림으로 3초 만에 들어왔어요(0016).
  - 개발 환경(작품 89편, 2026-10-04): 사용자가 iPhone Safari로 라이브러리의 스크롤, 페이지 이어 붙이기, 상세 왕복을 봤어요. 작품 상세의 시즌 시트와 카드도 봤어요(0013·0014). 이때 보기·정렬·회차 순서를 새로고침하면 처음으로 돌아가게 바꿨어요(사용자 결정, `80643c4`).
  - 나머지 동작은 Rust 시험과 로컬 브라우저로 확인했어요. Transmission·Anissia·AniList·nyaa는 대개 가짜 서버나 기록한 응답으로 대신했어요. 티켓마다의 `검증한 것`에 있어요.
- 남은 것이에요. 티켓마다의 다른 한계는 보관한 각 티켓의 `검증하지 못한 것`과 `남은 일`에 있어요.
  - 실제 AniList로 하지 않은 확인: 작품 표지 고르기, 시즌 자동 연결·속편 제안·줄거리, 자동 표지가 시즌 연결을 따라가는 것(0015·0017·0027)이에요.
  - 실제 Anissia 화면으로 하지 않은 확인: 편성표 구독, 제목 대기, 이번 주 편성, 기존 YAML 주석의 구독 제안(0018·0020·0021·0022)이에요. 분기가 바뀌는 날의 `이번 분기`·`다음 분기` 나눔도 시험으로만 봤어요(0018).
  - 실제 Transmission으로 하지 않은 확인: 구독이 받은 영상의 시즌 연결과 `409` 화면(0019), 보관 제안(0023), 영상 회차 변환(0024), 영상 수정본 대체(0025), 지난 회차 검색으로 받기(0026)예요. 보관·복원 뒤 시딩이 이어지는지(0011)와 실제 DB에서 수집 폴더 마이그레이션 결과(0010)도 기록이 없어요.
  - 결과 목표 5로 넘긴 것: 작품 표지와 시즌 정보의 앱 YAML 내보내기·가져오기 필드(0015·0017), 설정 내보내기의 `episode_auto` 왕복(0024)이에요.
  - 스크린 리더로 읽은 결과는 보지 않았어요(0013·0014).
  - 작품 상세에서 뒤 목표로 넘긴 부분은 0014의 `남은 일`에 있어요. 라이브러리 할 일 배지와 작품 상세의 `할 일` 카드는 아래 목표 3의 남은 것에 적었어요.

### 3. 자막 후보와 수신

자막 후보를 찾고, 구독 제작자는 자동으로, 그 밖에는 사용자가 골라 받으며, 인증은 trss 안에서 끝내요.
이 목표의 수신은 받은 묶음을 앱 데이터 폴더의 수신 영역에 두는 데까지이며, 분석·보관·적용은 결과 목표 4예요. 출처별 다운로드의 "적용까지 이어지는지"의 확인은 목표 4에서 끝나요.

2026-10-04에 닫았어요. 범위, 결정, 진행 순서와 티켓 0029–0057은 [보관한 목표 3](../archive/tickets/3-subtitle-candidates-and-receiving/README.md)에 있어요.

완료는 다음을 모두 관찰한 때예요: Anissia 최근 자막 목록의 변화가 30분마다 후보로 쌓이고 연결한 시즌의 후보를 작품 상세에서 골라 받을 수 있으며, 구독 제작자의 새 회차와 수정본이 선택 없이 받아지고, 여섯 경로가 각각 실제 서버의 수신 영역까지 파일을 받으며, erulabo는 실제 웹 화면에서 사람이 CAPTCHA만 풀어 받고, 직접 찾기와 올리기로 지난 회차를 들일 수 있어요.

2026-10-04에 이 목표의 티켓이 모두 끝났어요. 그 뒤 같은 날 사용자가 실제 휴대폰으로 원격 화면을 쓰다 알린 문제로 0056·0057을 더했고, 같은 날 둘 다 끝났어요. 위의 관찰은 개발 환경(실제 외부 사이트, 서버 DB 복사본)에서 해도 돼요(사용자 결정, 2026-10-04). 실제 서버에 배포해 보는 것은 이 목표의 완료 조건이 아니에요. 구독 제작자의 수정본은 제작자가 게시물을 고쳐야 생겨서 관찰할 때를 정할 수 없어요. 그래서 0045의 시험으로 확인한 것으로 둬요(사용자 결정, 2026-10-04). 구독 제작자의 새 글을 관찰해 자동 작업이 생기는 것도 시험으로 확인한 것으로 둬요(사용자 결정, 2026-10-04). 실제로 보려면 제작자의 다음 글을 며칠 기다려야 하는데, 그 경로를 처음부터 끝까지 도는 시험이 있어서예요.

- 관찰한 것: 개발 환경의 worker가 Anissia 최근 자막 목록을 읽어 후보를 쌓고(0035), 작품 상세에서 고른 후보를 받았어요. 여섯 경로 모두 worker가 실제 게시물에서 수신 영역까지 받았어요. Blogger·Drive 개별 파일과 ZIP(0042), Tistory 일반 첨부(0038), Tistory WinPNG(0043), Naver(0044), erulabo(0041)예요. WinPNG는 하느 763에서 SMI 325,531바이트와 ASS 170,859바이트를 받았어요. 2026-10-03(리뷰 수정 전 코드)과 2026-10-04(`d17edfb`)에 받은 두 파일의 바이트가 같았어요. erulabo는 사람이 PC(2026-10-03)와 실제 휴대폰(2026-10-04, 0040)의 웹 원격 화면에서 확인을 풀어 받았어요. 직접 찾기(0046)는 실제 제작자 블로그에서 받았고, 올리기(0047)는 개발 환경의 웹에서 들였어요.
- 구독 제작자의 받지 않은 회차를 선택 없이 받았어요(0045, 2026-10-04, `d17edfb`). 전생했더니 검이었습니다 2기 구독의 `자막 받기`를 켜자 `자막 구독` 제안이 생겼어요. 수퍼소닉EX를 제작자로 정하자 제안이 사라지고 `auto:14` 작업이 생겼어요. 이 작업은 Naver 게시물에서 1화 SMI 76,408바이트와 폰트 3개를 받았어요. 회차 대응은 `자동 · 1화가 방영 뒤에 올라왔고 시즌 회차 수(12) 안이에요`였어요.
- 이 관찰을 위한 준비예요. 개발 Transmission은 넣은 토렌트를 시작하지 않아요(`start-added-torrents: false`). 그래서 파일 목록이 없고, 구독이 시즌에 이어지지 않아요. 그 구독의 1화 토렌트를 파일 목록이 생길 때까지만 시작했다 멈췄어요(받은 영상 0바이트). 그 경로에 빈 영상 파일을 두자 시즌 연결과 Anissia 연결이 생겼어요. 시즌의 AniList 항목(159042)은 작품 상세의 연결로 이었어요.
- 시험으로 확인한 것: 새 관찰이 만든 자동 작업이에요. 위 `auto:14`는 제작자를 정한 때 만들어졌어요. `crates/trss-worker/tests/anissia_captions.rs`의 `a_reading_that_finds_the_subscribed_creators_new_episode_makes_and_runs_its_job`은 실제 worker와 웹 API에, 2026-10-02에 실제 Anissia에서 읽은 모양의 가짜 Anissia와 가짜 출처를 써요. 최근 목록 읽기가 구독 제작자의 새 회차를 찾으면 worker가 자동 작업을 만들어 바로 받아요. 제작자를 정할 때와 목록을 읽은 뒤 모두 같은 `Follow::evaluate`가 작업을 만들어요. 실제 Anissia에 새 줄이 생겨 실제 worker가 작업을 만드는 흐름 전체는 보지 않았어요. 수정본은 0045의 시험이에요.
- 남은 것이에요. 티켓마다의 다른 한계는 보관한 각 티켓의 한계 절에 있어요.
  - 결과 목표 4로 넘긴 것: 받은 묶음에서 회차의 파일을 고르는 분석, ZIP이 아닌 압축 풀기(0047), 받은 파일 이름의 회차와 대응을 견주는 확인, 회차 대응을 바꿀 때 보관본과 미완료 작업을 새 기준으로 다시 보는 요구(0052, 아직 티켓 없음), 작품별 자막 형식 순서(0049)예요.
  - 원격 화면에서 휴대폰의 가상 키보드로 원격 페이지에 글자를 넣는 것은 실제 휴대폰에서 확인하지 않았어요. 페이지 창의 입력란은 확인했어요(0057). HTTPS 앞단 프록시 뒤의 WSS도 확인하지 않았어요(0040).
  - 실제로 본 적 없는 출처 응답은 알려진 표시로만 가려요. Drive의 확인·할당량·로그인 페이지, Naver의 비공개 글·보안 확인 페이지 같은 것이에요. 처음 나오면 확인해요(0042·0044).
  - erulabo 제작자가 수정본을 같은 Drive 파일에 덮어쓰는지는 재확인 관찰이 쌓여야 정해요(0050, 사용자 결정 2026-10-02).
  - 티켓 없이 남은 것: 라이브러리 격자 표지의 할 일 배지와 작품 상세 위쪽의 `할 일` 카드([라이브러리 화면](../specs/library.md#라이브러리-화면), [할 일과 회차 목록](../specs/library.md#할-일과-회차-목록))를 만들지 않았어요. 할 일은 할 일 화면과 메뉴 배지에서만 보이고, `회차 확인 필요`는 작품 상세의 자막 후보 구역으로 이어요. 0013은 이 배지를 목표 3에서 붙인다고 적었지만, 목표 3의 범위와 티켓에는 들어 있지 않았어요. 교체 승인 카드는 목표 4예요.
