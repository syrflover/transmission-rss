# 0056 원격 화면의 페이지가 멈추면 알리고 서버 브라우저를 새로 띄워요

- 상태: 완료
- 출처: [작업 화면 안의 인증과 브라우저 수명](../specs/jobs.md#작업-화면-안의-인증과-브라우저-수명), 사용자 보고와 결정(2026-10-04)
- 막는 티켓: 없음

## 배경

2026-10-04에 사용자가 실제 휴대폰으로 직접 찾기의 원격 화면을 쓰다가 새로고침이 되지 않는다고 알렸어요. 새로고침을 여러 번 누르자 `서버 브라우저가 닫혔어요`가 떴고, 다시 연결하면 됐어요.

개발 환경에서 확인한 것이에요(2026-10-04, `d17edfb`에서 지은 이미지).

- 보통 상태에서는 새로고침이 3–41ms에 답했고 페이지가 실제로 새로 읽혔어요. 연타하거나 터치와 섞어도 연결이 끊기지 않았어요.
- 페이지가 떠나기 확인 창(`beforeunload`)을 띄우게 하자(시험으로 넣은 처리기) 같은 증상이 났어요. 새로고침 명령은 답했지만 페이지는 새로 읽히지 않았어요. 그 뒤 터치 하나가 30초 동안 답을 받지 못했고, 웹이 화면을 `ended`(`browser`)로 끝내 `서버 브라우저가 닫혔어요`가 떴어요. 다시 열어도 `Page.enable`이 30초 안에 답하지 않아 `서버 브라우저에 닿지 못했어요`로 끝났어요. 실행을 끝내야만 풀렸어요.

원인은 둘이에요. 보이지 않는 페이지 창은 [0057](0057-remote-screen-page-dialogs.md)이 다뤄요. 이 티켓은 멈춘 페이지를 다뤄요.

- 웹은 입력 명령 하나가 30초(`COMMAND_TIMEOUT`) 안에 답하지 않으면 묶음의 모든 소켓을 `browser`로 끝내요. 브라우저는 닫히지 않았는데 화면은 닫혔다고 말해요.
- 소켓은 메시지를 하나씩 처리해요. 그래서 명령의 답을 기다리는 동안 그 소켓의 ping·프레임·끝 알림도 멈춰요.
- 멈춘 페이지를 되살리는 길이 화면에 없어요. 실행은 worker의 풀만 시작하고 끝내요. 사람이 누르는 `다시 열기`는 살아 있는 실행을 그대로 써요.

휴대폰의 페이지가 어떤 상태였는지는 확인하지 못했어요. 휴대폰에서는 다시 연결하자 됐으므로, 재현한 상태와 같지는 않았을 수 있어요.

## 사용자 결정 (2026-10-04)

- 페이지가 응답하지 않으면 화면을 끊지 않고 `페이지가 응답하지 않아요`를 보여요. 그 자리에 서버 브라우저를 새로 띄워 게시물을 다시 여는 버튼을 둬요.
- 입력이 답을 기다리는 동안에도 다른 메시지를 막지 않아요.

## 정한 방식

- **응답하지 않음**: 웹이 페이지에 보낸 입력(`Input.dispatch*`, `Input.insertText`)·새로고침·크기 바꾸기 명령이 5초(`ANSWER_WITHIN`) 안에 답하지 않으면, 웹은 묶음의 소켓에 `{"type":"page","responding":false}`를 보내요. 화면은 끝내지 않아요. 그 뒤 오는 입력은 페이지로 보내지 않고 버려요. 브라우저에 쌓였다가 페이지가 풀린 뒤 한꺼번에 들어가지 않게 하려는 거예요.
- **다시 응답함**: 응답하지 않는 동안 웹은 1초마다 페이지에 가벼운 명령(`Runtime.evaluate`)을 보내요. 답이 오면 `responding:true`를 보내요. 그리고 마지막 기기 크기를 다시 적용해 화면 전송을 새로 시작해요(세대가 올라가요). 멈춘 사이 크기 바꾸기가 중간에 끊겼을 수 있어서예요.
- **끝내는 경우**: CDP 연결이 닫히거나 페이지에서 떨어지면 지금처럼 `ended`(`browser`)예요. 브라우저가 입력·새로고침을 거절하면 그 명령만 하지 않고 화면은 그대로예요.
- **멈춘 페이지에 새로 붙을 때**: 소켓이 처음 붙을 때 `Page.enable`이 10초 안에 답하지 않으면 `ended`(`stuck`)로 끝내요. 이 티켓 전에는 30초 뒤 `unreachable`이었어요.
- **소켓**: 소켓마다 메시지를 받은 순서대로 처리하는 작업을 따로 둬요. 소켓의 루프는 그동안에도 ping·프레임·끝 알림을 처리해요. 처리를 기다리는 메시지가 쌓이면 마우스 이동·휠·터치 이동부터 버려요. 누르기·떼기·키·크기·새로고침·뒤로·앞으로는 줄(64개)이 다 찼을 때만 버려요. 떼기를 잃으면 페이지에 버튼이나 손가락이 눌린 채로 남기 때문이에요.
- **새로 띄우기**: `POST /api/subtitle-jobs/{id}/screen/restart` `{ "run", "bound" }`.
  - 웹은 사람이 본 묶음(`run`, `bound`)이 그대로일 때만 요청을 화면 행에 적고(`restart_run_id`, 마이그레이션 48) worker를 깨워요. 그러면 202, 묶음이 바뀌었으면 409, 작업이 없으면 404예요. 사람의 입력으로 세요. 웹은 실행을 시작하거나 끝내지 않는다는 원칙은 그대로예요.
  - worker는 준비 요청과 같은 자리에서 요청을 가져가요. 그 실행이 살아 있으면 끝내고(`AuthBrowser::release`), 작업을 다시 줄에 세워 새 실행으로 게시물을 다시 열어요. 실행이 이미 없으면 지금의 다시 열기와 같아요. 받는 중인 다운로드가 있으면(`AuthBrowser::downloading`) 그것이 끝날 때까지 미뤄요. 받은 파일은 남고, 실행의 쿠키와 다른 탭은 사라져요.
  - 새로 띄우려고 끝낸 실행은 `서버 브라우저가 쉬는 동안 닫혔어요`로 묶음을 풀지 않아요. 작업 기록은 `서버 브라우저를 새로 띄워 사이트 확인 화면을 다시 준비해요`(직접 찾기는 `서버 브라우저를 새로 띄워 제작자의 게시물을 다시 열어요`)예요.
- **화면**: `responding:false`를 받으면 원격 화면 위에 `페이지가 응답하지 않아요` 안내와 `새로 띄우기`를 둬요. `ended`(`stuck`)에도 같은 안내와 `새로 띄우기`를 두고, `다시 연결`도 둬요. `새로 띄우기`를 누르면 묶음이 바뀔 때까지 `서버 브라우저를 새로 띄우고 있어요`를 보여요.

## 완료 기준

| 입력·상태 | 기대 결과 |
| --- | --- |
| 페이지가 입력에 5초 넘게 답하지 않음 | 화면이 끝나지 않고 소켓이 `responding:false`를 받아요. 그 뒤 입력은 페이지로 가지 않아요. |
| 그 페이지가 다시 답함 | 소켓이 `responding:true`와 새 세대의 크기를 받고, 입력이 다시 페이지로 가요. |
| 입력이 답을 기다리는 동안 | 같은 소켓의 ping 응답, 프레임, 끝 알림이 막히지 않아요. |
| CDP 연결이 끊기거나 페이지가 떨어짐 | 지금처럼 `ended`(`browser`)예요. |
| 멈춘 페이지에 새 화면이 붙음 | 10초 안에 `ended`(`stuck`)를 받아요. |
| 묶음이 그대로인 `새로 띄우기` | worker가 실행을 끝내고 새 실행으로 게시물을 다시 열어요. 화면은 새 묶음으로 붙어요. 받은 파일은 남아요. |
| 다른 묶음의 `새로 띄우기` | 409이고 아무것도 바뀌지 않아요. |
| 받는 중인 다운로드가 있는 실행의 `새로 띄우기` | 다운로드가 끝난 뒤에 새로 띄워요. |
| 실제 서버 브라우저 이미지 | 스크립트가 붙든 페이지에서 위 동작이 돼요. |
| 휴대폰 폭(375px) | 안내와 버튼이 가로 스크롤 없이 들어가요. |

## 결과 (2026-10-04)

정한 방식대로 구현했어요.

- 웹(`trss-web`의 `screen_api`·`screen_api/hub`): 페이지 명령의 5초 한도와 `page` 메시지, 1초마다 보내는 응답 확인, 회복할 때 크기를 다시 적용하기, `Page.enable` 10초 한도와 `stuck`, 소켓마다 따로 둔 처리 작업과 64칸 줄, `POST .../screen/restart`를 더했어요. CDP 클라이언트의 `command_marked_within`을 공개했어요.
- worker(`trss-jobs`): 화면 행의 `restart_run_id`(마이그레이션 48), `ScreenStore::request_restart`, `tend_screens`의 새로 띄우기와 다운로드 미루기, 작업 기록 두 문구, 새로 띄우려고 끝낸 실행의 묶음을 `실행이 닫혔어요`로 풀지 않는 조건을 더했어요.
- 화면(`RemoteScreen`): `페이지가 응답하지 않아요` 안내와 `새로 띄우기`, `stuck`의 `새로 띄우기`·`다시 연결`, 묶음이 바뀔 때까지 보이는 `서버 브라우저를 새로 띄우고 있어요`를 더했어요.

| 입력이 답을 기다리는 동안 | 첫 시험에서 입력이 답을 기다리는 사이 프레임이 0.6초 안에 왔어요. `inputs_that_pile_up_behind_one_the_page_does_not_answer_are_let_go_but_never_a_size`에서 쌓인 이동 100개는 페이지에 가지 않았고 크기는 버려지지 않았어요. `a_full_queue_lets_moves_go_but_never_a_press_a_release_a_key_or_a_size`는 줄이 48개를 넘었을 때 이동·휠만 버리는지 봐요. ping 응답과 끝 알림은 프레임과 같은 루프에서 처리하지만, 기다리는 동안의 ping은 따로 시험하지 않았어요. |
| CDP 연결이 끊김 | 기존 시험(`browser` 끝)이 그대로 통과했어요. |
| 멈춘 페이지에 새 화면 | `a_screen_that_opens_on_a_page_that_does_not_answer_ends_stuck`. 실제 이미지에서 10.0초에 `ended`(`stuck`)였어요. |
| 묶음이 그대로인 `새로 띄우기` | `a_person_asks_the_worker_to_start_the_run_anew_and_the_web_ends_no_run`, worker 시험 `a_restart_of_a_live_run_ends_it_and_puts_the_job_back_in_line_with_its_own_event`·`a_restart_of_a_run_that_is_gone_puts_the_job_back_in_line_without_ending_anything`·`a_restart_ends_the_stuck_run_after_its_download_and_opens_the_same_post_in_a_new_one`(직접 찾기). 실제 이미지에서 요청 0.8초 뒤 새 실행이 게시물을 다시 열었고, 새 묶음의 화면에 프레임이 왔으며, 작업 기록에 `서버 브라우저를 새로 띄워 제작자의 게시물을 다시 열어요`가 있고 `실행이 닫혔어요` 기록은 없었어요. |

전체 검사(2026-10-04): `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace --no-fail-fast`(검토를 반영한 뒤 2,230개 통과), 웹 `npm test`(75개 통과)·`npm run typecheck`·`npm run build`가 통과했어요. 실제 이미지 시험 `remote_screen_docker` 세 개도 통과했어요.

독립 검토(2026-10-04, 동시성·마이그레이션·공개 API)에서 다섯 가지를 고친 뒤 다시 확인받았어요.

- 이미 멈춘 묶음에 새로 붙은 화면은 프레임을 받지 못해 `불러오는 중`에 머물렀어요. 이제 첫 프레임 전에도 `responding:false`면 안내와 `새로 띄우기`를 보여요.
- 줄이 차면 떼기·키까지 알림 없이 버려져, 페이지에 버튼이나 손가락이 눌린 채 남을 수 있었어요. 이제 이동·휠부터 버려요.
- 멈춤과 회복이 엇갈리면 깃발은 멈춤인데 소켓에는 응답한다고 남을 수 있었어요. 이제 깃발과 `page` 메시지를 한 잠금 안에서 바꿔요.
- 회복이 크기 잠금을 잡기 전에 크기를 읽어, 그사이 온 새 크기를 옛 크기로 덮을 수 있었어요. 이제 잠금을 잡은 뒤 읽어요.
- 끝난 소켓의 처리 작업이 `dropped` 알림을 보내지 못하면 남은 메시지를 버렸고, 그 전까지는 밀려난 소켓의 입력을 계속 페이지에 보냈어요. 이제 소켓이 끝나면 처리하던 메시지만 마치고 멈춰요.

검토가 남긴 것이에요. 아래는 고치지 않았어요.

- 크기 바꾸기가 5초를 넘기면 세대는 올라가지만 `viewport`를 보내지 않아요. 멈춘 동안 입력은 버려지고 회복이 새 세대를 알리므로 해가 없어요.
- 새로 띄우기 요청과 worker의 처리 사이에 실행이 저절로 끝나고 사람이 `받기 끝내기`를 누르면, 작업은 끝나기 전에 새 실행을 한 번 더 띄워요. 그 틈은 웹이 요청을 적은 뒤 worker가 깨어 처리하기까지예요.
- 새로 띄우기 경로는 서버 브라우저가 없는 웹에서도 요청을 적어요. 탭 전환·닫기 경로와 같고, 그때 화면에는 버튼이 없어요.
- `Runtime.evaluate`에는 답하지만 입력에는 계속 답하지 않는 페이지라면 멈춤과 회복을 몇 초마다 오갈 수 있어요. 그런 페이지는 보지 못했어요.

휴대폰 확인(2026-10-04): 개발 환경(`9235d43`에서 지은 이미지, LAN 주소로 연 웹)에서 사용자가 아이폰으로 직접 찾기 작업(코코렛, `felia.tistory.com`의 게시물)의 원격 화면을 썼어요. 실제 사이트는 스스로 멈추지 않아요. 그래서 별도 CDP 연결로 스크립트를 넣었어요. 이 스크립트는 다음 탭 0.3초 뒤부터 페이지의 스레드를 20초 동안 붙들어요.

- 멈춘 동안 한 번 더 탭하자 `페이지가 응답하지 않아요`와 `새로 띄우기`가 떴어요. 붙듦이 풀리자 안내가 저절로 사라졌어요. 페이지의 긴 작업 기록에 20.0초짜리가 남았어요.
- 다시 멈춘 뒤 `새로 띄우기`를 누르자 작업 기록에 `서버 브라우저를 새로 띄워 제작자의 게시물을 다시 열어요`가 남았어요. 1초 뒤 새 묶음이 게시물을 열었고, 사용자는 화면이 잘 이어졌다고 알렸어요.
- 새로고침을 여러 번 빠르게 눌러도 연결이 끊기지 않았어요.

확인하지 않은 것이에요.

- 실제 휴대폰과 개발 환경의 실제 사이트에서는 확인하지 않았어요. 같은 날 뒤에 한 휴대폰 확인(위)은 넣은 스크립트로 멈춘 페이지예요. 실제 사이트가 스스로 멈춘 경우는 보지 않았어요.
- 받는 중인 다운로드를 미루는 것은 가짜 브라우저로만 확인했어요.
- 사용자의 휴대폰에서 페이지를 멈춘 원인은 여전히 모르는 채예요. 페이지 창이 원인이면 이 티켓으로는 `응답하지 않음`과 `새로 띄우기`까지이고, 창에 답하는 것은 [0057](0057-remote-screen-page-dialogs.md)이에요.
