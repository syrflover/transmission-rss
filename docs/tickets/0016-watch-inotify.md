# 0016 감시 폴더의 변경을 inotify로 바로 반영해요

- 상태: 완료 (실제 서버에서 Transmission이 받은 회차가 알림으로 3초 만에 들어온 것을 봤어요. 아래 "실제 서버 확인")
- 출처: [작품 발견과 감시 폴더](../specs/library.md#작품-발견과-감시-폴더)
- 막는 티켓: [0012](0012-watch-folders-discovery.md)

## 작업

worker가 감시 폴더의 변경을 커널의 inotify 알림으로 받아, 바뀐 작품만 곧바로 다시 읽어요.
inotify로 알 수 없는 때만 [0012](0012-watch-folders-discovery.md)의 폴더 수정 시각 확인으로 메워요(사용자 결정, 2026-10-01).
5분마다 폴더 1,500개쯤을 확인하던 읽기를 없애고, 새 회차가 다음 주기를 기다리지 않고 라이브러리에 나타나게 하려는 거예요.
inotify는 감시 하나에 커널 메모리 1KB쯤을 고정으로 쓰는 대신, 감시하는 폴더의 inode가 캐시에서 밀려나지 않아 대체 확인도 디스크를 읽지 않아요.

- 감시 폴더·작품 폴더·시즌 폴더에 감시를 걸고, 만들기·지우기·이름 바꾸기·감시 대상 자체의 이동과 삭제만 받아요. 받는 중인 파일의 쓰기(수정) 알림은 받지 않아요. 받기가 끝나 `.part`가 제 이름으로 바뀌는 것은 이름 바꾸기로 잡혀요.
- 알림은 무엇이 바뀌었는지가 아니라 어느 작품을 다시 읽을지의 신호로만 써요. 같은 작품의 알림을 몇 초 모은 뒤 worker 잠금 안에서 그 작품 하나를 다시 읽어요. 그래서 알림 순서가 섞이거나 일부를 놓쳐도 기록은 디스크와 같아져요.
- 새 작품·시즌 폴더가 생기면 감시를 걸고 곧바로 그 폴더를 한 번 읽어요. 감시를 걸기 전 사이에 생긴 파일을 놓치지 않으려는 거예요.
- 폴더 수정 시각 확인으로 메우는 때: worker가 시작할 때(꺼진 동안의 변경), 커널 알림 큐가 넘쳤을 때(그 감시 폴더 전체), 감시 한도 등으로 감시를 걸지 못한 폴더(그 폴더만 주기마다), 그리고 안전망으로 1시간마다 한 번이에요.
- 추가 시각은 0012의 규칙 그대로예요. 알림으로 찾은 파일도 앱이 처음 본 시각을 써요.
- 감시를 걸지 못한 폴더가 있으면 감시 폴더 줄에 그 수와 까닭(예: 감시 한도)을 한 문장으로 보여줘요.

## 완료 기준

| 입력·상태 | 기대 결과 |
| --- | --- |
| worker가 도는 중에 시즌 폴더에 회차 파일을 넣음 | 수집 주기를 기다리지 않고 몇 초 안에 그 회차가 기록되고, 그 작품만 다시 읽혀요(다른 작품은 읽지 않음을 시험에서 확인). |
| 받는 중인 `.part` 파일에 계속 씀 | 그 쓰기로는 다시 읽지 않아요. `.part`가 제 이름으로 바뀌면 회차가 기록돼요. |
| 새 작품 폴더와 시즌 폴더를 한꺼번에 만들고 바로 파일을 넣음 | 작품·시즌·회차가 모두 기록되고, 새 폴더에도 감시가 걸려 다음 파일도 알림으로 잡혀요. |
| 작품 폴더를 지우거나 감시 폴더 밖으로 옮김 | 작품이 `폴더 없음`이 되고 그 감시가 풀려요. |
| [0011](0011-archive-folder-move.md)의 보관 이동 | 옮긴 작품이 같은 ID로 보관 폴더 쪽에 이어지고, 두 폴더의 감시가 새 위치에 맞게 바뀌어요. |
| worker가 꺼진 동안 파일을 더하고 지운 뒤 다시 켬 | 시작할 때의 수정 시각 확인으로 둘 다 반영돼요. |
| 알림 큐 넘침을 흉내 냄(시험 경계) | 그 감시 폴더 전체를 수정 시각 확인으로 다시 맞춰요. |
| 감시 한도를 작게 둔 환경 | 감시를 걸지 못한 폴더는 주기마다 수정 시각으로 확인되고, 감시 폴더 줄에 까닭이 보여요. 나머지는 알림으로 동작해요. |
| 변경이 없는 1시간 | 안전망 확인 한 번 말고는 감시 폴더를 읽지 않아요(로그로 확인). |
| Transmission 컨테이너가 받은 파일(같은 호스트의 다른 컨테이너) | 알림으로 잡혀요. 배포 뒤 실제 서버에서 한 회차로 확인해요. |

## 결과

### 구현한 것

- 감시(`crates/trss-library/src/live/`): worker가 감시 폴더마다 inotify 인스턴스 하나를 열어 감시 폴더 뿌리, 작품 폴더, `Season NN` 폴더에 감시를 걸어요(커널의 재귀 감시가 아니라 폴더마다). 받는 알림은 만들기·지우기·이름 바꾸기(`moved_from`·`moved_to`)·대상 자체의 삭제와 이동(`delete_self`·`move_self`)뿐이고 쓰기(수정)는 받지 않아요. 새 의존성 없이 이미 쓰는 `rustix`의 inotify를 직접 써요. 알림 큐 넘침(`IN_Q_OVERFLOW`)과 감시 한도(`ENOSPC`)를 날것으로 구별할 수 있고, 감시 폴더마다 인스턴스를 따로 두면 넘침이 그 폴더 하나의 일이 되기 때문이에요.
  - 알림은 어느 작품을 다시 읽을지의 신호로만 써요(`tree.rs`). 같은 작품의 알림은 처음 알림에서 3초(`LiveConfig::debounce`) 뒤에 한 번 모아 읽어요. 숨김 항목(`.trss/` 포함)의 알림은 신호가 아니에요. 새 작품·시즌 폴더는 알림을 처리할 때 곧바로 감시를 걸고, 읽기는 그 뒤(디바운스 뒤)에 하므로 감시를 걸기 전 사이에 생긴 파일은 그 읽기가 보아요. 지워지거나 밖으로 옮겨진 폴더와 그 아래의 감시는 풀어요(커널 감시는 경로가 아니라 inode를 따라가서, 풀지 않으면 옮겨진 폴더가 옛 이름으로 계속 알려요).
  - 읽기는 worker의 `flock`(`CycleLock`) 안에서만 해요(`watcher.rs`). 잠금이 잡혀 있으면(주기나 명령이 도는 중) 1초 뒤에 다시 시도하고, 모은 작품은 그대로 남아요. 주기는 반대로 worker 자신의 감시가 잠금을 잠깐 쥔 것이면 최대 20초 기다렸다가 잠금을 잡아서, 그 순간에 걸려 주기가 통째로 건너뛰어지지 않아요.
  - 작품 몇 개만 읽는 `discovery::scan_works`(`scan_incremental`과 같은 규칙, 같은 캐시)와 그 기록 `LibraryStore::record_works`를 더했어요. 기록은 그 작품들만 바꿔요. 이름을 준 작품의 폴더가 없으면 `폴더 없음`으로 표시하고 ID와 기록은 남아요. 추가 시각은 0012 그대로 그 읽기의 시각(worker의 시계)이고 파일시스템 시각은 읽지 않아요. 작품 몇 개만 읽은 기록은 폴더의 기준선과 오류를 지우지 않아요(읽지 못한 작품이 있으면 오류 문장을 더하기만 해요).
- 수정 시각 확인으로 메우는 때(`watch::scan_all`, `LiveWatch::poll_for`): worker가 시작한 뒤 첫 주기(감시를 먼저 걸고 읽어서 읽는 동안의 변경은 알림으로 와요), 알림 큐가 넘쳤을 때(그 감시 폴더의 감시를 다시 맞추고 폴더 전체를 읽어요), 감시를 걸지 못한 폴더(그 작품만 주기마다 읽고, 뿌리를 걸지 못했으면 그 폴더 전체를 주기마다 읽어요), 안전망(마지막으로 폴더를 통째로 읽은 지 1시간이 지난 주기에 한 번 읽고 감시도 다시 맞춰요), 그리고 마지막 읽기가 오류를 남긴 폴더(읽지 못한 폴더나 작품이 있으면 그 폴더를 주기마다 읽어요). 모든 디렉터리를 감시하는 조용한 폴더는 주기가 감시 폴더를 읽지 않아요. `Worker::run`이 시작해야 감시가 켜지고, `tick`만 부르는 worker는 감시가 없어서 이전처럼 주기마다 모든 폴더를 읽어요(기존 시험이 그대로 통과해요).
  - 실행 중 등록한 감시 폴더는 3초마다(명령을 보는 때) 알아채서 감시를 걸고 바로 한 번 읽어요(웹이 읽은 뒤 감시가 걸리기 전 사이의 변경을 찾으려는 거예요). 등록 해제하거나 경로가 바뀐 폴더는 감시를 풀어요.
  - 보관 이동(`rule_archive`)이 끝나면 옮긴 작품 폴더의 두 감시 폴더에서 그 작품의 감시를 다시 맞춰요(이동의 알림도 같은 일을 해요). 같은 ID가 보관 폴더 쪽으로 이어지고, 두 폴더 감시가 새 위치에 맞게 바뀌어요.
- 감시를 걸지 못한 폴더의 알림(`watch_folders.watch_note`, 마이그레이션 12(표지가 먼저 11을 써서 병합 때 12가 됐어요. 병합 전 0016 브랜치로 만든 개발 DB는 `user_version` 11이 `watch_note`를 뜻해서 지금의 11(표지)·12와 맞지 않으므로 다시 만들어야 해요), 웹 API 필드 `watch_note`, 설정의 폴더 줄): 걸지 못한 디렉터리의 수와 가장 흔한 까닭을 한 문장으로 worker가 적어요. 까닭은 감시 한도(`fs.inotify.max_user_watches`를 늘리라고 알려요), 읽을 권한 없음, 링크(감시는 경로가 아니라 가리키는 폴더를 따라가서 링크 작품은 직접 읽어요), 그 밖의 오류예요. 웹 화면은 별도 커밋이고 `FoldersPanel.tsx`에 문장 한 줄만 더했어요.
- 시험 경계(알림이 닿지 않는 일을 시험하려는 것): `LiveConfig`(디바운스·재시도·안전망·`max_watches`), `LiveWatch::simulate_overflow`, `LiveWatch::readings`·`read_counts`(어느 작품·폴더를 읽었는지), `LiveWatch::status`.
- 알려진 한계: 알림은 시즌 폴더 안의 하위 폴더(여러 파일 토렌트의 폴더)와 시즌 폴더 밖의 폴더(`Extras` 같은)에는 감시를 걸지 않아요. 그 안의 변경은 회차 없는 파일 수에만 영향을 주고 안전망(1시간)이 찾아요. SMB·NFS처럼 다른 기계가 바꾸는 공유의 변경도 커널이 알리지 않아서 안전망이 찾아요. 이름이 UTF-8이 아닌 작품 폴더의 알림은 그 폴더 전체를 읽게 해요.

### 검증한 것

- `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test` 전부 통과(단위 422개 + 통합). `web/`의 `npm run typecheck`·`npm run build` 통과.
- 통합 시험 `crates/trss-worker/tests/live_watch.rs`(진짜 inotify, 임시 폴더, 웹 API, 가짜 Transmission, 수동 시계; 대기는 DB를 폴링). 완료 기준의 행마다:
  - 도는 중에 회차 파일을 넣음: 주기 없이 기록되고 추가 시각이 그때의 시계 값이에요. 읽은 곳이 그 작품 하나뿐이고(`readings`) 다른 작품과 폴더 전체는 읽지 않았어요.
  - `.part`: 만들 때 한 번 읽고(받는 중인 파일로 세요) 5번 더 쓰는 동안 읽기 횟수가 그대로예요. 제 이름으로 바꾸면 회차가 기록돼요.
  - 새 작품·시즌 폴더와 파일을 한꺼번에: 작품·시즌·회차가 기록되고, 감시가 2개 늘고, 다음 파일과 새 시즌의 파일도 알림으로 기록돼요.
  - 작품 폴더 삭제·밖으로 이동: `폴더 없음`이 되고 감시가 풀려요(7개 → 3개). 옮겨진 폴더 안의 변경은 옛 이름으로 알려지지 않아요. 같은 이름 폴더가 돌아오면 같은 ID로 이어져요.
  - 보관 이동: 같은 ID가 보관 폴더에 이어지고, 수집 폴더의 감시가 5개 → 3개, 보관 폴더의 감시가 3개 → 5개로 바뀌고, 보관 폴더 쪽에 새로 들어온 파일이 알림으로 기록돼요.
  - worker가 꺼진 동안 파일을 더하고 지움: 첫 주기에 둘 다 반영되고, 새 파일의 추가 시각은 그 주기의 시각이며 폴더 전체 읽기 한 번뿐이에요.
  - 알림 큐 넘침(`simulate_overflow`): 감시가 없는 하위 폴더의 파일은 넘침 전엔 기록되지 않고, 넘침 뒤 폴더 전체를 읽어 찾아요.
  - 감시 한도(`max_watches`=5): 감시를 걸지 못한 작품 하나가 주기마다 그 작품만 읽혀 기록되고(폴더 전체 읽기 없음), 감시한 작품은 알림으로 기록돼요. 웹 API 목록의 `watch_note`가 `폴더 1개`와 `fs.inotify.max_user_watches`를 말해요.
  - 변경 없는 1시간: 수동 시계로 5분 주기 11번(55분)을 돌려도 폴더 읽기가 늘지 않고, 열두 번째 주기에서 한 번, 그 다음엔 다시 없어요.
  - 잠금: 다른 쪽이 잠금을 쥐고 있으면 알림이 와도 기록하지 않고, 풀리면 기록해요.
  - 감시를 켜지 않은 worker는 주기마다 모든 폴더를 읽어요. 실행 중인 worker는 나중에 등록한 폴더에 감시를 걸고 그 사이 변경을 찾으며, 등록 해제하면 감시를 풀고, 멈추면 모두 풀어요.
  - 진짜 `trss-worker` 프로세스(주기 3600초): 첫 주기 뒤 넣은 파일이 3초쯤 뒤 알림으로 기록돼요(로그 `1 works read (A)`).
- 단위 시험: 감시 배치와 알림 해석(`tree.rs` 12개: 쓰기는 알림이 아님, 숨김 항목, 이름 바꾸기, 빈 폴더 위로 이름 바꾸기, 한도, 링크, 뿌리 사라짐, 디바운스와 되돌림), `scan_works`, `record_works`(영역 밖 작품과 폴더 오류가 그대로), `watch_note`.
- 시험을 12개씩 동시에, CPU를 태우면서 돌려도 모두 통과했고, 같은 시험을 15번 되풀이해도 통과했어요.
- 실제 프로세스 측정(디버그 빌드, tmpfs의 임시 폴더, 작품 500개·시즌 1,000개·파일 3,000개, 디렉터리 1,501개, 주기 20초, 12코어): 감시 1,501개(프로세스의 inotify fdinfo로 센 값, 호스트 한도 524,288), 감시를 거는 데 172 ms, 첫 읽기 155 ms(디렉터리 1,501개 나열). 이후 100초(주기 5번) 동안 감시 폴더를 읽은 로그가 0줄이고 CPU는 user 2 + sys 1틱(0.03 s, RSS 작업 포함), 메모리 RSS 28.8 MB. 파일 하나를 넣으면 그 작품 하나만 읽고 기록하는 데 2 ms였어요(`1 works read (Work 7)`). 커널 쪽 감시 메모리는 문서 기준 감시당 1KB쯤이라 1.5MB쯤이고 직접 재지 않았어요.

### 실제 서버 확인 (2026-10-02, j4105, 0.5.0)

- Transmission 컨테이너가 받은 회차가 알림으로 들어왔어요. `FX Senshi Kurumi-chan S01E01.mkv`(1.4GB)가 수집 폴더에 완성된 시각이 10:07:49.97(KST, 파일 시각)이고, worker 로그의 `1 works read (FX Senshi Kurumi-chan): 1 found, 1 new, 1 files added`가 10:07:52.97이었어요. 다음 주기(10:08:13)보다 21초 앞서 주기 밖에서 읽었어요. 그 주기 끝에 규칙이 시즌 1에 이어졌어요.
- 첫 등록 때 감시가 74개 디렉터리에 걸렸고(`0 not`), 호스트의 `fs.inotify.max_user_watches`는 54260이에요.
- `docker stats`(릴리스 빌드, 감시 중, 받는 것 없음): worker 7.4MiB, web 3.9MiB / 128MiB, CPU 0.1% 아래였어요.

### 검증하지 못한 것

- 실제 `fs.inotify.max_user_watches` 소진(`ENOSPC`): 시험 경계(`max_watches`)와 오류 번호 해석(`ENOSPC` → 감시 한도)만 봤고, 호스트 한도를 낮춰 실제로 소진시키지 않았어요(권한이 필요해요).
- 실제 1시간: 변경 없는 1시간은 수동 시계로 주기를 돌려서 봤고, 실제 시계로 1시간을 기다리지 않았어요. 실제 프로세스는 100초만 봤어요.
- SMB·NFS 마운트, 멈춘 마운트에서 감시를 거는 경로(`attach`의 제한 시간 15초)는 시험하지 않았어요. 설정의 폴더 줄에 `watch_note`가 보이는 모양은 브라우저에서 보지 않았고 타입 검사와 빌드만 했어요.
- 독립 검토(`complex-reviewer`)가 짚은 것 중 고친 것: 읽기를 기록하지 못했을 때 모은 작품이 사라지던 것, 빈 폴더 위로 이름을 바꾼 작품의 새 폴더에 감시가 안 걸리던 것(재현해 고쳤고 시험을 더했어요), 읽기가 잠금을 시도하기 전에 알리지 않아 주기가 건너뛰어질 수 있던 것, 감시 못 건 작품이 있을 때 매 주기 폴더 전체를 나열하던 것. 고치지 않은 것은 `남은 일`에 적었어요.
- 감시를 거는 중 폴더가 바뀌는 경쟁, 알림이 몰리는 대량 복사(수천 개)는 시험하지 않았어요.

### 남은 일

- 독립 검토에서 고치지 않은 것: (1) 읽지 못하는 작품이 영구히 있는 폴더(읽기 권한 없음, UTF-8이 아닌 이름)는 매 주기 폴더 전체를 읽어요(오류가 남은 폴더를 주기마다 읽는다는 결정의 비용이고, 작품별로 다시 읽으려면 읽기 결과에 작품별 문제를 담아야 해요). (2) 작품 몇 개만 읽은 기록이 폴더의 `error`를 그 작품 문장으로 바꾸고 `checked_at`을 갱신해요. (3) 알림 큐 넘침 중 `IN_IGNORED`까지 잃은 상태에서 폴더가 지워졌다 다시 생기면 경로가 죽은 감시를 가리킨 채 남을 수 있어요(재현하지 못했어요). (4) 감시를 아예 걸지 못한 폴더(인스턴스 한도, 15초 초과)는 `watch_note`가 없어요. (5) 멈춘 마운트에서 감시 작업이 멈추면 마지막 상태가 '모두 감시 중'으로 남아 안전망까지 읽지 않아요. (6) 아주 큰 폴더를 차가운 디스크에서 나열하면 15초를 넘어 다음 명령 확인 때 다시 시도해요.
- 시즌 폴더 안의 하위 폴더나 `Extras` 안의 변경도 바로 반영하려면 감시 범위를 넓혀야 해요. 지금은 1시간 안전망이 찾아요.
