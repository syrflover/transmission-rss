# 0162 바뀐 구조를 서버에 올려 확인해요

- 상태: 완료
- 출처: [구조 가볍게 하기 명세의 서버 확인](lighter-structure.md#서버-확인), [티켓 목록의 운영](README.md#운영)
- 막는 티켓: [0149](0149-no-worker-in-texts.md)(문구), [0160](0160-test-setup-costs.md)(테스트 고정 비용). 둘을 마치면 코드를 바꾸는 티켓을 모두 마친 거예요.

## 작업

이 변경을 마친 뒤 0140을 기다리지 않고, 따로 서버(j4105)에 올려 확인해요(사용자 결정, 2026-10-21). 릴리스 태그, 이미지 게시, 배포는 사용자가 승인한 뒤에 해요.

- 이 릴리스에는 0.7.0 뒤 master에 들어간 0137–0139·0141·0142의 기능도 함께 들어가요. 그 수정의 서버 확인을 [0143](0143-deploy-feedback-fixes.md)대로 이 배포에서 함께 봐요(사용자 결정, 2026-10-22). 0140에 기대는 `Season 00` 극장판의 확인은 0140을 올릴 때 봐요.
- 이 변경에는 마이그레이션이 있어요. `worker_heartbeat`와 효과별 기록 테이블을 지우고, 실행 도중이던 자막 작업을 `중단됨`으로 바꿔요. 그래서 올리기 전에 서버 DB의 새 복사본으로 마이그레이션을 확인해요([티켓 목록의 운영](README.md#운영)).
- 0.7.0이 끝내지 못한 파일 효과가 서버 DB에 있는지, 마이그레이션하기 전의 복사본에서 아래 쿼리로 세어요. 승인된 교체 계획에 그런 효과가 있으면 업그레이드 뒤 그 계획은 낡은 것이 되고, 그 원래 파일과 보호 복사본은 예전 `.trss/tmp/`에 남아요([0153 결과의 남은 한계](0153-no-effect-records.md#남은-한계)).

  ```sql
  SELECT e.kind, e.state, r.state AS plan_state, count(*)
    FROM subtitle_file_effects e
    LEFT JOIN subtitle_replacements r ON r.id = e.plan_id
   WHERE e.state IN ('intended', 'prepared', 'set_aside', 'held')
   GROUP BY 1, 2, 3;
  ```

- 마이그레이션 뒤의 DB로는 0.7.0이 돌지 않아요. 되돌릴 때는 앱 데이터 폴더의 되돌림 사본과 0.7.0의 Compose 파일로 돌아가요.
- 서버의 Compose는 `trss-web`·`trss-worker` 서비스에서 `trss` 서비스 하나로 바뀌어요. readme의 업데이트 절차를 따라요.
- 서버 명령은 j4105에서 실행할 명령이라고 블록마다 밝혀요.

## 결과

2026-10-22에 사용자 승인을 받아 0.8.0을 서버(j4105)에 올렸어요. 첫 수집 주기에 오류가 없었고, 토렌트 목록은 그대로였고, 컨테이너는 `trss`와 `trss-browser` 둘이에요. 명령 하나의 결과가 이벤트로 화면에 닿는 것도 봤어요.

### 올리기 전 확인

2026-10-22에 서버 DB의 새 복사본으로 이 릴리스의 마이그레이션을 확인했어요. 마이그레이션은 오류 없이 끝났고, 지운 두 테이블 말고는 행 수가 그대로예요. 0.7.0이 끝내지 못한 파일 효과는 없어서, 낡은 교체 계획이나 `.trss/tmp/`에 남는 파일을 정할 것이 없어요. 원자료는 이 PC의 `dev/local/measure/0162/`에 있어요.

14:17에 `dev/compose.sh pull --force`로 서버(j4105)의 DB, 표지, 미디어 파일 이름을 복사했어요. 폴더 2,054개, 파일 13,452개, 표지 75개였고 16초 걸렸어요. 서버의 `trss-web`·`trss-worker`는 복사하는 동안 멈췄다가 다시 시작했어요. 서버가 이 PC 셸의 ssh 키를 받지 않아서, 사용자가 터미널에서 비밀번호를 넣어 실행했어요.

복사본은 0.7.0이 남긴 schema 62이고, `PRAGMA integrity_check`가 `ok`였어요. 작업에 적은 쿼리로 세니 끝나지 않은 파일 효과가 0개였어요. `subtitle_file_effects`의 150행은 모두 `done`이고, 자막 작업 22개도 모두 `done`이에요. 교체 계획 20개는 `done` 13개와 `kept` 7개예요.

마이그레이션은 두 가지로 확인했어요. 먼저 복사본을 `trss-core`의 `Db::open`으로 열기만 하는 임시 프로그램(release, glibc)을 새 사본에 세 번 돌렸어요. 마이그레이션 4개가 51.8–53.4 ms에 끝났고, `user_version`이 이 빌드의 마이그레이션 수인 66이 됐어요. `worker_heartbeat`과 `subtitle_file_effects`가 없어지고 `movie_anissia`가 생겼어요. `integrity_check`는 `ok`였고 `foreign_key_check`는 아무것도 내지 않았어요.

다음으로 `dev/compose.sh up`으로 릴리스와 같은 Dockerfile의 이미지를 빌드해, 이 복사본으로 개발 환경을 띄웠어요. 컨테이너는 `trss`와 `trss-browser`였고, 첫 수집 주기가 `0 failed`로 끝났고 로그에 오류 줄이 없었어요. 라이브러리 API는 작품 92개를, 규칙 API는 규칙 32개와 채널 2개를 돌려줬어요. 상태판의 주기는 멈춤이 아니었고, 이벤트 스트림은 `ready`를 보냈어요. 이 주기 뒤 시즌·회차·파일이 몇 개 늘었는데, 감시 폴더 읽기가 서버의 파일 목록에서 파일 2개를 새로 찾은 것이에요.

릴리스 대상인 musl로 `dev/musl-test.sh`를 `f2881126`에서 돌렸어요. 코드는 `ace59821`과 같아요. 테스트 바이너리 27개에서 3,201개가 통과했고, 실패는 0개, 무시는 12개였어요.

서버의 musl 빌드와 디스크에서 마이그레이션에 걸리는 시간은 측정하지 않았어요. 위의 시간은 이 PC의 glibc release 빌드 값이에요.

### 배포

릴리스 버전은 `0.8.0`이에요(사용자 결정, 2026-10-22). compose 서비스 이름이 바뀌고 마이그레이션 뒤의 DB로는 0.7.0이 돌지 않아서 minor를 올렸어요. readme의 `.env` 예시와 compose 파일의 안내 문구도 `0.8.0`으로 고쳤어요.

사용자 승인을 받아 master와 태그 `0.8.0`을 push했어요. Deploy 워크플로가 7분 37초 만에 `ghcr.io/syrflover/transmission-rss`와 `ghcr.io/syrflover/trss-browser`의 `0.8.0`과 `latest`를 게시했어요.

서버 명령은 사용자가 j4105에서 실행했어요. 확인, 준비, 전환, 관찰의 네 블록이고, 실행하기 전에 0.7.0 상태의 clone과 가짜 `docker`·`sudo`·`python3`로 이 PC에서 돌려 봤어요. 준비 블록은 trss를 멈추지 않고 0.7.0 파일을 남긴 뒤 `git pull`, `TRSS_VERSION=0.8.0`, 이미지 받기를 했어요. 전환 블록은 토렌트 목록을 저장하고 0.7.0 컨테이너 셋을 멈춘 뒤, 데이터 폴더를 복사하고 `docker compose -f docker-compose.trss.yml up -d --remove-orphans`로 올렸어요. 사용자가 붙여 준 것은 관찰 블록의 출력이에요.

되돌림 사본은 서버의 `~/trss-rollback-0.7.0`에 있어요. 앱 데이터 폴더의 사본 `data/`, 0.7.0의 `.env`, `docker-compose.yml`, `docker-compose.trss.yml`, 그때 서버 clone의 커밋을 적은 `commit.txt`예요. 전환 블록은 데이터 폴더를 복사해야 새 컨테이너를 올리도록 이어 놓았고, 새 컨테이너가 떴으므로 복사는 끝났어요.

### 서버에서 본 것

2026-10-22, 0.8.0에서 본 것이에요. 서버 web은 이 PC에서 읽기 전용으로 열었어요.

- 시작: `trss`가 예전 릴리스의 파일 일곱 개(`trss.db.wake`와 잠금 파일 여섯)를 지우고 시작했어요. 시작 로그 앞 20줄에 오류가 없었어요.
- 첫 수집 주기: 14:36:29에 시작해 14:36:32에 끝났어요. 상태판의 문제는 0개였고, 두 채널 모두 정상으로 읽었어요. 규칙 32개, 채널 2개, 작품 92개가 화면 API에 그대로 나왔어요.
- 토렌트 목록: 올리기 전과 첫 주기 뒤 모두 4개이고, `diff`가 같았어요.
- 컨테이너: `docker ps -a --filter name=trss`에 `trss`와 `trss-browser`만 있었고 둘 다 `0.8.0`이었어요. 멈춘 `trss-web`·`trss-worker`도 남지 않았어요.
- 메모리: 시작하고 1분쯤 뒤 `trss` 14.26MiB(한도 384MiB), `trss-browser` 13.86MiB(한도 768MiB)였어요. [0058](0058-server-oom-and-resource-limits.md)에 적었어요.
- 명령과 이벤트: 사용자 승인을 받아 `설정 > 감시 폴더`의 `/downloads/Shows (current)`에서 `다시 확인`을 한 번 눌렀어요. `watch_rescan` 명령이 14:43:33.006에 접수돼 23ms 뒤 `scanned`로 끝났어요. 같은 때 이 PC에서 연 이벤트 스트림에 명령 이벤트 셋과 라이브러리 이벤트 셋이 왔어요. 화면은 명령을 두 번, 감시 폴더를 한 번 다시 읽었고, 누른 뒤 0.25초 안에 `다시 확인했어요.`가 나왔어요.

0143의 확인 가운데 0140에 기대지 않는 것은 [0143의 결과](0143-deploy-feedback-fixes.md#결과)에 적었어요.

큰 폴더 스캔과 표지 올리기 때의 최대 메모리는 이 배포에서 측정하지 않았어요. 0058이 계속 봐요.
