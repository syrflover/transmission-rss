# 0077 대응이 없어 같은 번호로 본 연결이 나중에 정한 대응을 따라요

- 상태: 완료 (2026-10-06)
- 출처: [파일의 회차](../specs/subtitles.md#파일의-회차), [자막의 회차 대응](../specs/library.md#자막의-회차-대응)의 재평가, [0071](0071-mapping-change-reevaluation.md)의 한계에서 사용자가 고른 후속(사용자 결정, 2026-10-06)
- 막는 티켓: [0071](0071-mapping-change-reevaluation.md)(재평가와 재배치)

## 작업

- 출처에 회차 대응이 없어 후보나 파일 이름의 번호를 그대로 쓴 연결을, 사람이 정한 연결(`explicit`)과 따로 표시해요.
- 그 출처의 대응이 나중에 정해지면 이 연결을 다시 평가해요. 보관본과 끝나지 않은 줄은 새 회차로 옮기고, 이미 적용한 파일은 재배치 표로 확인받아요.
- 사람이 배치 확인 표에서 회차를 고친 줄은 `explicit` 그대로예요.
- 이전 빌드가 `explicit`로 남긴 같은 번호 연결은 마이그레이션으로 표시를 바꾸고, 시험을 더해요.

## 완료 기준

| 입력·상태 | 기대 결과 |
| --- | --- |
| 대응이 없는 출처의 후보 3화를 받아 3화에 적용한 뒤, 대응을 −1로 저장 | 보관본은 바로 2화가 되고, 재배치 표에 `3화 적용본 제거 → 2화 적용`이 나와요. 확인하기 전에는 3화 적용본이 그대로예요. 확인하면 2화로 옮겨요. |
| 사람이 표에서 4화로 고친 줄 | 대응을 정해도 4화 그대로이고 재배치가 없어요. |
| 대응이 회차를 그대로 두는 경우(차이 0) | 그 회차의 교체 승인은 낡지 않고, 승인하면 반영돼요. |
| 이전 빌드의 DB | 사람이 확인한 적 없는 후보 작업의 같은 번호 줄과, 그 줄들만 가리키는 보관본이 `same_number`가 돼요. 사람이 확인한 줄, 올리기, 대응이 이미 정해진 출처의 줄은 그대로예요. |

## 결과

### 만든 것 (2026-10-06)

- 연결 값 `same_number`를 더했어요(`Assignment::SameNumber`). 출처가 있는 작업에서 대응이 없어 번호를 그대로 쓴 파일은 이 값과 관찰한 회차의 근거(`basis`)를 가져요.
  후보 작업의 자기 회차는 근거 `anissia`, 묶음의 다른 회차와 올리기·직접 찾기의 파일은 근거 `attachment`예요. 출처를 모르는 파일은 따를 대응이 없어 `explicit`이에요. 이름이 시즌 번호라고 추론한 묶음의 파일(`Numbering::Season`)도 `explicit` 그대로예요.
- 재평가(`relocate::reevaluate_in`)는 정한 대응에서 `mapped`와 `same_number`를 함께 옮기고, 그 출처의 남은 `same_number` 보관본과 끝나지 않은 줄을 `mapped`로 바꿔요. 끝난 줄은 기록이라 그대로예요(구현 결정, 2026-10-06).
  이름표만 바꾸는 이 갱신은 줄의 `updated_at`을 건드리지 않아요. 같은 보관본을 가리키는 줄 가운데 무엇을 고를지가 `updated_at` 순서를 따르기 때문이에요.
- 교체 계획의 증거 검사(`replace::changed`)는 계획의 `same_number`가 같은 회차·같은 근거의 `mapped`가 된 경우를 같은 대상으로 봐요. 그래서 대응이 회차를 그대로 두면 이미 한 승인이 유지돼요(구현 결정, 2026-10-06).
- 배치 확인 표에서 회차를 그대로 둔 줄은 계획의 연결(`same_number`)을, 고친 줄은 `explicit`를 가져요(0071에서 바뀐 것 없음). 사용자 결정의 "표에서 고친 줄은 그대로"를 이렇게 읽었어요.
- **마이그레이션 60**(`same_number.sql`, 재생성): `subtitle_stored`·`subtitle_job_plan`·`subtitle_replacements`의 CHECK에 `same_number`를 더하고, 색인과 트리거를 다시 만들어요. 보관본의 CHECK는 `same_number`에도 근거와 출처를 요구해요.
  이전 빌드가 `explicit`로 남긴 같은 번호 연결은 사람이 관여하지 않은 것만 바꿔요. 조건은 넷이에요. 후보 작업(`pick`·`auto`)이고 출처가 있어요. 배치 확인 단계가 없어요(어떤 범위의 확인이든 이 단계를 남겨요). 회차가 후보의 회차 번호와 같아요. 출처에 정한 대응이 지금 없어요.
  보관본은 가리키는 줄이 모두 바뀐 경우에만 바꾸고, 그 줄의 교체 계획도 같은 연결로 다시 적어요.
- 문서: [파일의 회차](../specs/subtitles.md#파일의-회차)·[배치 확인](../specs/subtitles.md#배치-확인), [자막의 회차 대응](../specs/library.md#자막의-회차-대응), [보관 관계 필드](../specs/settings.md#보관-관계-필드)의 `mode: same_number`, [용어집](../glossary.md)의 `같은 번호로 본 연결`, 작업 API 문서와 웹 타입(`placementTypes.ts`).

### 검증한 것

| 완료 기준 | 근거 |
| --- | --- |
| 대응이 없는 출처의 후보 3화를 적용한 뒤 대응을 −1로 저장 | `a_link_made_by_the_same_number_follows_the_mapping_decided_later`에서 보관본은 `same_number`·3화에서 `mapped`·2화가 되고, 재배치 작업 하나가 3화 적용본 제거를 계획해요. 확인 전에는 3화 적용본이 그대로이고, 확인하고 실행하면 2화로 옮겨요. 후보 작업의 끝난 줄은 `same_number`로 남아요. |
| 사람이 표에서 4화로 고친 줄 | `an_episode_a_person_chose_for_a_source_with_no_mapping_stays`: 이름(4)과 후보(3)가 달라 물은 줄을 사람이 4화로 정하면 `explicit`이고, 대응을 정해도 4화 그대로이며 재배치가 없어요. |
| 대응이 회차를 그대로 둠(차이 0) | `an_approval_holds_when_the_mapping_keeps_the_same_number`: 교체 승인을 기다리던 줄과 보관본이 `mapped`가 되어도 계획은 낡지 않고, 승인하면 3화가 바뀌어요. |
| 이전 빌드의 DB | `a_candidates_file_put_on_its_own_number_follows_the_mapping_after_the_migration`: 확인하지 않은 후보 작업의 자기 회차 줄만 `same_number`가 돼요. 다른 회차 줄, 확인한 작업, 정한 대응이 있는 출처, 올리기, 확인한 줄도 가리키는 보관본은 그대로예요. 그 줄의 교체 계획도 같이 바뀌어요. `the_same_number_migration_keeps_every_index_and_trigger`는 재생성 전후의 색인·트리거 이름이 같음을 봐요. |

그 밖의 시험도 있어요.

- 배치 단위 시험: 출처가 있으면 `same_number`·`anissia`, 없으면 `explicit`(`a_source_without_a_mapping_is_the_same_number`). 제작자를 아는 올리기는 `same_number`·`attachment`예요(`an_upload_of_a_creator_without_a_mapping_is_placed_until_one_is_decided`). 제작자를 모르는 올리기는 `explicit`이에요.
- 변이 12개를 하나씩 넣으면 모두 시험이 실패해요(`probe-out/same-number-mutations.txt`). 재평가가 `same_number`를 보지 않음, 보관본이나 줄을 `mapped`로 바꾸지 않음, 교체 증거 검사를 좁힘, 후보를 다시 `explicit`로 둠, 백필의 다섯 조건, 교체 계획을 다시 적지 않음, 다시 만든 표의 색인 누락이에요. S11(다른 줄이 사람의 것인 보관본)은 처음에 살아남아 시험 데이터를 보강한 뒤 잡혔어요. S12는 검토 지적 1을 고친 뒤 더했어요.
- 개발 DB(2026-10-06, 마이그레이션 59)의 복사본에 외래 키를 끈 트랜잭션으로 마이그레이션 60을 돌렸어요. 끊긴 참조 0, `integrity_check` `ok`였어요. 계획 줄 24개, 보관본 14개, 교체 계획 6개가 `same_number`가 됐고 빠졌던 색인도 생겼어요. `Db::open`의 실제 실행 경로가 아니라 `sqlite3`로 같은 순서를 흉내 낸 것이고, 개발 DB 자체에는 적용하지 않았어요.

### 독립 검토 (2026-10-06)

`stora:reviewer`가 마이그레이션의 스키마 동등성, 백필이 사람의 선택을 건드리는지, 재평가와 교체 증거 검사를 봤어요. 마이그레이션 1–59를 적용한 스키마와 60 뒤의 스키마를 비교했어요.

- 고친 것:
  - 지적 1: `subtitle_job_plan_by_file` 색인(마이그레이션 56)이 재생성에서 빠졌어요. 다시 만들고 색인·트리거 이름을 비교하는 시험을 더했어요. 개발 DB에는 이 색인이 처음부터 없어서, 그 스키마를 본으로 삼은 제가 놓쳤어요.
  - 지적 5: 이름표만 바꾸는 갱신이 `updated_at`을 바꿔 같은 보관본의 줄 순서를 흔들 수 있었어요. 이제 바꾸지 않아요.
- 한계로 남긴 것: 지적 2·3·6(아래 한계).
- 사용자 결정의 범위로 둔 것: 지적 4(배치 확인 표를 그대로 둔 줄은 `same_number`로 남아 대응을 따라요). 결정이 "고친 줄"만 그대로 둔다고 했고, 적용본은 재배치에서 다시 확인받아요.
- 검토자가 확인한 것: 세 표는 CHECK 말고 열·순서·기본값·외래 키·`ON DELETE`·`WITHOUT ROWID`·트리거가 같고, 다른 트리거·뷰가 세 표를 참조하지 않아요. 새 보관본 CHECK는 기존 값에 대해 이전과 같아요. 교체 증거 검사는 회차·근거·보관본·자산·영상을 여전히 비교해서 다른 대상에 승인을 쓰지 않아요.

### 한계

- 계획을 쓰는 트랜잭션(`records::add_plan`)은 대응 버전을 다시 보지 않아요. 대응이 정해지기 전에 만든 계획을 정해진 뒤에 쓰면 그 줄은 다음 대응 저장까지 `same_number`로 남아요. 0071부터 `mapped` 줄에도 있는 경합이에요.
- 작품을 합칠 때 대응을 합치는 쓰기(`merge_subtitle_mappings`)는 다시 평가하지 않아요(0071과 같아요). 합친 뒤 정해진 대응이 있어도 `same_number`는 다음 대응 저장 때 바뀌어요(검토 지적 6).
- 백필은 후보 작업의 자기 회차 줄만 바꿔요. 묶음의 다른 회차 줄(이전 빌드가 `explicit`로 남김)은 `anissia_episode`가 없고, 이름이 시즌 번호라고 추론한 `explicit` 줄과 데이터로 구별되지 않아 그대로 둬요. 같은 파일이라도 업그레이드 뒤에 받으면 대응을 따르고, 전에 받았으면 따르지 않아요(검토 지적 2). 올리기·직접 찾기의 옛 줄도 사람이 확인한 표의 줄이라 그대로예요.
- 백필 뒤에 계획 줄은 `same_number`인데 그 보관본은 `explicit`일 수 있어요. 다른 `explicit` 줄이 같은 보관본을 가리키는 경우예요. 대응이 정해지면 끝나지 않은 줄만 새 회차로 가고 보관본은 그대로라, 줄과 보관본의 회차가 달라질 수 있어요. 교체 증거 검사는 이를 낡은 것으로 보아 안전하게 멈춰요(검토 지적 3).
- 사람이 배치 확인 표를 고치지 않고 확인한 같은 번호 줄은 대응을 따라요. 이미 적용한 파일은 재배치에서 다시 확인받지만, 보관만 한 파일은 묻지 않고 옮겨요(검토 지적 4, 사용자 결정의 범위).
- 대응이 미정인 출처를 정해 보지 않고 둔 경우는 0071의 재평가가 이미 아무것도 옮기지 않아서, 따로 시험하지 않았어요.
