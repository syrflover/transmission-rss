# 0076 여덟 경로의 실제 묶음이 적용본까지 가는지 확인해요

- 상태: 완료
- 출처: 목표 4의 [완료 조건](README.md#4-보관적용과-교체-승인) 1, [출처별 다운로드](../specs/subtitles.md#출처별-다운로드)에서 목표 4로 넘어온 "적용까지 이어지는지"의 확인
- 막는 티켓: [0065](0065-archive-extraction.md)(압축 묶음), [0066](0066-placement-confirmation.md)(올리기·직접 찾기)

## 작업

목표 4를 마무리하는 관찰이에요. 개발 환경(실제 외부 사이트, 서버 DB 복사본)에서 해요(사용자 결정, 2026-10-04).

- 목표 3에서 받아 둔 여덟 경로의 작업이 다시 받지 않고 적용본까지 가는지 봐요. 경로는 erulabo, Blogger·Drive 개별 파일, Drive 회차 ZIP, Tistory 일반 첨부, Tistory WinPNG, Naver, 직접 찾기, 올리기예요. 받아 둔 작업이 없는 경로는 새로 받아요.
- 후보 작업은 확인 없이, 올리기와 직접 찾기는 배치 확인 뒤에 적용돼야 해요.
- 영상이 없는 회차에는 시험용 영상 파일을 둬요.
- 경로마다 작업 ID, 받은 파일, 보관본·적용본 경로, 거친 단계를 기록해요.

### 찾은 결함

- **직접 찾기의 승인이 끝없이 낡음**(고침, `a24514b`): 직접 찾기의 1화 줄(첨부 근거)이 Drive 회차 ZIP 후보가 남긴 같은 바이트의 보관본(Anissia 근거)을 함께 썼어요. 교체 계획은 보관본이 계획의 연결을 가져야 하므로, 승인할 때마다 `회차 대응이 바뀌었어요`로 낡고 다시 비교를 만들었어요(v1–v3).
  - 사용자가 근거까지 같아야 보관본을 함께 쓰도록 정했어요(2026-10-06). [자막 명세](../specs/subtitles.md)의 보관 절에 규칙을 적었어요.
  - 고친 뒤에는 v3를 승인하자 한 번 낡고, 줄이 제 연결의 새 보관본(`9dfd551a`, 원래 보관본과 같은 보관 시각)으로 옮겨졌어요. v4를 승인하자 적용됐어요.
  - 시험: `an_upload_of_bytes_a_pick_stored_keeps_its_own_link_and_is_applied_once_approved`, `a_row_on_a_stored_subtitle_of_another_link_is_given_its_own_before_it_is_compared`.
- **PC를 다시 켜면 열린 교체 계획이 `영상이 바뀌었어요`로 낡음**(고치지 않음): 10-05에 만든 Drive 회차 ZIP과 erulabo의 계획이 10-06 승인 때 한 번씩 낡았어요.
  - 계획은 영상을 `장치:inode`로 기억해요. 영상 파일은 그대로였어요(inode 6574705). btrfs가 다시 켤 때 익명 장치 번호를 바꿔 47이 46이 됐어요.
  - 다시 만든 계획은 승인하면 반영됐어요. 사람이 한 번 더 승인해야 하는 비용이라, 장치 번호를 영상이 바뀐 근거로 보지 않게 하는 일은 따로 남겼어요.
