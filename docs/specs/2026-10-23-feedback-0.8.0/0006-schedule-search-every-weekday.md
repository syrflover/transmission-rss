# 0006 편성표의 `작품 찾기`가 Anissia 검색으로 모든 요일에서 찾아요

- 상태: 완료
- 출처: [명세의 편성표 검색](spec.md#편성표-검색), [명세의 작품 찾기의 포커스](spec.md#작품-찾기의-포커스), 사용자 피드백 2·3번(2026-10-23)
- 막는 티켓: 없음

## 작업

편성표에서 작품을 고르는 칸(`web/src/screens/collect/subs/add/PickAnime.tsx`)은 Anissia의 요일별 편성표를 한 요일씩 받아요. `작품 찾기`는 받아 둔 그 요일 목록 안에서만 걸러요. 그래서 다른 요일의 작품을 찾으려면 요일 탭을 바꿔야 하고, 결과에는 요일이 없어요. 이 칸은 구독 화면, 규칙 상세의 연결, 작품 상세 시즌 연결 창의 `편성표` 탭이 함께 써요.

사용자가 정한 것은 다음과 같아요(2026-10-23).

- `작품 찾기`는 쓴 검색어로 Anissia 전체 목록을 찾고, `종영`을 뺀 작품을 모든 요일에서 보여줘요. 결과마다 요일을 보여줘요.
- 한국어 제목으로만 찾아지는 것은 감수해요. 모든 요일 편성표를 받아 거르는 안(처음 18초쯤)과 하루 한 번 저장하는 안은 고르지 않았어요.

검색에는 작품 상세의 연결 창이 쓰는 Anissia 전체 목록 검색(`trss-anissia`의 `search_anime`, `/anime/list/<page>?q=`, 30개씩)을 써요. 그 창의 검색 API는 작품과 시즌에 매여 있으므로, 구독 화면에서도 쓸 수 있는 검색 API가 필요해요. 2026-10-23 조회에서 검색 결과는 편성표와 같은 필드를 줬어요. `신작` 작품은 `week` 8, 상태는 `ON`·`OFF`·`END`예요.

구독 요청은 지금 작품을 고른 요일을 함께 보내요. 검색으로 고른 작품은 검색어와 페이지를 보내고, 서버는 그 목록에 작품이 있는지 확인해요. 작품 상세의 연결 창이 쓰는 확인 방식과 같아요.

검색은 Enter나 `검색` 버튼을 누를 때, 또는 입력을 멈추고 잠시 지났을 때 해요. 글자마다 Anissia에 묻지 않으려는 구현 결정이에요. Anissia 요청 간격(2초)과 `429` 대기는 다른 Anissia 요청과 함께 지켜요.

2번(글자를 모두 지우면 포커스가 풀림)은 재현하지 못했어요. 사용자는 PC의 Firefox와 iOS 홈 화면 앱을 쓰고, 어느 쪽에서 봤는지는 기억하지 못해요. 이 칸을 다시 만들면서 포커스가 유지되는지 확인해요. iOS는 [0011](0011-deploy-and-check-on-server.md)에서 봐요.

## 완료 기준

- [x] 구독 화면에서 검색어를 쓰면 모든 요일에서 찾은 작품이 나오고, `종영`인 작품은 빠져요. 검색어를 지우면 고른 요일 탭의 편성이 다시 보여요. 규칙 상세의 연결과 작품 상세 시즌 연결 창의 `편성표` 탭도 같아요.
- [x] 결과의 줄마다 요일(`일`–`토`, `기타`, `신작`)이 방영 시각, 시작일, 종영일과 함께 보이고, `구독 중`과 `결방` 표시는 지금과 같아요.
- [x] 30개를 넘는 결과는 `결과 더 보기`로 이어 받아요. 검색칸 옆에 한국어 제목으로 찾아진다는 안내가 있어요.
- [x] 검색이 실패하면 까닭과 재시도가 보이고, 요일 탭으로 고르는 길은 그대로 쓸 수 있어요.
- [x] 검색으로 고른 작품으로 구독을 만들 수 있고, 서버는 요청이 말한 목록에 없는 작품을 거절해요. 가짜 Anissia로 API 테스트를 해요.
- [x] 검색 결과를 요일과 함께 만드는 부분과 `종영`을 빼는 부분을 테스트로 확인해요.
- [x] `작품 찾기`에 글자를 썼다가 백스페이스로 모두 지워도 입력칸이 포커스를 잃지 않아요. 개발 환경의 Chromium에서 확인하고, PC의 Firefox에서도 확인해요(사용자에게 부탁하거나 Firefox를 띄울 수 있으면 직접). 원인을 찾으면 결과에 적고, 찾지 못하면 확인한 환경을 적어요.
- [x] [RSS 수집 명세의 방영작 구독](../../requirements/collection.md#방영작-구독)과 [라이브러리 명세의 작품 연결과 제외](../../requirements/library.md#작품-연결과-제외)에서 편성표 고르기를 고치고, 검증 표의 행을 고쳐요.
- [x] `cargo test --workspace`, `npm test`, `npm run typecheck`가 통과해요.

## 결과

### 만든 것

`GET /api/anissia/search?q=&page=`가 생겼어요. 서버가 Anissia 전체 목록에서 그 쪽(30개)을 받아, 편성표와 같은 줄(요일, 방영 시각, 시작일, 종영일, 방영 상태, 구독한 규칙)로 만들고 `종영`인 작품을 빼요. `종영`은 편성표의 `종영` 표시와 같은 판정이라, Anissia가 `END`로 준 작품과 종영일이 지난 작품이에요. 순서는 Anissia가 준 그대로이고, 다음 쪽이 있는지도 함께 줘요.

`작품 찾기` 칸은 요일 탭 아래에 늘 있어요. 글자를 쓰고 0.7초 멈추거나 Enter나 `검색`을 누르면 이 API로 찾고, 결과의 줄은 `수요일 22:00 · 10월 7일 시작`처럼 요일로 시작해요. 찾는 동안에는 눌린 요일 탭이 없고, 요일 탭을 누르거나 검색어를 지우면 그 요일의 편성으로 돌아가요. 검색이 실패하면 서버가 준 까닭과 `재시도`를 보여주고, 요일 탭은 그대로 쓸 수 있어요. 구독 화면, 규칙의 `편성표와 연결`, 작품 상세 시즌 연결 창의 `편성표` 탭이 이 칸을 함께 써요.

고른 작품은 고른 곳(요일, 또는 검색어와 쪽)과 함께 넘어가고, 구독(`POST /api/subscriptions`)과 `편성표와 연결`(`POST /api/rules/{id}/subscription`) 요청이 그것을 보내요. 서버는 시즌 연결 창이 이미 쓰던 방식대로 그곳을 Anissia에서 다시 읽어, 작품이 있을 때만 거기서 받은 정보로 구독해요. 구독, `편성표와 연결`, 시즌의 Anissia 연결, 극장판 연결이 이 확인을 함께 쓰도록 `crates/trss/src/web/anissia_lists.rs`로 옮겼고, 새 검색 요청도 같은 곳의 검색을 써요.

### 정한 것

- `종영`은 서버가 쪽마다 빼요. 그래서 한 쪽에 남는 작품이 없을 수 있고, 화면은 그때 `결과 더 보기`로 더 찾으라고 알려요. 다음 쪽까지 서버가 대신 읽으면 Anissia 요청 간격(2초)만큼 답이 늦어지기 때문이에요(구현 결정).
- 결과는 요일순으로 다시 늘어놓지 않고 Anissia의 순서(새 작품부터)를 따라요. 쪽마다 받으므로, 다시 늘어놓으면 쪽을 이어 받을 때 순서가 섞여요(구현 결정).
- 구독 화면에서 검색으로 작품을 고른 뒤 첫 단계로 돌아오면 그 작품의 요일 탭이 열려요(구현 결정).

### 포커스

글자를 모두 지우면 포커스가 풀리는 문제는 재현하지 못했고, 원인도 찾지 못했어요. 2026-10-23에 이 PC에서 확인한 환경은 다음과 같아요.

- 내장 브라우저(Chromium 152)에서 바꾸기 전 칸(개발 환경)에 `abc`와 `zzzz`를 쓰고 백스페이스로 지워도 포커스가 남았어요.
- headless Firefox 158(새 프로필, WebDriver BiDi로 키 입력)에서 서버의 0.8.0 칸에 `abc`를 쓰고 지워도 포커스가 남았어요.
- 같은 Firefox에서 바꾼 칸(개발 환경)에 `abc`, `마녀`를 쓰고 지워도, 검색 결과가 뜬 뒤 지워 목록이 편성으로 바뀌어도 포커스가 남았어요.

바꾸기 전 칸은 그 요일의 편성을 받아 둔 동안에만 있었어요. 받아 둔 편성이 지워지면 칸이 다시 만들어져 포커스를 잃을 수 있는데, 글자를 지우는 것과 이어지는 길은 찾지 못했어요. 바꾼 칸은 편성과 상관없이 늘 있어요. iOS 홈 화면 앱은 [0011](0011-deploy-and-check-on-server.md)에서 봐요.

### 테스트

2026-10-23에 c61bcfd1 위의 작업 트리(0005 커밋 fa584db9 포함)에서 `cargo test --workspace`가 모두 통과했어요(3,225개 통과, 12개 무시, 테스트 바이너리 27개의 합 37.73초, `dev/measure/when-quiet.sh`로 다른 빌드가 없을 때 측정했어요). `cargo clippy --workspace --all-targets`에 경고가 없고, `npm test`(318개)와 `npm run typecheck`도 통과했어요. 원본 로그는 이 PC의 `dev/local/measure/feedback-0.8.0-0006/`에 있어요.

- `trss` `src/web/subscriptions_api/tests.rs` `a_search_lists_the_anime_of_every_week_that_have_not_ended_with_their_week`는 가짜 Anissia의 전체 목록에서 요일과 방영 상태가 붙는 것, Anissia가 끝낸 작품과 종영일이 지난 작품이 빠지는 것, 쪽 번호와 다음 쪽을 겨눠요. 종영을 빼는 줄을 지운 코드에서는 `[3320, 2969, 3002, 3005]`가 나와 실패했어요.
- 같은 파일 `a_search_needs_its_text_and_a_page_in_range_and_its_failure_leaves_the_weeks`는 검색어와 쪽 번호의 거절, Anissia 실패의 502와 문장, 그 뒤에도 편성표가 답하는 것을 겨눠요.
- 같은 파일 `subscribing_to_an_anime_found_by_a_search_checks_it_against_that_page`와 `rule_detail::a_rule_is_linked_to_an_anime_found_by_a_search_checked_against_that_page`는 검색으로 고른 작품의 구독과 연결, 그 쪽에 없는 작품과 고른 곳이 없거나 둘인 요청의 거절, 저장되는 정보가 검색에서 받은 것인지를 겨눠요.
- 시즌 연결의 검색 확인은 옮긴 코드를 그대로 쓰고, 기존 `trss` `src/web/seasons_anissia_api/tests.rs`가 통과했어요.

### 개발 환경 확인

2026-10-23에 서버 DB 사본(2026-10-22에 받은 것)으로 띄운 개발 환경을 이 작업 트리로 다시 만들어, 내장 브라우저와 실제 Anissia로 확인했어요.

- `마녀`로 찾자 Anissia가 준 19편 가운데 `END` 14편을 뺀 5편이 `수요일 22:00`, `월요일 21:30`, `기타`, `신작`과 함께 떴고, 구독 중인 작품에 `구독 중`이 붙었어요.
- `는`은 첫 쪽에 4편이 떴고, `결과 더 보기`로 다음 쪽의 3편이 더해졌어요.
- `마녀와 용병`을 검색으로 골라 subsplease.org 채널에 제목 대기 구독을 만들었어요. 구독에 저장된 Anissia 정보는 3501, `신작`(8), 시작 `2027-04`였어요. 이 구독은 개발 환경에 남겨 뒀어요.
- 규칙 `Mushoku Tensei/Season 03`의 `편성표와 연결`에서 `무직`으로 찾은 작품을 고르자 `연결`이 켜졌고, `Kore Kaite Shine` 시즌 연결 창의 `편성표` 탭에서 `마녀`로 찾은 작품을 고르자 `고른 작품: 마녀와 용병`과 `연결`이 켜졌어요. 둘 다 저장하지 않았어요.
- 390px 폭에서 가로로 넘치지 않았고, `검색` 버튼이 입력칸 옆에 있었어요.
- 참고(가짜 출처): 페이지의 `fetch`를 바꿔 검색 답을 502로 넣자 까닭과 `재시도`가 떴고, `수` 탭을 누르자 검색어가 비고 수요일 편성 7편이 보였어요.
