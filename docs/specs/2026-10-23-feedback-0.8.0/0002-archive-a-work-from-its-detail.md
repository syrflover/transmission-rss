# 0002 작품 상세에서 작품을 보관 폴더로 옮겨요

- 상태: 완료 (2026-10-23, 테스트와 개발 환경으로 확인. 서버 확인은 [0011](0011-deploy-and-check-on-server.md)에서 해요. 아래 "결과")
- 출처: [명세의 보관](spec.md#보관), [보관 ADR](../../adr/0022-archiving-deletes-rules-and-follows-the-folder.md), 사용자 피드백 9·11번(2026-10-23)
- 막는 티켓: 없음

## 작업

작품 상세에 `보관 폴더로 옮기기`를 만들어, 규칙이 없어도 작품을 보관할 수 있게 해요. 사용자가 정한 것은 다음과 같아요(2026-10-23).

- 그 작품 폴더에 받는 규칙이 있으면 수집 중인 것과 `멈춤`인 것을 모두 보여주고, 확인받은 뒤 함께 지우고 옮겨요.
- 옮기지 못하면 까닭과 `다시 옮기기`를 작품 상세에 보여줘요. 규칙은 이미 지워졌으므로 재시도할 곳은 작품이에요.

지금의 폴더 이동은 규칙에 매인 명령(`rule_archive`, 방향 `archive`·`restore`)이에요. 이 티켓은 작품 폴더를 대상으로 하는 이동 명령을 만들고, 규칙을 지운 뒤에 그 명령을 접수해요. 새 회차가 옛 자리에 들어오지 않게, 규칙을 먼저 지우고 폴더를 옮겨요. 실제 이동(Transmission의 위치 옮기기, `.trss/`, 같은 이름 폴더의 합침과 겹침 검사, 같은 파일시스템의 이름 바꾸기, 중단 뒤 이어 하기)은 지금의 [보관과 복원의 폴더 이동](../../requirements/collection.md#보관과-복원의-폴더-이동)의 코드를 그대로 써요. [0003](0003-archive-deletes-the-rule.md)의 규칙 보관도 이 명령으로 폴더를 옮겨요.

`그 작품 폴더에 받는 규칙`은 저장 폴더의 첫 부분이 그 작품 폴더인 규칙이에요(모든 채널). 동작은 수집 폴더 바로 아래의 작품이고 보관 폴더가 정해져 있을 때만 보여요. 옮길 곳이 없으면 두지 않는다는 것은 명세가 정한 구현 결정이에요.

## 완료 기준

- [x] 작품 상세에서 `보관 폴더로 옮기기`를 누르면, 그 작품 폴더에 받는 규칙을 채널, 저장 폴더, 상태와 함께 보여주는 확인이 떠요. 받는 규칙이 없으면 옮긴다는 확인만 떠요. 확인하면 규칙을 모두 지운 뒤 이동 명령을 접수하고, 취소하면 아무것도 바뀌지 않아요. API 테스트로 확인해요.
- [x] 이동이 끝나면 작품 폴더가 보관 폴더에 있고, 작품 ID, 시즌 연결, 표지 선택, 제작자 지정, 수집 이력이 그대로예요. Transmission의 그 작품 토렌트는 새 위치를 가리켜요. 지금의 보관 이동 테스트와 같은 가짜 Transmission으로 확인해요.
- [x] 겹치는 파일, 다른 파일시스템, Transmission이 답하지 않음으로 옮기지 못하면, 작품 상세가 그 까닭과 `다시 옮기기`를 보여줘요. 겹친 파일을 치운 뒤 `다시 옮기기`가 옮겨요. 옮기는 동안에는 `보관 폴더로 옮기는 중이에요`를 보여줘요.
- [x] 옮기는 동안 trss가 멈추면 다음 실행에서 남은 것만 이어 옮겨요. 테스트로 확인해요.
- [x] 수집 폴더 밖의 작품(보관 폴더나 다른 감시 폴더의 작품)과, 보관 폴더를 정하지 않은 설치에서는 동작이 보이지 않아요.
- [x] 개발 환경(서버 DB 사본)에서 작품 하나를 옮겨 보고, 확인 창, 이동 상태 문장, 옮긴 뒤의 작품 상세를 결과에 적어요.
- [x] [라이브러리 명세의 작품 상세 화면](../../requirements/library.md#작품-상세-화면)과 [RSS 수집 명세의 보관과 복원의 폴더 이동](../../requirements/collection.md#보관과-복원의-폴더-이동)에 이 동작을 적고, 검증 표의 행을 더해요.
- [x] `cargo test --workspace`, `npm test`, `npm run typecheck`가 통과해요.

## 결과

### 만든 것

작품 폴더를 대상으로 하는 이동 명령 `work_archive`를 만들었어요(`trss-collect`의 `commands/work_archive.rs`). 페이로드는 작품 폴더 이름 하나이고, 명령의 대상(subject)도 그 이름이라 한 작품 폴더에는 열린 이동이 하나뿐이에요. worker는 `rule_archive`처럼 두 폴더의 그 작품 폴더에 쓰기 차례를 잡고 토렌트 관문을 쥔 채, `rule_archive`의 `move_folder`를 그대로 불러요. 그래서 Transmission의 위치 옮기기, `.trss/`, 합침과 겹침 검사, 같은 파일시스템의 이름 바꾸기, 라이브러리의 작품 잇기, 중단 뒤 이어 하기가 규칙 보관과 같아요. 이름이 한 단계의 보통 이름이 아니면(`..`, `/`가 든 이름, 빈 이름) 아무것도 하지 않고 실패로 끝나요.

웹은 `POST /api/library/works/{id}/archive`로 확인 창이 보여 준 규칙과 그 버전을 받아요. 지금 그 작품 폴더에 받는 규칙과 같을 때만 그 규칙을 모두 지우고 이동 명령을 접수하는데, 둘은 한 트랜잭션이라 함께 되거나 함께 안 돼요(`work_archive::accept_deleting`). 다르면 아무것도 지우지 않고 `409`와 지금의 규칙 목록을 돌려줘요. 작품 상세 응답에는 `archive`(`available`과 보여줄 이동 명령)를 더했고, 규칙에 `version`을 더했어요.

화면은 작품 상세의 `수집` 카드에 `보관 폴더로 옮기기`를 두고, 누르면 카드 안에 확인이 펼쳐져요. 이동 상태 문장은 카드가 접혀 있어도 보이게 머리 아래에 둬요.

### 정한 것

- 확인은 모달이 아니라 그 자리에서 펼쳐요. 규칙 상세의 `삭제` 확인과 같은 방식이에요(구현 결정).
- 확인과 이동 사이에 새로 생긴 규칙은 수집 중일 때만 이동을 막아요. `멈춤`인 규칙은 [0003](0003-archive-deletes-the-rule.md)의 사용자 결정처럼 막지 않아요. 다시 켜면 작품 폴더를 수집 폴더로 먼저 옮기기 때문이에요.
- 규칙 삭제와 명령 접수는 한 트랜잭션이에요. 명령 저장소에 명령과 함께 다른 행을 같은 트랜잭션에서 쓰는 `CommandStore::accept_with`를 더했고, 명령의 ID가 이미 있거나 그 작품 폴더의 이동이 열려 있으면 아무것도 지우지 않아요. 처음에는 두 단계로 만들었는데, 독립 리뷰가 둘 사이에서 접수가 실패하면 규칙만 지워지고, 같은 요청을 다시 보내면 그 요청이 지운 규칙 때문에 `규칙이 바뀌었어요`가 나온다고 짚었어요(구현 결정).
- 작품 상세의 규칙 목록은 저장 폴더를 글자대로 읽어 정해요. `Other/../X`도 `X`에 받는 규칙으로 보이고, 확인하면 함께 지워요. 이동 명령이 폴더를 막는 규칙을 이렇게 읽으므로, 확인에 보이지 않은 규칙이 이동을 막아 작품 상세에서 풀 수 없는 일이 없게 맞췄어요(구현 결정).
- 끝난 이동 가운데 `failed`와 `kept`만, 작품이 수집 폴더에 있고 그 작품 폴더에 받는 규칙이 없는 동안 작품 상세를 다시 열어도 보여요. 규칙이 다시 생기면 지난 결과가 지금의 작품을 말하지 않으므로 숨겨요(구현 결정).
- 옮기지 못한 문장은 이동이 적은 까닭만 보여주고 덧붙이지 않아요. 까닭이 이미 무엇을 옮겼고 무엇을 하고 `다시 옮기기`를 누르라고 말하기 때문이에요. 개발 환경에서 처음 본 문장은 그 뒤에 `까닭을 해결한 뒤 다시 옮겨 주세요.`를 붙여 같은 말을 되풀이해서 뺐어요.

### 테스트

2026-10-23에 feaacd98 위의 작업 트리에서 `cargo test --workspace`가 모두 통과했어요(3,219개 통과, 12개 무시, 테스트 바이너리 합 36.86초). `npm test`(311개)와 `npm run typecheck`도 통과했어요.

- `trss-collect` `commands/work_archive/tests.rs`는 명령의 규칙을 겨눠요. 토렌트와 함께 옮기고 작품 ID와 시즌 연결이 남는 것, 수집 중인 규칙은 막고 `멈춤`은 막지 않는 것, 수집·보관 폴더가 없을 때의 까닭, 겹치는 파일이면 아무것도 옮기지 않고 치운 뒤 새 명령이 옮기는 것, Transmission이 늦으면 다음 차례가 남은 것을 옮기는 것, 폴더 하나를 가리키지 않는 페이로드예요.
- `trss` `src/web/library_work_api/archive/tests.rs`는 API를 겨눠요. 동작이 보이는 작품, 보여 준 규칙(`..`로 그 작품 폴더에 닿는 규칙 포함)을 지우고 한 번만 접수하는 것, 다른 규칙 목록이면 아무것도 지우지 않는 것, 옮길 수 없는 작품의 거절, 지난 결과를 보여주는 조건이에요.
- `trss` `tests/it/archive_move.rs`의 `a_work_moved_from_its_detail_loses_its_rules_at_once_and_the_worker_moves_its_folder`와 `a_work_move_stopped_after_transmission_moved_finishes_the_rest_on_the_next_run`은 진짜 worker로 끝까지 돌리고, 도중에 멈춘 worker의 다음 실행이 남은 것만 옮기는 것을 겨눠요.
- `trss-collect` `store/channels/delete_rule_tests.rs` `several_rules_go_together_or_none_does`는 여러 규칙을 모두 지우거나 하나도 지우지 않는 것을 겨눠요.
- `trss-collect` `commands/work_archive/tests.rs` `the_rules_are_deleted_with_the_stored_move_or_not_at_all`과 `trss-core` `commands/tests.rs` `a_write_with_the_command_is_stored_with_it_or_not_at_all`은 규칙 삭제와 명령 접수가 함께 되거나 함께 안 되는 것, 이미 있는 ID나 열린 이동이면 아무것도 지우지 않는 것을 겨눠요.
- `web` `src/screens/library/detail/archiveNotice.test.ts`는 이동 상태 문장과 `다시 옮기기`가 보이는 조건을 겨눠요.

표지 선택과 제작자 지정이 남는 것은 이동이 작품 ID를 그대로 두는 것으로 확인했어요. 작품 잇기가 그것들을 남기는 것은 `trss-library`의 기존 테스트가 겨눠요. 다른 파일시스템과 답하지 않는 Transmission의 경우는 `rule_archive`와 같은 이동 코드라 `rule_archive/work_folder/tests.rs`의 테스트가 겨누고, 이 명령으로 따로 돌리지 않았어요.

### 개발 환경 확인

2026-10-23에 서버 DB 사본(2026-10-22에 받은 것)으로 띄운 개발 환경에서, 이 작업 트리로 이미지를 다시 만들어 확인했어요. 확인 뒤 데이터, 미디어, Transmission 설정은 확인 전의 백업으로 되돌렸어요.

- `Sekai Saikyou no Majo, Hajimemashita`(수집 폴더, 수집 중인 구독 규칙 1개)에서 `보관 폴더로 옮기기`를 누르자 `규칙 1개를 지우고 보관 폴더로 옮길까요?`와 규칙(`수집 중`, `subsplease.org`, `Sekai Saikyou no Majo, Hajimemashita/Season 01`)이 펼쳐졌어요. `취소`하면 규칙과 작품이 그대로였어요.
- 확인하자 `보관 폴더로 옮기는 중이에요.`의 `접수하는 중이에요.`와 `접수됐어요. …`가 지나고, `보관 폴더로 옮기지 못했어요.`가 떴어요. 개발 환경의 Transmission은 더한 토렌트를 멈춰 두므로 3화 토렌트를 다 받지 않았고, 이동이 아무것도 옮기지 않았다는 까닭과 `다시 옮기기`가 함께 나왔어요. 규칙은 이미 지워졌고, 그 규칙의 수집 이력 3행은 남았어요.
- 그 토렌트를 Transmission에서 지운 뒤(데이터는 남김) `다시 옮기기`를 누르자 명령이 3 ms 만에 `moved`로 끝나고 `보관 폴더로 옮겼어요.`가 떴어요. 작품은 같은 ID로 `/downloads/Shows`에 있었고 표지, 시즌 1의 Anissia 연결(3513), 자막 제작자 `liar`가 그대로였으며 `보관 폴더로 옮기기`는 사라졌어요.
- 문장을 고친 이미지로 `Chii Fuyo`도 같은 까닭으로 옮기지 못하게 해 봤어요. 작품 상세를 다시 열어도 `보관 폴더로 옮기지 못했어요.`, 까닭, `다시 옮기기`가 남았고, 375px 폭에서도 가로로 넘치지 않았어요.

### 한계

- 서버에서 확인하지 않았어요. [0011](0011-deploy-and-check-on-server.md)에서 봐요.
- 확인을 그리는 컴포넌트(`WorkArchive.tsx`)와 명령을 따라가는 훅(`useWorkArchive.ts`)은 시험이 없고, 개발 환경에서 눈으로만 봤어요. 답을 잃은 경우(`같은 요청 다시 보내기`, `다시 확인`)는 화면에서 만들어 보지 않았어요.
- 개발 환경에서는 규칙이 하나인 작품만 옮겨 봤어요. 여러 규칙과 `멈춤` 규칙을 함께 지우는 것은 API 테스트로만 확인했어요.
