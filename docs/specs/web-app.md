# 웹 앱 공통 명세

## 목표와 범위

작품별 영상·자막 상태와 RSS 수집 규칙을 웹에서 관리하고, 사용자가 고르거나 구독한 자막의 다운로드·분류·이름 맞춤·배치를 서버가 이어서 처리해요.
사용자는 필요한 CAPTCHA를 trss 작업 화면 안에서 해결하며, 직접 파일을 내려받아 업로드하거나 압축을 풀고 옮기는 방식으로 자동화를 대체하지 않아요.
대상은 혼자 LAN·VPN에서 사용하는 환경이며, 앞으로 trss가 받는 영상, trss로 받은 기존 영상, 사용자가 지정한 trname 정리 폴더의 영상을 모두 포함해요.

이 문서는 여러 주제에 걸친 웹 앱의 공통 요구와 구현 경계를 담당하고, 주제별 요구는 다음 문서가 담당해요.
한 개념의 규칙은 한 문서에만 적고, 다른 문서는 그 문서를 링크해요.

[웹 재설계 주제 문서](../brainstorm/web-redesign.md)와 [처음 주제 문서](../brainstorm/web-gui-subtitles.md)는 선택 배경과 조사·실험 근거를, [용어집](../glossary.md)은 도메인 의미를, `docs/adr/`의 기록은 선택과 이유를 담당해요.
제품 구현의 진행과 검증 기록은 [실행 계획과 티켓](../tickets/README.md)에 있어요. 여섯 문서의 완료 조건을 모두 통과한 것은 아니에요.

화면의 정보 구조와 시각 언어는 로컬 브랜치 `prototype/web-redesign-review-1`의 커밋 `3899c21c06418487232bc4bb38b3fcb63bbbe07d`에 보존한 통합 시안 `.scratch/redesign-home-2/prototype/trss.html`을 기준으로 해요.
이 시안은 처음 주제 문서의 사쿠라 시안을 대체하며, 사쿠라 시안에 묶였던 배치·치수·색상 값은 더 이상 요구가 아니에요.
시안의 수용은 제품 구현·파일 처리·실제 배포 검증의 완료가 아니에요.
시안을 보존한 뒤 정한 두 가지는 시안과 달라요: 할 일의 `제안`에 `제목 후보`가 더해지고, 영상 수정본으로 대체한 이전 영상은 정리 대상으로 남지 않고 바로 삭제돼요.

CAPTCHA 우회, 앱 자체 로그인·다중 사용자 기능, Transmission 제어 화면의 중복 구현, 외부 알림 채널은 범위 밖이에요.
자막 후보의 자동 선택은 [구독 제작자의 받지 않은 회차](subtitles.md#구독-제작자-자동-수신)에 한정하며, 그 밖의 후보를 자동으로 고르거나 기존 자막을 승인 없이 덮어쓰지 않아요.
서버 전역 폰트 설치와 원본 영상 재먹스도 선택한 동작에 포함하지 않아요.
다른 형식·언어·릴리스 지원의 미확정 범위를 기본 지원으로 간주하지 않으며, 기존 영상 이름을 임의로 다시 정리하는 기능으로 범위를 넓히지 않아요.
회차 스틸 이미지를 회차 줄의 배경이나 정보로 보여주는 기능은 두지 않아요.

## 요구사항과 완료 기준

### 접근 경계와 기기

- 앱 자체 로그인 대신 실제 배포 환경의 LAN·VPN·앞단 인증으로 접근을 제한해요.
  허용된 접속으로 웹·작업 조작·원격 입력을 사용한 뒤, 보호 경계 밖에서 앱 직접 주소와 원격 화면·제어 경로에 접근해 보호를 우회할 수 없는지 확인해야 해요.
  서버 브라우저의 페이지가 앱에 닿지 않도록, 웹은 서버 브라우저 네트워크(`browser_net`)에서 오는 모든 연결을 끊고, 그 네트워크를 알아내지 못하거나 자기 기본 경로가 그 네트워크를 지나면(LAN에서 오는 연결까지 끊기게 돼요) 시작하지 않아요([작업 화면 안의 인증](jobs.md#작업-화면-안의-인증과-브라우저-수명)).
  이 차단과 시작 검사는 구현과 테스트로 확인했어요(2026-10-03, 0040). 2026-10-07 실제 서버에서 웹은 서버 브라우저의 네트워크(`172.20.0.0/16`)를 거절한다고 알리고 떴고([0081](../archive/tickets/5-deployed-verification/0081-deploy-new-release.md)), LAN에서 보낸 다른 Host·Origin 요청은 거절됐으며 서버 브라우저의 송신 프록시는 LAN·게이트웨이·루프백 대상을 모두 거절했어요([0082](../archive/tickets/5-deployed-verification/0082-deployed-access-boundary.md)). VPN 경로와 HTTPS 앞단 프록시 뒤의 경로에서는 확인하지 않았어요.
- 웹은 경계 안 브라우저에 열린 다른 출처의 페이지가 웹을 쓰지 못하게 모든 경로(화면 파일·`/api`·WebSocket)에서 Host와 Origin을 검사해요(0053).
  Host가 IP 주소이거나 `localhost`이거나 `TRSS_WEB_HOSTS`(쉼표로 구분한 이름, 대소문자와 포트는 보지 않아요)에 적힌 이름일 때만 답하고, 그 밖의 이름은 `421`로 거절해요. 공격자 이름을 LAN 주소로 풀리게 하는 DNS 재바인딩을 막기 위해서예요. 사용자는 LAN IP:포트로 들어가므로 설정이 필요 없어요. Host 헤더가 아예 없는 요청은 받아요. 브라우저는 늘 Host를 보내고, 재바인딩한 페이지의 요청에는 공격자 이름이 실리기 때문이에요.
  `GET`·`HEAD`·`OPTIONS`가 아닌 요청과 모든 WebSocket 연결은 `Origin`이 `null`이거나 요청 자신의 출처와 다르거나 `Sec-Fetch-Site`가 `cross-site`이면 `403`으로 거절해요. WebSocket 연결은 `Origin`이 반드시 있어야 하고, 다른 요청은 `Origin`이 없으면(브라우저 페이지가 아닌 클라이언트) 받아요. 거절 응답은 `/api` 아래면 JSON 오류(`host_not_allowed`·`forbidden`), 그 밖에는 짧은 글이에요.
  요청 자신의 출처는 Host로 정하고 scheme은 견주지 않아요. 웹은 평문 HTTP로 답하고, 앞단에서 HTTPS를 끝내는 프록시 뒤에서는 페이지 출처가 `https://`이며, 앞단이 보낸 scheme 헤더는 웹이 믿을 수 없어서예요. Host에 포트가 없으면 Origin scheme의 기본 포트로 봐요. 브라우저가 쓴 scheme을 웹이 알 수 없어서예요. 그래서 포트 없이(80, 또는 프록시 뒤 443) 들어오는 웹에서는 같은 호스트의 `http://이름`과 `https://이름`을 모두 자기 출처로 받아요. 그런 페이지는 같은 호스트의 서버만 낼 수 있어서 바깥 공격자의 페이지는 아니에요. 앞단 프록시는 브라우저의 Host를 그대로 넘겨야 하고(nginx `proxy_set_header Host $host`), 그 이름을 `TRSS_WEB_HOSTS`에 적어야 해요.
- PC·태블릿·휴대폰에서 구독, 후보 선택, 자막 비교·승인, 설정 편집과 원격 인증을 끝낼 수 있어야 해요.
  작은 화면에서는 상세를 단계적으로 펼칠 수 있지만 필수 비교 정보나 확인 동작을 생략하지 않아요.
  실제 좁은 화면과 터치·가상 키보드로 주요 흐름을 수행하고, 원격 화면을 확대하거나 크기·방향을 바꾼 뒤에도 보이는 위치와 입력 위치가 맞는지 확인해요.
  원격 입력에 초점이 있을 때와 trss의 다른 폼을 편집할 때를 구분하며, UI 라이브러리 선택만으로 모바일 인증이 검증됐다고 표시하지 않아요.
- 1440·1024·768·390·320px 폭의 라이트·다크 모드에서 모든 화면에 가로 페이지 넘침이 없고, 휴대폰 하단 메뉴와 그 위에 고정한 동작 막대가 서로 가리지 않아야 해요.
- Transmission은 상태와 기존 관리 화면으로 이동하는 링크를 제공해요.
  trss 웹에 시작·일시정지·삭제 기능을 중복 구현하지 않으며, 기존 영상 RSS 처리의 Transmission 연동까지 읽기 전용으로 바꾸는 것은 아니에요.

### 메뉴와 탐색

주 메뉴는 `이번 주 편성`·`라이브러리`·`할 일`·`수집`·`설정`이고, 앱 표시 이름은 `TRSS`예요.
PC에서는 상단 메뉴, 휴대폰에서는 하단 메뉴로 이동하고, 두 메뉴가 모두 맞지 않는 태블릿 폭(721–979px)에서는 상단 메뉴를 아이콘만으로 보여주며 이름은 보조 기술에 남겨요.
현재 메뉴는 색만이 아니라 배경·글자 굵기·표시선으로 구분하고, 실제 Tab 이동으로 다른 메뉴에 초점만 옮겼을 때 경로와 현재 메뉴 표시는 바뀌지 않아야 해요.
휴대폰 하단 메뉴는 실제 기기의 안전 영역을 보호해요.

`할 일` 메뉴의 개수 배지는 [할 일](jobs.md#할-일)의 `처리 필요`만 세고, `제안`은 세지 않아요.
처리 필요가 없거나 [처음 설정](settings.md#처음-실행) 중이면 배지를 두지 않아요.
화면 모드(시스템·라이트·다크)는 상단의 한 칸짜리 전환 버튼이 맡고, 설정 화면에는 두지 않아요.

모든 목록은 `더 보기` 버튼 대신 끝에 닿으면 이어서 불러오는 무한 스크롤을 쓰고, 내용을 펼치거나 이어 붙일 때 스크롤 위치를 옮기지 않아요.
휴대폰에서 시즌 고르기처럼 짧은 선택만 아래에서 올라오는 시트로 열고, 나머지 창은 왼쪽 제목과 오른쪽 닫기의 머리를 써요.
뒤로 화살표는 같은 창이나 화면 안에서 이전 단계로 돌아갈 때만 써요.
등록 해제·삭제처럼 되돌리기 어려운 동작은 위험을 드러내는 모양으로 두고, 별도 창 대신 누른 자리에서 결과를 설명하는 확인을 한 번 더 거쳐요.
화면 사이를 오갈 때 도착 위치를 잠깐 칠해 보여주는 강조는 두지 않고, 스크롤과 초점 이동만 해요.

### 이번 주 편성

앱의 첫 화면은 `이번 주 편성`이에요.
구독한 방영작의 이번 주 회차를 요일별로 묶어 영상·자막 상태를 보여주고, 할 일 목록은 두지 않아요.
작품 카드에는 표지·제목·방영 시각·회차와 `영상 받음`·`자막 받음`·`영상 대기`·`자막 대기` 같은 상태 줄을 두고, 사용자가 해야 하는 일은 `인증 필요`·`회차 확인 필요` 같은 상태 줄로만 알려요.
강조는 `인증 필요`·`회차 확인 필요`·`영상 받는 중`에만 쓰고, 제작자를 기다리는 `자막 대기`는 조용한 상태로 둬요.
방영 전 작품도 같은 카드로 보여주고, 영상 `방영 전`과 `자막 대기`·제작자를 조용하게 둬요.
`자막 받기`를 끈 작품은 자막 상태 줄을 두지 않고, `영상 받기`를 끈(멈춤) 작품은 카드를 남긴 채 `받기 멈춤`을 조용한 상태 줄로 둬요.
Anissia가 작품을 결방·휴방(`OFF`)으로 주면 카드를 남긴 채 영상·자막 상태 줄 대신 조용한 `결방`을 둬요(사용자 결정, 2026-10-01).
카드는 Anissia의 종영일이 지나면 빠지고, 종영일이 없으면 Anissia 편성표가 그 작품을 더는 싣지 않는 것을 확인한 때부터 빠져요. Anissia에 닿지 못하는 동안에는 카드가 그대로 남아요(사용자 결정, 2026-10-01). 어느 요일 목록이 비어서 왔는데 그 요일에 싣던 작품이 있으면 그 답은 믿지 않아요. 그 요일의 작품은 이번 갱신에서 편성표에서 빠진 것으로 치지 않고, 다른 요일은 그대로 판단해요.
보관한 구독은 카드가 없어요(사용자 결정, 2026-10-01).
방영이 없는 날은 날짜와 요일, `방영 없음`만 담은 얇은 한 줄이에요.
카드 전체가 작품 상세로 가는 링크이며, 올려 두면 제목에 밑줄 대신 카드 배경을 한 단계 밝혀요.

휴대폰에서는 날짜 열 옆에 작품 카드를 쌓고, 넓은 화면에서는 한 줄에 여러 작품을 줄바꿈해 보여주되 가로 스크롤은 만들지 않아요.
화면 제목 `이번 주 편성`은 다른 화면 제목과 같은 크기이고, 그 옆의 `오늘로 이동`은 오늘 줄로 스크롤하고 초점을 옮겨요.
제목 아래에는 이번 주 범위와 분기, 기준 시각을 둬요.

수집 상태와 다음 분기 구독은 편성 아래가 아니라 PC에서는 편성 옆의 좁은 열에, 휴대폰에서는 편성 위의 한 줄 요약에 둬요.
수집 상태를 먼저 두고, RSS의 `확인`·`다음` 시각(`오늘 17:53`처럼 날과 시각으로 적고, 수집 화면의 상태판도 같은 모양이에요. 사용자 결정, 2026-10-01), [수집 화면](collection.md#수집-화면)과 같은 기록에서 센 `최근 7일 추가 N개`(휴대폰 요약은 `7일`), Transmission의 받는 중·시딩 수를 보여줘요.
예정된 RSS 확인 시각이 한 주기 넘게 지나면(일하는 worker는 멈춘 것으로 보지 않아요. worker가 주기와 그 뒤의 감시 폴더 읽기, 명령, 알림이 부른 읽기까지 잠금을 쥐는 동안 15초마다 남기는 기록이 1분 안이면 일하는 것으로 보고, 그 기록이 1분 넘게 멈췄는데 끝나지 않은 주기가 있으면 바로 멈춘 것으로 봐요. 기록이 이어져도 `max(30분, 주기 간격의 10배)`를 넘게 잠금을 쥐고 있으면 멈춘 것으로 봐요. 기록을 남기지 않는 이전 worker는 끝나지 않은 주기가 그 시간을 넘게 돌 때만 멈춘 것으로 봐요) `다음` 자리에 `RSS 확인이 멈췄어요. worker가 돌고 있는지 확인해 주세요.`를 강조 색으로 두고, 휴대폰 요약에는 `RSS 멈춤`만 둬요. 수집 화면의 상태판도 같아요(사용자 결정, 2026-10-01).
다음 분기 구독은 제목 대기 수와 편성표에서 추가하는 바로가기를 둬요.
[처음 설정](settings.md#처음-실행) 중에는 편성 자리에 체크리스트를 두고 수집 상태·다음 분기 구독·휴대폰 요약 줄을 두지 않아요.

### 시각 방향과 테마

시각 언어는 표지를 중심에 둔 어두운 영화관 톤이며, 라이트 모드에도 같은 언어를 옮겨요.
라이트 모드는 무난한 관리 화면처럼 보이지 않도록 배경과 카드 면의 명도 차이를 키우고 카드·표지에 그림자를 줘요.
다크 모드는 배경과 카드가 구분되도록 카드 면을 배경보다 조금 밝게 둬요.
구체적인 색상·간격 값은 기준 시안의 토큰을 출발점으로 삼되, 아래 읽기·구분 조건을 우선해요.

라이트·다크를 제공하며 기본은 접속 기기의 시스템 설정을 따르고, 사용자가 화면 모드를 직접 바꿀 수 있어야 해요.
시스템 모드에서는 기기 설정 변경을 따라가고 직접 선택한 모드는 그 선택을 유지하며, 화면 이동·새로고침에서도 선택한 모드를 보존해요.

- 빨간색은 실패와 수집·적용을 막는 오류, 되돌리기 어려운 동작에만 써요.
  할 일에서는 `인증 필요`·`받기 실패`만 빨갛게 두고, `교체 승인`·`회차 확인 필요`·`제목 후보`는 차분한 파랑, `보관 제안`은 보라처럼 경고색이 아닌 강조색을 써요.
- 상태 배지는 테두리와 아이콘이 있는 한 가지 모양만 쓰고, 한 상태를 화면마다 다른 모양으로 그리지 않아요.
  물음표 아이콘은 `확인 필요`에만, 바깥으로 나가는 화살표는 AniList·Transmission 같은 외부 링크에만 써요.
- 받은 영상·자막의 체크 표시는 모든 화면에서 초록으로 보여줘요.
- 화면만 옮기는 이동 버튼은 색 없이 두고, 보관·받기·삭제처럼 상태를 바꾸는 동작 버튼은 맥락 강조색의 테두리와 글자로 드러내요.
  꽉 찬 색은 그 화면의 주 동작과 제자리 확인의 최종 버튼에만 쓰고, 옅은 배경으로 채운 동작 버튼은 쓰지 않아요.
- 카드 전체가 링크인 카드는 올려 두면 제목 밑줄 대신 배경을 밝히고, 밑줄은 문장 속 글자 링크에만 남겨요.

두 모드 모두 제목·상태·초점·선택을 읽고 구분할 수 있어야 하며, 상태를 색만으로 전달하지 않아요.
선택 상태는 배경·테두리·글자 굵기를 함께 사용해 구분하고, 아이콘은 텍스트를 보조하며 아이콘만으로 의미를 전달하지 않아요.
작은 본문·라벨은 실제 렌더링 배경에서 최소 4.5:1의 글자 대비를 확인하고, 표지 위의 글자는 단색 토큰 계산만으로 통과 처리하지 않아요.
선택 글자·상태 배지·보유 체크·키보드 초점을 같은 상태의 두 모드에서 직접 관찰해요.

### 문구와 표기

화면 문구는 자리의 크기에 맞춰 써요.

- 버튼·배지·상태 줄·목록 줄·항목 값·기록 줄은 짧은 명사구로 써요.
  버튼 이름은 `~하기`를 붙이지 않고 `인증`·`비교`·`연결`·`보관`·`검색`·`시즌 변경`처럼 명사로 끝내요.
  `받기`·`다시 받기`·`받는 중`은 정한 용어라 예외이고, `보기`·`열기`·`닫기`·`펼치기`·`접기`·`자세히`처럼 자연스러운 한자어가 없는 말도 그대로 써요.
- 빈 화면·알림·확인 질문·실패 이유, 그리고 상태 배너·구역 안내처럼 넓은 설명 영역은 까닭과 누른 뒤의 결과를 한두 문장의 해요체로 써요.
  배너 제목은 위의 배지가 이미 말하는 상태 이름을 되풀이하지 않고 `이 규칙을 보관할까요?`처럼 질문이나 설명으로 써요.
- 설명 줄은 배지·단계·시각·항목 결과가 이미 말하는 것을 되풀이하지 않고 새 정보가 있을 때만 두며, 구역 제목 옆 설명은 제목만으로 오해될 때만 짧게 남겨요.
- 여러 정보를 ` · `로 한 줄에 잇지 않고, 정보 종류마다 모양을 달리해 간격으로 나눠요.
  회차는 굵게, 제작자는 자막 아이콘과 함께, 채널·형식·버전·맥락은 작은 태그로, 개수는 `추가 2`처럼 숫자 태그나 `작품 469편`처럼 이름표 달린 값으로, 시각은 흐린 이름표 뒤에, 방영 시작일·근거처럼 덧붙이는 값은 흐리게 둬요.
  상태와 그 결과를 잇는 설명은 두 줄로 나눠 첫 줄을 상태로, 다음 줄을 흐리게 둬요.
  기록 줄은 일어난 일을 먼저 쓰고 덧붙이는 정보는 흐리게 옆에 둬요.
- 경로는 본문 글꼴로 보여주고, 해시·시각표 같은 값만 고정폭 글꼴로 남겨요.
- 한국어 제목과 문장은 띄어쓰기 단위로 줄바꿈해요.

같은 뜻은 한 단어로 쓰고, 한자어 용어가 있으면 그것을 써요.

| 개념 | 쓰는 말 |
| --- | --- |
| 바꾸기·지우기·고르기·되돌리기·찾기·찾음·만들기 | `변경`·`삭제`·`선택`·`복원`·`검색`·`발견`·`생성` |
| 시즌 | 설명·버튼·타일 모두 `시즌 1`처럼 `시즌` |
| 회차 보유 | `영상 ✓`·`자막 −`이며, `파일`은 폴더·정리 카드 이름과 실제 파일 이름을 가리킬 때만 써요. |
| 기다리는 상태 | `제목 대기`·`영상 대기`·`자막 대기`처럼 `무엇 + 대기`이고, 자막 출처에 연결되지 않아 다시 확인을 기다리는 작업도 `자막 대기`예요. |
| 교체 승인 | 할 일 종류·회차 배지·기록 모두 `교체 승인` |
| 회차를 정하지 못한 파일 | 편성·할 일·작품 상세·기록 모두 `회차 확인 필요` |
| 할 일 종류 | `인증 필요`·`받기 실패`·`교체 승인`·`회차 확인 필요`·`제목 후보`·`자막 구독`·`보관 제안` |
| 수집 개념 | `일치 문구`·`저장 폴더`·`수집 폴더`·`보관 폴더`·`보관 제안`·`제작자 미정`·`받기`, 영상이 아닌 자막 후보는 `자막 후보` |

시각은 모든 화면에서 `오늘 13:40`·`어제 00:05`·`9월 13일 12:35`로, 날짜만 쓸 때는 `9월 13일`로 쓰고 올해가 아니면 연도를 붙여요.
날짜 머리는 `9월 28일 (월)`이고, `9/13` 같은 숫자만의 표기와 `2시간 전` 같은 상대 표기는 쓰지 않아요.
날짜가 길어져 휴대폰에서 정보 줄이 한 줄 늘 수 있지만, 정보 조각 단위로 줄바꿈하고 날짜 중간에서 끊지 않아요.
개수는 항목·규칙·파일에 `개`, 작품에 `편`, 기록에만 `건`을 써요.

### 웹 명령과 상태 갱신

설정 저장 응답은 서버에 반영된 설정과 그 버전을 확인하는 응답이며, 다운로드·적용 명령의 접수 응답은 영속화된 명령·작업 ID를 확인하는 응답이에요.
후자의 접수를 파일 수신·적용 완료로 표시하지 않고, worker가 기록한 실제 항목별 진행·대기·실패·완료 결과를 따로 보여줘요.
규칙·대응·가져오기 계획의 편집에는 확인한 대상 버전을, 교체 승인에는 확인한 불변 계획의 ID·버전을 전달하며 서버가 다시 검증해요.
이 실행 중 버전은 YAML 교환 규격의 `version`과 다른 값이고, 화면에 보여주지 않아요.

접수한 명령은 worker가 바로 실행을 시작해요(사용자 결정, 2026-10-02).
worker는 정해진 주기의 확인을 기다리지 않고 접수를 알아채며, 진행 중인 RSS 수집 주기나 감시 폴더 읽기, 관계없는 다른 명령이 끝나기를 기다리지 않아요.
같은 토렌트·작품 폴더·파일처럼 대상이 겹치는 명령과 수집 처리는 겹치는 구간만 차례로 실행하고, 수집 주기가 Transmission에서 사라진 토렌트를 지우는 판단과 명령의 토렌트 추가가 엇갈리지 않게 해요.
명령이 토렌트를 다루는 중이면 그 수집 주기는 사라진 토렌트 정리를 건너뛰고 다음 주기에 해요. 정기 처리(사라진 토렌트 정리, 주기의 감시 폴더 읽기)는 명령 뒤에 줄 서지 않아요.
worker가 멈춰 있거나 재시작 중이면 명령은 접수된 채 기다리며, 화면은 이를 실행 실패로 표시하지 않아요.

| 입력·통신 상황 | 필요한 처리와 관찰 |
| --- | --- |
| 두 화면에서 같은 설정을 편집 | 먼저 저장한 뒤 오래된 버전으로 보낸 저장은 변경 없이 충돌로 거부해요. 두 번째 화면의 편집 입력은 남기고 현재 서버 값과 비교해 다시 저장할 수 있어야 해요. |
| 비교 후 계획·대상이 변경 | 이전 화면의 승인 버튼이 활성화돼 있어도 서버가 오래된 승인을 거부하고 새 비교를 요구해요. 현재 버전으로 몰래 치환해 승인하지 않으며, 실제 파일도 바뀌지 않아야 해요. |
| 같은 명령의 중복 전달 | 같은 사용자 동작의 명령 ID와 내용을 고정해 전달하고, 이미 접수한 같은 명령이면 기존 결과·작업을 돌려줘요. 같은 ID에 다른 내용을 붙이면 거부하며, 반복 전달 후 실제 작업이 추가 생성되지 않았는지 확인해요. |
| 명령 접수 후 응답 단절 | 같은 명령 ID로 접수 결과를 조회하고, 확인 전에는 성공·실패를 단정하거나 새 ID로 자동 재전송하지 않아요. 기록을 찾을 수 없는 경우도 확인 불가와 실행 실패를 구분해요. |
| 목록 정렬·필터·새 조회 | 행 위치가 아니라 항목 ID와 확인한 대상 정보를 기준으로 선택을 유지해요. 새로 나타난 후보를 자동 선택하지 않으며, 사라지거나 바뀐 선택 대상은 확인 필요로 표시해요. |
| 늦게 도착한 이전 조회 응답 | 현재 화면의 대상·검색 조건과 조회 순서를 확인해, 이전 응답이 최신 상태나 이미 확인한 명령 접수 결과를 덮어쓰지 않게 해요. 응답 순서를 뒤집은 경우에도 선택과 완료 상태가 잘못 되돌아가지 않아야 해요. |
| 연결 단절·접근 거부 | 마지막으로 확인한 상태와 조회 시점을 남기되 최신 상태로 표시하지 않아요. 조회 실패만으로 서버 작업을 실패·취소 처리하지 않으며, 접근이 거부되면 새 명령과 원격 입력을 중지해요. |
| 화면 재접속 | 서버의 현재 작업과 항목별 결과를 조회해 복원하고, 화면을 복원하는 것만으로 다운로드·적용·승인을 다시 보내지 않아요. |

작업 상태 갱신은 우선 HTTP 주기 조회를 사용하고, 화면·입력을 전달하는 원격 인증 WebSocket과 구분해요.
보이는 화면의 기본 조회 간격은 2초로 두며, 앞선 조회가 끝나지 않았으면 같은 화면의 주기 조회를 쌓지 않아요.
이는 초기 UI 기본값이며 처리 완료 시간의 보장이나 실측 성능값이 아니에요.
숨겨진 화면의 주기 조회는 멈추고 다시 활성화되면 갱신하되, 서버의 5분 RSS 처리·30분 자막 후보 관찰이나 진행 중 작업은 계속돼요.
화면의 마지막 동기화 시각과 출처·파일 상태를 실제로 관찰한 시각을 구분하며, 편집 중인 입력을 새 조회 값으로 자동 덮어쓰지 않아요.
상태 조회는 브라우저를 시작하거나 사용자 조작 시각을 갱신하지 않아요.

출처에서 받은 자막 본문·파일명·오류 문구와 RSS 항목 제목은 데이터로 표시하며, SMI의 태그나 첨부 HTML을 trss 페이지의 실행 가능한 마크업으로 삽입하지 않아요.

## 구현 경계와 실행 순서

[현재 코드와 제약](../brainstorm/web-gui-subtitles.md#현재-제품의-근거와-한계)을 출발점으로 삼고, 기존 RSS·규칙·Transmission·trname 동작을 재사용해요.
웹 화면 추가만으로 기존 미완성 Anissia 경로가 완성되거나 `regex: true`가 동작한다고 가정하지 않아요.

[웹 기술 ADR](../adr/0004-rust-react-web-stack.md)에 따라 기존 Rust·Tokio를 유지하고 axum 서버와 React·TypeScript·shadcn/ui 화면을 사용해요.
shadcn/ui를 사용해도 작은 화면의 기능 범위나 웹 명령·선택·승인 계약은 축소하지 않아요.
프런트엔드의 정적 빌드 결과는 Rust 서버가 제공하며, 운영용 Node 서버 없이 실제 배포 이미지에서 화면·작업 API·원격 인증 연결을 사용할 수 있어야 해요.
실행 구성은 [웹·작업 바이너리 분리 ADR](../adr/0006-separate-web-worker-binaries.md)에 따라 공통 Rust 라이브러리와 `trss-web`·`trss-worker` 두 바이너리로 나눠요.
두 바이너리는 같은 앱 이미지에 포함하고, 같은 호스트의 별도 컨테이너에서 같은 릴리스 버전으로 운용해요.

[저장소 ADR](../adr/0005-local-sqlite-app-state.md)에 따라 앱 설정·구독·작품 연결·회차 대응·수집 이력·작업·승인·보관 이력은 로컬 SQLite에 저장해요.
DB와 [앱 데이터 폴더](../adr/0008-trss-folder-and-app-data-files.md)는 앱 호스트의 로컬 영속 볼륨에 두고, 영상·자막·폰트 파일 및 임시 브라우저 프로필과 구분해요.
컨테이너 재생성 후에도 저장한 상태를 읽을 수 있어야 하며, SQLite DB를 SMB·NFS 공유 경로에 배치하지 않아요.
웹과 단일 worker 프로세스가 이 DB를 공유하며, 별도 Redis나 분산 작업 시스템을 도입하는 구성은 아니에요.

[trss Compose](../../docker-compose.trss.yml)는 같은 이미지의 `trss-web`과 `trss-worker`를 상시 컨테이너로 실행하고, worker는 5분마다 수집 처리를 돌려요.
0.4.0 이전에는 cron이 5분마다 종료형 컨테이너를 띄웠고, 그 실행 파일과 cron 스크립트는 걷어냈어요.
새 배포 구성에서 Transmission의 미디어 경로와 앱이 읽고 쓰는 경로의 대응, 감시 폴더 마운트, 실행 사용자 권한을 확인하고 실제 보관·복사 적용을 수행해야 해요.
`trss-worker`는 Transmission이 받은 파일과 같은 uid·gid 1000:1000으로 실행해요(사용자 결정, 2026-10-04). 재생기는 미디어 디스크를 NFS로 읽고 NFS는 소유를 숫자로 보여서, root로 쓴 보관본·적용본은 같은 폴더의 영상과 소유가 달라져요.
`trss-web`도 같은 사용자로 실행해요. 두 프로세스가 같은 SQLite DB(WAL과 공유 메모리 파일 포함)와 앱 데이터 폴더의 수신 영역을 함께 쓰므로, 사용자가 다르면 한쪽이 만든 파일을 다른 쪽이 쓰거나 지우지 못해요.
이미지와 Compose가 이 사용자를 정하고, 이전 배포에서 root로 만든 앱 데이터 폴더의 파일은 전환할 때 소유를 옮겨요.
두 프로세스는 시작할 때 앱 데이터 폴더와 trss가 거기에 쓰는 것(DB와 WAL·공유 메모리 파일, 잠금 파일, 깨우기 소켓, `receive/`·`artwork/`·`subtitle-files/`의 폴더)에 쓸 수 있는지 확인해요. 쓸 수 없으면 그 경로와 필요한 uid를 알리고 오류로 멈춰서, 이전 배포가 남긴 root 소유 파일이 나중에 조각조각 실패하지 않게 해요. `lost+found`나 백업 사본처럼 trss가 쓰지 않는 것은 보지 않아요. 서버 브라우저의 `browser-downloads/`는 worker가 따로 준비하고, 준비하지 못하면 worker는 서버 브라우저 없이 돌아요.
시험용 작품에 보관·복사·승인한 교체를 수행해 Transmission에서 보이는 경로와 앱의 실제 파일이 대응하는지 확인하고, 읽기 전용·권한 거부·마운트 누락에서는 기존 파일을 보존하며 실패를 표시해야 해요.
5분 RSS 처리와 30분 자막 후보 관찰의 실행 주체는 worker이고, 운영 안내에 새 실행·중지 절차를 명시해요.
이 검증은 실제 네트워크의 접근 보호를 대신하지 않아요.

설정·구독·작품 연결·회차 대응·자막 정책과 작업·보관 이력은 브라우저 프로필과 수명을 분리해야 해요.
실제 파일 상태, 수신한 출처 정보, 적용 계획과 승인 대상을 구분해 기록하고, 화면의 상태가 파일 변경의 성공을 앞서 선언하지 않게 해요.
웹은 화면·API·설정·사용자 요청을, worker는 정기 조회·다운로드·브라우저 수명·파일 반영을 담당해요.
웹 요청과 worker의 작업 인계를 기록으로 연결하고, worker를 중복 기동해도 같은 작업·정기 처리가 중복 수행되지 않아야 해요.
단일 worker는 프로세스 수의 결정이며 내부 작업 동시성은 별도로 제한해요.
웹만 재시작하는 동안 진행 중 worker 작업을 유지하고, 웹 복귀 후 같은 작업과 유효한 원격 인증 화면에 다시 연결되는지 확인해요.
이때 다운로드 재실행이나 승인 자동 부여가 발생하지 않고, 브라우저의 기존 유휴 종료 정책도 유지돼야 해요.
worker 재시작은 [작업 복구 계약](jobs.md#체크포인트와-중단-복구)을 따라요.

### 공통 라이브러리의 모듈 구성

공통 Rust 라이브러리는 기능별 모듈로 구성하고, 각 기능의 판정·저장 코드와 그 계약을 검증하는 코드를 가까이 둬요.
[기능별 크레이트 ADR](../adr/0011-feature-crate-workspace.md)에 따라 저장소는 Cargo workspace이고, 아래 책임은 공통 기반·기능·웹·worker 크레이트로 나눠 그 경계와 의존 방향을 컴파일러가 강제해요.
한 행이 꼭 크레이트 하나가 된다는 뜻은 아니며, 실제 크레이트 지도는 모듈 의존 관계에서 정해요.
기능의 판정과 조회·갱신 코드는 그 기능의 크레이트에 두고, DB가 하나이고 스키마가 기능 경계를 넘으므로 마이그레이션 SQL과 순서는 하나로 공통 기반에 둬요.

| 모듈 | 책임 |
| --- | --- |
| 앱 설정 | 전역 자막·브라우저 정책의 읽기·검증·저장을 담당하며, 배포 환경 값과 분리해요. |
| RSS | 채널·규칙·구독의 저장과 순서, 피드 수집·판정, 수집 이력, 지난 회차 검색, 영상 수정본 판정, 미리보기와 실제 처리에서 공유하는 규칙 평가를 담당해요. |
| 작품·보관 | 작품·시즌·회차 대응, 보관본·자산 관계와 경로·내용 식별, 파일의 안전한 보관·독립 복사를 담당해요. |
| 자막 | 후보·구독 제작자 자동 수신·출처별 수신·묶음 분석·비교·배치 계획을 담당하며, 작품·보관 모듈의 인터페이스로 대상과 자산을 다뤄요. |
| 작업 관리 | 요청·작업 상태·승인 근거·재개 지점의 영속화와 중복 실행 방지, 할 일의 집계를 담당해요. 출처별 다운로드 방법은 소유하지 않아요. |
| 설정 교환 | 기능 모듈의 인터페이스를 조합해 YAML 내보내기·검증·선택 가져오기 계획과 반영을 담당해요. 이전 작업 실행 권한을 가져오는 경로는 두지 않아요. |
| 공통 기반·외부 연동 | DB 접속·트랜잭션·마이그레이션 등 실제 공통 기능과, 여러 기능이 함께 쓰는 기능 규칙 없는 부품([ADR 0016](../adr/0016-shared-parts-in-core.md))을 제공해요. Transmission·Anissia·AniList·브라우저처럼 여러 기능이 사용하는 연동만 공유하고, 특정 자막 출처에만 필요한 코드는 자막 모듈에 둬요. |
| 웹·worker 진입부 | 웹은 화면·요청을 기능 인터페이스에 연결하고, worker는 기록된 작업과 정기 처리를 실행·복구해요. 규칙 평가나 파일 비교 로직을 각각 다시 구현하지 않아요. |

의존 방향은 웹·worker에서 기능 모듈로, 기능 모듈에서 필요한 공통 기반·외부 연동으로 향해요.
기능 모듈이 웹 라우터나 worker의 실행 루프를 역으로 참조하지 않으며, 다른 기능의 테이블을 직접 갱신해 그 기능의 검증을 우회하지 않아요.
여러 기능의 상태를 함께 반영해야 하면 설정 교환이나 작업 실행 측에서 하나의 트랜잭션 범위를 조율하고, 개별 저장 메서드가 먼저 독립 커밋해 일부만 반영되지 않게 해요.
파일 변경과 DB 기록이 하나의 원자적 트랜잭션이라고 가정하지 않으며, 작업 기록과 실제 파일의 대조를 통한 복구 요구를 유지해요.

파일 반영은 worker의 실행 경로에서만 수행해요.
배치 계획·승인 근거·현재 파일을 반영 직전에 함께 확인하는 책임을 웹의 사전 검사로 대체하지 않으며, 승인 무효화·복사 실패·중단 복구 사례를 이 실행 경로에서 검증해요.
미리보기와 실제 규칙 처리도 같은 RSS 모듈의 인터페이스를 사용해 결과 차이를 막아요.
화면(TypeScript)도 서버의 규칙을 다시 계산하지 않고, 서버가 계산해 보낸 값을 보여줘요. 입력하는 동안의 미리보기도 서버에 물어요. 날짜와 크기처럼 표기만 하는 일과, 보는 사람의 시간대로 같은 날 받은 사본에 시각을 붙이는 일은 화면이 맡아요(사용자 결정, 2026-10-09).
API의 Rust 응답 구조체와 화면의 TypeScript 타입은 생성 도구 없이 손으로 맞춰요(사용자 결정, 2026-10-07).
기능의 데이터가 저장된다는 이유만으로 범용 저장소 인터페이스를 추가하지 않고, 실제로 서로 다른 외부 동작을 교체해야 하는 지점에 필요한 인터페이스를 둬요.

### 구현 순서

실행 의존성은 다음과 같으며, 단계 구분이 뒤 단계의 필수 범위를 제외한다는 뜻은 아니에요.

1. 앱 소유 설정의 저장·가져오기 계약과 실행 수명을 정하고, 기존 규칙 판정과 미리보기가 같은 기준을 사용하게 해요.
   수집 이력 기록은 이 단계에서 시작해야 이후의 소급 적용·다시 받기가 기록된 항목을 쓸 수 있어요.
2. 세 종류 영상 입력의 작품·회차 발견, 방영작 구독과 확인한 연결의 유지, 지난 회차 검색과 영상 수정본 대체를 연결해요.
3. 자막 후보 조회·선택과 구독 제작자 자동 수신, 출처별 수신과 서버 브라우저 인증을 작업 기록에 연결해요.
   서로 독립적인 출처는 공통 결과·실패 표현을 정한 뒤 병행할 수 있어요.
4. 수신한 묶음의 분석·보관·폰트 재사용·배치 계획을 연결하고, 복사 적용·교체 승인·영상 대기를 실제 파일로 검증해요.
5. 전체 웹 흐름과 실제 배포의 접근 보호·재생기 호환을 확인하고 운영 안내를 갱신해요.
6. 앱 YAML의 [내보내기](settings.md#내보내기)와, 작품·보관 관계까지 담은 [가져오기](settings.md#앱-yaml)를 만들어요.
   실제 배포를 확인하고 동작을 바꾸지 않는 리팩터링을 마친 뒤에 해요(사용자 결정, 2026-10-07).

모듈 내부의 소스 파일 배치, 파일시스템 동작과 동기화 수단, CPU·메모리·압축 해제 한도와 외부 조회 간격의 수치는 구현 환경에 맞춰 구체화하고 검증해야 해요.
구현에 필요한 국소 상세는 기존 구조를 우선해 정하고, 대안 간 책임·의존 방향·호환·운영 비용이 의미 있게 달라지는 선택은 해당 구현 전에 사용자와 결정해요.

기준 시안의 정적 HTML·직접 DOM 조작·예시 상태를 제품 코드로 그대로 승격하지 않고, 위 웹 기술·역할 분리와 서버 권위 안에서 화면 요구를 구현해요.
예시 자료로 화면이 동작하는 상태를 실제 파일·작업 API와 연결된 제품의 완료로 표시하지 않아요.

## 검증 근거와 완료 판정

각 주제 문서의 요구에 붙은 입력·상태·관찰 결과가 그 동작의 완료 기준이에요.
규칙 우선순위, 선택 가져오기 보존, 회차 대응, 복사 독립성, 승인 유효성, 대기 전이, 위험한 묶음의 경계, 영상 수정본 판정처럼 회귀 시 사용자 파일이나 결과가 달라지는 계약은 격리된 작은 입력으로 검증해요.
정상 입력 처리와 잘못된 입력·자원 과다에 대한 안전 검증을 구분하고, 외부 사이트 인증을 일반 자동 테스트의 무인 성공 조건으로 만들지 않아요.

현재 [빌드 이미지](../../Dockerfile)는 `cargo build --release`를 수행하고, [배포 workflow](../../.github/workflows/deploy.yml)는 태그 기반 이미지 빌드·게시이며 테스트 단계는 없어요.
일반 `cargo test`는 실제 Transmission에 접근하는 테스트를 두지 않고, Transmission은 가짜 서버로 대신해요.
규칙 판정과 RSS 제외·첫 일치 선택의 기존 동작을 검증 가능한 경계로 재사용하되, 외부 Transmission과 파일 변경은 지정된 격리 검증 환경에서 다뤄요.
구현 결과에 맞는 빌드·회귀 검증 명령과 결과를 기록하고, 실제 배포 이미지에서도 자막 기능과 UI가 동작하는지 확인해요.
명세 작성 중에는 제품 빌드·테스트·배포를 실행하지 않았으며, 배포 workflow의 존재가 게시 권한을 뜻하지 않아요.

통합 확인은 실제 trss 웹 화면에서 수행하고, 소스별 다운로드 결과와 파일시스템 결과를 함께 확인해요.
다운로드·압축 분석의 모의 응답이나 API 테스트만으로 사용자 인증·프록시·재생기 검증을 완료 처리하지 않아요.
실제 사용에서 수동 다운로드·업로드·이름 변경·이동과 채널 설정 주석의 수작업이 남는지 관찰하는 것은 코드 검증과 별개이며, 그 관찰 전에는 수작업 감소 효과를 입증했다고 표시하지 않아요.

기존 근거는 다음 범위에 한정해 재사용해요.

- [웹 재설계 주제 문서의 시각 언어 결정](../brainstorm/web-redesign.md#시각-언어의-결정-방법)과 기준 시안은 사용자 한 명의 시안 검토이며, 2026-09-29에 조회한 실제 작품·편성·제작자·표지와 시뮬레이션한 수신 상태·할 일을 구분해요.
  헤드리스 Chromium으로 여러 폭의 가로 넘침과 휴대폰 첫 화면의 사람 확인 상자 위치를 확인했고, 실제 휴대폰·태블릿에서는 확인하지 않았어요.
  제품의 React 화면·API·자동 파일 처리는 시안이 아니라 목표 1–5의 티켓에서 확인했어요. 실제 휴대폰·태블릿의 주요 흐름은 사용자가 [0085](../archive/tickets/5-deployed-verification/0085-phone-and-tablet-flows.md)에서 확인했어요(2026-10-07).
  원격 페이지에 가상 키보드로 입력하는 것과 스크린 리더를 포함한 전체 접근성은 검증하지 않았어요.
- [처음 주제 문서의 사쿠라 시안](../brainstorm/web-gui-subtitles.md#채택한-시안과-검토-근거)은 대체된 디자인의 역사적 근거이며, 현재 화면 요구의 증거로 쓰지 않아요.
- [출처 표본 기록](../brainstorm/web-gui-subtitles.md#공개-자막-경로-조사)은 Drive 개별·ZIP, Tistory 일반 첨부·WinPNG, Naver HTTP 첨부의 실제 바이트와 형식 확인 근거예요.
  출처별 수신 경로의 묶음이 trss에서 적용본까지 가는 것은 [0076](../archive/tickets/4-store-apply-and-replace/0076-eight-paths-end-to-end.md)이 여덟 경로로 개발 환경에서 확인했어요(2026-10-06). 링크 유효기간은 확인하지 않았어요.
- [서버 브라우저 비교](../brainstorm/web-gui-subtitles.md#일반-chromium-직접-연결-비교)는 새 프로필의 일반 Chromium에서 사람이 CAPTCHA를 해결한 뒤 서버 파일 수신에 성공한 표본이에요.
  Selenium 구성 실패의 단일 원인, 지속 성공, LAN·VPN 배포, trss 내부 화면과 최종 배치의 증거는 아니에요.
- [재생기 근거](../brainstorm/web-gui-subtitles.md#재생기-파일명과-폰트-호환-근거)와 보관·적용 ADR의 IINA 숨김 검색 제외는 문서·소스 조사예요.
  실제 기기에서는 사용자가 실제 서버의 작품 폴더를 Infuse로 열어, 적용본은 자막으로 보이고 `.trss/`의 보관본은 보이지 않는 것을 확인했어요([0061](../archive/tickets/4-store-apply-and-replace/0061-infuse-placement-check.md)·[0084](../archive/tickets/5-deployed-verification/0084-three-players.md), 2026-10-07).
  IINA와 팟플레이어, 폰트 적용은 관찰하지 않았어요.
- nyaa 검색 RSS의 반환 범위, SubsPlease·Erai-raws 릴리스 이름의 CRC32 관례, Anissia 4분기 제작자 등록 비율은 2026-09-29의 표본 조회이며 [RSS 수집 명세](collection.md)에서 그 한계를 함께 적어요.

출처별 종단 간 처리, 교체 비교 화면, 보호된 내부 인증 화면, 배치와 대기 동작, 구독에서 첫 수집까지의 흐름을 모두 충족하기 전에는 전체 구현 완료로 표시하지 않아요.
실제 배포·재생기·사용 관찰이 남으면 코드 검증 결과와 분리해 해당 범위와 남은 조건을 기록해요.

## 남은 구체화와 비차단 보류

- CPU·메모리 한도, nyaa 추가 검색의 묶음 크기와 요청 간격 같은 구체 수치는 대표 입력 측정 후 구현 시 명시하고 해당 경계를 검증해요.
  압축 해제 한도는 [압축 해제의 격리와 한도](subtitles.md#압축-해제의-격리와-한도)에 정했고, 실제 서버에서도 측정했어요(0065, 2026-10-08).
- 중복 영상의 세부 선택 흐름은 같은 릴리스의 수정본을 뺀 나머지 경우에 대해 보류해요.
  보류 중에도 오배치 금지 요구는 유지해요.
- 외부 알림은 보류해요.
  외부 알림 없이 웹에서 후보·실패·인증 필요를 확인하는 요구는 유지해요.

## 검증 표

요구마다 실제 사용에서 본 것(날짜와 티켓), 테스트로 확인한 것(크레이트와 파일, 테스트 이름), 확인하지 않은 것을 나눠 적었어요. 테스트는 요구를 가장 직접 겨눈 것만 골라 적었고 같은 요구를 다루는 다른 테스트는 나열하지 않았어요.
이 표는 2026-10-10에 `6e46ef1`에서, [0113](../tickets/0113-remaining-area-tests.md)이 남은 영역의 테스트를 나눈 뒤 만들었어요. 실제 사용은 배포한 서버(j4105)와 로컬 개발 환경이고, 무엇으로 봤는지(서버 DB 사본, iPhone Safari 등)를 티켓이 적은 경우 괄호에 적었어요. `서버(0.5.0)`은 원격 화면이 생기기 전의 0.5.0을 본 것이에요.
행은 요구의 항목 하나(최상위 글머리 기호, 규칙을 담은 문단, 입력·결과 표의 행)이고, 한 항목 안에서 확인 방법이 갈리는 부분은 칸 안에서 `<br>`로 나누고 `(1)`, `(2)`로 번호를 붙였어요. 외부 서비스, 브라우저, 디스크를 본 기록은 trss를 본 것이 아니라서 `근거만:`으로, 가짜 출처나 바꿔 넣은 응답으로 본 개발 환경의 확인은 `참고(가짜 출처):`로, 실제 데이터 없이 빈 화면이나 스크래치 DB를 헤드리스 브라우저로 본 확인은 `참고(헤드리스 브라우저):`로 따로 적었어요.
코드가 명세와 다른 요구는 `코드가 이 요구와 달라요`로 적고, 리팩터링 뒤에 그것을 고칠 티켓을 붙였어요.

### 확인하지 않은 요구

실제 사용에서 본 것도 없고 테스트도 없는 요구는 48행 중 17행이에요.

- 시각 방향과 테마의 8행 모두: 영화관 톤과 면 구분, 라이트·다크와 모드 보존, 빨간색 한정과 할 일 종류의 색, 상태 배지의 모양과 아이콘, 체크 표시의 초록, 버튼 색, 카드 링크를 올려 둔 표시, 두 모드의 구분과 4.5:1 대비예요. 넷은 시안 검토나 헤드리스 브라우저로만 봤어요. 빨간 할 일 개수 배지와 `교체 승인` 배지의 물음표는 코드가 요구와 달라서 [0133](../tickets/0133-web-notation-rules.md)에서 고쳐요.
- 문구와 표기의 9행: 자리에 맞춘 문구, 짧은 명사구와 버튼 이름, 해요체와 배너 제목, 설명 줄, 경로의 글꼴, 띄어쓰기 단위 줄바꿈, 같은 뜻은 한 단어, `표: 바꾸기·지우기·고르기·되돌리기·찾기·찾음·만들기`, `표: 수집 개념`이에요. 화면 문구 전체를 이 규칙으로 검토한 기록이 없어요. 같은 뜻의 상태 이름은 [0131](../tickets/0131-waiting-state-names.md)에서 맞춰요.

나머지 행에도 일부만 확인한 요구가 있어요. 그 부분은 행마다 `확인하지 않은 것`에 적었어요.
