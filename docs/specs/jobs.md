# 작업과 인증 명세

## 목표와 범위

사용자가 해야 하는 일과 자막 작업의 진행을 한 곳에서 찾게 하고, 인증·교체 승인 같은 사람의 입력을 trss 안의 작업 상세에서 끝내게 해요.
자막이 왜 들어오지 않았는지를 할 일 화면 한 곳에서 찾을 수 있어야 하며, 서버 브라우저·worker가 멈추거나 재시작해도 받은 파일과 승인·대기 상태를 잃지 않아야 해요.

이 문서는 할 일의 종류와 할 일 화면, 작업 상세, 서버 브라우저 인증과 수명, 작업 결과와 체크포인트·중단 복구의 요구를 담당해요.
각 할 일을 만드는 조건은 해당 기능 문서([RSS 수집](collection.md), [자막](subtitles.md), [라이브러리](library.md))에, 교체 비교의 내용은 [자막 명세](subtitles.md#교체-비교와-승인)에, 웹 명령과 상태 갱신의 계약은 [웹 앱 공통 명세](web-app.md#웹-명령과-상태-갱신)에 있어요.
근거와 선택 배경은 [웹 재설계 주제 문서](../brainstorm/web-redesign.md#화면-구조)에 있어요.

## 요구사항과 완료 기준

### 할 일

할 일은 사용자가 처리하거나 결정할 것만 모은 목록이며, 일곱 종류를 두 무리로 나눠요.

| 무리 | 종류 | 만드는 조건 | 이어지는 곳 |
| --- | --- | --- | --- |
| 처리 필요 | `인증 필요` | 자막 수신에 사람의 CAPTCHA 해결이 필요해요. | 작업 상세의 인증 |
| 처리 필요 | `받기 실패` | Transmission 추가 실패나 영상 수정본 대체의 실패처럼 사용자가 손봐야 하는 수집 실패예요([RSS 수집](collection.md#채널과-다운로드-규칙)). | 수집 기록의 해당 항목, 대체 실패는 작품 상세의 해당 회차 |
| 처리 필요 | `교체 승인` | 기존 자막을 바꿀 새 자막이 준비돼 비교를 기다려요. | 작업 상세의 교체 승인 |
| 처리 필요 | `회차 확인 필요` | 받은 영상이나 자막의 회차를 확정하지 못했어요. | 작품 상세의 해당 회차 |
| 제안 | `제목 후보` | 제목 대기 구독이 있을 때 새 작품 제목이 처음 나타났어요([방영작 구독](collection.md#방영작-구독)). | 수집 화면 구독 탭 |
| 제안 | `자막 구독` | 제작자 미정 작품에 자막 후보가 처음 나타났어요([구독 제작자 자동 수신](subtitles.md#구독-제작자-자동-수신)). | 작품 상세의 [자막 후보 구역](library.md#자막-후보-구역) |
| 제안 | `보관 제안` | 방영이 끝났거나 새 항목이 없는 규칙이에요([규칙 보관](collection.md#규칙-보관)). | 수집 화면의 규칙 보관 |

- `처리 필요`는 수집이나 적용을 막는 일이고, `제안`은 미뤄도 되는 일이에요.
  메뉴의 개수 배지는 처리 필요만 세며, 처리 필요가 없으면 제안이 있어도 배지를 두지 않아요.
- 실패한 자막 작업은 할 일로 올리지 않아요.
  아래 `자막 작업`의 맨 위가 `실패`라서 따로 올리지 않아도 놓치지 않아요.
- 할 일은 조건이 풀리면 사라지고, 사용자가 처리한 할 일이 다시 나타나지 않아요.
  같은 작품의 같은 조건은 할 일 하나로 모아요.
- 한 상태는 할 일 종류·회차 배지·기록에서 같은 이름을 써요.
  예전의 `교체 승인 대기`·`회차 미확정`·대기 사유 `연결 확인`은 쓰지 않으며, 자막 출처에 연결되지 않아 다시 확인을 기다리는 작업은 `자막 대기`이고 까닭은 줄의 설명에 적어요.

### 할 일 화면

할 일 화면은 두 구역이에요.
위에는 사용자가 처리할 할 일을, 아래 `자막 작업`에는 진행 중·대기·실패·완료한 자막 작업을 두어, 화면이 길어지는 비용을 처리할 것을 위에 두는 순서로 다뤄요.
머리는 라이브러리·수집처럼 제목과 한 줄 설명이고, 소제목 옆의 개수는 숫자만 든 개수 칩이에요.

- 처리 필요는 표지를 카드 높이의 세로 열로 두는 카드로, 제안은 그 아래 얇은 줄 목록으로 보여줘요.
  처리 필요 안에서는 빨간 종류(`인증 필요`·`받기 실패`)를 먼저 두고, 이 둘만 카드 테두리도 빨갛게 해요.
  종류별 색은 [시각 방향과 테마](web-app.md#시각-방향과-테마)를 따라요.
  처리 필요의 버튼은 모두 파랑, 제안의 버튼은 무채색이에요.
- 카드는 위에 종류 배지와 시각, 그 아래 제목, 대상, 사유 순서예요.
  대상과 사유는 ` · `로 한 줄에 잇지 않고 정보 종류마다 모양을 달리해요.
  회차는 굵게, 제작자는 자막 아이콘과 함께, `다시 받기` 같은 맥락은 작은 태그로 대상 줄에 두고, `CAPTCHA`·`Transmission 연결 거부` 같은 사유는 다음 줄에 둬요.
  교체 승인의 사유 줄은 `대사 추가 2`·`대사 변경 12`·`타이밍 3` 같은 숫자 태그예요.
  설명은 종류 이름을 되풀이하지 않고, 표지가 없으면 다른 화면과 같은 중립 아이콘을 둬요.
  여러 장에 같은 뜻으로 붙는 `가장 시급` 같은 배지는 두지 않아요.
- 할 일에서 작품 상세나 작업 상세로 들어가면 해당 위치로 스크롤하고 초점을 옮기며, 도착 위치를 테두리로 잠깐 강조하지 않아요.
- `자막 작업`은 `실패` → `대기 중` → `진행 중` → `최근 완료` 순서이고, 완료는 다섯 개만 보인 뒤 무한 스크롤로 이어져요.
  `실패`에는 `일부 실패`도 들고, `대기 중`에는 `인증 필요`, `자막 대기`, 재시작 뒤 확인하지 못한 파일 때문에 멈춘 `보류`, worker가 아직 집지 않은 `시작 대기` 순서로 들어요.
  작업 줄은 라이브러리 목록처럼 48px 표지와 올려 두면 밝아지는 배경을 쓰고, 완료한 작업은 소제목이 이미 완료를 말하므로 줄마다 배지를 붙이지 않아요.
  `실패` 배지는 수집 기록과 같은 모양(빨간 테두리·경고 아이콘)이에요.
- 작업 줄을 누르면 설명 한 줄과 이름표 달린 칸을 펼치고, 작업 상세로 가는 `자세히`만 둬요.
  실패 작업의 설명 앞에는 [실패 분류](#공통-수신-결과와-실패-분류)를 작은 태그로 둬요.
  인증·교체 승인을 기다리는 작업 줄도 같은 방식이며, `인증`·`비교`는 위의 할 일 카드에만 두어 한 화면에 같은 동작을 두 번 두지 않아요.
- 할 일도 작업도 없으면 빈 화면 문장으로 알려요.

| 입력·상태 | 필요한 화면 결과 |
| --- | --- |
| 인증 필요 1·교체 승인 1·보관 제안 3·제목 후보 1 | 처리 필요 카드 두 장이 인증 필요, 교체 승인 순서로 있고, 아래 제안 줄 목록에 넷이 있어요. 메뉴 배지는 2예요. |
| 제안만 있음 | 처리 필요 구역이 없고 메뉴 배지도 없어요. |
| 자막 작업 실패 2·대기 5·진행 1·완료 115 | 실패 2개가 맨 위에 있고, 완료는 다섯 개 뒤 스크롤하면 이어져요. 실패는 할 일에 없어요. |
| 교체 승인을 기다리는 작업 줄을 펼침 | 설명과 `자세히`만 있고 `비교`는 없어요. |

### 작업 상세

모든 자막 작업은 할 일 메뉴 아래 `/todo/job/<작업>`의 한 종류의 작업 상세 페이지를 쓰고, 원격 인증과 교체 비교·승인은 그 페이지의 한 상태예요.
작품 상세·할 일 카드의 `인증`·`비교`와 자막 작업 줄의 `자세히`가 모두 이 페이지로 이어지며, PC·휴대폰 모두 외부 창이나 PC 우측 패널로 대신하지 않아요.
페이지는 위에서부터 돌아가기 링크, 머리, 작업 단계, 상태에 따른 주 영역, 경로, 작업 기록으로 한 번에 스크롤해요.

- 머리에는 작품·시즌·회차, 제작자, 출처와 현재 상태를 둬요.
  [직접 찾기와 자막 올리기](subtitles.md#직접-찾기와-자막-올리기)로 만든 작업도 같은 작업 상세를 쓰며, 출처 자리에 `직접 찾기`·`올림`을 적어요. 직접 찾기 작업의 주 영역은 원격 화면이에요.
  올린 작업(`origin = upload`)은 만들어질 때 이미 `완료`예요. 단계는 `받기`만 있고 `직접 올림`·`올림` 표시와, 제작자를 정하지 않았으면 `제작자 알 수 없음`을 머리에 적어요.
  주 영역은 `올린 파일`(자막·폰트·압축 파일 종류별 목록)과 `뺀 파일`(이름과 이유)이에요. 압축 파일(ZIP·RAR·7z·gzip·bzip2·xz·tar, 나뉜 조각은 조각마다, 첫 조각의 형식으로)에는 형식과 `묶음 분석을 기다려요`, `안의 분류는 묶음 분석을 기다려요`를 적어요.
  작업 줄에는 `올린 파일`과 `뺀 파일`의 개수를 적고, 받은 회차 수는 적지 않아요.
- 작업 단계는 `후보 발견`·`게시물 열기`·`인증`·`받기`·`보관`·`적용`처럼 작업이 거친 단계와 지금 단계를 시각과 함께 보여줘요.
  교체 작업은 `적용` 대신 `교체 승인`에서 멈춰요.
  휴대폰에서는 머리를 줄이고 단계를 한 줄 요약으로 접어, 인증 작업의 사람 확인 상자가 첫 화면에 보이게 해요.
- 주 영역은 상태에 따라 인증 화면, [교체 비교와 승인](subtitles.md#교체-비교와-승인), 또는 회차·파일별 결과예요.
  일괄 작업은 회차·파일별 실제 결과와 남은 이유를 보여주고, 일부 실패를 `모두 완료`로 표시하지 않아요.
  받은 파일은 형식과 크기를, 실패한 회차·파일은 [실패 분류](#공통-수신-결과와-실패-분류)와 이유, 알면 HTTP 상태를 보여줘요.
  ZIP은 `묶음으로 받음`을 함께 적어요. 안의 어느 파일이 어느 회차의 것인지는 받은 뒤 [묶음 분석](subtitles.md#자막-묶음-분석과-안전한-배치-판단)이 정해요.
  이름에 `폰트`, `글꼴`, `font`(대소문자 무시)가 든 ZIP은 회차 묶음이 아니라 게시물의 폰트라서 `묶음으로 받음` 대신 `폰트 묶음`이라고 적어요.
- 경로 구역은 영상, 적용본, 보관본의 경로를 구분해 보여줘요.
  경로는 본문 글꼴로 보여주고, 해시·시각표 같은 값만 고정폭으로 둬요.
- 작업 기록은 일어난 일을 최신 순으로 적고, 덧붙이는 정보는 흐리게 옆에 둬요.
  쿠키·토큰·서명 다운로드 URL은 기록하지 않아요.

| 입력·상태 | 필요한 화면 결과 |
| --- | --- |
| 390×844 휴대폰에서 인증 필요 작업을 엶 | 한 줄로 접힌 단계 아래 원격 화면의 사람 확인 상자가 첫 화면 안에 보여요. |
| 브라우저가 유휴 종료된 인증 필요 작업을 엶 | 단계는 `인증`에 머물고, 페이지를 열면 브라우저와 인증 화면이 다시 준비돼요. 이미 받은 파일과 기록은 그대로예요. |
| 교체 승인 작업을 PC에서 스크롤 | 결정 카드가 화면 위쪽에 붙어 따라와요. |
| 3개 회차 중 1개 적용 실패 | 회차별 결과에 성공 2·실패 1과 실패 이유가 나오고, 상태는 `일부 실패`예요. |

### 작업 화면 안의 인증과 브라우저 수명

- 인증이 필요한 작업은 서버 소유 Chromium을 직접 실행하고 CDP로 제어해요.
  서버가 게시물 열기와 정상 다운로드 시작을 처리하고, 작업 상세에 원격 화면·마우스·키보드 입력을 제공해요.
  원격 화면은 CDP 화면 전송(`Page.startScreencast`)과 입력 전달(`Input.dispatch*`)을 웹이 중계하는 방식이에요(사용자 결정, 2026-10-02). 가상 디스플레이를 VNC로 보내는 방식도 인증은 통과했지만 데스크톱 창 전체가 축소돼 보여 누르기 어려웠어요([원격 화면 비교](../brainstorm/web-gui-subtitles.md#2026-10-02-원격-화면과-기기-폭-비교)).
  Chromium은 가상 디스플레이 위에서 창 있는 모드로 실행해요. 헤드리스(`--headless=new`)는 erulabo가 연결을 끊었고, 브라우저를 위장하지 않으므로 쓰지 않아요.
  서버는 정상 다운로드 시작 요소를 화면 가운데로 스크롤한 뒤 눌러, 그 자리에 뜨는 사람 확인 상자가 PC와 휴대폰의 첫 화면 안에 있게 해요(사용자 요구, 2026-10-02). 인증 상자 자체는 조작하지 않아요.
  서버 브라우저는 광고·추적 주소를 막아 화면을 가리는 광고와 자원 사용을 줄여요. 인증 서비스의 주소는 막지 않아요.
  별도 주소·창으로 이동하거나 외부 사이트를 iframe으로 넣는 방식으로 요구를 대체하지 않아요.
- 사용자는 인증을 PC와 휴대폰에서 비슷하게 하므로, 원격 페이지는 화면을 연 기기가 보고하는 화면 크기·기기 픽셀 비율·터치 여부를 기기 지표 흉내로 받아 그 기기의 배치로 보여요. 창 크기 바꾸기는 일반 창이 약 500px 밑으로 줄지 않고 느려서 쓰지 않아요.
  렌더링 배율은 1배예요(사용자 결정, 2026-10-02). 2배는 휴대폰에서 선명하지만 작업 중 메모리 최고치가 약 1.25GiB로 1배보다 크게 늘었어요.
  두 기기가 같은 작업을 열면 마지막으로 연 기기의 크기를 따르고, 먼저 연 화면은 바뀐 크기의 프레임을 받아요.
  크기가 바뀌는 동안과, 바뀌기 전 프레임을 보고 만든 입력은 버려서 엉뚱한 자리에 가지 않게 해요.
  원격 화면 옆에는 원격 페이지 `새로고침`을 둬요.
- Chromium은 앱과 분리한 비공개 컨테이너에 배치해 의존성과 자원 한도를 분리해요.
  작업 실행 측의 시작·종료 제어와 서버 수신 파일 전달을 통합하고, 별도 컨테이너에서도 아래 인증·유휴 종료·프로필 폐기 조건을 확인해야 해요.
- 실제 웹 화면에서 후보 선택 → 인증 필요 → 직접 CAPTCHA 해결 → 서버 파일 수신을 이어서 관찰해요.
  수동 파일 다운로드·업로드·이동이나 CAPTCHA 자동 우회를 개입시키지 않고, 받은 파일의 형식·무결성과 해당 작업의 결과를 확인해야 해요.
- 원격 화면을 제공하는 페이지와 화면·입력 WebSocket 모두 같은 접근 보호를 받아요([접근 경계](web-app.md#접근-경계와-기기)).
  원본 CDP 포트를 별도로 노출하지 않으며, HTTPS 배포에서는 WSS 연결과 앞단 프록시의 연결 전달·접근 차단을 실제 배포 경로에서 확인해요.
  외부 페이지에서 보낸 허용되지 않은 상태 변경·원격 입력 연결과 보호 계층을 우회한 직접 접속도 거부되는지 확인해요.
  원격 입력은 해당 작업과 브라우저 실행에 묶고, 끝난 실행의 연결이 다음 작업을 조작하지 못하게 해요.
- 브라우저가 작업을 실행 중이지 않고 사용자 조작도 없는 유휴 시간의 초기 설계 기본값은 5분이며, 만료하면 브라우저를 종료하되 인증 필요 작업은 남겨요.
  이후 해당 작업을 열면 페이지와 필요한 인증 화면을 자동으로 다시 준비하고, 이미 받은 파일과 작업 기록도 유지해요.
  유휴 종료가 실행 중 다운로드를 끊지 않는 경우와, 인증 필요 상태에서 종료 후 재개하는 경우를 구분해 확인해요.
  상태 조회는 브라우저를 시작하거나 사용자 조작 시각을 갱신하지 않아요.
  원격 연결이 끊기면 같은 작업의 유효한 실행에 다시 연결하되, 유휴 종료된 브라우저를 연결 재시도만으로 계속 새로 띄우지 않아요.
  화면을 열어 둔 채 입력 없이 유휴 종료를 맞은 경우와, 실제로 돌아와 재개한 경우를 나눠 관찰해요.
- 실행마다 새 전용 프로필을 쓰고 종료 시 쿠키·사이트 저장 상태를 버려요.
  작업 기록과 받은 파일은 프로필과 별도로 보존하고, 쿠키·토큰·서명 다운로드 URL을 설정 내보내기나 일반 로그에 노출하지 않아요.
  프로필 폐기 후에도 작업과 받은 자막이 남고 다음 실행에 이전 사이트 상태가 재사용되지 않는지 확인해요.
- 동시 브라우저 작업 수의 초기 설계 기본값은 1개이며, 유휴 시간과 동시 작업 수는 [설정의 공통 정책](settings.md#공통-정책)에서 조정해요.
  이는 실측 성능값이 아닌 보수적인 시작값이에요.
  동시성을 높인 설정에서는 작업별 화면·입력·프로필·수신 파일이 섞이지 않고 설정한 상한이 지켜지는지 확인해요.
  서버 브라우저 컨테이너의 메모리 한도 시작값은 768MiB예요. 2026-10-02에 1배·광고 차단·이 한도에서 인증과 수신이 되었고 실제 프로세스 메모리는 약 450MiB였어요([원격 화면 비교](../brainstorm/web-gui-subtitles.md#2026-10-02-원격-화면과-기기-폭-비교)). 브라우저는 작업이 있을 때만 떠 있어요.
  CPU·메모리와 압축 해제의 총량·파일 수·중첩 깊이·실행 시간 한도는 대표 정상 묶음과 과다 입력을 측정해 구현 시 유한한 값으로 정해요.
  한도 도달은 성공이나 동일 파일 판정과 구분해 표시하고, 이미 보관한 파일·승인 대기·인증 필요 작업을 잃지 않아야 해요.

### 작업 결과

- 불명확한 연결, 미지원·손상 묶음, 수신 실패, 적용 실패를 성공으로 표시하지 않아요.
  재개가 이미 받은 정상 파일의 수동 재업로드를 요구하지 않아요.
- 인증 필요·교체 승인·영상 대기·자막 대기는 서로 다른 대기 사유로 구분해요.
- worker 재시작 후에는 기록과 실제 파일을 대조해 확인 가능한 지점부터 미완료 작업을 자동 재개해요.
  수신·보관 완료가 확인된 파일은 재사용하고, 인증·승인이 필요한 단계는 기다리며, 파일 반영 여부가 불명확하거나 승인 대상이 달라졌으면 보류해요.
  수신 후 중단, 복사 반영 전후 중단, 승인 대상의 외부 변경을 각각 발생시켜 중복 수신·무승인 변경·허위 완료 없이 재개 또는 보류되는지 확인해요.
  다른 환경으로 설정·보관 정보를 가져오는 동작에 이 자동 재개 정책을 적용하지 않아요.

#### 공통 수신 결과와 실패 분류

여섯 경로가 함께 쓰는 수신 결과와 실패 분류예요(티켓 0038).
신호는 [2026-10-02의 경로 확인](../brainstorm/web-gui-subtitles.md#2026-10-02-경로별-재확인)(티켓 0033)과 2026-10-03의 Tistory 재확인에서 관찰한 사실이에요.
Tistory 일반 첨부가 이 결과로 처음 구현됐고, 이후 출처(0041–0044)는 경로만 더해요. Blogger·Google Drive(0042)가 두 번째, Naver 블로그 첨부(0044)가 세 번째 경로예요.

출처에서 파일 하나를 받으려는 시도는 `받음`이나 아래 실패 분류 하나로 끝나요.
게시물 열기는 그 밖에 `인증 필요`나 `자막 대기`로 멈출 수 있고, 둘 다 실패가 아니에요.

- `받음`은 수신 영역의 파일(경로·바이트 수·SHA-256), 검증으로 판별한 형식(ZIP·ASS·SRT·SMI·그 밖), 사이트가 준 파일 이름, 응답의 HTTP 상태와 `Content-Type`, 파일 정보 스냅샷, 받은 시각을 가져요.
  받은 바이트 수와 견주는 길이는 응답이 미리 알린 정확한 길이(`Content-Length`, Naver의 `attachFileSize`)뿐이에요.
  게시물이 표시한 크기(Tistory의 `0.01MB`)는 대략적이라 견주지 않고 스냅샷에만 남겨요.
- 파일 정보 스냅샷은 출처마다 다른 값을 이름과 함께 `[이름, 값]`의 JSON 배열로 저장해, 같은 경로의 다음 스냅샷과만 견줘요.
  Tistory는 게시물의 `article:modified_time`, 표시 크기(`declared_size`), 응답에 있으면 `Last-Modified`(`last_modified`)를 남겨요.
  Google Drive 파일은 게시물의 수정 시각(Blogger는 JSON-LD의 `dateModified`가 있는 테마에서만, Tistory 본문의 링크는 `article:modified_time`), 응답의 `Last-Modified`(`last_modified`), 알린 길이(`content_length`)를 남겨요.
  Naver 첨부는 게시물의 작성 시각(`publish_date`, 이 글의 영역 `id="post-view<logNo>"` 안의 `se_publishDate`가 `2026. 6. 23. 5:19`처럼 날짜일 때만이에요. 하루가 안 된 글은 `3시간 전`처럼 보여서 남기지 않아요. 그래서 처음 스냅샷에 없던 `publish_date`가 다음 스냅샷에 생기는 것은 변경이 아니고, 스냅샷 비교(0050)는 이것을 변경으로 보지 않아야 해요), `attachFileSize`의 바이트 수(`attach_file_size`), Naver가 표시한 제한(`blocked`, 있을 때만)을 남겨요. 수정 시각과 `Last-Modified`는 없어요.
  이 값으로 Anissia 줄이 그대로인 게시물 수정을 찾는 일은 [구독 제작자 자동 수신](subtitles.md#구독-제작자-자동-수신)의 받은 뒤 14일 재확인이에요.
- 실패는 분류, 이유 한 문장, 응답이 있었으면 HTTP 상태·`Content-Type`(매개변수를 뺀 미디어 형식)·응답 크기를 가져요.
  실패한 회차도 분류를 가지며, 작업은 첫 실패 회차의 분류로 보여요.
- 서명 URL·쿠키·토큰은 저장하지 않고 작업 기록·로그·API 응답에도 내지 않아요.
  출처가 게시물에서 얻은 서명 주소는 그 파일을 받을 때까지 메모리에만 있어요.
  파일은 서명이 든 쿼리를 뺀 주소의 호스트와 경로(`tistory:blog.kakaocdn.net/dna/…`)로 알아봐요.
- 분류는 응답 신호로 가려요.
  Drive·Tistory·Naver 모두 정상 파일을 `application/octet-stream`으로 줘서 `Content-Type`만으로는 정상과 오류가 갈리지 않고, 오류는 `text/html`로 와요.
  오류 응답의 크기는 신호가 아니에요. Tistory의 거절된 서명 URL은 2026-09-26에 552바이트, 2026-10-03에 150바이트였어요.
  파일인지와 형식은 받은 바이트로 확인해요(아래 검증).

| 분류 | 관찰한 신호 | 다음 동작 |
| --- | --- | --- |
| 받음 | `200`에 검증을 통과한 바이트예요. 알린 길이가 있으면 받은 바이트 수와 같아요. Tistory 수모모 492는 2026-10-03에 쿠키·Referer 없이 11,379바이트 ZIP(멤버 `Seihantai - 24.srt` 하나)이었어요. | 분석으로 넘겨요. |
| 인증 필요 | erulabo에서 카드를 누르면 Turnstile이 떠요. 다른 다섯 경로에서는 인증을 보지 못했어요. | 실패가 아니라 `인증`에서 기다려요. |
| 자막 대기(다른 곳에 있음) | 게시물은 열리는데 자막이 이 앱이 아직 받지 못하는 곳에 있어요. Tistory 게시물에 첨부도 Drive 파일 링크도 없이 본문 안에 `*.kakaocdn.net`의 `.png` 이미지가 있거나(WinPNG, harne1 739), Tistory·Blogger 본문에 Drive 파일 링크 없이 Drive 폴더 링크(`drive/folders/`)만 있어요. 본문은 아래 Tistory·Blogger 본문 컨테이너이고, 그 밖의 스킨 링크·썸네일은 보지 않아요. 별명따위 블로그는 모든 게시물의 본문 밖에 `자막 모음(작업 중)` 폴더 링크가 있어요. | 실패가 아니라 출처가 없는 주소처럼 `자막 대기`로 기다리고, 어디에 있는지를 이유로 보여줘요. worker가 시작할 때 다시 줄에 세워요. |
| 만료 | 서명 URL이 `400`·`403`·`404`·`410`에 `text/html`로 거절돼요. Tistory는 `404`, Naver는 `400`에 3,452바이트, erulabo는 60초가 지난 요청이 `403` HTML이었어요(2026-09-26). | 출처가 게시물을 한 번 다시 읽어 같은 파일의 새 주소로 한 번만 다시 받아요. 새 주소도 거절되면 `만료`, 다시 읽은 게시물에 그 파일이 없으면 `원본 없음`으로 끝나요. |
| 원본 없음 | 게시물이 `404`·`410`(네 호스트 모두 404 HTML, Tistory는 1,952바이트, Blogger는 76,064바이트, Naver는 없는 글의 내부 페이지가 106,631바이트이고 없는 블로그가 3,228바이트)이거나, Drive 파일이 `404`에 `text/html`(2026-10-02에 1,704바이트, 2026-10-03에 1,652바이트)이거나, 다시 읽은 게시물에서 파일이 사라졌어요. Drive가 로그인을 요구하는 것(`accounts.google.com`으로의 리디렉션, 로그인 페이지, `401`·`403`)도 여기예요. 제작자가 파일 공유를 끈 것이라 그 파일만의 일이고 다시 시도해도 받을 수 없어서, 사이트 구조의 변화(`출처 구조 바뀜`)가 아니라 원본이 공개돼 있지 않은 것으로 봐요. 이 응답은 아직 보지 못했어요. Naver의 없는 글은 내부 페이지가 `404`에 `게시물이 삭제되었거나 다른 페이지로 변경되었습니다.` 알림(`var msg`)이고, 글이 아닌 페이지의 알림에 이 `삭제되었거나` 문구가 있으면 `200`으로 와도(아직 보지 못했어요) 여기예요. 그 밖의 알림은 `출처 구조 바뀜`이고 알림 글자(100자까지)를 이유에 적어요. Naver가 첨부를 악성 코드(`maliciousCodeYn`)나 이용 제한(`punishType`이 `0`이 아님)으로 표시한 것도 여기예요. 표시된 첨부는 요청하지 않아요. 그 파일만의 일이고 다시 시도해도 받을 수 없어서예요. 표시된 첨부는 아직 보지 못했어요. | 다시 시도하지 않고 실패로 알려요. 후보 기록은 남겨요. |
| 파일 아님 | 받은 바이트가 아래 검증을 통과하지 못해요. `200`인데 `text/html` 오류 페이지이거나, 비어 있거나, 알린 길이와 다르거나, CRC가 맞지 않는 ZIP이거나, 이름이 약속한 형식이 아니에요. 파일 하나의 상한(200MiB)을 넘거나, 응답이 `identity`가 아닌 `Content-Encoding`으로 왔어요. Drive가 파일 대신 `200` `text/html`로 준 다운로드 확인 페이지(검사할 수 없는 큰 파일의 바이러스 검사 경고)와 할당량 초과 페이지도 여기예요. 응답은 파일이 아니지만 게시물과 사이트 구조는 그대로라서 `출처 구조 바뀜`이 아니에요. 확인을 건너뛰는 요청(`confirm`)은 보내지 않아요. 두 페이지는 아직 보지 못해서, 알려진 표시(`download-form`, `Quota exceeded`)로 이유만 나누고 그 밖의 Drive HTML도 같은 분류예요. | `받음`으로 기록하지 않고 받은 바이트를 지워요. 다시 시도하지 않아요. |
| 출처 구조 바뀜 | 게시물은 열리는데 단서가 없어요. `.fileblock`·`aPostFiles`·Drive 링크·`og-link-button`·본문 `.png`가 없거나, Naver가 게시물(`aPostFiles`를 선언한 내부 페이지) 대신 보안 확인(CAPTCHA)이나 다른 페이지를 줬거나, 알아보는 본문 컨테이너가 없거나(Blogger는 본문이 둘 이상인 블로그 첫 화면도), 여섯 경로에 없는 주소(유튜브·블로그 첫 화면)이거나, 뷰어 스크립트를 읽지 못하거나, 뜻밖의 HTTP 상태예요. 따라갈 수 없는 곳으로의 리디렉션(`3xx`)도 여기예요. Drive 링크가 있는데 후보의 회차를 받을 링크가 없을 때도 여기이고, 이유가 회차를 밝혀요(`게시물에 24화 파일이 없어요`). | 실패로 알리고 사람이 확인해요. 같은 호스트의 다른 작업도 같은 이유로 실패할 수 있어요. |
| 네트워크 실패 | 연결 실패, 시간 초과, `5xx`, `429`, 받는 도중 끊김, 파일 하나가 요청부터 15분 안에 다 오지 않음이에요. `429`는 아직 보지 못했어요. | 게시물 열기와 파일 받기 각각, 같은 회차 실행 안에서 2초와 10초를 기다려 두 번 더 시도해요. 그래도 실패하면 이 분류로 끝나요. 기다리는 동안 종료 요청이 오면 바로 멈추고, 다음 시작이 이어가요. |

- 한 출처는 같은 호스트에 1초 이상 간격을 두고 요청해요. 첨부 25개인 게시물(isulbi 40)도 한꺼번에 받지 않아요. Google Drive는 Tistory와 Blogger가 함께 쓰는 하나의 간격이에요.
- Tistory는 `.fileblock a[href]` 중 `https`이고 호스트가 `*.kakaocdn.net`·`*.daumcdn.net`인 주소만 첨부로 봐요. 그 밖의 링크는 첨부가 아니며, 남는 첨부가 없으면 첨부 없는 게시물로 읽어요.
  - 첨부 없는 게시물은 본문 컨테이너 안만 봐요. 컨테이너는 실제 게시물에서 본 `.tt_article_useless_p_margin`·`.contents_style`(편집기가 넣는 클래스, harne1 739·felia 1187·sumomomo 491 모두)과 `#article-view`(sumomomo 491에서 위 클래스를 감싸요)예요(2026-10-03). 스킨에는 본문 밖에 `img1.daumcdn.net/thumb/…?fname=<kakaocdn .png>` 썸네일 같은 링크와 이미지가 있어서, 본문을 찾지 못하면 `자막 대기`가 아니라 `출처 구조 바뀜`이에요.
  - 요청에는 쿠키도 `Referer`도 없어요. HTTP 클라이언트의 자동 `Referer`를 꺼서, 리디렉션에서도 서명 주소가 다음 호스트로 가지 않아요.
  - 리디렉션은 처음 요청이 갈 수 있는 곳으로만 열 번까지 따라가요. 게시물은 `https`인 `tistory.com` 블로그로, 파일은 `https`인 위 CDN 호스트로만 가요. 그 밖은 따라가지 않고 그 `3xx` 응답을 `출처 구조 바뀜`으로 남겨요.
- Blogger는 `https`인 `<블로그>.blogspot.com` 게시물을 쿠키 없이 읽어요(`http` 주소도 `https`로 요청해요). 게시물이 리디렉션되면 `https`인 `blogspot.com` 블로그로만 따라가요.
  - 본문은 `.post-body`이고(2026-10-03에 C소라·카이란·별명따위·에텔레로사·soso_sagak·이마이·fanic의 모든 테마), 게시물 하나에 하나예요. 본문이 없거나 둘 이상이면 `출처 구조 바뀜`이에요. 본문 밖의 링크는 보지 않아요.
  - 본문의 링크 가운데 Drive 파일 링크와 그 글자를 읽어요. 같은 파일을 가리키는 링크가 여럿이면 글자가 있는 첫 링크의 글자를 써요.
- Naver는 `blog.naver.com`·`m.blog.naver.com`의 글 주소에서 블로그와 글 번호를 읽어요(0044). 주소는 `/<blogId>/<logNo>`(개발 DB의 Naver 줄 일곱 개 모두), `PostView.naver`·`PostView.nhn`의 `?blogId=…&logNo=…`, `/<blogId>?Redirect=Log&logNo=…` 꼴이에요. 그 밖의 주소는 요청하지 않고 `출처 구조 바뀜`이에요.
  - 글 주소의 페이지는 2.9KB의 프레임이고 글은 내부 프레임 `PostView.naver?blogId=…&logNo=…&redirect=Dlog&widgetTypeCall=true&noTrackingCode=true&directAccess=false`에 있어요. 없는 글도 프레임은 `200`이라서 프레임은 읽지 않고, 그 내부 페이지를 `https`로 쿠키 없이 바로 읽어요. 모바일 페이지(`m.blog.naver.com`)에는 `aPostFiles`가 없어서 같은 내부 페이지를 읽어요. 리디렉션은 `https`인 두 블로그 호스트로만 따라가요.
  - 첨부는 내부 페이지의 `aPostFiles[<n>] = JSON.parse('…')` 목록이에요. 글의 페이지인지는 이 대입이나 `aPostBaseInfo[<n>] = "<logNo>|…"`로 알아봐요. 선언(`var aPostFiles = [];`)만으로는 글의 페이지가 아니고, 그 밖의 언급(`aPostFiles[0].length`, 본문의 글자)은 목록이 아니에요. 글의 페이지가 아니면 위 알림·CAPTCHA·다른 페이지로 나눠요. 기록 하나에 이름(`encodedAttachFileName`), 정확한 크기(`attachFileSize`, `44,155`처럼 쉼표), 표시(`maliciousCodeYn`·`punishType`), 서명 주소(`encodedAttachFileUrl`)가 함께 있어서 이 목록만 읽어요. 저장 버튼(`a.se-file-save-button`)은 같은 주소를 되풀이할 뿐이라 맞춰 보지 않아요. `aPostBaseInfo`가 있으면 이 글 번호로 시작하는 것의 목록만 읽고, 이 글 번호가 없으면 `출처 구조 바뀜`이에요. `aPostBaseInfo`가 없으면 목록이 하나일 때만 그 목록을 읽고, 둘 이상이면 `출처 구조 바뀜`이에요. 읽을 수 없는 대입(`JSON.parse('…')`나 `[]`가 아닌 값)도 `출처 구조 바뀜`이에요.
  - 표시는 닫힌 쪽으로 읽어요. `maliciousCodeYn`이 비었거나 `false`·`n`·`0`(대소문자 무시)일 때만, `punishType`은 비었거나 `0`일 때만 표시가 없는 것으로 봐요. 스냅샷의 `blocked`에는 `malicious_code`나 `punish_type=<값>`을 남기고, 값은 영문자·숫자 16자까지만 남겨요.
  - 한계: 한 글에 이름이 같은 첨부가 둘이면 첫 것만 받아요. 글꼴 첨부만 있는 글은 본문의 Drive 링크를 보지 않고, 받을 자막 첨부가 없다는 이유로 `출처 구조 바뀜`이에요.
  - 파일은 토큰 없는 `naver:<blogId>/<logNo>/<파일 이름>`으로 알아봐요. 주소는 `https`인 `download.blog.naver.com`일 때만 받고, 토큰이 글을 읽을 때마다 바뀌어서 메모리에만 둬요.
  - 받기는 쿠키·`Referer` 없는 GET이고, 리디렉션 없이 `200` `application/octet-stream`, `Content-Length`, `Content-Disposition: attachment; filename="…"; filename*=UTF-8''…`로 와요(2026-10-03). `Last-Modified`·`ETag`는 없어요. 리디렉션은 `download.blog.naver.com`으로만 따라가요.
  - 응답이 알린 길이가 `attachFileSize`와 다르면 받지 않고 `파일 아님`이에요. 길이를 알리지 않으면 받은 바이트를 `attachFileSize`와 견줘요.
  - 토큰이 거절되면(`400` `text/html` 3,452바이트) Tistory처럼 내부 페이지를 한 번 다시 읽어 같은 파일의 새 주소로 한 번 더 받아요.
  - 실제 글의 내부 페이지에는 언제나 안부게시판·댓글용 CAPTCHA 프레임(`captchalayeredframe`)이 숨어 있어서, CAPTCHA라는 말은 `aPostFiles`가 없는 페이지에서만 이유를 가려요. 첨부는 `aPostFiles`에서만 얻어요.
  - 첨부가 없는 글은 본문(`.se-main-container`, 옛 편집기는 `#postViewArea`)의 Google Drive 링크를 Tistory처럼 받아요. 그런 글은 아직 보지 못했어요.
- Google Drive 파일 링크는 Blogger 본문과 첨부 없는 Tistory·Naver 본문에서 같은 규칙으로 받아요(0042).
  - 링크는 `drive.google.com/file/d/<id>/…`(C소라·카이란·에텔레로사·soso_sagak·이마이·fanic·felia), `drive.google.com/uc?…id=<id>&export=download`(별명따위), `open?id=<id>` 꼴이에요. 로그인한 계정 번호(`/u/<n>/…`)나 Workspace 도메인(`/a/<domain>/…`)이 앞에 붙은 같은 꼴도 같은 링크예요. ID는 영문자·숫자·`-`·`_`이고, 파일은 서명 없는 `drive:<id>`로 알아봐요. 주소가 늘 같아서 다시 얻을 것이 없고 `만료`도 없어요.
  - 받기는 `drive.usercontent.google.com/download?id=<id>&export=download`에 쿠키·`Referer` 없는 GET이에요. Drive가 응답마다 쿠키(`NID`)를 줘도 다음 요청에 싣지 않아요. `drive.google.com/uc?export=download&id=<id>`는 `303`으로 이곳에 넘겨요(2026-10-03). 리디렉션은 `https`인 `drive.google.com`·`drive.usercontent.google.com`으로만 따라가요.
  - 정상 응답은 `200`, `application/octet-stream`, `Content-Length`, `Last-Modified`, `Content-Disposition: attachment; filename="…"`이에요. 파일 이름은 `filename*` 없이 UTF-8 바이트 그대로 와서 UTF-8로 읽어요. 게시물은 링크 글자만 주므로, 받은 파일의 이름은 이 응답의 이름이고 이름이 없으면 링크 글자예요. 이름은 바이트를 쓰기 전에 기록해서 재시작이 찾는 임시 파일 이름과 같아요.
- Drive 링크와 Naver 첨부가 여럿인 게시물에서는 후보의 회차에 맞는 것만 받아요. 규칙은 Drive 링크의 글자와 Naver 첨부의 파일 이름만 보고, 회차 비교는 [자막의 회차 대응](library.md#자막의-회차-대응)의 숫자 키(앞자리 0과 소수 끝의 0을 뺀 문자열, 부동소수점 없음)예요.
  - 한 회차를 밝힌 링크(`24화`·`제24화`·`EP24`·`고양이와 용 08`·`… 12.zip`)는 그 회차가 후보의 회차와 같을 때 받아요. 범위를 밝힌 링크(`1 ~ 12화`·`03-04`·`… 1-12.zip`)는 후보의 회차가 범위 안이면 받아요.
  - 범위는 `~`로 잇거나 띄어 쓰지 않은 `-`로 이은 두 숫자예요(`1-3`·`03-04`). 띄어 쓴 `-`는 어느 쪽에 `화`(`話`·`회`)가 붙었을 때만 범위이고(`1 - 12화`), 아니면 제목과 회차를 가르는 것이라 뒤 숫자 한 회차예요(`Title 3 - 05`는 5화). 두 끝이 같거나 거꾸로면(`03-03`·`24-12`) 범위가 아니라 숫자 하나하나로 읽어요. 둘 다 맞으면 둘 다 받아요(에텔레로사의 `공각기동대 03`과 `1-3`).
  - 회차를 밝히지 않은 글꼴 링크(`폰트`·`글꼴`·`font`)는 언제나 받아요. ASS가 쓰는 글꼴이에요. 회차를 밝힌 글꼴 링크(`24화 (폰트 포함)`·`1화 폰트`)는 그 회차의 링크예요. 글꼴 파일(`.ttf`·`.otf`·`.ttc`·`.woff`·`.woff2`)은 이름의 숫자와 상관없이 글꼴이에요(수퍼소닉EX의 `H2MPRB.TTF`·`a옛날목욕탕L.ttf`).
  - 회차를 밝히지 않은 압축 파일(`자막 모음.zip`)은 받아요. 안의 회차는 묶음 분석이 정해요.
  - 회차를 밝힌 링크가 하나도 맞지 않고, 게시물의 자막 링크(글꼴이 아닌 링크)가 회차를 밝히지 않은 하나뿐이면 그것을 받아요. 그림만 있는 링크(카이란), `자막 다운로드`(felia), `BLACK TORCH`(soso_sagak)처럼 게시물 하나에 파일 하나인 경우예요.
  - 그 밖에는 `출처 구조 바뀜`이고 이유가 회차를 밝혀요(`게시물에 24화 파일이 없어요`). 회차를 밝히지 않은 링크가 둘 이상이면 고를 수 없다고 적어요. Drive 파일 이름으로 다시 고르지 않아요. 이름은 받아야 알 수 있고, 그런 게시물은 아직 보지 못했어요.
  - 링크 글자의 숫자는 홀로 선 것만 회차로 봐요. 글자에 붙은 숫자(`S2`·`4th`·`2기`·`3장`·`1080p`·`그랑블루3`)는 회차가 아니고, `제`·`第`·`EP`·`E` 뒤의 숫자는 회차예요. 시즌 뒤의 `E`도 회차를 표시해요(`S02E01`은 1화). `E`·`EP` 뒤의 범위는 끝 숫자 앞에 표시가 다시 와도 범위예요(`E01-E12`·`EP01-EP12`·`S02E01-E12`는 1–12화). `화`(`話`·`회`)가 붙은 숫자를 먼저 보고, 없으면 마지막 숫자를 봐요(`… 4 24.zip`는 24화예요). 표시가 없는 숫자 가운데 연도(1900–2099의 네 자리, `Title 05 (2026)`), 날짜(`2026-10-03`), 1000을 넘는 수, 점으로 글자에 붙은 숫자(`H.264`·`AAC2.0`), `.5`가 아닌 소수(`2.0`)는 회차로 보지 않아요. `화`가 붙으면 이런 수도 회차예요(`1001화`·`13.5화`). 주소 그대로인 글자는 회차를 밝히지 않은 것으로 봐요.
  - 한 작업의 여러 회차가 같은 게시물이면 글꼴처럼 겹치는 파일은 한 번만 받아요(아래).
- 파일 하나는 200MiB까지, 요청부터 마지막 바이트까지 15분 안에 받아요. 알린 길이가 상한을 넘으면 받기 전에, 알리지 않았으면 넘는 순간 멈춰요(`파일 아님`). 기한을 넘기면 `네트워크 실패`예요.
- 길이 비교는 언제나 `Content-Length`로 해요. 응답에 `identity`가 아닌 `Content-Encoding`(대소문자 무관)이 있으면 그 바이트와 길이는 인코딩의 것이라 받지 않고 `파일 아님`이에요. 클라이언트는 아무것도 풀지 않아요.
- Tistory 첨부(`.fileblock`)는 게시물이 제공하는 파일을 모두 받아요. 시리즈 전체 ZIP, 회차별 SMI, 폰트 ZIP을 가리지 않아요(isulbi 40, kiriu 323). Drive 링크와 Naver 첨부는 위 규칙으로 고른 것만 받아요.
  어느 파일이 어느 회차의 것인지, 받은 파일이 최종본인지(`미완성(2)`·`마커표시본` 같은 임시본)는 [묶음 분석](subtitles.md#자막-묶음-분석과-안전한-배치-판단)이 정해요.
  한 작업 안에서 같은 파일은 한 번만 받아요.
- 받은 바이트는 완료(`done`)로 기록하기 전에 검증해요.
  재시작 복구가 `받음`(`fetched`) 기록의 임시 파일을 공개하기 전과, 공개 뒤 기록 전에 멈춘 파일을 완료로 기록하기 전에도 같은 검증을 해요. 그때 파일이 아니면 그 시도를 실패로 끝내고 바이트를 지운 뒤 새로 받아요.
  - 비어 있으면 파일 아님이에요.
  - BOM과 공백 뒤 `<`로 시작하면서 `<SAMI`가 없으면(대소문자 무관) 웹 페이지라 파일 아님이에요.
  - 200MiB를 넘는 파일은 파일 아님이에요.
  - `PK\x03\x04`로 시작하면 ZIP으로 열어 모든 멤버를 끝까지 읽어 CRC를 확인해요. 열 수 없거나 CRC가 맞지 않으면 파일 아님이에요. 이 빌드가 읽지 못하는 압축 방식이나 암호가 걸린 멤버는 판정하지 않고 넘겨요. 풀린 크기가 1GiB를, 멤버가 10,000개를 넘으면 파일 아님이에요.
    열기 전에 파일 끝의 끝 레코드(ZIP64면 그 레코드)가 주장하는 멤버 수를 직접 읽어, 10,000개나 파일 길이가 담을 수 있는 수(목록 항목 하나는 최소 46바이트)를 넘으면 열지 않고 파일 아님으로 끝내요. 주석 안에 숨긴 끝 레코드도 같이 봐요.
  - BOM 뒤 `[Script Info]`는 ASS, `<SAMI`는 SMI, 시각표 줄(`00:00:01,000 --> …`)이 있으면 SRT예요. `WEBVTT`로 시작하면 시각표 줄이 있어도 SRT가 아니라 `그 밖`이에요. UTF-8·UTF-16의 BOM과, ASCII를 그대로 쓰는 옛 인코딩을 읽어요. 그 밖은 `그 밖`으로 남겨 분석이 정해요.
  - 이름의 확장자가 ZIP·ASS(SSA)·SRT·SMI(SAMI)를 약속하는데 바이트가 그 형식이 아니면 파일 아님이에요.
  - 검증 자체가 비정상으로 끝나면(panic) 파일인지 판정하지 않고, 바이트를 지우지 않은 채 그 시도를 `보류`해요.
  - ZIP 멤버가 자막인지는 받을 때 판정하지 않아요(결정, 0038). 초안은 자막 멤버가 없는 ZIP을 파일 아님으로 봤지만, 폰트 ZIP처럼 자막이 없는 ZIP도 정상 파일이라 멤버의 내용은 묶음 분석이 판정해요. ASS의 `[Events]`도 받을 때는 보지 않아요.
- 기록은 `subtitle_job_files`의 `format`·`failure`·`http_status`·`content_type`·`response_size`·`snapshot`과 `subtitle_job_items.failure`예요(마이그레이션 36).
  네트워크 실패로 다시 시도한 시도는 `abandoned`로 남기되 분류와 응답 사실을 함께 남겨요.
  SQLite 정수에 들지 않는 크기는 저장하지 않아요.
  `받음`까지 간 시도가 실패하면 실패를 공개할 경로와 함께 먼저 기록하고, 그 바이트를 지운 뒤 경로 기록을 지워요. 경로 기록이 사라지면 다음 시도가 같은 이름을 쓸 수 있어요.
  지우기는 성공했거나 파일이 이미 없을 때만 지운 것으로 봐요. 그 밖의 오류면 그 시도를 `보류`해요.
- 작업 상세는 파일마다 형식과 크기를, 실패한 회차·파일에는 분류 이름(`원본 없음`·`만료`·`파일 아님`·`출처 구조 바뀜`·`네트워크 실패`)과 이유, 알면 HTTP 상태를 보여줘요.
  할 일 화면의 `자막 작업` 줄은 펼친 설명 앞에 실패 작업의 분류를 보여줘요.
- 관찰하지 못한 후보: 키가 필요한 WinPNG예요. 어느 분류에 넣을지는 해당 출처를 구현할 때 정해요. Naver가 악성·제한으로 표시한 첨부는 `원본 없음`으로 정했고(0044), Naver의 비공개 글과 보안 확인 페이지는 위처럼 분류를 정했지만 실제 응답은 보지 못했어요. Drive의 접근 제한·확인·할당량 화면은 위처럼 분류를 정했지만(0042) 실제 응답은 아직 보지 못했어요. 이전 공유 링크의 `resourcekey`가 필요한 파일도 보지 못했고, 받지 않아요.

#### 체크포인트와 중단 복구

복구 정보는 SQLite의 작업·항목·파일 동작 기록에 남기며, 별도 범용 워크플로 엔진이나 작품별 복원 목록을 도입하지 않아요.
선택한 후보와 출처, 수신 시도 ID와 전용 임시 경로, 검증된 수신물·자산 참조, 불변 계획과 승인 참조, 각 파일 동작의 ID·의도·전후 조건·완료 증거를 구분해 저장해요.
다운로드 완료와 정상 자막 판정은 별개이며, 파일 효과를 시작하기 전에 그 의도를 커밋하고 실제 결과를 확인한 뒤 완료를 기록해요.
임시 영역은 보관 자산과 구분하고, 작업의 임시 파일이나 보호 복사본을 YAML 자산으로 가져오는 경로를 허용하지 않아요.

| 중단 위치 | 복구 판정과 처리 |
| --- | --- |
| 인증 필요·수신 중 | 선택과 인증 필요 상태를 유지해요. 완료 기록이 있는 수신물은 바이트를 확인해 재사용하고, 완료 여부가 불명확하면 보류해요. |
| 바이트 수신 후 완료 기록 전 | 신뢰할 수 있는 예상 길이·내용 식별 정보나 독립적인 완료 증거가 있어야 완료로 인정해요. 현재 길이·로컬 해시·파싱 가능 여부만으로 수신 완료를 만들어내거나 곧바로 다시 받지 않아요. |
| 분석·압축 해제 중 | 검증된 원 수신물에서 필요한 분석만 다시 수행해요. 이미 받은 묶음을 다시 다운로드하지 않으며, 정상 추출물·미지원 항목·실패를 구분해요. |
| 보관 준비 후 등록 전 | 새 자산의 예상 경로와 바이트, 재사용 자산의 참조를 기록하고 검증해요. 새 목적지가 이미 다른 파일로 차 있으면 덮어쓰지 않아요. 공개된 파일과 기록의 관계가 불명확하면 예약과 증거를 남겨 보류해요. |
| 보관 완료·영상 대기·승인 대기 | 검증한 보관본과 폰트 자산 참조를 유지하고 필요한 조건만 기다려요. 브라우저나 worker의 수명이 이 자료를 삭제하지 않아요. |
| 적용 준비 후 공개 경로 변경 전 | 보관본과 별개인 임시 복사본의 바이트를 검증하고 준비된 파일의 객체 식별 증거를 기록해요. 계획·대응·승인·기존 상태가 여전히 유효하고 효과가 아직 실행되지 않았음이 확인되면 이어가요. |
| 공개 경로 변경 후 완료 기록 전 | 기록한 임시 파일의 객체와 최종 파일의 연결, 바이트·경로·계획이 일치하는 등 해당 동작의 결과임을 확인할 수 있어야 완료로 대조해요. 이름이나 원하는 바이트가 있다는 이유만으로 앱이 반영했다고 기록하지 않아요. |
| 여러 경로 중 일부만 반영 | 확인된 완료 효과는 유지하고 항목·경로별 결과를 보여줘요. 새 파일의 정상 반영을 확인한 뒤 승인된 이전 경로를 제거하며, 제거 실패를 전체 성공이나 자동 전체 롤백으로 처리하지 않아요. |
| 제거 후 완료 기록 전 | 파일이 없다는 사실만으로 이 작업이 제거했다고 단정하지 않아요. 행위의 결과를 확인할 수 없으면 보호 자료를 유지하고 보류해요. |

기존 자막을 교체·제거하기 전에는 승인한 기존 바이트의 독립적인 임시 보호 복사본을 준비해요.
공간 부족이나 복사·검증 실패는 파괴적인 효과 전에 중단하고, 실패·불명확한 부분 완료가 남으면 보호 복사본도 남겨요.
임시 보호 자료는 해당 작업이 확인된 완료 상태에 이르거나 사용자가 불명확한 결과의 정리를 명시한 뒤 정리하며, 외부에서 바뀐 공개 경로 위로 자동 복원하지 않아요.
임시 복사본을 최종 경로에 공개하는 내부 이름 변경은 보관 원본을 이동해 적용하는 방식이 아니며, 보관 원본은 독립적으로 남아야 해요.
새 경로 추가에는 지원되는 덮어쓰기 금지 방식을 사용하고, 사전 존재 검사 뒤 일반 덮어쓰기로 이어지는 방식을 동등한 보호로 취급하지 않아요.

복구를 맡는 worker는 같은 호스트의 이전 파일 쓰기 주체가 더 이상 실행할 수 없다는 배타성을 확보해야 해요.
DB 임대 시각이 지났다는 이유만으로 멈춰 있던 이전 worker와 새 worker를 동시에 파일 쓰기 주체로 두지 않아요.
독립적인 회차·파일은 각각 진행할 수 있지만, 겹치는 목적지·제거 경로와 폰트 자산의 정리는 직렬화해요.
폰트 정리는 남은 보관본뿐 아니라 진행 중·보류·복구 작업의 참조도 보호하고, 참조가 없는지 확인한 뒤 삭제하는 사이에 새 참조가 생기는 경쟁도 막아야 해요.
불명확한 임시 파일이나 미등록 파일을 이름만 보고 쓰레기로 지우지 않아요.

회차 대응 변경과 한 파일 효과가 겹치면 먼저 확정된 쪽을 기준으로 처리해요.
대응 변경이 먼저이면 반영 전에 계획을 다시 확인하고, 파일 효과가 먼저이면 실제 완료 경로는 유지한 채 남은 작업을 재평가해요.
효과 자체가 불명확한 중단 상태는 먼저 실제 파일과 대조하며, 새 대응이 그 불명확한 파일의 이동·삭제 권한을 주지는 않아요.
인증·영상 대기처럼 오래 멈춘 작업 전체 기간에 대응 설정을 잠가두지 않아요.

영상 수정본 대체의 이전 영상 제거와 이름 변경도 파일 동작의 의도와 완료 증거를 기록해요.
이전 영상은 보호 복사본 없이 되돌릴 수 없게 제거하므로, 제거 전에는 새 영상의 수신·CRC32 확인이 끝났다는 기록이 있어야 하고, 제거 뒤에는 목적지 이름이 비어 있을 때만 이름 변경을 이어가요([영상 수정본의 대체](collection.md#영상-수정본의-대체)).
재시작 뒤에도 새 영상을 지우거나 이름이 겹친 두 파일을 만들지 않아요.

수신 단계는 이 원칙을 다음 순서로 지켜요(티켓 0036).
받은 파일은 앱 데이터 폴더의 수신 영역 `receive/<작업>/<사이트가 준 이름>`에 두고, 한 수신 시도는 자기 임시 폴더 `receive/.tmp/<시도>/`에만 써요.
시도 ID와 임시 폴더를 `의도`로 기록한 뒤 출처가 알린 길이를 기록하고, 바이트를 해시하며 임시 파일에 받아 동기화해요.
알린 길이와 다르면 실패로 끝내고 그 바이트를 지워요.
길이·SHA-256·임시 파일의 객체(`장치:inode`)·공개할 경로를 `받음`으로 기록한 뒤 바이트를 [검증](#공통-수신-결과와-실패-분류)해요. 파일이 아니면 실패를 경로와 함께 기록하고, 그 바이트를 지운 뒤 경로 기록을 지워요.
검증을 통과하면 덮어쓰지 않는 이름 바꾸기로 공개하고, 폴더를 동기화한 다음 판별한 형식과 함께 `완료`를 기록해요.
한 작업 안에서 같은 파일(출처가 같은 이름으로 알리는 파일)은 한 번만 받고, 다른 회차에는 그 수신을 가리키는 기록을 남겨요.
재시작한 worker는 회차의 게시물을 다시 열기 전에, 끝나지 않은 기록을 디스크와 이렇게 대조해요. 게시물이 사라졌거나 출처를 쓸 수 없어도 대조는 먼저 끝내요.

| 기록 | 디스크 | 처리 |
| --- | --- | --- |
| 의도 | 임시 파일이 없거나 비어 있음 | 받은 바이트가 없으므로 버리고 새로 시도해요. |
| 의도 | 알린 길이보다 짧은 임시 파일 | 끝까지 받지 못한 것이 확실하므로 그 바이트를 지우고 새로 시도해요. 받기를 마친 파일을 다시 받는 것이 아니에요. |
| 의도 | 알린 길이와 같은 임시 파일 | 알린 길이를 신뢰할 근거로 보고 받음으로 기록한 뒤 검증하고 공개해요. |
| 의도 | 알린 길이가 없거나 그보다 긴 임시 파일 | 보류해요. |
| 받음 | 기록한 객체·길이·해시의 임시 파일 | 검증하고 공개해요. |
| 받음 | 임시 파일 없음, 공개 경로에 기록한 객체·길이·해시 | 검증하고 완료로 기록해요. 파일이 아니면 이 시도의 파일이므로 실패를 기록하고 지운 뒤 경로 기록을 지워요. 검증이 비정상으로 끝나거나 지우지 못하면 보류해요. |
| 받음 | 그 밖 | 보류해요. 같은 바이트가 다른 파일로 있어도 이 시도의 결과로 보지 않아요. |
| 완료 | 공개 경로의 길이·해시가 기록과 같음 | 재사용해요. |
| 완료 | 그 밖 | 보류해요. |
| 실패, 경로 기록이 남음 | 실패 기록과 바이트 삭제 사이에 멈췄어요. | 임시 파일과 공개 경로 중 기록한 객체·길이·해시인 파일만 지우고, 다른 파일은 그대로 둔 채 경로 기록을 지워요. 읽거나 지우지 못하면 보류해요. |

보류한 파일은 그 회차를, 보류한 회차는 그 작업을 보류하며, worker는 보류한 작업을 스스로 다시 집지 않아요. 임시 파일과 공개 경로의 파일은 그대로 남겨요.
수신 기록은 커밋마다 동기화해서, 전원이 꺼져도 파일 효과보다 그 의도의 기록이 먼저 남아요. 다섯 번 시작해도 실행이 한 번도 끝나지 않은 작업은 뒤의 작업을 막지 않도록 보류해요. 실행이 한 번 끝나면, 기다림으로 끝나도, 다시 세요.

위 각 파일 효과 전후와 DB 완료 기록 전후에 중단한 사례를 구분해 검증해요.
공개 후 기록 전의 재시작, 불명확한 제거, 보호 복사 공간 부족, 새 경로의 외부 점유, 멈춘 이전 worker, 폰트 참조 생성과 정리의 경쟁을 관찰해 중복 효과·무승인 변경·허위 완료와 자료 손실을 막는지 확인해요.
실제 파일시스템의 공개·동기화·객체 식별 동작은 구현 환경에서 검증해야 하며, 이 절차를 정한 것만으로 프로세스 중단이나 저장장치 장애의 내구성을 입증한 것은 아니에요.

## 남은 구체화

- 원격 화면은 휴대폰 한 대와 이 개발 PC의 LAN에서만 확인했어요. 다른 휴대폰, VPN·HTTPS(WSS) 경로, 지연, 휴대폰 가상 키보드 입력, CPU 한도에서의 인증은 확인하지 않았어요.
- 사용자는 원격 화면의 스크롤이 부드럽지 않다고 했어요. 인증은 서버가 인증 상자를 가운데에 두므로 스크롤이 필요 없고, 직접 찾기처럼 원격 화면을 둘러보는 경로에서는 부드러우면 좋지만 필수는 아니에요(사용자 판단, 2026-10-02).
- 작업 단계의 이름은 출처마다 다를 수 있어요(인증이 없는 출처는 `인증`을 거치지 않아요).
  출처별 단계 목록의 초안은 아래 [출처별 단계 초안](#출처별-단계-초안)이고, 출처를 구현할 때 실제 코드로 다시 확인해요.

### 출처별 단계 초안

단계 이름은 [작업 상세](#작업-상세)의 `게시물 열기`·`인증`·`받기`를 따르고, 출처에 따라 `파일 찾기`와 `복원`을 더해요.
`브라우저`는 서버 브라우저가 필요한지이고, 모든 경로에서 HTTP로 게시물을 읽을 수 있었어요.

| 경로 | 단계 | 브라우저 |
| --- | --- | --- |
| erulabo | 게시물 열기(HTTP 200 또는 서버 브라우저) → 파일 찾기(카드 `data-file-url`, 카드 제목 `(회차)`) → 인증(카드를 누르면 Turnstile, 사람이 풀어요) → 받기(같은 브라우저가 폴더에 받아요) → 검증(ZIP) | 필요(인증 때문에). 카드 이후는 0032에서 확인해요. |
| Blogger·Drive 개별 | 게시물 열기(HTTPS, `.post-body`의 Drive 파일 링크와 글자, 후보의 회차에 맞는 링크와 `폰트` 링크를 고름) → 받기(`drive.usercontent.google.com/download?id=<id>&export=download`, 쿠키·Referer 없음, Drive 호스트로만 리디렉션, 200MiB·15분 상한, 이름은 `Content-Disposition`) → 검증(공통 규칙). 구현했어요(0042). 작업 단계는 `게시물 열기`·`받기`이고, 파일 찾기는 게시물 열기에 들어요. 첨부 없는 Tistory 본문의 Drive 링크도 같아요. | 불필요. Drive 보기 페이지의 `다운로드` 버튼도 같은 바이트를 받아요. |
| Blogger·Drive 회차 ZIP | 개별과 같아요. 범위를 밝힌 링크(`1 ~ N화`, `… 1-12.zip`)는 후보의 회차가 범위 안일 때 고르고, 받은 ZIP은 CRC를 확인해 묶음으로 받아요. 멤버가 자막 형식인지와 멤버 이름의 인코딩은 묶음 분석이 봐요. 구현했어요(0042). | 불필요. |
| Tistory 일반 | 게시물 열기(HTTPS, CDN 호스트의 `.fileblock a`마다 이름·서명 URL·표시 크기) → 받기(쿠키·Referer 없는 GET, CDN으로만 리디렉션, 200MiB·15분 상한, 거절되면 게시물을 한 번 다시 읽음) → 검증(공통 규칙, ZIP은 모든 멤버의 CRC). 구현했어요(0038). 작업 단계는 `게시물 열기`·`받기`이고, 파일 찾기는 게시물 열기에 들어요. | 불필요. 링크를 누르는 브라우저 다운로드도 같은 ZIP이에요. |
| Tistory WinPNG | 게시물 열기(브라우저) → 파일 찾기(본문에서 주소가 `.png`로 끝나는 이미지) → 복원(이미지를 눌러 스킨의 뷰어가 만든 파일 목록) → 받기(뷰어의 링크나 blob을 폴더로) → 검증(SMI·ASS, 한 PNG에 든 여러 파일) | 필요. 인증이 아니라 뷰어 스크립트 때문이고 사람의 조작은 없었어요. PNG를 HTTP로 받아 직접 복원하는 길은 확인하지 못했어요. |
| Naver 블로그 첨부 | 게시물 열기(HTTPS, 글 주소에서 `PostView.naver?blogId=…&logNo=…` 내부 페이지 주소를 만들어 읽고, `aPostFiles`의 이름·크기·표시·서명 주소에서 후보의 회차에 맞는 첨부와 글꼴 첨부를 고름) → 받기(쿠키·Referer 없는 GET, `download.blog.naver.com`으로만 리디렉션, 200MiB·15분 상한, 거절되면 내부 페이지를 한 번 다시 읽음) → 검증(공통 규칙, 길이는 `attachFileSize`와 같은지). 구현했어요(0044). 작업 단계는 `게시물 열기`·`받기`이고, 파일 찾기는 게시물 열기에 들어요. | 불필요. 브라우저로는 저장 버튼에 이어 `내 컴퓨터 저장`을 한 번 더 눌러야 받아져요. |

- 다운로드가 서버 폴더에 떨어졌는지는 폴더로 판단해요. Naver처럼 새 창이 시작한 다운로드는 페이지 연결로는 `Browser.download*` 이벤트가 오지 않았지만 파일은 폴더에 있었어요.
- 이 표는 개발 PC의 헤드리스 Chromium과 HTTP 클라이언트로 본 것이고, 서버 브라우저 컨테이너([브라우저 수명](#작업-화면-안의-인증과-브라우저-수명))에서의 수신은 출처 구현에서 확인해야 해요.

### 수신 확인에서 미상으로 남은 것

- erulabo 카드 이후의 응답·파일 이름·크기·헤더는 0032에서 사람이 인증한 뒤 확인해요. 그 전에는 erulabo의 `받음` 신호와 파일 정보를 정하지 않아요.
- WinPNG를 서버 브라우저 없이 복원할 수 있는지, 뷰어 스크립트 버전이 바뀌면 같은 PNG의 SMI·ASS 바이트가 달라지는지(하느 762의 12화는 2026-09-26과 크기가 달랐고, 게시물 수정과 스크립트 버전 변경을 가르지 못했어요)는 미상이에요. 뷰어가 만든 바이트를 같은 파일의 판정 근거로 쓰기 전에 확인해야 해요.
- Tistory 서명 URL이 월 말(`expires`가 이달 말 23:59:59 KST)을 지난 뒤의 거절, Naver 토큰의 최대 유효 시간(20분 이상은 확인)은 보지 못했어요.
- 게시물 수정 시각의 변화가 언제나 파일 변경인지는 미상이에요. 글만 고쳐도 바뀌어요.
