# 작업과 인증 명세

## 목표와 범위

사용자가 해야 하는 일과 자막 작업의 진행을 한 곳에서 찾게 하고, 인증·교체 승인 같은 사람의 입력을 trss 안의 작업 상세에서 끝내게 해요.
자막이 왜 들어오지 않았는지를 할 일 화면 한 곳에서 찾을 수 있어야 하며, 서버 브라우저·worker가 멈추거나 재시작해도 받은 파일과 승인·대기 상태를 잃지 않아야 해요.

이 문서는 할 일의 종류와 할 일 화면, 작업 상세, 서버 브라우저 인증과 수명, 작업 결과와 체크포인트·중단 복구의 요구를 담당해요.
각 할 일을 만드는 조건은 해당 기능 문서([RSS 수집](collection.md), [자막](subtitles.md), [라이브러리](library.md))에, 교체 비교의 내용은 [자막 명세](subtitles.md#교체-비교와-승인)에, 웹 명령과 상태 갱신의 계약은 [웹 앱 공통 명세](web-app.md#웹-명령과-상태-갱신)에 있어요.
근거와 선택 배경은 [웹 재설계 주제 문서](../brainstorm/web-redesign.md#화면-구조)에 있어요.

## 요구사항과 완료 기준

### 할 일

할 일은 사용자가 처리하거나 결정할 것만 모은 목록이며, 일곱 종류를 두 무리로 나눠요.

| 무리 | 종류 | 만드는 조건 | 이어지는 곳 |
| --- | --- | --- | --- |
| 처리 필요 | `인증 필요` | 자막 수신에 사람의 CAPTCHA 해결이 필요해요. | 작업 상세의 인증 |
| 처리 필요 | `받기 실패` | Transmission 추가 실패나 영상 수정본 대체의 실패처럼 사용자가 손봐야 하는 수집 실패예요([RSS 수집](collection.md#채널과-다운로드-규칙)). | 수집 기록의 해당 항목, 대체 실패는 작품 상세의 해당 회차 |
| 처리 필요 | `교체 승인` | 기존 자막을 바꿀 새 자막이 준비돼 비교를 기다려요. | 작업 상세의 교체 승인 |
| 처리 필요 | `회차 확인 필요` | 받은 영상이나 자막의 회차를 확정하지 못했어요. 구독 제작자 출처의 [회차 대응](library.md#자막의-회차-대응)이 미정이거나 새 회차가 대응과 어긋난 때, 작업이 [배치 확인](subtitles.md#배치-확인)을 기다리거나 받은 파일을 [보류](subtitles.md#파일의-회차)한 때도 만들어요. | 작품 상세의 해당 회차, 회차 대응은 [자막 후보 구역](library.md#자막-후보-구역)의 그 제작자 묶음, 배치 확인과 보류한 파일은 작업 상세 |
| 제안 | `제목 후보` | 제목 대기 구독이 있을 때 새 작품 제목이 처음 나타났어요([방영작 구독](collection.md#방영작-구독)). | 수집 화면 구독 탭 |
| 제안 | `자막 구독` | 제작자 미정 작품에 자막 후보가 처음 나타났어요([구독 제작자 자동 수신](subtitles.md#구독-제작자-자동-수신)). | 작품 상세의 [자막 후보 구역](library.md#자막-후보-구역) |
| 제안 | `보관 제안` | 방영이 끝났거나 새 항목이 없는 규칙이에요([규칙 보관](collection.md#규칙-보관)). | 수집 화면의 규칙 보관 |

- `처리 필요`는 수집이나 적용을 막는 일이고, `제안`은 미뤄도 되는 일이에요.
  메뉴의 개수 배지는 처리 필요만 세며, 처리 필요가 없으면 제안이 있어도 배지를 두지 않아요.
- 실패한 자막 작업은 할 일로 올리지 않아요.
  아래 `자막 작업`의 맨 위가 `실패`라서 따로 올리지 않아도 놓치지 않아요.
- [직접 찾기](subtitles.md#직접-찾기와-자막-올리기) 작업은 원격 화면에서 기다려도 `인증 필요` 할 일로 올리지 않아요.
  사용자가 스스로 연 화면이고, 사이트 확인이 아니라 사용자의 탐색을 기다리기 때문이에요. 아래 `자막 작업`의 `대기 중`에 `직접 찾는 중`으로 있어요.
- 할 일은 조건이 풀리면 사라지고, 사용자가 처리한 할 일이 다시 나타나지 않아요.
  같은 작품의 같은 조건은 할 일 하나로 모아요.
- 구독 제작자 출처의 `회차 확인 필요`는 저장해 둔 값이 아니라 읽을 때마다 정해요.
  작품에 회차 대응이 미정인 구독 제작자 출처가 있거나, 정한 대응(예외 포함)이 가리키지 못한 회차가 기록돼 있으면 작품마다 할 일 하나가 있어요.
  미정인 출처는 `0`(`00`도 같아요)이 아닌 회차의 관찰이 하나라도 있어야 물어요. 등록 줄만 있는 출처는 받지도 묻지도 않아요.
  대응을 정하거나 예외로 어긋난 회차를 덮으면 다음에 읽을 때 사라지고, 개수 배지는 다른 처리 필요와 함께 세요.
  카드는 가장 앞 시즌의 확인 하나를 이름 붙이고 작품 상세의 그 제작자 묶음으로 이어요.
- 배치 확인을 기다리거나 보류한 파일이 있는 작업의 `회차 확인 필요`는 작업마다 하나이며, 그 작업 상세의 배치 확인 표로 이어져요.
  사용자가 표를 반영하거나 보류한 파일을 모두 정하면 사라져요.
- 한 상태는 할 일 종류·회차 배지·기록에서 같은 이름을 써요.
  예전의 `교체 승인 대기`·`회차 미확정`·대기 사유 `연결 확인`은 쓰지 않으며, 자막 출처에 연결되지 않아 다시 확인을 기다리는 작업은 `자막 대기`이고 까닭은 줄의 설명에 적어요.

### 할 일 화면

할 일 화면은 두 구역이에요.
위에는 사용자가 처리할 할 일을, 아래 `자막 작업`에는 진행 중·대기·실패·완료한 자막 작업을 두어, 화면이 길어지는 비용을 처리할 것을 위에 두는 순서로 다뤄요.
머리는 라이브러리·수집처럼 제목과 한 줄 설명이고, 소제목 옆의 개수는 숫자만 든 개수 칩이에요.

- 처리 필요는 표지를 카드 높이의 세로 열로 두는 카드로, 제안은 그 아래 얇은 줄 목록으로 보여줘요.
  처리 필요 안에서는 빨간 종류(`인증 필요`·`받기 실패`)를 먼저 두고, 이 둘만 카드 테두리도 빨갛게 해요.
  종류별 색은 [시각 방향과 테마](web-app.md#시각-방향과-테마)를 따라요.
  처리 필요의 버튼은 모두 파랑, 제안의 버튼은 무채색이에요.
- 카드는 위에 종류 배지와 시각, 그 아래 제목, 대상, 사유 순서예요.
  대상과 사유는 ` · `로 한 줄에 잇지 않고 정보 종류마다 모양을 달리해요.
  회차는 굵게, 제작자는 자막 아이콘과 함께, `다시 받기` 같은 맥락은 작은 태그로 대상 줄에 두고, `CAPTCHA`·`Transmission 연결 거부` 같은 사유는 다음 줄에 둬요.
  교체 승인의 사유 줄은 `대사 추가 2`·`대사 변경 12`·`타이밍 3` 같은 숫자 태그예요.
  설명은 종류 이름을 되풀이하지 않고, 표지가 없으면 다른 화면과 같은 중립 아이콘을 둬요.
  여러 장에 같은 뜻으로 붙는 `가장 시급` 같은 배지는 두지 않아요.
- 할 일에서 작품 상세나 작업 상세로 들어가면 해당 위치로 스크롤하고 초점을 옮기며, 도착 위치를 테두리로 잠깐 강조하지 않아요.
- `자막 작업`은 `실패` → `대기 중` → `진행 중` → `최근 완료` 순서이고, 완료는 다섯 개만 보인 뒤 무한 스크롤로 이어져요.
  `실패`에는 `일부 실패`도 들고, `대기 중`에는 `인증 필요`, `자막 대기`, 재시작 뒤 확인하지 못한 파일 때문에 멈춘 `보류`, worker가 아직 집지 않은 `시작 대기` 순서로 들어요.
  원격 화면에서 기다리는 직접 찾기 작업(`직접 찾는 중`)은 사이트 확인이 아니므로 `인증 필요`와 함께 앞에 서지 않고, `자막 대기`와 같은 자리에서 만든 순서대로 섞여요.
  작업 줄은 라이브러리 목록처럼 48px 표지와 올려 두면 밝아지는 배경을 쓰고, 완료한 작업은 소제목이 이미 완료를 말하므로 줄마다 배지를 붙이지 않아요.
  남긴 파일 없이 끝난 직접 찾기 작업만 완료 줄에도 `받은 파일 없음` 배지를 붙여요. 받은 것이 없다는 사실이 소제목의 완료와 달라서예요.
  `실패` 배지는 수집 기록과 같은 모양(빨간 테두리·경고 아이콘)이에요.
- 작업 줄을 누르면 설명 한 줄과 이름표 달린 칸을 펼치고, 작업 상세로 가는 `자세히`만 둬요.
  실패 작업의 설명 앞에는 [실패 분류](#공통-수신-결과와-실패-분류)를 작은 태그로 둬요.
  인증·교체 승인을 기다리는 작업 줄도 같은 방식이며, `인증`·`비교`는 위의 할 일 카드에만 두어 한 화면에 같은 동작을 두 번 두지 않아요.
- 할 일도 작업도 없으면 빈 화면 문장으로 알려요.

| 입력·상태 | 필요한 화면 결과 |
| --- | --- |
| 인증 필요 1·교체 승인 1·보관 제안 3·제목 후보 1 | 처리 필요 카드 두 장이 인증 필요, 교체 승인 순서로 있고, 아래 제안 줄 목록에 넷이 있어요. 메뉴 배지는 2예요. |
| 제안만 있음 | 처리 필요 구역이 없고 메뉴 배지도 없어요. |
| 자막 작업 실패 2·대기 5·진행 1·완료 115 | 실패 2개가 맨 위에 있고, 완료는 다섯 개 뒤 스크롤하면 이어져요. 실패는 할 일에 없어요. |
| 교체 승인을 기다리는 작업 줄을 펼침 | 설명과 `자세히`만 있고 `비교`는 없어요. |

### 작업 상세

모든 자막 작업은 할 일 메뉴 아래 `/todo/job/<작업>`의 한 종류의 작업 상세 페이지를 쓰고, 원격 인증과 교체 비교·승인은 그 페이지의 한 상태예요.
작품 상세·할 일 카드의 `인증`·`비교`와 자막 작업 줄의 `자세히`가 모두 이 페이지로 이어지며, PC·휴대폰 모두 외부 창이나 PC 우측 패널로 대신하지 않아요.
페이지는 위에서부터 돌아가기 링크, 머리, 작업 단계, 상태에 따른 주 영역, 경로, 작업 기록으로 한 번에 스크롤해요.

- 머리에는 작품·시즌·회차, 제작자, 출처와 현재 상태를 둬요.
  [직접 찾기와 자막 올리기](subtitles.md#직접-찾기와-자막-올리기)로 만든 작업도 같은 작업 상세를 쓰며, 출처 자리에 `직접 찾기`·`올림`을 적어요. 직접 찾기 작업의 주 영역은 원격 화면이에요.
  직접 찾기 작업(`origin = find`)은 받기를 끝내기 전까지 머리 바로 아래에 원격 화면(`직접 찾기`)과 `받기 끝내기`를 둬요. 실행을 준비하는 동안에는 그 자리에 게시물을 열고 있다고 적어요. 원격 화면의 브라우저 도구(뒤로·앞으로·새로고침·호스트·탭)는 인증 화면과 같아요.
  상태는 원격 화면이 열려 있으면 `직접 찾는 중`, 받기 끝내기를 누른 뒤 받기가 끝나기 전에는 `끝내는 중`, 남긴 파일 없이 끝나면 `받음`이 아니라 `받은 파일 없음`이에요. 끝난 시각은 `끝냄`으로 적어요.
  받기까지의 단계는 거친 것만(`게시물 열기`·`받기`) 있고, 결과는 올린 작업처럼 `받은 파일`(종류별)과 `뺀 파일`(이름과 이유)이에요. 작업 줄에는 `받은 파일`과 `뺀 파일`의 개수를 적어요.
  올린 작업(`origin = upload`)은 만들어질 때 받기가 이미 끝나 있고, worker가 압축 파일을 풀고 묶음을 분석해 배치 확인을 기다릴 때까지 진행 중이에요. 단계는 `받기`에서 시작하고, `직접 올림`·`올림` 표시와, 제작자를 정하지 않았으면 `제작자 알 수 없음`을 머리에 적어요.
  올린 작업과 직접 찾기 작업은 받기 뒤 [배치 확인](subtitles.md#배치-확인)을 거쳐 보관·적용으로 이어져요. 확인을 기다리는 동안 주 영역은 배치 확인 표예요. 확인하기 전에는 `.trss/`에도 영상 옆에도 쓰지 않아, 다른 작품의 게시물에서 받은 파일이 작품 폴더에 남지 않아요. 확인한 뒤에는 받은 결과 아래에 회차·파일별 결과를 보여줘요.
  주 영역의 받은 결과는 `올린 파일`(자막·폰트·압축 파일 종류별 목록)과 `뺀 파일`(이름과 이유)이에요. 압축 파일(ZIP·RAR·7z·gzip·bzip2·xz·tar, 나뉜 조각은 조각마다, 첫 조각의 형식으로)에는 형식을 적고, 푼 압축 파일에는 안에서 나온 파일 수와 그 가운데 자막·폰트 수를 적어요. 안의 파일은 묶음 분석 뒤 배치 확인 표에 나와요. 풀지 못한 압축 파일은 `풀지 못함`과 그 까닭을 적어요.
  작업 줄에는 `올린 파일`과 `뺀 파일`의 개수를 적고, 받은 회차 수는 적지 않아요.
- 작업 단계는 `후보 발견`·`게시물 열기`·`인증`·`받기`·`보관`·`적용`처럼 작업이 거친 단계와 지금 단계를 시각과 함께 보여줘요.
  올리기·직접 찾기는 `받기`와 `보관` 사이에 `배치 확인`이 있어요.
  교체 작업은 `적용` 대신 `교체 승인`에서 멈춰요.
  휴대폰에서는 머리를 줄이고 단계를 한 줄 요약으로 접어, 인증 작업의 사람 확인 상자가 첫 화면에 보이게 해요.
- 주 영역은 상태에 따라 인증 화면, [배치 확인](subtitles.md#배치-확인) 표, [교체 비교와 승인](subtitles.md#교체-비교와-승인), 또는 회차·파일별 결과예요.
  일괄 작업은 회차·파일별 실제 결과와 남은 이유를 보여주고, 일부 실패를 `모두 완료`로 표시하지 않아요.
  받은 파일은 형식과 크기를, 실패한 회차·파일은 [실패 분류](#공통-수신-결과와-실패-분류)와 이유, 알면 HTTP 상태를 보여줘요.
  ZIP은 `묶음으로 받음`을 함께 적어요. 안의 어느 파일이 어느 회차의 것인지는 받은 뒤 [묶음 분석](subtitles.md#자막-묶음-분석과-안전한-배치-판단)이 정해요.
  고르지 않은 회차의 자막은 [보관만 한 것](subtitles.md#고르지-않은-회차)으로, 버린 멤버는 이름과 이유로 적어요.
  파일이 여럿인 묶음은 파일마다 적지 않고 `적용함`·`영상 대기`·`보관만 함`·`회차에 붙이지 않음`·`폰트·첨부`·`버림`으로 나눠 적으며, 사람이 정할 것(`확인 필요`·`보류`)과 `보관·적용 실패`를 그보다 앞에 둬요(0064·0067, 2026-10-05). 줄마다 회차와 까닭을 함께 적어요.
  이름에 `폰트`, `글꼴`, `font`(대소문자 무시)가 든 ZIP은 회차 묶음이 아니라 게시물의 폰트라서 `묶음으로 받음` 대신 `폰트 묶음`이라고 적어요.
- 경로 구역은 영상, 적용본, 보관본의 경로를 구분해 보여줘요.
  경로는 본문 글꼴로 보여주고, 해시·시각표 같은 값만 고정폭으로 둬요.
- 작업 기록은 일어난 일을 최신 순으로 적고, 덧붙이는 정보는 흐리게 옆에 둬요.
  쿠키·토큰·서명 다운로드 URL은 기록하지 않아요.

### 작업 화면 안의 인증과 브라우저 수명

- 인증이 필요한 작업은 서버 소유 Chromium을 직접 실행하고 CDP로 제어해요.
  서버가 게시물 열기와 정상 다운로드 시작을 처리하고, 작업 상세에 원격 화면·마우스·키보드 입력을 제공해요.
  원격 화면은 CDP 화면 전송(`Page.startScreencast`)과 입력 전달(`Input.dispatch*`)을 웹이 중계하는 방식이에요(사용자 결정, 2026-10-02). 가상 디스플레이를 VNC로 보내는 방식도 인증은 통과했지만 데스크톱 창 전체가 축소돼 보여 누르기 어려웠어요([원격 화면 비교](../brainstorm/web-gui-subtitles.md#2026-10-02-원격-화면과-기기-폭-비교)).
  Chromium은 가상 디스플레이 위에서 창 있는 모드로 실행해요. 헤드리스(`--headless=new`)는 erulabo가 연결을 끊었고, 브라우저를 위장하지 않으므로 쓰지 않아요.
  서버는 정상 다운로드 시작 요소를 화면 가운데로 스크롤한 뒤 눌러, 그 자리에 뜨는 사람 확인 상자가 PC와 휴대폰의 첫 화면 안에 있게 해요(사용자 요구, 2026-10-02). 인증 상자 자체는 조작하지 않아요.
  서버 브라우저는 광고·추적 주소를 막아 화면을 가리는 광고와 자원 사용을 줄여요. 인증 서비스의 주소는 막지 않아요.
  별도 주소·창으로 이동하거나 외부 사이트를 iframe으로 넣는 방식으로 요구를 대체하지 않아요.
- 사용자는 인증을 PC와 휴대폰에서 비슷하게 하므로, 원격 페이지는 화면을 연 기기가 보고하는 화면 크기·기기 픽셀 비율·터치 여부를 기기 지표 흉내로 받아 그 기기의 배치로 보여요. 창 크기 바꾸기는 일반 창이 약 500px 밑으로 줄지 않고 느려서 쓰지 않아요.
  렌더링 배율은 1배예요(사용자 결정, 2026-10-02). 2배는 휴대폰에서 선명하지만 작업 중 메모리 최고치가 약 1.25GiB로 1배보다 크게 늘었어요.
  두 기기가 같은 작업을 열면 마지막으로 연 기기의 크기를 따르고, 먼저 연 화면은 바뀐 크기의 프레임을 받아요.
  크기가 바뀌는 동안과, 바뀌기 전 프레임을 보고 만든 입력은 버려서 엉뚱한 자리에 가지 않게 해요.
  원격 화면 위에는 도구 줄을 둬요. 뒤로·앞으로·새로고침 버튼, 지금 보이는 페이지의 호스트(경로·쿼리 없이), 터치 기기에서는 `키보드`예요. 실행의 페이지가 둘 이상이면 그 아래에 탭 줄을 둬요. 탭마다 제목이 있어요. 제목이 없거나 주소를 담았을 수 있으면(제목 없는 페이지에 브라우저가 붙이는 주소, 다른 주소의 인용) 호스트를, 호스트도 없으면 `새 창`을 보여줘요. 보이는 탭은 표시해요. 탭을 누르면 화면이 그 페이지로 옮겨요. 브라우저는 앞에 있는 탭만 그리므로, 웹은 화면에 붙을 때 그 페이지를 앞으로 가져와요(새 창 뒤로 간 처음 탭으로 돌아갈 때). 탭을 고르거나 보이는 탭을 닫으면, 새 페이지의 첫 프레임이 올 때까지 화면을 흐리게 덮고 도는 표시와 `창을 바꾸는 중이에요`를 보여요. 그동안 도구 줄과 탭 줄은 누를 수 없어요. worker가 1초마다, 웹이 2초마다 살펴서 옮기는 데 몇 초 걸릴 수 있어요(사용자 요청, 2026-10-04). worker가 스스로 화면을 옮기면(페이지가 연 새 창으로, 또는 보이던 창이 닫혀 남은 창으로) 같은 표시와 `화면을 불러오는 중이에요`를 보여요. 보이던 페이지가 닫히면(사람이 닫든 스스로 닫히든) 묶음이 바뀌기 전에 소켓이 `ended`(`browser`)로 끝나므로, 화면은 이것도 옮기는 중으로 봐요. 10초 동안 다음 단계가 없으면 표시를 거두고 연결 상태대로 보여줘요(끝난 소켓이면 그 이유와 `다시 열기`). 실행이 처음 연 페이지가 아닌 탭에는 닫기가 있어요. 뒤로는 서버가 페이지를 준비하며 거친 빈 페이지(`about:blank`)로 가지 않아서, 돌아갈 페이지가 없으면 누를 수 없어요. 주소 입력은 없어요. 인증 화면과 직접 찾기 화면이 같은 도구 줄과 탭 줄을 써요. 휴대폰 폭(375px)에서도 가로 스크롤 없이 들어가요.
- Chromium은 앱과 분리한 비공개 컨테이너에 배치해 의존성과 자원 한도를 분리해요.
  작업 실행 측의 시작·종료 제어와 서버 수신 파일 전달을 통합하고, 별도 컨테이너에서도 아래 인증·유휴 종료·프로필 폐기 조건을 확인해야 해요.
  구현했어요(0039, 2026-10-03). 컨테이너(`Dockerfile.browser`)는 항상 떠 있고, 쉬는 동안에는 가상 디스플레이(Xvfb)와 작은 실행기 `trss-browserd`만 담아요(사용자 결정, 2026-10-03).
  worker가 비공개 compose 네트워크로 실행기에 작업의 브라우저 실행을 시작·종료하라고 요청하고, 실행기는 실행마다 새 프로필로 Chromium을 띄워 종료할 때 프로필을 지워요. Docker 소켓은 어디에도 주지 않아요.
  실행기는 `TRSS_BROWSER_TOKEN`이 든 요청만 받고, 컨테이너는 호스트에 포트를 열지 않아요. 실행기 주소와 토큰, 다운로드 폴더는 worker의 `TRSS_BROWSER_URL`·`TRSS_BROWSER_TOKEN`·`TRSS_BROWSER_DOWNLOADS`로 정해요. `TRSS_BROWSER_URL`이 없으면 worker는 브라우저 없이 돌아요. 웹도 같은 `TRSS_BROWSER_URL`·`TRSS_BROWSER_TOKEN`으로 원격 화면을 보여줘요(아래 원격 화면). 웹에 `TRSS_BROWSER_URL`이 없으면 원격 화면은 `unavailable`이에요.
  브라우저는 열라고 받은 사이트의 페이지를 실행해요. 그래서 Transmission이 있는 `trss_net`에는 두지 않고, worker·웹과 나누는 별도 compose 네트워크 `browser_net`에 둬요(worker와 웹은 두 네트워크에 모두 있어요). 이 네트워크는 페이지가 인터넷에 닿아야 하므로 `internal`이 아니에요.
  웹은 로그인이 없으므로 `browser_net`에서 오는 모든 HTTP·WebSocket 연결을 아무것도 읽기 전에 끊어요(사용자 결정, 2026-10-03). 웹은 시작할 때 `TRSS_BROWSER_URL`의 호스트를 풀고(브라우저 컨테이너가 늦게 뜨면 30초까지 다시 시도해요), 그 주소가 든 자기 인터페이스의 직접 연결 경로(`/proc/net/route`)를 `browser_net`의 서브넷으로 삼아요. 서브넷을 찾지 못하거나 그 호스트에 IPv6 주소가 있으면 이유를 남기고 시작하지 않아요.
  compose는 웹의 기본 게이트웨이를 `trss_net`으로 정해요(`gw_priority`, Docker Engine 28 이상). Docker는 게시한 포트를 기본 게이트웨이 네트워크로 넣는데, 정하지 않으면 이름 순서로 `browser_net`이 골라져 LAN에서 온 모든 연결이 `browser_net`의 게이트웨이 주소로 들어왔고 웹이 그것을 모두 거부했을 거예요(2026-10-03, Docker 29.8.2·Compose 5.5.1에서 관찰). 브라우저 페이지가 호스트의 LAN 주소로 게시한 포트에 닿는 경로는 `trss_net`의 게이트웨이 주소로 들어와서 웹의 거부로는 가려낼 수 없어요(사용자 결정, 2026-10-03). 이 경로는 아래 송신 프록시가 사설 주소로 막아요(0053). 웹은 시작할 때 자기 기본 경로(`/proc/net/route`의 기본 경로 중 metric이 가장 낮은 것)의 게이트웨이가 `browser_net` 안에 있으면 `gw_priority`와 필요한 버전(Docker Engine 28·Compose 2.33 이상)을 로그에 적고 시작하지 않아요. 거부한 연결은 연결마다 적지 않고 1분에 한 번까지 그동안의 개수만 적어요.
  `browser_net`은 bridge라서 그대로는 호스트 LAN 주소·Docker 게이트웨이·LAN에 닿아요. 그래서 브라우저의 모든 연결은 실행기 안의 송신 프록시(컨테이너 루프백에서 들어요)를 거쳐요(0053). 프록시는 CONNECT(HTTPS와 두 scheme의 WebSocket)와 절대 형식의 HTTP 요청만 받아요. 이름은 프록시가 직접 풀고, 풀린 주소 가운데 하나라도 공개 주소가 아니면 연결하지 않아요. 공개 주소가 아닌 것은 사설·루프백·링크 로컬·CGNAT(Tailscale 포함)·멀티캐스트·문서용·벤치마크·예약 주소이고, IPv4와 IPv6를 모두 보며, IPv4를 담은 IPv6(대응·호환·6to4)는 담긴 IPv4로 판정해요. 주소 종류와 별도로, 실행기가 시작할 때 컨테이너의 라우팅 표(`/proc/net/route`·`/proc/net/ipv6_route`)에서 컨테이너가 붙은 네트워크와 게이트웨이를 읽어 그 주소도 거절해요. 그래서 사설 대역 밖의 Docker 주소 풀로 만든 네트워크나 IPv6 `browser_net`에도 닿지 않아요. 통과한 이름은 다시 풀지 않고 판정한 그 주소로 연결하므로, 처음엔 공개 주소였다가 사설 주소로 바뀌는 이름(DNS 재바인딩)도 연결마다 막혀요. 거절은 HTTP 요청이면 `403`과 짧은 안내문, CONNECT면 터널 실패예요. 거절한 목적지와 허용한 목적지는 로그에 남기지 않고, 거절한 수만 1분에 한 번까지 남겨요. 요청 머리는 64KiB와 30초까지 읽어요. 이름 풀기는 15초까지 기다리고 한 번에 8개까지만 풀며, 연결은 풀린 주소마다 15초까지 기다려요.
  프록시가 주소로 가려낼 수 없는 길은 막지 못해요. 공유기의 WAN 주소로 들어가 LAN으로 되돌아오는 경로(hairpin NAT)와, 그 WAN 주소를 가리키는 사용자 자신의 도메인은 프록시에게 공개 주소예요. 공유기가 그런 연결을 LAN의 포트 포워딩으로 넘기면 브라우저가 그 포트에 닿을 수 있어요.
  Chromium은 이 프록시와 함께 루프백을 프록시 밖으로 보내는 기본 예외를 없애고(`--proxy-bypass-list=<-loopback>`), QUIC을 끄고(`--disable-quic`), WebRTC가 프록시 밖 UDP를 쓰지 않게(`--webrtc-ip-handling-policy=disable_non_proxied_udp`) 시작해요. 이미지의 관리 정책도 QUIC·프록시 밖 WebRTC UDP·Cast 탐색(`EnableMediaRouter`)을 꺼요. 실행기 설정의 Chromium 인자(`TRSS_BROWSER_CHROMIUM_ARGS`)에 프록시·QUIC·WebRTC 주소 처리·`host-rules`·`host-resolver-rules`에 관한 인자가 있으면 실행기가 시작하지 않아요. 실행기는 Chromium을 Debian의 `/usr/bin/chromium` 래퍼로 띄우고, 래퍼가 읽을 수 있는 `CHROMIUM_FLAGS`·`CHROMIUM_USER_FLAGS`를 Chromium 환경에서 빼요. 래퍼가 더하는 인자는 root만 쓰는 이미지의 `/etc/chromium.d`에서만 와요. 공개 주소가 아니어도 통과시킬 정확한 `IP:포트`(`TRSS_BROWSER_EGRESS_ALLOW`)는 시험 호스트에 사이트를 띄우는 실제 이미지 시험만 쓰고, 배포와 개발 환경에는 두지 않아요.
  호스트 방화벽으로 `browser_net`에서 사설 대역으로 가는 연결을 버리는 규칙은 앱이 있는지 확인할 수 없어서 필수가 아니에요. `docker-compose.trss.yml` 설명에 선택 방어로 예시를 적었어요.
  worker는 실행기를 거쳐 실행의 CDP에 닿고, 원본 CDP 포트는 실행기 밖으로 나오지 않아요. 이 연결이 끊긴 실행은 끝난 것으로 보고 거둬요. 실행기는 Chromium에 `TRSS_BROWSER_TOKEN`을 넘기지 않아요.
  같은 작업에 시작을 다시 요청하면 살아 있는 실행을 돌려주고, 그 요청도 사용한 것으로 쳐서 유휴 시간이 거기서부터 세어져요. 동시 상한을 넘는 작업은 기다리고, 실행기가 종료를 확인해야 자리를 비워요.
  유휴 종료와 작업 단계 시작은 하나의 잠금 안에서 순서가 정해져서, 유휴 종료 직전에 시작한 단계는 실행이 끝나지 않게 하고 종료된 뒤의 단계는 `RunEnded`를 받아요.
  worker의 시작 요청이 시간 초과로 끊겨도 실행기의 시작은 자기 작업에서 끝까지 가요. 이때 worker가 그 실행의 종료를 요청하면 실행기는 진행 중인 시작을 멈추고 기다린 뒤 응답하므로, 끊긴 요청이 Chromium이나 프로필·다운로드 폴더를 남기지 않아요. 실행기는 실행이 끝날 때 프로필과 다운로드 폴더를 지워요.
  실행기 하나는 worker 하나만 써요. worker는 풀을 만들 때 실행기를 초기화하고 반복 점검에서 자기가 모르는 실행을 끝내므로, 둘이 쓰면 서로의 실행을 끝내요. worker는 프로세스가 사는 동안 `<DB 경로>.browser.lock`을 잡고, 이미 다른 worker가 잡고 있으면 서버 브라우저 없이 돌아요.
  받은 파일은 `TRSS_DATA_DIR/browser-downloads/`에서 작업의 수신 영역으로 같은 파일시스템 안의 이름 바꾸기로 옮겨요. worker는 실행기 초기화에 성공한 뒤에 이 폴더를 비우고(실행기에 닿지 못하면 처음 쓸 때 다시 시도해요), 브라우저가 uid 10001로 쓰도록 열어요(모드 1777). worker는 root가 아니라서 자기 소유인 폴더의 모드만 바꿀 수 있고, 스티키 비트 아래에서는 폴더의 주인만 브라우저가 만든 실행 폴더를 지울 수 있어요. 그래서 폴더가 worker의 소유가 아니면(Docker가 없는 폴더를 root로 만든 첫 설치, root로 돌던 이전 배포가 남긴 폴더) 모드가 1777이어도 쓰지 않아요. 이때 worker는 멈추지 않고 경로·주인·고치는 명령을 알린 뒤 서버 브라우저 없이 돌아요(서버 브라우저가 없을 때와 같아요). 서버 브라우저의 잠금은 그대로 쥐어서 다른 worker가 브라우저를 쓰지 못하게 하고, 그래서 이전 worker가 남긴 원격 화면의 묶음은 아무의 것도 아니므로 브라우저가 있을 때처럼 시작할 때 닫아요(실행기 초기화만 건너뛰어요). 잠금을 쥐지 않은 worker는 다른 worker의 것일 수 있어서 묶음을 그대로 둬요.
  받은 파일은 브라우저의 소유(uid 10001)를 그대로 가진 채 수신 영역으로 옮겨져요. 수신 영역의 폴더는 worker 소유라 worker가 지우고 읽을 수 있어요.
  폴더는 침해될 수 있는 브라우저가 쓰는 곳이므로 옮길 때 아무것도 믿지 않아요. 파일 이름은 UUID(Chromium의 다운로드 guid)여야 하고, 실행 폴더는 링크를 따르지 않고 열어 실제 폴더인지 확인해요. 파일은 링크를 따르지 않고 일반 파일이며 이름이 하나뿐인지 확인한 뒤 열어 둔 폴더 기준으로 옮기고, 옮겨 간 자리에서 다시 확인해요. 이 조건에 맞지 않는 파일은 옮기지 않고 오류(`UnsafeDownload`)로 알려요.
  다운로드는 파일 하나 200MiB, 한 실행의 합계 1GiB를 넘으면 받는 도중 취소하고, 120초 동안 진행 보고가 없으면 취소해요. 취소 중인 다운로드는 실행을 바쁘게 붙들지 않아요. 한도 값은 `trss-browser`의 `MAX_DOWNLOAD_BYTES`·`MAX_RUN_DOWNLOAD_BYTES`·`DOWNLOAD_STALL`이에요(구현 시작값이며 측정으로 정한 값은 아니에요).
  worker가 브라우저 이벤트를 따라가지 못해 일부를 놓치면 무엇을 놓쳤는지 알 수 없으므로 그 실행을 끝내고, 작업이 새 실행을 요청해요.
  브라우저는 응답 본문을 읽지 않으므로 페이지마다 `Network.enable`의 버퍼 한도를 0으로 줘서 본문을 보관하지 않아요. 본문을 읽는 출처는 자기 한도로 직접 켜야 해요.
  풀은 자동 연결로 붙은 target마다 설정 명령(page·iframe의 `Network.enable`, `Network.setBlockedURLs`, `Target.setAutoAttach`)과, 디버거를 기다리는 target에는 `Runtime.runIfWaitingForDebugger`를 답을 기다리지 않고 이 순서로 보낸 뒤 답을 함께 기다려요(0054). 브라우저는 한 세션의 명령을 받은 순서대로 처리하므로 차단 목록은 새 창·프레임의 문서가 보내는 요청보다 먼저 걸리고, 디버거를 기다리는 target은 `Network.enable`에 답하지 않지만 그 답이 풀어주는 것을 늦추지 않아요. 설정 명령이 실패하거나 답하지 않아도 target은 풀리고, 실패는 주소 없이 로그에 남아요. 새 창의 최초 이동 요청은 디버거가 붙기 전에 시작돼서 이 차단이 걸리지 않아요(2026-10-04).
  페이지 이동이 다운로드로 바뀌면 브라우저는 먼저 그 문서의 응답(`Network.responseReceived`, 종류 `Document`)을 알리고 같은 주소·프레임으로 다운로드를 시작해요(2026-10-03, 공개 Drive 파일로 새 창과 같은 창 이동 모두). 풀은 프레임마다 마지막 문서 응답(최대 64개)을 기억했다가 같은 프레임·같은 주소의 다운로드에 그 응답의 상태·형식·`Content-Length`·`Last-Modified`(`DownloadAnswer`)와 주소(`DownloadSource`, `Debug`에서 숨겨요)를 붙여요. 주소는 메모리에만 있어요.
  이 기반을 쓰는 출처는 Tistory WinPNG(0043)와 원격 화면의 사이트 확인(0040, 아래)이에요. 원격 화면으로 확인하는 실제 출처는 erulabo([0041](../archive/tickets/3-subtitle-candidates-and-receiving/0041-source-erulabo.md), 아래)예요.
  WinPNG를 읽는 작업은 읽기 직전에 `start(작업 ID)`로 실행을 얻고, 읽는 동안 `busy_guard`로 유휴 종료를 막아요. 작업의 실행이 끝나면(받음·실패·보류·자막 대기) 그 실행도 끝내요. 사이트 확인(`인증 필요`)을 기다리는 작업은 그 확인(0040·0041)을 위해 실행을 남겨 둬요. 작업의 브라우저 실행은 하나뿐이라, 작업의 다른 회차를 읽을 때는 같은 실행을 다시 받아요.
  측정(2026-10-03, Chromium 154.0.8037.92, `--memory 768m`): 이미지는 압축 해제 기준 1,325,423,965바이트(CJK 폰트 포함)예요. 쉬는 컨테이너는 약 17MiB(16.7~21.9MiB), 빈 페이지 하나를 연 실행은 약 286MiB(앞선 측정은 360MiB), 페이지 이동·광고 차단·다운로드를 거치면 약 330MiB, 실행을 끝낸 뒤에는 약 107MiB(대부분 파일 캐시)였어요. 메모리 한도 초과 종료는 없었어요. 같은 날 검토 보강 뒤 이미지를 다시 지어 한 번 더 쟀을 때는 회수 가능한 파일 캐시까지 센 값이 실행 중에 한도(768MiB)까지 찼고(익명 메모리는 약 175~199MiB, 쉬는 컨테이너 39MiB, 실행을 끝낸 뒤 익명 메모리 18MiB) 역시 초과 종료는 없었어요. 첫 값(286MiB)과의 차이는 방금 만든 이미지 파일이 캐시로 잡힌 정도의 차이로 보이지만 그 원인은 확인하지 않았어요. CPU는 재지 않았어요.
- 원격 화면을 구현했어요(0040, 2026-10-03). 서버 쪽과 작업 상세의 웹 화면(`web/`)이 있어요.
  작업 상세는 작업에 원격 화면이 있으면 단계 아래에 `인증` 영역을 둬요. 실행이 묶여 있으면(`ready`) 그 실행의 화면을 영역 폭에 맞춰 그리고, 준비 중(`preparing`)이면 준비하고 있다고, 닫혀 있으면(`closed`) 이유와 `다시 열기`를, 서버 브라우저가 없는 웹(`unavailable`)이면 그렇다고 보여줘요. 페이지가 응답하지 않으면(아래) 화면 위에 `페이지가 응답하지 않아요` 안내와 `새로 띄우기`를 두고, 멈춘 페이지에 붙지 못해 끝난 화면(`stuck`)에는 `새로 띄우기`와 `다시 연결`을 둬요. `새로 띄우기`를 누르면 묶음이 바뀔 때까지 `서버 브라우저를 새로 띄우고 있어요`를 보여요. 페이지가 창을 띄우면 화면 위에 그 창의 카드를 둬요(아래). 휴대폰 폭에서는 머리의 표지와 작품 버튼을 숨겨 확인 상자가 첫 화면 안에 들어오게 해요.
  페이지를 열면 서버에서 처음 읽은 작업에 화면이 있을 때 한 번만 준비 요청을 보내요(캐시에 남은 작업은 이유가 되지 않아요). 2초마다 작업을 다시 읽거나 소켓이 다시 연결할 때는 보내지 않고, 그 밖의 요청은 사람이 누른 `다시 열기`뿐이에요.
  화면은 마우스·터치·휠·키보드·조합 입력·붙여넣기를 받아 그 프레임의 CSS 픽셀로 옮겨 보내요. 키보드는 화면을 누르거나 터치 기기의 `키보드` 버튼으로 숨은 입력칸에 초점이 있을 때만 원격 페이지로 가고, Shift+Esc로 빠져나와요. `새로고침`은 원격 페이지를 새로고침하고, `뒤로`·`앞으로`는 원격 페이지의 방문 기록을 한 칸 옮겨요. 소켓이 저절로 끊기면 작업을 다시 읽고 같은 묶음이 남아 있을 때 0.5초부터 8초까지 다섯 번 다시 연결하고, 서버가 끝낸 소켓은 같은 묶음에 다시 붙지 않아요. 다른 실행이나 같은 실행의 새 묶음(`bound`가 다름)이 오면 그 묶음에 새로 연결해요.
  worker와 웹은 같은 앱 DB와 기존 깨우기 소켓으로 맞춰요. DB의 `subtitle_job_screens`(마이그레이션 45번)는 작업마다 한 행으로 브라우저가 확인을 보여주는 회차, 묶인 실행·페이지와 묶은 시각, 실행이 없는 이유, 준비 요청·응답 시각, 마지막 사람 입력 시각, 실행의 페이지 목록(`pages`, 페이지 ID만 온 순서대로)과 사람이 고른 페이지 요청(`switch_target_id`, 마이그레이션 47번), 새로 띄우기 요청(`restart_run_id`, 마이그레이션 48번)을 담아요. 토큰·쿠키·주소는 담지 않아요.
  실행의 시작·초기화·종료는 worker의 풀만 해요. 웹은 실행기의 토큰 보호 CDP 중계로 묶인 실행의 페이지에만 닿고, 원본 CDP 포트에는 닿지 않아요. 실행기는 한 실행에 여러 연결을 받아요.
  사람 확인이 필요한 게시물을 출처가 알려 주면(`BrowserAuth`), 작업은 서버 브라우저 실행을 얻어 새 페이지로 게시물을 열고, 출처의 순서대로 확인 직전까지 가요(다운로드 카드를 가운데로 스크롤해 누름). 그 실행과 페이지를 작업에 묶고 `인증`에서 기다려요. 한 작업에서 확인 화면에 오르는 회차는 한 번에 하나이고, 다른 회차는 `같은 작업의 다른 회차 사이트 확인을 먼저 마쳐야 해요`로 기다려요. 준비에 실패하면 실패가 아니라 이유와 함께 `인증`에서 기다리고, 페이지를 다시 열면 다시 준비해요. 서버 브라우저가 없는 worker에서는 그 회차가 `자막 대기`예요.
  worker는 기다리는 작업에 묶인 실행의 다운로드를 지켜봐요(깨울 때와 2초마다). 사람이 확인을 통과해 브라우저가 파일을 받으면, 그 파일을 회차의 폴더(`.tmp/check-<작업>-<회차>/`)로 옮기고 `인증`을 마친 뒤 작업을 다시 줄에 세워요. 다음 실행은 그 파일을 다른 출처의 파일처럼 `받기`에서 검증해 받고, 작업이 끝나면 실행을 끝내요. 끝나지 못한 다운로드는 기록하고 계속 기다려요. 회차의 폴더는 회차가 끝나면(받음·실패·보류) 지우고, 남은 폴더는 받기 영역 청소가 오래된 것 중 회차가 끝난 것만 지워요. 파일이 오는 사이에 묶음이 바뀌었어도 회차가 아직 파일을 받지 않았으면(줄에 있음·실행 중·대기) 파일을 남겨 두고, 다음 실행이 확인 없이 그 파일을 받아요.
  작업 상세를 열면 웹이 준비 요청(`POST /api/subtitle-jobs/{id}/screen`)을 쓰고 worker를 깨워요. 묶인 실행이 살아 있으면 worker는 그 요청을 사용으로 쳐서 유휴 시간을 거기서부터 세고, 없으면 작업을 다시 줄에 세워 새 실행으로 다시 확인 직전까지 가요. 작업·할 일 목록 조회와 원격 화면 연결·재연결은 실행을 요청하지도 사용으로 치지도 않아요. 웹이 다시 시작해도 묶인 실행이 살아 있으면 새 브라우저 없이 그 실행에 다시 연결해요.
  유휴 종료는 웹이 중계한 사람의 입력만 사용으로 쳐요. 웹은 입력을 최대 10초마다 DB에 적고, 풀은 반복 점검마다 그 시각을 읽어요. 화면 전송만으로는 사용이 아니에요. 유휴 종료된 실행은 묶음이 지워지고 작업은 `인증`에 남으며, 화면은 `서버 브라우저가 쉬는 동안 닫혔어요. 작업 화면을 다시 열면 다시 준비해요`라고 알려요. worker가 다시 시작하면 브라우저 실행이 모두 사라지므로 묶음을 모두 지워요. worker가 멈추며 끝낸 실행은 실행이 닫혔다고 적지 않고, 다음 시작이 묶음을 지우며 worker가 다시 시작했다고 알려요.
  작업의 화면 정보(`screen`)는 상태·실행과 함께 실행을 묶은 시각(`bound`, 밀리초)을 담아요. 같은 실행에서 작업의 다른 회차가 확인에 오르면 새 묶음이고 `bound`가 달라요.
  원격 화면은 열린 화면마다 WebSocket 하나(`GET /api/subtitle-jobs/{id}/screen/socket?run=&bound=`)이고, 연결할 때의 묶음(실행·페이지·묶은 시각)에 묶여요. 웹 전체의 Host·Origin 검사([접근 경계와 기기](web-app.md#접근-경계와-기기))에 걸리면 421이나 403, 인증을 기다리지 않는 작업은 409, 묶인 실행이 없거나 다른 실행·묶음이면 410으로 업그레이드 전에 거부해요. 한 묶음의 소켓들은 웹의 CDP 연결 하나를 나눠 쓰고, 그 연결이 2초마다 묶음이 그대로인지 DB에서 읽어요. 한 묶음에 화면은 4개까지 열려요. 하나 더 열리면 가장 오래된 화면에 `ended`(`replaced`)를 보내고 닫아서 그 자리를 새 화면에 줘요. 사람이 지금 쓰는 기기는 가장 새로 연 화면이고, 가장 오래된 화면은 잠든 휴대폰이 남긴 끊긴 연결일 수 있어서예요. 밀려난 화면은 저절로 다시 연결하지 않고, 사람이 다시 열기를 눌러야 다시 연결해요. 보낸 메시지를 10초 안에 받지 않는 소켓은 닫아요. 웹은 소켓마다 15초마다 ping을 보내고, 10초 안에 pong이나 다른 메시지가 오지 않으면 그 소켓을 끊어요. 그리는 것이 없는 페이지에서는 보낼 메시지가 없어서, 잠들거나 네트워크가 바뀐 기기의 끊긴 연결을 보내기 시간 제한만으로는 알아채지 못하기 때문이에요. 기기는 폭·높이·DPR·터치 여부를 보내고, 웹은 이를 `Emulation.setDeviceMetricsOverride`(그 DPR, 터치면 `mobile`)와 `Emulation.setTouchEmulationEnabled`로 적용해요. 브라우저는 자기 배율(1배)로 그려요. 크기를 바꿀 때마다 세대가 올라가고, 이전 세대나 크기를 바꾸는 동안 만든 입력은 버리고 `dropped`로 알려요. 크기를 바꾸기 시작할 때 눌려 있던 마우스 버튼이나 터치는 원격 페이지에서 먼저 놓아요(클릭 없는 `mouseReleased`, `touchCancel`). 프레임은 `Page.startScreencast`의 JPEG이고 받는 대로 확인 응답을 보내며, 지금 크기의 프레임만 보내요. 새 화면 전송 시작의 응답보다 먼저 온 프레임은 이전 배치의 것이라 새 세대로 보내지 않아요(CDP 연결의 이벤트 순번으로 가려요). 입력은 `Input.dispatchMouseEvent`·`dispatchTouchEvent`·`dispatchKeyEvent`·`insertText`로 전하고, `reload`는 페이지를 새로고침하고, `back`·`forward`는 `Page.navigateToHistoryEntry`로 방문 기록을 한 칸 옮겨요. 웹은 보이는 페이지의 방문 기록(`Page.getNavigationHistory`)에서 `about:blank`가 아닌 첫 항목을 가장 앞으로 보고, 지금 항목이 그보다 뒤일 때만 뒤로를, 마지막이 아닐 때만 앞으로를 허용해요. 이 판단은 단계마다 페이지의 기록으로 다시 하므로, 기기가 `back`을 보내도 빈 페이지로는 가지 않아요. 웹은 기기에 `nav`(`back`·`forward`·`host`)와 `tabs`(탭마다 `id`·`title`·`host`·`shown`·`closable`)를 보내요. 주 프레임이 이동하거나(`Page.frameNavigated`, `Page.navigatedWithinDocument`) 페이지가 생기고 사라지거나 제목이 바뀌면(`Target.targetCreated`·`targetDestroyed`·`targetInfoChanged`) 150ms 간격 안에서 다시 읽어 바뀐 것만 보내고, 새 소켓과 밀린 소켓에는 마지막 상태를 다시 보내요. 소켓에는 호스트만 가요. 전체 주소는 메시지, 로그, DB 어디에도 보내거나 남기지 않고, 호스트가 없는 페이지(`about:blank`, `data:`, `blob:`)는 호스트 없이 보내요. Chromium은 제목 없는 페이지의 제목을 주소로 알리므로, 제목이 주소 그대로이거나 경로·쿼리를 담으면 제목을 비워 보내고, 40자를 넘는 제목은 잘라 보내요. `back`·`forward`는 사람의 입력으로 세어 실행의 유휴 시간을 새로 시작해요. 묶음이 바뀌면 `ended`(`run`), 실행 페이지나 연결이 사라지면 `ended`(`browser`)를 보내고 닫아요. 메시지 형식과 `POST .../screen/switch`·`.../screen/close`·`.../screen/restart`는 `trss-web`의 `screen_api` 모듈 문서에 있어요.

  2. worker의 지켜보기는 첫 파일에서 멈추지 않고, 그 실행이 끝낸 다운로드를 모두 그 폴더로 받아 [올리기와 같은 기준](subtitles.md#직접-찾기와-자막-올리기)으로 가려 작업 폴더로 옮기거나 빼요. worker가 다시 시작해 남은 파일은 다음 지켜보기나 실행이 먼저 가려요.
  3. 지켜보기는 1초마다 실행의 페이지를 보고, 새 페이지(팝업)가 두 번 연달아 보이면 묶음의 페이지를 그것으로 바꿔요(`bound`도 새로 정해서 열린 화면은 새 묶음으로 다시 붙어요). 보이던 페이지가 닫히면 남은 가장 최근 페이지로 돌아가요. 이 지켜보기(`follow_pages`)는 직접 찾기와 인증 화면의 묶음에 똑같이 붙어요. 사람이 탭을 고르면 그 선택을 지켜서, 다음 확인에서 가장 최근 페이지로 되돌리지 않아요. 선택한 페이지가 사라지면 선택을 버려요. worker는 확인마다 실행의 페이지 목록을 온 순서대로 화면 행에 적어요(바뀔 때만). 두 번 연달아 보인 페이지만 목록에 들어가고, 시작할 때 Chromium이 여는 창은 목록에 없어요.
     탭 전환과 닫기는 웹이 요청만 적고 worker가 실행해요. 웹은 브라우저에 아무것도 보내지 않아요. 두 요청 모두 사람이 본 묶음(`run`, `bound`)이 그대로이고 대상이 화면 행의 페이지 목록에 있을 때만 적혀요. 아니면 거절해요(409, 작업이 없으면 404).
     - `POST /api/subtitle-jobs/{id}/screen/switch`(`run`, `bound`, `target`)는 보여줄 페이지를 `subtitle_job_screens.switch_target_id`에 적어요. worker가 다음 확인(1초 안)에 가져가 그 페이지가 살아 있으면 화면을 옮겨요(새 묶음).
     - `POST /api/subtitle-jobs/{id}/screen/close`(`run`, `bound`, 선택 `target`, 없으면 보이는 페이지)는 닫을 페이지를 `close_target_id`에 더해요(마이그레이션 46번에 시작. 47번부터 공백으로 나눈 여러 ID). 실행을 준비할 때 연 처음 페이지(`first_target_id`)는 웹이 거절하고 worker도 닫지 않아요. 보이지 않는 탭을 가리켜도 되고, 그러면 그 창만 닫히고 화면은 그대로예요. 보이는 탭을 닫으면 화면은 남은 가장 최근 페이지로 돌아가요. worker는 `Target.closeTarget`으로 닫아요. 인증 화면에서도 같아요.
     - 두 요청은 202로 답하고 본문은 `{}`예요. 둘 다 사람의 입력으로 세요.
     화면 정보의 `popup`(보이는 페이지가 처음 페이지와 다름)은 남아 있지만 웹 화면은 쓰지 않아요. 페이지를 아는 쪽이 worker이므로 시작 페이지를 지키는 판단도 worker에 둬요.
  4. 사람이 `받기 끝내기`를 누르면 웹이 그 요청을 적고(`subtitle_jobs.finish_at`, 마이그레이션 46번) worker를 깨워요. 웹은 작업을 끝내지 않아요. 지켜보기는 받는 중인 다운로드(브라우저에서 진행 중, 끝났지만 아직 넘기지 않음, 넘겨서 옮기는 중)가 없을 때 작업을 끝내고 실행을 닫아요. 묶인 실행이 없는 작업(실행이 닫혔거나, 재시작으로 묶음이 풀렸거나, 서버 브라우저가 없는 작업)은 worker가 원격 화면을 살필 때 회차 폴더에 남은 다운로드를 먼저 가려 담고 끝내요. 서버 브라우저가 없는 worker도 이것만은 해요. 한 작업의 폴더를 가려 담는 일과 끝내는 일은 worker 안에서 한 번에 하나씩이에요. 끝난 작업의 회차 폴더는 지우고, 준비하지 못해 기다리던 `게시물 열기` 단계는 전에 연 적이 있으면 완료로, 없으면 지워요.
  5. 유휴 종료로 실행이 닫히면 받은 파일은 남고 작업은 기다려요. 작업 화면을 다시 열면 새 실행이 같은 시작 게시물을 열어요(작업 기록 `제작자의 게시물을 다시 열어요`). 화면을 다시 열어도 사이트 확인을 되살리는 동작은 하지 않아요. 이전 실행의 페이지 주소는 남기지 않아요.
  확인(2026-10-04): 실제 브라우저 이미지에서 가짜 블로그(`https://fake.trss.invalid/blog/<이름>`)의 최근 게시물을 열고, 두 번째 CDP 클라이언트의 신뢰 클릭으로 이전 게시물로 옮겨 첨부 둘을 누르자 실행이 두 다운로드를 차례로 넘겼어요(무시된 테스트 `find_sample`). 같은 시험에서 `target="_blank"` 링크의 신뢰 클릭으로 연 새 창은 약 30초 뒤에야 실행의 페이지가 됐어요. 디버거를 기다리는 새 창에서는 브라우저 풀의 `Network.enable`이 답하지 않아, 풀이 명령 시간 한도(30초)까지 기다린 뒤 설정 없이(광고 차단 없이) 창을 풀어줘서예요. 그 뒤 시작 페이지 닫기는 거절되고 새 창은 닫혔어요. 웹 원격 화면으로 가짜 블로그를 둘러본 것, 실제 제작자 블로그, 실제 휴대폰은 확인하지 않았어요.
  개발 환경 확인(2026-10-04, 커밋 `d70e974`): 사용자가 웹의 `직접 찾기`로 실제 제작자(코코렛, felia.tistory.com)를 고르자 서버 브라우저가 관찰된 1화 게시물을 열었고, 원격 화면에서 받기를 누르자 `drive.usercontent.google.com`에서 받은 ZIP(1화 SMI) 하나가 그 작업의 묶음이 됐어요. `받기 끝내기` 뒤 작업이 끝났고, 아무것도 받지 않고 끝낸 다른 작업은 `받은 파일 없음`이었어요. 작업 기록과 worker 로그에는 호스트만 있었어요. 실제 블로그에서 다른 게시물로 옮기는 것과 실제 휴대폰은 확인하지 않았어요.
  확인(2026-10-04, 0054): 풀이 설정 명령과 풀어주는 명령을 답을 기다리지 않고 차례로 보내게 바꾼 뒤 같은 시험(`find_sample`)에서 `target="_blank"` 링크로 연 새 창은 클릭 뒤 약 0.1초에 실행의 페이지가 됐고, 문서가 열리자마자 차단 목록의 주소를 요청한 새 창과 다른 사이트의 프레임에서 그 요청이 막혔어요(목록에 없는 주소는 통과). 차단 목록 주소를 새 창의 주소 자체로 열면 막히지 않았어요.
  확인(2026-10-04, 0055): 실제 브라우저 이미지에서 직접 찾기 묶음의 원격 화면 소켓으로(무시된 테스트 `remote_screen_docker`) 시작 페이지의 방문 기록이 `about:blank`와 게시물이고 `back`이 꺼져 있으며 `back`을 보내도 움직이지 않는 것, 게시물에서 이전 게시물로 간 뒤 `back`·`forward`가 켜지고 옮겨지는 것, 새 창이 탭이 되고 처음 탭 선택이 유지되며 보이지 않는 탭과 보이는 탭을 닫으면 각각 그 창만 닫히고 화면이 처음 페이지로 돌아오는 것, 소켓 메시지 19개에 경로·쿼리·조각이 없는 것을 확인했어요. 인증 묶음의 팝업·전환·닫기는 가짜 브라우저로만, 375px 폭은 앱 안 브라우저의 크기 흉내로만 봤고 실제 휴대폰은 확인하지 않았어요.
  개발 환경 확인(2026-10-04, `9235d43`에서 지은 이미지, 0055): 사용자가 아이폰으로 같은 원격 화면을 써, 도구 줄이 가로 스크롤 없이 들어가고 누르기 편하며 호스트에 도메인만 보이고, 처음 게시물에서 뒤로가 꺼져 있고 다른 글로 옮긴 뒤 뒤로·앞으로가 되는 것을 확인했어요. 탭 줄에서는 새 창이 탭이 됐지만, 처음 탭으로 돌아가자 화면이 `화면을 불러오는 중`에서 멈췄어요. 그 탭이 브라우저 안에서 새 창 뒤에 가려져(`visibilityState: hidden`) 프레임이 오지 않았어요. 웹이 붙을 때 페이지를 앞으로 가져오게 고쳤어요. 고친 이미지에서 처음 탭으로 돌아가기와 보이는 새 창 닫기가 둘 다 그려지는 것을 같은 날 다시 확인했어요. 탭을 바꾸는 동안의 로딩 표시도 휴대폰에서 확인했어요. 탭 전환, 새 창으로 옮기기, 보이는 탭 닫기 모두 표시만 이어지다 새 페이지가 그려졌어요.
- 실제 웹 화면에서 후보 선택 → 인증 필요 → 직접 CAPTCHA 해결 → 서버 파일 수신을 이어서 관찰해요.
  수동 파일 다운로드·업로드·이동이나 CAPTCHA 자동 우회를 개입시키지 않고, 받은 파일의 형식·무결성과 해당 작업의 결과를 확인해야 해요.
- 원격 화면을 제공하는 페이지와 화면·입력 WebSocket 모두 같은 접근 보호를 받아요([접근 경계](web-app.md#접근-경계와-기기)).
  원본 CDP 포트를 별도로 노출하지 않으며, HTTPS 배포에서는 WSS 연결과 앞단 프록시의 연결 전달·접근 차단을 실제 배포 경로에서 확인해요.
  외부 페이지에서 보낸 허용되지 않은 상태 변경·원격 입력 연결과 보호 계층을 우회한 직접 접속도 거부되는지 확인해요.
  원격 입력은 해당 작업과 브라우저 실행에 묶고, 끝난 실행의 연결이 다음 작업을 조작하지 못하게 해요.
- 브라우저가 작업을 실행 중이지 않고 사용자 조작도 없는 유휴 시간의 초기 설계 기본값은 5분이며, 만료하면 브라우저를 종료하되 인증 필요 작업은 남겨요.
  이후 해당 작업을 열면 페이지와 필요한 인증 화면을 자동으로 다시 준비하고, 이미 받은 파일과 작업 기록도 유지해요.
  유휴 종료가 실행 중 다운로드를 끊지 않는 경우와, 인증 필요 상태에서 종료 후 재개하는 경우를 구분해 확인해요.
  상태 조회는 브라우저를 시작하거나 사용자 조작 시각을 갱신하지 않아요.
  원격 연결이 끊기면 같은 작업의 유효한 실행에 다시 연결하되, 유휴 종료된 브라우저를 연결 재시도만으로 계속 새로 띄우지 않아요.
  화면을 열어 둔 채 입력 없이 유휴 종료를 맞은 경우와, 실제로 돌아와 재개한 경우를 나눠 관찰해요.
- 실행마다 새 전용 프로필을 쓰고 종료 시 쿠키·사이트 저장 상태를 버려요.
  작업 기록과 받은 파일은 프로필과 별도로 보존하고, 쿠키·토큰·서명 다운로드 URL을 설정 내보내기나 일반 로그에 노출하지 않아요.
  프로필 폐기 후에도 작업과 받은 자막이 남고 다음 실행에 이전 사이트 상태가 재사용되지 않는지 확인해요.
- 동시 브라우저 작업 수의 초기 설계 기본값은 1개이며, 유휴 시간과 동시 작업 수는 [설정의 공통 정책](settings.md#공통-정책)에서 조정해요.
  이는 실측 성능값이 아닌 보수적인 시작값이에요.
  동시성을 높인 설정에서는 작업별 화면·입력·프로필·수신 파일이 섞이지 않고 설정한 상한이 지켜지는지 확인해요.
  서버 브라우저 컨테이너의 메모리 한도 시작값은 768MiB예요. 2026-10-02에 1배·광고 차단·이 한도에서 인증과 수신이 되었고 실제 프로세스 메모리는 약 450MiB였어요([원격 화면 비교](../brainstorm/web-gui-subtitles.md#2026-10-02-원격-화면과-기기-폭-비교)). 브라우저는 작업이 있을 때만 떠 있어요.
  CPU·메모리와 압축 해제의 총량·파일 수·중첩 깊이·실행 시간 한도는 대표 정상 묶음과 과다 입력을 측정해 구현 시 유한한 값으로 정해요. 압축 해제는 한도를 건 별도 프로세스에서 해요([압축 해제의 격리와 한도](subtitles.md#압축-해제의-격리와-한도)).
  한도 도달은 성공이나 동일 파일 판정과 구분해 표시하고, 이미 보관한 파일·승인 대기·인증 필요 작업을 잃지 않아야 해요.

### 작업 결과

- 불명확한 연결, 미지원·손상 묶음, 수신 실패, 적용 실패를 성공으로 표시하지 않아요.
  재개가 이미 받은 정상 파일의 수동 재업로드를 요구하지 않아요.
- 인증 필요·배치 확인·교체 승인·영상 대기·자막 대기는 서로 다른 대기 사유로 구분해요.
- worker 재시작 후에는 기록과 실제 파일을 대조해 확인 가능한 지점부터 미완료 작업을 자동 재개해요.
  수신·보관 완료가 확인된 파일은 재사용하고, 인증·승인이 필요한 단계는 기다리며, 파일 반영 여부가 불명확하거나 승인 대상이 달라졌으면 보류해요.
  수신 후 중단, 복사 반영 전후 중단, 승인 대상의 외부 변경을 각각 발생시켜 중복 수신·무승인 변경·허위 완료 없이 재개 또는 보류되는지 확인해요.
  다른 환경으로 설정·보관 정보를 가져오는 동작에 이 자동 재개 정책을 적용하지 않아요.
- 보관·적용 단계가 생기기 전에 받기까지만 하고 끝난 작업은, worker가 다시 집어 묶음 분석부터 이어가요(사용자 결정, 2026-10-04).
  수신 영역의 파일을 쓰고 다시 받지 않으며, 올리기·직접 찾기 작업은 배치 확인에서 기다려요.

#### 공통 수신 결과와 실패 분류

여섯 경로가 함께 쓰는 수신 결과와 실패 분류예요(티켓 0038).
신호는 [2026-10-02의 경로 확인](../brainstorm/web-gui-subtitles.md#2026-10-02-경로별-재확인)(티켓 0033)과 2026-10-03의 Tistory 재확인에서 관찰한 사실이에요.
Tistory 일반 첨부가 이 결과로 처음 구현됐고, 이후 출처(0041–0044)는 경로만 더해요. Blogger·Google Drive(0042)가 두 번째, Naver 블로그 첨부(0044)가 세 번째 경로예요.

출처에서 파일 하나를 받으려는 시도는 `받음`이나 아래 실패 분류 하나로 끝나요.
게시물 열기는 그 밖에 `인증 필요`나 `자막 대기`로 멈출 수 있고, 둘 다 실패가 아니에요.

- `받음`은 수신 영역의 파일(경로·바이트 수·SHA-256), 검증으로 판별한 형식(ZIP·ASS·SRT·SMI·그 밖), 사이트가 준 파일 이름, 응답의 HTTP 상태와 `Content-Type`, 파일 정보 스냅샷, 받은 시각을 가져요.
  받은 바이트 수와 견주는 길이는 응답이 미리 알린 정확한 길이(`Content-Length`, Naver의 `attachFileSize`)뿐이에요.
  게시물이 표시한 크기(Tistory의 `0.01MB`)는 대략적이라 견주지 않고 스냅샷에만 남겨요.
- 파일 정보 스냅샷은 출처마다 다른 값을 이름과 함께 `[이름, 값]`의 JSON 배열로 저장해, 같은 경로의 다음 스냅샷과만 견줘요.
  Tistory는 게시물의 `article:modified_time`, 표시 크기(`declared_size`), 응답에 있으면 `Last-Modified`(`last_modified`)를 남겨요.
  Google Drive 파일은 게시물의 수정 시각(Blogger는 JSON-LD의 `dateModified`가 있는 테마에서만, Tistory 본문의 링크는 `article:modified_time`), 응답의 `Last-Modified`(`last_modified`), 알린 길이(`content_length`)를 남겨요.
  Naver 첨부는 게시물의 작성 시각(`publish_date`, 이 글의 영역 `id="post-view<logNo>"` 안의 `se_publishDate`가 `2026. 6. 23. 5:19`처럼 날짜일 때만이에요. 하루가 안 된 글은 `3시간 전`처럼 보여서 남기지 않아요. 그래서 처음 스냅샷에 없던 `publish_date`가 다음 스냅샷에 생기는 것은 변경이 아니고, 재확인(0050)도 이것을 변경으로 보지 않아요), `attachFileSize`의 바이트 수(`attach_file_size`), Naver가 표시한 제한(`blocked`, 있을 때만)을 남겨요. 수정 시각과 `Last-Modified`는 없어요.
  이 값으로 Anissia 줄이 그대로인 게시물 수정을 찾는 일은 [구독 제작자 자동 수신](subtitles.md#구독-제작자-자동-수신)의 받은 뒤 14일 재확인이에요.
  재확인은 스냅샷을 서로 견주지 않고, 받은 파일의 바이트 수(`subtitle_job_files.size`)와 스냅샷의 `last_modified`를 기준으로 삼아 출처가 지금 알려 주는 값과 견줘요. Tistory는 정확한 전체 크기를 스냅샷에 남기지 않아서 받은 바이트 수가 기준이에요.
  재확인 기록은 회차(`subtitle_job_items`)마다 한 줄(`subtitle_item_rechecks`)이에요: 마지막으로 읽기로 한 시각(`checked_at`, 첫 요청 전에 써요), 읽은 횟수, 결과(`same`·`changed`·`missing`·`failed`·`unreadable`), 읽은 값(파일 키·크기·`Last-Modified`, 주소와 토큰은 없어요), 만든 작업이에요. erulabo 회차의 읽은 값에는 게시물의 수정 시각(`post: true`인 줄의 `modified`와 받을 때의 `was`)과, 스냅샷에 Drive 파일 ID가 있는 파일의 `HEAD` 결과(키·크기·`Last-Modified`, 읽지 못했으면 `problem`)가 들어가요. Drive 파일 ID는 넣지 않아요.
  재확인이 만든 수정본 작업의 요청 ID는 `recheck:<회차 번호>:<새 값의 요약>`이라 같은 변화로는 하나만 생겨요. 수정본 작업이 받은 파일이 이전에 받은 파일과 바이트까지 같으면 그 회차에 이전 작업을 가리키는 `unchanged_from`을 남겨요(`교체 승인`을 만들지 않는 근거예요).
  수정본 작업의 `revises_job`은 같은 관찰을 받은 이전 작업만 가리켜요(재확인의 수정본은 이전 수신과 같은 관찰을 다시 받기 때문이에요).
- 실패는 분류, 이유 한 문장, 응답이 있었으면 HTTP 상태·`Content-Type`(매개변수를 뺀 미디어 형식)·응답 크기를 가져요.
  `자막 없음`과 `추가 입력 필요`는 받을 파일이 생기기 전의 회차 항목에만 붙는 분류예요(`subtitle_job_files.failure`에는 들지 않아요).
  실패한 회차도 분류를 가지며, 작업은 첫 실패 회차의 분류로 보여요.
- 서명 URL·쿠키·토큰은 저장하지 않고 작업 기록·로그·API 응답에도 내지 않아요.
  출처가 게시물에서 얻은 서명 주소는 그 파일을 받을 때까지 메모리에만 있어요.
  파일은 서명이 든 쿼리를 뺀 주소의 호스트와 경로(`tistory:blog.kakaocdn.net/dna/…`)로 알아봐요.
- 분류는 응답 신호로 가려요.
  Drive·Tistory·Naver 모두 정상 파일을 `application/octet-stream`으로 줘서 `Content-Type`만으로는 정상과 오류가 갈리지 않고, 오류는 `text/html`로 와요.
  오류 응답의 크기는 신호가 아니에요. Tistory의 거절된 서명 URL은 2026-09-26에 552바이트, 2026-10-03에 150바이트였어요.
  파일인지와 형식은 받은 바이트로 확인해요(아래 검증).

| 자막 없음 | 게시물의 WinPNG 뷰어가 있는 스킨에서 본문의 `*.kakaocdn.net` `.png` 이미지를 모두 살펴봤지만 뷰어가 읽을 수 있는 이미지가 하나도 없어요(뷰어의 자체 판별이 `possibility` 0, 그림이에요). 판별이 이미지를 가져오지 못하거나 해석하지 못한 이미지가 있고 읽은 이미지가 하나도 없으면 자막이 없다고 알 수 없어서 `네트워크 실패`예요. 브라우저가 연 게시물에서 출처가 본 이미지를 하나도 찾지 못하면(늦게 불러오는 이미지, 페이지 변경) `출처 구조 바뀜`이에요. 게시물과 파일은 있어서 `원본 없음`도 `출처 구조 바뀜`도 아니에요. 회차의 항목에만 붙고 파일은 없어요. 2026-10-03에 실제 게시물의 이미지를 그림으로 바꿔 봐서 확인했어요(아래). | 다시 시도하지 않고 실패로 알려요. |

- 한 출처는 같은 호스트에 1초 이상 간격을 두고 요청해요. 첨부 25개인 게시물(isulbi 40)도 한꺼번에 받지 않아요. Google Drive는 Tistory와 Blogger가 함께 쓰는 하나의 간격이에요.
- Tistory는 `.fileblock a[href]` 중 `https`이고 호스트가 `*.kakaocdn.net`·`*.daumcdn.net`인 주소만 첨부로 봐요. 그 밖의 링크는 첨부가 아니며, 남는 첨부가 없으면 첨부 없는 게시물로 읽어요.
  - 첨부 없는 게시물은 본문 컨테이너 안만 봐요. 컨테이너는 실제 게시물에서 본 `.tt_article_useless_p_margin`·`.contents_style`(편집기가 넣는 클래스, harne1 739·felia 1187·sumomomo 491 모두)과 `#article-view`(sumomomo 491에서 위 클래스를 감싸요)예요(2026-10-03). 스킨에는 본문 밖에 `img1.daumcdn.net/thumb/…?fname=<kakaocdn .png>` 썸네일 같은 링크와 이미지가 있어서, 본문을 찾지 못하면 `자막 대기`가 아니라 `출처 구조 바뀜`이에요.
  - 요청에는 쿠키도 `Referer`도 없어요. HTTP 클라이언트의 자동 `Referer`를 꺼서, 리디렉션에서도 서명 주소가 다음 호스트로 가지 않아요.
  - 리디렉션은 처음 요청이 갈 수 있는 곳으로만 열 번까지 따라가요. 게시물은 `https`인 `tistory.com` 블로그로, 파일은 `https`인 위 CDN 호스트로만 가요. 그 밖은 따라가지 않고 그 `3xx` 응답을 `출처 구조 바뀜`으로 남겨요.
- Blogger는 `https`인 `<블로그>.blogspot.com` 게시물을 쿠키 없이 읽어요(`http` 주소도 `https`로 요청해요). 게시물이 리디렉션되면 `https`인 `blogspot.com` 블로그로만 따라가요.
  - 본문은 `.post-body`이고(2026-10-03에 C소라·카이란·별명따위·에텔레로사·soso_sagak·이마이·fanic의 모든 테마), 게시물 하나에 하나예요. 본문이 없거나 둘 이상이면 `출처 구조 바뀜`이에요. 본문 밖의 링크는 보지 않아요.
  - 본문의 링크 가운데 Drive 파일 링크와 그 글자를 읽어요. 같은 파일을 가리키는 링크가 여럿이면 글자가 있는 첫 링크의 글자를 써요.
- Naver는 `blog.naver.com`·`m.blog.naver.com`의 글 주소에서 블로그와 글 번호를 읽어요(0044). 주소는 `/<blogId>/<logNo>`(개발 DB의 Naver 줄 일곱 개 모두), `PostView.naver`·`PostView.nhn`의 `?blogId=…&logNo=…`, `/<blogId>?Redirect=Log&logNo=…` 꼴이에요. 그 밖의 주소는 요청하지 않고 `출처 구조 바뀜`이에요.
  - 글 주소의 페이지는 2.9KB의 프레임이고 글은 내부 프레임 `PostView.naver?blogId=…&logNo=…&redirect=Dlog&widgetTypeCall=true&noTrackingCode=true&directAccess=false`에 있어요. 없는 글도 프레임은 `200`이라서 프레임은 읽지 않고, 그 내부 페이지를 `https`로 쿠키 없이 바로 읽어요. 모바일 페이지(`m.blog.naver.com`)에는 `aPostFiles`가 없어서 같은 내부 페이지를 읽어요. 리디렉션은 `https`인 두 블로그 호스트로만 따라가요.
  - 첨부는 내부 페이지의 `aPostFiles[<n>] = JSON.parse('…')` 목록이에요. 글의 페이지인지는 이 대입이나 `aPostBaseInfo[<n>] = "<logNo>|…"`로 알아봐요. 선언(`var aPostFiles = [];`)만으로는 글의 페이지가 아니고, 그 밖의 언급(`aPostFiles[0].length`, 본문의 글자)은 목록이 아니에요. 글의 페이지가 아니면 위 알림·CAPTCHA·다른 페이지로 나눠요. 기록 하나에 이름(`encodedAttachFileName`), 정확한 크기(`attachFileSize`, `44,155`처럼 쉼표), 표시(`maliciousCodeYn`·`punishType`), 서명 주소(`encodedAttachFileUrl`)가 함께 있어서 이 목록만 읽어요. 저장 버튼(`a.se-file-save-button`)은 같은 주소를 되풀이할 뿐이라 맞춰 보지 않아요. `aPostBaseInfo`가 있으면 이 글 번호로 시작하는 것의 목록만 읽고, 이 글 번호가 없으면 `출처 구조 바뀜`이에요. `aPostBaseInfo`가 없으면 목록이 하나일 때만 그 목록을 읽고, 둘 이상이면 `출처 구조 바뀜`이에요. 읽을 수 없는 대입(`JSON.parse('…')`나 `[]`가 아닌 값)도 `출처 구조 바뀜`이에요.
  - 표시는 닫힌 쪽으로 읽어요. `maliciousCodeYn`이 비었거나 `false`·`n`·`0`(대소문자 무시)일 때만, `punishType`은 비었거나 `0`일 때만 표시가 없는 것으로 봐요. 스냅샷의 `blocked`에는 `malicious_code`나 `punish_type=<값>`을 남기고, 값은 영문자·숫자 16자까지만 남겨요.
  - 한계: 한 글에 이름이 같은 첨부가 둘이면 첫 것만 받아요. 글꼴 첨부만 있는 글은 본문의 Drive 링크를 보지 않고, 받을 자막 첨부가 없다는 이유로 `출처 구조 바뀜`이에요.
  - 파일은 토큰 없는 `naver:<blogId>/<logNo>/<파일 이름>`으로 알아봐요. 주소는 `https`인 `download.blog.naver.com`일 때만 받고, 토큰이 글을 읽을 때마다 바뀌어서 메모리에만 둬요.
  - 받기는 쿠키·`Referer` 없는 GET이고, 리디렉션 없이 `200` `application/octet-stream`, `Content-Length`, `Content-Disposition: attachment; filename="…"; filename*=UTF-8''…`로 와요(2026-10-03). `Last-Modified`·`ETag`는 없어요. 리디렉션은 `download.blog.naver.com`으로만 따라가요.
  - 응답이 알린 길이가 `attachFileSize`와 다르면 받지 않고 `파일 아님`이에요. 길이를 알리지 않으면 받은 바이트를 `attachFileSize`와 견줘요.
  - 토큰이 거절되면(`400` `text/html` 3,452바이트) Tistory처럼 내부 페이지를 한 번 다시 읽어 같은 파일의 새 주소로 한 번 더 받아요.
  - 실제 글의 내부 페이지에는 언제나 안부게시판·댓글용 CAPTCHA 프레임(`captchalayeredframe`)이 숨어 있어서, CAPTCHA라는 말은 `aPostFiles`가 없는 페이지에서만 이유를 가려요. 첨부는 `aPostFiles`에서만 얻어요.
  - 첨부가 없는 글은 본문(`.se-main-container`, 옛 편집기는 `#postViewArea`)의 Google Drive 링크를 Tistory처럼 받아요. 그런 글은 아직 보지 못했어요.
- Google Drive 파일 링크는 Blogger 본문과 첨부 없는 Tistory·Naver 본문에서 같은 규칙으로 받아요(0042).
  - 링크는 `drive.google.com/file/d/<id>/…`(C소라·카이란·에텔레로사·soso_sagak·이마이·fanic·felia), `drive.google.com/uc?…id=<id>&export=download`(별명따위), `open?id=<id>` 꼴이에요. 로그인한 계정 번호(`/u/<n>/…`)나 Workspace 도메인(`/a/<domain>/…`)이 앞에 붙은 같은 꼴도 같은 링크예요. ID는 영문자·숫자·`-`·`_`이고, 파일은 서명 없는 `drive:<id>`로 알아봐요. 주소가 늘 같아서 다시 얻을 것이 없고 `만료`도 없어요.
  - 받기는 `drive.usercontent.google.com/download?id=<id>&export=download`에 쿠키·`Referer` 없는 GET이에요. Drive가 응답마다 쿠키(`NID`)를 줘도 다음 요청에 싣지 않아요. `drive.google.com/uc?export=download&id=<id>`는 `303`으로 이곳에 넘겨요(2026-10-03). 리디렉션은 `https`인 `drive.google.com`·`drive.usercontent.google.com`으로만 따라가요.
  - 정상 응답은 `200`, `application/octet-stream`, `Content-Length`, `Last-Modified`, `Content-Disposition: attachment; filename="…"`이에요. 파일 이름은 `filename*` 없이 UTF-8 바이트 그대로 와서 UTF-8로 읽어요. 게시물은 링크 글자만 주므로, 받은 파일의 이름은 이 응답의 이름이고 이름이 없으면 링크 글자예요. 이름은 바이트를 쓰기 전에 기록해서 재시작이 찾는 임시 파일 이름과 같아요.
- Drive 링크와 Naver 첨부가 여럿인 게시물에서는 후보의 회차에 맞는 것만 받아요. 규칙은 Drive 링크의 글자와 Naver 첨부의 파일 이름만 보고, 회차 비교는 [자막의 회차 대응](library.md#자막의-회차-대응)의 숫자 키(앞자리 0과 소수 끝의 0을 뺀 문자열, 부동소수점 없음)예요.
  - 한 회차를 밝힌 링크(`24화`·`제24화`·`EP24`·`고양이와 용 08`·`… 12.zip`)는 그 회차가 후보의 회차와 같을 때 받아요. 범위를 밝힌 링크(`1 ~ 12화`·`03-04`·`… 1-12.zip`)는 후보의 회차가 범위 안이면 받아요.
  - 범위는 `~`로 잇거나 띄어 쓰지 않은 `-`로 이은 두 숫자예요(`1-3`·`03-04`). 띄어 쓴 `-`는 어느 쪽에 `화`(`話`·`회`)가 붙었을 때만 범위이고(`1 - 12화`), 아니면 제목과 회차를 가르는 것이라 뒤 숫자 한 회차예요(`Title 3 - 05`는 5화). 두 끝이 같거나 거꾸로면(`03-03`·`24-12`) 범위가 아니라 숫자 하나하나로 읽어요. 둘 다 맞으면 둘 다 받아요(에텔레로사의 `공각기동대 03`과 `1-3`).
  - 회차를 밝히지 않은 글꼴 링크(`폰트`·`글꼴`·`font`)는 언제나 받아요. ASS가 쓰는 글꼴이에요. 회차를 밝힌 글꼴 링크(`24화 (폰트 포함)`·`1화 폰트`)는 그 회차의 링크예요. 글꼴 파일(`.ttf`·`.otf`·`.ttc`·`.woff`·`.woff2`)은 이름의 숫자와 상관없이 글꼴이에요(수퍼소닉EX의 `H2MPRB.TTF`·`a옛날목욕탕L.ttf`).
  - 회차를 밝히지 않은 압축 파일(`자막 모음.zip`)은 받아요. 안의 회차는 묶음 분석이 정해요.
  - 회차를 밝힌 링크가 하나도 맞지 않고, 게시물의 자막 링크(글꼴이 아닌 링크)가 회차를 밝히지 않은 하나뿐이면 그것을 받아요. 그림만 있는 링크(카이란), `자막 다운로드`(felia), `BLACK TORCH`(soso_sagak)처럼 게시물 하나에 파일 하나인 경우예요.
  - 그 밖에는 `출처 구조 바뀜`이고 이유가 회차를 밝혀요(`게시물에 24화 파일이 없어요`). 회차를 밝히지 않은 링크가 둘 이상이면 고를 수 없다고 적어요. Drive 파일 이름으로 다시 고르지 않아요. 이름은 받아야 알 수 있고, 그런 게시물은 아직 보지 못했어요.
  - 링크 글자의 숫자는 홀로 선 것만 회차로 봐요. 글자에 붙은 숫자(`S2`·`4th`·`2기`·`3장`·`1080p`·`그랑블루3`)는 회차가 아니고, `제`·`第`·`EP`·`E` 뒤의 숫자는 회차예요. 시즌 뒤의 `E`도 회차를 표시해요(`S02E01`은 1화). `E`·`EP` 뒤의 범위는 끝 숫자 앞에 표시가 다시 와도 범위예요(`E01-E12`·`EP01-EP12`·`S02E01-E12`는 1–12화). `화`(`話`·`회`)가 붙은 숫자를 먼저 보고, 없으면 마지막 숫자를 봐요(`… 4 24.zip`는 24화예요). 표시가 없는 숫자 가운데 연도(1900–2099의 네 자리, `Title 05 (2026)`), 날짜(`2026-10-03`), 1000을 넘는 수, 점으로 글자에 붙은 숫자(`H.264`·`AAC2.0`), `.5`가 아닌 소수(`2.0`)는 회차로 보지 않아요. `화`가 붙으면 이런 수도 회차예요(`1001화`·`13.5화`). 주소 그대로인 글자는 회차를 밝히지 않은 것으로 봐요.
  - 한 작업의 여러 회차가 같은 게시물이면 글꼴처럼 겹치는 파일은 한 번만 받아요(아래).
- 파일 하나는 200MiB까지, 요청부터 마지막 바이트까지 15분 안에 받아요. 알린 길이가 상한을 넘으면 받기 전에, 알리지 않았으면 넘는 순간 멈춰요(`파일 아님`). 기한을 넘기면 `네트워크 실패`예요.
- 길이 비교는 언제나 `Content-Length`로 해요. 응답에 `identity`가 아닌 `Content-Encoding`(대소문자 무관)이 있으면 그 바이트와 길이는 인코딩의 것이라 받지 않고 `파일 아님`이에요. 클라이언트는 아무것도 풀지 않아요.
- Tistory 첨부(`.fileblock`)는 게시물이 제공하는 파일을 모두 받아요. 시리즈 전체 ZIP, 회차별 SMI, 폰트 ZIP을 가리지 않아요(isulbi 40, kiriu 323). Drive 링크와 Naver 첨부는 위 규칙으로 고른 것만 받아요.
  어느 파일이 어느 회차의 것인지, 받은 파일이 최종본인지(`미완성(2)`·`마커표시본` 같은 임시본)는 [묶음 분석](subtitles.md#자막-묶음-분석과-안전한-배치-판단)이 정해요.
  한 작업 안에서 같은 파일은 한 번만 받아요.
- 받은 바이트는 완료(`done`)로 기록하기 전에 검증해요.
  재시작 복구가 `받음`(`fetched`) 기록의 임시 파일을 공개하기 전과, 공개 뒤 기록 전에 멈춘 파일을 완료로 기록하기 전에도 같은 검증을 해요. 그때 파일이 아니면 그 시도를 실패로 끝내고 바이트를 지운 뒤 새로 받아요.
  - 비어 있으면 파일 아님이에요.
  - BOM과 공백 뒤 `<`로 시작하면서 `<SAMI`가 없으면(대소문자 무관) 웹 페이지라 파일 아님이에요.
  - 200MiB를 넘는 파일은 파일 아님이에요.
  - `PK\x03\x04`로 시작하면 ZIP으로 열어 모든 멤버를 끝까지 읽어 CRC를 확인해요. 열 수 없거나 CRC가 맞지 않으면 파일 아님이에요. 이 빌드가 읽지 못하는 압축 방식이나 암호가 걸린 멤버는 판정하지 않고 넘겨요. 풀린 크기가 1GiB를, 멤버가 10,000개를 넘으면 파일 아님이에요.
    열기 전에 파일 끝의 끝 레코드(ZIP64면 그 레코드)가 주장하는 멤버 수를 직접 읽어, 10,000개나 파일 길이가 담을 수 있는 수(목록 항목 하나는 최소 46바이트)를 넘으면 열지 않고 파일 아님으로 끝내요. 주석 안에 숨긴 끝 레코드도 같이 봐요.
  - BOM 뒤 `[Script Info]`는 ASS, `<SAMI`는 SMI, 시각표 줄(`00:00:01,000 --> …`)이 있으면 SRT예요. `WEBVTT`로 시작하면 시각표 줄이 있어도 SRT가 아니라 `그 밖`이에요. UTF-8·UTF-16의 BOM과, ASCII를 그대로 쓰는 옛 인코딩을 읽어요. 그 밖은 `그 밖`으로 남겨 분석이 정해요.
  - 이름의 확장자가 ZIP·ASS(SSA)·SRT·SMI(SAMI)를 약속하는데 바이트가 그 형식이 아니면 파일 아님이에요.
  - 검증 자체가 비정상으로 끝나면(panic) 파일인지 판정하지 않고, 바이트를 지우지 않은 채 그 시도를 `보류`해요.
  - ZIP 멤버가 자막인지는 받을 때 판정하지 않아요(결정, 0038). 초안은 자막 멤버가 없는 ZIP을 파일 아님으로 봤지만, 폰트 ZIP처럼 자막이 없는 ZIP도 정상 파일이라 멤버의 내용은 묶음 분석이 판정해요. ASS의 `[Events]`도 받을 때는 보지 않아요.
- 기록은 `subtitle_job_files`의 `format`·`failure`·`http_status`·`content_type`·`response_size`·`snapshot`과 `subtitle_job_items.failure`예요(마이그레이션 36).
  마이그레이션 44가 항목의 분류에 `no_subtitle`·`needs_input`을 더하고(SQLite는 `CHECK`를 바꿀 수 없어 열을 새로 만들어 값을 옮긴 뒤 이름을 바꿔요. 기존 값은 그대로예요), 파일에 `folder`(받은 파일이 작업 폴더 안에서 놓이는 하위 폴더)를 더해요.
  네트워크 실패로 다시 시도한 시도는 `abandoned`로 남기되 분류와 응답 사실을 함께 남겨요.
  SQLite 정수에 들지 않는 크기는 저장하지 않아요.
  `받음`까지 간 시도가 실패하면 실패를 공개할 경로와 함께 먼저 기록하고, 그 바이트를 지운 뒤 경로 기록을 지워요. 경로 기록이 사라지면 다음 시도가 같은 이름을 쓸 수 있어요.
  지우기는 성공했거나 파일이 이미 없을 때만 지운 것으로 봐요. 그 밖의 오류면 그 시도를 `보류`해요.
- 작업 상세는 파일마다 형식과 크기를, 실패한 회차·파일에는 분류 이름(`원본 없음`·`만료`·`파일 아님`·`출처 구조 바뀜`·`네트워크 실패`, 회차에는 `자막 없음`·`추가 입력 필요`도 있어요)과 이유, 알면 HTTP 상태를 보여줘요.
  하위 폴더에 놓인 파일은 이름 앞에 폴더를 붙여(`예고/…smi`) 보여줘요.
  할 일 화면의 `자막 작업` 줄은 펼친 설명 앞에 실패 작업의 분류를 보여줘요.
- 관찰하지 못한 후보: 키가 필요한 WinPNG예요. 분류는 `추가 입력 필요`로 정했지만(0043) 실제 이미지는 아직 보지 못했어요. Naver가 악성·제한으로 표시한 첨부는 `원본 없음`으로 정했고(0044), Naver의 비공개 글과 보안 확인 페이지는 위처럼 분류를 정했지만 실제 응답은 보지 못했어요. Drive의 접근 제한·확인·할당량 화면은 위처럼 분류를 정했지만(0042) 실제 응답은 아직 보지 못했어요. 이전 공유 링크의 `resourcekey`가 필요한 파일도 보지 못했고, 받지 않아요.

#### 체크포인트와 중단 복구

복구 정보는 SQLite의 작업·항목·파일 동작 기록에 남기며, 별도 범용 워크플로 엔진이나 작품별 복원 목록을 도입하지 않아요.
선택한 후보와 출처, 수신 시도 ID와 전용 임시 경로, 검증된 수신물·자산 참조, 불변 계획과 승인 참조, 각 파일 동작의 ID·의도·전후 조건·완료 증거를 구분해 저장해요.
다운로드 완료와 정상 자막 판정은 별개이며, 파일 효과를 시작하기 전에 그 의도를 커밋하고 실제 결과를 확인한 뒤 완료를 기록해요.
임시 영역은 보관 자산과 구분하고, 작업의 임시 파일이나 보호 복사본을 YAML 자산으로 가져오는 경로를 허용하지 않아요.

| 중단 위치 | 복구 판정과 처리 |
| --- | --- |
| 인증 필요·수신 중 | 선택과 인증 필요 상태를 유지해요. 완료 기록이 있는 수신물은 바이트를 확인해 재사용하고, 완료 여부가 불명확하면 보류해요. |
| 바이트 수신 후 완료 기록 전 | 신뢰할 수 있는 예상 길이·내용 식별 정보나 독립적인 완료 증거가 있어야 완료로 인정해요. 현재 길이·로컬 해시·파싱 가능 여부만으로 수신 완료를 만들어내거나 곧바로 다시 받지 않아요. |
| 분석·압축 해제 중 | 검증된 원 수신물에서 필요한 분석만 다시 수행해요. 이미 받은 묶음을 다시 다운로드하지 않으며, 정상 추출물·미지원 항목·실패를 구분해요. |
| 보관 준비 후 등록 전 | 새 자산의 예상 경로와 바이트, 재사용 자산의 참조를 기록하고 검증해요. 새 목적지가 이미 다른 파일로 차 있으면 덮어쓰지 않아요. 공개된 파일과 기록의 관계가 불명확하면 예약과 증거를 남겨 보류해요. |
| 보관 완료·영상 대기·승인 대기 | 검증한 보관본과 폰트 자산 참조를 유지하고 필요한 조건만 기다려요. 브라우저나 worker의 수명이 이 자료를 삭제하지 않아요. |
| 적용 준비 후 공개 경로 변경 전 | 보관본과 별개인 임시 복사본의 바이트를 검증하고 준비된 파일의 객체 식별 증거를 기록해요. 계획·대응·승인·기존 상태가 여전히 유효하고 효과가 아직 실행되지 않았음이 확인되면 이어가요. |
| 공개 경로 변경 후 완료 기록 전 | 기록한 임시 파일의 객체와 최종 파일의 연결, 바이트·경로·계획이 일치하는 등 해당 동작의 결과임을 확인할 수 있어야 완료로 대조해요. 이름이나 원하는 바이트가 있다는 이유만으로 앱이 반영했다고 기록하지 않아요. |
| 여러 경로 중 일부만 반영 | 확인된 완료 효과는 유지하고 항목·경로별 결과를 보여줘요. 새 파일의 정상 반영을 확인한 뒤 승인된 이전 경로를 제거하며, 제거 실패를 전체 성공이나 자동 전체 롤백으로 처리하지 않아요. |
| 제거 후 완료 기록 전 | 파일이 없다는 사실만으로 이 작업이 제거했다고 단정하지 않아요. 행위의 결과를 확인할 수 없으면 보호 자료를 유지하고 보류해요. |

기존 자막을 교체·제거하기 전에는 승인한 기존 바이트의 독립적인 임시 보호 복사본을 준비해요.
공간 부족이나 복사·검증 실패는 파괴적인 효과 전에 중단하고, 실패·불명확한 부분 완료가 남으면 보호 복사본도 남겨요.
임시 보호 자료는 해당 작업이 확인된 완료 상태에 이르거나 사용자가 불명확한 결과의 정리를 명시한 뒤 정리하며, 외부에서 바뀐 공개 경로 위로 자동 복원하지 않아요.
임시 복사본을 최종 경로에 공개하는 내부 이름 변경은 보관 원본을 이동해 적용하는 방식이 아니며, 보관 원본은 독립적으로 남아야 해요.
새 경로 추가에는 지원되는 덮어쓰기 금지 방식을 사용하고, 사전 존재 검사 뒤 일반 덮어쓰기로 이어지는 방식을 동등한 보호로 취급하지 않아요.

복구를 맡는 worker는 같은 호스트의 이전 파일 쓰기 주체가 더 이상 실행할 수 없다는 배타성을 확보해야 해요.
DB 임대 시각이 지났다는 이유만으로 멈춰 있던 이전 worker와 새 worker를 동시에 파일 쓰기 주체로 두지 않아요.
독립적인 회차·파일은 각각 진행할 수 있지만, 겹치는 목적지·제거 경로와 폰트 자산의 정리는 직렬화해요.
폰트 정리는 남은 보관본뿐 아니라 진행 중·보류·복구 작업의 참조도 보호하고, 참조가 없는지 확인한 뒤 삭제하는 사이에 새 참조가 생기는 경쟁도 막아야 해요.
[보관 파일 정리](library.md#보관-파일의-정리)는 worker가 작업을 돌리는 같은 흐름에서 작업보다 먼저 하므로 보관·연결과 겹치지 않고, 지우기 직전에 참조를 다시 확인해요.
정리는 사람이 지우기로 확인한 파일만 지우고 보호 복사본을 두지 않아요. 그래서 위 표의 `제거 후 완료 기록 전`과 달리, 재시작 뒤 파일이 없으면 지워진 것으로 기록해요. 이 기록은 앱이 지웠다는 뜻이 아니라 파일이 없음을 확인했다는 뜻이에요.
불명확한 임시 파일이나 미등록 파일을 이름만 보고 쓰레기로 지우지 않아요.

회차 대응 변경과 한 파일 효과가 겹치면 먼저 확정된 쪽을 기준으로 처리해요.
대응 변경이 먼저이면 반영 전에 계획을 다시 확인하고, 파일 효과가 먼저이면 실제 완료 경로는 유지한 채 남은 작업을 재평가해요.
효과 자체가 불명확한 중단 상태는 먼저 실제 파일과 대조하며, 새 대응이 그 불명확한 파일의 이동·삭제 권한을 주지는 않아요.
인증·영상 대기처럼 오래 멈춘 작업 전체 기간에 대응 설정을 잠가두지 않아요.

영상 수정본 대체의 이전 영상 제거와 이름 변경도 파일 동작의 의도와 완료 증거를 기록해요.
이전 영상은 보호 복사본 없이 되돌릴 수 없게 제거하므로, 제거 전에는 새 영상의 수신·CRC32 확인이 끝났다는 기록이 있어야 하고, 제거 뒤에는 목적지 이름이 비어 있을 때만 이름 변경을 이어가요([영상 수정본의 대체](collection.md#영상-수정본의-대체)).
재시작 뒤에도 새 영상을 지우거나 이름이 겹친 두 파일을 만들지 않아요.

수신 단계는 이 원칙을 다음 순서로 지켜요(티켓 0036).
받은 파일은 앱 데이터 폴더의 수신 영역 `receive/<작업>/<사이트가 준 이름>`에 두고, 한 수신 시도는 자기 임시 폴더 `receive/.tmp/<시도>/`에만 써요.
시도 ID와 임시 폴더를 `의도`로 기록한 뒤 출처가 알린 길이를 기록하고, 바이트를 해시하며 임시 파일에 받아 동기화해요.
알린 길이와 다르면 실패로 끝내고 그 바이트를 지워요.
길이·SHA-256·임시 파일의 객체(`장치:inode`)·공개할 경로를 `받음`으로 기록한 뒤 바이트를 [검증](#공통-수신-결과와-실패-분류)해요. 파일이 아니면 실패를 경로와 함께 기록하고, 그 바이트를 지운 뒤 경로 기록을 지워요.
검증을 통과하면 덮어쓰지 않는 이름 바꾸기로 공개하고, 폴더를 동기화한 다음 판별한 형식과 함께 `완료`를 기록해요.
한 작업 안에서 같은 파일(출처가 같은 이름으로 알리는 파일)은 한 번만 받고, 다른 회차에는 그 수신을 가리키는 기록을 남겨요.
재시작한 worker는 회차의 게시물을 다시 열기 전에, 끝나지 않은 기록을 디스크와 이렇게 대조해요. 게시물이 사라졌거나 출처를 쓸 수 없어도 대조는 먼저 끝내요.

| 기록 | 디스크 | 처리 |
| --- | --- | --- |
| 의도 | 임시 파일이 없거나 비어 있음 | 받은 바이트가 없으므로 버리고 새로 시도해요. |
| 의도 | 알린 길이보다 짧은 임시 파일 | 끝까지 받지 못한 것이 확실하므로 그 바이트를 지우고 새로 시도해요. 받기를 마친 파일을 다시 받는 것이 아니에요. |
| 의도 | 알린 길이와 같은 임시 파일 | 알린 길이를 신뢰할 근거로 보고 받음으로 기록한 뒤 검증하고 공개해요. |
| 의도 | 알린 길이가 없거나 그보다 긴 임시 파일 | 보류해요. |
| 받음 | 기록한 객체·길이·해시의 임시 파일 | 검증하고 공개해요. |
| 받음 | 임시 파일 없음, 공개 경로에 기록한 객체·길이·해시 | 검증하고 완료로 기록해요. 파일이 아니면 이 시도의 파일이므로 실패를 기록하고 지운 뒤 경로 기록을 지워요. 검증이 비정상으로 끝나거나 지우지 못하면 보류해요. |
| 받음 | 그 밖 | 보류해요. 같은 바이트가 다른 파일로 있어도 이 시도의 결과로 보지 않아요. |
| 완료 | 공개 경로의 길이·해시가 기록과 같음 | 재사용해요. |
| 완료 | 그 밖 | 보류해요. |
| 실패, 경로 기록이 남음 | 실패 기록과 바이트 삭제 사이에 멈췄어요. | 임시 파일과 공개 경로 중 기록한 객체·길이·해시인 파일만 지우고, 다른 파일은 그대로 둔 채 경로 기록을 지워요. 읽거나 지우지 못하면 보류해요. |

보류한 파일은 그 회차를, 보류한 회차는 그 작업을 보류하며, worker는 보류한 작업을 스스로 다시 집지 않아요. 임시 파일과 공개 경로의 파일은 그대로 남겨요.
수신 기록은 커밋마다 동기화해서, 전원이 꺼져도 파일 효과보다 그 의도의 기록이 먼저 남아요. 다섯 번 시작해도 실행이 한 번도 끝나지 않은 작업은 뒤의 작업을 막지 않도록 보류해요. 실행이 한 번 끝나면, 기다림으로 끝나도, 다시 세요.

보관과 적용은 받기가 끝난 뒤 같은 실행에서 이 원칙을 다음 순서로 지켜요(티켓 0063).
받은 파일마다 배치 계획 줄(파일, 회차와 그 근거, 할 일)을 먼저 기록하고, 줄마다 파일 효과 하나(보관, 또는 영상 옆 적용)를 실행해요.
효과는 ID·작품 폴더 안의 임시 파일 `.trss/tmp/<ID>`·목적지·바이트의 길이와 SHA-256을 `의도`로 기록한 뒤, 원본(보관이면 수신 영역의 파일, 적용이면 보관본)을 임시 파일에 복사해 동기화하고 다시 읽어 확인해요.
임시 파일의 객체를 `준비`로 기록하고, 적용이면 그 회차를 다시 보아 그사이 자막이 생겼으면 덮어쓰지 않고 임시 파일을 지운 뒤 [교체 계획](subtitles.md#교체-계획과-반영)을 만들어 승인을 기다려요.
덮어쓰지 않는 이름 바꾸기로 공개하고 두 폴더를 동기화한 다음, 효과의 `완료`와 그것이 만든 기록(자산·보관본, 또는 적용본)을 한 트랜잭션에 기록해요.
보관 목적지가 그사이 다른 파일로 차면 다음 번호의 이름으로 다시 시도하고(그 이름에 같은 바이트의 보관본이 있으면 그것을 써요), 적용 목적지가 차면 덮어쓰지 않고 그 회차의 교체 계획을 만들어요(0068).
다른 작업의 끝나지 않은 적용 효과가 그 회차를 가려고 있으면, 적용하지도 교체 계획을 만들지도 않고 보관만 해요. 끝나지 않은 효과는 그 작업이 다시 돌 때 이어지기 때문이에요.
적용본을 공개한 경로에 이전 적용본의 기록이 남아 있으면 그 기록을 지워진 것으로 적어요. 덮어쓰지 않는 이름 바꾸기가 성공했으니 사람이 그 파일을 지운 것이에요.
공개한 파일의 기록을 DB가 제약 위반으로 거절하면 다시 해도 같으므로 그 효과를 보류해요.
받은 파일의 모든 줄을 보관한 뒤 수신 영역의 그 파일을 지우며, 지우기 전에 그 사실을 기록해요. 그 파일을 같이 쓰는 수신(`same_as`)도 함께 지운 것으로 적어요. 뒤의 실행에서 같은 파일을 받는 회차는 다시 받지 않고 지운 수신을 같이 써요.
작품 폴더가 없으면(공유가 아직 붙지 않았거나 작품이 옮겨짐) 아무것도 쓰지 않았으므로 보류하지 않고 `영상 대기`로 기다려요. worker가 시작할 때 다시 줄에 세워요.
회차에 영상이 없는 적용 줄은 보관까지만 하고 `영상 대기`로 기다리다가, 라이브러리가 그 회차의 영상을 기록하면 worker가 다시 줄에 세워 적용해요([영상 대기](subtitles.md#영상-대기)).
재시작한 worker는 끝나지 않은 효과를 디스크와 이렇게 대조해요.

| 기록 | 디스크 | 처리 |
| --- | --- | --- |
| 의도 | 무엇이든 | 임시 파일은 이 효과만 쓰므로 지우고 효과를 버린 뒤, 그 줄을 처음부터 다시 해요. |
| 준비 | 기록한 객체·길이·해시의 임시 파일 | 공개부터 이어가요(적용이면 회차를 다시 봐요). |
| 준비 | 임시 파일 없음, 목적지에 기록한 객체·길이·해시 | 이름 바꾸기가 끝났어요. 폴더를 동기화하고 완료로 기록해요. |
| 준비 | 그 밖 | 보류해요. 같은 바이트가 목적지에 있어도 이 효과의 결과로 보지 않아요. |

보류한 효과는 그 줄과 작업을 보류하고, worker는 스스로 다시 집지 않으며, 그 파일들은 그대로 둬요. 보류한 효과의 목적지는 다른 효과가 쓸 수 있어요.
다섯 번 시작해도 끝나지 않아 보류한 작업의 끝나지 않은 효과(옮겨 둔 제거 포함)도 그 줄, 그 효과의 승인한 교체 계획과 함께 보류해요. 완료한 교체 계획의 정리만 남은 효과는 보류하지 않고, 그 작업이 다시 돌 때 정리해요.
교체의 제거·들이기 효과와 재시작 대조는 [교체 계획과 반영](subtitles.md#교체-계획과-반영)의 순서를 따르며, 표는 `trss-jobs`의 `place::replace` 모듈 문서에 있어요. 마이그레이션 52는 이 효과를 위해 묶음·효과 표를 외래 키를 끈 트랜잭션에서 새로 만들고, 커밋 전에 참조를 검사해 그 마이그레이션이 새로 깨뜨린 참조가 있으면 실패해요. 그 전부터 깨져 있던 참조로는 멈추지 않아요.
목표 3에서 받기까지만 하고 끝난 후보 작업은 마이그레이션이 다시 줄에 세워, worker가 다시 받지 않고 보관과 적용을 이어가요.

위 각 파일 효과 전후와 DB 완료 기록 전후에 중단한 사례를 구분해 검증해요.
공개 후 기록 전의 재시작, 불명확한 제거, 보호 복사 공간 부족, 새 경로의 외부 점유, 멈춘 이전 worker, 폰트 참조 생성과 정리의 경쟁을 관찰해 중복 효과·무승인 변경·허위 완료와 자료 손실을 막는지 확인해요.
실제 파일시스템의 공개·동기화·객체 식별 동작은 구현 환경에서 검증해야 하며, 이 절차를 정한 것만으로 프로세스 중단이나 저장장치 장애의 내구성을 입증한 것은 아니에요.

## 남은 구체화

- 원격 화면은 휴대폰 한 대와 이 개발 PC의 LAN에서만 확인했어요. 다른 휴대폰, VPN·HTTPS(WSS) 경로, 지연, 원격 페이지에 치는 휴대폰 가상 키보드 입력, CPU 한도에서의 인증은 확인하지 않았어요. 페이지 창의 입력칸은 휴대폰에서 바로 입력받아 아이폰 기본 키보드로 확인했어요(2026-10-04).
- 사용자는 원격 화면의 스크롤이 부드럽지 않다고 했어요. 인증은 서버가 인증 상자를 가운데에 두므로 스크롤이 필요 없고, 직접 찾기처럼 원격 화면을 둘러보는 경로에서는 부드러우면 좋지만 필수는 아니에요(사용자 판단, 2026-10-02).
- 작업 단계의 이름은 출처마다 다를 수 있어요(인증이 없는 출처는 `인증`을 거치지 않아요).
  출처별 단계 목록의 초안은 아래 [출처별 단계 초안](#출처별-단계-초안)이고, 출처를 구현할 때 실제 코드로 다시 확인해요.

### 출처별 단계 초안

단계 이름은 [작업 상세](#작업-상세)의 `게시물 열기`·`인증`·`받기`를 따르고, 출처에 따라 `파일 찾기`와 `복원`을 더해요.
`브라우저`는 서버 브라우저가 필요한지이고, 모든 경로에서 HTTP로 게시물을 읽을 수 있었어요.

- WinPNG 읽기(0043): 게시물을 HTTPS로 읽어 첨부도 Drive 파일 링크도 없고 본문 컨테이너에 `*.kakaocdn.net`의 `.png` 이미지가 있으면 서버 브라우저로 넘겨요. 첨부가 없는 게시물만 브라우저를 켜요.
  1. 작업의 브라우저 실행에 게시물을 열고, 뷰어의 패널(`#winPNG`, `#viewFileList`)과 스크립트(`downloadZip`·`WithTarget`·`BufferedImage`)가 뜰 때까지 45초 기다려요. 스킨에 뷰어가 없으면 `출처 구조 바뀜`이에요.
  2. 본문(`.tt_article_useless_p_margin`·`.contents_style`·`#article-view`)의 이미지 중 출처가 WinPNG로 알아본 것, 곧 `*.kakaocdn.net`의 주소가 `.png`로 끝나는 것을 차례로 봐요. 주소는 이미지의 `currentSrc`·`src`·`data-src` 순으로 찾고, 늦게 불러오는 이미지는 `src`를 그 주소로 채운 뒤 열어요. 같은 주소의 이미지는 한 번만 봐요. 이미지마다 뷰어 자신의 판별(`WithTarget.possibility`, 이미지를 페이지 안에서 `fetch`해 읽어요)을 물어 0이면 그림이라 건너뛰고, 판별이 이미지를 가져오거나 해석하지 못한 이미지도 건너뛰어요. 다른 이미지가 읽히면 게시물은 그대로 이어가요.
  3. 읽을 수 있는 이미지는 클릭해 열어요. 뷰어가 작업을 마쳤다는 신호는 패널에 `progress` 클래스가 없고, 받을 수 있는 링크(`blob:`·`data:` 주소)가 하나 이상이고, 만드는 중인 항목(`a.processing`)이 없는 상태가 반 초 간격의 두 번 연속 같은 목록인 것이고, 90초 안에 오지 않으면 `네트워크 실패`예요. 직전 이미지가 남긴 목록은 열기 전에 표시해 두어 새 목록과 섞지 않아요.
  4. 뷰어가 띄우는 대화상자(`alert`·`confirm`·`prompt`)는 모두 취소로 닫아요. 이 중 키를 묻는 입력창(`prompt`)이 뜬 이미지가 하나라도 있으면 다른 이미지에서 파일이 나왔더라도 그 게시물은 `추가 입력 필요`예요(키가 필요한 실제 이미지를 아직 보지 못해서, 일부만 받지 않고 사람이 확인하게 하는 쪽으로 정했어요). `prompt`가 아닌 대화상자는 키를 묻는 것으로 보지 않아요. 대화상자는 게시물을 열기 전에 처리하도록 켜 둬서 페이지가 불러오는 동안 띄우는 것도 닫혀요.
  5. 링크를 목록 순서대로 마우스로 눌러(다른 링크에 가려지지 않는 지점을 찾아 눌러요) 브라우저 다운로드로 받고, 링크마다 임시 폴더 안의 번호 폴더에 옮겨요. 뷰어는 한 번에 많은 다운로드를 시작하면 열한 번째쯤부터 다운로드를 조용히 버려서(2026-10-03, 같은 링크를 다시 누르면 받아져요), 20초 안에 다운로드가 끝나지 않으면 같은 링크를 최대 네 번까지 눌러요. 그래도 안 되면 `네트워크 실패`예요. 끝난 다운로드는 페이지가 준 이름이 누른 링크의 이름과 같을 때만 그 링크의 파일이에요(브라우저가 파일 이름에 못 쓰는 글자를 `_`로 바꾼 것은 같은 이름으로 봐요). 이름이 다른 다운로드는 앞에서 포기한 클릭이 늦게 끝난 것이라 버리고, 다음 링크의 바이트로 쓰지 않아요. 실행을 시작할 때 이미 끝나 있던 이전 읽기의 다운로드는 먼저 비워요.
  6. 파일의 위치는 뷰어가 보여 주는 폴더(`#viewFileList`의 항목 앞 경로)와 링크의 `download` 이름이에요. 파일은 뷰어가 준 그대로 받고(JMK는 뷰어가 링크를 없애므로 변환된 SMI·ASS만 와서 JMK는 남지 않아요), 폴더 이름은 각각 파일 이름 규칙으로 안전하게 바꿔요. 폴더가 여덟 단계보다 깊거나 폴더 경로가 600바이트를 넘는 파일은 잘라서 받지 않고 그 파일만 `파일 아님`으로 실패해요(다른 파일은 받아요). 작업 폴더 안에서 파일 `X`와 폴더 `X`가 만나면 나중에 오는 쪽의 이름을 `X (2)`로 번호를 붙여 피해요. 파일 이름이 겹치는 경우와 같아요.
  파일의 키는 `winpng:<이미지의 호스트와 경로>#<폴더>/<이름>`이고 서명이 든 쿼리는 들어가지 않아요. 스냅샷은 게시물의 `article:modified_time`과 이미지(`winpng_image`)예요.
  재확인(0050)은 WinPNG에서 나온 파일을 읽지 않고 `출처 구조 바뀜`으로 답해 `읽을 수 없음`이 돼요.
  작업이 다시 시작되면 읽기는 처음부터 다시 해요. 뷰어가 꺼낸 파일은 작업의 임시 폴더(`.tmp/winpng-<작업 ID>`)에 두었다가 회차 하나를 마칠 때마다 지워요. 프로세스가 중간에 죽어 남은 폴더는 같은 작업이 다시 읽을 때 지워지고, 그러지 않더라도 업로드 정리(`Uploads::sweep`)가 한 시간 넘게 아무것도 쓰지 않은 `.tmp/winpng-<UUID>` 폴더를 지워요. 실패 이유에는 브라우저가 말한 글을 넣지 않고 고정된 문장만 보여줘요.
- 다운로드가 서버 폴더에 떨어졌는지는 폴더로 판단해요. Naver처럼 새 창이 시작한 다운로드는 페이지 연결로는 `Browser.download*` 이벤트가 오지 않았지만 파일은 폴더에 있었어요.
- 이 표는 개발 PC의 헤드리스 Chromium과 HTTP 클라이언트로 본 것이고, 서버 브라우저 컨테이너([브라우저 수명](#작업-화면-안의-인증과-브라우저-수명))에서의 수신은 출처 구현에서 확인해야 해요.

### 수신 확인에서 미상으로 남은 것

- erulabo 확인 뒤의 응답은 실제로 보지 못했어요. 0032에서 사람이 푼 다운로드가 `drive.usercontent.google.com/download?id=…`에서 왔다는 것만 알고, 사이트의 `download_url`이 그 Drive 주소인지 erulabo를 거쳐 넘어가는지, 서버 브라우저에서 새 창이 막히는지, 60초가 지난 주소를 브라우저가 어떤 문서로 받는지는 미상이에요. 그래서 거절 판단은 페이지(창·팝업의 메인 프레임)가 받은 Drive 호스트·erulabo `/file/…`·Google 로그인 문서로 한정했고, 다른 호스트의 문서는 거절로 보지 않아요(다운로드가 오지 않으면 실행의 유휴 종료까지 기다려요). 그런 호스트의 문서가 페이지에 오면 실행마다 한 번, 호스트 이름만(주소·경로·쿼리 없이) 서버 로그에 남겨서 실제 확인에서 받기 호스트를 알 수 있게 해요. 남은 한계는 둘이에요. 사람이 확인을 기다리는 동안 메인 프레임을 직접 Drive 페이지로 옮기면 그 문서도 거절로 봐서 항목이 실패해요. 페이지 안의 프레임이 받은 거절(예: 프레임으로 연 다운로드 주소의 `403`)은 보지 못해서, 그 프레임에서 파일이 오지 않으면 유휴 종료까지 기다려요. 받은 파일에 Drive ID가 붙는지도 이 응답에 달렸어요.
- WinPNG를 서버 브라우저 없이 복원할 수 있는지, 뷰어 스크립트 버전이 바뀌면 같은 PNG의 SMI·ASS 바이트가 달라지는지(하느 762의 12화는 2026-09-26에 32,355바이트, 2026-10-03 오전에 33,627바이트, 같은 날 서버 브라우저 컨테이너에서 32,201바이트였고, 게시물 수정과 스크립트 버전 변경을 가르지 못했어요)는 미상이에요. 뷰어가 만든 바이트를 같은 파일의 판정 근거로 쓰기 전에 확인해야 해요.
- 키가 필요한 실제 WinPNG 이미지는 보지 못했어요. `추가 입력 필요`는 뷰어의 해석을 실패하게 만든 실제 뷰어로만 확인했어요.
- 뷰어의 판별 함수(`WithTarget.possibility`)와 패널의 구조(`#winPNG`·`#viewFileList`·`a.processing`)에 기대는 읽기라, 스킨이 뷰어를 바꾸면 `출처 구조 바뀜`이나 `네트워크 실패`로 보일 수 있어요.
- Tistory 서명 URL이 월 말(`expires`가 이달 말 23:59:59 KST)을 지난 뒤의 거절, Naver 토큰의 최대 유효 시간(20분 이상은 확인)은 보지 못했어요.
- 게시물 수정 시각의 변화가 언제나 파일 변경인지는 미상이에요. 글만 고쳐도 바뀌어요.
