# 웹 GUI와 자막 처리 구현 명세

## 목표와 범위

작품별 영상·자막 상태와 다운로드 규칙을 웹에서 관리하고, 사용자가 선택한 자막의 다운로드·분류·이름 맞춤·배치를 서버가 이어서 처리해요.
사용자는 필요한 CAPTCHA를 trss 작업 화면 안에서 해결하며, 직접 파일을 내려받아 업로드하거나 압축을 풀고 옮기는 방식으로 자동화를 대체하지 않아요.
대상은 혼자 LAN·VPN에서 사용하는 환경이며, 앞으로 trss가 받는 영상, trss로 받은 기존 영상, 사용자가 지정한 trname 정리 폴더의 영상을 모두 포함해요.

이 문서는 해당 범위의 현재 요구와 완료 기준을 담당해요.
[주제 문서](../brainstorm/web-gui-subtitles.md)는 선택 배경과 조사·실험 근거를, [용어집](../glossary.md)은 도메인 의미를, [설정](../adr/0001-app-managed-download-rules.md)·[인증](../adr/0002-server-browser-subtitle-authentication.md)·[보관과 적용](../adr/0003-stored-and-applied-subtitles.md) ADR은 선택과 이유를 담당해요.
명세 작성 시점에는 제품 구현을 시작하지 않았으며, 아래 완료 조건을 통과한 것으로 간주하지 않아요.

후보 자동 선택, 무승인 덮어쓰기, CAPTCHA 우회, 앱 자체 로그인·다중 사용자 기능, Transmission 제어 화면의 중복 구현, 외부 알림 채널은 범위 밖이에요.
서버 전역 폰트 설치와 원본 영상 재먹스도 선택한 동작에 포함하지 않아요.
다른 형식·언어·릴리스 지원의 미확정 범위를 기본 지원으로 간주하지 않으며, 기존 영상 이름을 임의로 다시 정리하는 기능으로 범위를 넓히지 않아요.

## 요구사항과 완료 기준

### 웹 관리와 접근 경계

- 작품·시즌·회차별로 영상 유무, 자막 보관·적용 상태, 누락 및 수정 후보를 확인하고 후보 선택이나 해당 작업으로 이동할 수 있어요.
  보관본만 있는 회차를 적용 완료로 표시하지 않으며, 관리 전부터 존재한 자막도 없는 것으로 취급하지 않아요.
- 실패·인증 대기 작업을 모아 막힌 이유와 진행 상태를 확인하고, 같은 작업에서 필요한 인증이나 재시도를 이어갈 수 있어요.
  브라우저 탭을 닫았다 다시 열어도 이미 얻은 후보·작업·설정이 사라지지 않아야 해요.
- PC·태블릿·휴대폰에서 후보 선택, 자막 비교·승인, 설정 편집과 원격 인증을 끝낼 수 있어야 해요.
  작은 화면에서는 상세를 단계적으로 펼칠 수 있지만 필수 비교 정보나 확인 동작을 생략하지 않아요.
  실제 좁은 화면과 터치·가상 키보드로 주요 흐름을 수행하고, 원격 화면을 확대하거나 크기·방향을 바꾼 뒤에도 보이는 위치와 입력 위치가 맞는지 확인해요.
  원격 입력에 초점이 있을 때와 trss의 다른 폼을 편집할 때를 구분하며, UI 라이브러리 선택만으로 모바일 인증이 검증됐다고 표시하지 않아요.
- Transmission은 상태와 기존 관리 화면으로 이동하는 링크를 제공해요.
  trss 웹에 시작·일시정지·삭제 기능을 중복 구현하지 않으며, 기존 영상 RSS 처리의 Transmission 연동까지 읽기 전용으로 바꾸는 것은 아니에요.
- 앱 자체 로그인 대신 실제 배포 환경의 LAN·VPN·앞단 인증으로 접근을 제한해요.
  허용된 접속으로 웹·작업 조작·원격 입력을 사용한 뒤, 보호 경계 밖에서 앱 직접 주소와 원격 화면·제어 경로에 접근해 보호를 우회할 수 없는지 확인해야 해요.

#### 화면 구성

앱의 첫 화면은 작품 목록·작업 목록과 별개의 요약 홈으로 제공해요.
새 자막 후보와 인증 대기·승인 대기·실패 작업을 함께 요약하고, 관련 작품이나 작업의 상세 화면으로 이동할 수 있어야 해요.
확인이 필요한 작업과 새 후보는 비슷한 비중으로 다루며, PC에서는 나란히, 모바일에서는 확인 필요·새 후보 순서로 보여줘요.
그 아래에 진행 중인 작업과 최근 완료 작업을 배치해요.

주요 메뉴는 홈·작품·작업·다운로드 규칙·설정이며, PC에서는 사이드바, 모바일에서는 하단 탭으로 이동해요.
모바일에서는 다운로드 규칙 메뉴를 규칙으로 줄여 표시해요.

작품 상세에는 시즌 선택과 회차·자막 후보·보관 자막·작품 설정 탭을 두며, 기본으로 회차 상태를 보여줘요.
홈의 새 후보에서 이동하면 해당 작품의 자막 후보 탭으로 바로 연결해요.
작품 목록은 왼쪽의 표지와 오른쪽의 작품명·영상·자막 상태를 묶은 목록형으로 제공해요.
표지를 작은 아이콘 크기로 제한하지 않으며, 표지를 충분히 볼 수 있는 행 높이를 사용해요.
이미지가 없거나 불러오지 못해도 작품명과 영상·자막 상태를 확인하고 작품을 열 수 있어야 해요.
표지는 작품 정보로 외부 검색해 자동 지정하고, 사용자가 검색 결과에서 다시 고르거나 이미지를 직접 지정할 수도 있어요.
사용자가 선택·직접 지정한 결과를 이후 자동 검색 결과로 덮어쓰지 않아요.
표지 연결은 표시용이며, Anissia 연결이나 영상·자막의 작품·시즌·회차 대응을 변경하는 근거로 사용하지 않아요.
표지의 구체적인 반응형 크기는 실제 화면에서 조정해요.

자막 비교·승인과 원격 인증은 PC·모바일 모두 trss 내부의 전용 작업 상세 페이지에서 진행해요.
작품 화면과 작업 목록 어느 쪽에서 들어가도 같은 작업·항목별 결과와 승인 계획으로 연결하며, 외부 창이나 PC 우측 패널로 대신하지 않아요.

작품과 다운로드 규칙은 각각 채널 구분 없는 통합 목록으로 보여주며, 먼저 채널을 골라야 목록을 볼 수 있는 구조로 만들지 않아요.
RSS 채널은 작품의 분류가 아니라 어디서 어떻게 다운로드 후보를 받아올지에 관한 설정이며, 규칙 목록에서 적용되는 수집 경로를 확인할 수 있어요.

설정은 공통 정책·감시 폴더·가져오기와 내보내기의 세 탭으로 나눠요.
공통 정책에는 자막 형식 우선순위와 앱에서 관리하는 브라우저 유휴 시간·동시 작업 수를 두며, 배포 환경 값의 웹 편집으로 범위를 넓히지 않아요.

#### 웹 명령과 상태 갱신

설정 저장 응답은 서버에 반영된 설정과 그 버전을 확인하는 응답이며, 다운로드·적용 명령의 접수 응답은 영속화된 명령·작업 ID를 확인하는 응답이에요.
후자의 접수를 파일 수신·적용 완료로 표시하지 않고, worker가 기록한 실제 항목별 진행·대기·실패·완료 결과를 따로 보여줘요.
규칙·대응·가져오기 계획의 편집에는 확인한 대상 버전을, 교체 승인에는 확인한 불변 계획의 ID·버전을 전달하며 서버가 다시 검증해요.
이 실행 중 버전은 YAML 교환 규격의 `version`과 다른 값이에요.

| 입력·통신 상황 | 필요한 처리와 관찰 |
| --- | --- |
| 두 화면에서 같은 설정을 편집 | 먼저 저장한 뒤 오래된 버전으로 보낸 저장은 변경 없이 충돌로 거부해요. 두 번째 화면의 편집 입력은 남기고 현재 서버 값과 비교해 다시 저장할 수 있어야 해요. |
| 비교 후 계획·대상이 변경 | 이전 화면의 승인 버튼이 활성화돼 있어도 서버가 오래된 승인을 거부하고 새 비교를 요구해요. 현재 버전으로 몰래 치환해 승인하지 않으며, 실제 파일도 바뀌지 않아야 해요. |
| 같은 명령의 중복 전달 | 같은 사용자 동작의 명령 ID와 내용을 고정해 전달하고, 이미 접수한 같은 명령이면 기존 결과·작업을 돌려줘요. 같은 ID에 다른 내용을 붙이면 거부하며, 반복 전달 후 실제 작업이 추가 생성되지 않았는지 확인해요. |
| 명령 접수 후 응답 단절 | 같은 명령 ID로 접수 결과를 조회하고, 확인 전에는 성공·실패를 단정하거나 새 ID로 자동 재전송하지 않아요. 기록을 찾을 수 없는 경우도 확인 불가와 실행 실패를 구분해요. |
| 목록 정렬·필터·새 조회 | 행 위치가 아니라 항목 ID와 확인한 대상 정보를 기준으로 선택을 유지해요. 새로 나타난 후보를 자동 선택하지 않으며, 사라지거나 바뀐 선택 대상은 확인 필요로 표시해요. |
| 늦게 도착한 이전 조회 응답 | 현재 화면의 대상·검색 조건과 조회 순서를 확인해, 이전 응답이 최신 상태나 이미 확인한 명령 접수 결과를 덮어쓰지 않게 해요. 응답 순서를 뒤집은 경우에도 선택과 완료 상태가 잘못 되돌아가지 않아야 해요. |
| 연결 단절·접근 거부 | 마지막으로 확인한 상태와 조회 시점을 남기되 최신 상태로 표시하지 않아요. 조회 실패만으로 서버 작업을 실패·취소 처리하지 않으며, 접근이 거부되면 새 명령과 원격 입력을 중지해요. |
| 화면 재접속 | 서버의 현재 작업과 항목별 결과를 조회해 복원하고, 화면을 복원하는 것만으로 다운로드·적용·승인을 다시 보내지 않아요. |

작업 상태 갱신은 우선 HTTP 주기 조회를 사용하고, 화면·입력을 전달하는 원격 인증 WebSocket과 구분해요.
보이는 화면의 기본 조회 간격은 2초로 두며, 앞선 조회가 끝나지 않았으면 같은 화면의 주기 조회를 쌓지 않아요.
이는 초기 UI 기본값이며 처리 완료 시간의 보장이나 실측 성능값이 아니에요.
숨겨진 화면의 주기 조회는 멈추고 다시 활성화되면 갱신하되, 서버의 5분 RSS 처리·2시간 후보 조회나 진행 중 작업은 계속돼요.
화면의 마지막 동기화 시각과 출처·파일 상태를 실제로 관찰한 시각을 구분하며, 편집 중인 입력을 새 조회 값으로 자동 덮어쓰지 않아요.

상태 조회는 브라우저를 시작하거나 사용자 조작 시각을 갱신하지 않아요.
원격 연결이 끊기면 같은 작업의 유효한 실행에 다시 연결하되, 유휴 종료된 브라우저를 연결 재시도만으로 계속 새로 띄우지 않아요.
사용자가 작업 화면을 다시 열거나 재개할 때는 기존 수명 정책에 따라 필요한 브라우저를 준비해요.
화면을 열어 둔 채 입력 없이 유휴 종료를 맞은 경우와, 실제로 돌아와 재개한 경우를 나눠 관찰해요.

불명확해서 보류된 같은 회차·형식의 대안은 원래 파일명·출처·관찰한 용도·릴리스와 판별 근거를 함께 보여주고 사용자가 선택하게 해요.
모르는 값은 미상으로 남기며, 목록의 첫 행이나 큰 파일을 기본 선택하지 않아요.
작은 화면에서도 상세를 열어 같은 정보를 확인할 수 있어야 하고, 필터 변경·상세 열기·새로고침만으로 선택이나 교체 승인이 생기지 않아야 해요.
출처에서 받은 자막 본문·파일명·오류 문구는 데이터로 표시하며, SMI의 태그나 첨부 HTML을 trss 페이지의 실행 가능한 마크업으로 삽입하지 않아요.

### 앱 설정과 다운로드 규칙

- 실행 기준은 앱이 관리하는 설정으로 전환해요.
  웹에서 저장한 채널·규칙을 다음 처리에 사용하고, 기존 `CHANNELS_CONFIG_URL`의 외부 YAML 변경이 앱 설정을 계속 덮어쓰는 경로는 남기지 않아요.
- 기존 YAML과 새 앱 YAML을 가져올 때 현재 정보와 비교하고, 사용자가 선택한 항목만 추가하거나 지정한 기존 항목을 교체해요.
  선택하지 않은 항목, 가져온 파일에 없는 기존 설정·보관 정보, 작업 이력, 실제 영상·자막 파일이 적용 전후에 그대로 남는지 확인해요.
- 기존 YAML은 채널 단위로 추가·교체하고 채널 안의 규칙 순서를 보존해요.
  이름·조건 유사성으로 규칙을 임의 병합하거나 자막 연결 설정을 바꾸지 않아요.
  채널의 `excludes`와 규칙의 `episode`·`directory`도 기존 의미를 보존하고, 기본값이 생략된 기존 YAML을 읽을 수 있어야 해요.
- 새 앱 형식은 기존 YAML 구조에 묶이지 않으며, 채널 안의 규칙별 선택 가져오기를 지원해요.
  선택하지 않은 규칙은 유지하고, 추가·교체되는 규칙 및 최종 평가 순서를 실행 전에 확인해요.
- 새 YAML은 `version`으로 교환 규격을 식별하고, 설정 영역과 보관 정보 영역을 구분해요.
  항목의 안정적인 ID와 참조를 보존하되, 같은 이름·조건만으로 기존 항목에 덮어쓰지 않아요.
  추가로 복제하는 항목에는 새 ID를 부여하고 그 참조를 함께 연결하며, 지정한 기존 항목을 교체할 때는 그 항목의 ID를 유지해요.
  미지원 버전이나 중복 ID를 가진 입력은 변경 없이 거부하고, 선택한 가져오기 계획의 참조가 해결되지 않으면 필요한 연결을 표시해 반영을 보류해요.
- 내보내기는 채널·규칙, 감시 폴더, 작품 연결, 회차 대응·자막 정책과 보관본의 제작자·출처·회차·수정본·자산·폰트 연결 정보를 담아요.
  새 환경에서 실제 파일과 함께 가져와 설정과 보관 관계를 복원할 수 있어야 하며, 작업 이력·큐·과거 승인·영상·자막·폰트 바이트는 포함하지 않아요.
  구버전 trss용 YAML이나 전체 DB·파일 백업으로 안내하지 않아요.
  Transmission 접속 주소·기존 속도 제한·큐 크기, 서버 포트와 DB 위치는 환경 변수·배포 설정으로 분리하며 앱 YAML의 가져오기·내보내기로 변경하지 않아요.
  새 환경에서 이 값은 별도로 설정하고, 기존 RSS 처리의 Transmission 설정 적용 동작은 유지해요.
- 보관 정보는 SQLite에만 유지하고 작품 폴더에 별도 복원용 목록을 상시 저장하지 않아요.
  파일은 `.trss-subtitles/`를 포함한 작품 폴더로 따로 옮기며, 가져오기에서 새 폴더 위치와 보관 파일의 상대 경로·내용 식별 정보를 대조해요.
  누락되거나 내용이 다른 파일은 정상 복원·적용으로 표시하지 않고, 가져온 경로가 확인한 폴더 밖의 파일을 가리키게 하지 않아요.
  보관 정보 복원 자체로 다운로드·적용·파일 정리를 실행하거나 과거 승인을 되살리지 않으며, 실제 적용 상태는 현재 파일로 확인해요.
- 기존 채널 제외 문자열 판정, 부분 문자열·대소문자 무시 조건과 첫 일치 규칙 우선순위를 유지하면서 정규식 조건도 실제 동작하게 해요.
  규칙 변경 시 현재 RSS 항목을 변경 중인 규칙으로 평가해, 실제 다운로드 실행 전에 선택 여부·적용 규칙·저장 위치를 웹에서 미리 보여줘요.
  같은 RSS 항목과 같은 설정으로 미리보기와 실제 실행을 비교해 선택 여부, 적용 규칙, 저장 위치가 일치해야 해요.
  여러 규칙에 동시에 맞는 항목, 일치하지 않는 항목, 잘못된 정규식을 구분하고, 정규식 오류를 부분 문자열 검색으로 바꾸거나 실행 중 패닉으로 처리하지 않아요.

#### 새 YAML의 구성

새 교환 형식은 `version: 1`과 `settings`·`library` 영역으로 구성해요.
규칙은 기존처럼 채널 안의 순서 있는 목록으로 두고, 보관 정보는 작품별로 묶어 설정의 작품 ID를 참조해요.
DB 테이블을 그대로 덤프하는 형식이 아니며, YAML의 버전은 앱 릴리스나 SQLite 스키마 버전과 구분해요.

| 영역 | 담는 정보와 관계 |
| --- | --- |
| `settings.channels` | 안정적인 채널 ID, `url`·`directory`·`excludes`, 채널 안의 순서 있는 `rules` 목록이에요. |
| `settings.channels[].rules` | 안정적인 규칙 ID와 기존 `match`·`regex`·`case_insensitive`·`directory`·`episode` 의미를 유지해요. |
| `settings.watch_folders` | 감시 폴더의 안정적인 ID와 앱에서 접근하는 경로예요. |
| `settings.works` | 작품 ID와 작품 폴더, 작품 안의 시즌 및 확인한 Anissia 연결·출처별 회차 대응을 담아요. |
| `settings.subtitle_policy` | 전역 형식 우선순위이며, 작품별 재정의는 해당 작품 설정에 둬요. |
| `settings.browser` | 유휴 시간을 초로 나타내는 `idle_timeout_seconds`와 동시 작업 상한 `max_concurrent_jobs`예요. |
| `library.works` | 설정의 작품 ID별로 보관본·수정본·출처·자산과 폰트 연결을 묶어요. 실제 적용 여부를 확정하는 권한이나 작업 재개 지시는 담지 않아요. |

기존 `episode`는 영상 이름 변경에 전달하는 값이며, 자막 출처의 회차 대응으로 전용하거나 복사하지 않아요.
기존 채널 경로와 규칙 경로로 정하는 다운로드 위치도 명시적인 작품 ID나 확인된 Anissia 연결을 대신하지 않아요.
ID가 없는 구형 YAML에서 새 앱 항목을 추가할 때도 새 ID를 발급해요.
구형 파일에 없는 작품 연결·회차 대응을 추측해 생성하지 않아요.

보관 자산은 작품 폴더 기준 상대 경로, 원래 파일명, 파일 종류, 바이트 크기와 내용 식별 정보를 가지며, 보관본이 자막·폰트·첨부 자산을 ID로 참조해요.
경로와 표시 이름을 ID로 쓰지 않으므로 이름 변경이 곧 다른 작품이나 자산의 생성은 아니에요.
내보내기는 일관된 DB 읽기 시점의 설정·보관 관계를 사용하되, 실제 파일을 함께 백업했다는 뜻은 아니에요.

##### 작품·회차 대응의 필드

ID는 비어 있지 않은 문자열이며, 문서 안에서 항목을 선언하는 ID는 중복될 수 없어요.
참조는 해당 종류와 작품 범위의 항목으로 연결되어야 하며, 표시 이름·경로·외부 사이트의 번호를 앱 ID로 대신하지 않아요.
아래의 선택적 관찰값은 생략하거나 `null`이면 미상이며, 빈 문자열이나 추측값으로 사실을 만들어 채우지 않아요.

| 위치 | 필드와 의미 |
| --- | --- |
| `settings.works[]` | `id`, 앱이 접근하는 작품 폴더 `directory`, `seasons`, 선택적 작품별 `subtitle_policy`예요. 정책이 없으면 전역 값을 사용해요. |
| `seasons[]` | `id`, 0 이상 정수인 `number`, 작품 폴더 기준 상대 경로 `directory`, 확인한 `anissia_anime_no`, `sources`, `episode_mappings`예요. 미연결 Anissia 번호는 `null`이에요. |
| `sources[]` | `id`와 출처를 구분하는 `label`, 관찰한 `creator`·`site`를 담는 자막 출처 연결(Subtitle Source Binding)이에요. 한 웹사이트의 모든 제작자·릴리스가 같은 회차 체계를 쓴다고 간주하지 않아요. |
| `episode_mappings[]` | `id`, 같은 시즌의 `source_id`, 번호의 근거인 `basis`, `mode`, `overrides`와 조건부 `offset`이에요. |
| `basis` | Anissia 후보의 회차를 쓰는 `anissia` 또는 첨부에서 확인한 회차를 쓰는 `attachment`예요. 후보 회차와 파일 이름에서 읽은 회차를 근거 없이 같은 값으로 취급하지 않아요. |
| `mode`·`offset` | `offset` 모드는 정수 차이 `offset`을 적용하고, `explicit` 모드는 명시한 대응만 사용하므로 `offset` 필드를 두지 않아요. |
| `overrides[]` | 출처의 회차 문자열 `source_episode`와 0 이상 정수인 `local_episode`의 쌍이며, 기본 차이보다 먼저 적용하는 명시적 대응이에요. |

같은 출처 연결과 `basis`에 여러 기본 대응을 겹쳐 두지 않아요.
숫자 회차의 비교 키는 부동소수점 변환 없이 불필요한 앞자리 0과 소수 끝의 0만 제거해 만들고, 원래 문자열은 보존해요.
따라서 `013`·`13.0`은 같은 숫자 키이며, 서로 다른 결과를 가진 중복 예외로 등록할 수 없어요.
숫자가 아닌 회차 표시는 명시적 문자열 대응만 사용하고, `13.5`를 `13`이나 `14`로 반올림하지 않아요.

적용 순서는 확인한 작품·시즌·출처 연결 확인 → 해당 `basis`의 회차 관찰값 확인 → 명시적 대응 조회 → 정수 회차에 한해 기본 차이 적용 → 대상 회차와 영상의 모호성 확인이에요.
예외가 없는 소수·특수 회차, 음수 결과, 표현 범위를 넘는 값, 미확인 출처나 여러 대상은 보류해요.
`offset: -12`의 `13 → 1`·`14 → 2`, `13.5`의 명시적 예외 유무, 잘못된 출처·시즌, 후보 번호와 첨부 번호의 불일치를 구분해 확인해요.
이 대응은 숫자 해석과 연결의 계약이며, 미지원 영상 이름이나 특수편을 자동 식별한다는 약속은 아니에요.

##### 보관 관계의 필드

| 위치 | 필드와 의미 |
| --- | --- |
| `library.works[]` | 설정의 작품을 가리키는 `work_id`와 `packages`·`stored_subtitles`·`assets` 목록이에요. |
| `packages[]` | `id`, 수신 경로 종류 `source_kind`, 관찰한 게시물 `source_page`, 선택적 `received_at`, `entries`예요. 수신 시각은 시간대가 명시된 시각이며 모르면 비워 둬요. |
| `entries[]` | `asset_id`, 출처가 제공한 원래 파일명·묶음 내부 이름인 `original_name`, 선택적 `source_file_date`예요. 같은 폰트가 다른 이름·보고 날짜로 들어와도 각 출처의 관찰값을 보존해요. |
| `assets[]` | `id`, `kind`, 작품 폴더 기준 `relative_path`, 0 이상 정수 `byte_size`, 소문자 64자리 16진수 `sha256`예요. |
| `kind` | `subtitle`·`font`·`attachment`·`companion`·`other`로 보관 파일의 역할을 구분해요. 이 값만으로 실제 형식이나 자동 적용 지원을 확정하지 않아요. |
| `stored_subtitles[]` | 특정 보관 수정본의 `id`, `package_id`, `subtitle_asset_id`, 선택적 `source_id`, 원래 회차 관찰값 `source_episodes`, 현재 연결의 근거 `assignment`, 관찰한 `format`·`encoding`·`creator`·`language`·`purpose`·`release`·`revision_label`, `font_asset_ids`·`attachment_asset_ids`·`companion_asset_ids`예요. |
| `source_episodes` | 관찰 가능한 `anissia`·`attachment` 회차를 각각 원래 문자열로 담아요. 모르는 번호를 다른 쪽 값이나 현재 적용 경로로 채우지 않아요. |
| `assignment` | `mode: mapped`이면 `mapping_id`를 참조하고 그 대응의 `basis`와 원래 회차로 현재 대상을 계산해요. `mode: explicit`이면 사용자가 직접 연결한 `season_id`·`episode`를 담아요. 미연결은 `null`이며 두 방식을 섞지 않아요. |
| 출처 관찰 정보 | 보관본의 선택적 `anissia_observation`에 `anime_no`·`episode`·`creator`·`website`·`updDt_raw`를 보존해요. 특정 파일과 해당 후보의 관계를 확인하지 못했다면 이 객체로 연결을 확정하지 않아요. |

보관본의 ID가 수정본을 구분하며, `revision_label`은 관찰한 표시에 불과해요.
날짜·파일명·크기로 이전 수정본과의 계보를 추측해 생성하지 않으며, 서로 다른 보관본이 같은 바이트의 자산을 참조할 수 있어요.
의존 자산 목록은 `null`이면 관계 미확인, `[]`이면 분석에서 연결된 자산이 없었다는 뜻이고, 사용자 기기에 필요한 폰트가 없다는 뜻은 아니에요.
같은 작품의 검증된 동일 폰트는 공유 자산으로 재사용하고, 가져오기 계획에서도 새 보관본의 ID 발급과 기존 공유 자산의 재사용을 구분해 참조를 연결해요.
패키지의 `entries`는 미선택·미지원 파일의 출처도 남기며, 패키지에 포함됐다는 사실로 적용 권한을 만들지 않아요.

`updDt_raw`는 원문을 남겨 기존 `Asia/Seoul` 규칙으로 해석하고, 부재와 해석 실패를 구분해요.
`source_file_date`는 제공된 원문 `raw`, 근거 `origin`, 확인 가능한 시간대 `timezone`을 가진 관찰값이며, 모르는 시간대를 서버 시간대로 보충하지 않아요.
Anissia 후보 갱신일·출처에서 보고한 파일 날짜·앱 수신 시각·현재 파일시스템 시각을 서로 대체하거나 최초 공개일로 단정하지 않아요.
게시물 출처에 쿠키·인증 토큰·만료되는 서명 다운로드 URL을 저장해 내보내지 않아요.

##### 가져오기 검증과 파일 가용성

필수 필드·자료형·열거값·참조 종류·작품 범위와 선택한 항목의 참조 연결을 변경 전에 검증해요.
새 형식의 알 수 없는 필드, 중복 YAML 키, 잘못된 값은 조용히 무시하지 않고 해당 위치를 표시해 반영을 거부해요.
형식 우선순위는 지원하는 `ass`·`srt`·`smi`를 각각 한 번 포함하고, 브라우저 시간·동시 작업 수는 양의 정수이며 구현에서 명시할 지원 상한을 넘어설 수 없어요.
상대 경로는 확인한 작품 폴더 밖으로 나갈 수 없고, 보관 자산은 `.trss-subtitles/` 안에 있어야 해요.
절대 경로·`..`·심볼릭 링크를 통한 이탈을 허용하지 않으며, `original_name`은 표시용 원문이지 파일을 쓸 경로가 아니에요.

구조와 참조가 올바른 보관 정보는 실제 파일이 없어도 복원하되, 파일의 크기와 SHA-256을 대조해 `available`·`missing`·`mismatch`·`unverified`로 현재 가용성을 구분해요.
접근 거부나 검사 실패는 `missing`이나 동일 내용으로 바꾸지 않아요.
이 가용성은 가져온 선언을 신뢰하는 값이 아니라 현재 환경에서 새로 검사한 결과이며, YAML로 이전 환경의 검증 완료 상태를 가져오지 않아요.
파일이 누락되거나 내용이 다르면 관계와 기대 크기·해시는 유지하고, 올바른 파일을 옮긴 뒤 다시 검증할 수 있게 해요.
관계·자료형·경로 자체가 잘못된 입력까지 정상 메타데이터로 받아들이는 예외는 아니에요.
미선택 기록이나 기대 해시를 실제 파일에 맞춰 자동 수정하지 않으며, 사용할 수 없는 자산의 적용을 막아요.
바이트 일치는 파일의 가용성만 확인하므로, 실제 자막 형식·내용 판독과 지원 여부도 확인해야 적용할 수 있어요.
같은 이름·다른 바이트, 다른 이름·보고 날짜로 받은 같은 폰트의 자산 재사용과 출처별 관찰값 보존, 누락 후 올바른 파일 추가, 내용 불일치 후 재검증, 선택하지 않은 참조의 보존을 각각 확인해요.

### 작품과 회차 연결

- Transmission 목록에 없는 기존 영상과 지정 폴더도 trname의 작품·시즌·회차 구조를 기준으로 발견해요.
  신규 trss 영상·기존 trss 영상·독립 지정 폴더를 각각 사용해 웹의 작품 상태와 대상 경로가 실제 파일에 대응하는지 확인해요.
- 로컬 작품·시즌에 대응하는 Anissia 작품 후보를 제안하고 사용자가 최초 한 번 확인해요.
  같은 작품의 다음 회차에서 확인한 연결을 재사용하며, 이름이 비슷하다는 이유만으로 다른 작품·시즌에 확정 연결하지 않아요.
- 작품·시즌을 최초 연결할 때 출처별 회차 대응(Episode Mapping)도 사용자에게 확인받고 기억해요.
  다음 회차부터는 확인한 대응을 재사용해 매번 다시 묻지 않으며, 번호가 같다는 이유만으로 사용자 확인을 대신하지 않아요.
  자막 누적 13화가 영상 `S02E01`인 사례와 일반적인 같은 번호 사례를 각각 확인하고, 대응 후에도 불명확한 파일은 이유를 표시해 보류해요.
  같은 회차의 중복 영상이 발견돼도 임의의 대상에 배치하지 않으며, 그 선택 UI의 세부 동작은 아직 정하지 않았어요.
- 회차 대응을 수정하면 해당 대응에 연결된 기존 보관본과 미완료 작업을 새 기준으로 재평가해요.
  원래 출처 회차와 실제 적용했던 경로의 기록을 새 대응으로 덮어쓰지 않으며, 원래 회차 정보가 불명확하면 추측하지 않고 보류해요.
  대상이 달라진 배치 계획은 다시 확인받고, 이전 교체 승인을 재사용하지 않아요.
  이미 적용한 파일은 그대로 두며, 대응 설정을 바꾸는 것만으로 파일을 옮기거나 복사·삭제하지 않아요.

### 후보 탐색과 선택

- 화면이 닫혀 있어도 2시간마다 누락·수정 후보를 조회해 모아두며, 다시 접속하면 결과를 확인할 수 있어요.
  이 주기는 기존 영상 RSS 처리 주기를 변경하지 않고, 후보 발견만으로 다운로드나 교체를 승인하지 않아요.
- 반복 자동 조회의 나이 기준은 Anissia 후보의 `updDt`이며, 표시된 후보 갱신일부터 30일 이내인 대상을 조회해요.
  [Anissia 공식 API 문서](https://github.com/anissia-net/anissia/blob/master/docs/anime_schdule.md)에 따라 시간대 없는 `YYYY-MM-DD HH:mm:ss`는 `Asia/Seoul`로 해석하고, 서버 로컬 시간대와 무관하게 같은 시점으로 비교해요.
  후보나 갱신 날짜가 없거나 날짜를 해석할 수 없으면 해당 회차 영상을 앱에서 처음 발견한 시각을 사용하고, 날짜 해석 실패는 구분해 표시해요.
  같은 시점이 서버의 시간대 설정에 따라 달라지지 않는지, 경과 시간이 정확히 30일인 경우와 그 직후, 후보·날짜 부재·잘못된 날짜를 제어된 시각으로 확인해요.
  30일 이내는 경계값을 포함하며, 기간이 지나도 기존 후보 기록과 받은 파일이 남아 있어야 해요.
- 최초 검색과 사용자 요청 새로고침은 위 기간 제한을 적용하지 않아요.
  오래된 영상에서도 직접 조회할 수 있어야 하며, 자동 조회 중단 후의 새 자막·수정을 놓칠 수 있음을 안내해요.
  `updDt`를 자막 최초 공개일·회차 방영일·파일 변경의 확정 증거로 표시하지 않아요.
- 한 작품의 자막 후보는 제작자·출처별로 묶어 보여줘요.
  제작자와 회차 범위로 후보를 묶어 선택하고 개별 항목을 조정할 수 있어요.
  누락 회차와 이미 자막이 있는 회차의 수정 후보를 구분하고, 선택하지 않은 후보까지 다운로드·적용하지 않아요.

### 출처별 다운로드

모든 아래 경로가 첫 지원 범위예요.
한 경로의 성공으로 다른 출처의 완료를 대신하지 않으며, 파일 수신뿐 아니라 실제 trss 작업에서 분석·보관·영상 연결·적용까지 이어지는지 각각 확인해요.
하나의 범용 링크 추출만으로 처리된다고 가정하지 않아요.

| 필수 경로 | 해당 경로의 관찰 조건 |
| --- | --- |
| erulabo | 서버가 정상 다운로드를 시작하고 사용자가 필요한 CAPTCHA를 해결한 뒤 같은 서버 브라우저가 파일을 수신해요. 만료·오류 HTML을 자막으로 보관·적용하지 않아요. |
| Blogger·Google Drive 개별 자막 | 게시물에서 연결된 개별 파일을 수신하고 실제 자막 형식과 회차를 확인해 적용해요. |
| Blogger·Google Drive 회차 ZIP | 여러 회차를 복원하고 사용자가 선택한 범위만 적용해요. 개별 파일 수신 성공만으로 묶음 처리를 완료로 보지 않아요. |
| Tistory 일반 첨부 | 일반 첨부에서 파일을 수신하고 압축 내부 자막을 처리해요. 실제 구현에 필요한 URL 취득·재취득 경로를 확인해요. |
| Tistory WinPNG | 이미지에서 실제 자막 바이트를 복원하고 개별 회차 파일 수신·적용으로 이어져요. PNG 다운로드나 뷰어 표시만으로 성공으로 보지 않아요. |
| Naver 블로그 첨부 | 게시물에서 유효한 첨부 경로를 얻어 실제 파일을 수신해요. 이전 HTTP 표본의 성공으로 구현한 브라우저 경로까지 검증됐다고 표시하지 않아요. |

출처가 요구하지 않는 CAPTCHA·로그인을 추가하지 않아요.
실제 다운로드 과정의 사용자 조작은 필요한 인증에 한정하며, 후보 선택·연결 확인·교체 승인은 별개의 의도적인 입력으로 유지해요.
과거 수신 결과와 미검증 경로는 [출처 조사 기록](../brainstorm/web-gui-subtitles.md#공개-자막-경로-조사) 및 [erulabo 기록](../brainstorm/web-gui-subtitles.md#주요-출처-erulabo의-보안-확인)을 근거로 삼아요.

### 작업 화면 안의 인증과 브라우저 수명

- 인증이 필요한 작업은 서버 소유 Chromium을 직접 실행하고 CDP로 제어해요.
  서버가 게시물 열기와 정상 다운로드 시작을 처리하고, trss의 해당 작업 화면에 원격 화면·마우스·키보드 입력을 제공해요.
  별도 주소·창으로 이동하거나 외부 사이트를 iframe으로 넣는 방식으로 요구를 대체하지 않아요.
- Chromium은 앱과 분리한 비공개 컨테이너에 배치해 의존성과 자원 한도를 분리해요.
  작업 실행 측의 시작·종료 제어와 서버 수신 파일 전달을 통합하고, 별도 컨테이너에서도 아래 인증·유휴 종료·프로필 폐기 조건을 확인해야 해요.
- 실제 웹 화면에서 후보 선택 → 인증 대기 → 직접 CAPTCHA 해결 → 서버 파일 수신을 이어서 관찰해요.
  수동 파일 다운로드·업로드·이동이나 CAPTCHA 자동 우회를 개입시키지 않고, 받은 파일의 형식·무결성과 해당 작업의 결과를 확인해야 해요.
- 원격 화면을 제공하는 페이지와 화면·입력 WebSocket 모두 같은 접근 보호를 받아요.
  원본 VNC·CDP 포트를 별도로 노출하지 않으며, HTTPS 배포에서는 WSS 연결과 앞단 프록시의 연결 전달·접근 차단을 실제 배포 경로에서 확인해요.
  외부 페이지에서 보낸 허용되지 않은 상태 변경·원격 입력 연결과 보호 계층을 우회한 직접 접속도 거부되는지 확인해요.
  원격 입력은 해당 작업과 브라우저 실행에 묶고, 끝난 실행의 연결이 다음 작업을 조작하지 못하게 해요.
- 브라우저가 작업을 실행 중이지 않고 사용자 조작도 없는 유휴 시간의 초기 설계 기본값은 5분이며, 만료하면 브라우저를 종료하되 인증 대기 작업은 남겨요.
  이후 해당 작업을 열면 페이지와 필요한 인증 화면을 자동으로 다시 준비하고, 이미 받은 파일과 작업 기록도 유지해요.
  유휴 종료가 실행 중 다운로드를 끊지 않는 경우와, 인증 대기 중 종료 후 재개하는 경우를 구분해 확인해요.
- 실행마다 새 전용 프로필을 쓰고 종료 시 쿠키·사이트 저장 상태를 버려요.
  작업 기록과 받은 파일은 프로필과 별도로 보존하고, 쿠키·토큰·서명 다운로드 URL을 설정 내보내기나 일반 로그에 노출하지 않아요.
  프로필 폐기 후에도 작업과 받은 자막이 남고 다음 실행에 이전 사이트 상태가 재사용되지 않는지 확인해요.
- 동시 브라우저 작업 수의 초기 설계 기본값은 1개이며, 유휴 시간과 동시 작업 수는 운영 설정으로 조정할 수 있게 해요.
  이는 실측 성능값이 아닌 보수적인 시작값이에요.
  동시성을 높인 설정에서는 작업별 화면·입력·프로필·수신 파일이 섞이지 않고 설정한 상한이 지켜지는지 확인해요.
  CPU·메모리와 압축 해제의 총량·파일 수·중첩 깊이·실행 시간 한도는 대표 정상 묶음과 과다 입력을 측정해 구현 시 유한한 값으로 정해요.
  한도 도달은 성공이나 동일 파일 판정과 구분해 표시하고, 이미 보관한 파일·승인 대기·인증 대기를 잃지 않아야 해요.

### 자막 묶음 분석과 안전한 배치 판단

자막 묶음(Subtitle Package)을 파일 하나·회차 하나로 취급하지 않고, 실제 구성과 회차 대응을 바탕으로 배치 계획(Placement Plan)을 만들어요.
Anissia의 한국어 자막을 대상으로 하고, 별도의 다국어 선호·언어 우선순위 설정은 제공하지 않아요.
자동 분석·적용 대상은 ASS·SRT·SMI이며, SSA·WebVTT·이미지 자막 등 다른 형식은 안전하게 보관·분류하되 미지원 상태를 표시하고 자동 적용하지 않아요.
정상적으로 판별되는 작업에 불필요한 확인 단계를 추가하지 않으며, 아래 사례를 별도로 관찰해요.
추가 형식·암호·중첩 구조를 다룬다는 것은 모두 자동 복원할 수 있다고 약속하는 뜻이 아니에요.

| 입력 사례 | 필요한 결과와 안전 경계 |
| --- | --- |
| 여러 회차·하위 폴더 | 각 자막을 대상 회차에 연결하고 선택 범위만 적용해요. 회차 불명은 보류해요. |
| ASS·SRT·SMI 복수 형식 | 형식을 보존하고 정한 우선순위로 최초 적용본을 정해요. 확장자 변경을 형식 변환으로 취급하지 않아요. |
| 같은 회차·확장자의 여러 파일 | 제작자·전체 대사와 간판 전용·TV와 BD·수정본 차이를 구분하며, 대상이 불명확하면 임의 선택하지 않고 보류해요. |
| 한 파일의 여러 언어·IDX와 SUB 같은 구성 파일 | 파일 하나가 언어 하나라고 단정하지 않고, 미지원 구성 파일을 각각 독립 자막으로 적용하지 않아요. 확인 가능한 구성 요소의 누락도 표시해요. 이 안전한 식별 요구가 다국어 설정이나 이미지 자막 자동 적용 지원을 뜻하지는 않아요. |
| 폰트·설명·라이선스 파일 | 자막의 보조 자산으로 식별·보관하며 자막 파일로 적용하지 않아요. |
| 중복과 이름 충돌 | 바이트가 같은 파일과 이름만 같고 내용은 다른 파일을 구분하고, 대상 경로 충돌을 변경 전에 표시해요. |
| 인코딩 차이·잘못된 확장자·손상 | 확인 가능한 실제 형식·인코딩을 사용하고, 판별·비교 실패를 동일 내용이나 정상 적용으로 표시하지 않아요. |
| 중첩 압축·암호·알 수 없는 첨부 | 지원 여부·추가 입력 필요·분석 실패를 구분해요. 오류 HTML을 자막으로 적용하지 않아요. |
| 경로 이탈·링크·과도한 압축 해제 | 작업 경계 밖의 파일을 만들거나 덮어쓰지 않고, 압축 해제 자원을 유한하게 제한해요. 거부 후 경계 밖 파일과 기존 정상 파일이 보존되는지 확인해요. |

### 보관본과 복사한 적용본

- 보관본(Stored Subtitle)은 작품 폴더의 `.trss-subtitles/` 안에서 사람이 구분할 수 있게 배치해요.
  자막은 `subtitles/제작자/시즌·회차/수정본/원래파일명`, 공유 폰트는 `fonts/원래폰트명-식별자.확장자`, 설명·라이선스 등은 `attachments/묶음별/` 형태로 분류해요.
  이름 충돌과 파일시스템 제약에 필요한 안전한 표기·식별자를 보완하되, 원래 파일명과 관계는 SQLite에 보존해요.
  같은 표기·다른 내용의 파일을 덮어쓰지 않고, 사람이 읽는 경로를 보관 정보의 별도 권위로 사용하지 않아요.
  동일 폰트를 수정본 폴더마다 복제하지 않으며, 경로를 변경하는 경우 DB와 이후 내보내는 정보의 파일 참조를 실제 경로에 맞춰 갱신해요.
- 적용본(Applied Subtitle)은 선택한 보관본을 영상 옆에 같은 파일명 줄기로 복사한 독립된 파일이에요.
  이동·하드 링크·심볼릭 링크를 사용하지 않으며, 적용본 수정·교체·삭제 후에도 보관본의 내용과 재적용 가능성이 유지되는지 실제 파일로 확인해요.
- 최초 적용은 선택한 제작자·회차의 한국어 자막에서 우선 형식 하나예요.
  같은 회차·형식에 용도·릴리스 등이 다른 여러 대안이 있어 구분이 안 되면 기존 보류·선택 원칙을 적용하며, 모든 정상 작업에 별도 언어 선택을 요구하지 않아요.
  전역 기본 ASS → SRT → SMI와 작품별 재정의를 각각 확인하고, 같은 제작자의 다른 형식은 사용자가 선택하면 추가 적용해요.
  추가 적용은 기존 적용본을 자동 제거하지 않아요.
- 웹에서 다른 제작자·형식·이전 수정본을 비교·선택할 수 있고, 이전 수정본 복원도 해당 보관본을 다시 복사해요.
  이전 보관본은 사용자가 정리하기 전까지 유지하고, 복사 실패를 적용 완료로 표시하거나 기존 정상 적용본·보관본을 잃지 않아요.
- 적용 위치와 보관 위치를 구분해 보여주고, 적용됐다는 사실을 재생기가 그 트랙을 실제로 선택했다는 뜻으로 표시하지 않아요.
  숨김 폴더명 역시 접근 권한 보호로 안내하지 않아요.

### 폰트 재사용과 전송

- 작품의 보관 영역에서 내용이 같은 폰트는 한 번만 저장하고 여러 보관본이 함께 참조해요.
  같은 이름·다른 내용의 폰트는 구분하고, 한 수정본 정리 후에도 다른 보관본이 참조하는 폰트가 남아 사용 가능한지 확인해요.
- 출처가 파일별 수신과 검증 가능한 변경 정보를 제공하면 기존 폰트를 재사용하고 추가·변경 파일만 받아요.
  기존 폰트와 새 폰트가 함께 있는 갱신 사례에서 실제 전송된 파일과 보관 결과를 각각 관찰하며, 파일명만으로 변경 없음을 판단하지 않아요.
- 개별 파일을 받을 수 있지만 변경 여부를 사전에 확인할 신뢰할 만한 정보가 없으면 필요한 해당 파일만 받아 내용으로 비교해요.
  동일하면 기존 자산을 재사용하고, 갱신된 내용이면 별도 자산으로 보관하며, 확인 목적의 재수신을 표시해요.
  이 조건만으로 추가 사용자 확인을 요구하지 않으며, 이미 동일함을 확인한 다른 폰트까지 다시 받지 않아요.
- 통째 묶음으로만 수신할 수 있는 출처는 전체 다운로드를 예외로 허용해요.
  수신 후 동일 폰트는 기존 자산을 재사용하고, 화면에는 전체 묶음 수신과 실제 신규 자산 추가를 구분해 보여줘요.
  로컬 중복 제거만 확인하고 네트워크 재수신도 방지했다고 보고하지 않아요.
- 폰트 보관과 실제 재생기의 사용을 구분해요.
  자막 묶음에 폰트가 없다는 이유만으로 사용자 기기에 필요한 폰트가 없다고 판정하지 않아요.

### 교체 비교와 승인

기존 파일을 바꾸기 전에 아래 정보를 기존·새 파일에 대해 나란히 보여줘요.
지원하는 형식의 파싱 결과로만 내용 차이를 설명하고, 비교 불가를 차이 없음으로 표시하지 않아요.
처음에는 대상·실제 변경 경로·판단 한계와 기존·새 파일의 요약을 보여주고, 내용·시간·스타일의 상세 차이는 펼쳐서 확인하게 해요.
비교 불가·경고나 실제 변경 경로를 접힌 상세 안에만 숨기지 않아요.

| 비교 정보 | 관찰할 내용 |
| --- | --- |
| 대상·연결 근거 | 작품·시즌·회차, 영상 경로, 원본 자막 이름, 적용한 회차 대응, 불명확한 연결의 이유예요. |
| 출처·이력 | 확인된 제작자·게시물, Anissia 갱신일, 앱 수신 시각을 구분해요. 기존 비관리 파일의 출처를 모르면 미상으로 표시해요. |
| 파일 특성 | 형식·크기·확인 가능한 인코딩·언어·용도와 바이트 동일 여부예요. |
| 내용·시간·스타일 | 파싱 가능한 대사 추가·삭제·변경, 타임코드 차이, 스타일·폰트 변화를 구분해요. 이미지 자막이나 읽지 못한 형식은 내용 비교 불가로 표시해요. |
| 의존 파일 | 신규·변경·재사용 폰트, 필요한 구성 파일과 누락·충돌, 실제 재생 환경의 폰트 활용 미확인 여부예요. |
| 실제 변경 | 유지·추가·교체·제거할 정확한 경로와 보관본·적용본의 구분이에요. |
| 판단 한계 | 출처 미상, 분석 불가, 릴리스 불일치 가능성 등을 표시해요. 최신 날짜·큰 크기·많은 대사만으로 품질이나 싱크가 더 좋다고 판정하지 않아요. |

여러 교체 후보를 모아 보여주고 사용자가 승인한 항목만 반영해요.
제작자·형식 변경으로 이전 적용 파일을 제거해야 하면 그 경로도 승인에 포함하고, 관계없는 파일은 추측해서 정리하지 않아요.
적용 파일 제거가 보관본 삭제로 이어지지 않아야 해요.

승인은 비교한 기존·새 파일과 대상·변경 내용에 연결해요.
승인 후 반영 전 기존·새 자막의 내용, 아래 기준의 영상 식별 정보, 대상 경로 또는 변경 계획이 바뀐 사례에서 이전 승인을 재사용하지 않고 다시 비교·확인을 요구하는지 확인해요.
승인하지 않은 파일의 내용과 존재 여부가 그대로 유지되는지도 관찰해요.

#### 승인 증거와 반영 직전 검사

승인 기록은 변경할 수 없는 `plan_id`·계획 버전, 작품·시즌·회차와 대응 근거, 영상 식별 정보, 기존 파일의 존재 여부·경로·크기·SHA-256, 새 보관 자산의 ID·경로·크기·SHA-256, 추가·교체·제거할 경로와 동작에 연결해요.
승인 후 계획을 수정하면 새 계획으로 취급하며, 작업 ID에 붙인 포괄적인 승인 표시만으로 실행하지 않아요.
최초 적용의 후보 선택·연결 확인과 기존 파일 교체 승인은 구분하고, 영상 대기 후 충돌 없이 처음 적용할 수 있는 기존 계약은 유지해요.

대상 영상은 경로, 일반 파일 여부, 사용할 수 있는 파일 객체 식별자, 크기와 변경 시각으로 확인하고 전체 영상 해시는 계산하지 않아요.
영상 전체를 반복해서 읽는 비용을 피하는 선택이며, 같은 식별 정보 뒤에 숨은 바이트 변경까지 탐지한다고 보장하지 않아요.
필요한 식별 정보를 신뢰할 수 없거나 읽는 도중 달라지면 확인 불가로 보류해요.
기존·새 자막과 사용되는 보관 자산은 실제 바이트를 다시 검증하므로, 파일 크기나 수정 시각만 같은 다른 내용을 승인된 자막으로 취급하지 않아요.

최종 검사·공개 경로 반영·제거 중에는 같은 영상·자막을 비협조적인 외부 프로그램이 동시에 수정하지 않는 운영 조건을 둬요.
앱 내부에서 겹치는 경로의 반영, 관련 회차 대응 변경과 자산 정리는 해당 효과가 반영되는 구간에 직렬화하고, 발견한 외부 변경은 보류해요.
파일 해시나 앱의 잠금이 임의의 외부 쓰기까지 강제로 차단한다는 뜻은 아니며, 검사 후 `rename`·삭제 사이의 경쟁을 모든 파일시스템에서 원자적으로 해결한다고 안내하지 않아요.
이 조건을 지킬 수 없는 상태에서는 파괴적인 반영을 진행하지 않고, 확인 가능한 상태에서 새 계획으로 다시 비교해요.
긴 다운로드·해시 계산 중에는 SQLite 쓰기 트랜잭션을 잡아두지 않으며, 관련 설정의 최종 확인과 실제 효과 사이에 앱 내부 변경이 끼어들지 않게 조율해요.

영상 식별 정보 변경, 같은 크기·다른 바이트의 기존 자막, 새 보관 자산의 외부 변경, 승인 후 회차 대응 수정, 추가 예정 경로에 생긴 파일을 각각 검사해 보류·재확인과 기존 파일 보존을 확인해요.
앱의 두 작업이 같은 경로를 동시에 바꾸려는 경우도 관찰하며, 운영 조건 밖의 외부 쓰기와 영상 메타데이터만으로 보이지 않는 변경을 탐지한 결과로 과장하지 않아요.

### 영상 대기와 작업 결과

- 영상이 없어도 선택한 자막을 먼저 받아 영상 대기(Awaiting Video)로 보관해요.
  연결된 폴더에 영상이 준비되면 자막 재선택·재다운로드 없이 적용하며, 그때 기존 자막이 생겼으면 교체 승인으로 이어져요.
  다운로드 중이라고 확인된 영상은 아직 배치 가능한 대상으로 취급하지 않고 준비될 때까지 기다려요.
- 영상 대기는 인증 대기와 구분하고, 영상이 생기거나 사용자가 정리하기 전까지 받은 파일을 자동 삭제하지 않아요.
  브라우저 종료와 후보 자동 조회 기간 종료 후에도 대기 작업·파일이 남아 있어야 해요.
- 불명확한 연결, 미지원·손상 묶음, 수신 실패, 적용 실패를 성공으로 표시하지 않아요.
  일괄 작업은 회차·파일별 실제 결과와 남은 이유를 확인할 수 있어야 하고, 재개가 이미 받은 정상 파일의 수동 재업로드를 요구하지 않아요.
- worker 재시작 후에는 기록과 실제 파일을 대조해 확인 가능한 지점부터 미완료 작업을 자동 재개해요.
  수신·보관 완료가 확인된 파일은 재사용하고, 인증·승인이 필요한 단계는 기다리며, 파일 반영 여부가 불명확하거나 승인 대상이 달라졌으면 보류해요.
  수신 후 중단, 복사 반영 전후 중단, 승인 대상의 외부 변경을 각각 발생시켜 중복 수신·무승인 변경·허위 완료 없이 재개 또는 보류되는지 확인해요.
  다른 환경으로 설정·보관 정보를 가져오는 동작에 이 자동 재개 정책을 적용하지 않아요.

#### 체크포인트와 중단 복구

복구 정보는 SQLite의 작업·항목·파일 동작 기록에 남기며, 별도 범용 워크플로 엔진이나 작품별 복원 목록을 도입하지 않아요.
선택한 후보와 출처, 수신 시도 ID와 전용 임시 경로, 검증된 수신물·자산 참조, 불변 계획과 승인 참조, 각 파일 동작의 ID·의도·전후 조건·완료 증거를 구분해 저장해요.
다운로드 완료와 정상 자막 판정은 별개이며, 파일 효과를 시작하기 전에 그 의도를 커밋하고 실제 결과를 확인한 뒤 완료를 기록해요.
임시 영역은 보관 자산과 구분하고, 작업의 임시 파일이나 보호 복사본을 YAML 자산으로 가져오는 경로를 허용하지 않아요.

| 인증 대기·수신 중 | 선택과 인증 대기를 유지해요. 완료 기록이 있는 수신물은 바이트를 확인해 재사용하고, 완료 여부가 불명확하면 보류해요. |
| 바이트 수신 후 완료 기록 전 | 신뢰할 수 있는 예상 길이·내용 식별 정보나 독립적인 완료 증거가 있어야 완료로 인정해요. 현재 길이·로컬 해시·파싱 가능 여부만으로 수신 완료를 만들어내거나 곧바로 다시 받지 않아요. |
| 분석·압축 해제 중 | 검증된 원 수신물에서 필요한 분석만 다시 수행해요. 이미 받은 묶음을 다시 다운로드하지 않으며, 정상 추출물·미지원 항목·실패를 구분해요. |
| 보관 준비 후 등록 전 | 새 자산의 예상 경로와 바이트, 재사용 자산의 참조를 기록하고 검증해요. 새 목적지가 이미 다른 파일로 차 있으면 덮어쓰지 않아요. 공개된 파일과 기록의 관계가 불명확하면 예약과 증거를 남겨 보류해요. |
| 보관 완료·영상 대기·승인 대기 | 검증한 보관본과 공유 자산 참조를 유지하고 필요한 조건만 기다려요. 브라우저나 worker의 수명이 이 자료를 삭제하지 않아요. |
| 적용 준비 후 공개 경로 변경 전 | 보관본과 별개인 임시 복사본의 바이트를 검증하고 준비된 파일의 객체 식별 증거를 기록해요. 계획·대응·승인·기존 상태가 여전히 유효하고 효과가 아직 실행되지 않았음이 확인되면 이어가요. |
| 공개 경로 변경 후 완료 기록 전 | 기록한 임시 파일의 객체와 최종 파일의 연결, 바이트·경로·계획이 일치하는 등 해당 동작의 결과임을 확인할 수 있어야 완료로 대조해요. 이름이나 원하는 바이트가 있다는 이유만으로 앱이 반영했다고 기록하지 않아요. |
| 여러 경로 중 일부만 반영 | 확인된 완료 효과는 유지하고 항목·경로별 결과를 보여줘요. 새 파일의 정상 반영을 확인한 뒤 승인된 이전 경로를 제거하며, 제거 실패를 전체 성공이나 자동 전체 롤백으로 처리하지 않아요. |
| 제거 후 완료 기록 전 | 파일이 없다는 사실만으로 이 작업이 제거했다고 단정하지 않아요. 행위의 결과를 확인할 수 없으면 보호 자료를 유지하고 보류해요. |

기존 자막을 교체·제거하기 전에는 승인한 기존 바이트의 독립적인 임시 보호 복사본을 준비해요.
공간 부족이나 복사·검증 실패는 파괴적인 효과 전에 중단하고, 실패·불명확한 부분 완료가 남으면 보호 복사본도 남겨요.
임시 보호 자료는 해당 작업이 확인된 완료 상태에 이르거나 사용자가 불명확한 결과의 정리를 명시한 뒤 정리하며, 외부에서 바뀐 공개 경로 위로 자동 복원하지 않아요.
임시 복사본을 최종 경로에 공개하는 내부 이름 변경은 보관 원본을 이동해 적용하는 방식이 아니며, 보관 원본은 독립적으로 남아야 해요.
새 경로 추가에는 지원되는 덮어쓰기 금지 방식을 사용하고, 사전 존재 검사 뒤 일반 덮어쓰기로 이어지는 방식을 동등한 보호로 취급하지 않아요.

복구를 맡는 worker는 같은 호스트의 이전 파일 쓰기 주체가 더 이상 실행할 수 없다는 배타성을 확보해야 해요.
DB 임대 시각이 지났다는 이유만으로 멈춰 있던 이전 worker와 새 worker를 동시에 파일 쓰기 주체로 두지 않아요.
독립적인 회차·파일은 각각 진행할 수 있지만, 겹치는 목적지·제거 경로와 공유 자산의 정리는 직렬화해요.
공유 폰트 정리는 남은 보관본뿐 아니라 진행 중·보류·복구 작업의 참조도 보호하고, 참조가 없는지 확인한 뒤 삭제하는 사이에 새 참조가 생기는 경쟁도 막아야 해요.
불명확한 임시 파일이나 미등록 파일을 이름만 보고 쓰레기로 지우지 않아요.

회차 대응 변경과 한 파일 효과가 겹치면 먼저 확정된 쪽을 기준으로 처리해요.
대응 변경이 먼저이면 반영 전에 계획을 다시 확인하고, 파일 효과가 먼저이면 실제 완료 경로는 유지한 채 남은 작업을 재평가해요.
효과 자체가 불명확한 중단 상태는 먼저 실제 파일과 대조하며, 새 대응이 그 불명확한 파일의 이동·삭제 권한을 주지는 않아요.
인증·영상 대기처럼 오래 멈춘 작업 전체 기간에 대응 설정을 잠가두지 않아요.

위 각 파일 효과 전후와 DB 완료 기록 전후에 중단한 사례를 구분해 검증해요.
공개 후 기록 전의 재시작, 불명확한 제거, 보호 복사 공간 부족, 새 경로의 외부 점유, 멈춘 이전 worker, 공유 폰트 참조 생성과 정리의 경쟁을 관찰해 중복 효과·무승인 변경·허위 완료와 자료 손실을 막는지 확인해요.
실제 파일시스템의 공개·동기화·객체 식별 동작은 구현 환경에서 검증해야 하며, 이 절차를 정한 것만으로 프로세스 중단이나 저장장치 장애의 내구성을 입증한 것은 아니에요.

### 실제 재생 환경

주 재생 환경은 Infuse·IINA·팟플레이어이며, Infuse는 SMB·NFS·WebDAV 계열 폴더 공유를 이용해요.
특정 Apple 기기에 한정하지 않는 호환은 사용자의 희망이며, 지원 기기·버전·공유 방식 전 조합이 검증됐다는 뜻은 아니에요.

각 실제 시험에서 재생기·버전·기기·공유 경로·자막 검색 설정을 기록하고, 영상과 동일 이름의 적용본 인식, 숨김 보관본의 검색 제외 여부, 추가 형식의 선택 동작, 필요한 폰트의 실제 렌더링을 구분해 관찰해요.
파일 존재나 폰트 다운로드 성공만으로 재생·스타일 재현 성공을 판정하지 않아요.
검증하지 않은 조합과 재생기 제약은 명시하고, 서버 전역 폰트 설치·원본 재먹스·손실 변환을 임의로 추가해 제약을 숨기지 않아요.
`.default`나 `.forced` 파일명으로 모든 재생기의 기본 선택을 통제한다는 계약은 두지 않아요.

폰트 확인에는 기본 글꼴과 구별되는 서체를 요구하는 자막·폰트 표본을 쓰고, 해당 폰트의 사용 가능 여부를 바꾼 대조나 재생기의 실제 글꼴 선택 정보로 대체 글꼴과 구분해요.
파일 교체 후에는 재생기의 자막 다시 읽기나 영상 다시 열기를 거쳐 현재 적용본을 확인하며, 이미 재생 중인 앱의 캐시까지 즉시 갱신된다고 가정하지 않아요.

## 구현 경계와 실행 순서

[현재 코드와 제약](../brainstorm/web-gui-subtitles.md#현재-제품의-근거와-한계)을 출발점으로 삼고, 기존 RSS·규칙·Transmission·trname 동작을 재사용해요.
웹 화면 추가만으로 기존 미완성 Anissia 경로가 완성되거나 `regex: true`가 동작한다고 가정하지 않아요.

[웹 기술 ADR](../adr/0004-rust-react-web-stack.md)에 따라 기존 Rust·Tokio를 유지하고 axum 서버와 React·TypeScript·shadcn/ui 화면을 사용해요.
shadcn/ui를 사용해도 작은 화면의 기능 범위나 웹 명령·선택·승인 계약은 축소하지 않아요.
프런트엔드의 정적 빌드 결과는 Rust 서버가 제공하며, 운영용 Node 서버 없이 실제 배포 이미지에서 화면·작업 API·원격 인증 연결을 사용할 수 있어야 해요.
실행 구성은 [웹·작업 바이너리 분리 ADR](../adr/0006-separate-web-worker-binaries.md)에 따라 공통 Rust 라이브러리와 `trss-web`·`trss-worker` 두 바이너리로 나눠요.
두 바이너리는 같은 앱 이미지에 포함하고, 같은 호스트의 별도 컨테이너에서 같은 릴리스 버전으로 운용해요.

[저장소 ADR](../adr/0005-local-sqlite-app-state.md)에 따라 앱 설정·작품 연결·회차 대응·작업·승인·보관 이력은 로컬 SQLite에 저장해요.
DB는 앱 호스트의 로컬 영속 볼륨에 두고, 영상·자막·폰트 파일 및 임시 브라우저 프로필과 구분해요.
컨테이너 재생성 후에도 저장한 상태를 읽을 수 있어야 하며, SQLite DB를 SMB·NFS 공유 경로에 배치하지 않아요.
웹과 단일 worker 프로세스가 이 DB를 공유하며, 별도 Redis나 분산 작업 시스템을 도입하는 구성은 아니에요.

현재 [cron](../../scripts/cron.sh)은 5분마다 `docker compose run --rm`으로 실행하고, [주 실행 파일](../../src/main.rs)은 한 번의 RSS 처리를 마치면 종료해요.
[trss Compose](../../docker-compose.trss.yml)는 웹 포트·미디어 볼륨이 없고 CPU 0.1·메모리 96M 제한의 종료형 컨테이너예요.
이를 웹·서버 브라우저까지 수용하는 구성으로 그대로 사용할 수 있다고 가정하지 않아요.
새 배포 구성에서 Transmission의 미디어 경로와 앱이 읽고 쓰는 경로의 대응, 감시 폴더 마운트, 실행 사용자 권한을 확인하고 실제 보관·복사 적용을 수행해야 해요.
시험용 작품에 보관·복사·승인한 교체를 수행해 Transmission에서 보이는 경로와 앱의 실제 파일이 대응하는지 확인하고, 읽기 전용·권한 거부·마운트 누락에서는 기존 파일을 보존하며 실패를 표시해야 해요.
기존 5분 RSS 처리와 2시간 자막 후보 조회의 실행 주체는 worker로 이관하고, 운영 안내에 기존 cron 해제와 새 실행·중지 절차를 명시해요.
이 검증은 실제 네트워크의 접근 보호를 대신하지 않아요.

설정·작품 연결·회차 대응·자막 정책과 작업·보관 이력은 브라우저 프로필과 수명을 분리해야 해요.
실제 파일 상태, 수신한 출처 정보, 적용 계획과 승인 대상을 구분해 기록하고, 화면의 상태가 파일 변경의 성공을 앞서 선언하지 않게 해요.
웹은 화면·API·설정·사용자 요청을, worker는 정기 조회·다운로드·브라우저 수명·파일 반영을 담당해요.
웹 요청과 worker의 작업 인계를 기록으로 연결하고, worker를 중복 기동해도 같은 작업·정기 처리가 중복 수행되지 않아야 해요.
단일 worker는 프로세스 수의 결정이며 내부 작업 동시성은 별도로 제한해요.
웹만 재시작하는 동안 진행 중 worker 작업을 유지하고, 웹 복귀 후 같은 작업과 유효한 원격 인증 화면에 다시 연결되는지 확인해요.
이때 다운로드 재실행이나 승인 자동 부여가 발생하지 않고, 브라우저의 기존 유휴 종료 정책도 유지돼야 해요.
worker 재시작은 위 작업 복구 계약을 따르며, 복구 판정의 구현은 아래 모듈 책임에 맞춰 구체화해요.

### 공통 라이브러리의 모듈 구성

공통 Rust 라이브러리는 기능별 모듈로 구성하고, 각 기능의 판정·저장 코드와 그 계약을 검증하는 코드를 가까이 둬요.
다음은 책임 구분이며, 모든 행이 별도 Cargo 패키지나 프로세스가 된다는 뜻은 아니에요.

| 모듈 | 책임 |
| --- | --- |
| 앱 설정 | 전역 자막·브라우저 정책의 읽기·검증·저장을 담당하며, 배포 환경 값과 분리해요. |
| RSS | 채널·규칙의 저장과 순서, 피드 수집·판정, 미리보기와 실제 처리에서 공유하는 규칙 평가를 담당해요. |
| 작품·보관 | 작품·시즌·회차 대응, 보관본·자산 관계와 경로·내용 식별, 파일의 안전한 보관·독립 복사를 담당해요. |
| 자막 | 후보·출처별 수신·묶음 분석·비교·배치 계획을 담당하며, 작품·보관 모듈의 인터페이스로 대상과 자산을 다뤄요. |
| 작업 관리 | 요청·작업 상태·승인 근거·재개 지점의 영속화와 중복 실행 방지를 담당해요. 출처별 다운로드 방법은 소유하지 않아요. |
| 설정 교환 | 기능 모듈의 인터페이스를 조합해 YAML 내보내기·검증·선택 가져오기 계획과 반영을 담당해요. 이전 작업 실행 권한을 가져오는 경로는 두지 않아요. |
| 공통 기반·외부 연동 | DB 접속·트랜잭션·마이그레이션 등 실제 공통 기능을 제공해요. Transmission이나 브라우저처럼 여러 기능이 사용하는 연동만 공유하고, 특정 자막 출처에만 필요한 코드는 자막 모듈에 둬요. |
| 웹·worker 진입부 | 웹은 화면·요청을 기능 인터페이스에 연결하고, worker는 기록된 작업과 정기 처리를 실행·복구해요. 규칙 평가나 파일 비교 로직을 각각 다시 구현하지 않아요. |

의존 방향은 웹·worker에서 기능 모듈로, 기능 모듈에서 필요한 공통 기반·외부 연동으로 향해요.
기능 모듈이 웹 라우터나 worker의 실행 루프를 역으로 참조하지 않으며, 다른 기능의 테이블을 직접 갱신해 그 기능의 검증을 우회하지 않아요.
여러 기능의 상태를 함께 반영해야 하면 설정 교환이나 작업 실행 측에서 하나의 트랜잭션 범위를 조율하고, 개별 저장 메서드가 먼저 독립 커밋해 일부만 반영되지 않게 해요.
파일 변경과 DB 기록이 하나의 원자적 트랜잭션이라고 가정하지 않으며, 작업 기록과 실제 파일의 대조를 통한 복구 요구를 유지해요.

파일 반영은 worker의 실행 경로에서만 수행해요.
배치 계획·승인 근거·현재 파일을 반영 직전에 함께 확인하는 책임을 웹의 사전 검사로 대체하지 않으며, 명세의 승인 무효화·복사 실패·중단 복구 사례를 이 실행 경로에서 검증해요.
미리보기와 실제 규칙 처리도 같은 RSS 모듈의 인터페이스를 사용해 결과 차이를 막아요.
기능의 데이터가 저장된다는 이유만으로 범용 저장소 인터페이스를 추가하지 않고, 실제로 서로 다른 외부 동작을 교체해야 하는 지점에 필요한 인터페이스를 둬요.

### 구현 순서와 남은 상세

실행 의존성은 다음과 같으며, 단계 구분이 뒤 단계의 필수 범위를 제외한다는 뜻은 아니에요.

1. 앱 소유 설정의 저장·가져오기 계약과 실행 수명을 정하고, 기존 규칙 판정과 미리보기가 같은 기준을 사용하게 해요.
2. 세 종류 영상 입력의 작품·회차 발견, 확인한 연결의 유지, 후보 조회·선택을 연결해요.
3. 출처별 수신과 서버 브라우저 인증을 작업 기록에 연결해요.
   서로 독립적인 출처는 공통 결과·실패 표현을 정한 뒤 병행할 수 있어요.
4. 수신한 묶음의 분석·보관·폰트 재사용·배치 계획을 연결하고, 복사 적용·교체 승인·영상 대기를 실제 파일로 검증해요.
5. 전체 웹 흐름과 실제 배포의 접근 보호·재생기 호환을 확인하고 운영 안내를 갱신해요.

새 YAML의 회차 대응·보관 관계와 값 검증, 승인 증거와 체크포인트별 복구 판정은 위에서 정했어요.
모듈 내부의 소스 파일 배치, 이를 구현할 파일시스템 동작과 동기화 수단, CPU·메모리 및 압축 해제 한도의 수치는 구현 환경에 맞춰 구체화하고 검증해야 해요.
구현에 필요한 국소 상세는 기존 구조를 우선해 정하고, 대안 간 책임·의존 방향·호환·운영 비용이 의미 있게 달라지는 선택은 해당 구현 전에 사용자와 결정해요.
미확정 구조는 별도 결정 대상이며, 이 설계 결정은 제품 구현 착수를 뜻하지 않아요.

## 검증 근거와 완료 판정

위 요구에 붙은 입력·상태·관찰 결과가 각 동작의 완료 기준이에요.
규칙 우선순위, 선택 가져오기 보존, 회차 대응, 복사 독립성, 승인 유효성, 대기 전이, 위험한 묶음의 경계처럼 회귀 시 사용자 파일이나 결과가 달라지는 계약은 격리된 작은 입력으로 검증해요.
정상 입력 처리와 잘못된 입력·자원 과다에 대한 안전 검증을 구분하고, 외부 사이트 인증을 일반 자동 테스트의 무인 성공 조건으로 만들지 않아요.

현재 [빌드 이미지](../../Dockerfile)는 `cargo build --release`를 수행하고, [배포 workflow](../../.github/workflows/deploy.yml)는 태그 기반 이미지 빌드·게시이며 테스트 단계는 없어요.
[현재 인라인 테스트](../../src/main.rs)의 `test_get_torrent`는 하드코딩된 외부 Transmission 주소에 접근하므로, 일반 `cargo test`를 환경 독립적인 검사로 간주하지 않아요.
규칙 판정과 RSS 제외·첫 일치 선택의 기존 동작을 검증 가능한 경계로 재사용하되, 외부 Transmission과 파일 변경은 지정된 격리 검증 환경에서 다뤄요.
구현 결과에 맞는 빌드·회귀 검증 명령과 결과를 기록하고, 실제 배포 이미지에서도 자막 기능과 UI가 동작하는지 확인해요.
명세 작성 중에는 제품 빌드·테스트·배포를 실행하지 않았으며, 배포 workflow의 존재가 게시 권한을 뜻하지 않아요.

통합 확인은 실제 trss 웹 화면에서 수행하고, 소스별 다운로드 결과와 파일시스템 결과를 함께 확인해요.
다운로드·압축 분석의 모의 응답이나 API 테스트만으로 사용자 인증·프록시·재생기 검증을 완료 처리하지 않아요.
실제 사용에서 수동 다운로드·업로드·이름 변경·이동이 남는지 관찰하는 것은 코드 검증과 별개이며, 그 관찰 전에는 수작업 감소 효과를 입증했다고 표시하지 않아요.

기존 근거는 다음 범위에 한정해 재사용해요.

- [출처 표본 기록](../brainstorm/web-gui-subtitles.md#공개-자막-경로-조사)은 Drive 개별·ZIP, Tistory 일반 첨부·WinPNG, Naver HTTP 첨부의 실제 바이트와 형식 확인 근거예요.
  출처별 다른 수신 경로·링크 유효기간·실제 trss 배치는 별도로 남아 있어요.
- [서버 브라우저 비교](../brainstorm/web-gui-subtitles.md#일반-chromium-직접-연결-비교)는 새 프로필의 일반 Chromium에서 사람이 CAPTCHA를 해결한 뒤 서버 파일 수신에 성공한 표본이에요.
  Selenium 구성 실패의 단일 원인, 지속 성공, LAN·VPN 배포, trss 내부 화면과 최종 배치의 증거는 아니에요.
- [재생기 근거](../brainstorm/web-gui-subtitles.md#재생기-파일명과-폰트-호환-근거)와 보관·적용 ADR의 IINA 숨김 검색 제외는 문서·소스 조사예요.
  실제 사용자 기기에서의 재생·폰트 적용 관찰은 아직 없어요.

출처별 종단 간 처리, 교체 비교 화면, 보호된 내부 인증 화면, 배치와 대기 동작을 모두 충족하기 전에는 전체 구현 완료로 표시하지 않아요.
실제 배포·재생기·사용 관찰이 남으면 코드 검증 결과와 분리해 해당 범위와 남은 조건을 기록해요.

## 남은 구체화와 비차단 보류

- 표지의 외부 제공자, 모호한 검색 결과의 자동 지정 기준, 직접 지정 입력 방식과 이미지 보관·이동 방식을 구체화해야 해요.
  표지 선택 상태의 영속화와 YAML 교환 필드도 이에 맞춰 추가해야 하며, 현재 열거된 설정·보관 필드만으로 표지 기능의 데이터 설계까지 완료된 것은 아니에요.
- 재생기별 폰트 활용 방식과 Apple 기기별 실제 호환은 실기 검증이 필요해요.
  저장·복사·비교 작업과 독립적으로 진행할 수 있지만, 폰트 활용의 보장에는 필요한 근거예요.
- 출처별 변경 확인·부분 수신 가능성은 아직 검증하지 않았어요.
  현재 표본에는 폰트가 없고, 같은 폰트의 실제 전송 생략이나 ZIP 부분 수신도 확인하지 않았어요.
  개별 링크의 존재와 변경 없는 바이트의 증명은 구분하고, 실제 전송량과 보관 중복 제거를 각각 검증해요.
- CPU·메모리·압축 해제 한도의 구체 수치는 대표 입력 측정 후 구현 시 명시하고 해당 경계를 검증해요.
  유휴 5분·동시 브라우저 작업 1개의 초기 설계 기본값과 조정한 설정 모두 수명·격리·상한 준수의 검증 대상이에요.
- 중복 영상의 세부 선택 흐름과 외부 알림은 보류해요.
  중복 영상 보류 시 오배치 금지와 외부 알림 없이 웹에서 후보·실패·인증 대기를 확인하는 요구는 유지해요.
