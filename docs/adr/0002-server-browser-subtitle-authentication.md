# 자막 인증은 서버 브라우저의 원격 화면에서 처리해요

브라우저 네트워크를 worker와만 나눈다는 부분은 [웹의 브라우저 네트워크 ADR](0013-web-on-browser-network.md)이 2026-10-03에 대체했어요: 웹도 `browser_net`에 들어가 실행의 CDP에 닿고, 그 네트워크에서 오는 연결은 받지 않으며, 브라우저의 송신은 실행기의 프록시가 공개 주소로만 보내요.

다운로드 과정에서 사용자가 할 일을 CAPTCHA 해결로 한정하고, 수동 파일 다운로드·업로드·이동 없이 서버에서 자막 처리를 이어가야 해요.
인증이 필요한 자막 다운로드는 서버가 소유한 Chromium을 직접 실행하고 CDP로 제어하며, 별도 주소나 창으로 이동하지 않고 trss의 해당 작업 화면 안에서 직접 인증하도록 정했어요.
서버가 페이지 열기와 정상 다운로드 시작을 처리하고, 사용자의 직접 인증 후 같은 브라우저가 서버 저장소에 파일을 받아요.
기존 자막 후보 선택과 교체 승인 요구는 유지해요.

사용자 브라우저 확장은 서버의 브라우저 운영 부담을 줄일 수 있지만, 사용자 PC의 확장 설치·사이트 권한·브라우저별 지원과 별도 서버로의 파일 전달이 필요해요.
서버 브라우저 방식을 선택해 사용자 PC의 확장 설치와 파일 전달 경계를 피하는 대신, 서버의 브라우저 자원과 프로필·원격 화면 운영을 맡아요.
원격 화면과 제어 경로도 기존 VPN·앞단 인증의 접근 보호를 우회해서는 안 돼요.

trss 페이지 안에 작업 전용 원격 브라우저 화면을 표시하고, 사용자의 마우스·키보드 입력을 그 브라우저에 전달해요.
외부 자막 사이트 자체를 iframe으로 넣거나 CAPTCHA를 복제하는 방식이 아니라, 서버 브라우저의 화면을 전송하는 방식이에요.
화면 전송은 CDP의 화면 전송과 입력 전달을 웹이 중계하는 방식으로 정했어요(사용자 결정, 2026-10-02).
처음 후보였던 noVNC(가상 디스플레이를 VNC로 보냄)도 erulabo 인증을 통과했지만, 데스크톱 창 전체가 축소돼 보여 PC·휴대폰 모두 누르기 어려웠어요. CDP 방식은 원격 페이지만 보이고 기기 지표 흉내로 휴대폰 배치를 정확히 맞출 수 있어요([원격 화면 비교](../brainstorm/web-gui-subtitles.md#2026-10-02-원격-화면과-기기-폭-비교)).
그 대신 화면 프레임과 입력 중계를 trss가 직접 만들고, 스크롤의 부드러움 같은 조작감도 직접 다듬어야 해요. VNC 서버와 창 관리자는 필요 없어요.

인증 화면을 제공하는 페이지뿐 아니라 화면·입력 WebSocket 연결도 같은 접근 보호를 받아야 해요.
원본 CDP 포트를 사용자에게 별도로 공개하는 방식으로 보호를 우회하지 않아요.
HTTPS 배포에서는 보안 WebSocket을 사용하고, 앞단 프록시의 연결 전달과 접근 통제를 함께 검증해야 해요.

[erulabo 표본 검증](../brainstorm/web-gui-subtitles.md#일반-chromium-직접-연결-비교)에서는 Selenium 기반 실행이 인증 실패했고, 일반 Chromium 직접 연결에서는 사용자의 CAPTCHA 해결 후 서버 파일 수신이 성공했어요.
이 비교는 인증 결과의 단일 원인을 입증하거나 모든 출처·환경에서의 지속적인 성공을 보장하지 않아요.
OMP 연결 도구와 Selenium이 포함된 실험 이미지를 제품 의존성으로 채택한 결정은 아니에요.

브라우저는 앱과 분리한 비공개 컨테이너에서 실행하기로 했어요.
앱 컨테이너의 자식 프로세스로 두면 수명 제어와 파일 경로는 단순하지만, 브라우저 의존성과 자원 사용을 앱과 함께 관리해야 해요.
별도 컨테이너를 선택해 의존성과 자원 한도를 분리하는 대신 내부 제어 연결, 실행·종료 연동과 수신 파일 공유를 관리해요.
컨테이너 분리 자체가 접근 보호를 대신하지 않으며, 위 페이지·WebSocket·CDP 보호 요구는 그대로 유지해요.
[별도 worker 바이너리](0006-separate-web-worker-binaries.md)가 브라우저 수명을 관리하고, 웹은 보호된 작업 화면과 원격 입력 연결을 제공해요.

인증 대기 작업 자체는 보존하되, 브라우저가 작업을 실행 중이지 않고 사용자 조작도 없는 유휴 시간이 지나면 브라우저를 종료해요.
초기 설계 기본값은 유휴 5분과 동시 브라우저 작업 1개이며, 두 값은 운영 설정으로 조정할 수 있게 해요.
이는 실측 성능값이 아닌 보수적인 시작값이며, 동시성을 높여도 작업별 화면·입력·프로필·수신 파일이 격리되어야 해요.
사용자가 돌아와 작업을 열면 페이지와 필요한 인증 화면을 자동으로 다시 준비해요.
브라우저를 계속 켜두어도 사이트의 인증 만료를 막을 수 없으므로, 화면의 지속 보존보다 작업 보존과 서버 자원 회수를 선택했어요.

브라우저 실행마다 새 전용 프로필을 사용하고, 종료하면 쿠키·사이트 저장 상태를 버려요.
작업 기록과 받은 자막은 프로필과 별도로 보존하므로 브라우저 종료가 다운로드 결과나 대기 작업을 삭제하지 않아요.
프로필을 유지하면 사이트가 저장한 인증 상태를 재사용할 가능성은 있지만, erulabo에서 반복 CAPTCHA가 줄어드는 효과는 검증하지 않았어요.
성공한 실험도 새 프로필을 사용했으므로, 확인되지 않은 편의를 위해 사이트 상태를 장기 보관하지 않는 방식을 선택했어요.

2026-10-03에 브라우저 컨테이너의 제어 방식을 정했어요(사용자 결정, 0039).
컨테이너는 항상 떠 있고 가상 디스플레이와 작은 실행기(`trss-browserd`)만 담아요. worker가 비공개 compose 네트워크로 실행기에 실행의 시작·종료를 요청하고, 실행기가 실행마다 새 프로필로 Chromium을 띄워 종료할 때 프로필을 지워요.
Docker 소켓은 worker에도 웹에도 주지 않아요. 소켓이 있으면 앱 컨테이너가 호스트의 Docker 전체를 다룰 수 있게 되기 때문이에요.
실행기는 공유 토큰이 든 요청만 받고 호스트에 포트를 열지 않으며, CDP는 실행기가 중계하므로 원본 CDP 포트는 컨테이너 밖에 나오지 않아요.
worker와 실행의 CDP 연결이 끊기면 그 실행은 끝난 것으로 보고 거둬요. 연결 없이 남은 브라우저가 자원을 쥐고 있지 않게 하려는 선택이에요.
브라우저는 열라고 받은 사이트의 페이지를 실행하므로 로그인이 없는 웹과 Transmission이 있는 `trss_net`에 두지 않고, worker와만 나누는 별도 네트워크에 둬요.
위 컨테이너 분리 결정과 유휴·프로필 결정은 그대로이며, 이 문단은 그 제어 방식을 구체화해요.

이 기록은 제품 방향이며, 컨테이너와 수명 제어(0039), 브라우저의 송신 제한(0053), trss 페이지 안의 원격 화면과 다운로드 재개(0040)를 구현했어요.
남은 것은 제품 이미지로 실제 erulabo 게시물을 사람이 인증해 받는 확인(0040·0041), 실제 휴대폰 확인, 배포 환경의 접근 보호예요.
현재 요구와 완료 조건은 [작업과 인증 명세](../specs/jobs.md#작업-화면-안의-인증과-브라우저-수명)를 따라요.
