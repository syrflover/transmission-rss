# 규칙은 그 규칙을 가진 크레이트에서 한 번만 테스트해요

2026-10-07 `6c175f1`에서 Rust 테스트는 2,759개였고, Rust 코드 229,557줄 중 101,698줄이 테스트 파일이었어요.
같은 규칙을 기능 크레이트, trss-web의 API 테스트, trss-worker의 통합 테스트에서 각각 테스트해 왔어요.

2026-09-25부터 2026-10-07까지의 `fix` 커밋 184개를 커밋 메시지와 diff로 분류했어요.
회귀(전에 되던 동작이 이 저장소의 다른 변경으로 깨진 것)는 15건이었고, 테스트가 실패해서 찾은 것은 하나도 없었어요.
15건 중 14건은 바로 옆 경우를 확인하는 테스트가 있었고 통과했어요. 깨진 것은 아무 테스트도 쓰지 않은 입력이었어요.
예를 들어 다시 받은 토렌트의 이름을 정하는 규칙은 2026-10-02에 58분 사이에 네 번 고쳤는데(`ab853a1`–`70013ab`), 고칠 때마다 다음 종류의 이름이 깨졌어요.
같은 규칙을 여러 층에서 테스트해도 층마다 같은 작성자가 떠올린 입력을 써요. 그래서 층을 더하면 테스트 개수는 늘지만 잡는 범위는 거의 넓어지지 않는다고 판단했어요.
실제 사용에서 찾은 결함 9건 중 7건은 가짜 서버로 도는 테스트가 닿지 않는 곳에서 났어요. 재부팅 뒤 바뀐 장치 번호, musl 빌드, cgroup과 커널, 실제 Chromium, 화면 렌더링이에요.
이 분류에서 발견 경로를 리뷰로 본 162건은, 관찰했다는 말 없이 시나리오만 적은 커밋을 그렇게 판단한 것이에요.

그래서 새로 쓰는 테스트는 다음처럼 나눠요(사용자 결정, 2026-10-07).

- 규칙은 그 규칙을 가진 크레이트에서 한 번만 테스트해요. 규칙은 입력에 따라 결과가 달라지는 판정과 계획이에요. 예를 들면 trss-collect의 규칙 판정과 회차 변환, trss-jobs의 배치와 교체 계획, trss-library의 회차 대응이에요.
- trss-web의 API 테스트는 웹이 맡은 것만 확인해요. 요청과 응답의 모양, 상태 코드, Host·Origin 검사예요. 규칙의 결과를 API로 다시 확인하지 않아요.
- trss-worker의 테스트는 프로세스에서만 생기는 문제를 확인해요. 잠금, 주기와 명령의 순서, 동시 실행, 자식 프로세스, 중단 뒤 이어 하기예요. 웹이 받은 명령이 worker까지 이어지는지도 여기서 확인해요.
- 릴리스 이름과 파일 이름의 해석처럼 입력의 종류가 많은 규칙은 실제 입력 묶음으로 테스트해요. 묶음은 서버 DB 복사본의 수집 이력에서 모은 이름과 공개 피드에서 모은 이름이에요. 저장소가 공개돼 있으므로 수집 이력에서는 이름만 넣고, 주소·해시·폴더·규칙은 넣지 않아요. 예제 테스트 여러 개 대신 묶음을 도는 테스트 하나를 둬요.
- 배포하기 전에 workspace 테스트를 배포 이미지와 같은 musl 대상(`x86_64-unknown-linux-musl`)으로도 돌려요. 평소 변경 때는 돌리지 않아요.

이미 있는 테스트는 리팩터링하는 영역마다 이 기준으로 정리해요.
그 영역을 리팩터링하는 동안에는 기존 테스트가 동작이 그대로인지 확인하는 수단이므로, 리팩터링을 마친 뒤에 정리해요.
위층에서만 확인하던 규칙은 테스트를 지우지 않고, 그 규칙을 가진 크레이트로 내려요.

실제 브라우저로 화면을 여는 테스트와 Docker 배포 환경의 테스트는 지금 만들지 않아요.
실제 사용에서 그 종류의 결함이 보이면 다시 정해요. 실제 디스크의 동작은 서버에서 `trss-probe`로 확인해요.

사용자 경로를 처음부터 끝까지 도는 테스트를 중심에 두는 안도 견줬어요.
개수는 가장 적지만, 테스트 하나가 느리고 실패했을 때 원인을 찾는 시간이 길어서 변경 비용이 커져요.
