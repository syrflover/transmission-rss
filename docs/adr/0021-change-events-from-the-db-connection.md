# 화면은 DB 연결이 알리는 바뀜을 SSE로 듣고 다시 읽어요

2026-10-21에 화면은 서버 상태를 18곳에서 주기적으로 다시 읽었어요. 간격은 0.7초에서 60초였고, 명령의 결과, 자막 작업, 할 일, 표지, 편성, 수집 상태판이 모두 이 모양이었어요.
[한 프로세스 ADR](0019-one-process-for-web-and-worker.md)로 web과 worker가 한 프로세스가 되면서, 상태를 바꾸는 코드와 화면에 응답하는 코드가 같은 프로세스에 있게 됐어요.

사용자는 구조를 가볍게 하며, 화면이 SSE 연결 하나로 무엇이 바뀌었는지 듣고 주기적으로 읽던 18곳을 모두 바꾸기로 했어요(사용자 결정, 2026-10-21).
이벤트는 바뀐 것의 종류와 ID만 담고, 화면은 지금의 조회 경로로 다시 읽어요. 데이터의 출처가 조회 경로 하나로 남고, 이벤트용으로 같은 데이터의 타입을 따로 두지 않아도 돼서예요.

DB 표의 바뀜은 쓰는 코드가 아니라 DB 연결이 알려요(사용자 결정, 2026-10-22).
연결이 표마다 임시 trigger를 걸어 트랜잭션 안에서 바뀐 표의 종류를 적고, 표에 대상을 가리키는 열(작업, 작품, Anissia 작품 같은 것)이 있으면 그 값을 ID로 함께 적은 뒤, 커밋하고 나서 알려요. 대상 열이 없는 표는 종류만 알려요.
쓰는 코드는 알림을 몰라도 되어서, 흩어진 쓰기와 스키마 trigger·cascade의 쓰기도 빠뜨리지 않아요. 마이그레이션이 만든 표에 알릴 종류를 정하지 않으면 테스트가 실패해요.
명령 표는 `CommandStore`가, 메모리에만 있는 지난 회차 검색의 진행은 그 서비스가 스스로 알려요.
서버 시계만으로 달라지는 상태(수집 멈춤, 방영 시각, 서울 날짜 같은 것)는 쓰는 코드가 없어서, 서버가 그 상태가 바뀌는 기한에 이벤트를 보내요. 화면이 기한을 계산해 다시 읽게 하면 판정 규칙이 화면과 서버 두 곳에 생겨서예요.

2026-10-21에는 상태를 쓰는 코드가 커밋한 뒤 알리고, 그러려고 대상마다 쓰는 길을 하나로 모으기로 했어요. DB가 스스로 알리면 행만 알고 화면의 대상을 모른다고 봤어요.
2026-10-22에 조사해 보니 테스트 밖의 쓰기 SQL 문이 390곳이었고, 할 일은 읽을 때 셈해서 ID가 없었고, DB trigger와 cascade가 화면에 보이는 행을 바꿨어요. 쓰는 곳마다 알리면 빠뜨리기 쉬운 것이 그대로여서 DB 연결이 알리는 쪽으로 바꿨어요. trigger는 바뀐 행의 열을 읽으므로 화면의 대상도 알 수 있어요.

서버는 바뀐 대상마다 따로 알려서, 수집 주기 하나가 `history` 바뀜을 250개쯤 보내요. 화면은 읽는 도중에 온 바뀜을 다음 읽기 하나로 모아요.
이벤트 경로, 이벤트의 모양, 화면이 다시 읽는 때와 숨긴 탭의 연결은 [웹 앱 공통 명세의 웹 명령과 상태 갱신](../requirements/web-app.md#웹-명령과-상태-갱신)에 있어요.

다른 안도 견줬어요.

- 쓰는 코드가 커밋한 뒤 알리는 안은 2026-10-21에 골랐다가 위의 까닭으로 바꿨어요.
- 이벤트에 바뀐 데이터를 담는 안은 이벤트용으로 같은 데이터의 타입을 따로 둬야 해서 고르지 않았어요.
