# 통합 테스트는 크레이트마다 바이너리 하나로 묶어요

Cargo는 `tests/` 바로 아래의 `.rs` 파일마다 테스트 바이너리를 하나씩 만들고, 바이너리마다 의존성 전체와 그 debuginfo를 link해요.
2026-10-06 ee284fa에서 `cargo test --workspace`는 테스트 바이너리 70개, 합계 23.09 GB를 돌렸고, 바이너리 하나가 0.3–0.66 GB였어요. 테스트가 10개 이하인 바이너리 28개가 테스트 96개로 8.6 GB를 차지했어요.
trss-jobs에 항목 하나를 더하고 `cargo test --workspace -j 4`를 돌리면 8분 40초(컴파일과 link 2분 38초)가 걸리고 SSD에 14.8 GB를 썼어요.
2026-10-05에는 `-j 4`로 동시에 돈 link 넷이 각각 391–516초 걸렸는데, 같은 link를 혼자 돌리면 0.5–1.5초였어요.
묶은 뒤에는 같은 측정에서 테스트 바이너리가 31개, 7.22 GB였고, 2분 16초(컴파일과 link 1분 9초)에 SSD에 5.2 GB를 썼어요. 이 시간과 쓰기에는 같은 날 SQLite의 메모리 통계를 끄고 SQLite·rustls-pki-types를 최적화해 빌드한 효과가 함께 들어 있어요.

그래서 크레이트의 통합 테스트 파일은 `tests/it/` 아래 모듈로 두고 `tests/it/main.rs`에서 모아, 크레이트마다 바이너리 하나로 link해요(2026-10-06).
파일들이 함께 쓰는 도구(`common`, `support`)도 그 바이너리의 모듈이에요.
기능이 있어야 도는 모듈은 `[[test]]`의 `required-features` 대신 `main.rs`의 `#[cfg(feature = "...")]`로 빼요.
파일 하나의 테스트만 돌릴 때는 `cargo test -p <크레이트> --test it <모듈>::`을 써요.
테스트 파일이 하나뿐인 크레이트는 묶어도 바이너리 수가 같아서 `tests/<이름>.rs`로 둬요.

프로세스를 따로 써야 하는 테스트만 자기 바이너리(`tests/<이름>.rs`)로 남겨요.

- 프로세스 전체의 메모리를 재는 테스트: `#[global_allocator]`로 할당을 세거나 최대 RSS(`VmHWM`)를 읽어서, 같은 프로세스의 다른 테스트가 값을 바꿔요. trss-web의 `*_peak.rs`, trss-collect의 `revision_crc_peak.rs`, trss-library의 `artwork_header_check.rs`예요.
- 실행 파일을 써서 바로 실행하는 테스트: 파일을 쓰는 사이에 다른 스레드가 프로세스를 시작하면, 새 프로세스가 exec하기 전까지 쓰기 핸들을 물려받아 들고 있어서 실행이 `ETXTBSY`("text file busy")로 실패해요. trss-jobs의 `extract_process.rs`는 자기 테스트끼리 프로세스 시작을 하나씩 하도록 막아 두었고, 다른 파일의 테스트는 그렇게 하지 않아요.

함께 묶인 파일의 테스트는 한 프로세스에서 돌아요. 환경 변수, 현재 폴더, 전역 할당자, 자식 프로세스 시작처럼 프로세스 전체에 걸리는 것을 다루는 테스트를 더할 때는 위처럼 자기 바이너리로 둬요.
그 대가로 테스트 파일 하나를 고쳐도 그 크레이트의 통합 테스트를 모두 다시 컴파일해요.

debuginfo를 줄이는 것은 바이너리의 크기를, 묶기는 개수를 줄여서 서로를 대신하지 않아요.
cargo-nextest는 테스트마다 프로세스를 따로 띄워 프로세스를 함께 쓰는 문제는 없애지만, 바이너리 수는 그대로예요.
