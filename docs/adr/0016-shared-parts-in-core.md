# 여러 크레이트가 함께 쓰는 기능 규칙 없는 부품은 trss-core에 둬요

2026-10-07 `07c454d`에서 구조를 조사해 보니, 여러 크레이트가 같은 개념을 따로 구현한 곳이 있었어요.

- 같은 파일인지 알아보는 일은 6곳에 있고, 저장 형식이 3가지예요. 재부팅 뒤 장치 번호가 바뀌는 문제와 musl에서 생성 시각을 읽지 못하는 문제를 고친 수정이 2026-10-06–07에 trss-jobs, trss-collect, trss-library의 표지에 따로 다섯 번 들어갔어요(`a2f2fa6`, `7eff742`, `c050eba`, `aa2944e`, `6c175f1`).
- DB에 저장하는 요청 간격은 AniList, Anissia, 지난 회차 검색에 세 벌 있어요. 기다리는 사이에 생긴 `429` 막힘을 다시 읽는 수정(`a35963c`)은 지난 회차 검색에만 들어갔어요.
- 임시 파일, fsync, 덮어쓰지 않는 이름 바꾸기로 파일을 안전하게 쓰는 일은 5개 크레이트의 10곳 넘게 손으로 썼고, fsync하는 범위가 곳마다 달라요.
- worker의 백그라운드 큐 네 개는 잠금, 재시도, 주기를 도는 같은 루프를 각자 가져요.
- 회차 텍스트의 키와 정렬은 8곳에 있어요.

[ADR 0011](0011-feature-crate-workspace.md)은 명령 큐, 하트비트, `rename_noreplace`처럼 기능 규칙이 없는 인계·파일 도구를 trss-core에 뒀어요. 그러면서 AniList·Anissia의 요청 간격 저장은 클라이언트 크레이트로 옮겼고, 그 뒤 지난 회차 검색이 같은 저장을 한 벌 더 만들었어요.

여러 크레이트가 함께 쓰고 기능 규칙이 없는 부품은 trss-core의 모듈로 두기로 했어요(사용자 결정, 2026-10-07).
위의 다섯 가지가 여기에 들어요. 외부 응답의 `Retry-After` 읽기와 응답 크기 제한도 들어요.
ADR 0011에서 요청 간격의 저장을 클라이언트 크레이트에 둔다는 부분은 이 결정으로 바뀌어요. 클라이언트 크레이트는 trss-core의 요청 간격을 써요.

- 부품은 기능 판단을 담지 않아요. 예를 들어 같은 파일인지 알아볼 때 inode만 견주는 규칙은 부품이 지키지만, 내용 해시, CRC, 수정 시각 같은 추가 검사는 그 검사를 쓰는 기능 크레이트에 남아요.
- 응답을 다루는 부품 때문에 trss-core가 reqwest에 의존하게 된다고 봤어요. [0102](../tickets/0102-request-pace-in-core.md)에서는 부품이 헤더 값과 응답을 조각으로 읽는 함수를 받게 만들어, 이 의존은 생기지 않았어요(2026-10-09). trss-archive와 trss-probe는 trss-core에 의존하지 않으므로 어느 쪽이든 영향이 없어요.
- trss-core를 바꾸면 그 위의 크레이트가 모두 다시 빌드돼요. 이 부품들은 자주 바뀌지 않는다고 봤어요. 크레이트 분리 뒤 코드가 바뀐 커밋 109개 중 45개가 trss-core를 건드렸고, 그중 35개는 마이그레이션 목록(`db.rs`)이었어요.

작은 공용 크레이트를 새로 만드는 안도 견줬어요. 경계는 더 뚜렷하지만, 크레이트가 늘어 전체 그림을 파악하기가 더 어려워져요.
쓰는 기능 크레이트 하나에 두는 안은 새 위치가 생기지 않지만, 외부 연동 크레이트가 기능 크레이트를 부를 수 없어서 요청 간격 같은 부품은 복사본이 남아요.
