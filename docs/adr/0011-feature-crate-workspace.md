# 공통 라이브러리를 기능별 크레이트의 workspace로 나눠요

[웹·작업 바이너리 분리 ADR](0006-separate-web-worker-binaries.md)은 공통 라이브러리를 패키지 하나 안의 기능별 모듈로 두고, 패키지까지 나눌 필요는 없다고 정했어요.
결과 목표 1·2를 거치며 라이브러리가 약 87,000줄이 됐고, [모듈 구성](../specs/web-app.md#공통-라이브러리의-모듈-구성)의 의존 방향(기능 모듈이 웹 라우터나 worker 실행 루프를 참조하지 않음, 다른 기능의 테이블을 직접 갱신하지 않음)은 관례로만 지켜지고 있어요.
기능별 SQL도 기능 모듈 곁이 아니라 `store/` 아래 기능별 하위 모듈에 모여 있어요.

자막·작업·서버 브라우저 코드를 더하는 결과 목표 3을 시작하기 전에, 저장소를 Cargo workspace로 바꾸고 공통 기반, 기능 크레이트, `trss-web`·`trss-worker` 바이너리 크레이트로 나누기로 했어요(사용자 결정, 2026-10-02).
기능의 저장 코드는 그 기능의 크레이트로 옮겨, 크레이트 경계와 의존 방향을 컴파일러가 강제하게 해요.
자막·작업·브라우저 코드는 처음부터 크레이트로 만들어요.
DB가 하나이므로 마이그레이션 순서도 하나로 유지해요.
구체적인 크레이트 지도는 실제 모듈 의존 관계에서 만들어 옮기기 전에 사용자와 확정해요.

얻으려는 것은 경계의 강제와 코드 탐색·정리이며, 증분 빌드 시간의 단축은 부차적이에요.
2026-10-02에 리프 모듈 한 줄을 바꾼 증분 빌드가 바이너리 22초, 테스트 27초였어요.
공통 기반 크레이트를 바꾸면 그 위의 크레이트가 모두 다시 빌드되므로, 분리가 빌드 시간을 늘 줄인다고 보지 않아요.

단일 크레이트를 유지하는 안은 이동 비용이 없지만 경계를 계속 검토로만 지켜야 해요.
새 자막 코드만 크레이트로 만드는 안은 기존 라이브러리가 새 크레이트와 바이너리 사이에 끼어 의존 순환을 피하기 어렵고, 목표 3 뒤로 미루는 안은 자막 코드까지 함께 옮겨야 해요.
그 대가로 동작을 바꾸지 않는 큰 이동이 목표 3의 기능 작업보다 먼저 와요.
다른 크레이트가 쓰는 항목은 `pub` 경계를 다시 정해야 해요.

[ADR 0006](0006-separate-web-worker-binaries.md)의 나머지 결정, 곧 두 바이너리와 별도 컨테이너, worker만 파일을 반영한다는 실행 책임, 단일 worker 프로세스는 그대로예요.
