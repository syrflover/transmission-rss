# 실행 도중 끊긴 자막 작업은 멈춰 두고 사람이 다시 시작해요

[ADR 0006](0006-separate-web-worker-binaries.md)은 worker가 다시 시작하면 기록과 실제 파일을 대조해, 확인할 수 있는 지점부터 미완료 작업을 자동으로 이어 하게 했어요. 중단 작업마다 수동 재개를 요구하는 안보다 반복 조작을 줄이는 쪽이었어요.
그래서 자막 작업은 받기·보관·적용·교체·재배치의 단계와 효과마다 기록을 남기고, 다시 시작할 때 그 기록과 디스크를 견줘요. 이 기록을 담는 테이블이 `jobs/store_apply.sql` 마이그레이션에만 9개예요.
서버에서 worker를 다시 시작한 뒤 작업이 이어진 것을 본 기록은 없어요(2026-10-21, [작업 명세의 검증 표](../specs/jobs.md#작업-결과-1)).

[한 프로세스 ADR](0019-one-process-for-web-and-worker.md)로 web과 worker가 합쳐져도 프로세스는 죽을 수 있어요.
사용자는 이때 실행 도중에 끊긴 자막 작업을 자동으로 이어 하지 않고, 멈춰 두었다가 사람이 다시 시작하게 하기로 했어요(사용자 결정, 2026-10-21).
인증·배치 확인·교체 승인·영상 대기·자막 대기처럼 사람을 기다리던 작업은 DB의 상태일 뿐이라 다시 시작한 뒤에도 그대로 기다려요. 이 결정이 닿는 것은 단계를 실행하던 도중에 끊긴 작업뿐이에요.
끊긴 작업은 할 일로 따로 올리지 않고, 실패한 작업처럼 할 일 화면의 `자막 작업` 맨 위에 `중단됨`으로 보여요(사용자 결정, 2026-10-21). 실패한 자막 작업을 할 일로 올리지 않는 [할 일 규칙](../specs/jobs.md#할-일)을 그대로 따른 거예요.
파일을 쓰는 단계는 새 파일을 끝까지 쓴 뒤 이름을 바꿔 제자리에 두는 순서로, 끊겨도 파일을 잃지 않게 해요.
자동 재개를 위한 효과별 기록과, 기록과 디스크의 대조는 없어져요.
수신 영역에 이미 받아 둔 묶음은 다시 시작할 때 다시 받지 않는다고 가정했어요. 작업의 `받음` 상태만으로 알 수 있어서예요.

이 결정을 고른 까닭은 사용자가 고른 목표, 곧 코드를 읽고 고치는 비용과 기능 하나를 더하는 단계를 줄이는 데 이 안이 가장 많이 기여하기 때문이에요. 끊기는 구간이 단계를 실행하는 동안뿐이라, 사람이 다시 시작해야 하는 일은 드물 거라고 봤어요. 이 빈도는 측정하지 않았어요.

다른 안도 견줬어요.

- 끊긴 작업을 처음 단계부터 다시 돌리되 이미 된 단계는 디스크를 보고 건너뛰는 안은 사람 손이 가지 않아요. 하지만 단계마다 이미 됐는지 판단하는 코드가 남아요.
- 지금처럼 효과별 기록과 대조로 자동 재개하는 안은 사람 손이 가지 않지만, 코드가 가장 많이 남아요.
