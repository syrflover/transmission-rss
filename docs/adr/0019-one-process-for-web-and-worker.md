# 웹과 worker를 한 프로세스로 합쳐요

[ADR 0006](0006-separate-web-worker-binaries.md)은 `trss-web`과 `trss-worker`를 별도 바이너리와 컨테이너로 나누고, 파일 반영은 worker만 하게 했어요.
그래서 파일이나 Transmission을 건드리는 사용자 동작은 모두 같은 경로를 거쳐요. web이 DB에 명령으로 적으면, worker가 깨우기 소켓이나 주기 조회로 알아채 worker 잠금 아래에서 집어 실행하고, 화면은 2초마다 결과를 조회해요.
명령 6종, 자막 작업, 원격 화면, 보관 파일 정리가 모두 이 모양이에요.

2026-10-21(`5cdae9e`)에 세어 보니, 이 인계와 관련된 코드가 `trss-core`의 명령·큐·깨우기·하트비트·잠금·폴더 차례 3,873줄과 `trss-worker` 10,503줄(테스트 7,059줄 포함)이었어요.
비용은 기능마다 다시 생겨요. 동작이 다른 프로세스에서 나중에 끝나므로, 화면·명세·테스트가 "접수됨"과 "끝남" 사이의 상태와, 중복 전달·응답 단절·늦게 도착한 응답 같은 전달 상황을 각각 다뤄요.
이 간접 비용의 줄 수는 세지 않았어요.

분리로 얻으려던 것은 web만 재시작해도 worker 작업이 이어지는 재시작 단위였어요.
두 바이너리는 같은 이미지와 같은 버전으로 함께 배포되므로, 이 이득은 web만 따로 멈춘 경우에만 나타나요.
자원을 나눠서 얻는 것도 거의 없었어요. 2026-10-02 서버에서 web은 3.9 MiB, worker는 7.4 MiB를 썼어요([0058](../specs/2026-10-04-server-resource-limits/0058-server-oom-and-resource-limits.md)).

사용자는 수집과 자막 기능을 모두 두되, 코드를 읽고 고치는 비용, 기능 하나를 더하는 단계, 테스트에 드는 계산 자원, 서버 운영을 줄이려고 web과 worker를 한 프로세스로 합치기로 했어요(사용자 결정, 2026-10-21).
한 프로세스가 화면과 API, 5분 수집 주기, 감시 폴더 읽기, 명령 실행, 자막 작업을 함께 돌려요. 합친 크레이트·바이너리·컨테이너의 이름은 `trss`예요(사용자 결정, 2026-10-21).
인증·배치 확인·교체 승인·영상 대기·자막 대기처럼 사람을 기다리는 자막 작업은 지금처럼 DB의 작업으로 남고, 같은 프로세스의 백그라운드 작업이 실행해요.
같은 폴더를 건드리는 동작의 차례는 프로세스 안에서 맞춰요.

명령은 지금처럼 `commands` 테이블에 기록으로 남기고, 다른 프로세스에 넘기는 부분만 없애요(사용자 결정, 2026-10-21).
API가 명령을 적은 뒤 같은 프로세스에서 곧바로 실행을 시작하고, 끝나기를 기다리지 않고 응답해요. 그래서 깨우기 소켓, 3초 주기 조회, worker 잠금 아래의 claim, heartbeat가 없어져요.
요청 안에서 끝내지 않는 까닭은 명령 6종이 모두 몇 초 넘게 걸릴 수 있어서예요. 한 번 받기는 magnet 정보를 1초 간격으로 17번까지 기다리고, 규칙 보관은 Transmission이 새 폴더를 보고하기를 한 번에 300초까지 기다려요.
테이블을 남기는 까닭은 이 테이블이 큐이면서 기록이기 때문이에요. 화면은 명령 ID로 결과를 조회하고, 같은 ID로 다시 보낸 명령은 한 번만 실행돼요. 규칙의 마지막 폴더 이동, 회차 되돌리기, Anissia 새로고침의 지난 결과와, 수집 주기가 세는 응답 없던 토렌트 추가도 이 테이블에서 읽어요.
그래서 화면이 다루는 "접수됨"과 "끝남" 사이의 상태와 응답 단절은 남아요. 줄어드는 것은 서버 쪽의 인계이고, 위의 3,873줄이 모두 없어지지는 않아요.

프로세스가 하나이므로 그 프로세스가 죽으면 화면과 작업이 함께 멈춰요.
다시 시작하면 끝나지 않은 명령을 다시 실행해요(사용자 결정, 2026-10-21). 명령 실행 코드는 이미 같은 명령을 다시 실행해도 되게 짜여 있어서, 이 일에 드는 코드가 거의 없어요. 업그레이드 직전에 남은 명령도 같은 길로 실행돼요.

합친 프로세스는 미디어를 쓰기로 마운트해요. 지금은 web이 미디어를 읽기 전용으로 마운트해서 API 코드가 경로를 잘못 다뤄도 읽기에서 그치지만, 합친 뒤에는 파일을 바꾸거나 지울 수 있어요.
사용자는 접근 경계인 LAN·VPN과 origin 검사를 그대로 두고 이를 받아들였어요(사용자 결정, 2026-10-21).

이 결정은 서버 브라우저 컨테이너와, 받은 압축 파일을 한도 안에서 푸는 별도 프로세스를 다루지 않아요.

다른 안도 견줬어요.

- 두 프로세스를 두고 web이 worker를 로컬 HTTP로 불러 결과를 기다리는 안은 화면의 중간 상태를 줄여요. 하지만 컨테이너 둘, worker가 꺼져 있을 때의 처리, 두 프로세스의 버전 맞춤이 남아서 고르지 않았어요.
- 구조를 그대로 두고 기능만 덜어내는 안은 이동 비용이 없어요. 하지만 사용자가 수집과 자막 기능이 모두 있어야 한다고 해서(2026-10-21), 남는 기능마다 인계 비용이 계속 들어요.
- `commands` 테이블을 없애고 명령의 진행을 메모리에만 두는 안은 테이블 코드를 덜어요. 하지만 지난 결과를 기능마다 따로 저장해야 하고, 다시 시작하면 진행 중이던 명령과 그 결과가 사라져서 고르지 않았어요(2026-10-21).
