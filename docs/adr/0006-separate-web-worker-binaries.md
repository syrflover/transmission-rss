# 공통 코드를 사용하는 웹·작업 바이너리를 분리해요

공통 Rust 라이브러리를 재사용하되 `trss-web`과 `trss-worker`를 별도 바이너리로 만들고, 같은 앱 이미지에서 각각 별도 컨테이너로 실행하기로 했어요.
한 바이너리의 역할별 실행 모드나 한 프로세스에 웹·작업을 합치는 대안보다, 실행 진입점과 재시작 단위를 명확히 나누는 방향을 선택했어요.
[Cargo의 여러 바이너리와 공통 라이브러리 지원](https://doc.rust-lang.org/cargo/reference/cargo-targets.html#binaries)을 사용하면 저장소나 패키지까지 별개로 나눌 필요는 없어요.

공통 라이브러리는 기능별 모듈로 구성해요.
데이터 모델·저장소·업무 처리를 전역 계층으로 나누는 대안보다, 한 기능의 규칙과 저장 코드를 가까이 두어 변경을 한곳에서 다루는 방향을 선택했어요.
DB 접속·마이그레이션 같은 공통 기반은 분리하되, 기능별 SQL과 판정 규칙을 하나의 공용 저장소 모듈에 모으지 않아요.
웹과 worker는 기능 모듈의 인터페이스를 사용하며, 이 코드 구성은 worker만 실제 파일 반영을 담당한다는 실행 책임을 바꾸지 않아요.

웹은 React 정적 화면·API·설정·사용자 선택과 승인 요청을 담당하고, 단일 worker 프로세스는 정기 조회·다운로드·브라우저 수명·파일 반영을 담당해요.
같은 호스트의 로컬 SQLite를 공유하고 같은 릴리스 버전으로 운용하며, 별도 Redis나 분산 작업 시스템을 전제로 하지 않아요.
작업 인계, 중복 실행 방지, 승인 대상 재검증과 중단 복구의 책임이 없어지는 것은 아니에요.
단일 worker는 프로세스 수의 결정이며 모든 다운로드를 반드시 직렬 처리한다는 뜻은 아니에요.

웹 재시작 중에도 worker의 작업은 유지하고, 웹이 돌아오면 기존 작업 상태를 다시 표시해야 해요.
원격 인증 화면 연결은 끊길 수 있으므로 다시 연결하며, 웹 재시작만으로 worker가 관리하는 유효한 브라우저 실행을 새로 만들지 않아요.
브라우저 유휴 종료와 새 실행별 프로필 정책은 [인증 ADR](0002-server-browser-subtitle-authentication.md)을 유지해요.

Chromium은 별도 비공개 이미지·컨테이너로 두고, 앱 이미지에는 두 Rust 바이너리와 정적 화면을 포함해요.
브라우저 분리는 의존성·자원·접근 범위를 나누는 선택이며 처리 속도 향상이 입증된 것은 아니에요.
같은 컨테이너와 별도 컨테이너의 성능 비교는 실행하지 않았어요.

worker 자체가 재시작하면 기록과 실제 파일을 대조하고, 완료가 확인된 수신·보관 단계를 재사용해 미완료 작업을 자동 재개해요.
중단 작업마다 수동 재개를 요구하는 대안보다 반복 조작을 줄이는 방향을 선택했어요.
반영 여부가 불명확하거나 승인 대상이 바뀌었으면 보류하고, 필요한 인증·승인을 기다리며 새 후보를 자동 선택하거나 승인하지 않아요.
다른 환경으로 정보만 가져오는 것은 같은 설치의 중단 복구가 아니므로, 가져오기가 과거 작업·승인을 재실행하는 경로가 되지 않아요.

현재 요구와 완료 조건은 [구현 명세](../specs/web-gui-subtitles.md)에 있어요.
이 기록은 설계 결정이며 제품 구현이나 배포 완료를 뜻하지 않아요.
