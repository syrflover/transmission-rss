# 0010 열 때만 읽던 화면도 바뀜을 들어요

- 상태: 완료
- 출처: [명세의 화면 갱신](spec.md#화면-갱신), [명세의 작품명](spec.md#작품명), [바뀜 알림 ADR](../../../adr/0021-change-events-from-the-db-connection.md), 사용자 피드백 1·4·5번(2026-10-23)
- 막는 티켓: 없음

## 작업

0.8.0에서 주기적으로 읽던 18곳은 바뀜 스트림을 듣고 다시 읽게 바뀌었어요([바뀜 알림 ADR](../../../adr/0021-change-events-from-the-db-connection.md)). 할 일, 메뉴의 할 일 개수, 이번 주 편성, 수집 상태판, 작품 상세의 일부(표지, 자막 후보, 시즌 정보, 보관 파일 정리)가 그래요.

주기적으로 읽지 않던 화면은 여전히 열 때만 읽어요. 그래서 다른 브라우저나 trss가 바꾼 것은 다시 열어야 보여요. 그런 화면은 이래요.

- 라이브러리 목록. 뒤로 가기로 돌아오면 지켜 둔 페이지를 다시 읽지 않고 할 일 배지만 고쳐요. 그래서 구독이 시즌에 붙어 작품명이 바뀌어도 예전 이름이 남을 수 있어요(코드로 본 추정, 2026-10-23).
- 작품 상세의 주 데이터(회차, 시즌, 연결, 규칙)
- 수집의 `구독`·`규칙`(목록과 상세)·`기록`·`채널` 탭
- 설정의 수집 폴더, 감시 폴더 목록, 파일 용량·정리, 공통 정책

사용자는 이 화면들도 바뀜을 듣게 하기로 했어요(2026-10-23). 각 화면은 지금의 조회 경로를 그대로 쓰고, 자기가 보여 주는 대상의 바뀜 종류(`library`, `rules`, `history`, `settings` 같은 것)와 `ready`·`lagged`를 받을 때 다시 읽어요. 편집 중인 입력을 새 조회 값으로 덮어쓰지 않는다는 요구([웹 명령과 상태 갱신](../../../requirements/web-app.md#웹-명령과-상태-갱신))는 그대로 지켜요. 규칙 편집, 채널 편집, 설정의 입력이 그런 곳이에요.

수집 이력은 수집 주기 하나에 `history` 바뀜을 250개쯤 보내요(2026-10-22 개발 환경). 다시 읽기는 도중에 온 바뀜을 하나로 모으므로, `기록` 탭은 주기마다 몇 번만 다시 읽을 거예요. 이 횟수를 개발 환경에서 측정해 결과에 적어요.

[0004](0004-library-folder-choice.md)와 [0005](0005-library-list-remembers.md)도 라이브러리 목록을 고쳐요. 같은 파일을 고치므로 함께 진행하지 말고 하나씩 해요.

## 완료 기준

- [x] 위의 화면마다 자기가 보여 주는 대상의 바뀜과 `ready`·`lagged`에 다시 읽어요. 어떤 바뀜에 다시 읽는지를 웹 단위 테스트로 확인해요.
- [x] 개발 환경에서 두 탭을 열고, 한쪽에서 규칙을 바꾸거나 작품 상세에서 시즌을 이으면 다른 쪽의 규칙 탭, 구독 탭, 라이브러리 목록이 다시 열지 않아도 바뀌어요. 결과에 적어요.
- [x] 구독이 시즌에 붙거나 작품 상세에서 시즌을 이은 뒤 뒤로 가기로 돌아온 라이브러리 목록이 새 작품명을 보여줘요. 이때 스크롤 위치와 보기·정렬·필터는 그대로예요.
- [x] 규칙이나 채널을 편집하는 도중에 그 규칙이 바뀜으로 다시 읽혀도 쓰던 입력이 그대로예요. 웹 단위 테스트나 개발 환경의 확인으로 봐요.
- [x] 수집 주기 하나 동안 `기록` 탭이 다시 읽은 횟수를 개발 환경에서 측정해 결과에 적어요.
- [x] [웹 앱 공통 명세의 웹 명령과 상태 갱신](../../../requirements/web-app.md#웹-명령과-상태-갱신)에서 `기록` 탭과 감시 폴더 목록이 열 때만 읽는다는 문장을 고치고, [라이브러리 명세의 라이브러리 화면](../../../requirements/library.md#라이브러리-화면)에서 뒤로 가기로 되찾은 목록의 다시 읽기를 고쳐요. 검증 표의 행도 고쳐요.
- [x] `npm test`, `npm run typecheck`가 통과해요.

## 결과

### 만든 것

열 때만 읽던 화면이 이제 바뀜 스트림을 듣고, 자기가 보여 주는 것의 바뀜과 `ready`·`lagged`에 지금의 조회 경로로 다시 읽어요. 다시 읽기는 0.8.0의 화면들처럼 `useRead`(읽기 하나에 바뀜을 모으고, 실패하면 간격 뒤에 다시 읽고, 숨겨진 동안 읽지 않아요)를 거쳐요. 화면마다 어떤 바뀜에 다시 읽는지는 그 경로가 읽는 표를 서버의 바뀜 종류로 묶어 정했어요(`library/listens.ts`, `library/detail/listens.ts`, `collect/listens.ts`, `settings/listens.ts`).

| 화면 | 다시 읽는 바뀜 |
| --- | --- |
| 라이브러리 목록 | `library`, `season_info`, `anissia`, `artwork`, `settings`, 할 일 배지가 모이는 `subtitle_job`·`subtitle_store`·`subtitle_mapping`·`rules`·`history` |
| 작품 상세의 주 데이터 | 그 작품의 `library`·`season_info`·`artwork`·`subtitle_store`·`subtitle_mapping`, 작품을 가리키지 않는 `rules`·`anissia`·`history`·`subtitle_job`·`settings`·`command`·`collect_status` |
| 작품 상세의 극장판 연결 | 그 작품의 `season_info`, `anissia` |
| 구독 탭 | `rules`, `anissia`, 서울 날짜가 바뀌는 `collect_status` |
| 제목 후보, 보관 제안 | 할 일 화면과 같은 제안의 종류 |
| 규칙 탭(목록과 상세) | `rules`, `anissia`, `history`, `settings`, `command`, `library`, `season_info`, `artwork` |
| 기록 탭 | `history`, `rules`, `anissia`, `command`, `settings`, `collect_status` |
| 채널 탭, 기록 탭의 채널 고르기 | `rules` |
| 설정의 수집 폴더 | `settings` |
| 설정의 감시 폴더 | `library` |
| 설정의 공통 정책 | `settings`, `library`, `season_info`, `anissia` |
| 설정의 파일 용량·정리 | `subtitle_store`, `subtitle_job`, `artwork`, `library`, `season_info`, `anissia` |

라이브러리 목록과 기록 탭은 페이지를 이어 붙이는 목록이라, 보이던 만큼을 위에서부터 서버가 한 번에 주는 만큼(200개)씩 다시 읽어 불러온 페이지를 갈아 끼워요. 그래서 다시 읽어도 불러온 페이지와 스크롤 위치가 그대로예요. 라이브러리 목록은 뒤로 가기로 되찾을 때도 같은 읽기를 해요. 할 일 목록만 읽어 배지를 고치던 0.8.0의 읽기와, 작품 상세가 목록 캐시를 버리던 곳(표지·시즌 정보·Anissia 연결이 바뀔 때, 작품 폴더를 옮긴 뒤)은 없앴어요. 캐시를 버리면 뒤로 가기에서 첫 페이지만 다시 읽어 스크롤 위치를 잃었기 때문이에요.

작품 상세는 표지를 기다리는 동안만 따로 표지를 읽던 효과를 없앴어요. 주 데이터가 그 작품의 `artwork`에 다시 읽으므로 같은 조회를 두 번 하지 않아요. 설정의 수집 폴더 화면은 공통 정책 화면처럼, 손대지 않은 동안 다시 읽은 새 값을 보여주게 했어요. 규칙 상세와 채널 편집은 이미 편집 중인 입력을 새 값으로 덮지 않았어요.

### 정한 것

- 다시 읽을 바뀜은 경로가 읽는 표를 모두 넣었어요. 할 일 화면처럼, 한 번 더 읽는 비용은 작고 놓친 바뀜은 화면을 낡게 두기 때문이에요(구현 결정).
- 재시도 간격은 작품 상세 10초(표지를 기다리는 동안 3초, 0.8.0과 같음), 나머지 30초예요. 이번 주 편성·수집 상태판과 같은 30초를 목록 화면의 기본으로 삼았어요(구현 결정).
- 구독 추가와 제목 이름 짓기의 고르기 목록(편성표, 채널, 제작자, 작품), 작품 상세의 제작자 고르기는 대화 상자 안에서 잠깐 쓰는 목록이라 바꾸지 않았어요(구현 결정).

### 테스트

2026-10-23에 9ad6f656 위의 작업 트리에서 아래 리뷰에서 고친 뒤 `npm test`(327개), `npm run typecheck`, `npm run build`가 통과했어요. 서버 코드는 바꾸지 않아서 `cargo test`는 돌리지 않았어요.

- `web` `src/lib/rereads.test.ts`의 `the library list reads again for its works, their titles, covers and badges, not for a remote screen or a command`, `a work's page reads again for its own work and for what names no work, and its movie link for its link and anime`, `the collection tabs read again for what their lists are made of, the history only where it is shown`, `the settings read again for what each shows, the folders for the library, the policy and the storage for the titles`는 화면마다 다시 읽는 바뀜과 읽지 않는 바뀜을 겨눠요. 바뀜을 모으고 실패 뒤에 다시 읽는 동작은 0.8.0의 같은 파일 테스트가 겨눠요.
- 할 일 배지만 고치던 `withKinds`와 그 테스트는 쓰는 곳이 없어져 지웠어요.

### 개발 환경 확인

2026-10-23에 이 작업 트리를 Vite 개발 서버로 띄워 `/api`를 개발 환경의 `trss` 컨테이너(서버 DB 사본)로 넘기고, 헤드리스 Chromium(1024×768)을 DevTools Protocol로 움직였어요. 내장 브라우저는 창이 숨겨져 있어 스크롤과 다시 읽기를 볼 수 없었기 때문이에요. 바꾸는 쪽은 따로 연 창의 페이지에서 앱의 API를 불렀고, 두 창 모두 보이는 상태였어요. 페이지마다 `fetch`와 이벤트를 기록했어요. 원본 기록과 쓴 스크립트는 이 PC의 `dev/local/measure/feedback-0.8.0-0010/`에 있어요. Vite는 React StrictMode로 돌아서, 화면이 처음 붙을 때의 읽기가 두 번씩 기록돼요.

- 라이브러리 목록에서 두 페이지 92편을 불러와 4000px 내려간 채, 다른 창이 `Undead Unluck` 시즌 1의 Anissia 연결을 끊었어요. `season_info` 바뀜 하나에 목록을 `limit=92`로 한 번 읽어 작품명이 바뀌었고, 92편과 스크롤 위치, 문서 높이가 그대로였어요.
- 그 작품의 상세에 들어간 사이 다른 창이 시즌 1을 `언데드 언럭`(Anissia 2504)에 이었어요. 상세의 머리 제목이 다시 열지 않아도 바뀌었고, 뒤로 가자 목록이 `언데드 언럭`을 보였으며 92편과 4000px가 그대로였어요. 목록 탭이 다른 탭 뒤에 숨어 있다가 다시 보일 때도 `ready`에 같은 읽기로 바뀌었어요. 확인 뒤 연결은 다시 끊었어요.
- 규칙 탭에서 `Re Zero kara Hajimeru Isekai Seikatsu` 규칙의 일치 문구 칸에 글자를 더해 저장할 수 있는 상태로 둔 채, 다른 창이 그 규칙의 `영상 받기`를 껐어요. 목록은 `/api/rules`를 한 번 읽어 그 규칙을 `멈춤`으로 보였고, 쓰던 입력은 그대로였어요.
- 구독 탭에서 다른 창이 `반딧불이의 혼례`의 `영상 받기`를 끄자, `/api/subscriptions`를 한 번 읽어 카드가 `멈춤`이 됐어요.
- 설정의 공통 정책 화면을 손대지 않고 연 채 다른 창이 브라우저 유휴 시간을 5분에서 10분으로 저장하자, 화면이 10분을 보였어요. 바꾼 규칙, 구독, 정책은 확인 뒤 되돌렸어요.
- 같은 날 보기 `목록`, 정렬 `제목순`, 폴더 `수집`으로 둔 라이브러리 목록(10편)을 400px 내린 채 `Himekishi wa Barbaroi no Yome`의 상세에 들어갔고, 다른 창이 그 시즌 1을 `공주 기사는 야만족의 신부`(Anissia 3423)에 이었어요. 뒤로 가자 목록이 새 작품명을 보였고, 보기·정렬·폴더·필터가 그대로였어요. 스크롤 값은 302px가 됐어요. 바뀐 이름 때문에 작품이 제목순에서 두 번째에서 여섯 번째로 옮겨 가자, 브라우저의 스크롤 고정(scroll anchoring)이 화면에 보이던 행을 제자리에 두었기 때문이에요. 바뀜 없이 같은 왕복을 하면 400px 그대로였고, 스크롤 고정을 끈(`overflow-anchor: none`) 채 같은 왕복을 하면 399px가 그대로였어요. 확인 뒤 연결은 다시 끊었어요.
- 기록 탭을 연 채 수집 주기 하나(시작부터 끝까지 19초)를 기록했어요. 주기는 시작에 `collect_status` 하나, 10 ms 안에 `history` 250개와 `collect_status` 하나, 끝에 `collect_status` 둘을 보냈어요. 기록 탭은 `/api/history`를 5번 읽었어요. 시작에 1번, 몰린 `history`에 2번(읽는 도중 온 것을 모은 한 번 포함), 끝에 2번이에요. 같은 시간에 주기와 따로 온 `anissia` 바뀜 둘에도 1번씩 읽었고, 바뀜과 1 ms 안에 맞물리지 않은 읽기는 없었어요.
- 아래 리뷰에서 고친 뒤, `FX 전사 쿠루미` 구독 규칙의 자막 제작자 고르기를 열어 `코코렛` 대신 `제작자 미정`을 골라 둔 채, 다른 창이 그 규칙을 멈췄다가 다시 켰어요(버전 2 → 3 → 4). 규칙 상세의 `영상 받기` 스위치는 두 번 모두 새 값을 따라갔고, 고르던 `제작자 미정`은 그대로였어요. 확인 뒤 고르기를 취소해서 규칙은 활성, 제작자 `코코렛`이에요.

### 리뷰와 고친 것

`stora:reviewer`가 커밋 전의 변경을 리뷰했어요. 라이브러리 목록과 기록 탭의 다시 읽기가 더 불러오기·첫 페이지 읽기와 엇갈리는 순서, 화면마다 `useRead`로 바꾼 뒤의 동작, 작품 상세에서 없앤 표지 읽기, 새 테스트의 세기를 봤고, 막는 문제는 찾지 않았어요. 다음을 고쳤고, 리뷰어가 고친 곳을 다시 봤어요.

- 목록 끝에서 더 불러오는 사이 다시 읽기가 먼저 끝나면, 더 불러온 페이지를 버린 뒤 다음 페이지를 다시 청하지 않아 목록이 끝에서 멈출 수 있었어요. 버린 뒤 새 페이지들의 다음을 곧바로 읽게 고쳤어요.
- 규칙 상세와 작품 상세의 자막 제작자 고르기가 규칙 버전을 key로 써서, 작업기가 회차를 올리는 바뀜에 고르던 값이 지워질 수 있었어요. 제작자가 바뀔 때만 다시 시작하게 고쳤어요. 이제 버전만 바뀐 충돌에서는 `다른 곳에서 먼저 바꿨어요` 문구도 남아요.
- 화면이 스스로 값을 쓴 사이 끝난 읽기는 답을 버리기만 해서, 그 읽기를 부른 바뀜이 다음 바뀜까지 화면에 보이지 않을 수 있었어요. 답을 버리면 한 번 더 읽게 고쳤어요. 화면이 쓰는 값은 모두 서버가 답한 뒤의 값이라, 다시 읽어도 옛 값으로 돌아가지 않아요.
- 라이브러리 목록의 첫 페이지를 읽는 동안 온 바뀜을 버렸고, 메뉴로 다시 연 목록에서는 그 사이 끝난 다시 읽기를 더 오래된 첫 페이지가 덮을 수 있었어요. 첫 페이지를 읽는 동안의 바뀜은 첫 페이지가 오거나 실패한 뒤 한 번 읽게 고쳤어요.

고치지 않은 것은 이래요. 화면이 붙어 있는 키를 다른 코드가 버리면 다음 바뀜까지 비어 있어요. `useCached` 때도 같았고, 버리는 곳마다 곧 바뀜이 와요. 직접 누른 `재시도`는 진행 중인 읽기가 끝나기를 기다리고(최대 15초), 그동안 이전 오류 문구가 남아요. 라이브러리 목록의 첫 페이지 읽기에는 0.8.0처럼 시간 제한이 없어서, 그 요청이 멈춘 동안은 목록의 다시 읽기도 미뤄져요.

### 한계

- 다시 읽기는 보이던 만큼을 모두 읽어요. 기록 탭을 5,000행까지 내렸다면 바뀜 하나에 200행씩 25번을 차례로 읽고, 15초 안에 끝나지 않으면 실패로 쳐서 30초 뒤에 다시 해요. 라이브러리 목록은 페이지마다 서버가 할 일 목록도 읽어요. 확인은 92편과 50행으로만 했어요.
- 같은 조회를 함께 보여 주는 두 부분은 바뀜 하나에 그 조회를 따로 읽어요. PC의 설정 화면에서 왼쪽 목록과 오른쪽 공통 정책 화면이 정책을 두 번 읽는 것을 봤어요.
- 다시 읽기를 화면에 잇는 코드(`library/pages.ts`, `HistoryTab.tsx`, 각 화면의 `useRead` 연결)는 웹 테스트가 없어요. 바뀜을 고르는 함수만 테스트하고, 나머지는 개발 환경에서 봤어요.
- 감시 폴더의 `새로 찾음`은 지난 7일을 세는데, 작품이 그 7일을 벗어나는 때는 알리는 바뀜이 없어서 다시 읽지 않아요.
- 열어 둔 채널 편집은 처음 값을 그대로 두므로, 다른 곳에서 그 채널이 바뀌면 저장할 때 충돌로 알게 돼요. 0.8.0과 같아요.
- 작품 상세의 시즌 연결 창을 거쳐 잇는 경우는 다른 창의 API 호출로 대신했어요. 연결 창이 목록 캐시를 버리던 코드는 지웠어요.
- 휴대폰 브라우저에서는 보지 않았어요. iOS 홈 화면 앱은 [0011](0011-deploy-and-check-on-server.md)에서 봐요.
