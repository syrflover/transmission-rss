# 0057 원격 화면에서 페이지의 알림·확인 창에 답해요

- 상태: 완료
- 출처: [작업 화면 안의 인증과 브라우저 수명](../../../specs/jobs.md#작업-화면-안의-인증과-브라우저-수명), 사용자 보고와 결정(2026-10-04)
- 막는 티켓: [0056](0056-remote-screen-stuck-page.md)(입력이 답을 기다리는 동안 소켓이 막히지 않아야 창에 답할 수 있어요)

## 배경

[0056](0056-remote-screen-stuck-page.md)의 재현에서 페이지를 멈춘 것은 페이지 창이었어요(2026-10-04).

- 페이지 창(`alert`·`confirm`·`prompt`·`beforeunload`)은 Chromium이 화면 전송에 그리지 않아요.
- 웹은 원격 화면을 위해 페이지에 `Page.enable`을 켜요. 그러면 Chromium은 창을 DevTools가 답하도록 맡겨요. 하지만 원격 화면에는 창에 답하는 코드가 없어요. 창은 WinPNG 읽기만 닫아요(`Page::dismiss_dialogs`).
- 창이 떠 있는 동안 페이지는 멈춰요. 새로고침은 답하지만 페이지를 다시 읽지 않고, 입력은 답을 받지 못해요.
- 창을 맡은 CDP 연결이 닫혀도 창은 가상 디스플레이(Xvfb)에 남아요. 나중에 붙은 연결은 그 창에 답할 수 없어요(`No dialog is showing`). 그래서 실행이 끝날 때까지 페이지가 멈춰 있었어요.

## 사용자 결정 (2026-10-04)

- 원격 화면 위에 창의 문구와 확인·취소 버튼을 띄워, 브라우저처럼 사람이 골라요.
- 사람이 누른 새로고침·뒤로·앞으로가 부른 떠나기 창은 떠나기로 바로 답해요. 탭 닫기도 이 결정에 들었지만, worker가 탭을 닫는 `Target.closeTarget`은 떠나기 처리기를 부르지 않아요. 그래서 탭 닫기에는 떠나기 창이 뜨지 않아요.

## 정한 방식

- **알리기**: 웹은 보이는 페이지의 `Page.javascriptDialogOpening`·`Page.javascriptDialogClosed`를 읽어 묶음의 소켓에 보내요.
  - 창이 뜨면 `{"type":"dialog","dialog":{"id","kind","message","host","prompt"}}`를 보내고, 닫히면 `{"type":"dialog","dialog":null}`을 보내요.
  - `kind`는 `alert`·`confirm`·`prompt`·`beforeunload`예요. `message`는 1,000자, `prompt`(입력 창의 기본값)는 2,000자까지 잘라요. `host`는 창을 띄운 프레임 주소의 호스트뿐이에요.
  - 새로 붙거나 메시지를 건너뛴 소켓에는 지금 떠 있는 창을 다시 보내요(`nav`·`tabs`와 같아요).
- **답하기**: 기기는 `{"type":"dialog","id","accept","text"}`를 보내요. 웹은 그 `id`가 지금 떠 있는 창일 때만 `Page.handleJavaScriptDialog`로 답해요. `text`는 `prompt`를 확인할 때만 쓰고 2,000자까지예요. 답은 사람의 입력으로 세요. 답은 입력 줄 뒤에서 기다리지 않아요. 창을 띄운 입력이 아직 답을 기다리고 있을 수 있어서예요.
- **떠나기 창 자동 답**: 사람이 보낸 새로고침·뒤로·앞으로 뒤 3초 안에 뜬 `beforeunload`는 웹이 바로 떠나기로 답하고 소켓에 보내지 않아요.
- **창이 떠 있는 동안**: 입력·새로고침·뒤로·앞으로는 페이지로 보내지 않아요. 창이 뜰 때 답을 기다리던 입력은 더 기다리지 않아요. 그 입력은 이미 페이지에 갔고, 페이지가 창이 닫힌 뒤 답하기 때문이에요. 이 기다림은 [0056](0056-remote-screen-stuck-page.md)의 `응답하지 않음`으로 세지 않고, 창이 떠 있는 동안에는 응답 확인도 쉬어요.
- **아무도 보지 않을 때**: 마지막 소켓이 닫혀 묶음의 CDP 연결이 닫힐 때 창이 떠 있으면, 웹이 먼저 그 창을 취소로 답해요. 알림 창은 확인이고, 떠나기 창은 머무르기예요. 답하지 않으면 창이 화면 밖에 남아 페이지가 실행이 끝날 때까지 멈추기 때문이에요. 열린 화면이 없을 때 뜬 창은 웹이 답할 수 없어요. 그때는 0056의 `stuck`과 `새로 띄우기`로 풀어요.
- **문구의 경계**: 창의 문구는 페이지가 사람에게 보여주는 글이에요. 그래서 화면 전송처럼 그대로 보여주고, 로그와 DB에는 남기지 않아요. 프레임 주소는 호스트만 보내요.
- **화면**: 창이 떠 있으면 원격 화면 위에 카드를 띄워요.
  - 제목은 `<호스트>의 메시지`이고, 호스트가 없으면 `이 페이지의 메시지`예요. 문구는 줄바꿈을 지키고, 길면 카드 안에서 스크롤해요.
  - `alert`는 `확인`, `confirm`은 `취소`·`확인`, `prompt`는 입력칸과 `취소`·`확인`이에요.
  - `beforeunload`는 문구 대신 `이 페이지를 떠날까요? 입력한 내용이 저장되지 않을 수 있어요.`와 `머무르기`·`떠나기`예요.
  - 창이 떠 있는 동안 도구 줄과 탭 줄은 누를 수 없어요.

## 완료 기준

| 입력·상태 | 기대 결과 |
| --- | --- |
| 페이지가 `alert`를 띄움 | 화면에 문구와 `확인`이 떠요. 누르면 창이 닫히고 페이지가 이어서 돌아요. |
| 클릭 처리기가 `confirm`을 띄움 | 화면이 끝나거나 `응답하지 않음`이 되지 않아요. `취소`와 `확인`이 페이지에 각각 `false`와 `true`로 가요. |
| `prompt` | 입력한 글이 페이지에 가요. 취소하면 `null`이에요. |
| 사람이 누른 새로고침이 `beforeunload`를 부름 | 창을 묻지 않고 페이지가 새로 읽혀요. |
| 페이지 스스로의 이동이 `beforeunload`를 부름 | 화면에 `머무르기`·`떠나기`가 떠요. |
| 창이 떠 있는 동안 새로 붙은 소켓 | 지금 떠 있는 창을 받아요. |
| 다른 `id`의 답 | 무시해요. |
| 창이 떠 있는 채로 마지막 화면을 닫음 | 창이 취소로 답해지고, 다시 연 화면이 페이지에 붙어요. |
| 소켓 메시지·로그 | 프레임 주소의 경로·쿼리가 없어요. 창의 문구는 로그에 없어요. |
| 실제 서버 브라우저 이미지 | 위 동작이 실제 Chromium에서 돼요. |
| 휴대폰 폭(375px) | 카드와 버튼이 가로 스크롤 없이 들어가요. |

## 결과 (2026-10-04)

정한 방식대로 구현했어요.

- 웹(`trss-web`의 `screen_api`·`screen_api/hub`)은 창이 뜨고 닫히는 이벤트를 `dialog` 메시지로 보내요. 소켓의 답은 입력 줄을 거치지 않고 `Page.handleJavaScriptDialog`로 가요.
- 사람의 새로고침·뒤로·앞으로 뒤 3초 안에 뜬 떠나기 창에는 웹이 바로 답해요.
- 창이 떠 있는 동안 입력·새로고침·단계는 보내지 않고, 크기는 미뤄요. 창을 띄운 입력은 창이 뜨면 기다림을 끝내요.
- Hub가 닫힐 때 떠 있는 창은 취소로 답해요.
- 화면(`PageDialogCard`)은 창의 카드를 원격 화면 위에 띄워요. 창이 떠 있는 동안 도구 줄과 탭 줄은 누를 수 없어요.

정한 방식에 없던 것을 더했어요. 모두 [작업 명세](../../../specs/jobs.md#작업-화면-안의-인증과-브라우저-수명)의 페이지 창 문단에 적었어요.

- 창이 닫히면, 창이 뜨기 전에 눌린 채 남은 버튼·손가락을 놓아요(`mouseReleased`·`touchCancel`). 누르기가 창을 띄우면, 그 떼기는 창이 떠 있는 동안 와서 페이지로 가지 않기 때문이에요. 창이 닫힌 뒤 새로 누른 것은 놓지 않아요.
- 리뷰에서 나온 것(아래) 네 가지예요.
  - 페이지가 사람의 답을 거절하면(`No dialog is showing`), 웹이 닫힘을 놓친 것으로 보고 창을 닫힌 것으로 다뤄요.
  - 창이 떠 있는 동안에는 답이 늦은 명령이 `응답하지 않음`을 만들지 않아요.
  - 브라우저가 거절한 뒤로·앞으로는 3초 자동 떠나기를 열지 않아요.
  - 한 창에 대한 사람의 답은 한 번에 하나만 보내요.

검증한 것이에요.

| 완료 기준 | 근거 |
| --- | --- |
| `alert` | 가짜 브라우저 시험 `a_dialog_left_open_by_the_last_screen_is_dismissed_and_the_page_opens_again`과 실제 이미지에서 알림이 화면에 왔어요. 실제 이미지에서 알림이 닫힌 뒤 페이지가 답했어요. 화면에서 알림 카드의 `확인`을 눌러 답이 가는 것은 따로 보지 않았어요. 그 버튼은 확인 창의 `확인`과 같은 답을 보내요. |
| 클릭 처리기의 `confirm` | `a_click_that_asks_to_confirm_shows_the_dialog_and_the_persons_answer_goes_to_the_page`. 창이 열릴 때 입력의 기다림을 끝내는 부분을 빼면 이 시험이 `responding:false`로 실패하는 것을 확인했어요. 실제 이미지에서 탭이 연 확인 창이 7초 동안 `응답하지 않음`·끝 없이 떠 있었고, `확인`이 페이지에 `true`로 갔어요. 확인 창의 `취소`가 페이지에 `false`로 가는 것은 실제 Chromium에서 보지 않았어요. 같은 `accept:false` 답은 입력 창 취소 시험과 실제 이미지의 `머무르기`에서 봤어요. |
| `prompt` | `a_prompt_gets_the_persons_text_and_a_long_message_is_cut`: 확인하면 글이 가고, 취소하면 글 없이 `accept:false`예요. 실제 이미지에서 페이지가 입력한 글을 받았어요. 취소의 `null`은 실제 이미지에서 보지 않았어요. |
| 사람의 새로고침이 부른 떠나기 창 | `a_beforeunload_of_the_page_itself_is_asked_and_one_after_a_persons_reload_is_left_at_once`. 실제 이미지에서 화면에 창 메시지 없이 페이지가 새로 읽혔어요. 시험 쪽 CDP 연결은 그 사이 `Page.reload`가 떠나기 창을 띄웠고 웹이 떠나기(`result:true`)로 답한 것을 봤어요. |
| 페이지 스스로의 이동이 부른 떠나기 창 | 같은 시험. 실제 이미지에서 페이지의 `location.reload()`가 부른 창이 화면에 왔고, `머무르기`로 페이지가 머물렀어요. |
| 창이 떠 있는 동안 새로 붙은 소켓 | 확인 창 시험에서 두 번째 소켓이 떠 있는 창을 받았어요. |
| 다른 `id`의 답 | 같은 시험에서 무시됐어요. |
| 창이 떠 있는 채로 마지막 화면을 닫음 | 가짜 브라우저 시험과 실제 이미지 모두 창이 취소로 닫혔고, 다시 연 화면이 붙었으며 페이지가 답했어요. 가짜 브라우저는 실제처럼 창을 연결이 아니라 페이지에 남겨요. 그래서 닫기 답을 빼면 다시 연 화면이 붙지 못해 시험이 실패해요(변이로 확인). |
| 소켓 메시지·로그 | 실제 이미지 시험의 소켓 메시지 22개에 경로·쿼리·조각이 없었어요(창의 문구와 입력 기본값은 페이지의 글이라 빼고 봤어요). 창의 문구를 남기는 로그 코드는 없어요. |
| 휴대폰 폭(375px) | 가짜 소켓 서버에 붙인 화면을 앱 안 브라우저의 375px 크기 흉내로 봤어요. 확인·입력·떠나기 카드가 가로 스크롤 없이 들어갔고, 긴 문구는 카드 안에서 스크롤됐어요. 답은 `{"id","accept"}`(입력 창은 `text`도)로 갔어요. |

더한 동작의 시험이에요. 각 시험은 해당 코드를 되돌리면 실패하는 것을 확인했어요.

- `a_press_that_opens_a_dialog_is_let_go_once_it_closed`: 창을 띄운 누르기는 창이 닫힌 뒤 클릭 없이 놓여요.
- `a_closed_dialog_lets_go_only_of_what_went_down_before_it_opened`(hub 단위 시험): 창이 닫힌 뒤 새로 누른 버튼·손가락은 그 창의 놓기에 들지 않고, 크기 변화는 모두 놓아요. 놓기 작업보다 새 누르기가 먼저 입력 잠금을 잡는 순서는 시간에 달려 있어서, 그 판단을 떼어 시험해요.
- `a_dialog_whose_close_was_missed_is_closed_when_the_persons_answer_is_refused`
- `a_command_a_dialog_holds_up_is_not_a_page_that_does_not_answer`
- `a_dialog_ends_a_stall_and_the_size_kept_meanwhile_is_applied_once_it_closed`(변이 확인은 하지 않았어요. 이미 있던 동작을 덮는 시험이에요.)

## 리뷰 (2026-10-04)

독립 리뷰(stora:complex-reviewer)는 막는 결함이 없다고 봤어요. 크기·응답 없음·입력 잠금의 불변식은 지켜지고, hub가 끝나는 모든 길에서 창을 닫는다고 했어요.

고친 것이에요.

- 닫힘 이벤트를 놓치면 화면이 창에 묶여 풀리지 않을 수 있었어요(P2). 사람의 답이 거절되면 창을 닫힌 것으로 다뤄요.
- 창이 뜨기 직전에 보낸 새로고침의 답이 늦으면 창이 떠 있는데 `응답하지 않음`이 될 수 있었어요(P3). 창이 떠 있으면 응답 없음으로 바뀌지 않아요.
- 창이 닫힌 뒤의 놓기가 그 사이 새로 누른 것을 끊을 수 있었어요(P3). 창이 뜨기 전에 눌린 것만 놓아요.
- 브라우저가 거절한 단계도 3초 자동 떠나기를 열었어요(P3). 거절되면 닫아요.
- 사람의 답마다 작업을 제한 없이 띄웠어요(P3). 한 창에 대한 답은 한 번에 하나만 보내요. 처음에는 모든 창에 잠금 하나를 두었는데, 재확인에서 앞 창의 늦은 답이 새 창의 답을 막을 수 있다고 나와 창 번호마다 잠그도록 바꿨어요.
- 시험 두 개가 이름보다 덜 증명했어요. 가짜 브라우저는 창을 연결마다 잊어서, 닫기 시험의 뒤쪽 절반이 실패할 수 없었어요. 이제 창을 페이지에 남겨요. 실제 이미지 시험은 사람의 새로고침이 떠나기 창을 띄웠는지 보지 않았어요. 이제 시험 쪽 연결로 그 창과 답을 봐요.

두고 기록한 것이에요.

- 같은 페이지의 다른 hub가 창을 닫을 수 있어요(P3). 두 소켓이 동시에 hub를 열어 남는 쪽이 버려지거나, 같은 페이지가 새 묶음으로 다시 묶이는 좁은 순간에 버려지는 hub가 그 창을 봤다면, 그 hub가 닫히며 사람이 답하려는 창을 취소로 닫아요. 남은 hub가 그 닫힘을 받는지는 확인하지 않았어요. 받지 못해도 사람이 카드에 답하면 거절되어 카드가 거둬져요.
- 답한 뒤 카드가 사라지면 초점이 페이지 본문으로 가요. 원격 페이지에 글을 치던 사람은 `키보드`를 다시 눌러야 해요.

재확인: 같은 리뷰어가 고친 것을 다시 봤어요. 닫힘을 놓친 창의 처리가 새 창을 지우거나 두 번 놓지 않는 것, 응답 없음 막기와 순서 바꾸기가 경쟁을 닫는 것, 누른 시점 기록, 답 잠금이 풀리지 않고 남는 길이 없는 것, 새 시험이 이름대로 닿는 것을 확인했어요. 재확인에서 나온 두 가지(누르기 시험 뒤쪽 절반이 실패할 수 없음, 답 잠금이 창 사이에 공유됨)는 위처럼 고쳤어요. 이 마지막 두 고침은 다시 리뷰받지 않았어요.

확인하지 않은 것이에요.

- 실제 휴대폰과 개발 환경의 실제 사이트에서는 확인하지 않았어요. 같은 날 뒤에 한 휴대폰 확인(아래)의 창은 넣은 스크립트가 띄웠어요. 실제 사이트가 스스로 띄운 창은 보지 않았어요.
- 거절된 뒤로·앞으로 뒤의 떠나기 창, 사람의 새로고침 뒤 3초가 넘어 뜬 떠나기 창은 시험하지 않았어요.
- 렌더러가 죽거나 이동이 취소될 때 Chromium이 닫힘 이벤트를 보내는지는 보지 않았어요. 보내지 않아도 사람의 답이 거절되면 풀려요.
- 열린 화면이 없을 때 뜬 창은 웹이 답하지 못해요. 그때는 0056의 `stuck`과 `새로 띄우기`로 풀어요.

## 휴대폰 확인 (2026-10-04)

개발 환경(`9235d43`에서 지은 이미지, LAN 주소로 연 웹)에서 사용자가 아이폰으로 직접 찾기 작업(코코렛, `felia.tistory.com`의 게시물)의 원격 화면을 썼어요. 실제 사이트는 창을 띄우지 않아요. 그래서 별도 CDP 연결로 페이지에 창을 띄우는 스크립트를 넣었어요. 페이지가 받은 답과 페이지 안의 창 이벤트도 그 연결로 읽었어요.

| 확인 | 결과 |
| --- | --- |
| 확인 창 | 사람이 `확인`을 누르자 페이지가 `true`를 받았어요. 카드의 제목·두 줄 문구와, 카드가 떠 있는 동안 도구 줄이 막히는 것도 사용자가 이상 없다고 알렸어요. |
| 입력 창 | 아이폰 기본 키보드로 한글을 입력하자 페이지가 그 글을 그대로 받았어요. |
| 알림 창 | `확인`을 누르자 창이 닫히고 페이지가 이어서 돌았어요. |
| 사람의 새로고침이 부른 떠나기 창 | 본문을 탭한 뒤 새로고침하자 페이지 안에서 떠나기 창이 떴어요. 같은 초에 웹이 `떠나기`(`true`)로 답했고, 휴대폰에는 카드가 뜨지 않았어요. 탭하지 않고 새로고침한 첫 시도에는 Chromium이 떠나기 창을 띄우지 않았어요. |
| 페이지 스스로의 이동이 부른 떠나기 창 | 탭 1초 뒤 페이지가 스스로 새로고침하게 하자 떠나기 창이 화면에 왔어요. 8초 뒤 사람의 `머무르기`(`false`)로 페이지가 남았어요. 카드의 문구와 `머무르기`·`떠나기`도 사용자가 이상 없다고 알렸어요. |

원격 화면의 터치는 Chromium에서 사람의 조작(user activation)으로 쳐져요. 떠나기 창이 본문을 탭한 뒤에만 뜬 것이 그 근거예요.
