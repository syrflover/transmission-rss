# 0032 서버 브라우저의 원격 화면과 창 크기를 확인해요

- 상태: 완료
- 출처: [작업 화면 안의 인증과 브라우저 수명](../../../specs/jobs.md#작업-화면-안의-인증과-브라우저-수명), [인증 운영 ADR](../../../adr/0002-server-browser-subtitle-authentication.md), [작업과 인증 명세의 남은 구체화](../../../specs/jobs.md#남은-구체화)
- 막는 티켓: 없음

## 작업

제품을 만들기 전에 확인할 일이에요. 결과 목표 3의 알려진 불확실성 가운데 서버 Chromium 창 크기를 다루고, 원격 화면을 어떤 방식으로 전할지도 함께 정해요.
`.scratch/`의 임시 실행물에서 확인하고, 제품 코드나 의존성은 바꾸지 않아요.

지금 근거는 2026-09-26의 실험이에요. Selenium 기반 실행에서는 Turnstile이 실패했고(`600010`), 같은 이미지에서 Chromium을 직접 실행하고 CDP로 연결했을 때는 사용자가 인증한 뒤 서버가 파일을 받았어요([서버 브라우저 임시 검증](../../../brainstorm/web-gui-subtitles.md#서버-브라우저-임시-검증)).

- 제품과 같은 배치(앱과 분리한 Chromium 컨테이너, CDP 직접 제어, 실행마다 새 프로필)를 꾸려요.
- 원격 화면 방식 두 가지를 비교해요. 하나는 가상 디스플레이와 VNC를 noVNC로 페이지에 붙이는 방식이고, 다른 하나는 CDP의 화면 전송과 입력 전달이에요. erulabo의 Turnstile을 사용자가 각 방식으로 직접 풀 수 있는지, LAN에서 조작이 쓸 만한지, 컨테이너의 CPU·메모리 사용량을 봐요.
- 휴대폰(390×844)에서 열었을 때 원격 페이지가 휴대폰 배치로 보이게 하는 방법을 비교해요. 하나는 창 크기 바꾸기이고, 다른 하나는 기기 지표 흉내(폭·기기 픽셀 비율·모바일 여부)예요. 그 방법이 Turnstile 통과에 영향을 주는지, 크기를 바꿔 다시 그리는 동안 입력이 섞이지 않게 막을 수 있는지 확인해요.
- 결과로 아래를 정해 [작업과 인증 명세의 남은 구체화](../../../specs/jobs.md#남은-구체화)를 갱신해요. 원격 화면 방식, 기기 폭에 맞추는 기준(보고하는 화면 폭, 기기 픽셀 비율), 두 기기가 같은 작업을 열었을 때 따를 크기, 컨테이너 자원 한도의 시작값이에요. 바뀐 방향이 ADR 0002의 후보(noVNC)와 다르면 ADR을 고쳐요.
  어느 방식도 인증을 통과하지 못하거나 휴대폰 배치와 인증 통과가 양립하지 않으면, 사용자가 정할 선택으로 올려요.

## 결과

2026-10-02에 이 개발 PC의 LAN과 사용자의 실제 휴대폰 한 대로 확인했어요. 근거와 수치는 [원격 화면 비교](../../../brainstorm/web-gui-subtitles.md#2026-10-02-원격-화면과-기기-폭-비교)에 있어요.
erulabo 인증은 매번 사용자가 직접 풀었고, 우회·위장 스크립트는 쓰지 않았어요.

| 확인 | 결과 |
| --- | --- |
| 두 원격 화면 방식의 인증과 수신 | CDP 화면 전송(PC·휴대폰)과 noVNC(PC·휴대폰) 모두 사용자가 Turnstile을 풀고 서버 다운로드 폴더에 ZIP(13,673·12,267바이트)이 생겼어요. noVNC는 데스크톱 창 전체가 축소돼 보여 누르기 매우 불편했고, 사용자는 CDP 화면 전송을 골랐어요. 헤드리스 Chromium은 erulabo가 연결을 끊어 쓸 수 없어요. |
| 실제 휴대폰의 기기 폭 | 기기 지표 흉내로 휴대폰이 보고한 402×666(DPR 3) 배치가 정확히 나왔어요. 창 크기 바꾸기는 일반 창이 약 500px 밑으로 줄지 않았어요. 게시물 그대로는 인증 상자가 첫 화면 밖이었고, 서버가 카드를 가운데로 스크롤한 뒤 누르자 첫 화면 안에 있었어요(사용자 확인). |
| PC에서 열던 작업을 휴대폰에서 다시 엶 | 크기가 139ms에 바뀌었고, 바뀌는 동안과 이전 프레임 기준의 입력은 버려졌으며 엉뚱한 자리로 간 입력은 없었어요. |
| 자원 | 1배·광고 차단·메모리 한도 768MiB에서 사람이 인증해 받았어요. 메모리 최고 585MiB, CPU 중앙값 0.2%·최고 142%, OOM 없음이에요. 2배는 메모리 최고 1,249MiB였어요. |
| 명세 | [작업과 인증 명세](../../../specs/jobs.md#작업-화면-안의-인증과-브라우저-수명)와 [ADR 0002](../../../adr/0002-server-browser-subtitle-authentication.md)를 고쳤어요. 검증하지 못한 조합은 [남은 구체화](../../../specs/jobs.md#남은-구체화)에 있어요. |

정한 것이에요.

- 원격 화면은 CDP 화면 전송과 입력 전달이에요(사용자 결정). VNC 서버·창 관리자는 두지 않아요.
- 렌더링 배율은 1배예요(사용자 결정). 휴대폰에서 덜 선명한 대신 메모리를 덜 써요.
- 인증 상자는 첫 화면에 바로 보여야 해요(사용자 요구). 서버가 정상 다운로드 시작 요소를 가운데로 스크롤한 뒤 눌러요.
- 기기 지표 흉내로 화면을 연 기기의 크기·DPR·터치를 따르고, 두 기기가 열면 마지막으로 연 기기를 따라요.
- 서버 브라우저는 광고·추적 주소를 막고, 컨테이너 메모리 한도 시작값은 768MiB예요.

남은 것이에요.

- 사용자는 원격 화면의 스크롤이 부드럽지 않다고 했어요. 인증에는 필요 없고, 직접 찾기(0046)에서는 부드러우면 좋지만 필수는 아니에요.
- erulabo의 실제 파일은 Google Drive 주소로 왔고, 855는 두 실행에서 같은 Drive ID였어요. 제작자가 수정본을 같은 파일에 덮어쓰는지 몰라서, 인증 수신 때의 ID와 14일 재확인의 `HEAD`를 관찰로 쌓아 정하기로 했어요(0041·0050).
- 다른 휴대폰, VPN·HTTPS(WSS) 경로, LAN 지연, 휴대폰 가상 키보드, CPU 한도는 확인하지 않았어요. 제품 이미지(Selenium 이미지 대신)에서의 인증은 0039에서 다시 확인해요.
