# 0053 서버 브라우저가 LAN에 닿지 못하게 하고, 웹이 다른 출처의 요청을 거절해요

- 상태: 완료
- 출처: [작업 화면 안의 인증과 브라우저 수명](../../../specs/jobs.md#작업-화면-안의-인증과-브라우저-수명), [접근 경계와 기기](../../../specs/web-app.md#접근-경계와-기기), [0039의 한계](0039-browser-container-lifecycle.md#한계)
- 막는 티켓: 없음

## 배경

서버 브라우저는 사용자가 고른 외부 게시물과 그 페이지의 스크립트를 LAN 안의 서버에서 실행해요. 0039는 브라우저를 `trss_net`에서 떼어 `browser_net`에 뒀지만, `browser_net`은 bridge라서 호스트의 LAN 주소에 게시된 포트에 닿아요(0039의 한계).

2026-10-03에 개발 환경에서 확인했어요. `browser_net`에 붙인 컨테이너에서 호스트 LAN 주소(`192.168.1.116:9091`)와 Docker 게이트웨이의 Transmission이 `200`으로 답했어요. 같은 경로로 `trss_net`의 컨테이너에 연결하면 받는 쪽에는 출발 주소가 `trss_net` 게이트웨이(`172.19.0.1`)로 보였어요. 그래서 받는 쪽이 출발 주소로 `browser_net`을 가려낼 수 없어요. 운영에서는 trss-web이 LAN 주소 `:8080`에, Transmission이 `9091`에 게시돼 있어요.

trss-web은 로그인이 없고 Host·Origin을 검사하지 않아요. 다른 출처의 페이지는 응답을 읽지 못하고 JSON 본문 요청도 쉽게 보내지 못하지만, 공격자 도메인을 LAN 주소로 풀리게 하는 DNS 재바인딩이면 웹 API를 모두 쓸 수 있어요. 이 경로는 서버 브라우저뿐 아니라 사용자의 PC·휴대폰 브라우저로도 열려요.

## 작업

두 겹으로 막고, 다음 릴리스 전에 끝내요(사용자 결정, 2026-10-03). 0040보다 먼저 해요.

- **브라우저의 송신 제한**: 서버 브라우저의 모든 연결이 실행기(`trss-browserd`) 안의 프록시를 거쳐요. 프록시는 이름을 풀어 본 뒤 그 주소로 연결하고, 사설·루프백·링크 로컬·CGNAT(Tailscale 포함)·멀티캐스트·예약 주소(IPv4·IPv6, IPv4 대응 IPv6 포함)로 가는 연결을 거절해요. 풀린 주소로 판정하므로 DNS 재바인딩도 막혀요. Chromium이 루프백을 프록시 없이 보내는 기본 예외를 없애고, 프록시 밖 UDP(WebRTC)를 쓰지 않게 해요. 거절은 연결 단위의 오류이고, 거절한 목적지 주소나 URL은 로그에 남기지 않아요.
- **웹의 출처 검사**: trss-web은 Host가 허용 목록에 없는 요청을 모두 거절해요. IP 주소와 `localhost`는 설정 없이 허용하고, 이름은 `.env`의 허용 목록에 적은 것만 받아요. 사용자는 지금 LAN IP:포트로 들어가요. 상태를 바꾸는 요청과 WebSocket 연결은 Origin이 있으면 요청 자신의 출처와 같아야 하고, `null`은 거절해요. WebSocket은 Origin이 반드시 있어야 해요.
- 호스트 방화벽 규칙은 앱이 확인할 수 없어서 필수로 두지 않고, 배포 설명에 덧붙이는 선택 방어로 적어요.
- 0040에서 정한 'browser_net에서 온 연결 거절'은 그대로 둬요. 이 티켓은 호스트 LAN 주소를 거치는 경로를 막아요.

## 완료 기준

| 입력·상태 | 기대 결과 |
| --- | --- |
| 실제 서버 브라우저 이미지에서 호스트 LAN 주소, Docker 게이트웨이, 루프백(실행기 포트 포함), 사설 주소로 풀리는 이름으로 이동·`fetch`·WebSocket | 모두 연결되지 않아요. |
| 같은 실행에서 공개 HTTPS 사이트를 엶 | 열려요. 실제 Tistory 게시물의 WinPNG 읽기(0043)가 그대로 돼요. |
| 이름이 처음엔 공개 주소, 다음엔 사설 주소로 풀림 | 사설 주소로 풀린 연결은 거절돼요. |
| 허용 목록에 없는 Host로 웹에 요청(API·화면) | 거절돼요. IP 주소와 `localhost`는 받아요. |
| 다른 Origin·`null` Origin의 상태 변경 요청과 WebSocket | 거절돼요. 같은 출처의 웹 화면은 그대로 동작해요. |
| 개발 환경 전체 흐름 | 웹 화면을 `localhost:8080`으로 쓸 수 있고, 개발 환경의 가짜 출처와 WinPNG 작업이 그대로 돼요. |

## 결과

### 만든 것 (2026-10-03)

- **송신 프록시**: 실행기(`trss-browserd`)가 컨테이너 루프백에 프록시를 띄우고, Chromium의 모든 연결이 이 프록시를 거쳐요. 프록시는 이름을 직접 풀어요. 풀린 주소 가운데 하나라도 공개 주소가 아니면 연결하지 않고, 통과하면 다시 풀지 않고 그 주소로 연결해요. 실행기가 시작할 때 컨테이너의 라우팅 표에서 읽은 자기 네트워크와 게이트웨이도 거절해요. 규칙 전체는 [작업 화면 안의 인증과 브라우저 수명](../../../specs/jobs.md#작업-화면-안의-인증과-브라우저-수명)에 있어요.
- **프록시 밖 길 닫기**: 루프백 예외를 없애고(`<-loopback>`), QUIC을 끄고, WebRTC가 프록시 밖 UDP를 쓰지 않게 해요. 이미지의 관리 정책에도 같은 설정을 넣었어요. `TRSS_BROWSER_CHROMIUM_ARGS`에 프록시·QUIC·WebRTC·`host-rules` 계열 인자가 있으면 실행기가 시작하지 않아요. Debian 래퍼가 읽는 `CHROMIUM_FLAGS`·`CHROMIUM_USER_FLAGS`는 Chromium 환경에서 빼요.
- **웹의 Host·Origin 검사**: 모든 경로(화면 파일·`/api`·WebSocket)에서 Host가 IP 주소, `localhost`, `TRSS_WEB_HOSTS`의 이름일 때만 답해요(그 밖은 `421`). 상태를 바꾸는 요청과 WebSocket은 다른 Origin, `null`, `Sec-Fetch-Site: cross-site`를 `403`으로 거절해요. 규칙과 scheme을 견주지 않는 이유는 [접근 경계와 기기](../../../specs/web-app.md#접근-경계와-기기)에 있어요.
- 거절 로그에는 목적지·주소를 남기지 않고, 횟수만 1분에 한 번까지 남겨요.
- 시험 호스트에 사이트를 띄우는 기존 실제 이미지 시험을 위해 `TRSS_BROWSER_EGRESS_ALLOW`(정확한 `IP:포트`)를 뒀어요. compose와 개발 환경에는 없고, compose 시험이 이를 지켜요.

### 검증한 것

| 완료 기준 | 근거 |
| --- | --- |
| LAN 주소·게이트웨이·루프백·사설로 풀리는 이름으로 이동·`fetch`·WebSocket | 실제 이미지 시험 `the_browser_reaches_public_addresses_only`(2026-10-03, Chromium 154.0.8037.92)에서 모두 거절됐어요. 대상은 호스트 LAN 주소 192.168.1.116, Docker 게이트웨이 172.17.0.1, 공개 대역으로 분류되는 시험 네트워크(11.255.53.0/24)의 게이트웨이, 169.254.169.254, 100.100.100.100, `host.docker.internal`, LAN 주소로 풀리는 이름, 실행기(127.0.0.1·localhost·[::1]·컨테이너 자기 주소의 9230)예요. WebRTC 후보는 0개였고 WebTransport는 실패했으며, 호스트에 TCP 연결과 UDP 데이터그램이 하나도 오지 않았어요. 컨테이너에 `CHROMIUM_FLAGS=--no-proxy-server`를 줘도 같았어요. 이전 이미지(0043)로 같은 시험을 돌리면 35개 탐침이 통과해서, 시험이 새는 것을 잡는다는 것도 확인했어요. |
| 공개 HTTPS 사이트, WinPNG 읽기 | 같은 시험에서 `https://example.com`이 200, `wss://ws.postman-echo.com/raw`가 열렸고 하느 763 게시물이 열렸어요. WinPNG 표본 시험(762·763, 그림·읽을 수 없는 이미지)도 이 이미지에서 통과했어요. 기존 실제 이미지 시험(쿠키·광고 차단·다운로드·초기화)도 통과했어요. |
| 처음엔 공개, 다음엔 사설로 풀리는 이름 | 단위 시험(이름 풀기 대역)에서 두 번째 연결이 거절되고 사이트는 연결을 한 번만 받았어요. 실제 DNS로는 확인하지 않았어요. |
| 허용 목록에 없는 Host | 단위 시험과 개발 환경(2026-10-03): `evil.example` Host는 `421`, `localhost`·`127.0.0.1`은 `200`이었어요. |
| 다른 Origin·`null` Origin, WebSocket | 단위 시험(Origin 없는 WebSocket 포함). 개발 환경에서 다른 Origin의 POST는 `403`, 같은 Origin의 POST는 통과했어요. |
| 개발 환경 전체 흐름 | `dev/compose.sh up` 뒤 `localhost:8080`의 할 일 화면이 열리고 API가 답했어요. |

최종 코드(2026-10-03)에서 `cargo fmt --check`, `cargo clippy --workspace --all-targets -D warnings`(경고 0), `cargo test --workspace`(2,093개 통과, 실패 0, 무시 4)가 통과했고, 그 코드로 다시 만든 개발 환경에서 위 Host·Origin 결과를 다시 확인했어요. 실제 이미지 시험은 리뷰 수정 뒤의 이미지에서 돌린 결과예요.

### 독립 리뷰

송신 프록시의 우회 경로, 주소 표, Chromium의 프록시 밖 길, 웹 검사의 범위를 두고 리뷰를 받았어요. 막는 결함은 없었고 아래를 고쳤어요.

| 지적 | 처리 |
| --- | --- |
| 공개 대역으로 분류되는 Docker 주소 풀·IPv6 `browser_net`에는 닿음 | 컨테이너 자신의 네트워크와 게이트웨이를 라우팅 표에서 읽어 거절해요. hairpin NAT는 한계로 적었어요 |
| 포트 없는 Host는 Origin scheme의 기본 포트로 봄 | 이유와 함께 명세에 적었어요(같은 호스트의 서버만 그런 페이지를 낼 수 있어요) |
| 첫 주소가 응답하지 않으면 다음 주소를 못 씀 | 주소마다 15초 |
| `host-rules` 계열 인자와 래퍼의 환경 변수로 프록시를 끌 수 있음 | 인자를 거절하고 환경 변수를 빼요 |
| 느린 DNS가 차단 스레드를 쌓음 | 이름 풀기는 한 번에 8개까지 |
| 쓰지 않는 시간 한도 설정 | 실패 종류(이름 없음·닿지 않음·시간 초과) 시험에 써요 |
| iptables 예시의 순서 설명 | 고쳤어요 |

### 한계

- 공유기의 WAN 주소나 그 주소를 가리키는 사용자 도메인으로 들어가 LAN으로 돌아오는 경로(hairpin NAT)는 프록시가 공개 주소로 봐서 막지 못해요.
- 앞단 프록시가 Host를 자기 upstream 주소로 바꾸면 웹의 Host 검사가 쓸모없어져요. 배포 요구로 적었고 앱이 알아낼 수는 없어요.
- iptables 예시와 실제 앞단 프록시 뒤 배포는 확인하지 않았어요.
