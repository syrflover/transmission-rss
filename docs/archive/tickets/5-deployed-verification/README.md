# 결과 목표 5. 실제 배포 검증

이 목표는 2026-10-08에 닫았어요. 완료 기록(관찰한 것, 대신 확인한 것, 남은 것)은 [티켓 목록의 목표 5](../../../tickets/README.md#5-실제-배포-검증)에 있어요. 아래는 이 목표를 진행하는 동안 티켓 목록에 있던 범위, 진행과 티켓이에요.

목표 1–4로 만든 것을 실제 서버에 올리고, 실제 배포 경로·재생기·기기에서 확인해요.
이 배포에서 확인한 동작은 뒤의 [리팩터링](../../../tickets/README.md#목표-5와-6-사이의-리팩터링)이 동작을 바꾸지 않았는지 견줄 기준선이 돼요.
원래 목표 5에 있던 앱 YAML 내보내기·가져오기는 리팩터링 뒤의 [목표 6](../../../tickets/README.md#6-앱-yaml-내보내기와-가져오기)으로 옮겼어요(사용자 결정, 2026-10-07).

- 실제 서버 배포와 1000:1000 전환([구현 경계와 실행 순서](../../../specs/web-app.md#구현-경계와-실행-순서)), 운영 안내
- [실제 배포의 접근 보호](../../../specs/web-app.md#접근-경계와-기기)와 실제 기기의 주요 흐름
- 실제 서버에서 구독부터 자막 적용까지([검증 근거와 완료 판정](../../../specs/web-app.md#검증-근거와-완료-판정))
- [실제 재생 환경](../../../specs/subtitles.md#실제-재생-환경)의 세 재생기

배포하기 전에 workspace 테스트를 musl 대상으로도 돌려요([테스트 나눔 ADR](../../../adr/0015-test-a-rule-once-in-its-crate.md)).
2026-10-07 구조 조사에서 동작이 바뀌는 결함을 찾았어요. 리팩터링은 동작을 바꾸지 않으므로, 작은 것은 배포하기 전에 따로 고쳐요(0086–0089). trname이 세 자리 회차와 `.5` 회차를 잘못 읽는 것도 실제 릴리스 이름 묶음을 만든 뒤 trname에서 고쳐요(0090·0091). 사용자가 만든 trname을 고쳐도 된다고 했어요(사용자 결정, 2026-10-07).
fsync를 하지 않는 파일 이름 바꾸기는 미디어 디스크에 비용이 생기므로, 리팩터링에서 파일 쓰기를 모을 때 정해요.
배포 전의 티켓 0079, 0080, 0086–0091, 0116과 목표 4의 [0060](../../../tickets/0060-server-filesystem-probe.md)(서버 미디어 디스크의 파일 쓰기)을 마치고, 2026-10-07에 0.6.0을 실제 서버에 올렸어요(0081). musl 테스트가 느린 원인을 분석하다 운영 앱의 메모리 할당기도 측정했고, musl의 malloc을 그대로 쓰기로 했어요(0116, 사용자 결정, 2026-10-07).
0082, 0084, 0085는 2026-10-07에 끝났어요. 0084는 Infuse만 보고 사용자 결정으로 닫았고, IINA와 팟플레이어, 폰트, 여러 형식, 다시 읽기는 관찰하지 않았어요. 0085는 사용자 확인으로 닫았고, 원격 페이지의 키보드 입력은 확인하지 않은 것으로 남겼어요. 남은 0083은 Kurumi-chan 2화(2026-10-08 방영)를 기다리지 않고, 이미 있는 회차와 로컬 개발 환경으로 대신 확인해 2026-10-08에 닫았어요(사용자 요청).
목표 4의 [0065](../../../tickets/0065-archive-extraction.md)(압축 해제의 서버 측정)는 이 목표를 막지 않아요.
0083에서 실제 서버의 작품 상세가 trss가 적용한 자막까지 `제작자 알 수 없음`으로 세는 결함을 찾았어요(0118). 이 목표의 확인을 마친 뒤 고쳐 0.6.1로 올리고, 그다음 리팩터링의 0092를 시작해요(사용자 결정, 2026-10-07).
보관본을 고르는 화면과 작업의 결함도 찾았어요. 회차 줄에서 적용해도 화면이 바로 바뀌지 않아요(0119). 자막이 있는 회차의 줄에 보관본과 `교체 비교`가 없어요(0120). 현재 자막과 바이트가 같은 보관본은 골라도 `교체 비교`가 남아요(0121). 교체하며 들인 보관본을 다시 고를 수 없어요(0122). 모두 0118과 함께 고쳐 0.6.1에 넣어요(사용자 결정, 2026-10-07).
보관 폴더에 있는 작품의 규칙이 수집을 시작하면 작품 폴더를 통째로 수집 폴더로 옮기는 기능(0123)도 0.6.1에 넣어요. 속편을 구독하면 작품이 두 감시 폴더로 나뉘던 것을 막아요(사용자 결정, 2026-10-07).
0118–0123은 2026-10-08에 구현했어요. 0121·0122와 0123은 독립 리뷰를 거쳐 고쳤고, 0123은 리뷰 뒤 수집 주기와 `받기`가 받기 직전에도 보관 폴더를 확인하게 했어요(사용자 결정, 2026-10-08). 2026-10-08에 `951e5a2`에 태그 `0.6.1`을 달아 실제 서버에 올렸어요. 그 커밋에서 workspace 테스트가 glibc와 musl 모두 2,806개 통과했어요. 0.6.0 이후 마이그레이션과 compose 파일은 바뀌지 않아서 `TRSS_VERSION`만 바꿨어요. 서버는 첫 주기를 실패 없이 마쳤고, 토렌트 목록이 전환 전과 같았어요. 되돌릴 때는 서버의 `~/trss-data-before-0.6.1`(전환 직전의 DB와 `artwork`)과 0.6.0 이미지를 써요. 0118과 0120–0122의 서버 확인은 끝났어요. 0119는 서버에 `적용`을 눌러 볼 회차가 없어 확인하지 못했어요. 0123은 2026-10-08에 `정반대의 너와 나` 2기 구독으로 작품 폴더를 옮기는 것을 확인했어요.
0122를 확인하며 `현재 유지`로 정한 보관본이 회차 줄에 계속 남는 것을 봤어요. 그런 보관본은 줄에서 빼기로 하고 0092 전에 고쳤어요(0124). 이것만으로 배포하지는 않아요(사용자 결정, 2026-10-08).
0123을 확인하며 두 가지를 봤어요. 구독할 때 체크한 지난 항목을 작품 폴더를 옮기느라 받지 않았고, 방영이 끝난 속편의 지난 회차를 받으면 회차 변환이 제안만 돼 시즌 중간 번호로 받아져요. 체크한 항목은 옮긴 뒤 받고(0125), 받기 전에 받을 이름과 제안을 보여주기로 했어요(0126). 둘 다 0092 전에 고치고, 이것만으로 배포하지는 않아요(사용자 결정, 2026-10-08).
0124–0126은 2026-10-08에 구현했고, 사용자 요청으로 같은 날 `bab88cf`에 태그 `0.6.2`를 달아 실제 서버에 올렸어요. 그 커밋에서 workspace 테스트가 glibc와 musl 모두 2,817개 통과했어요. 0.6.1 이후 마이그레이션과 compose 파일은 바뀌지 않아서 `TRSS_VERSION`만 바꿨어요. 전환 뒤 토렌트 목록이 전환 전과 같았고(2개), 서버의 규칙 미리보기가 받을 회차(`episode_name`)를 돌려줘 0.6.2가 도는 것을 확인했어요. 전환 뒤 세 컨테이너가 0.6.2 이미지로 돌았고, worker의 주기는 실패 0으로 끝났으며 `panic`과 `cannot write` 줄은 없었어요(사용자가 붙인 로그). 되돌릴 때는 서버의 `~/trss-data-before-0.6.2`(전환 직전의 DB와 `artwork`, 있으면 `subtitle-files`)와 0.6.1 이미지를 써요. 0.6.1은 0125가 `start` 명령에 담는 체크 항목을 읽지 못해서, 그런 명령이 열려 있으면 실패로 끝내고 규칙은 `멈춤`으로 남아요. 0126은 서버에서 받을 회차 표시가 실제로 받은 이름과 같은 것까지 확인했어요(`정반대의 너와 나` 2기 24화가 `S02E12`). 0124는 서버의 작품 상세 API로 `All Works Maid` 1화 줄에서 보관본이 빠진 것을 확인했어요. 0126의 받기 전 제안과 `적용`, 0125의 서버 확인은 아직 하지 않았어요. 그 대신 2026-10-08에 로컬 개발 환경에서 서버 DB의 사본으로 두 흐름을 확인했어요(0125·0126의 로컬 확인). 구독 확인 단계의 제안과 `적용`·`적용 취소`, 체크한 항목을 옮긴 뒤 받기, 규칙 화면의 받기 전 제안이 기대대로였어요. 0125의 worker 흐름에는 자동 시험을 더했어요.
0119도 같은 날 로컬에서 자막이 없는 회차의 보관본을 만들어 확인했어요. 실패는 줄에 까닭이 보였지만, 적용이 끝난 줄은 새로고침하기 전까지 자막이 `없음`으로 남았어요. 화면이 작품을 다시 읽는 때가 감시 폴더가 새 자막을 읽는 때보다 먼저라서예요. 작업이 끝난 뒤에도 화면이 작품에 적용한 파일이 보일 때까지 기다리게 해서 0092 전에 고쳤고(0127), 이것만으로 배포하지는 않아요(사용자 결정, 2026-10-08). 0125를 확인하며 방영이 끝난 작품을 구독하자마자 규칙 상세에 보관 제안이 뜨는 것도 봤어요. Anissia의 방영 종료만으로 제안하는 명세대로라 그대로 둬요(사용자 결정, 2026-10-08).
