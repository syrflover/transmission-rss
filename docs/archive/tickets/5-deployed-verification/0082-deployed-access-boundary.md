# 0082 실제 배포 경로에서 접근 보호를 확인해요

- 상태: 완료 (2026-10-07, LAN과 LTE의 시도, 서버의 송신 프록시, 휴대폰의 명령과 원격 화면 입력을 확인했어요. 아래 "결과")
- 출처: [접근 경계와 기기](../../../specs/web-app.md#접근-경계와-기기), [작업 화면 안의 인증과 브라우저 수명](../../../specs/jobs.md#작업-화면-안의-인증과-브라우저-수명)
- 막는 티켓: [0081](0081-deploy-new-release.md)

## 작업

웹에는 로그인이 없고, 접근은 LAN과 VPN으로 막아요.
원격 화면의 보호(서버 브라우저 네트워크에서 온 연결 끊기, Host·Origin 검사, 브라우저의 송신 제한)는 테스트와 개발 환경에서만 확인했어요(0040, 0053). 실제 배포 경로에서 확인하는 일은 목표 1부터 이 목표로 넘겨 왔어요.
새 릴리스가 올라간 실제 서버에서 허용된 경로와 막혀야 하는 경로를 차례로 시도해요.

- 휴대폰의 LTE에서는 VPN을 끈 채로 시도해요. 2026-10-04에 0.5.0의 웹과 Transmission이 이 경로로 닿지 않는 것은 사용자가 확인했어요. 이번에는 원격 화면과 서버 브라우저 경로까지 봐요.
- 사용자가 HTTPS 앞단 프록시를 쓰지 않으면, 프록시 뒤 WSS는 확인하지 않은 것으로 남겨요.

## 완료 기준

| 시도 | 기대 결과 |
| --- | --- |
| LAN이나 VPN에서 웹을 열고 명령 하나와 원격 화면 입력 하나를 해요 | 동작해요 |
| VPN 없이 LTE에서 웹 포트, 원격 화면의 WebSocket, 서버 브라우저의 포트에 닿아 봐요 | 어느 것도 연결되지 않아요 |
| `TRSS_WEB_HOSTS`에 없는 이름을 Host에 넣어 요청해요 | `421`이에요 |
| 다른 출처의 `Origin`으로 변경 요청과 WebSocket을 보내요 | `403`이에요 |
| 서버 브라우저의 실행에서 서버의 LAN 주소와 Docker 게이트웨이를 열어 봐요 | 송신 프록시가 거절해요 |

- 각 시도의 날짜, 경로, 결과가 결과 절에 있어요. 확인하지 않은 경로는 까닭과 함께 남은 일에 있어요.

## 만든 도구

`deploy/egress-check.sh`는 실제 서버에서 돌고 있는 trss-browser 안에서 송신 프록시에 직접 연결을 요청해요. Chromium의 연결이 프록시에 닿는 방식 그대로예요.

- 대상은 `.env`의 `TRSS_WEB_HOST_IP`(웹 포트와 Transmission 9091), 컨테이너가 붙은 네트워크·Docker 기본 브리지·`trss_net`의 게이트웨이(각각 웹 포트와 9091), 컨테이너 루프백의 실행기(9230)예요. LAN 주소로는 절대 형식의 `GET`도 보내요.
- 이미지에 curl이 없어서 bash의 `/dev/tcp`로 요청을 써요. 프록시 포트는 실행기가 시작할 때 정해지므로, 컨테이너 루프백에서 듣는 포트 가운데 `CONNECT example.com:443`에 `200`으로 답하는 포트를 프록시로 봐요. 이 대조 요청이 통과해야 나머지의 `403`이 "모두 거절하는 프록시"가 아니라는 근거가 돼요.
- 모든 로컬 대상이 `403`이면 종료 코드 0이에요. 아무것도 바꾸지 않고, 대조 요청은 example.com:443에 한 번 연결했다가 닫아요.
- 2026-10-07에 개발 환경의 trss-browser(`local` 이미지)에서 돌렸어요. 대조 요청은 `200`이었고, LAN 주소 192.168.1.116, 게이트웨이 172.17.0.1·172.19.0.1·172.20.0.1, 루프백 9230으로 가는 11개가 모두 `403`이었어요.

## 실행 방법

`[내 PC]`는 이 저장소가 있는 PC에서, `[서버]`는 서버(j4105, `~/trss`)에서 실행하는 명령이에요.

1. `[내 PC]` 스크립트를 서버의 compose 폴더로 복사해요.
   ```sh
   scp deploy/egress-check.sh j4105:~/trss/
   ```
2. `[서버]` 송신 프록시를 확인하고 출력을 파일에도 남겨요. 출력 마지막 줄이 `refused with 403: N of N`이어야 해요.
   ```sh
   cd ~/trss && chmod +x egress-check.sh && ./egress-check.sh 2>&1 | tee egress-check-$(date +%F).txt
   ```
3. `[휴대폰]` VPN을 끄고 LTE에서 공인 IP의 웹 포트(`http://<공인 IP>:8080`)를 열어 봐요. 사용자 도메인이 있으면 그 이름으로도 열어 봐요. 연결되지 않아야 해요. 원격 화면의 WebSocket도 같은 웹 포트로 가므로, 웹 포트가 닿지 않으면 WebSocket도 닿지 않아요.
4. 원격 화면 입력 하나는 [0083](0083-deployed-end-to-end.md)에서 휴대폰으로 erulabo의 CAPTCHA를 풀 때 VPN이나 LAN에서 한 것으로 기록해요. 같은 동작이라 따로 작업을 만들지 않아요.

## 결과

### LAN에서 한 시도 (2026-10-07)

LAN의 개발 PC(192.168.1.116)에서 실제 서버의 웹(`http://192.168.1.21:8080`, 0.6.0)에 curl로 보냈어요. `evil.example`은 `TRSS_WEB_HOSTS`에 있을 리 없는 이름이에요. 변경 요청과 WebSocket의 대상은 없는 작업 ID의 원격 화면(`/api/subtitle-jobs/no-such-job-0082/screen/close`, `…/screen/socket`)이라, 검사를 통과하더라도 서버의 상태가 바뀌지 않아요.

| 시도 | 결과 |
| --- | --- |
| `Host: evil.example`로 `GET /`와 `GET /api/health` | 둘 다 `421`이에요. |
| `Host: 192.168.1.21:8080`, `Host: localhost`로 `GET /` (대조) | 둘 다 `200`이에요. |
| `Origin: http://evil.example`, `Origin: null`, `Sec-Fetch-Site: cross-site`로 `POST …/screen/close` | 모두 `403`이에요. |
| 같은 출처의 `Origin`으로 `POST …/screen/close` (대조) | `415`예요. 검사를 지나 본문 형식에서 거절됐어요. |
| `Origin: http://evil.example`, `Origin` 없이 WebSocket 업그레이드 | 둘 다 `403`이에요. |
| 같은 출처의 `Origin`으로 WebSocket 업그레이드 (대조) | `404`예요. 검사를 지나 없는 작업에서 거절됐어요. |
| 서버의 9230(실행기) | 연결이 바로 거절됐어요. 호스트에 게시되지 않았어요. |

### 서버의 송신 프록시 (2026-10-07)

사용자가 실제 서버에서 `egress-check.sh`를 돌렸어요(13:23 UTC). 컨테이너는 `trss-browser`(`ghcr.io/syrflover/trss-browser:0.6.0`)이고, 프록시는 컨테이너 루프백의 33677 포트였어요.

| 대상 | 결과 |
| --- | --- |
| `CONNECT example.com:443` (대조) | `200`이에요. |
| LAN 주소 192.168.1.21의 8080·9091 | 둘 다 `403`이에요. |
| 게이트웨이 172.17.0.1·172.19.0.1·172.20.0.1의 8080·9091 | 여섯 개 모두 `403`이에요. |
| 루프백의 실행기(`127.0.0.1:9230`, `localhost:9230`) | 둘 다 `403`이에요. |
| `GET http://192.168.1.21:8080/` | `403`이에요. |

로컬 대상 11개가 모두 거절됐어요. 서버의 Docker 네트워크도 사설 대역이라 주소 종류만으로 거절되고, 컨테이너 자신의 네트워크로 거절되는 경우는 이 서버에서 생기지 않아요.

### 휴대폰 LTE (2026-10-07, 사용자 확인)

- 사용자가 VPN을 끈 LTE에서 웹 포트에 닿지 않는 것을 확인했다고 알렸어요. 연 주소와 걸린 시간 같은 관찰 값은 받지 않았어요.
- 원격 화면의 WebSocket은 웹 포트로 가요. 실행기 9230은 LAN에서도 연결이 거절돼 호스트에 게시되지 않았어요(위). 그래서 이 둘도 LTE에서 닿지 않아요.

### 명령과 원격 화면 입력 (2026-10-07, 사용자 확인)

- 사용자가 LAN에서 iPhone의 iOS 27 Safari로 실제 서버의 웹을 열고, `All Works Maid` 12화 후보를 골라 받았어요([0083](0083-deployed-end-to-end.md)의 작업 `f2403635`).
- 그 작업에서 erulabo의 확인이 원격 화면에 떴고, 사용자가 휴대폰에서 터치로 풀었어요. 화면을 확대하거나 돌린 뒤에도 누른 자리가 맞았다고 알렸어요([0085](0085-phone-and-tablet-flows.md)).

### 확인하지 않은 것

- VPN으로는 시도하지 않았어요. 완료 기준은 LAN이나 VPN 중 한 경로예요.
- 사용자는 LAN IP와 포트로 웹에 들어가요. HTTPS 앞단 프록시를 쓰지 않는 동안에는 프록시 뒤 WSS를 확인하지 않은 것으로 남겨요.
