# 0079 배포하기 전에 테스트를 musl 대상으로도 돌려요

- 상태: 완료 (2026-10-07)
- 출처: [테스트 나눔 ADR](../../../adr/0015-test-a-rule-once-in-its-crate.md), [검증 근거와 완료 판정](../../../specs/web-app.md#검증-근거와-완료-판정)
- 막는 티켓: 없음

## 작업

배포 이미지는 `clux/muslrust`에서 `x86_64-unknown-linux-musl` 대상으로 빌드해요. 그런데 테스트는 개발 PC의 glibc 대상으로만 돌았어요.
그 차이 때문에 생긴 결함이 있었어요. musl의 표준 라이브러리는 파일의 생성 시각을 읽지 못해서, 생성 시각을 견주는 검사가 배포에서는 한 번도 돌지 않았어요(`7eff742`, `6c175f1`).
ADR 0015에 따라, 배포하기 전에 workspace 테스트를 musl 대상으로도 돌리는 방법을 만들고 지금 코드에서 한 번 돌려요.

- 2026-10-07 개발 PC에는 musl 대상(`rustup target`)과 `musl-gcc`가 없어요. 번들 SQLite와 liblzma의 C 코드도 musl로 빌드해야 하므로, 이미지 빌드와 같은 `clux/muslrust` 컨테이너 안에서 돌리는 쪽이 배포와 가장 가까워요.
- 평소 변경 때는 돌리지 않고, 배포 절차의 한 단계로 둬요.
- 개발 PC에서 workspace 테스트는 link가 메모리를 많이 써서 `-j 4`로 돌려요. 컨테이너 안에서도 같은 제한을 둬요.
- 기본으로 건너뛰는 테스트(`#[ignore]`)는 이 실행에서도 건너뛰어요.

## 완료 기준

- 명령 하나로 musl 대상의 workspace 테스트를 돌릴 수 있어요. 그 명령이 readme의 개발 환경 안내와 배포 절차에 있어요.
- 결과 절에 실행한 커밋, 통과·실패·건너뛴 테스트 수, 걸린 시간이 있어요.
- musl에서만 실패하는 테스트가 나오면 원인을 가려 고쳐요. 제품 코드가 glibc에만 있는 동작에 기댄 것이면 제품 코드를, 테스트가 환경을 가정한 것이면 테스트를 고쳐요. 바로 고치지 못한 것은 결과 절의 남은 일에 적고, [0081](0081-deploy-new-release.md) 전에 사용자 결정을 받아요.

## 결과

### 만든 것 (2026-10-07)

- `dev/musl-test.sh`가 이미지 빌드와 같은 `clux/muslrust:stable` 컨테이너에서 `cargo test --locked --workspace -j 4`를 돌려요. 뒤에 준 인자는 `cargo test`로 가요.
  - 호출한 사용자로 돌려요. root는 쓰기가 거절되지 않아서, 거절을 기대하는 테스트가 root에서는 다르게 돌 수 있어요.
  - 빌드는 이 checkout의 `target/musl`에 하고, 개발 PC의 cargo registry와 git checkout(`~/.cargo`)을 마운트해 다시 받지 않아요. 개발 PC의 cargo 설정은 읽지 않고, 프로젝트의 `.cargo/config.toml`(SQLite 빌드 옵션)은 읽어요.
- readme의 개발 환경 절에 [Releasing](../../../../readme.md#releasing)을 더했어요. 태그를 올리기 전에 이 명령을 돌리는 것이 릴리스 절차의 한 단계예요.

### 검증한 것

2026-10-07, `1ad2be1`(이 스크립트와 readme 변경은 commit 전)에서 처음 돌렸어요.

| 항목 | 값 |
| --- | --- |
| 결과 | 통과 2,754개, 실패 0개, 무시 13개(테스트 바이너리 44개) |
| 걸린 시간 | 7분 27초. 의존성까지 모두 musl로 처음 빌드한 시간이 3분 3초예요. |
| 같은 커밋의 glibc 실행 | `cargo test -j 4 --workspace`가 통과 2,754개, 실패 0개, 무시 13개였어요. |
| `target/musl`의 크기 | 12 GB |

무시한 13개는 평소에도 건너뛰는 테스트예요. 서버 브라우저 이미지와 Docker가 필요한 것이 8개, 실제 Anissia·AniList·Blogger·Drive·Naver·Tistory에 닿는 것이 5개예요.
musl에서만 실패한 테스트는 없어서 고친 것은 없어요.

### musl에서 느린 테스트

테스트 바이너리가 보고한 시간의 합이 musl에서 260초, glibc에서 69초였어요(같은 커밋, 같은 `-j 4`, 2026-10-07).

| 바이너리 | musl | glibc |
| --- | --- | --- |
| trss-core (132개) | 43.36초 | 1.22초 |
| trss-worker 통합 테스트 (399개) | 44.47초 | 15.17초 |
| trss-jobs 통합 테스트 (405개) | 50.28초 | 14.75초 |
| trss-web (461개) | 38.28초 | 11.23초 |
| trss-collect (476개) | 21.88초 | 2.87초 |

여러 스레드가 함께 DB를 여는 테스트가 특히 느려요. musl의 메모리 할당기가 여러 스레드에서 느린 것이 원인으로 보이지만, 확인하지는 않았어요. 배포한 앱도 같은 할당기를 쓰므로, 서버에서 느린 곳이 보이면 이 차이를 먼저 의심할 만해요. 평소 변경 때는 돌리지 않는 단계라 이번에는 고치지 않았어요.
