# 결과 목표 4. 보관·적용과 교체 승인

이 목표는 2026-10-08에 닫았어요. 완료 기록(관찰한 것, 시험으로 확인한 것, 남은 것)은 [티켓 목록의 목표 4](../../../tickets/README.md#4-보관적용과-교체-승인)에 있어요. 아래는 이 목표를 진행하는 동안 티켓 목록에 있던 범위, 결정, 진행 순서와 티켓이에요.

받은 묶음을 분석해 `.trss/`에 보관하고, 영상 옆에 적용하며, 기존 자막의 교체는 비교와 승인을 거쳐요.
목표 3에서 넘어온 것(받은 묶음에서 회차의 파일 고르기, ZIP이 아닌 압축 풀기, 파일 이름의 회차와 대응 견주기, 대응을 바꾼 뒤의 재평가, 작품별 자막 형식 순서, 라이브러리 할 일 배지와 작품 상세 `할 일` 카드)도 이 목표예요.

목표 5로 넘기는 것은 실제 서버 배포(1000:1000 전환 포함), 세 재생기(Infuse·IINA·팟플레이어)의 폰트 렌더링·다시 읽기·여러 형식 선택, 실제 배포 경로의 접근 보호예요.

2026-10-04의 결정이에요(사용자 결정).

- 자막 파일 하나를 보관과 첫 적용까지 끝까지 잇는 조각을 먼저 만들어요. 보관의 DB 구조와 파일 효과의 기록을 그 조각에서 정해, 분석부터 만들어 보관 구조를 짐작으로 정하지 않으려는 거예요.
- 사람 없이 도는 후보 작업은 확인 없이 적용해요. 파일 이름의 번호가 Anissia 회차 표시나 대응으로 옮긴 시즌 회차와 맞는 파일을 고르고, 어느 쪽과도 다르면 보류해요.
- 올리기와 직접 찾기는 작업마다 한 번 배치 확인을 받아요. 시즌을 잘못 고르거나 다른 작품의 게시물로 들어가면 시즌 범위 안의 번호라도 엉뚱한 회차에 붙을 수 있어서예요.
- 묶음 안의 고르지 않은 회차는 보관만 하고 회차 줄에서 골라 적용해요. 자막 체크와 보유 범위에는 세지 않아요. 구독 제작자의 자동 작업이면 그 회차들에도 자동 수신 규칙을 적용해요.
- 목표 3에서 받기까지만 하고 끝난 작업은 자동으로 이어서 처리해요.
- 관리하지 않던 기존 자막은 지우거나 덮어쓰기 전에 `제작자 알 수 없음` 보관본으로 들여요.
- 여러 회차의 교체는 회차 목록에서 회차마다 고르고 `모두 교체`·`모두 유지`도 둬요. 승인 증거는 회차마다 남겨요.
- 대응을 바꿔 적용본의 대상이 달라지면 옛 적용본 제거와 새 회차 적용을 한 계획으로 묶어 배치 확인을 받아요.
- 고른 보관본으로 바꿀 때는 비교 화면을 바로 열어요.
- 바뀌지 않은 Drive 폰트는 `HEAD`의 크기와 `Last-Modified`로 알아보고 다시 받지 않아요. Naver·Tistory는 받아서 내용으로 비교해요.
- 압축 해제는 메모리·시간 한도를 건 별도 프로세스에서 해요.
- 라이브러리 할 일 배지와 작품 상세 `할 일` 카드를 이 목표에 넣어요.
- 재생기는 미디어를 NFS로 읽어요. worker는 1000:1000으로 실행하고, 이미지와 Compose는 이 목표에서 바꾸며 실제 서버의 전환은 목표 5의 배포에서 해요. 같은 DB를 쓰는 web도 같은 사용자로 맞춰요(0062).
- 실제 재생기 확인은 Infuse의 배치 확인 한 번만 이 목표에서 해요.

명세에 적은 구현 세부도 있어요. DB는 [보관 관계 필드](../../../specs/settings.md#보관-관계-필드)와 같은 관계를 담고, 보관·적용의 임시 파일은 목적지와 같은 파일시스템인 `.trss/` 안에 둬요. 원 수신물은 보관을 확인한 뒤 지우고 풀지 못한 압축 파일만 남기며, 자막·폰트·첨부·구성 파일이 아닌 멤버는 이유를 적고 버려요.

확인할 일 0059(압축 해제 도구와 한도), 0060(서버 탐침), 0061(Infuse 배치 확인, 사용자)과 실행 사용자 0062는 바로 시작할 수 있어요.
기능은 자막 파일 하나를 보관하고 처음 적용하는 0063이 먼저예요. 그 위에 여러 파일 묶음 0064, 영상 대기 0067, 교체 승인 0068이 나란히 가요.
0064 뒤에 압축 해제 0065(0059도 필요), 배치 확인 0066, 정리 0073, Drive 폰트 0074가 오고, 0068 뒤에 내용 비교 0069, 여러 회차 교체 0070, 고른 보관본 적용 0072가 와요.
대응 변경의 재평가 0071은 배치 확인과 교체를 함께 써서 0066·0068 뒤예요. 대응이 없어 같은 번호로 본 연결이 나중의 대응을 따르게 하는 0077은 0071을 하며 더한 후속이에요(사용자 결정, 2026-10-06). 할 일 카드 0075는 교체 승인 카드의 변경 태그 때문에 0069 뒤예요. 회차를 정하지 못한 영상의 할 일 0078은 0075에서 나눈 후속이고, 0076 뒤에 했어요(사용자 결정, 2026-10-06).
마지막 0076이 여덟 경로를 처음부터 끝까지 보며, 목표 3에서 받아 둔 작업이 이어지는 것을 관찰해요.
2026-10-07에 0061을 마쳐 0065의 서버 측정(완료 조건 9)만 남았고, 2026-10-08에 그 측정을 마쳐 이 목표를 닫았어요.

알려진 불확실성이에요.

- RAR 4·5와 나뉜 RAR은 순수 Rust 크레이트 `rars`로 풀기로 했지만, WinRAR로 만든 파일로는 아직 확인하지 않았어요(0059). `.z01`로 나뉜 ZIP은 풀지 않아요.
- worker 안에서 압축 해제와 복사의 페이지 캐시가 한도에 닿을 수 있어요(0060·0065). 64MiB 사전을 풀면 자식 프로세스가 70MB 남짓을 써서(0059), 0065에서 worker 한도를 256M로 올렸어요. 실제 서버의 256M 컨테이너에서 한 프로세스가 300MiB를 쓰고 읽을 때는 캐시가 한도에 닿았지만 `oom_kill`은 없었어요(0060, 2026-10-07). 압축 해제도 2026-10-08에 서버에서 측정했고 `oom_kill`이 없었어요(0065).
- SMI는 인코딩과 구조가 제각각이라 내용 비교의 가장 큰 위험이에요(0069).
- Infuse가 숨김 폴더 `.trss/`를 자막 검색에서 뒤진다면 ADR 0003·0008의 배치를 다시 정해야 해요(0061). 그래서 확인할 일을 맨 앞에 뒀어요. 실제 서버의 작품 폴더에서 Infuse는 적용본을 보여주고 `.trss/` 안의 보관본은 보여주지 않았어요(0061, 2026-10-07).
- 실제 서버의 xfs에서도 덮어쓰지 않는 이름 바꾸기, 마운트 사이의 `EXDEV`, 동기화가 개발 환경과 같았어요(0060, 2026-10-07).
