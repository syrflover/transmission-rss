# 0075 라이브러리 격자의 할 일 배지와 작품 상세의 `할 일` 카드를 보여줘요

- 상태: 완료 (2026-10-06). 영상의 회차 확인 카드는 [0078](0078-video-episode-check.md)로 나눴어요(사용자 결정, 2026-10-06).
- 출처: [라이브러리 화면](../../../specs/library.md#라이브러리-화면), [할 일과 회차 목록](../../../specs/library.md#할-일과-회차-목록). 목표 3에서 티켓 없이 넘어왔고 목표 4에 넣었어요(사용자 결정, 2026-10-04).
- 막는 티켓: [0069](0069-replacement-diff.md)(교체 승인 카드의 변경 태그)

## 작업

- 격자 보기의 표지 왼쪽 위에 그 작품의 할 일 배지를 올려요. 종류의 이름과 색은 [할 일 화면](../../../specs/jobs.md#할-일-화면)과 같아요. 목록의 한 페이지가 배지를 함께 담아 오고, 작품마다 따로 요청하지 않아요.
- 작품 상세 위쪽의 `할 일`에 사용자가 해야 하는 것만 색을 입힌 카드로 둬요.
  - 교체 승인 카드는 `현재`·`새 자막`의 받은 시각 한 줄과 변경 사항 숫자 태그를 두고, `비교`로 작업 상세를 열어요.
  - 인증 카드는 인증 방식과 요청 시각을 두고, `인증`으로 작업 상세를 열어요.
  - 회차 확인 카드는 확인할 RSS 항목 이름 조각을 제목으로 둬요. 자막 작업의 회차 확인(배치 확인, 보류한 파일)은 출처와 파일 수를 두고 `확인`으로 작업 상세를 열어요.
- 할 일이 없는 작품에는 빈 제목, 목록, 여백을 만들지 않아요.

## 완료 기준

| 입력·상태 | 기대 결과 |
| --- | --- |
| 교체 승인을 기다리는 작품 | 격자 표지에 배지가 있고, 작품 상세 위쪽에 교체 승인 카드(받은 시각, 숫자 태그, `비교`)가 있어요. `비교`가 작업 상세를 열어요. |
| 인증이 필요한 작업이 있는 작품 | `인증` 카드가 작업 상세를 열어요. |
| 배치 확인을 기다리는 올린 작업이 있는 작품 | 회차 확인 카드에 출처와 파일 수, `확인`이 있고 작업 상세로 가요. |
| 할 일이 없는 작품 | 배지와 `할 일` 구역이 없고 빈 여백도 없어요. |
| 할 일을 처리함 | 배지와 카드가 사라져요. |
| 격자의 한 페이지 | 배지를 위해 작품마다 따로 요청하지 않아요. |

## 결과

### 만든 것 (2026-10-06)

- **배지의 종류**: 처리 필요의 네 종류 `인증 필요`·`받기 실패`·`교체 승인`·`회차 확인 필요`예요. 작업의 배치 확인과 보류한 파일도 회차 대응의 확인처럼 `회차 확인 필요`예요.
  - 제안(`제목 후보`·`자막 구독`·`보관 제안`)은 배지로 올리지 않아요(구현 결정, 2026-10-06). 메뉴의 개수 배지와 작품 상세의 `할 일`처럼 사용자가 해야 하는 것만 올려요.
  - 이름·색·아이콘은 웹의 한 표(`todo/badges.tsx`의 `TodoBadge`)에서 와요. 할 일 화면의 카드도 이 표를 쓰고, 작업 상태 배지의 같은 이름에서 글자를 가져와 화면끼리 갈라지지 않아요.
- **목록 API**: `GET /api/library/works`의 작품마다 `todos`(종류 코드를 할 일 순서로 한 번씩)를 더했어요. 한 페이지를 만들 때 할 일 목록(`todo_api::todo_list`)을 한 번 읽어 작품별로 나눠요(`badges_by_work`). 할 일을 읽지 못하면 배지 없이 목록을 돌려주고 서버 로그에 남겨요.
- **격자**: 표지 왼쪽 위에 종류마다 배지 하나를 할 일 순서로 세로로 쌓아요. 종류가 여럿이면 모두 보여줘요(구현 결정, 2026-10-06). 화면 낭독기는 제목과 두 상태 줄 뒤에 배지를 읽어요. 사양대로 목록 보기에는 배지가 없어요.
- **뒤로 가기**: 목록을 되찾을 때는 스크롤을 지키려고 페이지를 다시 읽지 않아요. 그 사이 처리한 할 일이 있을 수 있어서 `GET /api/todo`를 한 번 읽어 남겨 둔 작품들의 배지만 바꿔요(구현 결정, 2026-10-06). 메뉴로 연 목록은 전처럼 첫 페이지를 다시 읽어요.
- **작품 상세의 `할 일`**: 시즌 정보와 Anissia 연결 아래, 자막 후보 위에 둬요. 할 일 화면과 같은 할 일 목록(`KEYS.todos`)을 10초마다 읽어 이 작품의 것만 골라요. 카드에는 표지와 작품 제목이 없고, 종류 배지와 시각, 대상 줄(회차, 제작자, 시즌이 여럿인 작품의 시즌 태그), 종류별 줄, 버튼이 있어요. 할 일이 없거나 아직 읽지 못했으면 구역을 그리지 않아요.
  - 교체 승인: `현재 … 받음`·`새 자막 … 받음` 한 줄, 변경 사항 숫자 태그, `비교`예요. 받은 시각은 승인을 기다리는 계획들 가운데 가장 최근 것이에요(구현 결정, 2026-10-06). 현재 자막이 모두 앱이 관리하지 않는 파일이면 작업 상세의 버전 줄처럼 `파일 시각 …`이라고 적어요.
  - 인증: 인증 방식(`CAPTCHA`), 요청 시각, `인증`이에요.
  - 배치 확인과 보류한 파일의 회차 확인: 출처(작업이 생긴 방식의 `올림`·`직접 찾기`·`재배치`·`자동` 태그, 제작자, 게시물 호스트)와 `파일 N개`, `확인`이에요.
  - 회차 대응의 회차 확인: 제작자, 회차, `대응 미정`·`어긋난 회차`, `회차 대응 정하기`예요. 같은 페이지의 자막 후보에서 그 제작자 묶음을 열어요.
  - `받기 실패`도 카드로 둬요(구현 결정, 2026-10-06). 격자의 배지와 같은 종류가 상세에도 보이게 하려는 거예요. 대체 실패는 `회차 보기`로 같은 페이지의 그 회차 줄에, 추가 실패는 `기록 보기`로 수집 기록에 가요.
- **API**: `교체 승인` 할 일에 `current_received_at`·`current_changed_at`·`new_received_at`을, 작업의 `회차 확인 필요`(`placement_check`)에 `origin`·`source`를 더했어요.
- **명세**: [라이브러리 화면](../../../specs/library.md#라이브러리-화면)과 [할 일과 회차 목록](../../../specs/library.md#할-일과-회차-목록)을 고쳤어요.

### 나눈 것

`회차 확인 카드는 확인할 RSS 항목 이름 조각을 제목으로 둬요`는 만들지 않았어요. 받은 영상의 회차를 정하지 못한 할 일을 만드는 코드가 아직 없어요. 회차를 읽지 못한 영상은 지금 작품 상세 `파일` 카드의 `회차를 확인하지 못한 파일`에만 나와요. 무엇을 할 일로 셀지, 어떻게 사라지는지, 메뉴 배지에 넣을지를 정하는 일과 함께 [0078](0078-video-episode-check.md)로 나눴어요(사용자 결정, 2026-10-06).

### 검증한 것

개발 환경의 DB 복사본(2026-10-06, 작품 89편)을 이 변경의 `trss-web`과 Vite로 띄워 확인했어요. 개발 컨테이너와 그 DB는 건드리지 않았어요.

| 완료 기준 | 근거 |
| --- | --- |
| 교체 승인을 기다리는 작품 | 시험 `the_library_badges_a_work_until_its_replacement_is_decided`에서 목록의 `todos`가 `["replacement"]`예요. 받은 시각은 `the_replacement_to_do_says_when_the_newest_current_and_new_subtitles_were_received`, `the_replacement_to_do_of_a_file_the_app_did_not_manage_has_its_change_time`, `a_current_subtitle_the_app_manages_gives_the_time_over_another_plans_file`이 확인해요. 태그는 0069의 시험과 같아요. 복사본에서는 `FX Senshi Kurumi-chan` 표지에 배지 셋(`인증 필요`·`교체 승인`·`회차 확인 필요`)이 있었어요. 작품 상세에는 `현재 어제 04:46 받음`·`새 자막 어제 20:08 받음`, 숫자 태그, `비교`가 든 카드가 있었고, `비교`를 누르자 작업 상세 `/todo/job/327d1e7d…`가 열렸어요. |
| 인증이 필요한 작업이 있는 작품 | 목록 시험 `a_page_badges_each_work_with_its_to_dos_in_the_to_do_order`가 `auth` 배지를 확인해요. 복사본의 `인증 필요` 카드는 13화, `CAPTCHA`, `10월 3일 00:05`를 보여줬고, `인증`의 주소는 그 작업 상세(`/todo/job/1770f261…`)였어요. |
| 배치 확인을 기다리는 올린 작업이 있는 작품 | API 시험 `an_upload_waiting_for_its_placement_shows_its_table_and_one_to_do`가 그 할 일의 `origin: upload`를 확인해요. 재배치는 `origin: relocate`예요. 복사본에는 올린 작업의 배치 확인이 없어서, 고른 후보의 작업이 보류한 파일 여섯 건으로 카드를 봤어요. 카드마다 `가짜 출처`, `fake.trss.invalid`, `파일 1개`, `확인`이 있었고, `확인`의 주소는 각 작업 상세였어요. `올림` 태그는 화면에서 보지 못했어요. |
| 할 일이 없는 작품 | 복사본의 `All Works Maid` 상세에 `할 일` 구역이 없었어요(DOM 확인). 목록 시험에서 할 일이 없는 작품의 `todos`는 `[]`예요. |
| 할 일을 처리함 | 시험에서 교체를 `유지`로 정하면 목록의 `todos`가 `[]`가 돼요. 복사본에서는 작업 상세를 연 채로 그 작품의 교체 승인 작업 9개를 SQL로 끝냈어요. 뒤로 가자 작품 상세의 교체 승인 카드가 사라졌어요. 한 번 더 뒤로 가자 라이브러리 표지에 `인증 필요`·`회차 확인 필요`만 남았고, 스크롤 위치도 그대로였어요. 승인 화면의 버튼으로 처리한 것은 아니에요. |
| 격자의 한 페이지 | 목록 응답이 배지를 함께 실어요. 복사본의 네트워크 기록에서 라이브러리 화면은 표지 이미지 말고는 작품별 요청이 없었고, 뒤로 가기에서는 목록을 다시 읽지 않고 `/api/todo`만 한 번 읽었어요(개발 모드라 StrictMode가 첫 요청을 취소해요). 60편 페이지의 응답은 15ms였어요. |

휴대폰 폭(375px·320px)에서 표지의 배지가 표지 안에 들고 가로 스크롤이 없었어요. 어두운 테마의 작품 상세 카드도 확인했어요. 콘솔 오류는 복사본에 표지 파일이 없어서 난 이미지 404뿐이었어요.

### 시험

이 작업 트리(2026-10-06, `f8c0f62` 위)에서 확인했어요.

- `cargo clippy --workspace --all-targets -j 4 -- -D warnings`는 경고가 없고(`probe-out/0075-clippy.txt`), `cargo fmt --all --check`도 통과해요.
- 웹은 `npm test` 194개가 통과하고 `tsc -b`가 통과해요.

  - Rust 6개: `a_works_badges_are_its_kinds_once_each_in_the_lists_order`, `a_page_badges_each_work_with_its_to_dos_in_the_to_do_order`, `the_library_badges_a_work_until_its_replacement_is_decided`, 받은 시각의 시험 3개. 배치 확인 시험 2개에 `origin`·`source` 확인을 더했어요.
  - 웹 5개: `kinds.test.ts` 4개, `changes.test.ts`의 받은 시각 줄 1개.
- 판정을 하나씩 망가뜨린 16가지(서버 9, 웹 7)를 모두 시험이 잡았어요(`probe-out/0075-mutations.txt`). 처음에는 관리하는 현재 자막과 관리하지 않는 파일이 함께인 경우를 잡는 시험이 없어서 하나 더했어요.

### 한계

- 목록을 열어 둔 동안 생기거나 처리된 할 일은 다음에 페이지를 읽거나 뒤로 가기로 돌아올 때 배지에 반영돼요.
- 라이브러리에서 작품을 찾을 수 없는 할 일(작품이 빠진 작업, 작품 폴더에 닿지 않는 규칙의 추가 실패)은 어느 작품에도 배지를 붙이지 않아요.
- 작품 상세는 메뉴의 개수와 별도로 할 일 목록을 10초마다 읽어요. 복사본에서 한 번 읽는 데 걸린 시간은 재지 않았어요. 목록 페이지(할 일 목록을 한 번 읽음)가 15ms였어요.
