# 0066 올리기와 직접 찾기의 배치를 한 번 확인받아요

- 상태: 완료
- 출처: [배치 확인](../../../specs/subtitles.md#배치-확인)(사용자 결정, 2026-10-04), [파일의 회차](../../../specs/subtitles.md#파일의-회차), [할 일](../../../specs/jobs.md#할-일), [작업 상세](../../../specs/jobs.md#작업-상세)
- 막는 티켓: [0064](0064-multi-file-packages.md)

## 작업

올리기와 직접 찾기는 파일 이름에서 회차를 읽어요. 시즌을 잘못 고르거나 다른 작품의 게시물로 들어가면 시즌 범위 안의 번호라도 엉뚱한 회차에 붙을 수 있어서, 사용자가 화면 앞에 있는 이 두 흐름은 작업마다 한 번 확인받아요.

- 받기 뒤 분석한 배치 계획을 작업 상세의 `파일 → 회차 → 붙을 영상 이름` 표로 보여주고, `적용` 한 번으로 반영해요. 확인하기 전에는 `.trss/`에도 영상 옆에도 쓰지 않아요.
- 회차는 파일 이름의 번호를 그 출처의 회차 대응으로 옮긴 것이에요. 대응이 없거나 제작자를 모르면 같은 번호예요.
  시즌 밖, 소수·문자 회차, 읽을 수 없는 번호, 미정인 대응은 보류한 줄이에요.
- 보류한 줄은 그 자리에서 회차나 대안을 고르거나 `적용하지 않음`으로 둬요. 적용하지 않은 자막은 보관만 해요.
- 반영한 줄 가운데 대응으로 옮긴 줄은 대응을 따르는 연결(`mapped`), 사용자가 고친 줄과 같은 번호로 본 줄은 직접 정한 연결(`explicit`)로 남겨요.
- 기다리는 동안 작업마다 `회차 확인 필요` 할 일 하나가 그 작업 상세로 이어요. 작업 단계는 `받기` 뒤에 `배치 확인`이에요.
- 목표 3에서 받아 둔 올린 작업과 직접 찾기 작업도 이 확인에서 기다려요.
- 자막이 이미 있는 회차는 확인 뒤 [교체 승인](0068-replacement-approval.md)으로 가요.

## 결과

### 만든 것 (2026-10-05)

- **기다림**(`place/mod.rs`의 `Placer::run`): 올린 작업과 직접 찾기 작업은 분석한 뒤, 배치를 확인하기 전에는 보관·적용·수신 영역 정리를 하지 않고 `배치 확인`(`wait = placement`)에서 기다려요. 메모는 `자막 n개가 붙을 회차를 확인해 주세요`예요. 보류한 줄이 있으면 `· 회차를 정할 파일 n개`가 붙고, 폰트와 첨부뿐이면 `받은 폰트와 첨부를 보관하기 전에 확인해 주세요`예요. 남길 것이 없는 묶음은 확인 없이 끝나요. 올리기 API는 이제 모든 올린 작업을 `대기`로 만들고 worker를 깨워요.
- **확인**(`place::records::confirm_placement`, `placeable`): 사람이 고른 표를 IMMEDIATE 트랜잭션 하나에서 받아요. 그 트랜잭션에서 줄을 쓰고, 작업의 `placement_confirmed_at`을 적고, 작업을 다시 줄에 세우고, 기록을 남겨요. 표에 넣는 줄은 확인 전에는 결과가 없는 자막 전부이고, 확인 뒤에는 묻는 줄(보류한 줄)이에요. 계획한 회차에 둔 줄은 그 연결(`mapped` 등)을 지키고, 옮기거나 계획한 회차가 없던 줄은 `explicit`이에요. 시즌 밖의 회차와 회차 없는 적용은 이유와 함께 거절하고, 표가 지금 묻는 줄과 다르면 `Stale`이에요. 이미 확인했거나 기다리지 않으면 `NotWaiting`이에요. 폰트와 첨부뿐인 묶음은 줄 없이 확인해요(`폰트와 첨부만 보관해요`).
- **직접 찾기의 받기**(`store.rs`): 직접 찾기 작업은 끝나지 않았고 아직 끝나지 않은 항목이 있는 동안 `받는 중`(`receiving`)이에요. `end_find`가 항목을 모두 끝내는 것은 한 번뿐이에요. 받은 파일이 있으면 `대기`로 돌아가 분석과 배치 확인으로 가고, 없으면 `받은 파일 없음`으로 끝나요. 받기가 끝난 작업에는 `ask_finish`가 `Ended`를 돌려주고, `unbound_finishes`도 그 작업을 다시 끝내지 않아요. 실행이 잡고 있는(`running`) 작업은 감시의 끝내기가 기다려요.
- **마이그레이션 54**(`placement_confirm.sql`): `placement_confirmed_at`을 더해요. 이전 빌드가 보관하지 않고 끝낸 올린 작업과 직접 찾기 작업 가운데 계획이 없고 수신 영역에 받은 파일이 남은 것을 `대기`로 돌려요. 그러면 다시 받지 않고 분석과 배치 확인으로 이어져요.
- **API**: 작업 상세에 `confirm`(`scope`, 표의 `positions`, 시즌 회차 수 `total`, 회차마다 영상 이름·수와 자막이 있는지)과 줄의 `named`·`assignment`, 작업의 `receiving`을 더했어요. `POST /api/subtitle-jobs/{id}/placement`는 `{ rows: [{ position, episode, apply }] }`를 받아요. 거절은 `400`, 표가 바뀌었거나 이미 확인했으면 `409`, 작업이 없으면 `404`예요. 할 일 `회차 확인 필요`는 이 작업들에도 하나씩 나오고, 파일은 표의 줄, 까닭은 작업 메모예요.
- **웹**(`PlacementConfirm.tsx`, `placementTable.ts`): 작업 상세의 `파일 → 회차 → 붙을 영상 이름` 표예요. 보류한 줄이 위에 오고, 회차는 기본 `select`(`n화`, `적용하지 않음`)로 골라요. 영상 칸은 영상 이름, `영상 없음 · 영상이 생기면 붙여요`, `보관만 해요`, `이미 자막이 있어 교체를 비교해요`를 보여줘요. 대응으로 옮긴 줄에는 `이름 13 → 1화 (회차 대응)`이 붙어요. 표 밖의 폰트·첨부와 뺀 파일은 요약해요. 고르지 않은 줄이 있으면 `적용`이 꺼지고, `409`를 받으면 작업을 다시 읽어요. 720px 이하에서는 세 칸이 위아래로 쌓여요. 확인한 뒤에는 `회차별 결과`에 묶음의 결과 그룹만 보여줘요(`PackageResults`). 직접 찾기의 원격 화면은 `receiving`일 때만 열려요.
- **명세**: [배치 확인](../../../specs/subtitles.md#배치-확인)에 `올리기·직접 찾기의 배치 확인은 이렇게 동작해요`를 더했어요. 올린 작업이 진행 중인 범위와 직접 찾기의 받기를 [작업 상세](../../../specs/jobs.md#작업-상세)와 [직접 찾기와 자막 올리기](../../../specs/subtitles.md#직접-찾기와-자막-올리기)에서 고쳤어요.

### 독립 검토

복잡한 불변식 검토(2026-10-05)는 확인 전 작품 폴더 쓰기, 직접 찾기의 겹치는 실행, `confirm_placement`, 마이그레이션 54, 작업 상세와 할 일의 일치, 후보 작업의 회귀에서 막는 결함을 찾지 못했어요. 지적은 이렇게 다뤘어요.

- 실행이 run을 묶은 직후 감시가 받기를 끝내면, 실행이 작업을 `인증 대기`로 덮어써 다시 끝낼 수 없게 될 수 있다는 지적이었어요. 저장소 함수를 실행 순서대로 부르는 시험으로 그 상태(`receiving`·`finishing` 없음, 화면 없음, `unbound_finishes` 비어 있음)가 남는 것을 재현했어요. 이제 `end_find`는 감시의 끝내기(`Some(run)`)를 `running` 작업에는 받지 않아요. 다시 한 검토는 이 수정이 맞다고 봤어요. 다만 worker는 `인증 대기` 작업에만 감시를 띄워서 실제로는 그 틈이 생기기 어렵다고 정정했어요. 그래서 이 수정은 저장소가 순서를 스스로 지키게 하는 방어예요.
- 보류한 줄의 확인이 할 일이 보이는 상태보다 넓게 받아들여진다는 설계 메모예요. `choose_stored`와 같은 기준이라 그대로 뒀어요.
- `confirm_placement`의 문서가 묻는 줄의 연결을 코드와 다르게 적었어요. 문서를 고쳤어요.
- 감시가 끝내기 직전에 들어온 다운로드를 잃을 수 있다는 지적은 이번 변경 전부터 있던 것이에요. 따로 다뤄요.

### 시험

### 한계

- 직접 찾기의 실제 묶음은 목표 3에서 받아 둔 것을 이었어요. 이 티켓에서 새 직접 찾기를 실제 사이트로 열어 받지는 않았어요. 받기를 끝내는 흐름은 가짜 브라우저로만 시험했어요.
- 실제 묶음이 확인 뒤 교체 승인으로 갔고, 승인까지는 하지 않았어요. 교체는 0068에서 확인했어요.
- 보류한 줄이 있는 후보 작업도 같은 표를 쓰지만(`보류한 파일의 회차`), 개발 환경에서는 올리기와 직접 찾기만 봤어요.
- 휴대폰 폭은 내장 브라우저의 휴대폰 크기로만 봤고, 실제 기기에서는 보지 않았어요.
- 압축 파일을 풀지 못하면 그 파일은 계속 실패로 남아요(0065). 기계 쪽 실패를 다시 시도할지는 아직 정하지 않았어요.
