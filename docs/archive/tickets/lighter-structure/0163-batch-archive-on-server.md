# 0163 `모두 보관`·`N개 보관`을 명령 하나로 받아 서버가 규칙 순서대로 보관해요

- 상태: 완료
- 출처: [구조 가볍게 하기 명세의 명령](lighter-structure.md#명령), [명세의 결정](lighter-structure.md#결정), [수집 명세의 보관 이동](../../../specs/collection.md)의 `모두 보관`·`N개 보관`
- 막는 티켓: [0154](0154-change-events-and-command-reads.md)(SSE 경로)

## 작업

보관 제안의 `모두 보관`·`N개 보관`은 화면이 규칙마다 규칙 보관 명령을 하나씩 보내고, 그 명령이 끝나기를 기다린 뒤 다음 규칙을 보내요. 순서를 화면이 쥐고 있어서, 화면이 기다리기를 멈추면 일괄 보관 전체가 멈춰요. [0154](0154-change-events-and-command-reads.md) 전에는 1초 주기 조회가 숨겨진 탭에서도 느리게나마 돌아 다음 규칙으로 넘어갔어요. 0154 뒤로는 숨겨진 탭이 이벤트 연결을 닫아서, 탭을 숨기면 지금 규칙 하나는 서버가 끝까지 옮기지만 남은 규칙은 다시 보일 때까지 보내지 않아요. 화면을 닫으면 남은 규칙은 보내지 않아요.

사용자는 일괄 보관을 서버가 순서대로 처리하게 하기로 했어요(2026-10-21, [명세의 결정](lighter-structure.md#결정)). 이 티켓은 화면이 고른 규칙을 요청 하나로 보내고, 서버가 명령 하나 안에서 규칙을 그 순서대로 보관하게 해요. 화면은 그 명령의 진행을 이벤트로 받아 다시 읽어요.

지금 일괄 보관이 지키는 것은 그대로예요.

- 규칙마다 같은 순서로 처리하고, 같은 작품 폴더의 규칙들을 한꺼번에 보관하면 마지막 규칙에서 한 번 옮겨요.
- 규칙 하나가 잘 끝나지 않으면 거기서 멈추고, 화면은 그 규칙의 이름과 까닭을 보여 줘요.
- 규칙 하나를 보관하는 동작(규칙 끄기, 폴더 이동, 까닭 문장)과 명령 안의 다시 시도 횟수·대기는 지금과 같아요.

명령의 모양(새 종류인지, 지금 규칙 보관 명령이 규칙 목록을 받는지), 진행을 어디에 적는지, 이미 열린 규칙 보관 명령과 겹칠 때 무엇을 하는지는 이 티켓에서 정해요. 화면에 보이는 것이 바뀌는 선택이면 사용자에게 물어요.

## 결과

2026-10-21에 `모두 보관`·`N개 보관`, 그리고 제안이 하나일 때의 `보관`을 명령 하나(`rule_archive_batch`)로 보내게 했어요. 서버는 그 명령 안에서 규칙마다 보통의 규칙 보관 명령(`rule_archive`)을 하나씩 만들어 끝나기를 기다리며 순서대로 보관해요. 탭을 숨기거나 화면을 닫아도 남은 규칙을 이어서 보관해요.

### 규칙마다 명령을 만드는 까닭

규칙 상세는 그 규칙의 마지막 `rule_archive` 명령에서 마지막 폴더 이동을 보여 주고, 한 규칙에는 열린 `rule_archive` 명령이 하나뿐이에요. 일괄 보관 명령 안에서 바로 보관하면 이 둘이 깨지므로, 규칙마다 명령을 만들어요. 그래서 규칙 하나를 보관하는 동작(규칙 끄기, 폴더 이동, 같은 작품 폴더는 마지막 규칙에서 한 번 옮기기, 까닭 문장, 다시 시도)은 그대로예요.

### 명령과 실행

- 본문은 `{"rules":[{"rule_id":…,"name":…}]}`이에요. 규칙은 하나 이상이고 서로 달라야 하며, `rule_id`는 64바이트, `name`은 500자까지예요. `name`은 화면이 보여 준 제목으로, 화면의 문장에만 써요. 개수 상한은 없어요. 처음에 둔 100개 상한은 화면이 하던 일을 바꾸므로 리뷰에서 뺐어요.
- 대상은 하나로 고정돼서 일괄 보관은 한 번에 하나만 열려요. 다른 탭에서 동시에 보내면 409 `다른 일괄 보관이 진행 중이에요. 그 결과가 나올 때까지 기다려 주세요.`로 거절해요. 예전에는 두 탭이 서로 다른 규칙을 나란히 보관할 수 있었는데, 같은 종류와 대상으로 열린 명령은 하나뿐이라는 명령 규칙을 따른 거예요.
- 규칙마다 만드는 명령의 ID는 `{일괄 보관 ID}-{순번}`이에요. 프로세스가 도중에 멈춰 일괄 보관을 다시 실행하면 같은 ID로 다시 접수해서, 이미 있는 명령을 돌려받아요. 끝난 규칙은 건너뛰고, 열린 규칙은 따라가요.
- 규칙 명령이 끝나기를 기다릴 때는 바뀜 채널([0154](0154-change-events-and-command-reads.md))을 먼저 듣고 읽어요. 그 명령이 바뀌었다는 이벤트, 채널이 뒤처졌다는 신호, 3초 대기 중 먼저 온 것에 다시 읽어서, 이벤트를 놓쳐도 멈추지 않아요. 규칙 명령을 만들면 명령 루프를 깨워 곧바로 시작하게 해요.
- 규칙 명령이 실패하면 일괄 보관은 `rule_failed`로, 그 규칙에 다른 보관 명령이 열려 있거나 규칙이 없으면 `refused`로 끝나요. 멈춘 규칙의 순번은 일괄 보관의 결과에 적어요. 시도 횟수를 넘겨 포기된 일괄 보관은 규칙을 가리키지 않아요. 리뷰에서 나온 것으로, 처음에는 끝난 규칙 수에서 실패한 규칙을 셌어서 포기된 뒤 끝난 규칙 명령이 시작도 안 한 규칙을 가리킬 수 있었어요.
- 일괄 보관은 폴더 차례와 토렌트 관문을 잡지 않아요. 규칙 명령이 잡아요. 수집 주기가 떠난 토렌트를 지울지 판단할 때 세는 "앞선 실행이 남긴 명령"에서도 일괄 보관은 빠져요. 다시 시작한 뒤의 일괄 보관이 그 정리를 끝날 때까지 막지 않게 하려는 것으로, 리뷰에서 나온 것이에요.
- 실행 코드는 기능 크레이트가 아니라 `trss` 크레이트의 `archive_batch`에 있어요. 명령 루프를 깨우는 `Wakes`가 `trss`에 있어서예요. 그래서 순서, 멈춤, 다시 시작을 확인하는 테스트도 `trss` 크레이트에 있어요.

### 읽는 경로와 화면

- `GET /api/archive-batches/{id}`와 `GET /api/archive-batches/current`가 일괄 보관의 상태, 전체 수, 끝난 수, 지금 규칙, 실패(규칙, 까닭, 거절인지)를 돌려줘요. `current`는 열린 일괄 보관이 없으면 404예요.
- 화면은 탭에 하나뿐인 `BatchTracker`로 일괄 보관을 보내고 따라가요. 그 일괄 보관 명령의 이벤트에 다시 읽고, 주기 조회를 하지 않아요. 화면이 사라져도 추적기는 끝까지 따라가 규칙마다 제안을 지우고 끝에 캐시를 정리해요. 예전 화면의 반복도 화면이 사라진 뒤 끝까지 돌며 정리했어서, 리뷰에서 그대로 맞췄어요. 화면을 다시 열면 진행 중인 일괄 보관을 찾아 보여 줘요.
- 진행 문장과 실패 문장은 지금과 같아요. 일괄 보관 전체를 거절한 경우(빈 요청, 다른 일괄 보관이 열림)는 예전에 없던 경우라 앞에 규칙 이름을 붙이지 않고, 규칙을 가리키지 않는 실패에는 `일괄 보관이 끝까지 가지 못했어요…`를 써요. 진행 숫자는 전체 수를 넘지 않아요.
- 보내기에 응답이 없을 때 다시 보내는 횟수와 간격, 읽기를 다시 하는 1초 간격과 실패를 견디는 횟수는 예전과 같아요.

### 개발 환경에서 확인

2026-10-21에 이 PC의 개발 환경(서버 DB 사본, 이 변경으로 빌드한 이미지, 로컬 Transmission)을 Vite 개발 서버와 built-in browser로 봤어요. 보관 제안이 없어서 DB를 백업한 뒤 규칙 셋에 지난 종영일을 넣은 구독을 만들었고, 확인한 뒤 DB와 폴더를 되돌렸어요. 숨김은 `visibilitychange`를 흉내 냈어요.

- 제안 3개를 `모두 보관`하자 첫 규칙에 Transmission이 덜 받은 토렌트가 있어 거기서 멈추고, `0개를 보관하고 멈췄어요. ‘…’을 옮기지 못했어요.`와 까닭을 보였어요. 그 뒤의 규칙은 옮기지 않았어요.
- 리뷰를 고친 이미지에서, Transmission 컨테이너를 잠시 멈춘 채 제안 2개를 `모두 보관`하고 0.3초 뒤 탭을 숨겼어요. 화면은 `(1/2)`에 멈춘 채 이벤트를 하나도 받지 않았고, 그동안 서버가 첫 규칙(2.2초)과 둘째 규칙을 옮겨 일괄 보관이 `done`이 됐어요. 둘째 규칙은 모두 숨긴 동안 실행됐어요. 다시 보이자 `ready` 뒤 한 번 읽고 `2개를 보관했어요.`를 보였어요.
- 같은 준비로 `모두 보관`한 뒤 앱 안에서 설정 화면으로 옮겼어요. 추적기는 그 화면에서도 이벤트에 일괄 보관을 읽었고, 끝난 뒤 구독으로 돌아오자 `2개를 보관했어요.`가 보이고 남은 제안이 없었어요.

확인하지 않은 것은 다음과 같아요.

- 브라우저가 실제로 탭을 숨길 때
- 설정 화면에서 돌아온 직후 옛 제안이 잠깐 보이는지: built-in browser 창이 가려져 화면을 프레임마다 읽지 못했어요.
- `ArchiveSuggestions.tsx`의 연결: 자동 테스트가 없고 추적기만 node 테스트가 있어요.
- 서버(j4105)의 Transmission을 거친 일괄 보관

### 검토

구현은 `stora:task` 에이전트가 했고, 독립 검토(`stora:reviewer`)는 막는 문제가 없다고 봤어요. 지적 여덟 가지 가운데 일곱은 위에 적은 대로 고쳤어요. 개수 상한, 실패한 규칙 기록, 결과를 확인하지 못한 뒤의 정리, 화면을 닫은 뒤의 정리, 떠난 토렌트 정리, 주석과 문서, 길이 제한이에요. 남은 하나(단일 실행으로 일괄 보관을 돌리면 멈춘다)는 테스트 도우미의 한계라 `Worker::run_commands` 문서에 적었어요.
