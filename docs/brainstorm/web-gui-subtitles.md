# 웹 GUI와 자막 수작업 개선

## 현재 방향

사용자는 자막(Subtitle)을 하나씩 내려받아 정리하는 수작업을 줄이고, 작품·다운로드 규칙·자막 작업을 웹에서 함께 관리하고 싶어 해요.
보통 Anissia에서 자막을 찾고 실제 이용 출처로 erulabo를 제시했으며, 대상 영상은 trname 방식으로 정리돼 있어요.
앞으로 trss가 받는 영상뿐 아니라 기존 영상과 사용자가 지정한 폴더도 다루며, 한 사람이 집 안 네트워크나 VPN에서 사용하는 제품이에요.
사용자가 제작자·회차 범위로 후보를 선택하면 다운로드·분류·보관·복사 적용을 이어가고, 필요한 CAPTCHA는 trss 작업 화면 안에서 직접 해결하는 방향으로 수렴했어요.

현재 요구와 관찰 가능한 완료 조건은 [웹 앱 공통 명세](../specs/web-app.md)와 거기서 나눈 주제별 명세로 이관했어요.
이 문서는 문제 배경, 선택 이유와 조사·실험 근거를 보존하며, 용어는 [용어집](../glossary.md), 선택의 권위는 아래 ADR에 있어요.
명세 이관은 구현 완료가 아니며, 후속 제안이 이 문서에 추가되더라도 명세의 요구를 자동으로 바꾸지 않아요.

## 선택지와 근거

- 후보까지 자동 선택하기보다 제작자·회차 범위 선택은 사용자에게 남기고, 그 뒤의 반복 파일 작업을 줄이는 방향을 선택했어요.
  수동 다운로드 후 GUI 업로드는 인증 뒤 자동 처리를 대신할 수 없어요.
- [앱 관리 설정](../adr/0001-app-managed-download-rules.md)을 선택해 웹 편집 후 외부 YAML에 다시 반영하는 단계를 없애요.
  설정·보관 정보는 선택한 항목만 가져오며, 새 규격의 규칙별 선택을 지원하되 기존 YAML은 채널 단위로 유지해요.
- [서버 브라우저 인증](../adr/0002-server-browser-subtitle-authentication.md)은 사용자 PC의 확장 설치·파일 전달 대신 서버가 브라우저 운영을 맡는 선택이에요.
  별도 창이 아닌 trss 페이지 내부 조작을 요구하고, 인증 대기 작업을 남기면서 유휴 브라우저와 실행별 사이트 상태는 정리하는 방향이에요.
- [보관본과 적용본 분리](../adr/0003-stored-and-applied-subtitles.md)는 여러 자막의 재생기 선택을 파일명 표식으로 통제하는 대안 대신 선택했어요.
  작품과 함께 이동·보관할 수 있도록 작품 안 숨김 폴더를 사용하고, 적용본은 이동·링크가 아닌 독립 복사로 만들어 원본과 이전 수정본을 보호해요.
  처음에는 우선 형식 하나를 적용하되 다른 형식의 선택적 추가 적용은 남겨요.
  숨김 보관 폴더 내부도 제작자·회차·수정본과 원래 이름을 사람이 구분할 수 있게 배치하고, 공유 폰트는 수정본마다 복제하지 않아요.
- erulabo만 먼저 지원하는 대안보다 조사한 Blogger·Drive, Tistory 일반 첨부·WinPNG, Naver 첨부까지 모두 첫 지원 범위로 선택했어요.
  표본 수신 성공을 제품 지원 완료로 해석하지 않아요.
  Anissia는 한국어 자막을 제공한다는 사용자 설명을 기준으로 다국어 선호 설정은 두지 않고, 자동 처리 형식은 ASS·SRT·SMI로 정했어요.
- 영상 준비 전 자막을 받아 보관하면 재다운로드·재인증을 피할 수 있어요.
  자동 삭제하지 않는 대신 대기 파일과 이전 수정본이 쌓일 수 있다는 비용을 수용해요.
- 후보는 화면을 닫아도 주기적으로 확인하되, 오래된 대상의 반복 조회는 제한하는 방향을 선택했어요.
  조회 중단 이후의 새 자막·수정을 놓칠 수 있으므로 최초 조회와 수동 새로고침은 별도로 남겨요.
- 폰트 중복 저장과 중복 전송을 구분하고, 부분 수신이 불가능한 묶음은 전체 수신을 허용해 새 자막·폰트 처리가 막히지 않게 해요.
- Transmission 제어 기능은 기존 화면을 이용하고 trss에는 상태 확인·이동만 두어 중복 구현을 피하기로 했어요.
- [Rust·axum과 React·TypeScript](../adr/0004-rust-react-web-stack.md)를 선택해 기존 서버 코드를 재사용하고 상호작용이 많은 화면을 구성해요.
  프런트엔드는 정적 번들로 제공해 운영용 Node 서버를 추가하지 않아요.
- [로컬 SQLite](../adr/0005-local-sqlite-app-state.md)를 선택해 앱 상태를 영속화하고 별도 DB 서버 운영을 피하기로 했어요.
  보관 관계를 작품 폴더의 별도 목록에도 유지하는 대신, 설정·보관 정보를 내보내고 실제 파일은 작품 폴더로 따로 옮기는 방식을 선택했어요.
  작업 이력·큐·과거 승인과 파일 바이트는 내보내기에 포함하지 않아요.
- [공통 Rust 라이브러리와 별도 웹·worker 바이너리](../adr/0006-separate-web-worker-binaries.md)를 선택해 코드와 배포 버전은 공유하면서 실행 역할과 재시작 단위를 나눠요.
  Chromium은 별도 비공개 컨테이너로 분리하되, 이 선택을 속도 향상의 실측 근거로 취급하지 않아요.

## 채택한 시안과 검토 근거

사용자 검토에서 홈·작품 목록·작품 상세의 정보 배치와 밝은 사쿠라 톤을 디자인 기준으로 채택했어요.
현재 화면 요구와 관찰 가능한 완료 조건은 명세에 이관했고, 이후 [웹 재설계](web-redesign.md)가 대체해 지금은 [웹 앱 공통 명세](../specs/web-app.md)와 주제별 명세에 있어요.
이 문서에는 선택 이유와 시안별 관찰 근거를 남기며, 아래의 과거 비교 결과를 현재 요구나 제품 구현 완료로 해석하지 않아요.

기준 시안은 로컬 브랜치 `prototype/sakura-web-design-review-1`의 커밋 `4f7895f66ef335b3294b424bda024ff274737e9a`에 보존했어요.
해당 커밋의 `.scratch/sakura-web-design/prototype`에 소스·표지·스틸·출처 기록이 함께 있으며, 현재 임시 폴더와 별개로 복원할 수 있어요.
원격에 게시하거나 제품 코드에 합치지는 않았어요.

### 화면 선택 이유

- 목록의 `보관`·`적용` 구분이 이해되지 않아 실제 받은 자막의 회차 범위로 단순화하고, 목록 안의 펼치는 미리보기 대신 작품 상세로 이동하는 방향을 선택했어요.
  정상 보유·배치 완료 설명의 반복은 줄이되, 파일 대기나 교체 대기를 이해하는 데 필요한 현재 상태는 남겨요.
  내부 보관 관계나 안전 조건을 없애거나 정상 최초 수신에 반복적인 수동 적용을 요구하는 선택은 아니에요.
- 에피소드는 점검 우선의 정렬된 행을 선택했어요.
  누락 탐색은 짧아질 수 있지만 회차 순서대로 정상 항목을 볼 때 묶음을 펼치는 조작이 필요해요.
  제작자 배지·라벨 행과 파일별 묶음을 비교한 뒤 열 정렬과 상시 파일 정보를 선택했고, 개별 파일 정보의 접기는 제거했어요.
- 시즌의 작은 보유 요약 타일을 선택기로 재사용해 상태와 선택을 함께 보여줘요.
  별도 드롭다운은 보유 현황을 숨기고 가로 나열은 모바일 스크롤 문제를 되살리므로, 모바일은 현재 타일과 세로로 스크롤하는 바텀시트를 선택했어요.
- 무채색은 선호하지 않아 제외했고, `연한` 색을 어둡고 탁한 로즈로 해석하는 방향도 채택하지 않았어요.
  밝은 벚꽃 파스텔의 장식과 중립색 글자·포커스의 읽기 대비를 분리하며, 과한 그라데이션·통계 타일·반복되는 큰 둥근 카드 대신 차분한 바탕과 정렬된 목록을 지향해요.
- 회차 이미지는 별도 정보 열이 아닌 배경을 선택했어요.
  모바일의 꽉 찬 배경은 유지하면서 PC의 좁은 오른쪽 이미지는 왼쪽으로 넓히되, 내용에 따라 변하는 카드 높이와 이미지의 여유·페이드를 함께 유지하는 방향이에요.
  이미지 진하기 슬라이더는 비교 실험을 위한 제어였으며 제품 설정으로 채택한 것은 아니에요.

### 회차 이미지 자료의 한계

2026-09-27의 공개 응답에서 My Hero Academia FINAL SEASON은 총 11화에 스트리밍 항목 7개와 누적 번호 163–170의 일부가 반환됐고, SPY×FAMILY는 총 12화에 스트리밍 항목 25개가 반환됐어요.
[AniList 스트리밍 항목](https://docs.anilist.co/reference/object/mediastreamingepisode)은 안정적인 회차 ID·구조화된 회차 번호를 제공하지 않으므로 배열 위치나 외부 번호만으로 로컬 회차 이미지를 자동 연결하지 않아요.
시안에서는 프리렌 1·6화로 명시한 예시만 연결하며, 실제 파일의 회차 매칭·전체 이미지 수록 범위·이용 허락을 검증한 것으로 보지 않아요.

### 시안 자료와 검증

제품 코드와 분리된 정적 HTML·CSS·JavaScript 시안을 홈·작품 목록·작품 상세로 구성했어요.
실제 작품 정보·표지·원문 소개를 사용하고, 파일·후보·작업 상태와 추가 시각은 시뮬레이션으로 구분해요.
사용한 작품은 [카우보이 비밥](https://anilist.co/anime/1), [Death Note](https://anilist.co/anime/1535), [Attack on Titan](https://anilist.co/anime/16498), [장송의 프리렌](https://anilist.co/anime/154587), [스파이 패밀리](https://anilist.co/anime/140960), [너의 이름은.](https://anilist.co/anime/21519), [My Hero Academia](https://anilist.co/anime/21459)이며, 마지막 작품은 [FINAL SEASON](https://anilist.co/anime/182896)까지 TV 시즌 여덟 개의 개별 정보를 사용해요.
2026-09-27의 공개 정보 조회와 표지 수신은 HTTP 200이었고, 브라우저에서 표지 일곱 장의 정상 표시를 확인했어요.
시즌 번호는 시안의 명시적인 로컬 묶음이며, AniList의 방영 분기나 실제 파일의 시즌·에피소드 대응을 자동 판정한 결과가 아니에요.

현재 장식 강조색은 라이트 `#e6a2bc`·다크 `#eab9cc`의 밝은 핑크예요.
강조 글자는 기존 본문·보조 글자의 중립색을 사용해요.
다크 선택면은 밝은 핑크 8%와 기존 표면색의 혼합으로 제한했어요.
390px 작품 목록의 같은 상태를 양쪽 모드에서 직접 관찰했고, 1440px 파일 대기 화면에서도 선택 글자·상태 배지·체크를 확인했어요.
실제 단색 쌍에서 선택 글자와 상태 배지의 대비는 라이트 8.29:1·다크 8.10:1, 체크는 7.83:1·9.76:1이었으며 이미지 합성 픽셀의 대비는 포함하지 않아요.
다크의 실제 Tab 이동에서는 중립색 포커스 윤곽선이 남고 현재 화면이 바뀌지 않았어요.
이미지 배치·목록 상태의 구현은 변경하지 않았어요.

강조색을 다시 교정하기 전에 확인한 이미지·상태·색상의 근거는 다음과 같아요.

- 같은 작품 목록 화면을 라이트·다크로 전환해 바탕·선택면·강조선·글자·체크의 역할을 함께 관찰했어요.
  실제 적용된 단색 토큰 쌍에서 선택 배경에 대한 강조색 대비는 라이트 3.19:1·다크 3.39:1, 선택 글자는 6.60:1·6.40:1이었어요.
  작은 강조 글자의 최소 대비는 5.99:1·6.13:1이었으며, 이 계산은 이미지 합성 픽셀이나 전체 접근성·미감 판정을 포함하지 않아요.
- 320·390·700·701·768·1440px에서 프리렌 1·6화의 기본 파일명과 긴 임시 파일명을 비교했어요.
  모바일은 카드 안쪽을 계속 채웠고, PC는 카드 높이가 달라도 여백을 유지하며 사진이 최대 420×210px 안에 놓였고 카드 가로 넘침은 없었어요.
  좁은 PC에서 폭 비율만 사용하면 사진이 더 오른쪽으로 좁아지는 문제를 발견해 높이·최소 폭·카드 안쪽 상한을 함께 반영했어요.
  수정 뒤 두 실제 카드 모두 기본 상태에서 이전보다 왼쪽으로 넓어진 것을 계측하고, PC와 두 모바일 테마의 실제 화면도 확인했어요.
- 일곱 작품의 목록에서 정상 파일 보유 설명과 정상 본편의 추가 상태 영역은 없어졌고, 전체 보유 범위·수신 전 후보·파일 대기·교체 승인·회차 미확정 맥락은 남았어요.
  개별 에피소드의 상시 파일 정보는 별도 요구이므로 제거하지 않았어요.
  홈에서 Tab으로 작품 메뉴에 초점을 옮겨도 현재 화면은 홈으로 남고 포커스 윤곽선이 표시됐어요.

PC 이미지를 카드 높이로만 계산하고 라이트 강조를 옅게 했던 이전 시안에서는 다음을 확인했어요.

- Chromium 320·390·768·1440px의 라이트·다크에서 기본 파일명과 긴 임시 파일명을 비교했어요.
  카드 높이가 내용에 따라 늘어도 모바일 이미지는 카드 전체를 채웠고, 비모바일 이미지 폭은 높이와 원본 비율을 따라가다가 카드 폭에서 제한됐으며 가로 넘침은 없었어요.
  16:9 원본 외에 1:2·12:1 임시 이미지로도 모바일 채움과 비모바일 비율·폭 제한을 확인한 뒤 원복했어요.
  비모바일의 왼쪽 이미지 경계는 페이드로 연결하고, 모바일의 전체 배경 페이드는 유지했어요.
- 보유·없음 모두 `파일`과 `자막` 라벨은 13px였어요.
  일곱 작품의 상태는 대상과 항목·값으로 표시됐고, 파일 대기·수신 전 후보·교체 승인·회차 미확정·본편 배치 및 4·6화의 비연속 범위를 구분했어요.
  작품 목록도 네 너비와 두 화면 모드에서 가로 넘침이 없었고, 모바일 상태 목록과 PC·모바일 에피소드 화면을 직접 관찰했어요.
- 라이트의 장식 강조색은 `#e9b1c5`, 작은 강조 글자는 `#896674`, 선택·링크 글자는 `#705760`으로 적용했어요.
  실제 적용된 단색 쌍으로 계산한 작은 강조 글자 대비는 4.70:1, 선택 글자는 5.37:1, 체크는 라이트 5.11:1·다크 4.51:1이었어요.
  이 수치는 이미지와 합성된 글자 픽셀의 명암비나 전체 접근성 감사 결과는 아니에요.
  전환이 끝난 화면에서 연한 선택 배경과 강조선을 확인했으며, 무채색 제어는 제거했어요.

전체 배경 이미지와 로즈·무채색을 비교했던 이전 시안에서는 다음을 확인했어요.

- Chromium 320·390·768·1440px의 두 팔레트·라이트·다크 16조합에서 가로 넘침 없이 파일 정보가 표시되고, 이미지가 카드 전체 폭에서 85% 불투명도로 남았어요.
  보유 체크는 15px, 인접 글자는 13px였고, 모바일 하단바는 일반 좌우 여백 없이 화면 안쪽 양 끝까지 닿았어요.
- 프리렌 원문의 마지막 출처 문단까지 표시됐어요.
  734자의 임시 줄거리도 두 문단과 `&`를 포함한 기대 문자열과 정확히 일치했고, 삽입한 SVG·스크립트는 실행되거나 본문 요소로 생성되지 않았으며 원문으로 복원했어요.
- 교체 승인 대기의 현재 A/SRT와 대안 B/ASS·승인 조건, 파일 대기 중인 B/ASS의 미배치 사유가 개별 펼치기 없이 노출됐어요.
  후보만 있는 회차는 자막 없음으로 남고, 극장판 본편과 회차 미확정의 별도 경고도 유지됐어요.
- 작품 목록의 상태 일곱 가지는 의미별 줄로 나뉘었고, 320·768px에서 목록과 항목의 가로 넘침이 없었어요.
  390px 라이트·1440px 다크의 무채색 목록과 모바일 에피소드 캡처에서 이미지의 색, 작은 보유 체크, 메뉴의 선택 체크 제거와 양 끝까지 이어진 하단바를 관찰했어요.
- 전환 완료 뒤 로즈와 무채색의 라이트·다크 강조색을 확인했고, 무채색의 배경·현재 메뉴·표시선은 회색 계열이었어요.
  독립 소스 검토에서 팔레트 버튼 선택자가 문서 루트까지 포함해 두 버튼의 선택 표시를 지우는 결함을 발견했고, 실제 발생을 확인한 뒤 버튼으로 범위를 제한했어요.
  수정 후 선택된 버튼 하나만 `aria-pressed=true`였고, 다른 조작과 작품 이동 뒤에도 무채색 선택이 유지됐어요.

그 이전의 보호된 본문·오른쪽 이미지 및 파일별 묶음·정렬된 행 비교에서는 다음을 관찰했어요.
이때의 명암비는 이후 선택한 전체 배경 이미지와 작은 체크의 대비를 입증하지 않아요.

- Chromium의 320·390·768·1440px, 라이트·다크에서 두 구조의 본문과 펼친 파일 정보가 보호 영역 안에 있고 가로 넘침이 없는지 확인했어요.
  표본의 회차·제작자·보유 표시·파일 정보 텍스트 명암비는 라이트 최소 5.19:1, 다크 최소 6.40:1이었고, 23px 원형 체크의 전경·배경 명암비는 각각 8.23:1·9.04:1이었어요.
  본문 배경을 임시로 투명하게 바꾼 입력은 불투명 보호 확인에서 실패했고, 원복한 상태는 통과했어요.
- 두 구조의 실제 화면을 관찰한 뒤, 이미지가 있는 행과 없는 행에서 열 위치가 달라지는 문제를 수정했어요.
  수정 후 320·390·768·1440px에서 회차·파일·자막·제작자 열의 좌표가 일치했고, 1051px의 데스크톱 전환 경계에서도 정보가 보호 영역을 벗어나지 않았어요.
  마지막 열 수정 뒤의 추가 캡처는 도구 타임아웃으로 얻지 못했으며, 해당 수정의 재확인은 브라우저의 실제 요소 좌표와 영역 계측에 한정돼요.
- 두 구조 모두 파일 대기 중인 B/ASS, 기존 A/SRT를 유지한 교체 승인 대기, 후보만 있는 회차와 극장판 본편을 구분했어요.
  구조를 전환해도 펼친 파일 정보와 대기 사유·현재 자막·교체 대안 파일 및 승인 조건이 유지됐어요.
  회차 미확정 파일은 계속 상단 경고로 분리해요.
- 네 너비에서 시즌 8에서 1로 선택을 바꿔도 같은 시즌 타일의 너비·높이는 변하지 않았어요.
  홈의 상단 후보 링크를 일시적으로 숨긴 전후에도 카드 높이가 같았고, 링크는 본문과 겹치지 않았어요.
  후보 링크와 항목 본문을 각각 눌러 같은 후보 탭으로 이동하는 것을 확인했어요.
- 사이드바 부제와 작품 정보의 `실제 AniList` 안내가 제거됐어요.
  PC의 세로 표시선과 모바일 하단바의 가로 표시선은 탭의 전체 안쪽 길이를 사용하고, 실제 Tab 키로 다른 메뉴에 초점을 옮겨도 현재 화면·현재 메뉴 표시는 바뀌지 않았어요.
  키보드 초점에는 분홍색 표시선과 윤곽선이 함께 남았어요.

이전 비교에서 확인한 자료·상태·탐색의 근거는 다음과 같으며, 새 구조의 검증과 구분해요.

- 등록된 시즌 14개의 방영 상태·시간·주요 스튜디오는 각 Media 응답을 사용해요.
  프리렌 1·6화 JPEG는 전체 수신 HTTP 200과 640×360 디코딩을 확인했고, 접힌 정상 항목을 펼쳐 노출한 뒤 브라우저에서도 표시됐어요.
- 초기 큰 행·큰 타일·점검 우선과 두 시즌 선택 방식의 여섯 조합, 이후 시즌 행·타일과 옆·배경 이미지, 제작자 배지·라벨 행을 각각 네 너비에서 비교했어요.
  각 단계에서 가로 넘침을 확인했고, 초기 여섯 조합에서는 불필요한 탭 세로 넘침도 없었어요.
  이미지·제작자 비교는 라이트·다크와 펼친 파일 정보도 관찰했어요.
  옆 이미지가 모바일에서 상단 이미지가 되던 배치를 수정해 옆 배치를 확인한 이력은 현재 선택한 배경 방식과 별개예요.
- 단일 시즌에서 선택 UI를 숨겨도 정보·보유 범위·출처 접근이 남았고, 대표 작품과 유일한 시즌의 출처가 다른 예시를 브라우저에서 구성해 별도 시즌 링크를 확인한 뒤 원복했어요.
  여러 시즌은 모바일에 현재 시즌만 남기고 바텀시트에서 선택했으며, 터치 선택·후보 탭 유지·열기 버튼 초점 복귀와 Escape·배경·닫기 버튼 동작을 확인했어요.
  시즌 외부 링크는 외부 이동만 차단한 클릭 관찰에서 현재 시즌이나 열린 창을 변경하지 않았어요.
- 홈·작품 항목의 빈 공간 이동, 일반 진입의 최신 시즌 8과 홈의 명시된 시즌 1, 시즌 변경의 스크롤·선택 초점·내용 갱신을 확인했어요.
  작품 호버는 제목 밑줄 없이 배경을 바꾸고, 선택 체크가 표시되며, 중첩 링크가 없는 것도 확인했어요.
  독립 소스 검토에서 발견한 현재 시즌 재선택의 초점 손실과 뒤로 간 다른 작품에 바텀시트가 남는 문제는 재현·수정 후 선택 링크와 새 작품 제목 초점으로 재확인했어요.
- 다섯 정렬을 예시 날짜·제목·시즌 연도의 예상 순서와 비교했고, 선택값은 상세 이동·뒤로 가기·새로고침·같은 브라우저의 새 페이지에서도 유지됐어요.
  초기 45% 슬라이더에서는 키보드 0%·100%·45→46% 변경과 이미지에만 적용되는 불투명도를 확인했어요.
  시안의 진하기·표현 선택은 페이지 내 이동에만 유지하고 새로고침하면 현재 기본값으로 돌아가는 실험 제어이며, 제품 설정 저장의 증거는 아니에요.
- 비교 과정에서 중간 자막 누락 4·6화의 우선 표시, 정상 묶음 펼치기, 후보만 있는 작품, 미확정 경고, 파일 대기, 기존 자막을 유지한 교체 대안과 극장판 본편의 상태를 보존했어요.
  홈의 확인 필요·새 후보 표지와 진행·완료의 이미지 제외, 검색 유지, 시스템 테마 반응, 키보드 시즌·탭 이동 및 깨진 표지에서도 남는 제목·상세 링크를 확인했어요.
  정상 최초 수신에 별도 적용 조작은 없지만 실제 파일 복사를 수행한 증거는 아니에요.

소스 독립 검토와 브라우저 관찰을 함께 사용했으며, 소스 검토 당시에는 시안이 비추적 상태여서 Git 패치 전후 비교에 한계가 있었어요.
수치·동작 검증은 미감이나 선호를 확정하지 않으며, 디자인 채택은 사용자의 시안 검토 결과에 근거해요.
실제 기기·가상 키보드·전체 접근성 감사, 기기 간 정렬 동기화와 제품의 자막 처리·원격 인증·자동 표지 매칭은 검증하지 않았어요.

후보 묶음과 비교 표시 방식은 [자막 명세](../specs/subtitles.md)의 [후보 조회](../specs/subtitles.md#자막-후보-조회)와 [교체 비교](../specs/subtitles.md#교체-비교와-승인)에 반영했어요.

채널을 먼저 선택하는 관리 화면 대신 작품과 규칙을 각각 통합 목록으로 보는 방향을 선택했어요.
RSS 채널은 작품 분류가 아니라 수집 경로·설정으로 다뤄요.
규칙 하나를 여러 채널에서 공유하는 대안은 선택하지 않고, 규칙마다 채널 하나에 연결하는 관계와 채널 안의 평가 순서를 유지해요.
이를 [설정 ADR](../adr/0001-app-managed-download-rules.md)에 반영했으며, 목록의 표시 정렬과 실행 우선순위는 구분해요.
규칙 편집은 PC에서 전체 목록을 함께 보는 병렬 배치를 선택하고, 모바일에서는 편집 화면으로 전환해요.
설정은 한 페이지에 모두 펼치는 안보다 관련 항목에 집중할 수 있는 세 탭을 선택했어요.

후보는 회차별 대안을 나란히 묶기보다 같은 제작자의 여러 회차를 고르는 흐름에 맞춰 제작자·출처별 묶음을 선택했어요.
작업 상세는 원래 목록을 옆에 남기는 PC 패널 대신 비교·원격 화면의 공간을 확보하는 전용 페이지를 선택했어요.
비교는 긴 상세 차이를 모두 펼쳐 시작하는 대신 요약을 먼저 보는 방향으로 정했으며, 경고와 실제 변경 경로는 처음부터 확인할 수 있게 해요.
작품을 이미지로도 구분할 수 있도록 표지와 정보를 나란히 배치하는 목록형을 선택했어요.
목록형에서도 표지를 작게 제한하지 않고, 표지의 시각적 비중과 상태 정보의 정렬을 함께 유지하는 방향이에요.
표지 중심 카드형도 비교했지만 선택하지 않았어요.

표지 확보는 검색 결과마다 사람이 먼저 고르는 안보다 명확한 후보의 자동 지정을 포함하되, 잘못된 표지를 사용자가 다시 고를 수 있게 해요.
제공자로 AniList를 선택하고, 직접 지정은 임의 URL 입력이 아니라 이미지 파일 업로드만 받으며, 작품 폴더의 `.trss-artwork/`에 앱이 관리하는 파일로 보관하기로 했어요.
표지 파일을 작품과 함께 옮길 수 있고 앱이 받는 외부 URL의 범위를 제한하는 선택으로, DB 관계와 YAML 메타데이터는 파일 바이트 백업을 대신하지 않아요.
제품의 표지 자동 검색·매칭·수신 흐름과 실제 PC·모바일 화면은 아직 구현·검증하지 않았으며, 프로토타입용 개별 정보·이미지 조회와 구분해요.
기존 Anissia 클라이언트의 자막 메타데이터와 trname의 경로 정리는 표지 URL이나 다른 서비스의 작품 ID를 제공하는 연동이 아니에요.
확인한 [Anissia API 문서](https://github.com/anissia-net/anissia/blob/master/docs/anime_schdule.md)의 작품·자막 필드에도 표지 정보가 없으며, trname의 TheTVDB식 명명만으로 TheTVDB 작품 연결이 확보됐다고 간주하지 않아요.
공식 문서에는 Anissia의 제목 `subject` 외에 선택적 원제 `originalSubject`와 시작일 `startDate`가 있어 검색 힌트로 사용할 수 있어요.
값이 없을 수 있고 특정 시즌의 시작일일 수 있으므로, 외부 작품 ID나 시리즈 최초 방영일과 같다고 간주하지 않아요.
자막 갱신일 `updDt`를 작품 방영 연도로 대신 쓰지 않아요.

### 표지 제공자 비교

초기 제공자는 [표지 ADR](../adr/0007-anilist-work-artwork.md)에 따라 AniList로 정했으며, 다음은 선택에 사용한 공식 문서상의 기능·운영 조건 비교예요.
제공자 비교는 공식 문서에 근거하며, 위의 시안 검증은 선택한 AniList의 작품·시즌 정보와 이미지를 개별 조회한 범위에 한정돼요.
정해진 작품을 대상으로 한 조회는 제목 검색의 전반적인 수록 범위·자동 매칭 정확도나 제품의 표지 수명 관리를 검증한 결과가 아니에요.

애니메이션 중심의 개인용 trss에서 키 없이 제목·표지를 조회하는 단순성을 우선해 AniList 하나를 선택했으며, 실제 한국어 검색 정확도가 더 높다고 검증한 판단은 아니에요.
TMDB의 원제·번역·별칭 검색과 작품·시즌 포스터도 대안이지만, 현재 범위에서 키 설정과 6개월 캐시 관리를 추가할 만큼의 이점은 확인하지 못했어요.
처음부터 여러 제공자를 통합하지 않아요.

AniList는 제목이 고유하지 않아 첫 검색 결과가 의도한 작품이라는 보장이 없다고 명시해요.
약관의 경쟁 서비스·대량 수집 제한이 trss의 구체적인 사용에 어떻게 적용되는지는 확인하지 않았으며, 고정 보관 기간이 명시되지 않았다고 영구 보관 권리가 보장되는 것은 아니에요.

TMDB 약관은 API에서 얻은 정보의 6개월 초과 캐시를 금지하고, 라이선스 종료 시 캐시를 포함한 TMDB 콘텐츠를 신속히 삭제하도록 요구해요.
TMDB를 선택한다면 자동 갱신이나 만료 처리 비용이 생기므로, 그 표지를 무기한 유지할 일반 자막 보관본과 같은 것으로 취급할 수 없어요.
TMDB는 로고와 지정 고지 문구를 요구하고, FAQ의 짧은 예시와 문구가 다르므로 [현재 API 약관의 Attribution 절](https://www.themoviedb.org/api-terms-of-use)을 기준으로 삼아요.

TheTVDB는 [현재 요금표](https://thetvdb.com/api-information)에 연 매출 5만 달러 미만 무료·출처 표시 구간을 두며, [구독 방식](https://thetvdb.com/subscribe)은 사용자당 연 11.99달러로 안내해요.
[프로젝트 키 발급·승인](https://support.thetvdb.com/kb/faq.php?id=62)과 [구독자 PIN](https://support.thetvdb.com/kb/faq.php?id=82)은 별개이고, trname의 명명 형식이 이 접근 자격을 제공하지 않아요.
[TheTVDB 약관](https://thetvdb.com/tos)은 API 라이선스가 관련 이미지의 사용·표시 권한까지 부여하지 않는다고 명시해요.

어느 제공자든 API 접근·이미지 URL 제공을 이미지 저작권 소유나 무제한 재배포 허가로 해석하지 않으며, 이 구분이 모든 개인 이미지 표시를 금지한다는 뜻도 아니에요.

가장 유력한 후보를 우선 붙이는 안 대신, 명확한 후보만 자동 지정하고 모호하면 표지 없이 남기는 정책을 선택했어요.
수동 선택이 늘 수 있더라도 잘못된 표지를 줄이는 방향이며, 표지 미지정 때문에 영상·자막 작업을 막지 않아요.

### 첫 화면 선택 이유

첫 화면 대안 중 별도 요약 홈을 선택해, 작품·작업 목록 외에 요약 화면을 유지하는 비용을 받아들였어요.
이는 화면 방향의 선택이며 실제 사용 빈도를 측정한 결과는 아니에요.

| --- | --- |
| 작품 목록 | 작품·시즌·자막 선택으로 바로 들어가며, 다른 작품의 막힌 작업은 눈에 띄는 작업 표시나 탐색으로 연결해야 해요. |

| 별도 요약 홈 | 새 후보와 막힌 작업을 함께 요약하지만, 작품·작업 목록과 별개의 요약 화면도 유지해요. |

## 현재 제품의 근거와 한계

- [README](../../readme.md)는 RSS 피드(RSS Feed)의 항목을 규칙에 따라 Transmission에 추가하고 파일명을 변경하는 도구로 설명해요.

저장소 코드와 공개 출처 조사에 더해, 2026-09-26에 출처별 실제 경로 확인을 시작했어요.
trss 제품 코드는 아직 실행·변경하지 않았으며, 파일 수신과 형식 확인 결과는 아래의 각 출처 근거에 한정돼요.
수동 작업, Anissia 사용, 모든 대상 폴더·파일명의 trname 정리, 같은 회차 중복 영상이 거의 없다는 설명은 사용자 보고예요.
주 실행 경로에서도 영상 파일명 변경에 trname을 사용하는 것을 확인했지만, 사용자의 실제 파일 구조를 직접 검사한 것은 아니에요.
공개 Anissia API와 연결된 일부 게시물을 읽기 전용으로 조사했으며, 사용자가 실제로 이용하는 출처로 erulabo를 제시했어요.

### 공개 자막 경로 조사

2026-09-25의 [Anissia 최근 자막 API](https://api.anissia.net/anime/caption/recent/0)와 공개 게시물 조사에서는 작품·회차·제작자·갱신 시각과 외부 게시물 주소를 확인했어요.
최근 자막 응답의 `updDt`는 후보별 날짜이며, 같은 작품·회차도 제작자에 따라 다른 값을 가질 수 있어요.
응답에는 자막 최초 공개일이나 회차 방영일을 구분하는 필드가 없고, `updDt`가 원본 파일의 어떤 변경을 반영하는지도 확인되지 않았어요.
따라서 자동 조회의 나이 기준으로 이 값을 쓴다면 Anissia에 표시된 후보 갱신일이라는 의미로 한정하며, 실제 자막 최초 공개일이나 영상 방영일로 간주하지 않아요.

[공식 API 문서](https://github.com/anissia-net/anissia/blob/master/docs/anime_schdule.md)의 자막 정보 절은 `updDt`를 `2012-02-01 00:00:00` 형태의 자막등록시간으로 설명하고 모든 날짜·시간에 `Asia/Seoul(+09:00)`을 적용한다고 명시해요.
[응답 DTO](https://github.com/anissia-net/anissia/blob/master/anissia-core/src/main/kotlin/anissia/anime/api/dto/CaptionDtos.kt)도 일반·최근 자막 응답에서 같은 형식의 문자열을 만들어요.
이는 날짜 해석의 근거이며, 원본 파일 변경이나 최초 공개 시각의 의미까지 입증하지는 않아요.

2026-09-26에는 아래 표본의 실제 파일 수신과 구조를 확인했어요.
이는 출처별 접근 방식의 타당성 근거이며 trss의 지원 구현, 영상과의 싱크, 자동 배치 성공을 뜻하지 않아요.
이 표본들에는 폰트가 없으며, 기존 폰트의 재수신 생략이나 ZIP의 부분 수신은 검증하지 않았어요.
개별 다운로드 링크가 있다는 사실만으로 파일 내용이 바뀌지 않았다고 판단할 수는 없어요.

#### 2026-10-02 경로별 재확인

[티켓 0033](../tickets/0033-source-paths-spike.md)에서 여섯 경로를 새 표본으로 다시 확인했어요.

서명 URL·쿠키·토큰·자막 본문은 저장소에 두지 않았고 받은 파일은 `.scratch/`에만 있어요.

- 브라우저에서도 받았어요. 저장 버튼을 한 번 누르면 `내 컴퓨터 저장`/`네이버 MYBOX에 저장` 선택 칸이 열릴 뿐이고(`se.22` 모듈이 첫 클릭의 기본 동작을 막아요), `내 컴퓨터 저장`을 한 번 더 눌러야 `window.open`으로 다운로드가 시작돼요. 프레임 안의 글(`blog.naver.com/<id>/<n>`)과 `PostView` 직접 열기 모두 같은 결과이고 HTTP와 바이트가 같았어요.
  2026-09-26에 다운로드가 보고되지 않았던 까닭은 첫 클릭이 선택 칸만 연 것과, 새 창이 시작하는 다운로드의 `Browser.download*` 이벤트를 페이지 연결에서 받지 못한 것으로 보여요. 이번에도 이벤트는 오지 않았지만 파일은 폴더에 떨어졌으므로 폴더를 보고 판단해야 해요.
- 다운로드 주소의 토큰은 게시물을 읽을 때마다 바뀌어요(첫 조각의 앞부분은 같고 뒤쪽 10자 안팎이 읽을 때마다 달라요). 먼저 받은 주소는 20분 넘게 계속 쓸 수 있었어요. 새 주소는 `PostView`를 다시 읽으면 얻어요.
  토큰을 바꾸면 400, `text/html`, 3,452바이트의 HTML이에요.
- 두 번째 제작자(zerocard2의 SMI 83,710바이트)와 elainalove1017의 글(`네죽사 1~8화 자막.zip` 106,408바이트와 ASS 하나)은 파일 정보만 읽고 받지 않았어요.

##### 게시물의 파일 정보를 다시 읽는 비용

Anissia 줄이 그대로인 게시물 수정이 실제로 있었는지와, 인증 없이 읽을 수 있는 값을 봤어요.

| 경로 | 인증 없이 다시 읽는 값 | 비용 |
| --- | --- | --- |
| erulabo | 게시물의 `dateModified`·카드 제목. 파일 크기·해시는 인증 뒤에야 보여 미상이에요. | 게시물 GET 약 170KB |
| Blogger·Drive | 파일 `Last-Modified`·`Content-Length`(`HEAD`로 읽어요), 게시물의 링크 목록과 JSON-LD `dateModified` | 파일당 `HEAD`(본문 없음), 링크 목록은 게시물 GET 90~220KB |
| Tistory 일반 | 게시물의 `article:modified_time`·파일 이름·거친 크기, 파일 주소에 `Range: bytes=0-0`을 건 응답의 정확한 전체 크기(206, 1바이트) | 게시물 GET 40~60KB + 파일당 1바이트 |

- Tistory·Drive·Naver 모두 `ETag`는 없었고, Drive만 `Last-Modified`가 있어요.
- 수정이 실제로 있었어요. 게시물 수정 시각이 Anissia 줄의 `updDt`보다 58시간 이상 늦은 게시물이 열한 곳 가운데 넷이었어요(하느 761·762, 스모모 461, C소라 season-3).
  Drive 파일은 여섯 개 가운데 둘이 `updDt`보다 13시간(별명따위 ZIP)·20시간(카이란 ASS) 뒤에 바뀌었고, 나머지 넷은 `updDt`보다 15분 안쪽 앞이었어요.
  이 시각은 게시물 수정이 곧 파일 변경이라는 뜻은 아니에요(글만 고쳐도 수정 시각은 바뀌어요).

##### Anissia 줄의 관찰

- 회차 표시 `0`: 작품별 자막 API 55줄 가운데 24줄이 `0`이고 그중 22줄은 주소가 비어 있었어요(아직 올리지 않은 줄로 보이지만 확인은 못 했어요).
  주소가 있으면서 `0`인 줄은 셋이에요. 극장판 게시물(스모모 420, 회차 번호 없는 `…Paradise.zip`), 유튜브 영상 주소(하느), 블로그 첫 화면 주소(코코렛, 2023년)예요.
  최근 자막 목록은 주소가 있는 줄만 주므로 70줄 가운데 `0`은 앞의 둘뿐이었어요.
  `0`이 등록 기본값이 남은 것인지 제작자가 고른 값인지는 미상이에요.
- 최근 70줄의 호스트는 Blogger 32, Tistory 24, Naver 7, erulabo 6, 유튜브 1로, 여섯 경로가 69줄을 덮어요. 유튜브 주소 같은 여섯 경로 밖의 주소가 줄에 올 수 있어요.
- 여러 회차를 담은 게시물은 열어 본 20개 가운데 7개예요(하느 761·762의 PNG, C소라 season-3·bang-dream의 ZIP, C소라 2026/07/2의 회차별 링크 열둘, 수퍼소닉EX의 49개 SMI ZIP, elainalove1017의 1~8화 ZIP). 나머지 13개는 회차 하나예요.
  제작자의 습관에 몰려 있고 끝난 작품의 마지막 게시물에 많아서, 비율을 일반화하지 않아요.
- 줄의 주소 변화: Anissia는 한 시점의 줄만 보여 주므로 같은 제작자·작품의 주소가 회차마다 바뀌었는지는 직접 보지 못했고, 아래는 주소·제목·시각에서 읽은 추정이에요.
  erulabo·스모모(Tistory)·수퍼소닉EX(Naver)는 회차 번호가 게시물 제목이나 주소에 들어 있고 같은 제작자의 줄마다 서로 다른 게시물이라 회차마다 새 게시물로 보여요.
  C소라·에텔레로사·이마이는 한 게시물을 고쳐 가요. Blogger 32줄 가운데 게시물 연월이 `updDt`보다 앞서는 줄이 15개이고(C소라 9, 에텔레로사 4, 카이란 1, 이마이 1), 이때 주소는 그대로고 회차 표시와 `updDt`만 바뀌는 것으로 보여요(C소라의 2026/07/2 게시물에는 13~24화 링크가 모두 있어요).
  Naver의 elainalove1017도 06-23에 쓴 한 게시물이 줄의 `updDt`(08-28)까지 이어졌어요.
- Anissia API의 `updDt`는 `2026-10-02T11:17:00`처럼 `T`로 이은 시간대 없는 값으로 왔어요(공식 문서의 예는 `2012-02-01 00:00:00`).

### 주요 출처 erulabo의 보안 확인

사용자가 제시한 [erulabo](https://erulabo.com/)의 [Anissia 연결 게시물](https://erulabo.com/854)에는 보안 확인 후 다운로드가 시작된다는 안내가 있어요.
2026-09-25에 해당 게시물과 [다운로드 스크립트](https://erulabo.com/js/download.js?v=20260923-1)를 읽기 전용으로 조사했어요.

- 클라이언트 코드는 자막 카드를 누르면 Cloudflare Turnstile을 실행하고, 완료 콜백의 토큰으로 `/file/<id>/token`에 요청해요.
  요청에는 CSRF 정보가 포함돼요.
- 성공 응답의 `download_url`로 새 탭을 열거나 현재 위치를 이동해요.
  인증 완료 후 사용자가 파일을 직접 업로드하거나 별도 다운로드 버튼을 다시 누르는 단계는 이 클라이언트 경로에 없어요.
- 이 코드는 사용자 인증 후 사이트가 다운로드로 이어가는 흐름의 근거예요.
  trss가 그 파일을 받아 영상 옆에 자동 배치할 수 있다는 실행 증거는 아니에요.

2026-09-26에 관리형 Chromium에서 다운로드 카드를 누르자 Turnstile의 `Verify you are human` 체크박스가 표시됐어요.
자동으로 인증을 처리하지 않고, 사용자가 직접 조작할 수 있는 Chrome을 OMP relay로 연결해 정상 인증 이후를 관찰했어요.
OMP relay는 이번 검증용 연결 도구이며 제품의 필수 의존성으로 선택한 것이 아니에요.

사용자의 직접 인증 후 `/file/<id>/token`이 HTTP 200으로 `download_url`과 `expires_in: 60`을 반환했어요.
발급 약 3.7초 뒤 사용자 다운로드 폴더에 저장된 `The Insipid Prince's Furtive Grab for the Throne - s01e12.zip`을 같은 컴퓨터의 프로그램에서 읽었어요.
ZIP 크기는 14,245바이트이고 CRC 검사를 통과했으며, 내부에는 47,068바이트의 `The Insipid Prince's Furtive Grab for the Throne - s01e12.ko.ass` 한 개가 있었어요.
ASS의 `[Script Info]`, `[Events]`, Style 10행과 Dialogue 497행을 확인했어요.
다운로드된 사용자 파일은 이동·삭제하지 않았고, 검증용 브라우저 연결과 응답 기록을 해제했어요.
서명 URL이나 인증 토큰은 저장소에 기록하지 않았어요.

추가 파일 요청은 URL 발급 92초 뒤에 수행돼 HTTP 403과 HTML 오류 페이지를 받았어요.
서버가 안내한 60초 유효기간 밖에서 수행한 요청이므로, 이 403을 정상 다운로드 실패나 유효한 URL의 세션·IP 종속성에 대한 증거로 사용하지 않아요.
정상 브라우저 다운로드는 이미 완료됐으며, 유효기간 내 별도 HTTP 클라이언트의 수신은 미검증이에요.

이번 실험은 사용자 인증 후 사이트가 다운로드를 이어가고 같은 컴퓨터의 프로그램이 실제 자막 바이트를 읽을 수 있음을 보여줘요.
relay에서 다운로드 경로를 지정한 연결은 도구의 `Browser target is not found` 오류로 실패했지만, 경로 지정을 빼면 연결됐고 Chrome의 실제 저장 파일로 수신을 확인했어요.
이 도구 한계를 제품 자체의 파일 수신 불가로 해석하지 않아요.
이 개인 Chrome 실험에서는 사용자 브라우저에서 별도 trss 서버로의 전달과 최종 자동 배치를 검증하지 않았어요.
서버 전용 브라우저의 원격 인증 경로는 아래 별도 실험에서 확인하며, 사용자가 파일을 옮기거나 업로드하는 방식으로 자동 배치 요구를 대체하지 않아요.

### 서버 브라우저 임시 검증

서버 전용 브라우저와 원격 인증 화면을 우선하는 방향으로 타당성을 확인했어요.
서버 파일 수신까지 확인한 뒤 제품의 인증 운영 방식도 서버 브라우저로 선택했으며, 결정과 대안의 비교는 [인증 운영 ADR](../adr/0002-server-browser-subtitle-authentication.md)에 기록했어요.
원격 웹 화면에서 사람이 인증한 뒤 파일이 서버 측 저장소로 내려오는지 확인한 결과, Selenium 실행은 실패했지만 일반 Chromium 직접 연결은 성공했어요.

기존 trss 코드·설정·의존성은 바꾸지 않고 `.scratch/server-auth-browser/prototype`에 격리된 임시 실행물을 구성했어요.
공식 `selenium/standalone-chromium` 이미지를 digest `sha256:08fd293648e126275782c616a61f4ee1d90cf413b1972ebc35dbd054d6789f55`로 고정해 사용해요.
검증에 사용한 환경은 Grid 4.49.0과 Chromium 152.0이며, 실행 시 원격 화면과 제어 포트는 각각 `127.0.0.1:17900`, `127.0.0.1:14444`에만 바인딩했어요.
브라우저 프로필은 컨테이너 안에 두고 다운로드 디렉터리만 임시 실행 디렉터리에 연결해요.
Grid 준비 응답, 로컬 전용 포트 바인딩, 서버 브라우저의 게시물 로드와 정상 다운로드 카드 클릭을 확인했어요.
서버 브라우저 스크린샷에 `Verify you are human` 체크박스가 표시됐고, 다운로드 검사 결과는 대기 파일·완료 파일·오류 모두 없는 상태였어요.
사용자가 원격 화면에서 직접 인증했지만 `verification failed`가 표시됐다고 보고했어요.
기존 브라우저 로그에서 Turnstile `600010`과 사이트의 `Turnstile timed out after error: 600010`을 확인했고, 서버 다운로드 폴더는 대기 파일과 완료 파일 모두 없는 상태였어요.
같은 설정의 인증을 다시 시도해 실패를 재현하지 않았어요.

[Cloudflare 오류 코드 문서](https://developers.cloudflare.com/turnstile/troubleshooting/client-side-errors/error-codes/)는 `600*`를 봇 행동이 감지된 일반 인증 실패로 분류해요.
이 코드만으로 WebDriver 연결, 새 프로필, 브라우저 버전 등 어느 차이가 원인인지 특정할 수는 없어요.
이번 결과는 Selenium 기반의 이 서버 브라우저 구성에서 실패했다는 증거이며, 원격 브라우저 방식 전체가 불가능하다는 증거는 아니에요.
개인 Chrome에서 성공한 결과와 구분하고, 브라우저 속성 위장이나 인증 우회로 실패를 숨기지 않아요.

실패한 Selenium 실험의 WebDriver 세션을 종료하고 컨테이너를 정지한 뒤, 다음 비교를 위해 같은 이미지의 컨테이너를 다시 구성했어요.
제품 코드는 변경하지 않았어요.

#### 일반 Chromium 직접 연결 비교

서버가 브라우저의 페이지 열기와 다운로드 시작을 처리하고, 다운로드 과정에서 사람이 할 일은 CAPTCHA에 한정하는 흐름을 검증했어요.
기존 자막 후보 선택과 교체 승인 정책을 없애는 변경은 아니에요.

같은 Chromium 152 이미지에서 WebDriver 세션을 생성하지 않고 브라우저를 직접 실행한 다음 CDP로 연결했어요.
별도의 임시 프로필을 사용하며, 브라우저 속성 위장이나 인증 우회 스크립트는 넣지 않았어요.
CDP 제어 포트는 `127.0.0.1:19222`에만 공개하고, 컨테이너 안의 작은 TCP 전달기로 Chromium의 루프백 디버깅 포트에 연결해요.
원격 화면은 기존 `127.0.0.1:17900`을 사용해요.

CDP 연결과 서버 다운로드 경로 `/home/seluser/Downloads` 설정, erulabo 게시물 열기, 정상 다운로드 카드 클릭을 확인했어요.
원격 화면에 CAPTCHA를 표시한 뒤 사용자가 직접 인증했고, 서버 다운로드 폴더에서 실제 파일을 읽었어요.
다운로드 URL을 따로 전달받아 재요청하지 않고, 같은 브라우저가 서버에 저장한 파일을 검사했어요.

- 받은 파일은 `The Insipid Prince's Furtive Grab for the Throne - s01e12.zip`이며 14,245바이트예요.
- ZIP 안에는 `The Insipid Prince's Furtive Grab for the Throne - s01e12.ko.ass` 한 개가 있고, 47,068바이트이며 CRC 검사를 통과했어요.
- UTF-8 ASS의 `[Events]`와 Dialogue 497행을 확인했어요.
- 대기 중인 다운로드와 파일 검사 오류는 없었어요.

이 결과는 해당 표본에서 CAPTCHA 외에 수동 파일 다운로드·업로드·이동 없이 서버 수신이 가능함을 보여줘요.
두 실행 구성의 차이 중 무엇이 인증 결과를 바꿨는지는 분리해 입증하지 않았으며, 지속적인 성공이나 다른 출처·배포 환경으로 일반화하지 않아요.
검증 환경은 같은 호스트의 격리된 컨테이너와 로컬 원격 화면이며, 실제 LAN·VPN 접속과 trss의 압축 해제·회차 연결·최종 배치는 검증하지 않았어요.
관찰 연결을 해제하고 컨테이너를 중지했어요.
사용자가 로컬 보관을 선택해 실행물·받은 표본·중지된 컨테이너를 남겼으며, 제품 코드나 원격 저장소에는 포함하지 않았어요.

#### 2026-10-02 원격 화면과 기기 폭 비교

[티켓 0032](../tickets/0032-server-browser-spike.md)에서 원격 화면 방식 둘과 기기 폭 맞추기 둘을 이 개발 PC의 LAN에서 비교했어요.
장치는 `.scratch/server-browser-0032/`의 임시 실행물(추적하지 않음)이에요. 위와 같은 이미지(`selenium/standalone-chromium`, 같은 digest)를 쓰되 Selenium Grid는 끄고, Chromium 152를 가상 디스플레이(Xvfb 1920×1200) 위에 창 있는 모드로 직접 띄웠어요. 실행마다 새 프로필이고 자동화·위장 플래그는 없어요. CDP는 호스트 루프백에만 열었어요.
Turnstile은 매번 사용자가 직접 풀었고, 서버는 게시물 열기와 정상 다운로드 카드 누르기만 했어요.
휴대폰은 사용자의 실제 휴대폰 한 대예요.

- 모드 A는 가상 디스플레이를 x11vnc·noVNC로 보내는 방식이고, 모드 B는 CDP 화면 전송(`Page.startScreencast`의 JPEG 프레임)과 입력 전달(`Input.dispatch*`)을 작은 중계기(WebSocket)가 잇는 방식이에요.

| 시각 | 방식·조건 | 게시물 | 결과 |
| --- | --- | --- | --- |
| 14:02 | 모드 B, PC | [859](https://erulabo.com/859) | 통과, ZIP 13,673바이트(ASS 하나 41,324바이트) |
| 14:05 | 모드 B, 휴대폰, 1배 | [855](https://erulabo.com/855) | 통과, ZIP 12,267바이트 |
| 14:08 | 모드 B, 휴대폰, 2배(`--force-device-scale-factor=2`) | 855 | 통과, 같은 ZIP |
| 14:11·14:12 | 모드 A, PC·휴대폰 | 859 | 통과, 같은 ZIP. 사용자는 데스크톱 창 전체가 축소돼 보여 누르기 매우 불편했다고 했어요 |
| 14:16 | 모드 B, `--headless=new` | 855 | 게시물이 `ERR_HTTP2_PROTOCOL_ERROR`로 열리지 않았어요. 헤드리스는 User-Agent에 `HeadlessChrome`을 밝혀요. 위장하지 않았어요 |
| 14:29 | 모드 B, 휴대폰, 1배, 광고·추적 차단, 메모리 한도 768MiB | 859 | 통과, 같은 ZIP. 서버가 카드를 화면 가운데로 스크롤한 뒤 눌렀고 인증 상자가 첫 화면에 있었어요 |

- 인증 뒤의 실제 파일은 모두 `drive.usercontent.google.com/download?id=…`에서 왔어요. 855는 서로 다른 새 프로필 두 실행에서 Drive 파일 ID가 같았어요(몇 분 사이). 제작자가 수정본을 같은 파일에 덮어쓰는지 새 파일로 올리는지는 몰라요.
- 기기 폭: 창 크기 바꾸기는 탭 있는 일반 창이 폭 약 500px 밑으로 내려가지 않았고(앱 창은 390까지), 바뀌는 데 0.12~1.5초였어요. 기기 지표 흉내(`Emulation.setDeviceMetricsOverride`의 폭·높이·DPR·모바일과 터치 흉내)는 요청한 크기가 정확히 나왔고 8~160ms였어요. 실제 휴대폰은 `402×666`, DPR 3으로 보고했어요.
- 선명도: 창 있는 Chromium은 흉내 낸 DPR과 상관없이 창의 배율(1배)로 그려서 휴대폰에서 흐렸어요(프레임 402×666). `--force-device-scale-factor=2`이면 프레임이 2배(390×844에서 780×1688)가 되고 사용자가 선명하다고 했어요.
- 크기를 바꾸는 동안 중계기는 입력을 버리고, 이전 크기의 프레임을 보고 만든 입력도 버렸어요(시험 중 버린 입력 0~15개). PC에서 연 화면을 휴대폰에서 다시 열었을 때(1272×753 → 402×666, 139ms) 엉뚱한 자리로 간 입력은 없었어요.
- 인증 상자 위치: Turnstile은 누른 카드 안, 설명 글 자리에 떠요. 게시물 그대로는 PC·휴대폰 모두 스크롤해야 보였고, 휴대폰 아래쪽에는 광고 띠가 겹쳤어요. 위젯은 닫힌 shadow DOM 안이라 문서에서 찾을 수 없어서, 카드를 기준으로 스크롤했어요.
- 사용자는 모드 B의 스크롤이 부드럽지 않다고 했어요(측정하지 않았어요).

자원은 2초마다 `docker stats`로 쟀어요. 메모리 값에는 회수할 수 있는 파일 캐시가 섞여 있어서, 인증 상자가 뜬 상태의 실제 프로세스 메모리(cgroup `anon`)를 함께 적어요.

### 재생기 파일명과 폰트 호환 근거

파일 이름의 기본 표시와 재생기의 기본 트랙 선택을 분리해서 검토해요.
아래는 문서·소스 확인 결과이며, 사용자 기기에서 실행한 재생 시험은 아니에요.

- [Infuse 외부 자막 안내](https://support.firecore.com/hc/en-us/articles/215090967-Using-Subtitles)는 영상과 같은 폴더의 동일 이름 자막과 `영상-en.srt` 같은 언어별 이름을 설명하며, UPnP·DLNA 연결의 외부 자막은 지원하지 않는다고 명시해요.
  [설정 안내](https://support.firecore.com/hc/en-us/articles/360015608854-Settings-Overview)의 언어·`default` 트랙 태그 선택 설명은 외부 파일명의 `.default`를 태그로 해석한다는 근거가 아니에요.
  같은 언어의 여러 외부 형식 사이 우선순위와 임의 접미사의 공통 인식은 확인하지 못했어요.
- IINA `v1.4.4`의 [AutoFileMatcher](https://github.com/iina/iina/blob/v1.4.4/iina/AutoFileMatcher.swift)는 파일 경로로 접근하는 영상의 주변 자막을 자체적으로 찾고, `subAutoLoadPriorityString`에 설정한 문자열이 들어 있는 일치 자막의 순서를 앞당겨요.
  [Preference](https://github.com/iina/iina/blob/v1.4.4/iina/Preference.swift)의 해당 기본값은 빈 문자열이므로 `.default`라는 이름 자체를 기본 지시자로 가정할 수는 없지만, 사용자 우선 문자열 설정에 연결하는 방안은 근거가 있어요.
  [PlayerCore](https://github.com/iina/iina/blob/v1.4.4/iina/PlayerCore.swift)는 일치 자막을 불러온 뒤 자막 트랙 1을 선택하므로, 내장 트랙·사용자 설정·실제 버전을 포함한 최종 선택은 별도 확인이 필요해요.
- [팟플레이어 공식 변경 이력](https://t1.kakaocdn.net/potplayer/PotPlayer/v4/Update2/Update.html)은 선호 자막 언어, 내장·외부 자막 우선순위와 이전 스트림 선택 기억 기능을 설명해요.
  이 기록만으로 외부 파일명의 `.default` 해석이나 같은 언어의 ASS·SRT·SMI 사이 선택 순서를 확정하지 않아요.

폰트를 자막 옆에 두는 것만으로 세 재생기에서 자동 사용하는 공통 규칙은 확인하지 못했어요.
[mpv 문서](https://mpv.io/manual/stable/#options-sub-fonts-dir)는 전용 폰트 디렉터리 `sub-fonts-dir`를 제공하지만, 그 기본 경로를 IINA의 실제 유효 설정으로 단정하지 않아요.
[Infuse 담당자의 과거 안내](https://community.firecore.com/t/subtitle-font-customization/36224/2)는 시스템 폰트와 iOS·tvOS의 차이를 설명하며, 이를 현재 모든 Apple 기기의 동작 보장으로 사용하지 않아요.
팟플레이어의 폰트 처리·libass 출력 관련 변경 이력도 인접한 폰트 파일 자동 검색의 근거와 구분해요.
`.forced`는 일반적인 기본 자막 표시와 의미가 다르므로, 기본 선택을 유도하려고 그 이름을 대신 사용하는 안은 취하지 않아요.

## 미해결 사항

시즌별 표시 정보·추가 기록, 남은 기술 선택, 추가 형식·언어·릴리스, 중복 영상, 실제 재생기·폰트·배포 검증의 범위는 [웹 앱 공통 명세의 남은 구체화](../specs/web-app.md#남은-구체화와-비차단-보류)와 각 주제별 명세의 남은 구체화에 있어요.
출처별 관찰 결과와 미검증 경로는 위 실험 기록에 남겨두며, 명세 작성으로 그 검증이 끝난 것은 아니에요.
