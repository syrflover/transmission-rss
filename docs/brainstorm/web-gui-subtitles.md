# 웹 GUI와 자막 수작업 개선

## 현재 방향

현재 사용자는 자막(Subtitle)을 하나씩 수동으로 다운로드하고 정리하고 있어요.
웹 GUI로 사용 편의성을 높이고, 자막 수작업을 줄이며, 함께 개선할 기능을 탐색하고 싶어 해요.
사용자는 보통 Anissia에서 자막을 찾을 수 있다고 설명했어요.
실제로 이용하는 자막 출처로 [erulabo](https://erulabo.com/)를 제시했어요.
현재 대상 영상의 폴더와 파일명은 모두 trname 방식으로 정리돼 있으며, 자막도 영상 옆에 같은 이름으로 두고 있어요.
자막 제작자와 회차 범위로 후보를 묶어 선택하고, 선택한 항목의 다운로드와 정리를 자동으로 일괄 처리하는 방향이에요.
CAPTCHA처럼 사람이 해야 하는 단계는 사용자가 해결한 뒤 자동 다운로드를 재개하는 경험을 원해요.
직접 받은 파일을 GUI에 넣는 방식으로 이 요구를 대체하지 않아요.
웹 GUI는 사용자 혼자 집 안 네트워크나 VPN에서 사용해요.
대상 영상은 앞으로 trss가 받는 영상, trss로 받은 기존 영상, trss 이용 여부와 무관하게 사용자가 지정한 폴더의 영상을 모두 포함해요.
제품 방향과 필수 지원 출처는 정했으며, 인증 후 자동 배치를 실현할 운영 방식은 실제 동작 검증 뒤에 선택하기로 했어요.

현재 사용자의 실제 작업 흐름을 기준으로 개선 방향을 정해요.
웹 GUI를 제공하는 것과 자막 수작업을 없애는 것은 별개의 효과이므로, 화면 추가만으로 문제가 해결된다고 가정하지 않아요.

## 선택지와 근거

웹 GUI에는 작품별 상태 확인, 작품·다운로드 규칙 관리, 자막 작업 처리 세 용도가 모두 필요하다는 사용자 선택이 있어요.
세 용도와 아래 네 가지 추가 기능을 모두 원하는 범위로 선택했으며, 남은 것은 세부 동작과 운영 방식이에요.
후보 선택은 사용자에게 남기고 반복적인 다운로드·정리를 줄이는 방향으로 정했어요.
후보까지 자동으로 선택하는 방향은 현재 선택에 포함하지 않아요.
일괄 선택은 한 작품의 자막 제작자와 회차 범위를 기준으로 묶고, 필요한 후보를 개별 조정하는 방식이에요.
사람이 처리해야 하는 CAPTCHA 등의 단계는 자동 우회하지 않고 수동으로 처리해요.
사용자는 직접 다운로드한 파일을 GUI에 넣는 방식보다, 인증만 해결한 뒤 자동 다운로드를 재개하는 방식을 선택했어요.
erulabo 표본에서는 원격 인증 후 서버 파일 수신을 확인했으며, 출처별 남은 검증 범위와 실제 자동 배치의 한계는 아래 근거에 구분해요.
기존 영상과 지정 폴더 전체도 대상이므로, Transmission의 현재 목록에 없는 파일도 작품·회차와 연결해야 해요.
영상 연결은 임의의 폴더·파일명 추측보다 이미 정리된 trname 구조를 읽는 것을 기준으로 해요.
로컬 작품·시즌에 대응하는 Anissia 작품 후보를 제안하고 사용자가 최초 한 번 확인해요.
확인한 연결은 기억해서 이후 회차마다 다시 묻지 않아요.
사용자는 이 정리 방식 때문에 같은 회차의 영상이 여러 개 있는 경우는 거의 없다고 설명했어요.
중복 영상을 일반적인 사용 흐름의 중심에 두지 않으며, 실제 발생 시의 세부 처리는 보류해요.
배치하려는 자막이 이미 있으면 교체 후보를 모아 사용자 확인을 받은 뒤 허용한 항목만 교체해요.

| 항목 | 현재 방향 | 남은 선택 |
| --- | --- | --- |
| 웹 관리 화면 | 작품별 상태, 작품·다운로드 규칙, 자막 작업을 다뤄요. 설정은 [앱에서 관리하고 YAML 가져오기·내보내기를 제공해요](../adr/0001-app-managed-download-rules.md). | 저장 방식과 가져오기·내보내기의 세부 계약은 설계 단계에서 구체화해야 해요. |
| 자막 선택과 일괄 처리 | 제작자·회차 범위로 묶어 선택하고 이후 작업을 자동화해요. | 여러 파일이 들어 있는 다운로드의 처리 기준을 정해야 해요. |
| 자막 배치 | trname 방식의 영상에서 작품·시즌 연결을 최초 확인하고, 기존 자막 교체는 모아서 확인해요. | 회차 번호가 다른 경우의 연결 보정과 압축 묶음 내 파일 선택 기준은 아직 구체화하지 않았어요. |
| 수동 개입 | 사람이 인증을 해결한 뒤 자동 다운로드와 배치를 이어가요. | 서버 전용 브라우저와 사용자 브라우저 확장 중 어느 방식을 쓸지는 실제 동작 검증 뒤에 결정해요. |
| 사용 범위 | 한 사람이 집 안 네트워크나 VPN에서 사용하며, 앱 자체 로그인 대신 VPN·앞단 인증으로 접근을 제한해요. | 배포 환경에서 앱에 직접 접근하는 우회 경로가 생기지 않도록 경계를 유지해야 해요. |

Transmission은 trss에서 상태를 확인하고 기존 Transmission 화면으로 이동하는 범위로 정했어요.
시작·일시정지·삭제를 trss에 중복 구현하는 방향은 선택하지 않았어요.

다음 네 가지 추가 기능을 모두 범위에 포함하기로 했어요.

- 누락 자막 모아보기: 보유 영상 중 자막 없는 회차를 모아 후보 선택·일괄 작업으로 연결해요.
- 실패·인증 대기 작업 관리: 막힌 이유와 상태를 모아 보고 해당 작업에서 인증이나 재시도를 이어가요.
- 수정 자막 확인: 이미 받은 자막의 갱신 후보를 보여주고 교체는 사용자 확인을 거쳐요.
- 다운로드 규칙 미리보기: 규칙 변경 시 현재 RSS 항목 중 무엇이 선택되고 어디에 저장될지 실행 전에 보여줘요.

### 지원 출처와 후보 갱신

첫 지원 범위에는 erulabo, Blogger·Google Drive, Tistory 일반 첨부·WinPNG, Naver 블로그 첨부를 모두 포함해요.
실제 이용하는 erulabo만 먼저 지원하는 대안 대신, 조사에서 다룬 출처 유형을 폭넓게 지원하는 방향을 선택했어요.
이는 필요한 지원 범위의 결정이며, 출처별 표본 수신 확인을 제품 구현 완료로 해석하지 않아요.

화면을 닫아도 주기적으로 누락·수정 자막 후보를 확인하고 모아둬요.
다음에 웹 화면을 열면 확인할 후보를 볼 수 있어야 해요.
주기적인 후보 탐색이 다운로드·교체의 자동 승인을 뜻하지 않으며, 자막 선택과 기존 파일 교체 확인은 계속 사용자에게 남겨요.
구체적인 조회 간격과 외부 알림 채널은 정하지 않았어요.

## 현재 제품의 근거와 한계

- [README](../../readme.md)는 RSS 피드(RSS Feed)의 항목을 규칙에 따라 Transmission에 추가하고 파일명을 변경하는 도구로 설명해요.
  현재 사용 안내는 Docker Compose, 환경 변수와 원격 YAML 설정 중심이에요.
- [예약 실행 스크립트](../../scripts/cron.sh)는 5분 간격 실행과 로그 파일 출력을 설정해요.
  저장소 조사에서는 trss 자체 웹 GUI를 찾지 못했어요.
- [주 실행 경로](../../src/main.rs)의 파일명 변경은 파일이 하나인 토렌트(Torrent)를 대상으로 해요.
  피드에서 사라진 관리 대상 토렌트를 Transmission에서 제거할 때 로컬 데이터는 삭제하지 않아요.
  따라서 이 기능을 자막 정리나 미디어 파일 자동 삭제 기능으로 간주하지 않아요.
- [Anissia 연동 코드](../../src/anissia.rs)에는 자막 메타데이터와 다운로드 관련 코드가 있지만 미완성 부분이 있고, [Cargo 설정](../../Cargo.toml)의 선택 기능으로 분리돼 있어요.
  현재 사용 가능한 종단 간 자막 자동화로 간주하지 않아요.

저장소 코드와 공개 출처 조사에 더해, 2026-09-26에 출처별 실제 경로 확인을 시작했어요.
trss 제품 코드는 아직 실행·변경하지 않았으며, 파일 수신과 형식 확인 결과는 아래의 각 출처 근거에 한정돼요.
수동 작업, Anissia 사용, 모든 대상 폴더·파일명의 trname 정리, 같은 회차 중복 영상이 거의 없다는 설명은 사용자 보고예요.
주 실행 경로에서도 영상 파일명 변경에 trname을 사용하는 것을 확인했지만, 사용자의 실제 파일 구조를 직접 검사한 것은 아니에요.
공개 Anissia API와 연결된 일부 게시물을 읽기 전용으로 조사했으며, 사용자가 실제로 이용하는 출처로 erulabo를 제시했어요.

### trname 형식

[현재 의존성이 고정한 trname README](https://github.com/syrflover/trname/blob/6169808/readme.md)는 TheTVDB 시즌 명명에 맞춘 `작품/Season 01/작품 S01E01.mkv`와 같은 구조를 보여줘요.
영상과 자막은 확장자를 제외한 이름이 같아요.
이 문서는 Movie·OVA 같은 Special은 지원하지 않는다고 명시하지만, 사용자가 설치한 trname의 버전까지 확인한 것은 아니에요.
이 형식은 로컬 작품·시즌·회차를 읽는 근거이며, Anissia의 작품 식별자와 회차 번호가 자동으로 일치한다는 증거는 아니에요.

### 공개 자막 경로 조사

2026-09-25의 [Anissia 최근 자막 API](https://api.anissia.net/anime/caption/recent/0)와 공개 게시물 조사에서는 작품·회차·제작자·갱신 시각과 외부 게시물 주소를 확인했어요.
2026-09-26에는 아래 표본의 실제 파일 수신과 구조를 확인했어요.
이는 출처별 접근 방식의 타당성 근거이며 trss의 지원 구현, 영상과의 싱크, 자동 배치 성공을 뜻하지 않아요.

#### Blogger·Google Drive

[Blogger 게시물](https://csora556.blogspot.com/2026/07/season-3.html)의 링크를 따라 전용 Chromium에서 공개 Drive 미리보기의 다운로드 버튼으로 두 파일을 받았어요.
로그인이나 CAPTCHA는 요구되지 않았어요.

- [개별 자막](https://drive.google.com/file/d/19-SuMGhXgKVLO9DLiWohA_s851qNhf0I/view): `Grand Blue S3 12.ass`, 46,967바이트예요.
  UTF-8 BOM, ASS의 `[Script Info]`, `[V4+ Styles]`, `[Events]`와 Style 11행·Dialogue 521행을 확인했어요.
- [회차 묶음](https://drive.google.com/file/d/10EFK_9-G9VPVFy08Zuit88H0ciLJMFKq/view): `그랑블루3 1-12.zip`, 183,503바이트예요.
  01–12화 ASS 파일 12개, 총 비압축 594,547바이트이며 ZIP CRC 검사를 통과했어요.
  디렉터리 항목이나 암호화는 없었고 12화 멤버는 별도 다운로드한 자막과 바이트 단위로 같았어요.

공유 Chromium의 프레임 분리·세션 종료 오류와 개별 파일 수신 후 다운로드 대기 API의 시간 초과가 있었지만, 전용 브라우저가 저장한 실제 파일과 ZIP 구조로 수신을 확인했어요.
이 도구 오류를 Drive의 다운로드 거부로 판단하지 않아요.
별도 HTTP 클라이언트의 파일 수신, 나머지 11개 회차의 개별 다운로드와 ZIP 멤버 비교, 향후 무인 실행은 검증하지 않았어요.

#### Tistory 일반 첨부

[Tistory 게시물](https://sumomomo.tistory.com/488)에 노출된 일반 첨부 링크로 비로그인 HTTP GET을 수행했어요.
`Buchigire Reijou - 12.zip`을 HTTP 200, `application/octet-stream`, attachment 응답으로 12,243바이트 수신했어요.
ZIP 무결성을 확인했고, 내부에는 `Buchigire Reijou - 12.srt` 한 개가 있으며 비압축 크기는 33,445바이트, SRT 타임스탬프 행은 416개였어요.
이 표본에서는 CAPTCHA나 추가 사람 동작이 필요하지 않았어요.
브라우저 클릭 경로와 게시물에서 얻은 서명 URL의 만료·재사용 가능성은 검증하지 않았어요.

#### Tistory WinPNG

[게시물](https://harne1.tistory.com/762)의 PNG를 클릭해 사이트의 [WinPNG Viewer](https://tistory1.daumcdn.net/tistory/913196/skin/images/Viewer.js?_version_=1790231817)에서 SMI 파일 12개를 복원했어요.
12화 파일 한 개와 `~11/` 폴더의 01–11화 파일 11개가 표시됐어요.
브라우저의 생성된 blob을 읽어 각 파일이 32,355–84,192바이트이고 UTF-8 BOM 뒤에 `<SAMI>`로 시작함을 확인했어요.
단순 이미지 표시가 아니라 자막 바이트 복원을 확인한 결과예요.

뷰어의 정상 파일 링크를 눌러 `[SubsPlease] Mebius Dust - 12 (1080p) [7624D7BF].smi`를 32,355바이트의 브라우저 다운로드로 수신했어요.
이미지 선택 외에 파일 키 입력, CAPTCHA, 로그인은 요구되지 않았어요.
별도 HTTP 클라이언트의 추출과 뷰어의 ZIP 다운로드는 검증하지 않았으며, 파일 키가 필요한 다른 이미지로 결과를 일반화하지 않아요.

#### Naver 블로그 첨부

[게시물](https://blog.naver.com/gkdlfn0850/224418549305)의 새 비로그인 HTTP 응답에서 얻은 첨부 링크로 `DBB 48.smi`를 수신했어요.
브라우저 쿠키 없이 HTTP 200, `application/octet-stream`, attachment 응답으로 53,100바이트를 받았어요.
UTF-16LE BOM과 SAMI의 HEAD·BODY·SYNC 524개 요소를 확인했어요.
CAPTCHA나 로그인은 요구되지 않았으며, 게시물의 안부게시판 CAPTCHA는 이 다운로드와 별개예요.

관리형 Chromium에서도 내부 프레임의 정상 첨부 링크를 클릭했지만, 다운로드 API가 수신을 보고하지 않았고 이후 탭 세션이 닫혀 브라우저의 파일 저장은 확인하지 못했어요.
HTTP 수신 성공을 브라우저 다운로드 처리나 첨부 URL의 유효기간·세션 종속성 검증으로 대체하지 않아요.

표본과 실험용 임시 파일은 검사 후 제거했으며, 서명 URL·쿠키·인증 토큰·자막 본문은 저장소에 보관하지 않았어요.
인증이 필요하지 않았던 표본의 성공은 erulabo의 인증 후 재개를 입증하지 않아요.

발급 약 3.7초 뒤 사용자 다운로드 폴더에 저장된 `The Insipid Prince's Furtive Grab for the Throne - s01e12.zip`을 같은 컴퓨터의 프로그램에서 읽었어요.

정상 브라우저 다운로드는 이미 완료됐으며, 유효기간 내 별도 HTTP 클라이언트의 수신은 미검증이에요.

이번 실험은 사용자 인증 후 사이트가 다운로드를 이어가고 같은 컴퓨터의 프로그램이 실제 자막 바이트를 읽을 수 있음을 보여줘요.
relay에서 다운로드 경로를 지정한 연결은 도구의 `Browser target is not found` 오류로 실패했지만, 경로 지정을 빼면 연결됐고 Chrome의 실제 저장 파일로 수신을 확인했어요.
이 도구 한계를 제품 자체의 파일 수신 불가로 해석하지 않아요.
이 개인 Chrome 실험에서는 사용자 브라우저에서 별도 trss 서버로의 전달과 최종 자동 배치를 검증하지 않았어요.
서버 전용 브라우저의 원격 인증 경로는 아래 별도 실험에서 확인하며, 사용자가 파일을 옮기거나 업로드하는 방식으로 자동 배치 요구를 대체하지 않아요.

### 서버 브라우저 임시 검증

서버 전용 브라우저와 원격 인증 화면을 우선하는 방향으로 타당성을 확인했어요.
사용자 PC의 확장과 서버 전송 경로를 먼저 만드는 대안은 이번 실험의 선택이 아니며, 제품의 최종 운영 방식이 확정된 것은 아니에요.
원격 웹 화면에서 사람이 인증한 뒤 파일이 서버 측 저장소로 내려오는지 확인한 결과, Selenium 실행은 실패했지만 일반 Chromium 직접 연결은 성공했어요.

기존 trss 코드·설정·의존성은 바꾸지 않고 `.scratch/server-auth-browser/prototype`에 격리된 임시 실행물을 구성했어요.
공식 `selenium/standalone-chromium` 이미지를 digest `sha256:08fd293648e126275782c616a61f4ee1d90cf413b1972ebc35dbd054d6789f55`로 고정해 사용해요.
검증에 사용한 환경은 Grid 4.49.0과 Chromium 152.0이며, 실행 시 원격 화면과 제어 포트는 각각 `127.0.0.1:17900`, `127.0.0.1:14444`에만 바인딩했어요.
브라우저 프로필은 컨테이너 안에 두고 다운로드 디렉터리만 임시 실행 디렉터리에 연결해요.
Grid 준비 응답, 로컬 전용 포트 바인딩, 서버 브라우저의 게시물 로드와 정상 다운로드 카드 클릭을 확인했어요.
서버 브라우저 스크린샷에 `Verify you are human` 체크박스가 표시됐고, 다운로드 검사 결과는 대기 파일·완료 파일·오류 모두 없는 상태였어요.
사용자가 원격 화면에서 직접 인증했지만 `verification failed`가 표시됐다고 보고했어요.
기존 브라우저 로그에서 Turnstile `600010`과 사이트의 `Turnstile timed out after error: 600010`을 확인했고, 서버 다운로드 폴더는 대기 파일과 완료 파일 모두 없는 상태였어요.
같은 설정의 인증을 다시 시도해 실패를 재현하지 않았어요.

[Cloudflare 오류 코드 문서](https://developers.cloudflare.com/turnstile/troubleshooting/client-side-errors/error-codes/)는 `600*`를 봇 행동이 감지된 일반 인증 실패로 분류해요.
이 코드만으로 WebDriver 연결, 새 프로필, 브라우저 버전 등 어느 차이가 원인인지 특정할 수는 없어요.
이번 결과는 Selenium 기반의 이 서버 브라우저 구성에서 실패했다는 증거이며, 원격 브라우저 방식 전체가 불가능하다는 증거는 아니에요.
개인 Chrome에서 성공한 결과와 구분하고, 브라우저 속성 위장이나 인증 우회로 실패를 숨기지 않아요.

실패한 Selenium 실험의 WebDriver 세션을 종료하고 컨테이너를 정지한 뒤, 다음 비교를 위해 같은 이미지의 컨테이너를 다시 구성했어요.
제품 코드는 변경하지 않았어요.

서버가 브라우저의 페이지 열기와 다운로드 시작을 처리하고, 다운로드 과정에서 사람이 할 일은 CAPTCHA에 한정하는 흐름을 검증했어요.
