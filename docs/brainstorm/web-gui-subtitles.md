# 웹 GUI와 자막 수작업 개선

## 현재 방향

현재 사용자는 자막(Subtitle)을 하나씩 수동으로 다운로드하고 정리하고 있어요.
웹 GUI로 사용 편의성을 높이고, 자막 수작업을 줄이며, 함께 개선할 기능을 탐색하고 싶어 해요.
사용자는 보통 Anissia에서 자막을 찾을 수 있다고 설명했어요.
실제로 이용하는 자막 출처로 [erulabo](https://erulabo.com/)를 제시했어요.
현재 대상 영상의 폴더와 파일명은 모두 trname 방식으로 정리돼 있으며, 자막도 영상 옆에 같은 이름으로 두고 있어요.
자막 제작자와 회차 범위로 후보를 묶어 선택하고, 선택한 항목의 다운로드와 정리를 자동으로 일괄 처리하는 방향이에요.
CAPTCHA처럼 사람이 해야 하는 단계는 사용자가 해결한 뒤 자동 다운로드를 재개하는 경험을 원해요.
직접 받은 파일을 GUI에 넣는 방식으로 이 요구를 대체하지 않아요.
웹 GUI는 사용자 혼자 집 안 네트워크나 VPN에서 사용해요.
대상 영상은 앞으로 trss가 받는 영상, trss로 받은 기존 영상, trss 이용 여부와 무관하게 사용자가 지정한 폴더의 영상을 모두 포함해요.
제품 방향과 필수 지원 출처를 정했고, 인증은 서버 브라우저의 원격 화면에서 처리하는 방식으로 선택했어요.

현재 사용자의 실제 작업 흐름을 기준으로 개선 방향을 정해요.
웹 GUI를 제공하는 것과 자막 수작업을 없애는 것은 별개의 효과이므로, 화면 추가만으로 문제가 해결된다고 가정하지 않아요.

## 선택지와 근거

웹 GUI에는 작품별 상태 확인, 작품·다운로드 규칙 관리, 자막 작업 처리 세 용도가 모두 필요하다는 사용자 선택이 있어요.
세 용도와 아래 네 가지 추가 기능을 모두 원하는 범위로 선택했으며, 남은 것은 세부 동작과 운영 방식이에요.
후보 선택은 사용자에게 남기고 반복적인 다운로드·정리를 줄이는 방향으로 정했어요.
후보까지 자동으로 선택하는 방향은 현재 선택에 포함하지 않아요.
일괄 선택은 한 작품의 자막 제작자와 회차 범위를 기준으로 묶고, 필요한 후보를 개별 조정하는 방식이에요.
사람이 처리해야 하는 CAPTCHA 등의 단계는 자동 우회하지 않고 수동으로 처리해요.
사용자는 직접 다운로드한 파일을 GUI에 넣는 방식보다, 인증만 해결한 뒤 자동 다운로드를 재개하는 방식을 선택했어요.
인증이 필요할 때는 별도 주소나 창을 열게 하지 않고 trss의 해당 작업 화면 안에서 직접 처리할 수 있어야 해요.
erulabo 표본에서는 원격 인증 후 서버 파일 수신을 확인했으며, 출처별 남은 검증 범위와 실제 자동 배치의 한계는 아래 근거에 구분해요.
기존 영상과 지정 폴더 전체도 대상이므로, Transmission의 현재 목록에 없는 파일도 작품·회차와 연결해야 해요.
영상 연결은 임의의 폴더·파일명 추측보다 이미 정리된 trname 구조를 읽는 것을 기준으로 해요.
로컬 작품·시즌에 대응하는 Anissia 작품 후보를 제안하고 사용자가 최초 한 번 확인해요.
확인한 연결은 기억해서 이후 회차마다 다시 묻지 않아요.
사용자는 이 정리 방식 때문에 같은 회차의 영상이 여러 개 있는 경우는 거의 없다고 설명했어요.
중복 영상을 일반적인 사용 흐름의 중심에 두지 않으며, 실제 발생 시의 세부 처리는 보류해요.
배치하려는 자막이 이미 있으면 교체 후보를 모아 사용자 확인을 받은 뒤 허용한 항목만 교체해요.
승인 화면에는 기존 파일과 새 파일의 비교 정보, 영상 연결 근거와 실제 변경될 경로를 함께 보여줘야 해요.

| 항목 | 현재 방향 | 남은 선택과 제약 |
| --- | --- | --- |
| 웹 관리 화면 | 작품별 상태, 작품·다운로드 규칙, 자막 작업을 다뤄요. [YAML 가져오기는 비교 후 선택한 항목만 추가·교체하고, 내보내기는 새 앱 설정 형식만 제공해요](../adr/0001-app-managed-download-rules.md). | 기존 YAML은 채널 단위로 적용하며, 내부 저장 방식과 새 YAML 스키마는 구현 설계에서 구체화해요. |
| 자막 선택과 일괄 처리 | 제작자·회차 범위로 선택한 묶음을 분석하고, 보관본과 영상 옆 적용본을 분리해요. | 변경 파일 수신을 우선하고, 통째 묶음만 가능한 출처는 전체 수신 후 중복 보관을 막아요. |
| 자막 배치 | 작품·시즌·출처의 회차 대응을 기억하고, 영상이 없으면 자막을 먼저 받아 기다려요. | 불명확한 연결은 보류하며, 영상 대기 파일은 자동 삭제하지 않아요. |
| 수동 개입 | [서버 브라우저와 웹 인증 화면](../adr/0002-server-browser-subtitle-authentication.md)으로 CAPTCHA를 처리하고 자동 다운로드와 배치를 이어가요. | 인증 대기 작업은 보존하고 유휴 브라우저는 종료하며, 실행마다 새 프로필을 사용해요. |
| 사용 범위 | 한 사람이 집 안 네트워크나 VPN에서 사용하며, 앱 자체 로그인 대신 VPN·앞단 인증으로 접근을 제한해요. | 배포 환경에서 앱에 직접 접근하는 우회 경로가 생기지 않도록 경계를 유지해야 해요. |

Transmission은 trss에서 상태를 확인하고 기존 Transmission 화면으로 이동하는 범위로 정했어요.
시작·일시정지·삭제를 trss에 중복 구현하는 방향은 선택하지 않았어요.

다음 네 가지 추가 기능을 모두 범위에 포함하기로 했어요.

- 누락 자막 모아보기: 보유 영상 중 자막 없는 회차를 모아 후보 선택·일괄 작업으로 연결해요.
- 실패·인증 대기 작업 관리: 막힌 이유와 상태를 모아 보고 해당 작업에서 인증이나 재시도를 이어가요.
- 수정 자막 확인: 이미 받은 자막의 갱신 후보를 보여주고 교체는 사용자 확인을 거쳐요.
- 다운로드 규칙 미리보기: 규칙 변경 시 현재 RSS 항목 중 무엇이 선택되고 어디에 저장될지 실행 전에 보여줘요.

규칙 관리에는 기존 부분 문자열·대소문자 무시 조건뿐 아니라 정규식 조건도 실제 동작하도록 포함해요.
규칙 미리보기와 실제 실행은 같은 조건 판정을 사용하고, 규칙의 첫 일치 우선순위를 보존해요.

### 지원 출처와 후보 갱신

첫 지원 범위에는 erulabo, Blogger·Google Drive, Tistory 일반 첨부·WinPNG, Naver 블로그 첨부를 모두 포함해요.
실제 이용하는 erulabo만 먼저 지원하는 대안 대신, 조사에서 다룬 출처 유형을 폭넓게 지원하는 방향을 선택했어요.
이는 필요한 지원 범위의 결정이며, 출처별 표본 수신 확인을 제품 구현 완료로 해석하지 않아요.

화면을 닫아도 2시간마다 누락·수정 자막 후보를 확인하고 모아둬요.
다음에 웹 화면을 열면 확인할 후보를 볼 수 있어야 해요.
주기적인 후보 탐색이 다운로드·교체의 자동 승인을 뜻하지 않으며, 자막 선택과 기존 파일 교체 확인은 계속 사용자에게 남겨요.
자막 후보 조회 주기는 기존 영상 RSS 처리 주기를 변경하지 않으며, 필요할 때 직접 후보를 새로고침할 수 있어요.
반복 자동 조회는 Anissia에 표시된 후보 갱신일부터 30일 이내인 후보를 대상으로 해요.
후보나 갱신 날짜가 없으면 해당 회차 영상을 앱에서 처음 발견한 날부터 기간을 세요.
최초 검색과 사용자가 요청한 새로고침에는 이 기간 제한을 적용하지 않아 오래된 영상의 자막도 찾을 수 있게 해요.
기간이 지나면 반복 자동 조회에서 제외할 뿐, 받은 자막이나 후보 기록을 삭제하지 않아요.
조회 중단 이후에 올라오는 자막이나 수정은 자동으로 발견하지 못할 수 있다는 한계를 수용해요.
외부 알림 채널은 현재 필수 요구에 포함하지 않아요.

### 회차 연결과 영상 준비 전 자막

작품·시즌을 처음 연결할 때 출처별 [회차 대응(Episode Mapping)](../glossary.md)도 확인하고 기억해요.
자막 누적 13화가 영상 시즌 2의 1화에 해당하는 경우처럼 번호 차이를 이후 작업에도 적용하며, 매번 다시 묻지 않아요.
대응 규칙으로도 불명확한 파일은 추측해서 배치하거나 덮어쓰지 않고 보류해요.

선택한 자막은 대상 영상이 아직 없어도 먼저 다운로드하고 [영상 대기(Awaiting Video)](../glossary.md)로 보관해요.
연결된 폴더에 영상이 준비되면 자막을 다시 선택하거나 받지 않고 자동 배치해요.
그때 기존 자막과 충돌하면 원래의 교체 승인 정책을 적용해요.
영상 대기 파일은 영상이 준비되거나 사용자가 정리할 때까지 자동 삭제하지 않아요.
재다운로드와 재인증을 피하는 대신 대기 파일이 쌓일 수 있다는 점을 수용해요.

### 다운로드 묶음과 배치 판단

다운로드 한 건을 곧바로 자막 파일 하나로 취급하지 않아요.
[자막 묶음(Subtitle Package)](../glossary.md)의 구성과 내용을 확인한 뒤 회차·자막 종류·보조 파일을 구분하고 [배치 계획(Placement Plan)](../glossary.md)을 만들어요.
기존에 선택한 회차 범위와 출처별 번호 대응을 적용하며, 불명확한 연결은 추측하지 않는 원칙을 유지해요.
정상적으로 판별되는 작업에는 불필요한 추가 확인을 넣지 않고, 해결되지 않은 선택이나 교체가 있는 부분을 구분해서 보여주는 방향이에요.

다음은 별도로 다룰 입력 사례이며, 목록 자체가 모든 추가 형식의 지원 완료나 지원 범위 확정을 뜻하지 않아요.

| 사례 | 구분해야 할 점과 처리 방향 |
| --- | --- |
| 여러 회차와 하위 폴더가 들어 있는 묶음 | 각 파일의 대상 회차를 연결하고 선택한 범위만 배치해요. |
| 같은 회차의 ASS·SRT·SMI 등 여러 형식 | 여러 형식은 보관하고, 처음에는 우선 형식 하나만 적용하며 다른 형식은 선택 시 추가 적용해요. |
| 같은 회차·형식의 여러 파일 | 언어, 제작자, 전체 대사·간판 전용, TV·BD 등 릴리스 차이와 수정본 가능성을 구분해야 해요. |
| 한 파일의 여러 언어 또는 여러 파일로 구성된 자막 | 파일 하나가 언어 하나라는 가정을 피하고, IDX·SUB 같은 구성 파일은 독립 자막으로 오인하지 않아요. |
| 폰트와 설명·라이선스 파일 | 자막과 연결된 보조 자산으로 식별하며, 폰트의 실제 활용 방식은 재생 환경을 확인한 뒤 정해요. |
| 중복 파일과 이름 충돌 | 바이트가 같은 중복과 이름만 같고 내용은 다른 파일을 구분하며, 대상 경로 충돌을 배치 전에 보여줘요. |
| 인코딩 차이·잘못된 확장자·손상된 파일 | 실제 읽을 수 있는 형식과 인코딩을 확인하고, 판별·비교 불가를 정상 처리나 동일 내용으로 표시하지 않아요. |
| 중첩 압축·암호가 걸린 묶음·알 수 없는 첨부 | 지원 여부와 추가 입력 필요 여부를 구분하며, 자막으로 위장한 HTML 오류 페이지 등을 배치하지 않아요. |
| 경로 이탈·링크·과도한 압축 해제 크기 | 격리된 작업 경계를 벗어나거나 자원을 무제한 사용하는 압축 해제를 허용하지 않아요. |

확장자 변경만으로 포맷을 변환하거나, 변환 과정에서 스타일·색상·위치 정보를 잃는 방식을 자동 적용하지 않는 안을 제안해요.
사용자의 주 재생 환경은 Infuse, IINA, 다음 팟플레이어예요.
Infuse는 SMB·NFS·WebDAV 계열의 폴더 공유로 접근하며, 특정 Apple 기기에 한정하지 않는 호환을 희망해요.
폰트를 영상 옆에 두는 것만으로 각 재생기가 실제 사용하는지는 별도로 확인해야 해요.
서버 전역 폰트 설치나 원본 영상 재먹스는 현재 선택한 동작에 포함하지 않아요.

### 자막 보관과 영상 옆 적용

[자막 보관·적용 ADR](../adr/0003-stored-and-applied-subtitles.md)에 따라 작품 폴더의 `.trss-subtitles/`에 제작자·형식·수정본과 관련 자산을 보관하고, 선택한 자막만 영상 옆에 같은 파일명 줄기로 적용해요.
웹에서 보관본을 비교·선택하고, 선택한 보관본을 영상 옆에 독립된 파일로 복사해 적용해요.
이동이나 링크 방식은 사용하지 않으며, 적용본을 수정·교체·삭제해도 보관본은 영향을 받지 않아요.

처음에는 전역 ASS → SRT → SMI 또는 작품별 우선순위로 한 형식만 적용하고, 사용자가 원하면 같은 제작자의 다른 형식도 추가 적용해요.

폰트를 함께 보관하는 것과 실제 재생기가 사용하는 것도 별개예요.

### 주요 출처 erulabo의 보안 확인

사용자가 제시한 [erulabo](https://erulabo.com/)의 [Anissia 연결 게시물](https://erulabo.com/854)에는 보안 확인 후 다운로드가 시작된다는 안내가 있어요.

- 클라이언트 코드는 자막 카드를 누르면 Cloudflare Turnstile을 실행하고, 완료 콜백의 토큰으로 `/file/<id>/token`에 요청해요.
  요청에는 CSRF 정보가 포함돼요.
- 성공 응답의 `download_url`로 새 탭을 열거나 현재 위치를 이동해요.
  인증 완료 후 사용자가 파일을 직접 업로드하거나 별도 다운로드 버튼을 다시 누르는 단계는 이 클라이언트 경로에 없어요.
- 이 코드는 사용자 인증 후 사이트가 다운로드로 이어가는 흐름의 근거예요.
  trss가 그 파일을 받아 영상 옆에 자동 배치할 수 있다는 실행 증거는 아니에요.

2026-09-26에 관리형 Chromium에서 다운로드 카드를 누르자 Turnstile의 `Verify you are human` 체크박스가 표시됐어요.
자동으로 인증을 처리하지 않고, 사용자가 직접 조작할 수 있는 Chrome을 OMP relay로 연결해 정상 인증 이후를 관찰했어요.
OMP relay는 이번 검증용 연결 도구이며 제품의 필수 의존성으로 선택한 것이 아니에요.

사용자의 직접 인증 후 `/file/<id>/token`이 HTTP 200으로 `download_url`과 `expires_in: 60`을 반환했어요.
발급 약 3.7초 뒤 사용자 다운로드 폴더에 저장된 `The Insipid Prince's Furtive Grab for the Throne - s01e12.zip`을 같은 컴퓨터의 프로그램에서 읽었어요.
ZIP 크기는 14,245바이트이고 CRC 검사를 통과했으며, 내부에는 47,068바이트의 `The Insipid Prince's Furtive Grab for the Throne - s01e12.ko.ass` 한 개가 있었어요.
ASS의 `[Script Info]`, `[Events]`, Style 10행과 Dialogue 497행을 확인했어요.
다운로드된 사용자 파일은 이동·삭제하지 않았고, 검증용 브라우저 연결과 응답 기록을 해제했어요.
서명 URL이나 인증 토큰은 저장소에 기록하지 않았어요.

추가 파일 요청은 URL 발급 92초 뒤에 수행돼 HTTP 403과 HTML 오류 페이지를 받았어요.
서버가 안내한 60초 유효기간 밖에서 수행한 요청이므로, 이 403을 정상 다운로드 실패나 유효한 URL의 세션·IP 종속성에 대한 증거로 사용하지 않아요.
정상 브라우저 다운로드는 이미 완료됐으며, 유효기간 내 별도 HTTP 클라이언트의 수신은 미검증이에요.

이번 실험은 사용자 인증 후 사이트가 다운로드를 이어가고 같은 컴퓨터의 프로그램이 실제 자막 바이트를 읽을 수 있음을 보여줘요.
relay에서 다운로드 경로를 지정한 연결은 도구의 `Browser target is not found` 오류로 실패했지만, 경로 지정을 빼면 연결됐고 Chrome의 실제 저장 파일로 수신을 확인했어요.
이 도구 한계를 제품 자체의 파일 수신 불가로 해석하지 않아요.
이 개인 Chrome 실험에서는 사용자 브라우저에서 별도 trss 서버로의 전달과 최종 자동 배치를 검증하지 않았어요.
서버 전용 브라우저의 원격 인증 경로는 아래 별도 실험에서 확인하며, 사용자가 파일을 옮기거나 업로드하는 방식으로 자동 배치 요구를 대체하지 않아요.

### 서버 브라우저 임시 검증

서버 전용 브라우저와 원격 인증 화면을 우선하는 방향으로 타당성을 확인했어요.
서버 파일 수신까지 확인한 뒤 제품의 인증 운영 방식도 서버 브라우저로 선택했으며, 결정과 대안의 비교는 [인증 운영 ADR](../adr/0002-server-browser-subtitle-authentication.md)에 기록했어요.
원격 웹 화면에서 사람이 인증한 뒤 파일이 서버 측 저장소로 내려오는지 확인한 결과, Selenium 실행은 실패했지만 일반 Chromium 직접 연결은 성공했어요.

기존 trss 코드·설정·의존성은 바꾸지 않고 `.scratch/server-auth-browser/prototype`에 격리된 임시 실행물을 구성했어요.
공식 `selenium/standalone-chromium` 이미지를 digest `sha256:08fd293648e126275782c616a61f4ee1d90cf413b1972ebc35dbd054d6789f55`로 고정해 사용해요.
검증에 사용한 환경은 Grid 4.49.0과 Chromium 152.0이며, 실행 시 원격 화면과 제어 포트는 각각 `127.0.0.1:17900`, `127.0.0.1:14444`에만 바인딩했어요.
브라우저 프로필은 컨테이너 안에 두고 다운로드 디렉터리만 임시 실행 디렉터리에 연결해요.
Grid 준비 응답, 로컬 전용 포트 바인딩, 서버 브라우저의 게시물 로드와 정상 다운로드 카드 클릭을 확인했어요.
서버 브라우저 스크린샷에 `Verify you are human` 체크박스가 표시됐고, 다운로드 검사 결과는 대기 파일·완료 파일·오류 모두 없는 상태였어요.
사용자가 원격 화면에서 직접 인증했지만 `verification failed`가 표시됐다고 보고했어요.
기존 브라우저 로그에서 Turnstile `600010`과 사이트의 `Turnstile timed out after error: 600010`을 확인했고, 서버 다운로드 폴더는 대기 파일과 완료 파일 모두 없는 상태였어요.
같은 설정의 인증을 다시 시도해 실패를 재현하지 않았어요.

[Cloudflare 오류 코드 문서](https://developers.cloudflare.com/turnstile/troubleshooting/client-side-errors/error-codes/)는 `600*`를 봇 행동이 감지된 일반 인증 실패로 분류해요.
이 코드만으로 WebDriver 연결, 새 프로필, 브라우저 버전 등 어느 차이가 원인인지 특정할 수는 없어요.
이번 결과는 Selenium 기반의 이 서버 브라우저 구성에서 실패했다는 증거이며, 원격 브라우저 방식 전체가 불가능하다는 증거는 아니에요.
개인 Chrome에서 성공한 결과와 구분하고, 브라우저 속성 위장이나 인증 우회로 실패를 숨기지 않아요.

실패한 Selenium 실험의 WebDriver 세션을 종료하고 컨테이너를 정지한 뒤, 다음 비교를 위해 같은 이미지의 컨테이너를 다시 구성했어요.
제품 코드는 변경하지 않았어요.

#### 일반 Chromium 직접 연결 비교

서버가 브라우저의 페이지 열기와 다운로드 시작을 처리하고, 다운로드 과정에서 사람이 할 일은 CAPTCHA에 한정하는 흐름을 검증했어요.
기존 자막 후보 선택과 교체 승인 정책을 없애는 변경은 아니에요.

같은 Chromium 152 이미지에서 WebDriver 세션을 생성하지 않고 브라우저를 직접 실행한 다음 CDP로 연결했어요.
별도의 임시 프로필을 사용하며, 브라우저 속성 위장이나 인증 우회 스크립트는 넣지 않았어요.
CDP 제어 포트는 `127.0.0.1:19222`에만 공개하고, 컨테이너 안의 작은 TCP 전달기로 Chromium의 루프백 디버깅 포트에 연결해요.
원격 화면은 기존 `127.0.0.1:17900`을 사용해요.

CDP 연결과 서버 다운로드 경로 `/home/seluser/Downloads` 설정, erulabo 게시물 열기, 정상 다운로드 카드 클릭을 확인했어요.
원격 화면에 CAPTCHA를 표시한 뒤 사용자가 직접 인증했고, 서버 다운로드 폴더에서 실제 파일을 읽었어요.
다운로드 URL을 따로 전달받아 재요청하지 않고, 같은 브라우저가 서버에 저장한 파일을 검사했어요.

- 받은 파일은 `The Insipid Prince's Furtive Grab for the Throne - s01e12.zip`이며 14,245바이트예요.
- ZIP 안에는 `The Insipid Prince's Furtive Grab for the Throne - s01e12.ko.ass` 한 개가 있고, 47,068바이트이며 CRC 검사를 통과했어요.
- UTF-8 ASS의 `[Events]`와 Dialogue 497행을 확인했어요.
- 대기 중인 다운로드와 파일 검사 오류는 없었어요.

이 결과는 해당 표본에서 CAPTCHA 외에 수동 파일 다운로드·업로드·이동 없이 서버 수신이 가능함을 보여줘요.
두 실행 구성의 차이 중 무엇이 인증 결과를 바꿨는지는 분리해 입증하지 않았으며, 지속적인 성공이나 다른 출처·배포 환경으로 일반화하지 않아요.
검증 환경은 같은 호스트의 격리된 컨테이너와 로컬 원격 화면이며, 실제 LAN·VPN 접속과 trss의 압축 해제·회차 연결·최종 배치는 검증하지 않았어요.
관찰 연결을 해제하고 컨테이너를 중지했어요.
사용자가 로컬 보관을 선택해 실행물·받은 표본·중지된 컨테이너를 남겼으며, 제품 코드나 원격 저장소에는 포함하지 않았어요.

### 재생기 파일명과 폰트 호환 근거

파일 이름의 기본 표시와 재생기의 기본 트랙 선택을 분리해서 검토해요.
아래는 문서·소스 확인 결과이며, 사용자 기기에서 실행한 재생 시험은 아니에요.

- [Infuse 외부 자막 안내](https://support.firecore.com/hc/en-us/articles/215090967-Using-Subtitles)는 영상과 같은 폴더의 동일 이름 자막과 `영상-en.srt` 같은 언어별 이름을 설명하며, UPnP·DLNA 연결의 외부 자막은 지원하지 않는다고 명시해요.
  [설정 안내](https://support.firecore.com/hc/en-us/articles/360015608854-Settings-Overview)의 언어·`default` 트랙 태그 선택 설명은 외부 파일명의 `.default`를 태그로 해석한다는 근거가 아니에요.
  같은 언어의 여러 외부 형식 사이 우선순위와 임의 접미사의 공통 인식은 확인하지 못했어요.
- IINA `v1.4.4`의 [AutoFileMatcher](https://github.com/iina/iina/blob/v1.4.4/iina/AutoFileMatcher.swift)는 파일 경로로 접근하는 영상의 주변 자막을 자체적으로 찾고, `subAutoLoadPriorityString`에 설정한 문자열이 들어 있는 일치 자막의 순서를 앞당겨요.
  [Preference](https://github.com/iina/iina/blob/v1.4.4/iina/Preference.swift)의 해당 기본값은 빈 문자열이므로 `.default`라는 이름 자체를 기본 지시자로 가정할 수는 없지만, 사용자 우선 문자열 설정에 연결하는 방안은 근거가 있어요.
  [PlayerCore](https://github.com/iina/iina/blob/v1.4.4/iina/PlayerCore.swift)는 일치 자막을 불러온 뒤 자막 트랙 1을 선택하므로, 내장 트랙·사용자 설정·실제 버전을 포함한 최종 선택은 별도 확인이 필요해요.
- [팟플레이어 공식 변경 이력](https://t1.kakaocdn.net/potplayer/PotPlayer/v4/Update2/Update.html)은 선호 자막 언어, 내장·외부 자막 우선순위와 이전 스트림 선택 기억 기능을 설명해요.
  이 기록만으로 외부 파일명의 `.default` 해석이나 같은 언어의 ASS·SRT·SMI 사이 선택 순서를 확정하지 않아요.

폰트를 자막 옆에 두는 것만으로 세 재생기에서 자동 사용하는 공통 규칙은 확인하지 못했어요.
[mpv 문서](https://mpv.io/manual/stable/#options-sub-fonts-dir)는 전용 폰트 디렉터리 `sub-fonts-dir`를 제공하지만, 그 기본 경로를 IINA의 실제 유효 설정으로 단정하지 않아요.
[Infuse 담당자의 과거 안내](https://community.firecore.com/t/subtitle-font-customization/36224/2)는 시스템 폰트와 iOS·tvOS의 차이를 설명하며, 이를 현재 모든 Apple 기기의 동작 보장으로 사용하지 않아요.
팟플레이어의 폰트 처리·libass 출력 관련 변경 이력도 인접한 폰트 파일 자동 검색의 근거와 구분해요.
`.forced`는 일반적인 기본 자막 표시와 의미가 다르므로, 기본 선택을 유도하려고 그 이름을 대신 사용하는 안은 취하지 않아요.

## 미해결 사항

- Infuse·팟플레이어 등 실제 재생 환경에서 숨김 보관 폴더의 검색 제외와 폰트 활용을 검증해야 해요.
  다른 언어·릴리스·용도 선택과 추가 자막 형식의 지원 범위도 구체화해야 해요.
- 교체 비교와 trss 페이지 내부의 직접 인증 화면은 요구에 포함하지만 아직 구현·통합 검증하지 않았어요.
- 내부 저장 방식과 YAML 스키마는 이후 구현 설계에서 구체화해요.
- 실제 배포 환경에서 원격 화면과 브라우저 제어 경로가 기존 접근 보호를 우회하지 않는지 확인해야 해요.
- erulabo, Drive 개별 파일·묶음, Tistory 일반 첨부, WinPNG 복원·개별 수신, Naver HTTP 첨부의 표본 확인을 완료했어요.
  각 출처의 미검증 경로는 위 관찰 결과에 남겨두었으며, 모든 출처의 실제 trss 자동 배치와 사용자 배포 환경 동작은 아직 검증하지 않았어요.
- 외부 알림 채널은 필수 범위 밖에 두고 구체화를 보류해요.
- 같은 회차 중복 영상은 드문 경우로 두고 세부 처리를 보류해요.

조사한 공개 경로는 일반 첨부 링크뿐 아니라 Drive 미리보기와 브라우저 내 WinPNG 해석까지 포함하므로, 하나의 링크 추출 방식으로 모두 처리된다고 가정하지 않아요.
메타데이터가 있다는 사실만으로 파일 다운로드나 올바른 영상 연결까지 가능하다고 판단하지 않아요.
